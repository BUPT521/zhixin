# 知新 · 应用工程

一个懂你的学习搭子，Flutter + SQLite 单机应用。产品定义见 [00](../docs/00-产品定义.md)，数据结构见 [01](../docs/01-ER数据模型.md)，页面与验收见 [02](../docs/02-产品与交互.md)。

## 运行

```bash
flutter pub get
flutter run                 # 接一台 Android 设备或模拟器
flutter build apk --debug   # 出调试包
```

改界面或者逻辑时用热重载，不必每次出包再装到手机。`flutter run` 连上设备之后，改完代码在它的会话里按 `r`，一两秒后新代码就在设备上生效，按 `R` 热重启；模拟器与真机都支持，只有改了原生配置或者新增插件时才需要重新构建安装。

```powershell
pwsh tool/dev.ps1           # 没有设备时先启动第一台 AVD，再执行 flutter run
```

`dev.ps1` 先看 `adb devices` 里有没有已经连上的设备，没有就用 `emulator -list-avds` 里的第一台 AVD 启动模拟器，等到开机完成之后执行 `flutter run`。`-Avd` 指定 AVD，`-Device` 指定设备序列号，`-TimeoutSeconds` 调整等待开机的时间。模拟器单独起进程，脚本退出之后它仍然留着，下一次直接连上。

模拟器按物理像素决定窗口大小、按逻辑像素决定位置，在 Windows 缩放 200% 的屏幕上会开到屏幕上方之外，标题栏拖不到。窗口超出屏幕时，脚本按工作区把它收到右下角，宽高保持 1080:2400 的比例，右边留 64 逻辑像素、下边贴着工作区；窗口本来放得下就不动，`-NoFit` 关掉这一步。

模拟器上的相机是虚拟场景，语音识别走系统服务，数据库、Keystore 与界面行为与手机一致。要验证更接近真实使用的效果，用 USB 连接手机并打开 USB 调试，Android 11 以上也可以用无线调试配对，`adb devices` 能列出之后直接执行 `flutter run`。

Windows 本机跑 `flutter test` 时，zvec 的实现需要一个本机的 C 库：从 zvec 的 GitHub Releases 下载 0.8.0 版本的 `zvec-sdk-windows-amd64.zip`，核对 SHA-256 为 `7fc16b1bf575d3300f4ae4728f09a6a096b67025d508c350c16302c665ccbbe8`，解压后把 `ZVEC_LIBRARY_PATH` 指向 `<解压目录>\lib\zvec_c_api.dll`，再把同一个 `lib` 目录加进 `PATH`，因为 `zvec.dll`、`zvec_core.dll` 与 `zvec_ailego.dll` 都在这个目录里。没有设置这个变量时，索引契约测试与后台 isolate 的用例会跳过并打印原因；CI 的 Linux 任务会下载并设置好，不受影响。

最低 Android 11（API 30），只出 arm64。构建需要 JDK 21 与 Android SDK 36；CI 的版本固定在 [ci.yml](../.github/workflows/ci.yml)。

## 检查

```bash
dart format --output=none --set-exit-if-changed lib test
flutter analyze
flutter test
```

CI 跑的就是这三条。测试用 drift 的内存库在 Dart VM 里执行同一套表结构，不必起模拟器；备份与恢复预检的只读副本用 `package:sqlite3` 打开，和执行器是同一个实现。语义索引的契约测试与后台 isolate 用例在 `ZVEC_LIBRARY_PATH` 没有设置时跳过并打印原因，CI 的 Linux 任务会设置这个变量。账号与云同步的用例用 `test/support/fake_server.dart` 的进程内假服务端走登录、刷新、备份、提交序列与附件的往返，不访问网络；服务端自己的行为由 `server/` 下的 Go 用例覆盖。

`ai/llm_client.dart` 是模型客户端的入口，只做导出：失败、取消与请求预算在 `ai/llm_failure.dart`，HTTP 收发与 SSE 读取在 `ai/llm_transport.dart`，Responses 的请求组装、流式事件解析与整段响应读取在 `ai/llm_protocol.dart`。`ai/ai_chat_service.dart` 按回答模式装配提示、工具和模型配置，`ai/llm_reply_reader.dart` 将增量或普通响应组装成单步结果，`ai/agent_loop.dart` 按调用顺序执行工具，并将助手消息和配对结果一起追加到续接上下文。工具规格与提案解析位于 `ai/buddy_tools.dart`，工具执行与批量调度位于 `ai/agent_tools.dart`，单步输出上限位于 `ai/llm_config.dart`，作答提问与学习步骤提示在 `ai/buddy_prompts.dart`。

提示词的规则、上下文说明、请求文本与工具说明在 `assets/prompts/`，按 `## 键名` 分段，`pubspec.yaml` 注册为 asset；`platform/prompt_assets.dart` 在启动时读取一次，`ai/prompt_text.dart` 负责解析与取段，`ai/buddy_prompt_builder.dart` 只按请求类型选取段落并替换占位符，`ai/buddy_tools.dart`、`ai/material_page_tool.dart` 与 `ai/search_sources_tool.dart` 的工具说明和参数说明也从同一份资源读取，改文案不需要改 Dart 代码。测试在 `test/flutter_test_config.dart` 里先读取同一份文本，提示词输出与写在代码里时一致；回答质量的第一版评测样例在 `test/evaluation/answer_quality_cases.dart`，覆盖 V1、V3、V6、V11 的提示词条件，真实模型对照按 [02 第 8.4 节](../docs/02-产品与交互.md#84-回答质量对照评测) 记录。

`application/service_runtime.dart` 是服务共用的运行环境：时间口径、数据代次、附件目录与模型调用失败的本机记录。应用根只装配一次，保存每日截止小时、整库恢复与清空之后，服务读到的是新值，不必给每个服务各传一个闭包；测试从 `test/support/service_runtime.dart` 取同一份装配。

安排页的三个表单集中在 `plan_dialogs.dart`，讨论消息与引用展示位于 `discussion_message.dart`，周视图拆在 `plan_week_view.dart`。页面继续负责加载数据与执行用户操作，周视图只接收已加载的周数据，并把选周与点击交回页面。

### 下一阶段的模块化建议

建议先在现有 Flutter 工程内按业务职责收窄接口。`AppServices` 提供八组服务入口，`AppScope` 负责依赖装配、连接替换、时间口径刷新、数据代次与附件维护，仓库字段对页面不可见，整库恢复、导入、导出与恢复点操作已经下沉到 `data/backup/data_version_service.dart`，截止小时由 `application/time_policy_controller.dart` 统一缓存与刷新，撤销经应用层 `application/undo_service.dart` 收口，语义索引配置经 `application/embedding_settings.dart` 保存与应用。下一步的收益主要来自把读路径的失败表达继续往统一的结果类型收，以及把 `plan_page.dart` 的页签继续拆开（[ADR-0014](../docs/adr/0014-流式查询与版本通知.md) 的页面重读已经换成订阅）。

1. **安排页按事项与目标订阅读取。** `plan_page.dart` 处理页面订阅与页签切换，`PlanService.watchOverview` 读取未完成事项、已完成数量与目标。事项页按页读取已完成事项，系统学习计划从首页入口进入。布局需求与验收见 [02](../docs/02-产品与交互.md)。
2. **随后收拢讨论与作答的回答入口。** `BuddyTimeline` 已经共用消息与回执展示，讨论和作答仍分别维护模型请求、失败兜底与写回流程，可以先共用回答请求的取消、失败分类和数据代次检查，同时让两个用例继续各自保存讨论消息、作答帮助与判断。`LlmClient` 的请求格式与流式解码适合按协议整理，`AgentLoop` 继续统一控制整轮预算、重试和工具调用顺序；这一批以无模型可用、停止生成、工具续接及恢复后拒绝旧回答为验收场景。
3. **给查找和引用建立明确入口。** 记录页继续使用 `SearchService` 的筛选与分页，模型上下文通过 `ContextService` 取得限定范围的材料、历史与记忆；两处共享来源标识、原文校验和索引失效规则。材料更正、改归属、撤销与恢复之后，测试应验证旧命中退出检索，同时验证独立复查期间的旧答案仍受访问限制。
4. **在业务接口可独立测试后收窄存储接口。** 应用根只承担装配，版本服务集中持有连接切换、提交回执与恢复后的数据刷新，业务用例通过所属仓库和命令事务写入。建库以 `lib/data/db/drift/tables.dart` 的表类为唯一结构来源，索引也声明在表类上，恢复预检与文档测试都对照实际建库结果；变更时同时核对外键、版本触发器、附件哈希与恢复回滚。

[`architecture_test.dart`](test/architecture_test.dart) 核对事项与目标页签的依赖方向。独立 Dart package 会增加公开 API、代码生成与测试的维护成本，等某部分有第二个使用方或独立发布需求时再评估。首批的任务指令随首批完成已经删除，要求与结论以本节为准。

## 数据

- 业务表主键是 UUIDv7 文本，由仓库在插入前用 `lib/domain/rules/uuid_v7.dart` 的 `newUuidV7()` 生成：前 48 位是毫秒时间戳，同一毫秒内的 12 位序号递增，按主键排序与按写入顺序一致，两台设备各自生成的标识也不会相撞；外键列、版本明细的 `row_key`、撤销与恢复的定位、检查点投影与两类数据包都按这个文本标识，`profile` 仍固定为 1，提交编号、检查点编号与恢复点编号仍是整数（[ADR-0018](../docs/adr/0018-业务表主键改用UUIDv7.md)）。
- 数据库是应用私有目录里的一个 SQLite 文件，业务表、提交历史与附件对象都在同一个库里，表清单、字段与当前版本见 [01](../docs/01-ER数据模型.md)。库文件由 drift 的 `NativeDatabase` 打开，SQLite 使用随包的 `sqlite3`；表结构在 `lib/data/db/drift/tables.dart`，生成文件入库，改表后要跑 `dart run build_runner build`。一条讨论就是一条学习记录，题目由首条用户消息与图片派生，作答直接挂在记录上；事项只保存一段说明，系统学习的步骤就是事项，计划只保存材料范围、顺序与继续位置。备份、恢复校验与版本包里的库副本同样用 `sqlite3` 打开，不再经过 sqflite（[ADR-0012](../docs/adr/0012-结束sqflite与drift并存.md)）。
- 仓库的常规查询和写入在 `lib/data/db/drift/queries/` 中定义，一张表一个文件，在生成时检查表名、列名、参数和可空性。生成读取在共享访问获准后选择连接，生成写入复用命令事务。执行器只保留“执行语句、读回行、开事务”三件事与生成查询两个方法，按表名拼条件的旧接口已经删除。检索里四类字面命中的整段查询仍用手写 SQL（`instr` 与命中位置的子串判断生成查询表达不了；范围规则与存在性判断共用一个表达式），其余查询都在 `.drift` 文件里，字面检索的取舍见 [ADR-0024](../docs/adr/0024-关键词检索并入zvec.md)；版本引擎、备份、恢复校验与撤销按 [ADR-0011](../docs/adr/0011-仓库查询改用drift生成代码.md) 继续使用原生 SQL，口径收敛见 [ADR-0021](../docs/adr/0021-实现口径统一与重构残留清理.md)。
- 同一个执行器上只开一个 `AppDatabase`：真机由 `openZhixinDatabase` 打开一次，恢复预检另开副本时用独立的执行器，结构元数据复用 `schemaMetadata` 这一个实例、不打开连接。drift 自带的“开了多个库”告警按运行时类型计数，多设备用例与没来得及关的库都会让它触发，测试里改由 `test/support/drift_warning_guard.dart` 按执行器判断，同一个执行器上出现第二个库直接让用例失败。
- 表结构与索引只写在 `lib/data/db/drift/tables.dart`（索引用 `@TableIndex`），`schema.dart` 不再有手写 DDL，只提供从表类派生的表名、必需列与索引名，恢复预检与文档测试都对照实际建库结果。值集合只在表类旁维护一份常量，建库 CHECK 由它生成。会话入口、会话状态、事项来源、材料种类与记忆的来源和状态在领域层是枚举，库里存字符串，读到未知值时回落 `unknown` 而不是顶成某个真实取值。
- 关键词检索并入 zvec 索引，业务库不再有 FTS5 表、关键词触发器与 `MATCH` 查询。索引拆成两个 collection：文本 collection 的 schema 固定，片段的正文写进 `content` 字段并建全文索引，只发全文查询；向量 collection 只存向量、来源键、来源版本、片段号、文本哈希与预过滤字段，不存正文。检索时两路各取候选，由应用层按名次倒数融合（RRF，平滑常数 60），向量 collection 不存正文，命中之后按当前记录重新计算摘要。没有配置嵌入模型时只有文本 collection，关键词检索照常可用；配置之后加上向量 collection，换模型只重建这一份（[ADR-0024](../docs/adr/0024-关键词检索并入zvec.md)、[ADR-0030](../docs/adr/0030-服务端不建检索索引.md)）。字面命中仍由业务库的 `instr` 按原字符匹配。
- 索引保存在应用私有目录的 `vector_index/` 下：文本 collection 在 `text/`，向量 collection 在 `vector/`，各自一个 collection 目录与一个同名状态文件，状态文件记录模型键、维度、文本处理版本、数据代次、刷新统计与可发送范围签名；向量这一份按嵌入模型键分目录，模型、维度或文本处理版本改变时换目录并删除旧目录，正文不重写。来源表有净变化的提交之后等 3 秒补建，启动、整版恢复与导入之后也补建；检索索引“已处理到的提交编号”记在库里的 `revision_cursor` 非阻塞位置（`search.index`），不再写进两份状态文件，刷新只读该位置之后 `revision_change` 涉及的材料页、消息与作答，删除行按旧行还原来源键、改动行按主键读回当前来源，只重写与重算这些来源，正文与向量两份 collection 都写成功才推进位置，刷新结束时再比一次 `HEAD`，期间又有提交时自动补跑一次。数据代次（`HEAD` 所在提交的 `generation`）变化、历史裁剪或可发送范围变化时把位置归零并退回全量扫描，普通写入不推进代次，只补变化的来源；同一版本内产生的旧状态文件仍然能读，里面多出来的提交编号在解析时忽略。索引里的向量与片段都能从业务库重建，结构损坏时删除并重建，界面不弹窗，只在本机诊断记录里留一条 `semantic_index` 类的说明；文本 collection 打不开或被占用时关键词与语义检索一起按不可用处理，向量 collection 打不开时关键词一路照常可用，字面命中不受影响；清空全部记录时先释放两份句柄再删除 `vector_index/`，索引不进入数据包（[ADR-0022](../docs/adr/0022-语义索引改用zvec.md)、[ADR-0030](../docs/adr/0030-服务端不建检索索引.md)）。旧的单 collection 目录不再读取，随清空本机数据一起删除，开发阶段不写迁移。
- 记忆召回另用一个纯文本的 collection，目录是应用私有目录下的 `memory_index/`，与语义索引目录同级：每次召回先按 `memory` 表同步有效且未过期的条目，正文或更新时间变了才重写，删除与过期的一并清理，再以来源键列表把排序限制在本次候选之内；只取全文一路，不调用嵌入来源。记忆索引读到哪里也登记在 `revision_cursor` 的非阻塞位置（`memory.index`），只用于记录进度，落后不会漏掉内容；索引打不开时退回原来的二元组排序，索引不进数据包与版本库备份，清空全部记录时随 `vector_index/` 一起删除（[ADR-0026](../docs/adr/0026-记忆召回改用zvec全文索引.md)）。
- 向量缓存按账号保存在服务端，索引仍只在本机。索引刷新先把同一段正文按 SHA-256 归并，再向知新服务批量查找已经算过的向量（`POST /v1/llm/embeddings/lookup`，返回小端序 FP16 的 base64，解码后按现有方式归一化），只对未命中的片段发嵌入请求，因此换机、索引重建与在模型之间来回切换不必重算已经算过的部分。查找只对知新服务的来源发出，本机哈希没有这个接口，旧服务端返回 404 之后本次会话不再尝试，网络失败与 5xx 退回整批嵌入，401、403 与 429 按来源不可用停下本次更新。写缓存只在登录且自动同步开启时声明，嵌入请求带 `X-Zhixin-Embedding-Cache: 1` 之后服务端才保存，检索查询的嵌入不带这个头（[ADR-0030](../docs/adr/0030-服务端不建检索索引.md)）。
- 讨论按记录标识打开，可以没有目标归属，也可以只有图片消息；图片按内容哈希分块存入同一个库的 `asset_object` 与 `asset_chunk`，消息只保存哈希引用，界面读取时把临时文件补回 `question_images/`，同一个哈希只保存一份。
- 材料按页保存，讨论可以带入材料与页码；回答里的引用先按页码取回原文、逐字核对，对不上的标为未核实，用户纠正后旧摘录不再作为依据。也可以直接导入 .docx：原文件按内容哈希与正文片段在同一条提交里写入，片段按 1 起编号，引用显示“第 N 个片段”，这类材料不能手工添加一页。添加一页遇到已有页码时拒绝写入，不覆盖已经校对过的原文；用户明确更正一页时改写内容，修改前后的整行随这次提交留在历史里，保存后提示条可以撤销，材料详情按页列出更正记录。
- 系统学习按材料范围保存步骤与继续位置，每一步是学习事项，完成状态在系统学习与事项详情共用。
- 学习判断只保存来源、结论与依据：`assessment(kind=model)` 是模型判断，`assessment(kind=user)` 是用户填写的核对依据，两者都不标记是否核对；用户自评由作答记录中的帮助、独立性与延迟情况推出，独立性只采信用户的三选一，未选择时记为未说明，对错可以暂不判断；`attempt.delayed` 区分当场完成与隔一段时间后重做。
- 普通求助只写讨论、记忆与下一步建议；用户可以选择目标，随后保存待办或立即开始。
- 题目不关联知识点；一次作答的对错由用户选择，可以暂不判断，应用内帮助、独立性选择与提交时刻分别记录。
- 本地库只认 01 写明的当前版本。打开时版本不一致就清空旧表并按当前结构重建：开发期只有可丢弃的测试数据，不保留迁移函数。导出包也只接受同一版本，其他版本的包在替换前拒绝。原因与代价见 [ADR-0002](../docs/adr/0002-本地数据不做迁移.md)。
- 每次业务写入形成一条提交，当前数据对应本机 `HEAD`。`GuardedDatabase` 把独立写入与命令事务统一收进同一个入口，触发器采集新增、修改、删除与外键级联，提交时按表和主键合并为净变化；业务行、附件分块、版本明细与 `HEAD` 在同一个事务提交，异常时一起回滚。版本化表拒绝 `REPLACE`，新增表必须登记版本分类；提交身份由 `uid` 表示，界面在动作开始时生成一次、同一次动作重试时沿用，写入层按 `revision_commit.uid` 的唯一索引先查，已存在就返回原提交，推送与服务端去重也按它判断，不再有两分钟窗口（[ADR-0053](../docs/adr/0053-标识按身份顺序指纹分工并收拢提交标识.md)），界面回执指向所属提交。撤销提交可以再撤销，含义是重做：沿 `reverted_commit_id` 的回指链判断层数，重做按原提交的变化正向写回、回执不恢复，提交类型仍是 `undo`（[ADR-0044](../docs/adr/0044-撤销提交可以再撤销.md)）。查看、比较、命名、撤销与重做都从最近的检查点重建，恢复优先按保留的净变化反向写入有差异的行（增量恢复），只在起点被裁掉或明细不完整时重建两份投影，恢复与导入推进数据代次，单项撤销只限当前代次，并核对相关字段在目标提交之后是否又被修改。记忆页的新增、修改与删除同样形成提交，提示条可以撤销；数据版本页与撤销入口共用同一套结构判断，不能撤销或重做的提交在列表里直接禁用并写出原因。数据版本页有“检查数据完整性”入口，一次跑完“从最近的检查点把变更明细重放到 `HEAD`、重放摘要与 `HEAD` 记录及按当前表重算的摘要比对”，再核对附件，结果写明“通过”或者第几处不一致与处理建议；远端提交在列表里写“来自另一台设备 · 设备标识前 8 位 · 某时某分”，时间取 `authored_at`、没有时退回 `created_at`，本机提交不写来源。设置页的每日截止小时保存成一条提交，保存与撤销后应用根重新读取设置，设置页与归属日口径立即使用新值。
- 页面数据跟随写入更新：版本引擎在提交收尾把这次净变化涉及的表（连带 `revision_commit`、`revision_change`、`revision_state`）交给 `GuardedDatabase`，事务提交成功之后、独占区释放之前发布一次，回滚的写入与没有净变化的写入不发布。应用服务经 `ServiceRuntime.watch` 给出整屏读法，`GuardedDatabase.watch` 用 `DatabaseGate` 的共享访问重跑读取并只回填最新一次结果；整库恢复、清空、导入与单项撤销之后按全部表补发一次，换连接之后订阅继续有效。通知按表发送，一张表被写入时读它的页面各重读一次，粒度与代价见 [ADR-0014](../docs/adr/0014-流式查询与版本通知.md)。
- 暂停目标的操作形成一条可撤销的提交。历史裁剪或清理之后，消息里指向已删除提交的回执去掉提交编号，清理作为一条普通提交写入，没有失效回执时不形成提交。历史裁剪前先重建校验新基线；留存按时间优先：最近 14 天的提交全部保留，更早的按 256 MB 预算裁剪，保留天数可以在数据版本页调整；提交超过 500 条或历史字节超过 256 MB 时，自动裁剪在空闲检查点之后触发，与手动裁剪共用同一套边界。
- 导出分为两类：当前数据包只含业务投影与仍被引用的附件，导入时追加一条提交；版本库备份是 `VACUUM INTO` 生成的整库快照，包含 `HEAD`、历史、命名版本与附件，恢复前先校验完整性、`HEAD`、重建结果与附件哈希，再走现有的临时副本校验与连接替换流程。两个恢复入口先预检再确认：本机版本恢复列出新增、修改与删除的数量，数据包恢复列出包内 `HEAD`、提交与命名版本数以及当前库规模；整库恢复在替换之前把当前状态保存成一份版本库备份，写入应用私有目录的 `restore_points/`，恢复成功后保留，数据版本页可以回到恢复前，最多保留最近 5 份，恢复点写不出来时本次恢复不执行。两类数据包都排除诊断记录与密钥。导出与备份前按数据库引用核对附件，缺图或哈希不符时中止并列出缺项；版本库恢复前核对完整性、`HEAD`、重建结果与检查点、变更明细和当前投影引用的附件。备份版本库与上传云端备份之前还会自动跑一次完整性检查，发现不一致时先说明第几处不一致与处理建议，再由用户决定取消还是继续，继续不会改动本机数据，但备份里可能缺内容。
- 备份、旧格式数据包与恢复点原先各写一遍校验：现在共用一个暂存库校验（结构版本、对象白名单、`integrity_check`、外键与必需列），旧格式包与版本库备份都走它，完整性检查统一用 `integrity_check`，不再手抄业务查询。

## 界面


界面组件与主题由 Forui 0.28.0 提供，底栏四栏与详情页共用 `ZhixinHeader`、内容区最大宽度及页面边距，详情页使用 `DetailScaffold`，滚动区域通过 `ZhixinSpace.pageInsets` 设定边距。带页签的列表页（记录、安排）共用 `TabbedPageFrame`：标题栏固定为页名，页签上方放一条搜索入口，页签下面是当前页签的节标题与列表，新建与导入动作放在节标题右侧，标题栏只放刷新、语义索引这类整页动作。底栏页面（现在、记录、安排、我的）使用 `TabScaffold`：它们外面已经有一层带底栏的 `FScaffold`（见 `home_shell.dart`），键盘弹出时由它让出一次键盘高度，页面自己的骨架不再按键盘缩放，否则内容会被扣掉两个键盘高度，输入区与发送按钮被裁掉，键盘上方只剩一条空白。组件的字号、颜色、留白和圆角从 `context.zhixin` 读取，Forui、Markdown 与 Material 控件的色值都由 `ui/theme.dart` 生成；按钮、输入框、选择框、列表项、卡片与折叠面板的默认样式也在这份 Forui 主题里配一次，开关的轨道、圆钮与禁用态在 Material 主题里配一次，页面不必各写一遍。页面文字不指定字族，中文与西文都跟随手机系统字体，Forui 的每一档文字也在主题里逐档去掉字族，因为指定自定义字族时中文会回落到思源黑体、绕过厂商的系统字体，而且回退字重只有常规与粗体两档，中间的档位会被就近取成粗体，所以字重只保留常规与强调两档，字距取 0；只有时间与计数保留 Forui 自带 Inter 的等宽数字。浅色使用纯白页面与纯白卡片，深色使用纯黑页面与中性深灰卡片，深浅两套的页面、卡片、描边与文字都不带色相；描边分两类，卡片、列表项、分隔线、底栏、对话框与面板用浅的 `outlineVariant`，输入框、选择框、复选框与 outline 按钮用深一档的 `outline`。主色是蓝色，只出现在按钮、链接、选中态、开关与强调卡片上，底栏的选中指示块与标签底用主色浅底 `primarySoft`，草稿与需要留意的状态使用橙黄的提醒色。


按钮、输入框、列表、卡片与表单优先使用 Forui，对话框和短提示分别通过 `showZhixinDialog` 和 `showToast` 打开。开关统一用 `ZhixinSwitch`，即 Material 的开关，标签与说明排在左边，整行都可以按；只有开关、没有可见标签时传 `semanticsLabel` 给读屏一个名称。短提示固定在中下，底部为底栏导航让出高度，位置与留白在 [ui/theme.dart](lib/ui/theme.dart) 的 `zhixinToasterStyle` 里定一次，不随平台改变；停留时间按平台的输入方式分开，手机上 3 秒自动收起，桌面上保留 Forui 默认的 5 秒，带操作按钮的提示两边都停 5 秒。底部面板和日期时间选择器使用 Material，分别通过 `showZhixinSheet`、`showZhixinDatePicker` 与 `showZhixinTimePicker` 打开，样式由同一主题提供。筛选使用 `ZhixinChip`，互斥的视图切换使用 `ZhixinSegmented`，选中底色是一块，切换时按整条平移到新的一项，深色外观下取 `ZhixinColors.surfaceSelected`，比轨道亮一档；它的每一项按下去时由 `PressScale` 放大几个百分点，松开或切换之后回位，当前项再按不放大；放大只改绘制、不改版面，系统要求减少动态效果时按下与松开直接到终态。业务图标统一从 [Lucide 图标库](https://lucide.dev/icons/) 选取，通过 `FLucideIcons` 引用。

测试里单独构建页面时，外层要补 `FTheme`；页面里会弹提示的，还要补 `FToaster`。少了这两层，页面读不到主题，提示也找不到宿主。

动效与加载按 [动画流畅性优化方案](../docs/动画流畅性优化方案.md) 第 5 节执行，新增页面照下面五条写，不再另立一套：

1. 逐帧变化的透明度只用 `FadeTransition`，不用 `Opacity` 组件；逐帧位移的子树先包 `RepaintBoundary`，让动画只动合成层。`FadeIn`、`ExpandReveal`、`TabSlideStack` 与 `SlideSwap` 已经把这三件事做在组件里，页面直接用。
2. 动画期间不改布局：输入框聚焦、分段选中这类状态变化只插值颜色，边框宽度与字重固定，不让整块重新布局。
3. 切栏、切页签与推入页面时读取立刻发起，回填前调用 `context.afterTransition()`，结果等过渡结束再交给界面；已有数据时返回不重播淡入，也不显示转圈。
4. 常驻但不可见的内容一律包 `TickerMode(enabled: false)`；底栏与页内页签用 `TabSlideStack` 常驻，换周这类同一块位置换内容用 `SlideSwap`，切换只换显示，输入、筛选、滚动位置与 `MaterialList` 的状态因此不丢。底栏、页签与换周按整幅页宽滑入滑出，其余位移不超过 24 像素。底栏传入 `TabSlideStack.onSwipe` 之后还可以左右划动切换：拖动途中按手指位移换算进度，松手按划过的比例（约三分之一页宽）与同方向的滑动速度（300 逻辑像素每秒）决定切过去还是退回，页面里能横向滚动的内容先接走横拖；划到的那一栏由调用方把 `index` 换过去，组件不自己改。首次启动引导的三步也用这层划动，并通过 `canSwipeTo` 挡住还不能去的一步，没勾选同意时向前划不跟手。页内页签不接划动，只按 `ZhixinSegmented` 点击切换。
5. 页面路由的过渡在 `ThemeData.pageTransitionsTheme` 里配一次（Android 用系统的预测性返回，普通推入由框架淡入前推；iOS 与 macOS 保留系统滑回手势；桌面淡入加右推 24 像素），各页不再各写一套；减少动态效果时直接给终态。`MaterialPageRoute` 照常写，过渡由主题统一决定。

首读占位一律用 `ListSkeleton`（与卡片同高的静态块），页面不再用居中转圈：转圈只占一行，内容读完之后下方整体下移，页面跟着跳动。详情页在骨架期间保留标题栏，列表页按将要出现的卡片高度摆好灰条。一级界面切进来时已经在后台读过首屏的二级页面直接用结果，不再摆骨架。只有没有版面可占位的等待仍用 `PageLoading`，即应用启动、相机预览与照片解码三处：Forui 的圆形指示默认取正文字号，手机上只有 18，看上去只是一个图标，所以这里定成 36 的直径并取主色；按钮、列表行与照片上的指示仍用 `sm`、`xs`，大小跟着所在控件走。这类差异在 Forui 的样式里改，界面里的 Material 只保留底部面板、日期时间选择与开关三处，同一种“正在读取”因此只有一套组件。

页面之间的跳转统一经 [ui/navigation.dart](lib/ui/navigation.dart) 的一页一个函数打开，页面不互相 import，路由也只在这个文件里构造；`PlanPage` 的底栏入口与 `PlanPage.detail` 详情入口分开，详情不参与切栏。讨论页的标题栏放“开始作答”，状态行只排目标、材料、查找与一个更多操作菜单，一行放不下时换行；回答卡片已经写明本地规则并给出重新回答与模型设置入口时，页面不再重复一条同样内容的错误说明。忙碌指示用 `FProgress` 与按钮内 `FCircularProgress`，错误与失败说明统一用 `InlineNotice`（可带重试），表单字段的就地校验文字保留在字段旁。确认框统一经 `confirmZhixin` 与 `showZhixinAlert` 打开，按钮形状与取消文案不再由调用方各写一份。文案集中在 [ui/copy.dart](lib/ui/copy.dart)（角色名、页签名与空态句式），时钟与日期格式、设备标识的脱敏与文件大小的写法集中在 [ui/format.dart](lib/ui/format.dart)，间距与圆角从 `ZhixinSpace`、`ZhixinRadius` 取，竖直排列的两个条目之间留 `space.sm`，历史记录、更正记录与步骤这类逐行排列的列表里相邻两行留 `space.tight`，两张独立卡片的描边不贴在一起，画面过渡、按下反馈与展开收起的时长与曲线只从 [ui/motion.dart](lib/ui/motion.dart) 取，滚动到指定位置与等待预读的时长由调用处给出。输入防抖、卡片分隔线与一次性结果说明在 [ui/workspace_widgets.dart](lib/ui/workspace_widgets.dart)，查找页的分页与结果状态用 [ui/search_state.dart](lib/ui/search_state.dart) 的 `SearchState` 与 [application/paged_result.dart](lib/application/paged_result.dart) 的 `PagedResult`、`kSearchPageSize`。记录、安排、材料与记忆这类由数据层推送的列表统一用 [ui/live_view.dart](lib/ui/live_view.dart) 的 `LiveView` 订阅：写入、撤销、导入与换库之后的重读由数据层推送，页面不再在保存或跳转返回后自己重读（[ADR-0014](../docs/adr/0014-流式查询与版本通知.md)）；账号摘要与预读结果只读一次，由页面在读到时取用。读取没有完成时不提供下拉刷新这类手势：数据本来就跟着写入回来，手势重跑的是同一条读法，恢复交给内容区的 `InlineNotice` 与“重试”，已经显示的内容保持不动。插件页与人格页读的是不形成提交的 `app_meta`，仍用 [ui/data_version_watcher.dart](lib/ui/data_version_watcher.dart) 在整库恢复与清空之后重读。

一级界面切进来时，[application/prefetch_service.dart](lib/application/prefetch_service.dart) 在后台读它下面几个二级界面的首屏（[ADR-0033](../docs/adr/0033-一级界面预读二级页面首屏.md)）：记忆页与数据版本页各一屏，设置页的模型配置、账号、可选模型与索引概况，云端备份列表（只在登录之后），账号与云同步页的首屏（与“我的”的账号卡共用同一份账号、同步状态与额度），“这周能做什么”的当前周结果，语义索引设置，人格与插件页的 `app_meta`，以及记录查找与安排查找的范围选项。预读只在对应的一栏切进来之后开始，首页启动时不读这些内容；结果保留 5 分钟，页面打开时先用这一份结果，`LiveView` 的 `initial` 因此不必先摆骨架，随后按各页原来的读法继续订阅或刷新。设置、云端备份、账号与语义索引设置只取用一次，之后再打开按当前状态重新读。学习、讨论、材料详情、系统学习与事项详情按具体条目打开，进入一级界面时还不知道要打开哪一条，仍在打开时读。

## 外观

设置页的“深浅色”可以选跟随系统、浅色或深色，“主题色”可以在一行六个圆形色块里选蓝色、苔绿、紫、玫红、橙或石墨，两项选择都立即生效，不必重启。取值分别写在应用私有目录的 `theme_mode` 与 `theme_accent` 两个文件里，不随数据包导出或恢复：主题要在数据库打开之前的第一帧生效，外观也只是这台手机上的偏好；两个文件分开保存，换深浅色不影响选中的主题色，换主题色也不影响深浅色。主题色默认蓝色，文件缺失、内容为空或存下的名称不认识时都回到蓝色，读取与回退在 `ZhixinAccent.parse` 与 `ThemeAccentController.load` 里做。深色沿用浅色的颜色角色，只改底色的灰度、主色取值与强调色的明度；相机的取景与框选手柄压在图片上，保留黑白叠加层。

色板与主题在 [lib/ui/theme.dart](lib/ui/theme.dart) 这一个库里分成四个 part 文件：令牌在 `theme_tokens.dart`，主色家族与提醒色在 `theme_palette.dart`，Forui 与 Material 两套主题分别在 `theme_forui.dart` 与 `theme_material.dart`，页面仍只 import `theme.dart`。色板本身分成两部分：`_NeutralPalette` 是固定的中性色，深浅各一份，不随主题色改变；`ZhixinAccent` 给出六个主题色的浅色与深色主色，主色家族与提醒色由 `_palette` 按亮度与主题色派生。页面与组件读 `context.zhixin.colors`，不写死色值，也不缓存旧主题的 const 或 static 颜色；切换时 `foruiThemesFor` 与 `materialThemesFor` 给出该主题色的两套 Forui 与 Material 主题，MaterialApp 与 FTheme 随之重建，生成过的主题按“主题色加亮度”缓存，换回来时直接取。浅色的页面与卡片都是纯白，深色的页面是纯黑、卡片是中性深灰，页面、卡片、拔高的表面、描边与文字在任何主题色下都不带色相；分段控件选中项的底色另取 `surfaceSelected`，浅色是纯白、深色比轨道亮一档，切换时不会出现比轨道更暗的一块。浅色下卡片与页面同为白色，所有卡片、输入框、对话框与底部面板都带 1px 描边，相邻表面不会并成一片；开关关闭时的轨道取同一档描边色，浅色下在白色卡片上也能看出轨道，开启时换成主色。随主题色变的只有主色家族：主色用在按钮、链接、开关、选中指示、Markdown 链接与引用条上，主色浅底与容器用在下拉框、分段、标签和 Markdown 表头的底色上。六个主题色的浅色与深色主色依次是蓝色 `#2563EB`／`#5B9BFF`、苔绿 `#245C48`／`#6FCF97`、紫 `#7C3AED`／`#A78BFA`、玫红 `#BE185D`／`#F472B6`、橙 `#C2410C`／`#FB923C`、石墨 `#18181B`／`#E4E4E7`。

主色家族在 OKLCH 里派生，混色与调明度都保留主色的色相，换成别的主题色不会串到邻近的色相上。浅色下主色浅底取主色在白色上的 8%，主色容器取 15%，容器上的文字把主色压暗 0.10 的明度，压在主色上的文字是白色；深色下主色浅底取主色在黑色上的 15%、主色容器取 30%，明度都不低于 0.33，浅底在纯黑页面与深灰卡片上都分得出来，容器上的文字把主色提亮 0.10，压在主色上的文字把主色压暗 0.10，压暗之后不足 4.5:1 时继续压暗到够为止。石墨是无彩色，主色家族直接取抬高的表面、卡片与正文色，不按色相生成。提醒色默认琥珀 `#B45309`（深色 `#F0B070`），用在草稿与优先这类需要留意的状态上；主题色为橙时提醒色改用紫色 `#7C3AED`（深色 `#A78BFA`），避免草稿标签与主按钮同色，这条规则写在生成函数里，页面不判断。错误色只表示错误与危险操作，不随主题色改变。

`app/test/ui/theme_test.dart` 按六个主题色乘浅深两套核对：主按钮文字与容器文字压在主色和容器上不低于 4.5:1，主色作为文字压在页面与卡片上不低于 4.5:1，链接悬停与容器文字悬停留出下限，深色浅底在页面与卡片上分得出来，换主题色时中性色与错误色逐个不变，蓝色主题的色值与换主题色之前的基线逐项一致。Forui 的悬停、按下与禁用态由基色按明度与透明度派生，色相不变；Forui 的描边统一取输入框描边色，比卡片描边深一档；Material 开关关闭时的轨道取卡片描边色、开启时取主色，圆钮压在两种轨道上都分得出来。回答正文的 Markdown 与日期时间选择器读 Material 的色板，这个色板由同一份色板直接构造，不走 `ColorScheme.fromSeed`，表面与容器的色调不会被主色染色。

## 模型

客户端只有“知新服务”一种模型来源，即服务端的模型代理，模型设置提供模型名、上下文上限与图片开关；模型名默认 `zhixin-chat`，与后台配置的对外模型名一致，嵌入模型从服务端列表里选。对话固定走 OpenAI 的 Responses，地址由当前知新服务地址拼出 `/v1/llm` 再加 `/responses`，访问令牌代替 key，令牌过期时先刷新再重试；令牌与地址由 `lib/application/account_service.dart` 在每次请求前补进配置，不写进 Keystore，也不在发请求时保存，聊天与嵌入共用每日免费额度和购买积分，额度用完时按服务端给出的原因分别说明：免费额度与积分都用完、积分不足时给购买积分入口或等次日恢复，实例预算用完与余额正在同步时只说明稍后重试（[ADR-0071](../docs/adr/0071-核销只读已结算用量与额度用完的原因.md)、[ADR-0073](../docs/adr/0073-余额副本的快照、刷新与放行原因.md)）。未登录或登录失效时不发模型请求，回答按本地兜底给出，页面给登录入口；上游提供方与模型的更换由管理员在服务端后台完成，客户端不受影响，取舍见 [ADR-0009](../docs/adr/0009-API后端采用Go与分层框架.md)、[ADR-0050](../docs/adr/0050-客户端统一为知新服务.md) 与 [ADR-0052](../docs/adr/0052-客户端改用OpenAI现行请求格式.md)。

请求走一个传输层，线格式只有 Responses 一种，请求体的组装与流式解析直接写在 `ai/llm_protocol.dart` 里。系统提示发 `instructions`，消息发 `input` 条目：用户与助手消息是 `message`，条目的内容块用 `input_text` 与 `input_image`，模型发起的工具调用是 `function_call`，客户端执行后的结果是 `function_call_output`，两者按 `call_id` 配对；工具声明用扁平的 `{type:function,name,description,parameters}`，参数放在 `input` 的 `input_text` 里，`tool_choice` 取 `auto`、`none` 或 `{type:function,name}`。输出上限用 `max_output_tokens`，取上下文上限的四分之一、最高 32768，与服务端允许的范围一致；请求带 `store: false`，也不发送 `temperature` 与 `top_p`，采样参数由上游模型的默认值决定（[ADR-0055](../docs/adr/0055-模型调用协议与上限统一.md)）。客户端不按模型名追加提供方的私有字段。

流式响应按 SSE 规范读取：一个事件可以由多行 `data:` 组成，空行才分发，注释行与 `event:`、`id:`、`retry:` 字段不影响负载，首行带 BOM 也能读。评估过 `sse`、`flutter_client_sse`、`simple_sse` 等现成包，都不能同时满足“POST 流、逐行超时与取消、无空行收尾时 flush”，因此保留自研解析器。增量按事件名分支：正文取 `response.output_text.delta` 的 `delta`，工具参数取 `response.function_call_arguments.delta` 并按 `output_index` 累积，`response.output_item.done` 用事件顶层的 `output_index` 归位，给出的完整参数覆盖先前的分片，正文条目只在这次流一条正文增量都没收到时才补发文字，避免把同一段正文收两遍，结束由 `response.completed` 判定，`response.incomplete` 的 `incomplete_details.reason` 为 `max_output_tokens` 时按截断保留已经生成的正文并提示，其余原因按服务端错误处理并带上原因，`response.refusal.delta` 与整段响应里的 `refusal` 按拒答处理、提示用户换一种问法，`response.failed` 与流内 `error` 事件按服务端错误处理，其余事件忽略。服务端省略 `event:` 时按负载里的 `type` 判断。非 2xx 的响应体会读出服务端自己的说明，便于定位额度、模型名与登录状态的问题；上游提供方拒绝服务端 key 时服务端只回统一的 `upstream_failed`，不转发提供方的错误正文。

回答正文使用 Markdown，模型可以用 `read_material_page` 读取本轮检索命中的原文，并在收到工具结果后继续回答。`propose_memories`、`propose_next_steps`、`propose_citations`、`propose_study_steps` 与 `propose_assessment` 提交的内容暂存在本轮，参数有误时丢弃对应提案，普通回答有完整正文即可结束。Responses 通过 `call_id` 配对 `function_call` 与 `function_call_output`。每轮的停止条件、材料范围与保存边界见 [00 第 9 节](../docs/00-产品定义.md#9-回答与工具调用)。

回答与记忆分开保存：用户明确说出的记忆在回答落库后单独写入，回答下方给一张可以撤销的卡片，写入失败只提示并保留待确认卡片，不回滚正文；模型推断的记忆先出确认卡片，点「记下」才写入，点「不记」收起。记忆写入形成一条提交，回执保存提交编号，讨论页可以按提交撤销；撤销后卡片回到待确认，同一批写入的多条记忆一起撤销。接受建议后创建的学习事项在同一条提交里记下已接受标题，回执同样指向这次提交。回答里的 Markdown 外链图片不自动加载，只显示可点击的提示，用户点击后才交给系统浏览器打开。

设置页可以填写模型的上下文上限，应用据此估算输入容量并预留输出空间。连接测试用一次最小工具请求检查登录与模型名能否返回可解析的工具参数。

没有配置、断网或调用失败时，讨论、题目、尝试、事项与记忆仍可查看与记录，下一步由本地规则给出，并标明来源。

## 账号与云同步

账号可选。`lib/data/cloud/server_client.dart` 是服务端的最小 HTTP 客户端，只拼路径、解 JSON 与把错误统一成 `ServerProblem`；账号会话、令牌刷新、邮箱验证、找回密码、退出登录、删除账号与“知新服务”配置在 `lib/application/account_service.dart`，令牌与设备标识只写 Android Keystore（`lib/data/cloud/account_store.dart`），服务地址与开发者模式写设备级的 `device.json`，自动同步开关、上次同步的账号与实例、同步状态与冲刷时刻写账号同步级的 `sync.json`（`lib/data/cloud/device_preferences_store.dart` 与 `lib/data/cloud/sync_preferences_store.dart`），两者都在应用私有目录，不进入数据库、数据包与整库备份；同步的两个位置在库里的 `revision_cursor`，随整库备份一起恢复，数据包不含它。没有保存地址时使用 `device_preferences_store.dart` 里的编译时默认值，正式包指向项目组的第一套实例，本地联调用 `--dart-define=ZHIXIN_SERVER_URL=...` 覆盖；在开发者模式中保存地址前，客户端调用目标实例的 `/readyz` 核对就绪状态与 schema，账号页只显示当前地址。登录用户可以在开发者模式中签发和撤销模型代理密钥，见 [ADR-0064](../docs/adr/0064-客户端开发者模式.md)。正式包只接受 https 地址，明文 http 只在显式开启 `ZHIXIN_ALLOW_INSECURE_SERVER` 的联调构建里可用；带令牌的服务端请求不跟随跨域重定向，同源重定向才继续。会话、进行中的刷新与同步位置都绑定到服务实例来源与账号，换实例或换账号时旧响应按身份代次丢弃并暂停自动同步，首次把本机记录上传到某个账号前要确认。

注册之后的邮箱默认未确认，账号页提供发送与确认验证码的入口，验证码只以六位数字邮件送达，服务端存 HMAC；未确认时找回密码收不到重设验证码。登录卡的“忘记密码”切到邮箱、验证码与新密码三段表单，重设成功之后服务端作废该账号的全部会话，本机清掉登录状态并回到登录表单。删除账号要先在确认框里重新输入当前密码，服务端回 401 `invalid_credentials` 时只提示密码错误并保留当前登录；“清除云端数据”调用 `DELETE /v1/cloud`，服务端回 409 时提示稍后重试，成功后页面显示完成状态并询问是否恢复自动同步。账号页同时读 `/v1/llm/quota` 显示今日已用与每日额度，设置页在“知新服务”来源下列出 `/v1/llm/models` 返回的允许模型；这两处读取失败只给一行说明，不影响本机功能、备份与同步。

云端备份在 `lib/application/cloud_backup_service.dart`：上传时用与“备份版本库”相同的 `VACUUM INTO` 快照生成 zip，上传前同样跑一次完整性检查、发现不一致时先说明再由用户决定是否继续，在文件上分块算出 SHA-256 之后由 `server_client.dart` 按文件流发送，不在内存里读整包，服务端按保留份数删除最旧的；列表、下载与删除都按账号隔离，下载由 `backupDownloadTo` 边收边写临时文件、核对响应头里的哈希与字节数，服务端拒绝、超时或校验不符时删掉临时文件，成功之后再交给本机已有的预检、确认与恢复点流程替换数据库，用完删除。云端备份入口与两个导入入口都在读取之前看包大小，上限 256 MiB 写在 `lib/domain/rules/package_budget.dart`，与服务端的 `ZHIXIN_MAX_BACKUP_BYTES` 同值，超过时不读进内存。附件随同步上传，服务端按账号累计字节，超过账号总量配额时返回 413 `storage_full`，页面显示已用量与上限并停止本轮上传，不逐个重试。页面在 `lib/ui/account_page.dart` 与 `lib/ui/cloud_backup_page.dart`，从“我的”页的账号卡、设置页模型段与数据版本页进入。

增量同步在 `lib/application/sync_service.dart` 与同目录的三个 part：`sync_snapshot.dart`（首次同步、快照重建与登记）、`sync_devices.dart`（设备名册）、`sync_refs.dart`（命名版本）。第一次同步先拉取服务端已有的全部提交并在本机应用，被远端提交触及过的表与主键整行跳过，只把本机独有的行作为基线上传，之后只推送新提交，全新设备不上传任何内容（[改进方案 3.6](../docs/数据版本系统对照git的改进方案.md)）；拉取到的远端提交经 `RevisionService.applyRemoteCommit` 在本机生成一条同样净变化的提交，撤销与数据版本页照常可用，远端提交的 uid 沿用到本机，拉取时按 uid 判断远端提交是否已经应用，重复下发不会叠加；推送时提交的 `uid` 就是提交身份，服务端按它永久去重。推送结束且本机没有待推送提交时，最后一条提交带上整库摘要；拉取到带摘要的最新一条、并且本机没有待推送提交时比较，不一致就在账号页显示“本机与云端不一致”并给一个“以本机为准重建云端”入口：清空账号的服务端提交序列之后把本机当前投影整份上传，另记一条 `cloud_sync_digest` 诊断（[ADR-0045](../docs/adr/0045-同步两端的一致性摘要.md)）。拉取时被远端取代的本机格子登记在 `sync_shadow`，推送时按格去掉被遮蔽的部分再推剩余，剩余为空的提交不推但推送位置照常前进，维护列 `updated_at` 不记冲突（[ADR-0040](../docs/adr/0040-数据版本的提交身份与同步变基.md)）。附件按内容哈希随提交上传与下载，拉取时核对哈希；服务端位置变化返回 409 时先拉取再重推，同一字段两台设备同时修改时后到达的覆盖先到达的，取舍见 [ADR-0023](../docs/adr/0023-首次同步上传基线.md)。应用根在提交之后延迟几秒排一次同步，账号页可以手动立即同步；同步失败只记一条说明与本机诊断，本机读写不受影响。

云端历史被压缩时，首次同步不再从第 1 条回放，改为按 `head` 返回的 `earliest_seq` 与 `snapshot` 下载快照，按附件哈希与整库摘要核对之后导入成一条 `baseline` 提交与一份 `initial` 检查点，两个同步位置分别写成快照位置与本机重建提交编号（[ADR-0046](../docs/adr/0046-客户端按快照浅克隆与重新克隆.md)）；已经有同步位置的设备在拉取途中收到 410 `history_compacted` 时先抛出 `SyncSnapshotProblem`（code 为 `confirmationRequired`），账号页与“我的”页按代码确认之后按快照重新克隆；服务端在 `head` 里声明压缩打开（`compact` 为真）、一轮同步成功、没有待推送提交并且服务端快照落后于服务端位置时，客户端才在收尾时把当前投影压缩上传并登记为快照，压缩关闭时不上传，服务端据此压缩提交序列。

同步请求带本机设备标识 `X-Device-Id` 与能力声明 `X-Sync-Capabilities: snapshot`，服务端据此维护账号的设备名册，压缩提交序列之前按名册判断有没有设备还没升级（[ADR-0047](../docs/adr/0047-快照附件回收与压缩前的客户端门槛.md)、[ADR-0048](../docs/adr/0048-设备名册与提交来源的别名.md)）。同步成功之后 `SyncService` 拉一次 `GET /v1/sync/devices` 并把名册缓存在内存里，数据版本页按远端提交里的设备标识查别名，查不到时仍然写标识前 8 位；账号页的“设备”一节列出名册、本机标识与最近同步时间，改名走 `PUT /v1/sync/devices`，别名去掉首尾空白之后 0–64 个字符，留空表示清除。名册读取失败只影响显示，不阻塞同步。

`lib/application/sync_service.dart` 与它的 part 只依赖 `GuardedDatabase`、版本服务与账号服务，不换库、不清空；远端提交的应用走 `GuardedDatabase.command`，因此与普通写入共用数据库独占区、表通知与版本通知。同步的两个位置在库里的 `revision_cursor`（`sync.pushed` 与 `sync.server_head`），带“账号编号 + 实例来源”的 `scope`：退出登录、删除账号与重设密码只把推送位置改成不阻塞、位置与 `scope` 保留，重新登录同一身份时从原位置继续增量同步；清除云端数据时两个位置与恢复标记一并删除，下一次同步按首次基线重建。整库恢复把库换成备份那一刻的内容之后，本机补记一条 `restore` 提交（恢复前后的差异，含删除），下一轮手动同步先确认“云端会改成恢复后的内容”，确认之后跳过拉取、只把这条差异推上去，两个位置收敛到当前服务端位置与本机 `HEAD`，待对齐期间自动同步不排期。

## 使用统计

不登录时的匿名活跃上报在 `lib/application/active_report_service.dart`，本机状态在 `lib/data/cloud/telemetry_store.dart`：安装标识首次启动时随机生成并保存在应用私有目录的 `telemetry.json`，不进入数据库、数据包与整库备份；应用根在首帧之后的空闲任务里调用一次，每天最多成功一次，失败静默重试一次并写本机诊断。登录之后再启动直接跳过，登录用户的活跃由服务端按请求日期统计。首次启动用一次说明讲清采集内容与用途，设置页“诊断与隐私”一张卡片里另有“匿名使用统计”开关，默认开启、可以关闭；关闭之后不再上报，已经上报的记录保留，口径见 [ADR-0019](../docs/adr/0019-留存统计用匿名上报.md)。

## 插件

插件随应用编译，运行时只加载第一方插件，不在运行时下载或执行第三方代码。目录与运行时第一版在 M1 建立，形态与权限的取舍见 [ADR-0010](../docs/adr/0010-客户端插件的两种形态与权限.md)，页面口径见 [02 第 3.15 节](../docs/02-产品与交互.md#315-插件与人格)，验收项见 [02 第 8.6 节](../docs/02-产品与交互.md#86-插件与人格验收)。

- 运行时基础设施在 `lib/plugins/runtime/`。`plugin_manifest.dart` 是不可变清单，字段为标识、名称、版本、说明、类型与四项权限，`validatePluginManifest` 返回可以直接显示的错误；人格插件声明任意一项权限都算不合格。`plugin.dart` 是 `FirstPartyPlugin` 接口，暴露 `manifest`，能力插件从 `start(PluginAccess)` 进入。`plugin_access.dart` 是网络、读数据、提交草稿与调用模型四个门面，未声明的权限在调用点抛 `PluginPermissionDenied`，不做静默降级；已经声明但本期没有接入的能力抛 `PluginCapabilityUnavailable`。`plugin_runtime.dart` 注册插件、读写启停状态、拒绝未知标识，并通过 `activePersonaPrompt` 给出当前人格段落。`plugin_metadata_store.dart` 是运行时依赖的设置读写窄接口，生产实现是 `lib/data/repository/plugin_metadata_store.dart` 里的 `SettingsPluginMetadataStore`。
- 目录规则：运行时基础设施放 `lib/plugins/runtime/`，单个插件放 `lib/plugins/<插件标识>/`。插件目录不 import `data/` 与 `ui/`，不持有数据库连接，也不依赖 Flutter；`test/architecture_test.dart` 对这三个边界逐条检查。
- 人格插件在 `lib/plugins/persona/`。`persona.dart` 定义 `Persona` 与按码位计数的 800 字校验，超过时由 `validatePersonaText` 说明超出的字数，不静默截断；`builtin_personas.dart` 是两个内置人格；`persona_catalog.dart` 读写 `app_meta` 并切换当前启用项；`persona_plugin.dart` 是人格插件的清单与本体，清单不声明权限。人格段落由 `ai/buddy_prompt_builder.dart` 拼在核心规则之后、当前时间与记忆之前，启用人格时另有一条规则说明用户本轮说明、人格与记忆讲解偏好的顺序与边界；停用后下一次请求不再带人格段落，读取到超长文本时用 `truncateCodePoints` 兜底。
- 设置键写在 `app_meta`：`persona.items` 保存人格 JSON 列表，`persona.active` 保存当前启用人格（空串表示未启用），`plugin.enabled.<插件标识>` 保存启停状态（`1` 或 `0`，没有写过时默认启用）。写入经 `SettingsRepository.setMetadata`，不形成提交，也不进数据版本页；整库备份包含 `app_meta`，恢复或清空之后下一轮回答与重新打开的页面都读恢复后的状态，当前数据包不包含这些设置。
- 本期做运行时骨架、人格插件、“我的”页的“插件”与“人格”两个入口以及四条调用点检查；能力插件与 B 站读取、第三方插件、沙箱与服务端分享码留到 M3。插件不保存第三方账号的密码、Cookie 或令牌，也不把学习内容发给第三方工具服务。

## 发布

### 签名

正式包只在 Actions 里出，本机不出。CI 用仓库 Secrets 里的四项配置还原 keystore，
再生成 `android/key.properties`；四项缺一项，发版任务会在“检查签名 secrets”一步直接失败，
不会悄悄打出一个 debug 签名的包。

| Secret | 内容 |
|---|---|
| `RELEASE_KEYSTORE_BASE64` | keystore 文件的 base64，用 `base64 -w0 release.jks`（macOS 用 `base64 -i release.jks`）生成 |
| `RELEASE_KEYSTORE_PASSWORD` | keystore 口令 |
| `RELEASE_KEY_ALIAS` | 密钥别名 |
| `RELEASE_KEY_PASSWORD` | 密钥口令 |

keystore 与口令由发版人保管，仓库与本机工程目录都不放：CI 把还原出来的 keystore 写到 runner 的临时目录，
`key.properties` 里用绝对路径引用它，发版结束随 runner 一起销毁。发版任务在构建之后用 `apksigner` 核对证书
不是 debug 证书，并对包体记录版本、提交与 SHA-256，随后用 Ed25519 私钥产出发布清单的哈希与签名材料。

### 发布清单签名

发布清单里的每一版安装包另有一把 Ed25519 签名密钥，用来让应用确认清单没有被替换；安装包本身由系统安装器在覆盖安装前核对签名。私钥的 PKCS8
编码以 base64 放在仓库 Secret `RELEASE_SIGNING_KEY_BASE64` 里，CI 在发版任务的“签名与清单”一步用它签名；
这一项与 keystore 的四项一样，缺失时发版任务直接失败，不会产出一份没有签名的清单片段。密钥的生成与保管
由发版人完成，命令如下：

```bash
openssl genpkey -algorithm Ed25519 -out release-signing.pem
openssl pkey -in release-signing.pem -pubout -out release-signing.pub.pem
base64 -w0 release-signing.pem   # 结果填入仓库 Secret RELEASE_SIGNING_KEY_BASE64
```

签名对象是安装包 SHA-256 的小写十六进制字符串本身，共 64 个 ASCII 字节，不加换行，也不签文件内容；
CI 用 `openssl pkeyutl -sign -rawin` 对这段字符串生成 64 字节签名，再转成 base64 写进 `app-release.apk.sig`，
同时产出 `app-release.apk.sha256`，两个文件与安装包一起上传为构件，并在 step summary 里给出可以直接填进
发布清单的 JSON 片段。公钥以常量形式内置在应用里：把 `release-signing.pub.pem` 的内容原样填进
`lib/platform/release_signing_key.dart` 的常量，或者构建时用
`--dart-define=RELEASE_PUBLIC_KEY_PEM="-----BEGIN PUBLIC KEY-----…"` 传入，两种方式取其一。更新检查核对 HTTPS 地址和 SHA-256 格式，并使用随包公钥对哈希字符串验签；检查阶段不下载安装包，验签通过即提示更新，用户确认后由系统浏览器下载一次，系统安装器核对签名后覆盖安装。签名、公钥或哈希缺失时，应用不提示更新。官方发版任务核对签名私钥是否与仓库内置公钥配对。启动后的自动检查与设置页的“检查更新”走同一套流程，本次启动只自动
检查一次。私钥与 keystore 一样只由发版人保管，不进仓库与本机工程目录；换密钥意味着旧版本应用无法验证
新清单，发版说明要写明这一点，并在应用内置公钥的下一次发版里同步更新。


正式包在 Actions 里手动运行“CI 与发版”，用仓库 Secrets 里的签名配置生成；本机不出正式包。版本号按 [03 第 3 节](../docs/03-团队分工与协作.md#3-交付节奏)递增，取值以本目录 `pubspec.yaml` 的 `version` 一行为准，只由发版人（见 [03 第 2 节](../docs/03-团队分工与协作.md#2-角色)）在发包前修改；开发包的版本名带 `-dev` 且按 `com.zhixin.app.dev` 另装一个应用，“我的”页的“关于”显示构建时写入的构建名与构建号，不另存版本常量；许可页同时列出知新自身的 MIT 许可与第三方组件许可，知新自身的许可从 `platform/app_license.dart` 读取，测试会核对它与仓库根目录的 `LICENSE` 同文。
