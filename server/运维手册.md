## 2. 权限

| 角色 | 持有什么 | 能做什么 |
|---|---|---|
| 陈思源（管理员） | 阿里云控制台、DNS、OSS 的 RAM 账号、DeepSeek 的 key、服务器 root | 全部；只有他能建实例、改 DNS、换密钥、做恢复演练 |
| 其他成员 | 各自一把 SSH 公钥授权到服务器 | 看日志、跑命令、部署自己改的服务端代码；不动机器上的其他站点 |
| AI 助手 | 各自一把无口令密钥，本机 `~/.ssh/config` 里一个别名 | 与服务端开发、联调、排障有关的一切命令；每次执行都是新进程 |
| 客户端 | 不含任何服务端密钥 | 用账号密码换访问令牌，拿令牌调同步、备份与模型代理 |

数据库口令与 OSS 密钥只有两种流转方式：由管理员直接写进服务器的 `api.env`，或者由管理员写到自己的私有目录再从那里拷贝；这两种方式都不经过仓库与聊天记录。模型提供方的 key 只经后台页面提交，用 `ZHIXIN_SECRET_KEY` 加密入库，运维手册与仓库里都不出现明文。

### 2.1 AI 助手接入的四步

第一次接入按下面四步走，已接入过的直接跳到第 4 步验证。

1. 在本机生成一把专用密钥，不要复用 GitHub 或别的机器的私钥：

   ```bash
   ssh-keygen -t ed25519 -N "" -C "<你的名字>-zhixin" -f ~/.ssh/id_ed25519_zhixin
   ```

   Windows 的 PowerShell 传空口令有坑：`-N ""` 会被吞掉，结果密钥带了奇怪的口令。稳妥的做法是用 `cmd /c` 或 .NET 的 `ProcessStartInfo.ArgumentList` 传参，生成之后用 `ssh-keygen -y -P "" -f <私钥>` 验证，能直接打印出公钥就说明没有口令。

2. 把 `<私钥>.pub` 的内容发给陈思源，由他追加到服务器上你自己账号的 `authorized_keys`（管理员先建账号并授予[§4.1](#41-ssh-与部署权限)里的最小 sudo 权限；root 直登关闭之后不再往 root 下加公钥）。

3. 在本机 `~/.ssh/config` 里加一段：

   ```
   Host zhixin-dev
     HostName 112.125.89.75            # 写 zhixin.chensiyuan.work 也行
     User <你的账号>
     IdentityFile ~/.ssh/id_ed25519_zhixin
     IdentitiesOnly yes
     ServerAliveInterval 30
   ```

4. 验证，`BatchMode=yes` 能过就说明不需要任何人工输入：

   ```bash
   ssh -o BatchMode=yes -o ConnectTimeout=10 zhixin-dev 'hostname; whoami; systemctl is-active zhixin-api'
   ```

撤销是删掉 `authorized_keys` 里对应的那一行（按 `-C` 备注找），不需要改 sshd。密钥不设口令，代价是这个文件等同于服务器上的那个账号，只能放在自己的开发机上；要带口令就得先启用 ssh-agent 并 `ssh-add` 一次，之后仍然可以非交互使用。

### 2.2 AI 助手能做什么、不能做什么

- 不能做的事：交互式程序（`vim`、`tmux`、`htop`、`psql` 的交互模式）、需要终端输入的 `sudo` 密码提示、二次验证提示。每次命令都是独立进程，`cd`、环境变量、后台任务都不跨命令保留，长任务要么用 `nohup`/`systemd` 落到服务上，要么一条命令跑完。
- 应做的事：改配置文件前先 `cp` 一份带时间戳的备份；动 nginx 先 `nginx -t` 再 reload；动数据库先确认是不是空库；测试数据用 `example.com` 邮箱并留下清理命令。
- 授权按[加固后的运维动作](#41-ssh-与部署权限)执行：日常操作用个人账号加 sudo，部署与排障不再共用 root 的密钥；能写 `/opt/zhixin`、`/etc/zhixin` 并重启本单元的普通账号就够，改 sshd、系统升级与防火墙留给管理员。
- 服务器 sshd 的收紧不在这台机器上单独决定：先在另一条连接上验证独立恢复通道，再关闭密码登录与 root 直登，步骤见[§4.1](#41-ssh-与部署权限)；改配置时保留一条已经登录的会话，避免把自己锁在门外。

Windows 上通过 PowerShell 远程执行时还有一个坑：这里的字符串按 CRLF 发送，远端 `bash` 会把 `\r` 当成参数的一部分，`free -m`、`head -2` 这类命令会报“invalid option”。可靠写法是加一层过滤：

```powershell
$script | ssh zhixin-dev "tr -d '\r' | bash -s"
```

三档存储形态：不设 `ZHIXIN_DATABASE_URL` 时全部在内存里，进程退出即丢，只能本地开发与测试；设数据库而不设 `ZHIXIN_S3_ENDPOINT` 时字节写 `ZHIXIN_BLOB_DIR`；两者都设时字节走 OSS。本地起一套最快的办法是 `cd server && go run ./cmd/zhixin-api`，不设任何变量就用内存存储，`curl localhost:8080/healthz` 应当返回 200；要试托管模型时按 [README 的本地运行](README.md#本地运行与检查)登记来源与模型，内存存储下这些配置随进程消失。

容易配错的几件事：`schema.sql` 没有 `IF NOT EXISTS`，带着 `ZHIXIN_APPLY_SCHEMA=1` 重启会因为表已存在而失败；`ClientSchemaVersion` 必须与 [01](../docs/01-ER数据模型.md) 的编号一致，客户端升 schema 时同一个 push 改；对象存储的端点不带 `https://` 前缀；`ZHIXIN_ACCESS_TTL` 必须短于 `ZHIXIN_REFRESH_TTL`，否则启动报错；配置了数据库之后，`ZHIXIN_MAIL_LOG` 必须为 `0`，`ZHIXIN_CODE_SECRET` 与 `ZHIXIN_TELEMETRY_SECRET` 必须是固定的随机值，否则服务拒绝启动；`ZHIXIN_TRUSTED_PROXIES` 留空时所有请求都按 nginx 的回环地址计数，按地址的限流会把真实用户算成一个桶；发布清单里的地址必须是 https、`sha256` 必填，改清单时按[§4.5](#45-新增配置部署前核对清单)的清单与发版流程一起更新。模型来源与模型清单没有写进 `api.env` 的入口，库里没有来源时托管接口返回 503，先按[§3](#3-配置)末尾的步骤在后台建好。

模型后台走 `/admin/`。服务只监听回环地址，管理员最稳妥的访问方式是 SSH 隧道：`ssh -N -L 18080:127.0.0.1:8080 zhixin-dev`，再在本机浏览器打开 `http://localhost:18080/admin/`。第一套实例用 `location ^~ /admin/ { return 404; }` 关闭公网入口，管理访问通过 SSH 隧道。后台没有操作审计，令牌等同于管理员本人，出现在聊天、截图或提交里时当次轮换。

来源与模型只在后台配置（ADR-0035），`api.env` 里没有模型地址、key 与模型清单。新实例、重建库之后或删掉全部来源之后，路由表是空的，聊天与嵌入接口一律返回 503，启动日志会写 `no model configured`：先在隧道里打开后台，新建一个来源（基础地址加 key），再新建对外模型并给一条路由，保存之后立即生效。换 key 也在这里：编辑来源，地址不变时 key 可以只填新的那一把；地址换了主机的必须同时重填 key。后台页面随可执行文件一起更新，部署之后已经打开的标签页要刷新一次，否则里面还是旧脚本，页面与接口的字段对不上。

## 4. 加固后的运维动作

这一节是加固轮次之后的固定动作，第一次按顺序执行一遍，之后每次部署按[§4.5](#45-新增配置部署前核对清单)逐项核对。动作的目标是让服务器、凭据与数据在默认配置下就是收紧的，不要等出事再补。

### 4.1 SSH 与部署权限

关闭密码登录与 root 直登之前，先验证一条独立恢复通道：在阿里云控制台确认实例的 VNC 或救援连接可用，或者在另一个终端用一把已经授权、口令已知的个人密钥登录成功，并且这条登录不依赖即将改动的配置。通道验证通过之后，先备份 `sshd_config`，再把 `PasswordAuthentication` 改为 `no`、`PermitRootLogin` 改为 `no` 或 `prohibit-password`，用 `sshd -t` 检查语法，保留当前会话并 reload，最后从新终端用个人账号登录一次确认可用；任何一步失败都先恢复备份并 reload，不要在没有第二条可用连接的情况下重启 sshd。

```bash
cp /etc/ssh/sshd_config /etc/ssh/sshd_config.bak-$(date +%F)
sed -i 's/^#\?PasswordAuthentication.*/PasswordAuthentication no/' /etc/ssh/sshd_config
sed -i 's/^#\?PermitRootLogin.*/PermitRootLogin no/' /etc/ssh/sshd_config
sshd -t && systemctl reload ssh
```

部署改用个人密钥：每个成员在自己的账号下放一把公钥，撤销时删掉 `authorized_keys` 里对应备注的那一行，不再共用 root 私钥。日常操作使用个人账号加 sudo，sudoers 只授予写 `/opt/zhixin`、`/etc/zhixin` 与执行 `systemctl restart zhixin-api` 的权限；改 sshd、升级系统、改防火墙与换证书留给管理员。加固之后普通账号不能直接写 `/etc/nginx` 与 `/etc/letsencrypt`，需要改这些地方时找管理员。

### 4.2 数据与备份的加密和访问权限

逐项核对并记录日期、核对人与结果，记录写在管理员的私有注记里，不写进仓库：

| 对象 | 核对内容 |
|---|---|
| 数据库 | 只监听 `127.0.0.1:5432`；`pg_hba.conf` 只允许本机连接；`api.env` 权限 600 且只由服务用户与管理员读取；云盘与快照开启加密 |
| 对象存储 | bucket 为私有、关闭公共读；RAM 子账号只授这一个 bucket 的读写；开启服务端加密；访问密钥只出现在 `api.env` |
| 上传临时目录 | 服务用户可读写、其他用户无权限；服务异常退出后残留的临时文件按天清理；目录所在磁盘留够备份与附件并发上传的空间 |
| 运维备份 | `pg_dump` 与 OSS 前缀对象先加密再离开服务器，备份介质只管理员可读，至少留一份离线副本，加密口令与备份分开存放 |
| 运维注记 | `/opt/zhixin/OPS.md` 权限 600，只写本机路径与恢复顺序，不写口令 |

### 4.3 保留期限与清理

反馈保留 365 天（`ZHIXIN_FEEDBACK_KEEP_DAYS` 的默认值），服务启动时清一次、之后每天清一次，正文、联系邮箱与诊断摘要一起删除，因此一份反馈的保存期限就是 365 天。匿名活跃保留 180 天，按滚动窗口删除，规则见 README 的留存统计。没有任何已验证登录方式的账号保留 7 天（`ZHIXIN_UNVERIFIED_KEEP_DAYS`），每日清理删除账号行，登录方式、会话与验证码随外键级联，这个账号本来就没有云端数据。历史备份按下面的期限保留，过期备份删除等同于删除其中含有的账号邮箱、反馈正文与学习数据副本，删除之前确认这一份不再需要用于恢复：

| 备份 | 建议保留 |
|---|---|
| 每日 `pg_dump` 与对象存储增量 | 14 天 |
| 每周一份完整备份 | 3 个月 |
| 每月一份归档 | 12 个月，覆盖一个学期与结题材料准备期 |

手工清理可以用 `DELETE FROM feedback WHERE created_at < now() - interval '365 days'`，清理之后用 `SELECT count(*) FROM feedback` 核对。访问日志按 journald 的 200M 上限滚动，模型代理不保存请求与回答正文，这两类不需要额外清理。

### 4.4 匿名入口与全局写入上限

反馈与匿名活跃上报继续保持匿名入口，不要求登录，这是用户自愿提交的渠道，不要为了限制写入改成登录后才能用。防止换地址绕过按地址的限流，靠全局写入上限：反馈默认每秒补 2 个、最多积 30 个，匿名上报默认每秒补 5 个、最多积 100 个，与按地址的桶同时生效，超限返回 429 并带 `Retry-After`。看到 429 比例升高时先看访问日志里的来源与时间分布，确认是反复写入还是正常用户变多，再决定临时调高 burst 或保持；调成 0 会关闭限流，只在排障时短暂使用。全局上限不改变匿名口径，也不在日志里记录反馈正文，两者都不能为了方便查看而打破。

### 4.6 发信配额与时段性配置

默认值按常见的免费邮局定：日发 200 封、每小时 60 封量级，按每日开满算平均每秒约 0.002 封，按高峰一小时开满算约 0.017 封，因此 `ZHIXIN_MAIL_GLOBAL_RATE=0.05` 留出约三倍余量，配合按收件地址每天 4 封的上限，正常的内测用量碰不到。换通道时先看服务商给的数字：免费邮局看日上限，企业邮箱看单账号的日上限与每小时上限，两者都换算成每秒的速率并取更紧的那一个；付费通道按套餐的日上限重算。调大之后重启服务生效，调小的效果立即生效，因为桶的状态在进程内存里。

发信撞到实例总量与熔断时都返回 429 并带 `Retry-After`，客户端按这个秒数等待；管理员在日志里看到 `auth: instance mail budget exhausted` 或 `auth: mail sender is paused` 就说明撞到了实例总量或熔断。熔断在连续三次临时失败之后开始，暂停 30 秒起翻倍、最长 5 分钟，一次发送成功之后计数归零，不需要手工重启；服务商侧封禁发信时熔断救不了，只能改口令或换通道，改完重启服务。

新学年开学、公测开始这类用户集中注册的时段，注册与发信两个实例上限要一起估：`ZHIXIN_REGISTER_GLOBAL_RATE` 默认每秒 0.05 个，`ZHIXIN_MAIL_GLOBAL_RATE` 默认每秒 0.05 封，能同时通过的速度大致相同。如果预计半小时内有超过 100 人注册并请求验证码，先把 `ZHIXIN_MAIL_GLOBAL_BURST` 调到 100 以上让突发不排队，再把两个速率按预计人数除以时段秒数调到每秒 0.1 左右；时段结束之后调回默认值，否则换地址刷验证码的成本重新变低。

### 4.7 云端数据清除

客户端设置页的“清除云端数据”在用户输入当前密码后调用 `DELETE /v1/cloud`，服务端依次删除该账号的备份、提交序列、附件索引与对象存储里 `backups/<账号>/`、`attachments/<账号>/` 前缀下的字节，成功返回 204；清除期间这个账号的写入返回 409 `conflict`，客户端退避之后重试。清除期间的互斥只保存在进程内，没有数据库里的清除标记，服务端按单实例部署时才能覆盖全部写入入口；进程中途崩溃时用户重新发起一次 `DELETE /v1/cloud`，从剩下的部分继续，从崩溃到重试之间另一台设备推送的内容会在重试时一并清除。

协助用户清除时没有管理接口，用这个账号的访问令牌调用 `DELETE /v1/cloud`，确认返回 204，随后用 `ossutil ls -r "oss://$BUCKET/backups/<账号 id>/"` 与 `ossutil ls -r "oss://$BUCKET/attachments/<账号 id>/"` 核对没有残留，再用 `SELECT count(*) FROM backup WHERE user_id='<账号 id>'`、`SELECT count(*) FROM sync_commit WHERE user_id='<账号 id>'` 与 `SELECT count(*) FROM sync_ref WHERE user_id='<账号 id>'` 核对数据库行。清除不影响账号、会话与本机数据，删除账号走 `DELETE /v1/me` 并且要重新提交密码。多实例部署时这套互斥不能跨进程，需要另做协调。

### 4.9 自动部署与回滚

`main` 收到 `server/**` 或 [deploy-server.yml](../.github/workflows/deploy-server.yml) 本身的推送之后，这个工作流先跑与服务端 CI 相同的一组检查（`gofmt`、`go mod tidy -diff`、`go vet`、`go test -race`，带临时 PostgreSQL），通过之后在 Runner 上交叉编译 `linux/amd64`，再用专用账号 `deploy` 上传、重启并核对 `/readyz`。手动运行时在 Actions 页面选「部署服务端」，它部署的是当时 `main` 的提交。取舍与代价见 [ADR-0032](../docs/adr/0032-main推送后自动部署服务端.md)。

自动部署依赖四个仓库 secret 与服务器上的一个账号，两边的对应关系如下：

| 位置 | 内容 | 说明 |
|---|---|---|
| 服务器 `/home/deploy/.ssh/authorized_keys` | 部署公钥，备注 `gha-deploy-zhixin` | 撤销自动部署就是删掉这一行 |
| secret `DEPLOY_SSH_KEY` | 同一把密钥的私钥，无口令 | 只放在 Actions 的加密 secret 里，不进仓库 |
| secret `DEPLOY_KNOWN_HOSTS` | `112.125.89.75` 的 ed25519 主机指纹 | 固定指纹，工作流不用 `accept-new` |
| secret `DEPLOY_HOST`、`DEPLOY_USER` | `112.125.89.75`、`deploy` | 换服务器时改这两个 |
| 服务器 `/etc/sudoers.d/zhixin-deploy` | 只允许 `deploy` 重启与查看 `zhixin-api` | `visudo -cf` 校验过；不授予其他命令 |

`deploy` 拥有 `/opt/zhixin/bin` 的写权限，读不到 `api.env`，也不能改 nginx、证书、系统包与别的站点。远端在同一个 SSH 会话里完成切换：新文件先传到 `zhixin-api.new-<提交前 12 位>`，当前文件备份成 `zhixin-api.prev`，用 `mv` 换上新文件并重启，二十秒内 `/readyz` 没有就绪就换回 `zhixin-api.prev` 再重启，工作流标红；成功后 Runner 再核对一次公网 `/readyz`。回滚可以重新运行一次部署工作流部署上一个通过检查的提交，也可以在服务器上执行 `cd /opt/zhixin/bin && mv -f zhixin-api.prev zhixin-api && sudo systemctl restart zhixin-api`。

轮换部署密钥时先在本机生成新密钥，把公钥追加到 `/home/deploy/.ssh/authorized_keys`，用 `ssh -i <新私钥> deploy@112.125.89.75 'sudo -n systemctl is-active zhixin-api'` 确认可用，再用 `gh secret set DEPLOY_SSH_KEY < <新私钥>` 更新 secret 并从 Actions 手动跑一次部署；旧的 `authorized_keys` 行在确认新密钥可用之后再删。删掉旧行而 secret 还没更新的那段时间，部署失败、线上服务不受影响。

这条流水线不处理表结构与运行配置：`schema.sql` 改动仍按[§4.5](#45-新增配置部署前核对清单)与 ADR-0001 停服重建库，`api.env` 的变量仍在服务器上改并重启。含这两类改动的推送照样会部署可执行文件，因此推送之前先把配置和库准备好，否则新进程可能起不来而自动回滚到旧版本。

同一天发出 0.3.0。Actions 的发版任务在 `0ec4aa6` 上构建 arm64 单包，74,529,199 字节，SHA-256 为 `8910290818259e607627b3297ad60b88f31cf4d65efc57c07deb6c2c048fe01f`，签名与哈希取自同一次运行的摘要；安装包放到 `/opt/zhixin/downloads/zhixin-0.3.0.apk`，从公网下载回来重算的哈希与清单一致；`/opt/zhixin/releases.json` 换成只有一条 0.3.0 的新清单，`min_version` 同为 0.3.0，`notes` 写明本机数据会清空、服务端账号要重新注册，旧清单留在 `/root/releases-0.2.0.json.bak`；重启 `zhixin-api` 之后 `GET /v1/app/releases` 返回新的一条，`/readyz` 仍是 schema 32。同一天推上 `v0.3.0` 标签，在 GitHub Release 上附 `zhixin-0.3.0.apk`、`.sha256` 与 `.sig`，并标为 Latest；0.1.0、0.1.1 与 0.2.0 三个标签补建 Release，0.1.x 当时没有对外安装包，只写说明，0.2.0 附上从下载站取回的同一个包与清单里的哈希、签名，安装包、清单与 Release 三处哈希一致。四个版本按 0.1.0、0.1.1、0.2.0、0.3.0 的顺序逐个创建，Release 列表按创建时间倒序排列，重建时顺序不能颠倒。R8 混淆表从同一次运行的构件取回，28,562,146 字节，存在 `/opt/zhixin/mapping/zhixin-0.3.0-mapping.txt`，构件 30 天后过期，线上崩溃栈要从这一份还原。

### 4.10 快照压缩开关与设备名册

`ZHIXIN_SYNC_COMPACT` 于 2026-11-23 在内测实例打开，`ZHIXIN_SYNC_COMPACT_KEEP` 设为 `720h`。打开之后服务端在 `head` 里返回 `compact: true`，客户端才开始上传整库快照；关闭期间客户端不上传，登记也只写指针。

确认开关生效：登录任意账号后 `GET /v1/sync/head`，响应里 `compact` 为 `true`；登记快照、过了保留期之后 `earliest_seq` 会跟着推进。两台设备的走查在 2026-11-23 用两个独立的客户端实例完成（各自的本机库与偏好目录、各自的设备标识，同一个账号与同一个实例），覆盖基线、快照登记、压缩、410 重建与双向同步，结果写进 [04 的 M1](../docs/04-长期路线图.md#m1-验收与内测包)。

2026-11-24 按提交 `3349122` 的二进制在发版前又核对了一次，范围是 `earliest_seq` 与快照指针。内测实例在 schema 32 重建之后用一个临时账号只读地调用 `GET /v1/sync/head`、`GET /v1/sync/snapshot` 与 `GET /v1/sync/commits?after=0`，三个响应都是 `compact: true`、`earliest_seq: 1`、`head: 0` 且不带 `snapshot`，账号随后删除；未确认邮箱的账号线上不能写入，已确认的账号也只推过一条提交，所以实例上仍然没有登记过快照，登记与指针这两步只有下面这一次本地走查覆盖。同一份二进制在本机以内存存储启动、把 `ZHIXIN_SYNC_COMPACT_KEEP` 压到 1ms 之后走了一遍：登记 seq 2 的快照之后 `earliest_seq` 从 1 推进到 3、指针停在 seq 2，`after=0` 与 `after=1` 返回 410 且 `extra` 带出保留下界、head 与快照的三项，`after=2` 返回空页，登记 seq 1 返回 409 且 `extra.snapshot_seq` 为 2，登记 seq 3 返回 400，同位置换哈希按幂等刷新指针，压缩之后继续推送的提交拿到 seq 3 而 `earliest_seq` 保持 3。PostgreSQL 实现由 CI 的服务端任务在带 PostgreSQL 服务的环境里跑 `TestPostgresSyncSnapshot` 与 `TestPostgresSnapshotOrphansAndDevices`，本机没有数据库，这两条用例跳过。

改回关闭：在 `api.env` 里把 `ZHIXIN_SYNC_COMPACT` 设为 `0` 或删掉这一行，重启服务；已经登记的提交与快照指针保留，客户端随即停止上传新快照。改保留窗口只改 `ZHIXIN_SYNC_COMPACT_KEEP` 再重启，已经删除的提交不会恢复。

### 4.11 即刻收积分包的上线与回滚

聊天额度改走即刻收之后，服务端多出 `nowpay_charge`、`nowpay_purchase` 与 `nowpay_balance` 三张表，见 [ADR-0067](../docs/adr/0067-聊天额度改走即刻收积分包.md) 与 [ADR-0069](../docs/adr/0069-积分余额的本地副本与预留放行.md)。它们是纯新增，生产库已有真实交易，不再按 [ADR-0057](../docs/adr/0057-服务端改表清空重建.md) 清空重建，只用下面三条可回滚的增量语句建表；回滚就是按依赖顺序删表，账号与订单数据都不受影响。

```sql
CREATE TABLE IF NOT EXISTS nowpay_charge (
  id            TEXT PRIMARY KEY,
  user_id       TEXT REFERENCES app_user(id) ON DELETE SET NULL,
  day           DATE NOT NULL,
  points        BIGINT NOT NULL CHECK (points > 0),
  billed_tokens BIGINT NOT NULL CHECK (billed_tokens > 0),
  status        TEXT NOT NULL DEFAULT 'pending'
                CHECK (status IN ('pending', 'processing', 'succeeded', 'failed')),
  note          TEXT NOT NULL DEFAULT '',
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS nowpay_charge_user_day_idx ON nowpay_charge (user_id, day);
CREATE INDEX IF NOT EXISTS nowpay_charge_unsettled_idx
  ON nowpay_charge (user_id, created_at) WHERE status IN ('pending', 'processing');

CREATE TABLE IF NOT EXISTS nowpay_purchase (
  out_request_no TEXT PRIMARY KEY,
  user_id        TEXT REFERENCES app_user(id) ON DELETE SET NULL,
  sku_id         TEXT NOT NULL DEFAULT '',
  purchase_url   TEXT NOT NULL,
  expires_at     TIMESTAMPTZ NOT NULL,
  created_at     TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS nowpay_purchase_user_created_idx
  ON nowpay_purchase (user_id, created_at DESC) WHERE user_id IS NOT NULL;

CREATE TABLE IF NOT EXISTS nowpay_balance (
  user_id          TEXT PRIMARY KEY REFERENCES app_user(id) ON DELETE CASCADE,
  remaining_points BIGINT NOT NULL CHECK (remaining_points >= 0),
  synced_at        TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

顺序固定为三步：先备份 `api.env`（`cp -a /etc/zhixin/api.env /etc/zhixin/api.env.bak-$(date +%Y%m%d%H%M%S)`），再建表，最后改配置并重启。改配置这一步保留支付宝应用凭证（`ZHIXIN_ALIPAY_APP_ID`、`ZHIXIN_ALIPAY_PRIVATE_KEY`、`ZHIXIN_ALIPAY_PUBLIC_KEY`），即刻收沿用同一个应用签名；等商品审核发布、拿到 `out_product_id` 之后再加 `ZHIXIN_NOWPAY_PRODUCT_ID`、`ZHIXIN_TOKENS_PER_POINT`（本项目设为 `10000`）与可选的 `ZHIXIN_NOWPAY_CALLBACK_URL`，重启后核对 `/readyz`。APP 支付时期的配置项已随通道删除，旧 `api.env` 里残留的同名变量不会再被读取。

商品 ID 没配时服务端不启用即刻收：购买接口只回空余额，`nowpay_*` 三张表不会被读写，也不会因为缺表启动失败。配了商品 ID 之后启动会检查三张表：`nowpay_charge` 与 `nowpay_purchase` 缺表直接退出并由自动部署回滚到上一份文件，这两张要在配置之前或同一次停服窗口里建好；`nowpay_balance` 缺表时只记一条错误日志，免费额度之外不再按积分放行，服务照常启动。余额副本是 2026-11-25 补的，已经在收款的实例可以先铺新版，再执行上面的建表语句并重启，放行从重启之后生效；建表之后还没有副本行的账号，在免费额度用完之后的第一次请求会回 429，服务端随即查一次余额写入，第二次请求就能用上积分，提前打开一次购买面板也可以写入。

档位按 [ADR-0068](../docs/adr/0068-聊天积分包的档位与价格.md) 在小程序里配置，三档的名称、价格与发放积分照表填写，名称用萤火、灯火、星河这三个不含期限的说法。审核发布之后在应用内用已验证的账号核对三档的名称、价格与积分数，再买一笔最小档，核对余额增加与一次核销，步骤同 [ADR-0067](../docs/adr/0067-聊天额度改走即刻收积分包.md) 的验收条目。改价或增减档位只改小程序，`ZHIXIN_TOKENS_PER_POINT` 保持 `10000`，改完不需要重启服务；审核期间与发布之前，应用显示的还是旧档位。

回滚只有一种：删掉 `ZHIXIN_NOWPAY_PRODUCT_ID` 再重启，客户端回到只显示余额的状态，已经核销的积分留在支付宝一侧，本地流水保留可查。APP 支付通道、订单表、钱包表与 Android SDK 通道已经删除，不能再靠改配置退回；需要恢复时按 [ADR-0065](../docs/adr/0065-支付宝购买聊天模型额度.md) 与当时补签结果重新开发，并重新生成契约与表结构。

## 6. 排障

- `/healthz` 返回 200 但 `/readyz` 不 ready：数据库连不上、bucket 不存在、OSS 密钥或端点不对，三者之一。先看 `journalctl -u zhixin-api -n 30 -o cat`，启动日志会打印用的是哪种存储与哪个 endpoint。
- 服务启动即退出并打印配置项：加固轮次之后启动会自检生产配置，`ZHIXIN_MAIL_LOG` 不是 0、`ZHIXIN_CODE_SECRET` 或 `ZHIXIN_TELEMETRY_SECRET` 为空、`ZHIXIN_TRUSTED_PROXIES` 写了 `0` 或信任全部地址、带 key 的上游是 http 公网地址都会拒绝启动，按报错里的变量名改 `api.env` 之后重启。
- 502 或 504：`zhixin-api` 没起来，或者 nginx 里的反代地址与 `ZHIXIN_ADDR` 不一致，先 `systemctl is-active zhixin-api`。
- 上传大备份返回 413：nginx 的 `client_max_body_size` 与服务的 `ZHIXIN_MAX_BACKUP_BYTES` 要对得上，前者必须不小于后者。
- 上传附件返回 413 `storage_full`：账号的全部附件超过了 `ZHIXIN_MAX_ACCOUNT_ATTACHMENT_BYTES`，`extra` 里带已用量与上限；先确认用户是不是真的传满，再核对 `SELECT count(*), coalesce(sum(size),0) FROM attachment WHERE user_id='<账号 id>'` 与 OSS 前缀对象数，两者对不上时按[§4.7](#47-云端数据清除)的核对语句查残留，附件索引由上传时同步写入，没有回填命令。
- 429 突然变多：先区分是按地址的桶、登录失败预算还是全局写入上限触发，访问日志里按路由模式与来源统计；反馈与匿名上报的全局上限见[§4.4](#44-匿名入口与全局写入上限)，登录失败预算是正常防暴力破解，不要为了让某个用户马上重试就把 `ZHIXIN_LOGIN_FAIL_RATE` 调成 0。
- 清除云端数据返回 409 `conflict`：这个账号还有一次云端写入或另一轮清除没有结束，互斥状态只在当前进程里，等上一轮结束再重试即可；进程中途崩溃时没有残留的数据库标记，重新调用一次 `DELETE /v1/cloud` 会从剩下的部分继续，残留对象按[§4.7](#47-云端数据清除)核对。
- 流式回答不吐字：nginx 这个站点必须关 `proxy_buffering`，并保留 `proxy_http_version 1.1`。
- 客户端报 `model_not_allowed`：模型名不在路由表里，或者它的路由全部停用、来源停用、key 无法解密。打开后台看模型与来源的状态，`key_error` 表示 `ZHIXIN_SECRET_KEY` 换过，重新填写 key 即可。
- 客户端报 `upstream_failed`：所有来源都连不上，或者最后一个来源拒绝了服务端的 key。后台来源列表的“最近错误”给出状态码，再用“测试”确认地址与 key。
- 证书续期失败：80 端口必须开着，certbot 走 HTTP-01；`certbot renew --dry-run` 可以演练。
- 磁盘紧张：`du -sh /var/log/journal`、`/opt/zhixin/data/blobs`、`/var/lib/postgresql` 依次看，日志用 `journalctl --vacuum-size=200M` 收。

## 7. 协作规则

改动服务端代码按 [CONTRIBUTING](../CONTRIBUTING.md) 第 7 节在本地跑完 `gofmt`、`go mod tidy -diff`、`go vet`、`go test` 再推；动 `schema.sql` 或契约要先重新生成 sqlc 与 oapi-codegen 的产物并一起提交。部署完把 `systemctl status` 与 `/readyz` 的结果贴在群里，不要只说“推了”。

联调产生的账号一律用 `example.com` 邮箱，测完删账号（`DELETE /v1/me`）并清理 OSS 前缀与数据库行；要留样例数据的话在群里说一声，别让下一轮验收把测试数据当成真实用户的。改动别人的站点、系统包、sshd 配置、证书，先问管理员。密钥或口令如果出现在聊天、截图或提交里，当次就轮换，并检查有没有进 git 历史。
