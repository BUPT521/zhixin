# 知新 · 服务端运维手册

> 这份文档写给团队的其他人，也写给他们的 AI 助手：服务端有哪些资源、地址是什么、谁能做什么、配置放在哪、常见操作怎么执行。密钥、数据库口令与模型 key 不写在这里，只写在服务器的 `/etc/zhixin/api.env` 与管理员私有的运维注记里，因为仓库是公开的。工程结构与接口见 [README](README.md)，部署取舍见 [ADR-0009](../docs/adr/0009-API后端采用Go与分层框架.md) 第 4 条与第 7 条，接口契约见 [api/openapi.yaml](api/openapi.yaml)。

## 2. 权限

| 角色 | 持有什么 | 能做什么 |
|---|---|---|
| 陈思源（管理员） | 阿里云控制台、DNS、OSS 的 RAM 账号、DeepSeek 的 key、服务器 root | 全部；只有他能建实例、改 DNS、换密钥、做恢复演练 |
| 其他成员 | 各自一把 SSH 公钥授权到服务器 | 看日志、跑命令、部署自己改的服务端代码；不动机器上的其他站点 |
| AI 助手 | 各自一把无口令密钥，本机 `~/.ssh/config` 里一个别名 | 与服务端开发、联调、排障有关的一切命令；每次执行都是新进程 |
| 客户端 | 不含任何服务端密钥 | 用账号密码换访问令牌，拿令牌调同步、备份与模型代理 |

数据库口令、OSS 密钥与模型 key 只有两种流转方式：由管理员直接写进服务器的 `api.env`，或者由管理员写到自己的私有目录再从那里拷贝。这两种方式都不经过仓库、不经过聊天记录之外的任何地方。

### 2.1 AI 助手接入的四步

第一次接入按下面四步走，已接入过的直接跳到第 4 步验证。

1. 在本机生成一把专用密钥，不要复用 GitHub 或别的机器的私钥：

   ```bash
   ssh-keygen -t ed25519 -N "" -C "<你的名字>-zhixin" -f ~/.ssh/id_ed25519_zhixin
   ```

   Windows 的 PowerShell 传空口令有坑：`-N ""` 会被吞掉，结果密钥带了奇怪的口令。稳妥的做法是用 `cmd /c` 或 .NET 的 `ProcessStartInfo.ArgumentList` 传参，生成之后用 `ssh-keygen -y -P "" -f <私钥>` 验证，能直接打印出公钥就说明没有口令。

2. 把 `<私钥>.pub` 的内容发给陈思源，由他追加到服务器 root 的 `authorized_keys`（或者你自己的账号）。

3. 在本机 `~/.ssh/config` 里加一段：

   ```
   Host zhixin-dev
     HostName 112.125.89.75            # 写 zhixin.chensiyuan.work 也行
     User root
     IdentityFile ~/.ssh/id_ed25519_zhixin
     IdentitiesOnly yes
     ServerAliveInterval 30
   ```

4. 验证，`BatchMode=yes` 能过就说明不需要任何人工输入：

   ```bash
   ssh -o BatchMode=yes -o ConnectTimeout=10 zhixin-dev 'hostname; whoami; systemctl is-active zhixin-api'
   ```

撤销是删掉 `authorized_keys` 里对应的那一行（按 `-C` 备注找），不需要改 sshd。密钥不设口令，代价是这个文件等同于服务器上的那个账号，只能放在自己的开发机上；要带口令就得先启用 ssh-agent 并 `ssh-add` 一次，之后仍然可以非交互使用。

### 2.2 AI 助手能做什么、不能做什么

- 不能做的事：交互式程序（`vim`、`tmux`、`htop`、`psql` 的交互模式）、需要终端输入的 `sudo` 密码提示、二次验证提示。每次命令都是独立进程，`cd`、环境变量、后台任务都不跨命令保留，长任务要么用 `nohup`/`systemd` 落到服务上，要么一条命令跑完。
- 应做的事：改配置文件前先 `cp` 一份带时间戳的备份；动 nginx 先 `nginx -t` 再 reload；动数据库先确认是不是空库；测试数据用 `example.com` 邮箱并留下清理命令。
- 现在的授权是 root，理由是这台机器上的数据都可以重建。公测前应收窄到能写 `/opt/zhixin`、`/etc/zhixin` 并重启本单元的普通账号，改 sshd 与系统升级留给管理员。
- 服务器 sshd 目前同时允许密钥登录与密码登录，root 也能直接登录。2026-11-17 评估后保留这个配置：这台机器的数据都能重建，收紧的收益不如改配置时把自己锁在门外的风险；要收紧时先在另一条连接上验证新配置，再关闭密码登录。

Windows 上通过 PowerShell 远程执行时还有一个坑：这里的字符串按 CRLF 发送，远端 `bash` 会把 `\r` 当成参数的一部分，`free -m`、`head -2` 这类命令会报“invalid option”。可靠写法是加一层过滤：

```powershell
$script | ssh zhixin-dev "tr -d '\r' | bash -s"
```

## 3. 配置

全部来自环境变量，代码里的清单与默认值见 [README 的配置表](README.md#配置)。第一套实例的实际值如下，带“见 api.env”的项是密钥或口令，不写在这里。

| 变量 | 生产值 | 说明 |
|---|---|---|
| `ZHIXIN_ADDR` | `127.0.0.1:8080` | 只监听回环，对外一律经 nginx |
| `ZHIXIN_DATABASE_URL` | 见 `api.env` | `postgres://zhixin:<口令>@127.0.0.1:5432/zhixin?sslmode=disable` |
| `ZHIXIN_BLOB_DIR` | `/opt/zhixin/data/blobs` | 配了 OSS 时不用，只在没配对象存储时生效，现在是空的 |
| `ZHIXIN_APPLY_SCHEMA` | `0` | 空库首次启动临时设 `1`，建完必须改回 `0` |
| `ZHIXIN_TIMEZONE` | `Asia/Shanghai` | 模型额度的自然日按这个时区切 |
| `ZHIXIN_S3_ENDPOINT` | `oss-cn-beijing.aliyuncs.com` | 不带协议，https 由 `ZHIXIN_S3_USE_SSL` 决定 |
| `ZHIXIN_S3_BUCKET` | 见 `api.env` | 私有 bucket，启动与 `/readyz` 会检查它是否存在 |
| `ZHIXIN_S3_REGION` | `cn-beijing` | OSS 签名需要 |
| `ZHIXIN_S3_USE_SSL` | `1` | OSS 公网端点走 https |
| `ZHIXIN_S3_ACCESS_KEY` | 见 `api.env` | RAM 子账号，只授这一个 bucket |
| `ZHIXIN_S3_SECRET_KEY` | 见 `api.env` | 同上 |
| `ZHIXIN_LLM_API_KEY` | 见 `api.env` | DeepSeek 的 key，只在服务端持有 |
| `ZHIXIN_SMTP_*` | 见 `api.env` | 发信服务器、发件人与口令；不配置时邮箱验证与找回密码返回 503，其余功能不受影响 |
| `ZHIXIN_CODE_SECRET` | 见 `api.env` | 验证码 HMAC 的密钥，用随机值并固定下来；不配置时每次重启都会让未使用的验证码失效 |
| 其余变量 | 用代码默认值 | 限流、上限、保留份数、额度等，见 README 的表 |

三档存储形态：不设 `ZHIXIN_DATABASE_URL` 时全部在内存里，进程退出即丢，只能本地开发与测试；设数据库而不设 `ZHIXIN_S3_ENDPOINT` 时字节写 `ZHIXIN_BLOB_DIR`；两者都设时字节走 OSS。本地起一套最快的办法是 `cd server && go run ./cmd/zhixin-api`，不设任何变量就用内存存储，`curl localhost:8080/healthz` 应当返回 200。

容易配错的四件事：`schema.sql` 没有 `IF NOT EXISTS`，带着 `ZHIXIN_APPLY_SCHEMA=1` 重启会因为表已存在而失败；`ClientSchemaVersion` 必须与 [01](../docs/01-ER数据模型.md) 的编号一致，客户端升 schema 时同一个 push 改；对象存储的端点不带 `https://` 前缀；`ZHIXIN_ACCESS_TTL` 必须短于 `ZHIXIN_REFRESH_TTL`，否则启动报错。

## 4. 常用操作

```bash
# 状态与日志
systemctl status zhixin-api --no-pager
journalctl -u zhixin-api -n 100 -o cat
curl -s https://zhixin.chensiyuan.work/readyz

# 重启与配置生效（助手用 sed 或 printf 改，不要用 vim 这类交互程序）
sed -i 's/^ZHIXIN_LLM_MODELS=.*/ZHIXIN_LLM_MODELS=deepseek-flash/' /etc/zhixin/api.env
systemctl restart zhixin-api

# 发布：开发机上交叉编译，传上去，重启
cd server
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath -ldflags="-s -w" -o zhixin-api-linux-amd64 ./cmd/zhixin-api
scp zhixin-api-linux-amd64 zhixin-dev:/opt/zhixin/bin/zhixin-api.new
ssh zhixin-dev 'mv /opt/zhixin/bin/zhixin-api.new /opt/zhixin/bin/zhixin-api && chmod +x /opt/zhixin/bin/zhixin-api && systemctl restart zhixin-api && sleep 1 && curl -s localhost:8080/readyz'

# 回滚：把上一个可执行文件换回来
ssh zhixin-dev 'ls -l /opt/zhixin/bin/'

# 数据库
su - postgres -c "psql -d zhixin -c '\dt'"
su - postgres -c "psql -d zhixin -tAc 'SELECT count(*) FROM app_user'"

# 对象存储（bucket 名从 api.env 读，不写进文档）
export OSS_ACCESS_KEY_ID=$(grep ^ZHIXIN_S3_ACCESS_KEY /etc/zhixin/api.env | cut -d= -f2)
export OSS_ACCESS_KEY_SECRET=$(grep ^ZHIXIN_S3_SECRET_KEY /etc/zhixin/api.env | cut -d= -f2)
BUCKET=$(grep ^ZHIXIN_S3_BUCKET /etc/zhixin/api.env | cut -d= -f2)
/opt/zhixin/bin/ossutil-2.1.0-linux-amd64/ossutil ls -r "oss://$BUCKET" -e oss-cn-beijing.aliyuncs.com --region cn-beijing

# 证书与反代
certbot certificates
nginx -t && systemctl reload nginx
```

备份是 `pg_dump` 加上 OSS 里 `backups/` 与 `attachments/` 两个前缀下的对象，删号与删除备份会按前缀清理，两处必须一起备。恢复的顺序是装数据库与可执行文件、还原 dump、把对象按原前缀传回 bucket、写回 `api.env`、启动服务、`curl /readyz` 确认。公测准备阶段要做一次完整演练，用备份重建一台可用实例，日期与结果写进结题材料。

## 5. 排障

- `/healthz` 返回 200 但 `/readyz` 不 ready：数据库连不上、bucket 不存在、OSS 密钥或端点不对，三者之一。先看 `journalctl -u zhixin-api -n 30 -o cat`，启动日志会打印用的是哪种存储与哪个 endpoint。
- 502 或 504：`zhixin-api` 没起来，或者 nginx 里的反代地址与 `ZHIXIN_ADDR` 不一致，先 `systemctl is-active zhixin-api`。
- 上传大备份返回 413：nginx 的 `client_max_body_size` 与服务的 `ZHIXIN_MAX_BACKUP_BYTES` 要对得上，前者必须不小于后者。
- 流式回答不吐字：nginx 这个站点必须关 `proxy_buffering`，并保留 `proxy_http_version 1.1`。
- 证书续期失败：80 端口必须开着，certbot 走 HTTP-01；`certbot renew --dry-run` 可以演练。
- 磁盘紧张：`du -sh /var/log/journal`、`/opt/zhixin/data/blobs`、`/var/lib/postgresql` 依次看，日志用 `journalctl --vacuum-size=200M` 收。

## 6. 协作规则

改动服务端代码按 [CONTRIBUTING](../CONTRIBUTING.md) 第 7 节在本地跑完 `gofmt`、`go mod tidy -diff`、`go vet`、`go test` 再推；动 `schema.sql` 或契约要先重新生成 sqlc 与 oapi-codegen 的产物并一起提交。部署完把 `systemctl status` 与 `/readyz` 的结果贴在群里，不要只说“推了”。

联调产生的账号一律用 `example.com` 邮箱，测完删账号（`DELETE /v1/me`）并清理 OSS 前缀与数据库行；要留样例数据的话在群里说一声，别让下一轮验收把测试数据当成真实用户的。改动别人的站点、系统包、sshd 配置、证书，先问管理员。密钥或口令如果出现在聊天、截图或提交里，当次就轮换，并检查有没有进 git 历史。
