# 知新 · 服务端运维手册

> 这台实例上有哪些资源、谁拿什么权限、配置放在哪，写在这一份里。具体地址、口令、密钥与证书内容不写进仓库（仓库公开），真实值只写在服务器上的 `/etc/zhixin/` 与管理员私有的运维注记里。工程结构与接口见 [README](README.md)，部署取舍见 [ADR-0009](../docs/adr/0009-API后端采用Go与分层框架.md) 第 4 条与第 7 条，接口契约见 [api/openapi.yaml](api/openapi.yaml)。

## 1. 资源

| 资源 | 现在的内容 | 真实值写在哪 |
|---|---|---|
| 云主机 | 一台阿里云 ECS，Debian 13，2 vCPU、1.6 GB 内存、40 GB 磁盘 | 阿里云控制台 |
| 应用 | 单个静态可执行文件 `zhixin-api`，由 systemd 单元 `zhixin-api.service` 拉起，只监听回环地址 | 服务器 `/opt/zhixin/bin/` 与 `/etc/systemd/system/` |
| 数据库 | PostgreSQL 17，用发行版包安装，库与角色都叫 `zhixin`，只在回环地址监听 | 服务器 `/etc/postgresql/` 与 `/etc/zhixin/api.env` |
| 对象存储 | 阿里云 OSS 的私有 bucket，按 S3 兼容接口访问，放整库备份与附件字节 | 服务器 `/etc/zhixin/api.env` 与阿里云控制台 |
| 域名与证书 | 一个子域指向这台机器，证书由 certbot 申请并自动续期 | DNS 控制台与 `/etc/letsencrypt/` |
| 反向代理 | 系统自带的 nginx，其中有单独一个 server 块只服务本项目 | 服务器 `/etc/nginx/sites-available/` |
| 模型提供方 | DeepSeek 的 key，只在服务端持有，客户端换成自己的访问令牌调用代理 | 服务器 `/etc/zhixin/api.env` |
| 持续集成 | GitHub Actions 执行服务端的格式检查、静态检查与测试 | 仓库 [ci.yml](../.github/workflows/ci.yml) |

有两件事会影响以后的操作。第一，这台机器只连得上部分软件源，Docker Hub、gcr.io 与 go.dev 都不通，因此构建放在开发机上交叉编译，不在服务器上装 Go 工具链。第二，系统装了 Docker 但没有在跑，第一套实例不依赖它；镜像源里只有部分仓库可拉，将来要容器化时先确认镜像能下下来。

## 2. 授权方式

### 2.1 管理员

管理员一个人持有阿里云控制台、DNS、OSS 的 RAM 账号、DeepSeek 的 key 与服务器 root，不设第二位管理员（[04 第 5 节](../docs/04-长期路线图.md#5-决定) D7）。数据库口令、对象存储密钥、证书与备份介质的存放位置，以及主机失联、数据库损坏、对象存储不可用三种情况下的恢复步骤，由管理员写在仓库之外的私有目录。

### 2.2 AI 助手调试

给 AI 助手的是非交互的 SSH 通道，不是交互式会话，具体做法有三条。

- 密钥：ed25519 专用密钥，无口令；私钥只在管理员开发机的 `~/.ssh/` 下，公钥追加到服务器 root 的 `authorized_keys`。
- 主机别名：写在开发机的 `~/.ssh/config` 里，用 `BatchMode=yes` 验证过能直连；每次执行都是新进程，状态不跨命令保留。
- 撤销：删掉 `authorized_keys` 里对应的那一行即可，不需要改 sshd。
- 现在的授权是 root，理由是这台机器上的数据都可以重建、重建的成本低于来回提权的成本；公测前应收窄到一个只写 `/opt/zhixin` 与 `/etc/zhixin`、并能重启本单元的普通账号，或者保留 root 但把 sudo 与改 sshd 的动作留给管理员。

不用密码登录，是因为助手每次执行命令都拿不到终端，审批弹窗也已经关闭，口令提示与带口令的私钥都无法输入；这也是密钥不设口令的原因，代价是这个私钥文件等同于服务器的那个账号，只能在管理员自己的开发机上保存。

权限边界按下面四条执行。

- 只碰本项目的东西：`/opt/zhixin`、`/etc/zhixin`、`zhixin-api` 单元、`zhixin` 库与 nginx 里本项目那一个 server 块。
- 这台机器上还有别的站点与系统包，改动这部分之前先问管理员。
- 不改 sshd 配置、不做系统大版本升级、不动其他站点的证书。
- 联调用的测试数据一律用 `example.com` 邮箱，跑完删掉账号并清掉对象与库里的行，现在库里与 bucket 都是空的。

### 2.3 对象存储与客户端

对象存储给服务用的是 RAM 子账号，策略只允许这一个 bucket 的列举、读写与分片上传，不用主账号的 AccessKey。两个密钥只写进服务器的 `/etc/zhixin/api.env`，不进仓库。轮换的做法是建新的子账号密钥、改 `api.env` 里对应的两行、重启服务，旧的密钥在控制台禁用。

客户端不持有服务端的任何密钥：它用账号密码换访问令牌，再拿令牌调同步、备份与模型代理，模型代理由服务端替换成自己持有的提供方 key。

## 3. 配置

全部配置来自环境变量，清单与默认值见 [README 的配置表](README.md#配置)，这里只说三档存储形态与几个容易配错的地方。

- 存储分三档。不设 `ZHIXIN_DATABASE_URL` 时全部在内存里，进程退出即丢，只能用于本地开发与测试；设了数据库而不设 `ZHIXIN_S3_ENDPOINT` 时，字节写到 `ZHIXIN_BLOB_DIR` 指向的本机目录；两者都设时字节走 S3 兼容存储。第一套实例是数据库加 OSS。
- 建表开关。空库首次启动前把 `ZHIXIN_APPLY_SCHEMA` 设为 `1`，建完改回 `0`；`schema.sql` 不带 `IF NOT EXISTS`，带着 `1` 重启会因为表已存在而失败。
- 监听地址。`ZHIXIN_ADDR` 只写回环地址，对外访问一律经过 nginx，不直接把 8080 暴露到公网。
- 数据版本。`server.ClientSchemaVersion` 必须与 [01](../docs/01-ER数据模型.md) 开头的编号一致，客户端升 schema 时在同一个 push 里改这个常量，否则提交与备份会按版本不符拒绝。
- 密钥类变量。数据库连接串、OSS 的两个密钥、模型提供方 key 只写在服务器的 `api.env` 里，仓库里只有变量名与默认值。

## 4. 日常操作

- 看状态用 `systemctl status zhixin-api` 与 `curl -s https://<子域>/readyz`，日志用 `journalctl -u zhixin-api -n 100 -o cat`；访问日志只记路由、状态码、字节数与耗时。
- 发布是三步：开发机交叉编译，把可执行文件 `scp` 到 `/opt/zhixin/bin/zhixin-api`，再 `systemctl restart zhixin-api`。
- 回滚是把上一个可执行文件换回去再重启。表结构按 [ADR-0001](../docs/adr/0001-开发阶段不向下兼容.md) 直接重建，不写迁移，所以数据库结构变化要一起安排重建与数据处置。
- 备份是 `pg_dump` 加上 OSS 里 `backups/` 与 `attachments/` 两个前缀下的对象；删号与删除备份会按前缀清理，两处要一起备才有意义。
- 恢复的顺序是装数据库与可执行文件、还原 dump、把对象按原前缀传回 bucket、写回 `api.env`、启动服务、`curl /readyz` 确认就绪；公测准备阶段做一次演练，日期与结果写进结题材料。
- `/readyz` 不 ready 的常见原因是数据库连不上、bucket 不存在、OSS 的密钥或端点不对；`/healthz` 只说明进程活着，不能用来判断依赖是否可用。
