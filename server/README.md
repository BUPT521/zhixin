# 知新 · API 后端

> 本目录是知新的自建 API 服务，第一期负责账号与登录、整库备份与增量同步、模型请求代理（聊天与嵌入，可以配置多个来源），另外提供应用内的更新检查与反馈接口，以及管理模型来源、用量、账号与反馈的后台。为什么要有服务端、它不负责什么，见 [ADR-0008](../docs/adr/0008-取消单机边界引入账号同步与模型代理.md)；为什么用 Go、怎样分层，见 [ADR-0009](../docs/adr/0009-API后端采用Go与分层框架.md)。接口以 [api/openapi.yaml](api/openapi.yaml) 为准，本文只说明工程结构、约定与本地运行。

## 当前状态

路由由 `api/openapi.yaml` 经 `oapi-codegen` 生成到 `internal/api/`，`internal/server/routes.go` 只把生成的路由转发给各业务包的处理器；契约改了而转发没跟上时编译失败。账号、登录方式验证与找回密码、提交序列的推送、拉取、快照登记与压缩（`/v1/sync/snapshot`，[ADR-0043](../docs/adr/0043-服务端快照登记与提交序列压缩.md)）、整库备份的上传下载与保留份数、附件的上传下载与存在检查、模型代理的转发与额度都已经按契约实现。应用内的更新检查与反馈接口也已经在 2026-11-18 实现：`GET /v1/app/releases` 公开返回发布清单，`POST /v1/feedback` 公开接收反馈并写入 `feedback` 表，两者都不需要登录，取舍见 [ADR-0025](../docs/adr/0025-应用内更新检查与反馈的接口口径.md)。留存统计的服务端部分同日完成：登录账号按服务端收到的请求日期记活跃，未登录设备通过 `POST /v1/telemetry/active` 匿名上报，安装标识只保存 HMAC-SHA256，匿名数据按 180 天滚动删除；模型额度也支持按账号单独调整（`llm_quota` 表），调整不用重启服务（[留存统计](#留存统计)、[模型代理](#模型代理)）。账号管理于 2026-11-26 补上后台入口：管理员可以按邮箱或账号编号搜索账号、调整两类额度与注销账号，注销复用账号本人的清理流程，取舍见 [ADR-0078](../docs/adr/0078-管理后台的账号注销与额度管理.md)。同日后台补上反馈查看：管理员可以按关键字分页查看反馈、读取诊断摘要与删除单条，公开接口仍然只写不读，取舍见 [ADR-0079](../docs/adr/0079-管理后台的反馈查看.md)。留存统计的后台读取也在 2026-11-26 补上：后台增加“留存”页签，`GET /admin/v1/retention` 只读返回每日活跃与按首次出现日分组的 7 日、28 日留存，公开的上报接口仍然只写不读，取舍见 [ADR-0080](../docs/adr/0080-管理后台的留存视图.md)。存储分两种：不设 `ZHIXIN_DATABASE_URL` 时全部在内存里，进程退出后数据丢失，只能用于本地开发与联调；设置之后账号、会话、提交序列、备份元数据、反馈、活跃数据与用量入库（`internal/store/pg`，查询由 `sqlc` 从 `internal/store/queries` 生成），字节放对象存储（`internal/objectstore`）：设了 `ZHIXIN_S3_ENDPOINT` 用 S3 兼容存储，没设时落到 `ZHIXIN_BLOB_DIR` 指定的本地目录，进程重启都不丢。首次在空库上启动时设 `ZHIXIN_APPLY_SCHEMA=1`，服务会按 `internal/store/schema.sql` 建表，建完可以去掉。附件按内容寻址，服务端核对 SHA-256 之后保存，单个上限见配置表的 `ZHIXIN_MAX_ATTACHMENT_BYTES`，一个账号的全部附件另有总量上限 `ZHIXIN_MAX_ACCOUNT_ATTACHMENT_BYTES`，超限时上传返回 413 `storage_full`。

2026-11-18 的加固轮次把服务端的默认行为收紧：启动时自检生产配置（配置了数据库时验证码不能写进日志、验证码与匿名统计的 HMAC 密钥必须固定、带凭据的上游地址必须走 https），公开写入接口在按地址的桶之外增加全局上限，反馈按保留期每日清理，登录失败按规范化的登录方式计预算，密码哈希受 Argon2 内存预算约束，每个账号的会话数有上限并在每天清理过期会话，刷新令牌轮换后只保留固定 60 秒的重试宽限，附件增加账号总量配额，清除云端数据统一为 `DELETE /v1/cloud`，模型代理增加未验证登录方式拒绝、账号并发上限、响应体上限、额度预留与实例总预算，发布清单要求 HTTPS、SHA-256 和 Ed25519 签名。配置项见下表，跨模块取舍与代价见 [ADR-0028](../docs/adr/0028-服务端加固的默认拒绝与预算.md) 和 [ADR-0031](../docs/adr/0031-云端写入与托管模型的资源预算.md)。

2026-11-20 的加固轮次补上了四处写路径的窗口：嵌入缓存按账号记代次，清除云端数据之后，清除之前发出的嵌入请求写不回旧向量；刷新令牌的轮换与重放记录在同一个事务或同一把锁里完成；备份对象每小时窗口之外由后台对账清理没有元数据的遗留字节；注册增加实例级上限，超过保留期仍没有任何已验证登录方式的账号由每日清理删除。取舍与代价见 [ADR-0037](../docs/adr/0037-遗留写路径与公开入口的加固.md)。

`schema.sql` 在 2026-11-17 增加了 `auth_code` 表与 `app_user.email_verified_at`，在 2026-11-18 增加了 `feedback`、`user_active`、`install_active` 与 `llm_quota` 四张表，同日的加固轮次又增加了 `attachment`、`user_purge` 与 `session_refresh_used` 三张表与相应索引（`user_purge` 已在 schema 32 删除，见下文）。模型路由增加了 `llm_provider`、`llm_model` 与 `llm_route`，并按用途记录 `llm_usage` 与额度覆盖值，用途见[表结构](#表结构)。开发阶段不写迁移（[ADR-0001](../docs/adr/0001-开发阶段不向下兼容.md)），已有实例按当前 `schema.sql` 重建库；当时实例里只有联调数据。2026-11-19 又增加了 `embedding_cache` 表，保存按账号隔离的嵌入向量缓存（[ADR-0030](../docs/adr/0030-服务端不建检索索引.md) 第一步）。2026-11-20 增加 `llm_instance_usage`，把实例当天的模型用量从账号用量里分出来，删号不再减少实例预算（[ADR-0036](../docs/adr/0036-实例模型预算与账号用量分开.md)）。同日还增加 `embedding_cache_generation`，记录每个账号的缓存代次，清空云端数据时加一，清除之前发出的嵌入请求因此写不回旧向量（[ADR-0037](../docs/adr/0037-遗留写路径与公开入口的加固.md)）。2026-11-20 又把账号与登录方式拆开：`app_user` 只保留 `id`、`password_hash` 与 `created_at`，邮箱移进新表 `user_identity`，`auth_code` 的主键换成（用途，kind，identifier）且 `user_id` 允许为空（[ADR-0038](../docs/adr/0038-账号与登录方式分开.md)）。

模型代理按优先级与权重从多个来源选择路由，嵌入接口按路由配置拆批，聊天与嵌入分别计入账号额度。模型来源与路由可在[管理后台](#管理后台)配置，取舍见 [ADR-0029](../docs/adr/0029-模型来源路由与嵌入代理.md)。

服务端按 [ADR-0030](../docs/adr/0030-服务端不建检索索引.md) 的第一步实现了嵌入向量缓存与查找接口：检索索引仍由客户端维护，服务端只承担“模型与文本到向量”这一层，换机、索引重建与切换模型时先查缓存、只补算未命中的片段。`POST /v1/llm/embeddings/lookup` 按账号与对外模型返回已经算过的向量，`POST /v1/llm/embeddings` 带 `X-Zhixin-Embedding-Cache: 1` 时写入缓存；缓存按账号隔离、有字节上限，随清除云端数据与删除账号一起删除。客户端已于同日接入：索引刷新先按 SHA-256 归并相同片段，再调查找接口取回命中的向量，只嵌入未命中的部分；写缓存标记只在登录且自动同步开启时带上。旧版客户端不调用查找接口，行为不变。

CI 使用临时 PostgreSQL 实例执行服务端存储测试；在开发机上可以设置 `ZHIXIN_TEST_DATABASE_URL` 执行同一组用例，连接串须指向允许重建表的专用测试库。

账号保留时可以单独清空云端数据：`DELETE /v1/cloud` 依次删除该账号的全部备份、提交序列、附件与对象存储里遗留的字节，成功返回 204，可重复调用，中途失败时重试从剩下的部分继续；清除期间这个账号的写入请求返回 409 `conflict`，客户端退避之后重试，账号、会话与本机数据都不受影响。原来的 `DELETE /v1/backups` 与 `DELETE /v1/sync/commits` 仍然保留，分别清空备份与提交序列；客户端设置页的“清除云端数据”改为调用 `DELETE /v1/cloud`，并在完成后显示状态、询问是否恢复自动同步。

第一套实例已经在一台单机 Debian 13 上跑起来，备份与附件的字节放阿里云 OSS 的 S3 兼容接口，部署方式见[部署与凭据](#部署与凭据)。客户端已经接入登录、登录方式验证、找回密码、整库备份、按提交的增量同步与“知新服务”模型来源，首次同步只上传云端还没有的行的取舍见 [ADR-0023](../docs/adr/0023-首次同步上传基线.md) 与[改进方案 3.6](../docs/数据版本系统对照git的改进方案.md)。更新检查与反馈的服务端接口也于 2026-11-18 就绪，应用内的提示与入口由吴闻杰在 M1 接入；接下来的顺序是两台设备的同步走查与限额调整。登录方式验证与找回密码按 [ADR-0009](../docs/adr/0009-API后端采用Go与分层框架.md) 第 5 条已经落地。

PostgreSQL 存取用 `pgx` 加 `sqlc` 生成，契约用 `oapi-codegen` 生成并挂到标准库路由上，登录与刷新令牌用 `golang.org/x/time/rate` 限流，对象存储用 `minio-go` 访问，依赖清单与理由见 [ADR-0015](../docs/adr/0015-服务端引入代码生成与限流依赖.md) 与 [ADR-0016](../docs/adr/0016-对象存储与附件接口.md)。生成代码与客户端一样提交入库，提交前重新生成并核对没有差异；生成命令在 `server/` 目录下执行，`api/cfg.yaml` 里的输出路径相对这个目录：

```bash
cd server
go run github.com/oapi-codegen/oapi-codegen/v2/cmd/oapi-codegen@v2.8.2 -config api/cfg.yaml api/openapi.yaml
go run github.com/sqlc-dev/sqlc/cmd/sqlc@v1.31.1 generate
```

## 表结构

服务端 PostgreSQL 的表与索引以 [internal/store/schema.sql](internal/store/schema.sql) 为唯一真相，本节只说明用途；客户端本机 SQLite 的表在 [01](../docs/01-ER数据模型.md)，两份文档不互相复制。开发阶段不写迁移（[ADR-0001](../docs/adr/0001-开发阶段不向下兼容.md)），结构变化时按当前文件重建库。

2026-11-18 的加固轮次新增了三张表，其中 `user_purge` 已随 schema 32 删除，现在只剩两张：

| 表 | 用途 | 关键列与约束 |
|---|---|---|
| `attachment` | 附件索引，按账号与内容哈希去重，用于账号附件总量配额；可空的 `orphaned_at` 记旧快照附件让位的时间，让位中的行仍然计入配额 | `user_id` 外键级联删除，`sha256`、`size`、`orphaned_at`，主键 `(user_id, sha256)`；对象字节仍在 `attachments/<账号>/<sha256>`，删号时按前缀清理 |
| `session_refresh_used` | 已用刷新令牌的摘要与重试宽限，支撑轮换与 60 秒宽限 | `token_hash` 主键，`session_id` 与 `user_id` 外键级联删除，`request_id`，`rotated_at`、`grace_until` 与轮换前后的访问令牌、刷新令牌摘要；重放不带匹配 `request_id` 或超出宽限时撤销该账号全部会话与模型代理密钥并记录安全事件 |

同轮新增的索引是 `session(refresh_expires)`、`session(user_id, created_at DESC)` 与 `auth_code(expires_at)`。字段与索引以 `schema.sql` 为准，本节只用于说明用途，不复制建表语句。

2026-11-20 增加 `user_identity`，一个账号的联系方式各占一行；`auth_code` 改成按登录方式保存，`user_id` 允许为空，索引相应换成 `auth_code(expires_at)` 与 `auth_code(user_id)`：

| 表 | 用途 | 关键列与约束 |
|---|---|---|
| `user_identity` | 账号的登录方式：邮箱现在唯一在用的种类，手机号与微信的位置已经留好 | `user_id` 外键级联删除，`kind` 的 check 约束为 `email`、`phone`、`wechat`，`identifier` 是规范化之后的值，`verified_at` 为空表示还没有确认；`(kind, identifier)` 唯一，一条联系方式只能属于一个账号；`(user_id, created_at)` 支撑账号页按顺序列出 |
| `auth_code` | 按登录方式保存的验证码，确认登录方式与找回密码共用 | 主键（用途，kind，identifier），`user_id` 外键可空且删号时级联删除，只存 HMAC-SHA256；用途的 check 约束为 `verify_contact` 与 `reset_password` |

2026-11-20 的加固轮次增加 `embedding_cache_generation`：每个账号一行缓存代次，清空云端数据时加一，嵌入请求在写入事务里比较代次，清除之前发出的请求因此写不回旧向量（[ADR-0037](../docs/adr/0037-遗留写路径与公开入口的加固.md)）。

2026-11-19 增加了 `embedding_cache` 表，保存按账号隔离的嵌入向量缓存（[ADR-0030](../docs/adr/0030-服务端不建检索索引.md)）：

| 表 | 用途 | 关键列与约束 |
|---|---|---|
| `embedding_cache` | 嵌入向量缓存，消除换机、索引重建与切换模型时的重复嵌入；属于派生数据，可以从业务库与嵌入服务重建，不进入数据包与整库备份 | `user_id` 外键级联删除，`model` 是对外模型名，`text_hash` 是片段文本的 SHA-256 小写十六进制，`dim` 与 `vector`（FP16 小端序）按长度 CHECK 绑定，主键 `(user_id, model, text_hash)`；`(user_id, last_used_at)` 支撑每账号的字节上限淘汰，`model` 上的索引支撑删模型时清理 |

`embedding_cache` 的表与索引同样以 `schema.sql` 为准；它不属于业务数据，重建库之后客户端重新查缓存、补算未命中的片段即可。

`llm_route_usage` 按自然日、用途、对外模型、来源编号和来源侧模型名保存统计计数，其中估算 Token 是结算 Token 的一部分，字段中没有账号标识或请求内容。2026-11-24 为缓存命中统计增加两列：`input_tokens` 是来源报告的输入量之和，`cached_tokens` 是其中命中上游上下文缓存的部分，来自 Responses 的 `usage.input_tokens_details.cached_tokens`；没有报告输入量的请求这两列为 0，计算命中占比时按有数据的请求单独汇总（方案第 7 节）。2026-11-26 再加八列，同一组数字按这次请求实际执行的第一条路由与前面尝试失败后接手的路由分成两栏：`first_input_tokens`、`first_cached_tokens`、`failover_input_tokens`、`failover_cached_tokens` 是两栏的输入量与命中量，`first_input_reports`、`first_cached_reports`、`failover_input_reports`、`failover_cached_reports` 是两栏的上报条数。上报条数用来分开“来源报了 0”与“来源没有给这个字段”，前者是这次确实没有命中，后者只是这次拿不到命中数据，两者的差额在后台显示为缺报，命中率与上报覆盖率因此各算一套，不会把缺报读成零命中。`input_tokens` 与 `cached_tokens` 仍是两栏之和。已有实例需要按当前 `schema.sql` 重建库，步骤见[运维手册](运维手册.md#49-自动部署与回滚) 与 [ADR-0057](../docs/adr/0057-服务端改表清空重建.md)。

2026-11-21 为同步序列的快照与压缩增加了三处结构（[ADR-0043](../docs/adr/0043-服务端快照登记与提交序列压缩.md)）：`sync_head` 增加 `trimmed_through`，记录已经删除到哪个序号，保留下界等于它加一；新增 `sync_snapshot` 保存账号当前的快照指针；新增 `sync_commit_seen` 保存已经接收过的提交身份，压缩删除旧提交之后仍然按它去重。同一天还为提交的一致性摘要给 `sync_commit` 增加可空列 `state_digest`（[改进方案 3.5](../docs/数据版本系统对照git的改进方案.md)）：客户端只在推送完成且本机没有待推送提交时带上，服务端原样保存、不解析，拉取时原样带回，没有带的提交这一列为空。之后为快照附件的回收与设备名册增加了两张表（[ADR-0047](../docs/adr/0047-快照附件回收与压缩前的客户端门槛.md)、[ADR-0048](../docs/adr/0048-设备名册与提交来源的别名.md)）：`sync_snapshot_orphan` 记录被替换下来的旧快照附件，`sync_device` 保存账号的设备名册，压缩之前按名册检查有没有设备还没声明 `snapshot` 能力。已有实例按当前 `schema.sql` 重建库，不写迁移（[ADR-0001](../docs/adr/0001-开发阶段不向下兼容.md)）。

## 约定

- 路径带 `/v1` 前缀，请求与响应用 JSON。错误一律是 `application/problem+json`，`code` 取 [契约](api/openapi.yaml) 里的 `ProblemCode` 枚举，客户端按 `code` 分支，`detail` 只给开发者看，不能写入学习内容、SQL、令牌或路径。
- 响应统一带 `X-Content-Type-Options: nosniff` 与 `Cache-Control: no-store`：接口响应里可能出现账号信息与学习数据，禁止浏览器猜测内容类型，也禁止中间层缓存。
- JSON 请求体拒绝未知字段与多余内容，超过上限返回 413。读取请求体时，两次读到数据之间最多等待 `ZHIXIN_BODY_IDLE_TIMEOUT`（默认 60 秒），超时中断本次请求；读完、请求体关闭或出错时清除这个时限，不影响之后的 SSE 响应。
- 中间件顺序固定为 request_id、访问日志、安全响应头、异常恢复、鉴权、上传限流、业务；401 与 429 都带 `request_id` 并进访问日志。上传限流在鉴权之后，按账号计数，备份与附件两类请求共用一个桶。
- 鉴权默认要求 Bearer：中间件按路由模式 `r.Pattern` 判断，只有契约里标了 `security: []` 的操作公开，即存活与就绪检查、注册、登录、刷新令牌、找回密码与重设密码、发布清单、反馈与匿名活跃上报，其余一律要求访问令牌。Bearer 的凭据以 `zx_` 开头、共 39 个字符且末尾校验码对得上时按模型代理密钥校验，只接受 `/v1/llm` 下的模型接口，访问其余受保护路由回 403 `key_scope_denied`（[ADR-0063](../docs/adr/0063-模型代理接入密钥.md)）。公开操作表集中在一处（`internal/routepolicy`），内容与契约的 `security: []` 对齐；增删接口时要改契约，并在同一个 push 里同步这张表。令牌无效返回 401，读取令牌时存储故障走统一的 500 problem，两者都带 `request_id`。
- 来源地址只信配置的反向代理网段：`ZHIXIN_TRUSTED_PROXIES` 写逗号分隔的 IP 或 CIDR，只有直接对端落在其中时才取 `X-Forwarded-For` 的最后一项作为客户端地址，前面的项由客户端自己写，不可信；没有配置时只看直接对端，客户端自己写这个头也换不到另一个限流桶。IPv6 地址按 /64 归并成同一个桶，因为一台机器可以用同一个 /64 内的不同地址绕过按地址的限流。
- 登录失败按规范化的登录方式计预算，默认每秒补 0.017 个令牌、最多攒 10 个，超出时短暂返回 429，登录与删号的密码确认共用一个口径；argon2id 密码哈希同时占用的内存受 `ZHIXIN_ARGON2_MEMORY_BUDGET_MIB` 约束，并发哈希数由预算除以单次约 19 MiB 得出，超出时排队而不是继续申请内存。
- 每个账号最多保留 `ZHIXIN_MAX_SESSIONS_PER_USER` 个会话，新登录超过上限时删最旧的，过期会话每天清理一次。刷新令牌轮换之后，旧刷新令牌只在固定的 60 秒宽限内、且客户端带同一个 `request_id` 重试时才被接受；其他重放按盗用处理，撤销这个账号的全部会话与模型代理密钥并记录安全事件，因此客户端每次刷新都要带 `request_id`。
- 删除账号要重新提交当前密码：`DELETE /v1/me` 的请求体是 `{"password":"..."}`，密码错误返回 401 `invalid_credentials`，应用只提示密码错误并保留当前登录。清除云端数据统一走 `DELETE /v1/cloud`，清除期间这个账号的写入返回 409 `conflict`，见[同步协议](#同步协议)。
- 模型代理在账号没有任何一种已验证登录方式时返回 403 `contact_unverified`；每个账号同时最多 `ZHIXIN_LLM_CONCURRENT_PER_USER` 个托管请求，整个实例的在途字节受 `ZHIXIN_LLM_MAX_INSTANCE_BYTES` 约束，非流式响应不超过 `ZHIXIN_LLM_MAX_RESPONSE_BYTES`，流式响应有空闲与总时限；额度在请求开始时预留、按实际用量结算，账号用途额度与实例当日总预算任一用完都返回 429 `quota_exceeded`。
- 附件的单个上限、账号总量上限与 `storage_full` 见[附件与备份的字节](#附件与备份的字节)；发布清单的地址必须是 https、`sha256` 与 `signature` 均必填，见[更新检查](#更新检查)。
- `/admin/v1/` 下的管理操作按匹配到的路由校验独立的管理令牌，配置方式见[管理后台](#管理后台)。
- 契约绑定的参数由生成的路由解析后传入处理器，缺 header 或参数不是整数由统一的错误处理函数返回 problem+json，处理器不再自己解析一遍；存储查询的参数统一用 `sqlc.arg`，日期与时间解析失败直接报错。
- 访问日志只记录路由模式、状态码、字节数与耗时，不记录请求体、查询串与请求头；模型代理不保存请求与回答正文，只记 token 数。
- 服务端接受的客户端数据版本是 `server.ClientSchemaVersion`，必须与 [01](../docs/01-ER数据模型.md) 开头的 schema 编号一致。客户端升 schema 时同一个 push 里改这个常量；其他版本的提交与备份一律拒绝，与 [ADR-0002](../docs/adr/0002-本地数据不做迁移.md) 相同。
- 1.0.0 之前接口与表结构都可以直接改，不写迁移，客户端与服务端一起升级（[ADR-0001](../docs/adr/0001-开发阶段不向下兼容.md)）。

## 同步协议

服务端为每个账号保存一条线性的提交序列，不合并、不解析内容。客户端推送时带上自己所知的 `base_seq`，等于服务端 head 才追加，否则返回 409 和最新 head；客户端先拉取 `after=<本机已同步位置>` 的提交，在本机按现有的净变化应用为新的本地提交（撤销与数据版本页因此照常可用），再重新推送。每条提交带 `uid`：它是客户端在用户动作发生时生成的提交身份，标识一条提交，不按命令参数生成，也不复用，服务端按它永久去重，已经收到过的提交会被跳过，所以丢失响应之后原样重试是安全的，同参数的不同提交不会互相顶掉（[ADR-0040](../docs/adr/0040-数据版本的提交身份与同步变基.md)、[ADR-0053](../docs/adr/0053-标识按身份顺序指纹分工并收拢提交标识.md)）。推送响应的 `seqs` 与请求里的 `commits` 按条数与顺序一一对应：新提交是服务端分配的序号，被当作重复跳过的提交回它在 `sync_commit_seen` 里记下的原序号，客户端据此判断整批重放（[ADR-0054](../docs/adr/0054-数据版本位置标记补强.md)）。每条提交必须给出 `kind`，取值与客户端的提交类型一致，即 `baseline`、`write`、`undo`、`restore`、`import` 与 `maintenance`，缺字段或取值不在其中返回 400 `invalid_request`；服务端只校验并原样保存，不据此解析内容，来源只看提交里的设备标识。每条提交还带客户端的 schema 版本，服务端只接受当前版本 32（`server.ClientSchemaVersion`），不符时返回 400 `invalid_request`，`extra.schema_version` 给出服务端接受的版本；`GET /v1/sync/head` 同样返回这个版本，客户端对照本机版本决定是否继续同步。同一字段在两台设备上并发修改时，后到达服务端的覆盖先到达的，被覆盖的值留在提交历史里；这条规则在 2026-11-18 的协议走查中确认可用，真机走查待内测阶段补做。客户端还可以在推送最后一条提交上带可选的 `state_digest` 与 `table_digests`，后者是“表名到 64 位十六进制值”的映射，服务端都只保存与回传、不解析，没有带的提交在响应里不出现这两个键。

客户端第一次同步时先拉取这个账号已有的全部提交并在本机应用，拉取时记下被远端提交触及过的表与主键，只把云端还没有的行作为一份或几份基线提交上传，全新设备不上传任何内容，之后只推送新提交，取舍见 [ADR-0023](../docs/adr/0023-首次同步上传基线.md) 与[改进方案 3.6](../docs/数据版本系统对照git的改进方案.md)。基线提交的来源记为 `system`、动作写“首次同步基线”，服务端与其他提交一样只做校验和保存，不区分基线；本机提交编号不进入提交内容；同步位置存在客户端库里的 `revision_cursor`（`sync.pushed` 与 `sync.server_head`），每个账号和服务实例组合各用一份本机库，重新登录时打开原空间并从原位置继续增量同步。清除全部数据会重建当前空间的本机库，下一次同步从空库开始。整库恢复之后本机补记一条差异提交，下一轮同步跳过旧位置、只把恢复前后的差异推上去，两个位置收敛到当前服务端位置与本机 `HEAD`，恢复之前的改动不会再从旧位置拉回来。提交里引用的附件在推送之后按哈希上传、拉取之后按哈希下载，服务端按内容寻址核对，业务行只保存哈希。同步推送与备份、附件上传共用按账号的写入速率，单条提交至多 2 MiB，单次请求至多 16 MiB，每账号提交序列预算为 256 MiB。超出请求大小返回 413 `payload_too_large`；超出序列预算时先按下一段的规则压缩，压缩之后仍然超出才返回 413 `storage_full`。客户端按字节和条数分批推送。PostgreSQL 拉取按 `ZHIXIN_SYNC_PULL_MAX_BYTES` 选出连续页，再读取正文，客户端以下一页起点之前的最后一个序号继续读取。如果游标的下一条旧提交单独就超出页上限，接口返回 413，由已备份本机数据的用户清除云端序列后重新上传基线。

每条提交还可以带一个可选的 `state_digest`（[改进方案 3.5](../docs/数据版本系统对照git的改进方案.md)）：客户端在推送完成、本机没有待推送提交的那一刻，把当前整库摘要附在最后一条提交上，摘要是全部业务行按“表名、主键、规范化整行”做 SHA-256 再求和的多重集哈希，64 位小写十六进制。服务端原样保存、不解析也不校验，拉取时原样带回；没有带摘要的提交在响应里不出现这个字段。其他设备拉到最新一条带摘要的提交、并且自己也没有待推送提交时比较本机摘要，不一致就在账号页显示“本机与云端不一致”并给出两个修复入口，同时写一条诊断记录；字段对旧客户端可省略，两者仍能互相收发提交。

服务端的提交序列可以压缩，压缩的基准是一份客户端上传的快照（[ADR-0043](../docs/adr/0043-服务端快照登记与提交序列压缩.md)）。已经同步到某个位置、没有待推送提交的设备，把当前投影按检查点格式压缩之后走 `PUT /v1/blobs/{sha256}` 当作附件上传，再用 `PUT /v1/sync/snapshot` 登记“序列 N 的快照是附件哈希 X、整库摘要是 D”。登记时 `seq` 必须在 1 与当前 head 之间，两个哈希都是 64 位小写十六进制，`sha256` 必须是这个账号已经上传、大小不超过单个附件上限的附件；位置比已经登记的快照小时返回 409，`extra.snapshot_seq` 给出当前位置，相同位置按幂等重试接受并刷新指针。服务端只保存最新一份快照指针，被替换下来的旧指针不再引用，附件字节的处理见本节最后一段与[表结构](#表结构)。

登记快照时服务端顺带压缩一次：快照位置及之前、服务端收到时间早于 `ZHIXIN_SYNC_COMPACT_KEEP`（默认 168 小时）的提交删除，保留下界 `earliest_seq` 跟着推进，它表示第一条仍然可以拉取的序号，没有删除过提交时为 1。`GET /v1/sync/head`、`GET /v1/sync/snapshot` 与 `GET /v1/sync/commits` 的响应都带 `earliest_seq` 与当前快照指针 `snapshot`（`seq`、`sha256`、`digest`、`created_at`），`GET /v1/sync/head` 另带压缩开关 `compact`，客户端据此判断要不要先下载快照、要不要上传快照。推送让账号超过 256 MiB 的提交序列预算时，服务端先做一次压缩：有快照就删掉快照位置及之前的全部提交，这一次不按保留期过滤，重新计算之后仍然超出才返回 413 `storage_full`；没有快照的账号维持原来的行为。这里的 256 MiB 只算提交序列与去重表的行，快照附件按附件配额单独计，两者不重复占用。

删除提交之前有两道检查（[ADR-0047](../docs/adr/0047-快照附件回收与压缩前的客户端门槛.md)）。`ZHIXIN_SYNC_COMPACT` 默认关闭，关闭时 `head` 的 `compact` 为假、客户端不上传整库快照，登记快照只写指针、预算压力也不删提交，仍然超出预算就返回 413 `storage_full`；打开之后还要看设备名册，账号最近 `ZHIXIN_SYNC_DEVICE_ACTIVE`（默认 720 小时）内出现过的设备里，只要有一台没有声明 `snapshot` 能力，两条删除路径都只写指针，不删提交，名册里没有任何设备时按可以压缩处理。常规压缩在保留期与快照位置之外还有第三条门槛：不越过同一活跃窗口内设备的最小 `synced_seq`，窗口之内落后的设备因此不会被压缩甩到 410；预算压力下的压缩不看这一条（[ADR-0054](../docs/adr/0054-数据版本位置标记补强.md)）。两端与开关的先后因此是：先部署会声明 `compact` 的服务端，再升级所有设备，最后打开开关；开关打开之前客户端不产生快照附件，“所有设备先升级”这一条由声明与名册共同保证。

客户端的拉取位置落在已经删除的区间时，接口返回明确的错误：`after + 1 < earliest_seq` 说明客户端要的下一条提交已经删除，`GET /v1/sync/commits` 返回 410，`code` 是 `history_compacted`，`extra` 给出 `after`、`earliest_seq`、`head` 与 `snapshot_seq`、`snapshot_sha256`、`snapshot_digest`。客户端按 `snapshot_sha256` 下载快照附件、导入本机、把同步位置改成 `snapshot_seq`，再把未推送的本机提交在快照之上重放，服务端的序列与快照本身不变。`after` 恰好等于 `earliest_seq - 1` 时照常增量返回；`after` 为 0 而保留下界大于 1 的首次同步同样返回 410，新设备应当先读 `head` 或拉取响应里的 `snapshot` 再下载。快照附件与业务附件共用账号附件总量配额；被替换下来的旧快照在宽限期之内继续计入配额，过了 `ZHIXIN_SYNC_SNAPSHOT_GRACE`（默认 24 小时）由下一次登记顺带删除对象存储字节与附件索引行，让位标记就是 `attachment.orphaned_at`，多台设备交替登记时账号占用因此有上限；客户端侧已经接入（[ADR-0046](../docs/adr/0046-客户端按快照浅克隆与重新克隆.md)）：首次同步按 `earliest_seq` 与快照做浅克隆，增量拉取遇到 410 时按快照重新克隆，服务端在 `head` 里声明压缩打开时空闲时把当前投影登记为快照。快照登记由已经同步到当前服务端位置、且没有待推送提交的客户端在同步收尾时做，同位置或更新位置已有快照时客户端跳过；服务端在收到第一份登记之前不删除任何提交。

清空一个账号的云端数据走 `DELETE /v1/cloud`：依次删除全部备份、提交序列、附件索引与对象存储里遗留的字节，可重复调用，失败之后重试从剩下的部分继续，返回 204。清除期间这个账号的写入请求返回 409 `conflict`，账号、会话与本机数据保留；下一次同步重新上传基线。互斥状态保存在进程内，服务端按单实例部署时覆盖全部写入入口（推送、附件上传、备份、快照登记、命名版本与设备别名），进程中途退出之后没有数据库标记可以接管，由用户重新发起一次 `DELETE /v1/cloud` 从剩下的部分继续；从崩溃到重试之间另一台设备推送的内容会在重试时一并清除。旧的 `DELETE /v1/sync/commits` 与 `DELETE /v1/backups` 仍然分别可用，只清空提交序列或备份，客户端设置页的“清除云端数据”改用 `DELETE /v1/cloud`。删除账号本身走 `DELETE /v1/me`，需要重新提交密码，删除之后账号、会话与云端数据一并消失。

同步请求还会维护账号的设备名册（[ADR-0048](../docs/adr/0048-设备名册与提交来源的别名.md)）。`GET /v1/sync/head`、`GET /v1/sync/commits`、`POST /v1/sync/commits` 与 `PUT /v1/sync/snapshot` 接受可选的 `X-Device-Id`（不超过 64 字符）与 `X-Sync-Capabilities`（逗号分隔的小写能力名，当前只有 `snapshot`），服务端按能力头整组替换这一台设备的快照能力、按请求推进设备位置，能力或位置确实变化时才更新最近出现时间，没有变化的一轮同步不写名册；别名保持用户设置的值。没有 `X-Device-Id` 的推送按提交里的设备标识补一行，快照能力、位置与别名都留空，旧版本客户端因此也会出现在名册里。带设备标识的拉取请求把 `after` 记成这台设备的 `synced_seq`，推送请求按 `base_seq` 推进它，确有新提交写入时再推进到当前 head，整批重放不推进到 head，任何情况下都不超过当前 head（[ADR-0054](../docs/adr/0054-数据版本位置标记补强.md)）。`GET /v1/sync/devices` 接受同样的两个头，先按请求更新名册再按最近出现时间倒序返回最多 50 条，刚登录、还没同步过的设备打开账号页时因此也能看到自己；`PUT /v1/sync/devices` 修改一台已知设备的别名，别名去掉首尾空白之后 0–64 个字符、空串表示清除，未知设备返回 404 `not_found`。名册随清除云端数据与删除账号一起清空，压缩门槛读的就是这份名册。

命名版本（[ADR-0054](../docs/adr/0054-数据版本位置标记补强.md)）走 `GET /v1/sync/refs` 与 `PUT /v1/sync/refs`：前者返回本账号全部命名版本，墓碑一并返回；后者请求体是两种形状之一，写入时带 `name`、`commit_uid` 与可选的 `note`，删除时带 `name` 与 `delete: true`。后写覆盖先写，不记冲突；名字先做 NFC 规范化，规范化之后最长 30 个字符，未删除的名字每账号最多 200 个，超限返回 400 `invalid_request`。名字已经是墓碑时，比删除时间更早的写入不会让它复活，返回的仍是墓碑。服务端不核对 `commit_uid` 是否存在，也不为命名版本保留被压缩的提交，所以服务端压缩之后新设备上的名字可能只剩标签；这两条接口与其它写接口一样要求登录，清除云端数据期间返回 409。

两台设备的走查在 2026-11-18 按这套协议完成了一遍，用例是 [sync_walkthrough_test.go](internal/server/sync_walkthrough_test.go)，用同一个账号的两次登录模拟两台设备：设备 A 以 `base_seq=0` 上传基线；设备 B 拉取 `after=0`、应用之后推自己的编辑；两台设备交替拉取与推送；两台设备基于同一个 head 修改同一行时，先到的成功、后到的得到 409 与最新 head，后到的设备拉取之后在本机应用为新的提交再推；丢失响应之后用同一个 `uid` 原样重推，head 与历史都不变、响应里的 `seqs` 回原来的序号；设备 A 上传附件之后设备 B 按哈希检查并取回；`DELETE /v1/sync/commits` 之后两台设备都从 0 重新上传基线。走查确认了本节写的规则：服务端只保证序列线性、不合并字段，同一字段并发修改时后到达的覆盖先到达的，被覆盖的值留在提交历史里，可以从数据版本页找回；真机上的两台设备走查仍待内测阶段补做。

## 附件与备份的字节

整库备份是客户端导出的 zip 原样保存，服务端只核对 `X-Content-SHA256` 与大小，不打开内容。附件走 `/v1/blobs/{sha256}`，路径里的 `sha256` 就是内容的哈希：`PUT` 把请求体写到临时文件并计算哈希，与路径一致才保存，`HEAD` 在同步前判断哪些附件已经上传过，`GET` 取回原始字节。两者都按账号隔离，键分别是 `backups/<账号>/<id>.zip` 与 `attachments/<账号>/<sha256>`，删除账号时按前缀清理；附件在同一个账号里按内容去重，不同账号之间不共享对象，因此 `HEAD` 也不会泄露别的账号有没有传过同样的内容。

设置了 `ZHIXIN_S3_ENDPOINT` 时用 S3 兼容存储，没设时写到 `ZHIXIN_BLOB_DIR`，不设数据库时用内存实现。上传的请求体先落到系统临时目录再入库，单份备份与附件的默认上限分别为 256 MiB 和 32 MiB，两个上传入口在读取请求体之前按单次上限预留临时空间，单个服务进程合计最多预留 1 GiB，用尽时返回 429。启用 PostgreSQL 的实例要求至少一种登录方式已经确认之后才接受同步、备份和附件写入，没有任何已验证方式时返回 403 `contact_unverified`。预签名直传的取舍见 [ADR-0016](../docs/adr/0016-对象存储与附件接口.md)，本期仍由服务端转发字节。

附件另有账号总量配额。每写入一个新对象之前，服务端按 `attachment` 表核对这个账号已用的字节数加上本次大小是否超过 `ZHIXIN_MAX_ACCOUNT_ATTACHMENT_BYTES`（默认 2 GiB），超过时返回 413 `storage_full`，`extra` 里带 `used_bytes` 与 `limit_bytes`，客户端提示用户清理附件或换一个账号；同一账号重复上传相同内容命中同一个对象与同一行索引，不重复计入总量。配额与用量读的是 `attachment` 索引，每次上传成功时同时写索引行；历史上只按对象前缀写入过字节、没有索引行的实例已随 schema 32 重建库清空，回填命令与 `ListAttachments` 查询一并删除（[数据库结构过度设计审查](../docs/数据库结构过度设计审查.md) 的 V6）。

备份的元数据与字节分两步写：上传先写对象再写行，删除与保留裁剪先删行再删对象，中断时只会留下没有元数据的对象，不会出现列表里有、下载失败的备份。删对象失败或请求被取消时，待删的 id 已经从库里消失，重试拿不到它们，所以服务按 `ZHIXIN_BACKUP_RECONCILE_INTERVAL`（默认 24 小时）对账一次：列出 `backups/` 下的对象，把库里查不到对应行、且写于一小时之前的对象删掉，一小时是给正在上传的备份留的窗口。

## 登录方式验证与找回密码

账号与登录方式分开放：`app_user` 只保存密码，邮箱这类联系方式在 `user_identity` 各占一行，取舍与代价见 [ADR-0038](../docs/adr/0038-账号与登录方式分开.md)。`kind` 的 check 约束已经写好 `email`、`phone`、`wechat` 三种，代码现在只写 `email`，注册与登录遇到识别出的手机号或微信按 `invalid_request` 拒绝。

注册与登录的请求体用 `identifier` 表示登录方式的值，服务端按值的形状识别种类并规范化：含 `@` 的按邮箱、转小写之后按 RFC 5322 的简单地址校验，符合可选加号加 6 至 20 位数字的按手机号，其余是无效输入。同一条联系方式已经登记时注册返回 409 `identifier_taken`。

注册之后的账号默认没有任何已验证的登录方式，`GET /v1/me` 返回 `{user_id, created_at, identities: [{id, kind, identifier, verified}]}`，其中 `verified` 全是 `false`。注册接口是公开的，除按来源地址限流外还有实例级上限（`ZHIXIN_REGISTER_GLOBAL_RATE` 与 `ZHIXIN_REGISTER_GLOBAL_BURST`），换地址也不能把未验证的账号刷满库；注册超过 `ZHIXIN_UNVERIFIED_KEEP_DAYS`（默认 7 天）仍没有任何一种已验证登录方式的账号由每日清理删除，登录方式、会话与验证码一并清掉，这个邮箱之后可以重新注册。

`POST /v1/me/identities/{id}/verification` 给指定的登录方式发一条六位数字验证码，`POST /v1/me/identities/{id}/verification/confirm` 用它把这条登录方式标为已确认；`id` 取自 `GET /v1/me`，只认当前账号名下的登录方式，别人的编号返回 404。已经确认过的再次请求直接返回 204，不重复发信。

`POST /v1/auth/password/forgot` 向账号登记的登录方式发送重设验证码，尚未确认的联系方式也可找回账号。`POST /v1/auth/password/reset` 在同一事务中消费验证码、确认收到验证码的那种登录方式、更新密码并撤销全部旧会话与全部模型代理密钥（[ADR-0063](../docs/adr/0063-模型代理接入密钥.md)）。发信按登录方式分发：现在只有邮箱走 SMTP，没有对应发送方的 kind 返回 501 `not_implemented`，发送通道没有配置时返回 503。两种验证码共用按 `kind:identifier` 的令牌桶，每 24 小时补充 4 枚，最多积存 4 枚。

验证码默认十分钟过期，同一种登录方式同一用途一分钟内只能发一次，输错超过五次就作废；库里只保存 HMAC-SHA256，密钥来自 `ZHIXIN_CODE_SECRET`，不保存六位数字本身。发信走 `ZHIXIN_SMTP_*` 配置，没有配置时这两个接口返回 503，登录、备份、同步与模型代理不受影响；`ZHIXIN_MAIL_LOG=1` 只用于本机联调，会把邮件正文写进日志，生产不能打开。验证码接口按登录方式、来源地址与联系方式分别限流，参数见下表的 `ZHIXIN_CODE_*`。

发信总量按实例控制：除了按地址与按收件地址的桶，所有发信再共用一个桶（`ZHIXIN_MAIL_GLOBAL_RATE` 与 `ZHIXIN_MAIL_GLOBAL_BURST`），换大量没有注册过的邮箱地址也绕不过去，超限返回 429 并带 `Retry-After`。桶的默认值按 SMTP 服务商免费额的保守值定，部署时按实际通道调整。每次发信同时占用的 SMTP 连接数不超过 `ZHIXIN_SMTP_MAX_CONCURRENT`，超出的请求排队而不是拒绝。连接失败、超时、4xx 这类临时失败按 `ZHIXIN_SMTP_MAX_ATTEMPTS` 重试，间隔为 1 秒与 3 秒，服务商在响应文本里给出 `Retry-After` 时取较大者，超过 30 秒就直接放弃这次发送并把验证码作废，不把请求挂住。连续三次临时失败之后整体暂停发信，暂停从 30 秒起翻倍、最长 5 分钟，暂停期间请求返回 429 而不是 503，发信恢复之后计数归零。

## 模型代理

客户端的模型调用只有“知新服务”一条路径：对话的线格式固定为 Responses（`POST <服务地址>/v1/llm/responses`），地址前缀是 `<服务地址>/v1/llm`，用访问令牌代替 key，客户端已按 Responses 组装请求与读取 SSE 事件（[ADR-0052](../docs/adr/0052-客户端改用OpenAI现行请求格式.md)）；客户端不再提供自填 key 直连提供方，自 2026-11-22 起用户不能绕开服务端调用模型（[ADR-0050](../docs/adr/0050-客户端统一为知新服务.md)）。服务端按请求里的 `model` 查路由表，核对这个账号当天这一类模型的用量是否低于额度，然后把 `model` 换成路由选中的来源侧模型名、换上这个来源的 key 转发，流式响应按事件边界逐块刷新，可转交的提供方错误由客户端读取。路由表只来自管理后台配置的来源与模型（`llm_provider`、`llm_model`、`llm_route` 三张表），没有环境变量来源（[ADR-0035](../docs/adr/0035-模型来源只保留后台配置.md)）；没有配置任何模型时聊天与嵌入接口返回 503。后台里的来源、模型与路由只由管理员维护，用户看不到也改不了，客户端的“知新服务”指的就是这个代理入口，与管理员配了几家上游无关，换上游或换模型都在后台完成，客户端不用发版。

一个对外模型可以有多条路由，请求按优先级从小到大尝试，最多执行 `ZHIXIN_LLM_MAX_ATTEMPTS` 次。请求声明了 `tools` 或输入里带图片时，服务端先排除没有对应能力标记的路由：一条都没有时回 502 `upstream_failed`，说明缺的是图片输入还是函数调用，不把请求发到读不了它的来源上。连接建立失败或 HTTP 401 会跳过本次请求中同来源的其他候选，模型响应异常只影响对应路由。冷却期间暂停普通请求，冷却到期后每个来源或路由只允许一次并发试探，完成有效请求后恢复常规分流。首段正文或一项工具调用开始转发时由原路由收尾，流式完成、未完成和失败的判定见 [ADR-0059](../docs/adr/0059-模型路由按故障范围切换与恢复.md)。

客户端通过请求头 `X-Zhixin-Session-Id` 发送最长 64 字节的稳定标识，讨论的追问、工具步骤、重试和无工具兜底共用讨论标识，同一次学习计划生成的各批次共用本次生成的标识。服务端按账号散列标识，再结合权重排列同一优先组内的候选，因此只要首选来源可用，同一会话就能优先向它发送请求，上游也有机会复用已经处理过的前缀。如果聊天请求未带有效标识，服务端使用账号与首条用户消息的散列值排列候选，没有可用的首条用户消息时继续按权重随机排列。首次尝试失败、由后面的来源接住这轮请求时，服务端按同一个调度键记住接手的路由，十分钟内同一讨论的候选顺序把这条路由排在最前，已经恢复的主来源因此不会在下一轮追问时马上把请求接回去，备用来源上已经热起来的前缀还能继续用；接手的路由被停用、进入冷却或缺少本次请求需要的能力时，仍按原顺序落到下一条候选，十分钟之后回到按会话与权重排列。标识、散列键与接手的记录仅用于代理内调度，记录只在进程内保存。取舍见 [ADR-0060](../docs/adr/0060-一轮回答的预算与按讨论分配来源.md)。

转发给来源时，会话标识还要按来源再带一次：来源地址指向 OpenCode（主机名含 `opencode.ai`）时，服务端把这条讨论的调度键写进 `x-opencode-session`，同一个会话的请求因此落到同一个上游；它的 Go 通道缺这个头会直接回 400 `MissingSessionID`，其它来源不带这个头。后台的“测试模型”与探活没有讨论标识，这类请求用固定值 `zhixin-probe`。

客户端在请求头 `X-Zhixin-Round-Budget-Ms` 里带这一轮剩下的时间，单位毫秒，从用户发出提问开始计算，工具调用后的后续请求沿用同一份预算。服务端按 `ZHIXIN_LLM_ROUND_BUDGET_MAX` 截断这个值，再把它用作整段回答、流式空闲等待与每次尝试等待首个有效输出的时限；候选还有多条时，等待首字的份额按还能尝试的候选数平分，所以首发与备用都落在同一轮预算内，不会出现客户端先结束等待、服务端还在等下一条来源的情况。一次尝试在首字时限内没有响应头时换下一条候选；响应头、心跳或开场事件已经到了、首段正文还没有到的时候，服务端先把这段先行事件暂存起来，这一阶段上游断开或超时同样换下一条，客户端看不到换路的过程。暂存受首字时限与 64 KiB 两个上限约束，如果只有先行事件、没有可用正文或完整函数调用，代理在达到上限时结束该次尝试并选下一条候选；交付前收到上游失败或空回答也按同一规则处理，已有用量照常结算。首段正文、拒答或一项完整函数调用交付之后，这次流绑定当前来源，后续中断由客户端保存已经收到的部分。达到输出上限时交付截断结果。这一轮预算在没有任何来源交付有效输出之前用完时，服务端中断上游请求并回 504 `upstream_failed`，客户端据此结束这一轮并给出重试入口；候选在交付有效输出之前全部失败、又没有可以转给客户端的上游状态时，代理回 502 `upstream_failed`，并在 `extra.reason` 写 `candidates_exhausted`。没有带这个请求头时（旧客户端与管理端探测）只按本机时限执行。

对话只接受 Responses 的字段：`model`、`instructions`、`input`、`max_output_tokens`、`temperature`、`top_p`、`store`、`stream`、`tools`、`tool_choice`、`parallel_tool_calls`、`reasoning` 与 `text`，其余字段直接回 400，`input` 必须是数组。`prompt_cache_key`、`prompt_cache_retention`、`prompt_cache_options`、`service_tier` 与 `include` 是例外：服务端接受但不转发，因为缓存亲和、缓存保留与服务档位由服务端与来源决定，`include` 只要求上游多返回推理内容而客户端不保存推理条目；DeepSeek Harness 一类的第三方工具每次请求都带 `prompt_cache_key`，开启思考时再带 `include`，这些字段转发给不认识它们的来源只会让整次请求按来源错误失败，直接回 400 又会让接入密钥在这些工具里不可用（[ADR-0063](../docs/adr/0063-模型代理接入密钥.md)）。`store` 可以出现在请求里，服务端一律改写成 `false`，也不保存会话，客户端每一轮都发完整上下文。客户端不再发送 `temperature` 与 `top_p`，管理端的探测与排查仍可带这两个字段。输出上限取 16 到 32768，与客户端 `buddyMaxOutputTokens` 相同，省略时补 4096；超出范围回 400 `invalid_request`。用接入密钥调用时按放宽的口径处理，也就是“内部严、外部松”（[ADR-0082](../docs/adr/0082-接入密钥的模型调用按放宽的校验口径.md)）：不认识的字段删掉再转发，输出上限超出范围时截到 16 与 32768 的边界、写不成数字时退回 4096，第三方工具不会因为一个用不上的参数整次失败；用访问令牌的知新客户端仍按上面的字段与上限严格校验，嵌入接口不在放宽范围内。每次尝试按请求里的文字与图片估算输入，口径与客户端 `estimateLlmTextTokens` 相同，图片每张按 2048 计；输出按 4096 与请求上限的较小值预留，然后按 `usage.total_tokens` 结算，缺少 `total_tokens` 时按 `input_tokens` 与 `output_tokens` 相加。流式响应从 `response.completed` 事件里的 `usage` 取用量，拿不到时按输入估算与已经转出的输出估算结算；流式请求收到 2xx 的整段响应时先读正文再决定，带 `usage` 就按 `usage` 结算，能解析成 Responses 响应对象就按正文估算输出，页面、错误体与没有读到正文的尝试仍记 0；来源明确拒绝、连接没有建立与首个有效输出之前的失败记 0，都不再沿用预留量（[ADR-0070](../docs/adr/0070-额度预留与失败结算口径.md)）。来源拒绝请求时，日志记一条 `模型来源拒绝了请求`，带请求编号、来源编号、上游模型、状态码与错误体的前 300 字节；这句只说明来源为什么拒绝，请求内容与响应正文仍然不记录，客户端收到的仍是 `upstream_failed`。嵌入按输入字节预留与估算，发生错误或换路由时也会结算已发出的批次。额度默认值只是占位，实际数字待内测用量出来之后再定。

嵌入走 `POST /v1/llm/embeddings`，请求与响应是 OpenAI 的格式，`input` 只接受字符串或字符串数组，单次最多 `ZHIXIN_LLM_EMBEDDING_MAX_INPUTS` 条，客户端在语义索引页选“知新服务”时，`RemoteEmbeddingClient` 每次请求前取 `<服务地址>/v1/llm` 与当前访问令牌，模型从列表里 `kind` 为 `embedding` 的项中选。路由的 `max_batch` 大于 0 时，服务端按条数拆批，普通请求同时最多发出四批，试探时逐批发出，最后按原顺序合并并从 0 连续编号。一批出现可重试故障时，下一条路由重新执行整次请求，因此每次请求的向量都来自同一条路由。配置了维度时逐条核对向量长度，返回维度不符按路由故障处理，客户端请求的 `dimensions` 与配置不一致时返回 400。`GET /v1/llm/models` 的每一项带 `kind`（`chat` 或 `embedding`），嵌入模型配置了维度时带 `dimensions`。

嵌入只有一个来源，文档向量与查询向量都从这里计算，客户端不在本地计算任何向量（[ADR-0049](../docs/adr/0049-嵌入统一走百炼与查询向量也走云端.md)）。第一套实例的来源是阿里云百炼的 `BAAI/bge-m3`，在管理后台按下面的口径建一次即可：来源基础地址填百炼的 OpenAI 兼容端点，对外模型名写 `zhixin-embedding`（客户端默认取这个名字，与聊天模型 `zhixin-chat` 同一套命名），`kind` 选 `embedding`，`dimensions` 填 1024，路由的上游模型名与每批条数按来源侧的模型名与限额填写。对外模型名在所有客户端上统一，客户端的索引键与 `embedding_cache` 都以它为准，改名等于换一个向量空间，索引与缓存都不会命中。同一个对外模型下如果再加备用路由，也只能指向 bge-m3 的同一权重部署，服务端只核对维度、核对不了向量空间；混入别的模型或精调版本会让同一个索引里出现两套空间的向量，排序会错但不报错。具体步骤写在[运维手册](运维手册.md#5-常用操作)。

嵌入向量另有按账号隔离的缓存，目的是消除换机、索引重建与模型在 A、B 之间切换时的重复嵌入与费用（[ADR-0030](../docs/adr/0030-服务端不建检索索引.md) 决定第 2、3 条）。客户端在自动同步开启、且这次是索引刷新时，给 `POST /v1/llm/embeddings` 带 `X-Zhixin-Embedding-Cache: 1`，服务端在嵌入成功之后按每条输入的 SHA-256 写进 `embedding_cache`，重复写入不覆盖已有的行；检索查询的嵌入不带这个头，未登录与同步关闭的用户因此不会留下派生数据；客户端没有其他嵌入来源，本机哈希不联网也不经过服务端。索引刷新先调 `POST /v1/llm/embeddings/lookup`，请求体是 `model` 与 `hashes`（UTF-8 字节的 SHA-256 小写十六进制，单次最多 `ZHIXIN_LLM_EMBEDDING_MAX_INPUTS` 条）；命中返回小端序 FP16 的 base64 向量与 `dimensions`，全部未命中时 `vectors` 为空数组、不是错误，查找不消耗额度、不写 `llm_usage`。缓存随 `DELETE /v1/cloud` 与删除账号一起删除，清除期间带缓存头的嵌入照常返回但不写缓存；清除时缓存代次加一，清除之前发出、清除之后才落库的嵌入请求会因为代次对不上而放弃写入，清除成功的承诺不会因为在途请求而失效。每账号上限由 `ZHIXIN_LLM_EMBEDDING_CACHE_BYTES` 控制，写入之后按 `last_used_at` 删除最久未用的行。同名模型必须保持同一个向量空间：更换部署要换对外模型名，管理后台删除模型或改变维度时会先删掉这个模型的缓存行，再保存或删除，旧名字再次出现时不会命中上一个向量空间的向量。

账号没有任何一种已验证登录方式时，聊天与嵌入请求均返回 403 `contact_unverified`，这个检查默认启用，开发联调时可通过 `ZHIXIN_LLM_REQUIRE_VERIFIED_CONTACT=0` 关闭。每个账号同时最多 `ZHIXIN_LLM_CONCURRENT_PER_USER` 个托管请求，超出的请求在读取请求体之前返回 429。整个实例同时在途的请求还共用一份 `ZHIXIN_LLM_MAX_INSTANCE_BYTES` 的字节预算：请求体按声明长度的两倍（长度未知时按请求体上限）、非流式响应与嵌入请求按各自的上限在读进内存之前预留，占不到时同样回 429，实例内存因此不随账号数量上涨。聊天与检索查询按前台请求处理，材料导入、索引重建与补算按后台批次处理：客户端在嵌入请求上用 `X-Zhixin-Workload: batch` 标明后台批次，缺省与 `query` 都按前台处理。每个账号的后台请求最多占用并发上限减去 `ZHIXIN_LLM_FOREGROUND_RESERVED` 的名额、且至少保留一个，实例字节预算里后台批次最多占 `ZHIXIN_LLM_BACKGROUND_INSTANCE_PERCENT`，其余留给前台；占不到容量时后台批次同样回 429，由客户端保留已完成的批次并稍后重试，前台请求因此不会被导入挤掉。非流式响应超过 `ZHIXIN_LLM_MAX_RESPONSE_BYTES` 时按无效响应处理，流式响应的空闲时限与总时限分别由 `ZHIXIN_LLM_STREAM_IDLE_TIMEOUT` 与 `ZHIXIN_LLM_STREAM_TOTAL_TIMEOUT` 决定，两者都不超过本轮剩余预算，响应开始转发后，超时会中断当前来源并结束响应。账号的用途额度与实例当日总预算 `ZHIXIN_LLM_INSTANCE_DAILY_TOKENS` 任一用完都返回 429 `quota_exceeded`，响应里的 `extra.reason` 说明是账号免费额度与积分都用完（`account`）、积分不够这一次（`points`）、实例预算用完（`instance`），还是余额副本缺失或过期、服务端刚排了一次查询（`syncing`），客户端据此给购买入口或只说稍后重试（[ADR-0071](../docs/adr/0071-核销只读已结算用量与额度用完的原因.md)、[ADR-0073](../docs/adr/0073-余额副本的快照、刷新与放行原因.md)）。实例预算读的是 `llm_instance_usage` 里按自然日记的账本，只累计免费额度内的用量，超出免费额度、由积分承担的部分不计入，付费用量因此不会占掉给免费额度兜底的预算（[ADR-0070](../docs/adr/0070-额度预留与失败结算口径.md)）。删号与清空云端数据都不减少这本账，提供方已经计费的部分因此不会重新变成可用额度。最后一次上游尝试返回 429 时，代理按 429 `rate_limited` 返回并原样转出上游的 `Retry-After`，客户端据此提示稍后重试；其余上游拒绝仍按 `upstream_failed` 处理，两者都不带上游响应正文。

聊天与嵌入各有一份每日额度，默认分别取 `ZHIXIN_LLM_DAILY_TOKENS` 与 `ZHIXIN_LLM_EMBEDDING_DAILY_TOKENS`，账号的用量按自然日、用途与这次调用所用的模型代理密钥分开记在 `llm_usage`（用访问令牌调用记空编号），这一行里 `tokens` 是已经结算的计费 token、`reserved_tokens` 是还在途的预留：额度判定看两者之和，核销与 `GET /v1/llm/quota` 的展示只看 `tokens`（[ADR-0071](../docs/adr/0071-核销只读已结算用量与额度用完的原因.md)），实例当天的免费部分另记一份在 `llm_instance_usage`（付费部分不计入，见 [ADR-0070](../docs/adr/0070-额度预留与失败结算口径.md)），两份在同一个事务里更新，删号只清账号那一份。聊天额度按计费 token 计：未命中缓存的输入 token 记 1，命中缓存的输入记 1/50，输出记 4，来源只报总量、说不出命中与否时按原始 token 记；权重取自上游的计价比例，拿不到输入拆分的请求因此不会被多扣四倍，取舍见 [ADR-0066](../docs/adr/0066-额度按缓存命中折算.md)。`llm_usage` 另记上游报告的原始输入量与其中命中缓存的部分，只用于统计命中率，不参与扣减。嵌入的提供方没有返回 `usage` 时按输入字数估算。需要单独调整某个账号时在管理后台的“账号管理”页保存额度，写入 `llm_quota` 的一行，两列分别对应聊天与嵌入，为空的一列用默认值；下一次请求就按新数字判定，不用重启服务，恢复默认会删掉这一行，删号时覆盖行随外键级联删除。当天改覆盖值会按新上限重算当天的免费部分，调低额度会让已经用掉的量变成待核销积分，调高则相反，所以额度调整尽量放在自然日切换之后。`GET /v1/llm/quota` 同时返回两类的用量与额度，429 的 `extra.kind` 表示请求用途，响应同时给出实例总用量与预算；开通收款的实例还返回 `charged_points` 与 `remaining_points`（当天核销成功的积分与可用积分，可用积分是余额副本减去没有反映的核销、再减去当天已占用量里还没有记进流水的计费量，已占用量按已结算与在途预留之和算；两个字段各按自己的数据是否可用返回，没有开通收款时都是 null，开通了收款但还没有余额副本时只有 `charged_points`），账号页据此写“今天已用多少分、还剩多少分”，见 [ADR-0071](../docs/adr/0071-核销只读已结算用量与额度用完的原因.md) 与 [ADR-0073](../docs/adr/0073-余额副本的快照、刷新与放行原因.md)。额度调整是运营动作，正常走管理后台的“账号管理”页；后台不可用或需要一次处理多个账号时，下面的语句写在[运维手册](运维手册.md#5-常用操作)里：

```sql
-- 调高或新建一个账号的额度；只调一类时另一列写 NULL
INSERT INTO llm_quota (user_id, daily_tokens, embedding_daily_tokens, note)
VALUES ('<账号 id>', 500000, 5000000, '内测高频用户')
ON CONFLICT (user_id) DO UPDATE
SET daily_tokens = EXCLUDED.daily_tokens,
    embedding_daily_tokens = EXCLUDED.embedding_daily_tokens,
    note = EXCLUDED.note, updated_at = now();

-- 回到默认值
DELETE FROM llm_quota WHERE user_id = '<账号 id>';
```

用户自己的脚本或第三方工具不保存登录凭据，改用模型代理密钥（[ADR-0063](../docs/adr/0063-模型代理接入密钥.md)）。用登录令牌调 `POST /v1/me/api-keys`（请求体 `{"name": "脚本", "password": "当前密码"}`）签发一把：签发只凭访问令牌就能换一把不过期的密钥，所以与删号、清空云端数据一样要再提交一次当前密码，密码错误返回 401，连续输错超过按账号的失败预算时返回 429。响应里的 `key` 形如 `zx_` 加 32 位随机字符再加 4 位校验码，共 39 个字符，明文只出现这一次，库里只存 SHA-256；`GET /v1/me/api-keys` 列出编号、名字、前缀、是否撤销、创建时间与最近使用时间，`DELETE /v1/me/api-keys/{id}` 撤销一把，`DELETE /v1/me/api-keys` 撤销全部，撤销之后立刻失效，重复撤销单把回 404。密钥放在 `Authorization: Bearer <key>` 里，调用方式与访问令牌相同，但作用域只有 `/v1/llm` 下的五条模型接口，访问同步、备份、附件与账号管理一律回 403 `key_scope_denied`。额度、并发、实例预算与“登录方式已验证”的门槛都按账号算，密钥不单独记录额度，也没有单把密钥的额度或速率；密钥没有有效期，只能显式撤销，每账号最多保留 20 把有效密钥，上限在存储层与写入一起判定，并发签发不会突破，撤销超过 30 天的行由每日清理删除；重设密码与刷新令牌重放检测都会撤销这个账号的全部密钥，删号时随外键级联删除，用量按 `llm_usage` 的密钥列分开记，最近使用时间按十分钟粒度写入、进程内也跳过这十分钟内的重复写库，因此有十分钟的滞后。只用密钥的请求不计入账号日活。工具收到 401 时应当停止，不要照着客户端的方式刷新令牌。`api_key` 是新表，第一套实例上线这条改动时按 [ADR-0057](../docs/adr/0057-服务端改表清空重建.md) 在计划内停服重建库，重建会清空现有账号。

## 即刻收收款

聊天额度按支付宝「即刻收」直连模式的积分包卖出，见 [ADR-0067](../docs/adr/0067-聊天额度改走即刻收积分包.md)。商品、收费模式、档位与价格都在「即刻收」小程序里配置，审核发布之后把商品详情页的 `out_product_id` 填进配置；应用不能自己定价，也不能生成商品 ID。商品必须配置成 `billing_mode=QUANTITY` 且 `quota_unit=POINT` 的积分包，购买与核销只接受这种商品：单位不匹配时购买回 409，余额接口回 409，核销结果不按积分记账、也不写副本，日志写明实际的单位。三档的名称、价格与发放积分见 [00 第 7 章](../docs/00-产品定义.md#7-边界) 与 [ADR-0068](../docs/adr/0068-聊天积分包的档位与价格.md)，应用不保存价格，改档位只改小程序。概览接口与额度接口都返回一个积分覆盖的计费 token 数（`tokens_per_point`，取自 `ZHIXIN_TOKENS_PER_POINT`），客户端据此把积分换算成 token 与天数，也把当天用量换算成积分展示。网关、RSA2 签名与公共参数沿用支付宝开放平台的同一套应用凭证，`internal/payment` 的签名与验签是唯一实现，`internal/nowpay` 只按接口名提交 `biz_content`；网关错误沿 `ErrGateway` 包装出具体步骤（超时、连接、HTTP 状态、解析或验签），日志能看出卡在哪一步。

服务端用到五个接口：`charge.query` 查收费能力与档位，`quota.query` 查积分余额，`purchase.create` 取托管购买页链接，`quota.verify` 核销，`quota.refresh` 用原请求号查询核销结果。买断与时长包要用的 `purchase.consult` 没有接，因为商品按积分包配置。即刻收的响应把中文按 GB18030 回，请求里写 `charset=utf-8` 也不改，所以网关先验签再转码，调用方拿到的是 UTF-8；签名覆盖的始终是原始字节。

契约里只有三条接口：`GET /v1/me/model-quota-purchases` 返回商品状态、积分余额与折算比例，`POST /v1/me/model-quota-purchases` 取购买链接（请求体带 `client_request_no`，同一个键重试复用同一张链接，换一次点击换新链接，不传键时服务端生成随机键），`GET /v1/me/model-quota-purchases/quota` 只查余额（[ADR-0074](../docs/adr/0074-购买入口按客户端请求号幂等.md)）。概览接口并行查商品与余额，商品能力在进程内缓存 60 秒；余额查不到时不回 503，而是照常返回商品与 `balance_unavailable=true`，客户端提示“暂时查不到余额”，见 [ADR-0073](../docs/adr/0073-余额副本的快照、刷新与放行原因.md)。支付宝的异步通知不再接收，`POST /v1/payments/alipay/notify` 已从契约删除；通知与查单处理器、Android 侧的 SDK 通道、订单表与钱包表都已删除，`internal/payment` 只保留签名、验签与网关调用。

`nowpay_charge` 保存积分核销流水，`id` 就是提交给即刻收的 `out_request_no`，结果未知时只能用它查询或重试；`nowpay_purchase` 保存购买入口请求，一行对应客户端的一次点击，按 `client_request_no` 幂等；`nowpay_balance` 保存积分余额的本地副本，额度预留按它放行。三张表的 DDL 见 [schema.sql](internal/store/schema.sql)。核销还配了两个后台任务：每十分钟一次的全局补查把创建超过五分钟、仍未终结的流水排进核销队列（每次五十条，删号之后失去归属的行不取，它们补查不到结果），每天一次的维护任务记一条按 `ZHIXIN_TIMEZONE` 取当天、按状态计数与实例账本的对账日志，并按保留期分批删除过期的购买入口（三十天）、终态流水与失去归属又没有结论的流水（一百八十天），参数与核对语句见[运维手册](运维手册.md#411-即刻收积分包的上线与回滚)。

额度预留先看当天免费额度，聊天在免费额度之外再加上余额副本折成的计费 token（[ADR-0069](../docs/adr/0069-积分余额的本地副本与预留放行.md)）。副本由三个地方写入：概览与单独查余额两个接口在 `quota.query` 成功之后写，核销或补查的响应带剩余积分时写，`NOW_PAY_QUOTA_INSUFFICIENT` 时按零写。`quota.query` 的响应带 `as_of_time` 时用它做副本的快照时刻，没有时用查询发起的时刻；核销结果只在 `SUCCEEDED`、`FAILED` 与余额不足时写副本，`SUCCEEDED` 与 `FAILED` 的快照时刻取响应给出的时刻与这次确认时刻里较晚的一个，刚确认的这一笔不会被算成“快照之后才确认”，`PROCESSING` 的剩余积分不覆盖副本，因为还不知道它有没有扣住那笔预占（[ADR-0073](../docs/adr/0073-余额副本的快照、刷新与放行原因.md)）。副本超过一分钟没有同步或者还没有副本时，预留排一次异步查询，这一轮仍按现有副本判断；如果这一轮本来就放行不了，429 的原因写 `syncing`，客户端只提示稍后重试，不引导购买。请求路径上因此不调用即刻收；免费额度以内的请求不读副本，也不触发查询。可用积分还要减去副本没有反映的核销：`pending` 与 `processing` 一律计入，`succeeded` 只在快照之后确认的计入；再减去当天已占用用量（已结算与在途预留之和）里还没有记进流水的计费量，同一笔用量不会因为预留与核销的先后被放行两次，账号页的剩余积分按同一个数算，显示的数因此不会大于实际还能放行的量。

核销在交付之后。每轮对话结算提交之后，服务端按当天用量算出应当由积分承担的计费 token 数（先减免费额度，超出部分才折成积分），按“一个积分等于 `ZHIXIN_TOKENS_PER_POINT` 个计费 token”向上取整，再由 `ReservePoints` 在同一个事务、同一把当日核销锁里按可用积分收口并写一条 `pending` 流水。收口规则：先算当天还没有申请的差额（累计应扣减去已经申请的积分），再按可用积分截断这个差额，已经申请过的积分不再从可用积分里减一次；可用积分为零时不再写流水、也不调用即刻收，差额大于可用积分时只申请可用积分的那一部分，差额等余额补上之后的下一次结算再算；副本行缺失、余额表未就绪或读取失败时保持整额申请，一次读取失败不会少记账（[ADR-0073](../docs/adr/0073-余额副本的快照、刷新与放行原因.md)）。流水排进核销队列，由独立的核销协程调用 `quota.verify`；余额刷新走另一条容量 64 的队列，超时 8 秒，队列满时丢弃并退回合并窗口，由下一次请求重新排一次查询，不占核销的时间预算。`SUCCEEDED` 记成功；`FAILED` 与 `NOW_PAY_QUOTA_INSUFFICIENT` 记失败，下一次结算重新算差额；`PROCESSING`、超时与网关错误保持原状态，下一轮对话开工前用 `quota.refresh` 补查。核销不提供撤销与返还，交付失败时只能由下一次结算的差额或人工处理。

| 环境变量 | 用途 |
|---|---|
| `ZHIXIN_ALIPAY_APP_ID` | 支付宝应用 ID，与即刻收商品属于同一商户 |
| `ZHIXIN_ALIPAY_PRIVATE_KEY` | RSA2 应用私钥，支持 PEM 或 Base64 DER |
| `ZHIXIN_ALIPAY_PUBLIC_KEY` | 支付宝公钥，支持 PEM 或 Base64 DER |
| `ZHIXIN_TOKENS_PER_POINT` | 一个积分覆盖的计费 token 数，代码默认与部署值都是 `10000`；核销与前台展示共用，比例的来源只有配置校验 |
| `ZHIXIN_NOWPAY_PRODUCT_ID` | 「即刻收」小程序里的商品 ID；为空表示不卖积分包 |
| `ZHIXIN_NOWPAY_CALLBACK_URL` | 可选，购买页返回后的跳转地址，必须是 HTTPS；它不是到账通知 |

配置了商品 ID 时启动会检查这三张表：`nowpay_charge` 与 `nowpay_purchase` 缺表直接退出，`nowpay_purchase` 缺 `client_request_no`、`state`、`updated_at` 或幂等键索引同样退出，`nowpay_balance` 缺表只记一条错误日志并停用免费额度之外的放行，服务照常启动（[ADR-0069](../docs/adr/0069-积分余额的本地副本与预留放行.md)、[ADR-0074](../docs/adr/0074-购买入口按客户端请求号幂等.md)）。这张副本表是纯新增，已经在收款的实例可以先部署新版，再按运维手册建表并重启，放行随之生效，不必为了建表顺序停服。在独立实例上先用增量语句建表，再改 `api.env` 并重启，核对 `/readyz` 返回 200。核对购买通道时用已验证邮箱的账号在真机上买一笔最小档位：`GET /v1/me/model-quota-purchases` 的 `balance_points` 增加，客户端回到前台后余额跟着刷新，`nowpay_balance` 出现这个账号的一行；再发一次对话，`nowpay_charge` 出现一条 `succeeded` 的流水，`quota.query` 的剩余积分按 `Usage.Billed` 折算后减少；同一轮重复发请求不会多扣，`PROCESSING` 时补查用的是同一行的 `id`。核对付费放行时把当天的免费额度用完（或在后台把账号额度调小）再发一次对话：请求应正常回答而不是回 429，`llm_usage` 的当天用量会超过免费额度，结算之后出现核销流水，`nowpay_balance` 的 `remaining_points` 随之减少。删掉这个账号的副本行再发一次对话，第一次回 429 且 `extra.reason` 是 `syncing`、日志里有一次余额查询，第二次正常回答；把副本的 `synced_at` 改到一小时前再发，第一次同样回 `syncing` 并排一次查询。

购买入口按幂等键核对：用同一个 `client_request_no` 连续请求两次 `POST /v1/me/model-quota-purchases`，两次的 `out_request_no` 相同、`nowpay_purchase` 只有一行、即刻收侧只创一次单；换一个键再请求，请求号与链接都不同；并发发两个同键请求，最终也只有一行。商品单位核对：把小程序里的商品改成计次或买断之后，购买与余额接口都回 409，核销结果不按积分记账，日志写明实际的 `quota_unit`。发布失败时不要回滚到不识别 `reserved_tokens` 的旧二进制，处置边界见[运维手册](运维手册.md#411-即刻收积分包的上线与回滚)。


## 管理后台

设置 `ZHIXIN_ADMIN_TOKEN`（至少 32 个字符，可以用 `openssl rand -base64 32` 生成）之后，浏览器打开 `<服务地址>/admin/`，输入这个令牌即可管理模型来源与路由，查看用量、留存、账号与积分，查看并删除反馈；没有设置时整个 `/admin` 返回 404。页面与脚本编进可执行文件，令牌只保存在浏览器标签页的 `sessionStorage` 里。页面上能做的事都对应 `/admin/v1/` 下的接口，契约写在 `openapi.yaml` 的 `admin` 标签下，用 `Authorization: Bearer <管理令牌>` 调用：

| 接口 | 用途 |
|---|---|
| `GET /admin/v1/providers` | 列出来源、key 末四位与健康状态（连续失败次数、最近错误、冷却到何时） |
| `POST /admin/v1/providers` | 新建来源，编号放在请求体里；编号已存在时返回 409，不覆盖原来源 |
| `PUT /admin/v1/providers/{id}` | 修改已有来源；编号不存在时返回 404。`api_key` 省略时保留原值，空字符串表示清除 |
| `DELETE /admin/v1/providers/{id}` | 删除来源；还有路由指向它时返回 409，`extra.models` 列出这些模型 |
| `POST /admin/v1/providers/{id}/test` | 用来源自己的 key 请求一次 `/models`，返回可用的模型名，编辑路由时可以直接选 |
| `GET /admin/v1/models` | 列出模型的可调用状态与每条路由的状态，包括来源停用、密钥解密失败和冷却 |
| `POST /admin/v1/models` | 新建模型，名称放在请求体里；名称已存在时返回 409，不覆盖原模型的路由 |
| `PUT /admin/v1/models/{name}` | 修改已有模型，路由整体替换；名称不存在时返回 404 |
| `DELETE /admin/v1/models/{name}` | 删除模型，路由随之删除 |
| `POST /admin/v1/models/{name}/test` | 发出最小请求并报告实际尝试顺序、失败原因、耗时与嵌入维度，同时传入 `provider_id` 与 `upstream_model` 时只探测指定路由 |
| `GET /admin/v1/usage?days=7` | 返回按日分用途的用量、各路由区间总量与有记录日期的用量，`days` 允许 1 至 30，默认 7 |
| `GET /admin/v1/key-usage?days=7` | 只读对账：返回区间内每把接入密钥的已结算与在途用量、缓存命中、尝试与失败次数、最近使用与撤销状态，对话与嵌入分开，访问令牌的调用记在 `key_id` 为空的一行 |
| `GET /admin/v1/retention?days=30` | 只读：返回区间内每天的匿名安装数与登录账号数，以及按首次出现日分组的 7 日与 28 日留存；`days` 允许 1 至 180，默认 30 |
| `GET /admin/v1/accounts?query=&limit=&offset=` | 按注册时间倒序分页列出账号，返回登录方式、额度覆盖值、生效额度与实例默认额度；`query` 匹配账号编号或邮箱片段 |
| `GET /admin/v1/accounts/{id}` | 读取一个账号的上述字段、今日已结算用量与积分视图：今天已核销的积分、可用积分、余额副本的快照时刻与最近五条流水 |
| `PUT /admin/v1/accounts/{id}/quota` | 整体替换这个账号的额度覆盖值；某一项省略或为 null 时回到实例默认值，两项都为空且没有备注时删除覆盖行 |
| `DELETE /admin/v1/accounts/{id}/quota` | 删除覆盖行，这个账号回到实例默认额度 |
| `POST /admin/v1/accounts/{id}/points/refresh` | 同步查询一次即刻收的积分余额并覆盖本地副本，返回刷新后的积分视图；实例没有开通收款时返回 409，即刻收不可用时返回 502 |
| `DELETE /admin/v1/accounts/{id}` | 注销账号；请求体必须带与路径一致的 `user_id`，清理与账号本人删号相同 |
| `GET /admin/v1/feedback?query=&limit=&offset=` | 按提交时间倒序分页列出反馈；`query` 匹配编号、正文、联系邮箱、版本与平台，列表不带诊断摘要，用 `has_diagnostics` 标明有没有 |
| `GET /admin/v1/feedback/{id}` | 读取一条反馈的正文、联系邮箱、版本、平台与诊断摘要；不存在时返回 404 |
| `DELETE /admin/v1/feedback/{id}` | 删除一条反馈，用于误提交或用户要求提前删除；保留期清理仍按每天一次执行 |

来源的 key 用 `ZHIXIN_SECRET_KEY`（32 字节的 base64，`openssl rand -base64 32`）加密入库，附加数据是来源编号与完整地址，后台修改地址的任一部分时都必须重新填写 key。生产后台的来源必须使用公网 HTTPS，连接前解析域名并核对实际连接的地址。打开后台并使用数据库时这个密钥必须配置，否则启动失败；内存存储时缺省用一把随进程消失的随机密钥。更换密钥或从旧地址绑定规则升级后，已保存的 key 显示为 `key_error`，需要在后台重新填写。来源与模型只从这三张表读取，管理后台是唯一的配置入口：新建实例或重建库之后，要先在后台新建来源、再新建模型并配置路由，聊天与嵌入接口才有可用的路由，否则一律返回 503；换 key 也在后台修改，改 `<服务地址>/admin/` 里的来源即可，不需要重启。

“对外模型与路由”页可以在模型名、备注、来源与来源侧模型名里搜索，按用途筛选，并只显示需要处理的模型：模型停用、没有可用路由，或者有冷却、试探、密钥异常、来源停用、来源缺失的路由。每条路由可以直接停用或启用，模型也可以不打开弹窗就整体停用；这两种改动按模型整体保存，与弹窗里保存调用同一个接口。列表按主用组与各备用组显示同组配置比例、当前首选概率或失败后尝试，并分别列出来源与路由的连续失败次数及冷却时间。点“复制”把这个模型的路由填进新增表单，填一个新的名称即可得到一套相同的路由。新增来源或模型时，编号或名称已经存在会被拒绝并提示去编辑，原有配置不会被覆盖；修改接口只更新已有条目，目标不存在时返回 404。

编辑路由时，在“路由组”下拉框选择主用组或已有备用组，也可以新建一个最后尝试的备用组。希望一条路由只在前组失败或不可用时接替请求，可以将其放在下一优先级。每条路由另有“工具”与“图片”两个复选框，对应 `supports_tools` 与 `supports_images`：关掉之后，带 `tools` 或图片的请求不会走这条路由；默认勾选，与加这项筛选之前的行为一致，管理员按实际调用核对之后再取消不支持的那一项。同组配置比例按所有已启用路由计算，表示会话落到各条路由的比例，不再表示每次请求的抽签比例。首选预览同时使用表单配置和最近读取的来源及路由状态，按权重给出当前首选概率；实际落到哪一条还取决于讨论标识，所以后台把配置比例、首选预览与实测请求量分开显示，来源停用、密钥异常、冷却或试探在途时对应路由退出当前候选。也可以模拟单个来源、主用组来源或全部来源冷却，保存时提交表单中的路由配置。

保存之后路由立即生效；服务不周期重读模型路由，直接改库之后要在管理后台保存一次或重启服务。令牌校验失败按来源地址限流（`ZHIXIN_ADMIN_RATE`、`ZHIXIN_ADMIN_BURST`），超限期间这个地址的管理请求全部返回 429。后台没有操作审计，令牌等同于管理员本人，生产上应在 nginx 里把 `/admin` 限制在管理员的地址，或者只经 SSH 隧道访问，做法见[运维手册](运维手册.md#3-配置)。

嵌入模型的几条路由必须是同一个模型的不同部署，例如两家服务商提供的 `BAAI/bge-m3`，服务端只能核对维度，向量空间是否一致由管理员保证。取舍与代价见 [ADR-0029](../docs/adr/0029-模型来源路由与嵌入代理.md)。

在“对外模型与路由”页，“测试模型”按正常的候选次序执行，并列出每次实际尝试与失败原因。单条路由旁的“探测”可以在冷却期间提前试探，已有试探在途或者模型、路由、来源已停用时会跳过发送。两种测试都会更新相应的进程内健康状态，探测用量由来源侧计量，知新的账号额度和路由用量不计入探测。

“用量统计”页按 `ZHIXIN_TIMEZONE` 显示今天、最近 7 天或最近 30 天的托管用量，管理员可以按用途、对外模型、来源和来源侧模型筛选，并查看首次尝试、故障切换、未成功尝试与 Token 的每日趋势和明细。从路由旁的“用量”进入看板时会直接应用该路由的筛选条件。首次尝试与故障切换按实际执行的次序汇总到 `llm_route_usage`，可以据此核对首次分流，嵌入拆批仍算一次尝试。未成功明细列出输出截断和客户端取消的次数，Token 明细列出估算部分，来源报告输入量与缓存命中量时另标出命中占比、首次与换路各自的命中率、缓存字段的上报覆盖率与缺报条数，提供方费用以其账单为准。计数口径见 [ADR-0034](../docs/adr/0034-模型路由用量汇总.md)，数据库重建要求见[运维手册](运维手册.md#49-自动部署与回滚)。

同一页下方的“按密钥计费”读取 `llm_usage` 中按密钥分开记的用量，显示每把密钥的对话与嵌入计费 token、尚未结算的在途预留、尝试与未成功次数、缓存命中、最近使用时间与撤销状态，按所选日期或整个区间汇总，并给出每日趋势。对话的计费 token 按核销同一比例（`ZHIXIN_TOKENS_PER_POINT`）折算成约合积分，嵌入只占免费额度、不计入积分；这个数字是折算值，不代表账号当天实际核销的积分，核销仍按账号合计。失败的调用按 [ADR-0070](../docs/adr/0070-额度预留与失败结算口径.md) 记 0，不产生 token，`llm_usage` 因此另记尝试与失败次数，让后台能区分“一直在失败”的密钥与没有用过的密钥，这两列不参与额度判定与核销，见 [ADR-0083](../docs/adr/0083-后台密钥视图记录失败的调用.md)。用量行按 `api_key_id` 关联密钥的名字与前缀，密钥撤销超过保留期被每日清理之后用量仍然保留，名字退化为空并按“已清理的密钥”显示；访问令牌发起的调用单列一行。视图只读，不改变额度、积分与失败结算的口径，取舍见 [ADR-0076](../docs/adr/0076-管理后台按密钥的对账视图.md)。

“账号管理”页按邮箱或账号编号搜索账号，列表显示登录方式、验证状态、注册时间、聊天与嵌入的生效额度以及是否单独调整过。打开一个账号的“额度与积分”弹窗时读取它今天的已结算用量，可以分别修改聊天与嵌入的每日额度并写一条备注，留空表示回到实例默认值；“恢复默认”删除整行覆盖值。弹窗下半部分显示积分：今天已核销的积分、可用积分、余额副本的快照时刻与最近五条核销流水，“刷新余额”同步查询一次即刻收并更新副本。积分一节只读，真正的余额在支付宝一侧，后台不提供补分、扣分或退款，实例没有开通收款或账号还没有副本时分别说明，不把缺失的余额写成零。注销账号要再输入一次邮箱或账号编号，请求体里同时提交账号编号；删除会清掉登录方式、会话、接入密钥、积分余额副本、备份、提交序列、附件与对象存储字节，无法恢复，剩余积分也不能退款。页面显示完整邮箱，是因为管理员要靠它辨认和联系账号本人；按密钥计费页仍然只显示编号。账号管理页读的是 `app_user`、`user_identity`、`llm_quota`、`llm_usage`、`nowpay_balance` 与 `nowpay_charge`，不新增表，搜索、额度调整与积分查看的取舍见 [ADR-0078](../docs/adr/0078-管理后台的账号注销与额度管理.md) 与 [ADR-0081](../docs/adr/0081-管理后台的积分查看.md)。

“反馈”页按编号、正文、联系邮箱、版本或平台搜索，列表显示提交时间、版本与平台、正文前三行与联系邮箱；打开一条反馈时读取全文与诊断摘要，删除按钮放在弹窗里，二次确认之后才提交。列表不返回诊断摘要，正文在列表里只显示前三行，是为了让一页二十条仍然便于浏览；诊断摘要至多 64 KiB，只在单条读取时返回。反馈不绑定账号，删除一条不通知提交人，保留期到期的行仍由每日清理删除。页面读的是 `feedback` 一张表，不新增表与列，取舍见 [ADR-0079](../docs/adr/0079-管理后台的反馈查看.md)。

## 更新检查

`GET /v1/app/releases` 公开返回发布清单，登录之前也能调用。清单是一份 JSON 文件，路径由 `ZHIXIN_RELEASE_FILE` 给出，启动时读入并校验：字段是否齐全、地址是否为绝对的 https 地址、`sha256` 是否必填且为 64 位小写十六进制、`signature` 是否是必填的 64 字节 Ed25519 签名 base64、平台是否重复。路径为空时接口返回空数组。配置的文件不存在或内容不合法时，服务拒绝启动。发版流程使用 `RELEASE_SIGNING_KEY_BASE64` 中的 Ed25519 私钥对安装包 SHA-256 的小写十六进制字符串签名，应用使用随包提供的公钥验签。应用的更新检查入口见 [02 第 3.16 节](../docs/02-产品与交互.md#316-账号与云同步)。

```json
{
  "releases": [
    {
      "platform": "android",
      "version": "0.3.0",
      "build": 4,
      "published_at": "2026-11-24",
      "url": "https://zhixin.chensiyuan.work/downloads/zhixin-0.3.0.apk",
      "sha256": "…64 位小写十六进制…",
      "signature": "…64 字节 Ed25519 签名的 base64…",
      "size": 74529199,
      "min_version": "0.3.0",
      "notes": "升级会清空本机数据，服务端账号需要重新注册"
    }
  ]
}
```

服务端只原样给出这些字段，不比较客户端版本，也不判断客户端是否低于建议的最低版本；客户端按平台取一项，自己比较 `version` 与 `build`，低于 `min_version` 时用“建议尽快更新”的措辞提示，并说明云端同步与在线模型可能不可用，仍然提供“以后再说”，不阻断使用。发布新版本时把安装包放到清单里的地址，用发版流程给出的 sha256 与 signature 改清单，再重启服务；次版本与公测包还要在标签上建 GitHub Release，附件与下载站用同一个哈希（[03 第 3 节](../docs/03-团队分工与协作.md#3-交付节奏)）；清单、签名与安装包要在同一步更新，客户端核对清单里的哈希格式与签名，对不上时不提示更新。检查阶段不下载安装包，用户确认后由系统浏览器下载一次，系统安装器核对签名后覆盖安装。清单格式随后端一起演进，开发阶段不承诺兼容（[ADR-0001](../docs/adr/0001-开发阶段不向下兼容.md)），取舍见 [ADR-0025](../docs/adr/0025-应用内更新检查与反馈的接口口径.md)。

## 应用内反馈

`POST /v1/feedback` 公开接收一条反馈，登录与否都能提交，服务端不读 `Authorization`，也不把反馈绑定到账号。正文 `content` 必填，去掉两端空白后 1 至 4000 字；`contact` 可选，必须是普通邮箱地址，用于回复；`app_version`、`platform` 与 `diagnostics` 可选，上限分别是 64 字、32 字与 64 KiB。诊断摘要由客户端先在本地说明会提交哪些内容，再截取用户看过的片段，不自动上传整份诊断记录。提交按来源地址限流，参数见下表的 `ZHIXIN_FEEDBACK_*`；来源地址通过之后再消耗实例额度，参数见 `ZHIXIN_FEEDBACK_GLOBAL_*`。实例最多保留 10,000 条反馈，满时返回 429，按保留期清理后可继续接收。

反馈写入 PostgreSQL 的 `feedback` 表，内存存储时只在进程里保留，重启即丢。公开接口只写不读；后台的“反馈”页与 `/admin/v1/feedback` 下的三个接口负责查看、读取单条与删除，读的是同一张表，也不把反馈绑定到账号，取舍见 [ADR-0079](../docs/adr/0079-管理后台的反馈查看.md)。保留期由 `ZHIXIN_FEEDBACK_KEEP_DAYS` 控制，默认 365 天，`feedback.PruneLoop` 在启动时清一次、之后每天清一次，平时不需要手工删除；后台不可用或要立刻清理时才执行下面的语句。

```sql
SELECT id, created_at, app_version, platform, contact, content, diagnostics
FROM feedback ORDER BY created_at DESC LIMIT 50;

DELETE FROM feedback WHERE created_at < now() - interval '365 days';
```

删除账号不影响已经提交的反馈，因为反馈本来就不属于账号；删除云端数据也不涉及这张表。正文与诊断摘要不写日志，与访问日志同一口径。

## 留存统计

S4 与 S5 要求统计一周与四周留存（[03 第 4 节](../docs/03-团队分工与协作.md#4-成功标准)），采集口径见 [ADR-0019](../docs/adr/0019-留存统计用匿名上报.md)，[00 第 7 章](../docs/00-产品定义.md#7-边界)写明不含学习内容。服务端分两路记录，都不解析学习内容：

- 登录账号的活跃：鉴权中间件在每次访问令牌校验成功之后调用 `retention.Service.RecordUserActive`，按 `ZHIXIN_TIMEZONE` 的自然日记一行到 `user_active`，同一个账号同一天只在第一次写库；模型代理密钥的请求不计入，日活仍按本人打开应用计算（[ADR-0063](../docs/adr/0063-模型代理接入密钥.md)）。不需要客户端额外上报，也不需要客户端带日期。
- 未登录设备的活跃：`POST /v1/telemetry/active` 公开接收 `install_id`、可选的 `app_version` 与 `platform`。服务端自己决定日期，不使用客户端时钟；安装标识校验格式之后算 HMAC-SHA256，库里只存哈希与日期，同一个标识同一天重复上报是幂等的。按来源地址限流，参数见配置表的 `ZHIXIN_TELEMETRY_*`，并受整个实例的全局写入上限 `ZHIXIN_TELEMETRY_GLOBAL_*` 约束；密钥来自 `ZHIXIN_TELEMETRY_SECRET`，为空时每次启动随机生成，重启后同一个安装会被当成新的，因此生产必须固定。

```json
{"install_id": "0f8fad5b-d9cb-469f-a165-70867728950e", "app_version": "0.2.0-dev+3", "platform": "android"}
```

匿名活跃按 180 天滚动删除：进程启动时清一次，之后每天清一次，`install_active` 里早于 180 天的行由 `retention.PruneLoop` 删掉；登录账号的活跃行数很小，随删号级联删除，不单独清理。两张表都不保存原始安装标识、IP、设备编号或账号之外的标识。后台的“留存”页读同一批数据：`GET /admin/v1/retention` 返回区间内每天的匿名安装数与登录账号数，以及按首次出现日分组的 7 日与 28 日留存，口径见 [ADR-0080](../docs/adr/0080-管理后台的留存视图.md)；匿名安装只统计首次出现日落在区间内的批次，首次当天不算回访。后台不可用或要逐行核对时仍可直接查库，语句与页面的判定一致：

```sql
-- 每日活跃：匿名安装数与登录账号数
SELECT day, count(*) AS active_installs FROM install_active GROUP BY day ORDER BY day;
SELECT day, count(*) AS active_users FROM user_active GROUP BY day ORDER BY day;

-- 一周留存：按首次出现的日子分组，7 天内再次活跃的比例；四周把 7 改成 28
WITH first_seen AS (
  SELECT install_hash, min(day) AS first_day FROM install_active GROUP BY install_hash
)
SELECT f.first_day,
       count(*) AS installs,
       count(*) FILTER (
         WHERE EXISTS (
           SELECT 1 FROM install_active a
           WHERE a.install_hash = f.install_hash
             AND a.day > f.first_day
             AND a.day <= f.first_day + 7
         )
       ) AS returned_7d
FROM first_seen f
GROUP BY f.first_day
ORDER BY f.first_day;
```

客户端的上报任务、安装标识的生成与保存、首次使用说明与设置页开关按 ADR-0019 已经接入：启动之后的空闲任务里尝试一次，每天最多成功一次，失败静默重试一次并写本机诊断；首次启动用一次说明讲清采集内容与用途，设置页“使用统计”可以随时关闭，关闭后不再上报。登录账号的活跃不需要客户端参与，两路数据因此都会进表；统计只用于按周与按月看留存，不统计功能使用，也不与其他数据关联。

## 部署与凭据

第一套实例跑在一台单机 Debian 13 上，不做容器化，原因与取舍见 [ADR-0009](../docs/adr/0009-API后端采用Go与分层框架.md) 第 7 条。`zhixin-api` 由 systemd 拉起，只监听回环地址，前面的 nginx 终止 TLS 并反向代理到它；数据库用发行版包安装的 PostgreSQL 17；备份与附件的字节放 S3 兼容的对象存储，第一套实例用阿里云 OSS，端点、地域、bucket 与密钥都写在服务器的环境变量里，不配置对象存储时回落到 `ZHIXIN_BLOB_DIR` 指向的本机目录，只用于本地开发。域名由管理员在 DNS 里指向这台机器，证书由 certbot 申请并自动续期。需要注入的环境变量就是上面配置表里的那些，仓库里不写口令与 key；资源清单、地址、接入方式与操作步骤见[运维手册](运维手册.md)。

加固轮次之后，启动时会自检生产配置：配置了数据库时 `ZHIXIN_MAIL_LOG` 必须为 `0`，`ZHIXIN_CODE_SECRET` 与 `ZHIXIN_TELEMETRY_SECRET` 必须固定，带认证的 SMTP 连接不允许 `none`，任何一项不满足都拒绝启动；第一套实例因此需要在 `api.env` 里补上两个固定密钥。带 key 的模型上游公网地址必须是 https，这条在后台保存来源时校验，不再随启动检查。按地址的限流要分清真实用户，`ZHIXIN_TRUSTED_PROXIES` 写 `127.0.0.1/32,::1/128`（nginx 只从回环地址连进来）；服务直接对外监听时保持为空。改了 `ZHIXIN_TRUSTED_PROXIES` 或其它配置之后重启服务生效，部署前按[运维手册](运维手册.md#4-加固后的运维动作)的核对清单逐项确认。

部署已经与仓库联动：`main` 收到 `server/**` 的推送后，[deploy-server.yml](../.github/workflows/deploy-server.yml) 先跑与服务端 CI 相同的一组检查，通过之后交叉编译、上传、重启并核对 `/readyz`，失败时自动换回上一份可执行文件，也可以从 Actions 手动运行；账号、secrets、回滚与轮换步骤见[运维手册](运维手册.md#49-自动部署与回滚)，取舍见 [ADR-0032](../docs/adr/0032-main推送后自动部署服务端.md)。自动部署不处理表结构与运行配置，`schema.sql` 与 `api.env` 的变化仍在服务器上手工执行；部署工作流本身不可用时，照旧三步手工发布：在开发机上交叉编译，把可执行文件传到服务器的 `/opt/zhixin/bin/`，再执行 `systemctl restart zhixin-api`，回滚是把 `zhixin-api.prev` 换回去重新启动。发版时还要把安装包放到清单里的地址，用 Actions 发版任务在 step summary 里给出的 `sha256` 与 `signature` 更新 `ZHIXIN_RELEASE_FILE` 指向的 JSON 文件，再重启服务；地址必须是 https，漏掉这一步或清单与安装包对不上时客户端都不会提示更新。空库首次启动前把 `ZHIXIN_APPLY_SCHEMA` 设为 `1`，建表之后改回 `0`，因为 `schema.sql` 不带 `IF NOT EXISTS`，重复执行会报错。schema 32 的结构变化（删 `user_purge`、`sync_commit` 增加必填 `kind`、删三条索引与 `sync_commit` 的 `UNIQUE (user_id, uid)`）同样要在现有实例上按当前 `schema.sql` 手工重建库，重建会清空全部账号，内测者需要重新注册（[ADR-0057](../docs/adr/0057-服务端改表清空重建.md)）；重建按[运维手册](运维手册.md#49-自动部署与回滚)的步骤停服、`pg_dump` 全量备份、只保留模型来源与模型路由和两张实例级用量表，建库之后用 ossutil 按 `attachments/` 前缀清空对象存储里的附件字节，这类字节在重建之后既没有索引行也没有对应的账号；清除云端数据期间的互斥只在进程内有效，服务端按单实例部署，换成多实例部署时要另做跨进程协调。保留期 `ZHIXIN_SYNC_COMPACT_KEEP` 有默认值 168 小时，不配置也照常运行，内测期间希望落后设备少重新克隆时可以调到 720 小时并写进 `api.env`，重启后生效。日常备份是 `pg_dump`，加上对象存储里 `backups/` 与 `attachments/` 两个前缀下的字节；删号与删除备份都会按前缀清理，所以两处要一起备。

服务器只有一位管理员（[04 第 5 节](../docs/04-长期路线图.md#5-决定) D7），不设第二位。数据库口令、对象存储密钥、TLS 证书与备份介质的存放位置，以及主机失联、数据库损坏、对象存储不可用三种情况下的恢复步骤，由管理员写在仓库之外的私有目录；仓库只保留需要哪些变量与恢复的先后顺序。公测准备阶段做一次恢复演练，用备份重建一台可用实例，演练日期与结果写进结题材料。

## 本地运行与检查

需要 Go 1.27。

```bash
cd server

curl localhost:8080/healthz
curl localhost:8080/v1/app/releases  # 没有配置发布清单时是空数组
curl -X POST localhost:8080/v1/feedback \
  -H 'Content-Type: application/json' \
  -d '{"content":"记录页按下一步没有反应","app_version":"0.2.0-dev+3","platform":"android"}'
curl -X POST localhost:8080/v1/telemetry/active \
  -H 'Content-Type: application/json' \
  -d '{"install_id":"0f8fad5b-d9cb-469f-a165-70867728950e","app_version":"0.2.0-dev+3","platform":"android"}'
```

本地要试模型代理时，先给服务一个管理令牌，再经管理接口登记来源与模型（内存存储的加密密钥随进程生成，重启后要重新登记）：

```bash
ZHIXIN_ADMIN_TOKEN=$(openssl rand -base64 32) go run ./cmd/zhixin-api
TOKEN=$ZHIXIN_ADMIN_TOKEN
curl -H "Authorization: Bearer $TOKEN" -X POST localhost:8080/admin/v1/providers \
  -H 'Content-Type: application/json' \
  -d '{"id":"deepseek","base_url":"https://api.deepseek.com/v1","api_key":"sk-..."}'
curl -H "Authorization: Bearer $TOKEN" -X POST localhost:8080/admin/v1/models \
  -H 'Content-Type: application/json' \
  -d '{"name":"zhixin-chat","kind":"chat","routes":[{"provider_id":"deepseek","upstream_model":"deepseek-chat"}]}'
curl localhost:8080/v1/llm/models
```

设置 `ZHIXIN_DATABASE_URL` 之后启动就用 PostgreSQL，备份与附件默认写到 `ZHIXIN_BLOB_DIR`。要连 MinIO 时设置 `ZHIXIN_S3_ENDPOINT`、`ZHIXIN_S3_BUCKET`、`ZHIXIN_S3_ACCESS_KEY` 与 `ZHIXIN_S3_SECRET_KEY`，bucket 要先建好，`/readyz` 会检查它是否存在。

2026 年 11 月 15 日用 PostgreSQL 17 与从 `RELEASE.2025-10-15T17-29-55Z` 构建的 MinIO 本地联调，服务端为 `9bf7474`。附件校验哈希，重复上传只保留一个对象，另一账号无法读取。约 18 MiB 的备份可上传并逐字节下载，保留两份时最旧对象会清理。删除备份和删除账号后直接列出 bucket，确认相应对象已清除。

提交前执行与 CI 相同的四条命令：

```bash
gofmt -l .        # 应当没有输出
go mod tidy -diff
go vet ./...
go test ./...
```

改了 `schema.sql` 或 `internal/store/queries/` 下的查询要先重新运行 `sqlc`，改了 `openapi.yaml` 要先重新运行 `oapi-codegen`，生成结果随源文件一起提交；CI 会重新生成并用 `git diff --exit-code` 核对，本地少了这一步时编译与测试仍可能通过，推上去却会在生成核对上失败。
