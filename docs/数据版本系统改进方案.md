# 知新 · 数据版本系统改进方案

> 范围是客户端的数据版本系统：`app/lib/data/revisions/` 下的采集、提交、投影、检查点、撤销与留存，`GuardedDatabase` 与 `WriteTransactions` 的命令入口，以及同步服务里推送本机提交与应用远端提交的两段。基线是 2026-11-20 的 `main`（`630b56d`），schema 27。服务端的同步协议不改。
>
> 组织方式：先由一个人完成很短的“阶段 0”，把表结构、枚举、文件拆分和几个挂钩函数定下来；之后六条泳道按文件归属并行开发，互相只通过阶段 0 定好的接口交互；最后由一个人收口文档与整体测试。每条泳道写明拥有哪些文件、对外承诺什么、怎样验收。
>
> 阶段 0 与六条泳道已经全部合入 `main`，之后的问题与改法另见[数据版本系统对照 git 的改进方案](数据版本系统对照git的改进方案.md)；本文保留作背景与验收依据，第 1 节的问题清单按 `630b56d`（schema 27）当时的代码写。

## 1. 现状与问题

现有设计的主线是对的：触发器把一次命令里的行变化写进暂存表，命令结束时合并成行级净变化；重建从检查点出发，按提交顺序回放并核对预期旧值；撤销按代次限定范围，并在同一事务里核对后续修改与业务约束。下面这些问题不推翻这条主线，按影响排序。

| 编号 | 级别 | 问题 | 位置 |
|---|---|---|---|
| R1 | 正确性 | `WriteTransaction.result()` 在 `finishCommand` 之前读 `active_commit`，没有净变化时仍返回 `WriteResult.committed(id)`；每个经过 `_run` 的事务都占一个编号，`clearHistory` 又把 `next_commit` 退回 `head+1`，占过但没落库的编号会被后来的提交复用 | `write_transactions.dart`、`guarded_database.dart:153-207`、`revision_engine.dart:499-589、1384` |
| R2 | 正确性 | `prune` 与 `clearHistory` 不看同步的 `pushedThrough`：离线期间清理历史，被删的提交再也推不到服务端；清理后保留的 HEAD 提交变化条数为 0 | `revision_engine.dart:1336-1519`、`sync_service.dart:632` |
| R3 | 正确性 | 应用远端提交时不看 `before`：新增撞上已有主键整行覆盖，更新遇到本机已删的行静默跳过，只记诊断；用户不知道哪些本机修改被覆盖 | `revision_engine.dart:817-886`、`sync_service.dart:698-740` |
| R4 | 性能 | 周期检查点按 `commit.id % 25` 触发，编号会跳号所以间隔不定；触发时在写事务里重建整库投影、编码 JSON、算 sha256，那一次写入明显变慢 | `revision_engine.dart:579-587` |
| R5 | 存储 | 检查点是整库 JSON，每个值包一层 `{"t","v"}`，体积约为原数据的 2～3 倍；命名一次就立即写一份完整副本 | `revision_engine.dart:1204-1263` |
| R6 | 性能 | `_pruneOnce` 为了数检查点条数把全部 `projection_json` 读进内存两次；附件回收与 `verifyAssets` 解码全部变更明细 JSON，两段代码几乎一样 | `revision_engine.dart:1458-1513、1534-1621` |
| R7 | 性能 | 按容量裁剪时保留条数逐次减半，每轮都 `VACUUM`，最多约 7 次整库复制 | `revision_engine.dart:1393-1421` |
| R8 | 性能 | “与当前比较”做两次整库重建，HEAD 一侧其实就是当前表 | `revision_engine.dart:934-938`、`data_version_page.dart:327` |
| R9 | 结构 | 动作文案兼任类型：`'恢复版本'`、`'导入数据'` 等中文标签参与撤销判断；`op` 与值类型都是字符串 | `revision_undo.dart:173-211`、`revision_models.dart` |
| R10 | 结构 | 写提交行的代码有两份，撤销提交再补一条 UPDATE 写 `reverted_commit_id`；投影比较有 `diffProjections`、`_changesFromDiff`、`_sameProjection`、`_verifyProjection` 四份 | `revision_engine.dart`、`revision_undo.dart:97-103` |
| R11 | 结构 | `RevisionEngine` 1734 行，类注释仍写“兼容 sqflite”；`WriteTransactions` 与 `installRevisionSchema` 各自 `new RevisionEngine()`，缓存、时钟、附件存储各一份 | `revision_engine.dart:104`、`write_transactions.dart:10、33` |
| R12 | 健壮性 | 安装采集时删除库里全部非 `sqlite_` 触发器；暂存表 `CREATE IF NOT EXISTS`，列变了也不重建 | `revision_engine.dart:1625-1670` |
| R13 | 结构与行为 | 撤销的业务约束（预约冲突、学习事项归属、课表）写在数据层；撤销把 `updated_at` 写回旧值，且任何后续修改都会改到 `updated_at`，所以同一行之后改过任意一列都不能再撤销 | `revision_undo.dart:31-49、213-290、508-532` |
| R14 | 一致性 | `undoCommit` 重建图片缓存失败会让已经生效的撤销报成失败，`restore` 已经单独处理了这种情况；`rowHistory` 的 SQL 写在服务层 | `revision_service.dart:114-133、244-253` |

## 2. 目标口径

改完之后系统应满足以下几条，后文各泳道的验收都从这里来。

提交编号只增不减，只在真正形成提交（或者命令里显式要了回执编号）时分配；`WriteResult.changed` 与是否落库一致。

历史的每个下游读者在库里登记读到哪里（同步推送、文本索引、记忆索引）。会丢数据的读者（同步推送）没读完的提交不能被裁剪或清理；只会退回全量重建的读者（索引）不阻止裁剪。

同步仍然是后到覆盖先到，但本机能列出每一处被远端覆盖的本机修改，并能一键把本机值作为新提交写回。

写事务里不再生成整库检查点；检查点压缩存储；命名版本只在跨过裁剪边界时才固化。

附件回收、附件核对、留存统计都不再解码全部变更明细；按容量裁剪最多 `VACUUM` 一次。

提交的类型由 `kind` 列决定，`action` 只给人看；撤销的业务约束由应用层注册。

## 3. 阶段 0：契约先行（串行，一人）

阶段 0 不改任何行为，只把后面并行需要的“接缝”做出来。完成标准是全部现有测试通过、`flutter analyze` 无新增告警。之后的泳道都从阶段 0 合入后的 `main` 拉分支。

### 3.1 表结构（schema 27 → 28）

按 [ADR-0017](adr/0017-表结构变化仍清空数据.md) 版本不一致即清空重建，不写迁移。在 `lib/data/db/drift/tables.dart` 里改，重新生成 `app_database.g.dart`，`zhixinSchemaVersion` 改为 28。

| 表 | 变化 | 用途 |
|---|---|---|
| `revision_commit` | 新增 `kind TEXT NOT NULL`，取值 `baseline`、`write`、`undo`、`restore`、`import`、`maintenance`、`remote`；新增 `byte_length INTEGER NOT NULL DEFAULT 0`，记这条提交变更明细的字节数；新增 `conflict_count INTEGER NOT NULL DEFAULT 0` | R9、R7、R3 |
| `revision_context` | 新增 `capturing INTEGER NOT NULL DEFAULT 0`；`active_commit` 保留为“已预留的提交编号”，可空 | R1 |
| `revision_checkpoint` | `projection_json` 改为 `payload BLOB NOT NULL`，新增 `encoding TEXT NOT NULL`（`json` 或 `json+gzip`）与 `raw_bytes INTEGER NOT NULL`；`checksum` 仍按解压后的原文计算 | R5 |
| `revision_cursor`（新） | `name TEXT PRIMARY KEY`、`position INTEGER NOT NULL`、`blocking INTEGER NOT NULL`、`updated_at TEXT NOT NULL` | R2 |
| `revision_asset_ref`（新） | `owner_kind TEXT`（`change` 或 `checkpoint`）、`owner_id INTEGER`、`hash TEXT`，主键是三列合起来，另建 `hash` 索引 | R6 |
| `revision_conflict`（新） | `id`、`commit_id`、`table_name`、`row_key`、`column_name`（整行冲突时为空）、`reason TEXT`、`local_json`、`remote_before_json`、`remote_after_json`、`resolved_commit_id`（可空） | R3 |

阶段 0 里 `encoding` 一律写 `json`、`payload` 存 UTF-8 字节，`byte_length` 照实写入，`revision_asset_ref` 与 `revision_conflict` 建表但不写。

## 4. 并行泳道

六条泳道之间没有先后依赖，只依赖阶段 0。共享文件只有 `revision_service.dart` 与 `data_version_page.dart`，下面写清楚各自只动哪些方法。测试一律新建文件，避免同时改 `revisions_engine_test.dart`；确实需要改已有测试时，由行为发生变化的那条泳道改，并在合并说明里写出来。

### 泳道 A：提交编号与写入结果（R1、R12）

拥有：`revision_capture.dart`、`revision_log.dart`、`guarded_database.dart`、`write_transactions.dart`、`domain/models/write_result.dart`。

做法：

1. 触发器的 `WHEN` 条件改为 `capturing = 1 AND suppress = 0`，暂存表去掉 `commit_id` 列（同一时间只有一个写事务，暂存表在事务外总是空的），合并与清空都按整张暂存表处理。
2. `beginCommand` 只把 `capturing` 置 1，不分配编号。`WriteTransaction.requireCommitId()` 第一次调用时从 `revision_sequence` 预留编号并写进 `active_commit`；`finishCommand` 有净变化时用预留的编号，没有预留就在这时分配。没有净变化且没有预留时，序号不动。
3. `GuardedDatabase.command` 把 `finishCommand` 的返回值交给 `WriteTransactions.run`；`run` 收到的结果是 `WriteResult` 且这次没有形成提交时，改成 `WriteResult.skipped()`。`lib/application/` 下约 38 处调用里，凡是把 `WriteResult` 包在记录或别的对象里返回的，逐个改成在 `run` 之外组装，这些改动都是机械替换。
4. `installRevisionSchema` 只删除 `rev_capture_` 前缀的触发器；暂存表在打开库时先删除再按当前列重建。

验收（新测试 `test/data/revision_commit_id_test.dart`）：写入值不变时 `WriteResult.changed` 为假、`revision_sequence` 不前进；只读 `transaction()` 不消耗编号；连续写入的提交编号连续；生成回执的命令预留的编号就是落库的提交编号；库里另有一个非 `rev_capture_` 触发器时，打开库后它仍在。

约 2.5 人日。

### 泳道 B：历史位置、留存与附件回收（R2 引擎侧、R5 命名部分、R6、R7）

拥有：`revision_maintenance.dart`、`asset_store.dart`；`revision_service.dart` 里的 `prune`、`clearHistory`、`name`、`deleteName`、`storageUsage`、`verifyAssets`、`historyBlockers`。

做法：

1. 裁剪的下界取“按保留条数算出的最早保留提交”与“所有 `blocking = 1` 的读取位置 + 1”中较小的一个。`clearHistory` 在存在阻塞位置落后于 HEAD 时不执行，`historyBlockers(clearing: true)` 返回原因，例如“还有 12 条修改没有同步到云端，先同步再清理”。`clearHistory` 不再回退 `next_commit`。
2. 实现 `recordAssetRefs`：提交写入时登记变更明细里的附件哈希，写检查点时登记检查点清单。附件回收改成一条反连接：当前投影的哈希加上 `revision_asset_ref` 里仍有主人的哈希之外的附件对象都可以删。裁剪、清理删除提交或检查点时，同时删除对应的引用行。`verifyAssets` 同样改为读引用表。
3. `_pruneOnce` 里所有只为计数的 `selectRows` 改为 `COUNT(*)`。
4. 按容量裁剪：用 `SUM(byte_length)` 和检查点的 `length(payload)` 估算每条提交的空间，一次算出保留条数，做一次裁剪、一次 `VACUUM`。
5. 命名版本：`nameCommit` 只写 `revision_ref`，不再写检查点；裁剪时，落在下界之前的命名提交先调用泳道 C 提供的 `materializeCheckpoint(txn, commitId, kind: 'named')` 固化，再删除历史。`deleteName` 只在这个命名提交已经固化、且没有别的名字指向它时删除检查点。

`materializeCheckpoint` 在阶段 0 里就是现有 `_writeCheckpoint` 加 `projectionAt` 的组合，B 直接调用即可，不必等 C。

验收（新测试 `test/data/revision_maintenance_test.dart`）：同步位置停在第 40 条时裁剪到只留 10 条，第 41 条之后全部仍在；有阻塞位置时清理历史被拒绝并给出原因；清理历史后的下一条提交编号大于清理前的最大编号；附件回收结果与旧算法在同一组数据上一致；按容量裁剪只执行一次 `VACUUM`（用计数的执行器包装断言）；命名之后检查点条数不变，裁剪跨过命名提交后多出一个 `named` 检查点，并且恢复到该命名版本的结果与命名时的数据相同。

约 3 人日。

### 泳道 C：投影、检查点与比较（R4、R5 压缩部分、R8、R10 后半）

拥有：`revision_projection.dart`；`revision_service.dart` 里的 `compare`、`previewRestore`、`restore`、`checkpoints`。

做法：

1. `checkpointAfterCommit` 改为空操作，写事务里不再生成检查点。`afterCommitIdle` 在独占区释放之后、空闲时检查“距最近检查点累计的 `byte_length`”，超过阈值（建议 8 MB，作为构造参数）就单独开一个维护事务，用 `readProjection` 读当前表生成检查点，不再从上个检查点回放。保留历史本来只有约 100 条，这个阈值多数用户很少碰到。
2. 检查点改为 `json+gzip` 编码（`dart:io` 的 `gzip`），读取时按 `encoding` 解码；校验值仍对解压后的原文计算。数据包（`revision_package.dart`）的格式不变。
3. 新增 `foldChanges(executor, from, to)`：在保留历史内按“表名＋主键”把 `(from, to]` 的净变化合并成一组，`compare` 优先走它，起点已被裁掉时才退回两次重建；`compare(x, head)` 的 HEAD 一侧改用 `readProjection`。
4. 四份投影比较合并为一个 `List<RevisionChange> diffProjections(before, after)`，`RevisionDiff` 从它派生，`_sameProjection` 与 `_verifyProjection` 改为判断这份结果是否为空。

验收（新测试 `test/data/revision_projection_test.dart`）：连续 100 次写入都不在写事务里插入检查点；超过阈值后空闲时多一个检查点，且从它重建的投影与当前表一致；gzip 检查点与旧 JSON 检查点重建结果一致，篡改一个字节报 `RevisionCorruption`；随机生成的 200 条写入序列上，任取两点，`foldChanges` 的结果与两次重建再比较的结果一致。

约 3 人日。

### 泳道 S：同步位置与冲突记录（R2 同步侧、R3）

拥有：`revision_remote.dart`、`application/sync_service.dart`、`data/cloud/cloud_preferences_store.dart`；`revision_service.dart` 里的 `applyRemoteCommit`、`commitsAfter`、`conflicts`、`keepLocal`。

做法：

1. `pushedThrough` 改存 `revision_cursor`，名字 `sync.pushed`，`blocking = 1`；从服务端拉到的位置存 `sync.server_head`，`blocking = 0`。偏好里只留账号与设备相关的字段。这样整库恢复时同步位置随库一起回去；若恢复的是旧备份，位置变小，会把服务端已有的提交再推一次，服务端按请求编号去重，结果不变。
2. 推送时按 `kind != 'remote'` 过滤，删掉 `remoteLocalIds`。
3. `applyChanges` 按列做三方比较，仍然写入远端值：

   | 远端变化 | 本机情况 | 记为冲突的条件 | `reason` |
   |---|---|---|---|
   | update | 行存在 | 某列本机当前值既不等于远端 `before` 也不等于远端 `after` | `concurrent_update` |
   | update | 行不存在 | 一律 | `deleted_locally`（仍跳过写入） |
   | insert | 行已存在 | 有列与远端整行不同 | `insert_collision` |
   | delete | 行存在 | 当前行与远端 `before` 有列不同 | `deleted_remotely_modified` |

   冲突写进 `revision_conflict`，提交的 `conflict_count` 随之更新；`skipped` 仍返回，诊断照记。
4. `keepLocal(conflictId)` 把 `local_json` 里的值作为一条普通 `write` 提交写回（动作文案“保留本机修改”），并在冲突行上记 `resolved_commit_id`；这条提交照常推送，其他设备上就是一次正常的后到覆盖。

验收（新测试 `test/data/revision_remote_conflict_test.dart`，以及在 `test/application/sync_service_test.dart` 末尾追加用例）：四种冲突各一例，记录内容正确且远端值已写入；`keepLocal` 之后本机值恢复、冲突标为已处理、新提交出现在待推送列表里；远端提交不会被再推回服务端；同步位置写进了库，偏好里不再有 `pushed_through`。

约 3 人日。

### 泳道 U：撤销规则（R9 撤销侧、R13、R14 前半）

拥有：`revision_undo.dart`、新目录 `lib/application/undo_guards/`；`revision_service.dart` 里的 `undoCommit`、`undoBlockReasons`；`app_scope.dart` 里构造 `RevisionService` 的那几行。

做法：

1. 阶段 0 包好的三个 guard（预约、学习事项、课表）移到 `application/undo_guards/`，连同它们依赖的 `schedule_conflicts` 调用。表白名单和 `_actionTables` 改为由各 guard 声明的 `tables` 与 `actionTables` 汇总，数据层只剩通用核对。`message` 回执清理是版本系统自己的规则，留在数据层。
2. `_laterChanges` 和“当前值等于提交后的值”这两项核对都排除 `revisionBookkeepingColumns`。撤销 update 时这些列写当前时间，不写回旧值；撤销 delete 重新插入时也写当前时间。
3. 远端提交（`kind = remote`）按普通写入同样适用白名单，撤销产生的 `undo` 提交照常推送。
4. `undoCommit` 里的图片缓存重建按 `restore` 的方式处理：失败只返回提示，不把已生效的撤销报成失败。

验收（新测试 `test/data/revision_undo_guard_test.dart`）：改了记忆内容之后再改它的有效期，先前那次内容修改仍可撤销；撤销后 `updated_at` 不早于撤销时刻；三个 guard 的原有用例在搬家后全部通过（`revision_flow_schedule_test.dart` 等不改断言）；缓存重建抛错时撤销结果为成功并带提示。

约 2.5 人日。

## 8. 实施记录

阶段 0 与六条泳道已经全部合入 `main`，提交历史里按 `merge:` 记录逐条可查；收口更新了 [01-ER数据模型](01-ER数据模型.md) 的撤销、数据版本表、导出恢复与同步位置几节，[ADR-0039](adr/0039-数据版本的提交类型与同步冲突记录.md) 状态改为已采纳。下面记录与上文写法的偏差和落地时补上的位置，后来的人读方案时以此为准。

引擎拆分用 `part` 加同库 `mixin`，不是把类成员直接拆到多个文件：Dart 不支持跨文件的类成员，每个 `part` 文件声明一个 `mixin RevisionXxxMixin`，通过 `RevisionEngine get self` 取字段与其他文件的方法，公有 API 与调用方不变。代价是读代码时先看 `revision_engine.dart` 的 `part` 表定位文件。

提交编号的结果不逐处改调用点，而是由 `WriteTransaction.result()` 返回占位值、`WriteTransactions.run` 在命令收尾之后定稿：形成提交时给落库编号，没有形成时给 `skipped`。因此凡是把 `WriteResult` 包在记录里返回的写法都要在 `run` 之外组装，本次改了两处（容量面板的预约时间块、清空一条讨论）；需要编号写回执时用 `requireCommitId()`，它会给本次命令预留编号，编号被占但没有形成提交时序号只增不减。

撤销写回时 `updated_at` 这类维护列一律写撤销时刻，先前“撤销把修改时间恢复成旧值”的口径随之作废。撤销的业务规则经 `RevisionService(undoGuards: ...)` 注入，生产装配在 `app_scope` 一次注册；测试装配用 `openTestRigWithUndoRules()`。

比较的折中路径用私有异常 `_FoldUnavailable` 表示“起点已被裁掉或中间有基线跳变”，`compare` 捕获后退回两次重建，`foldChanges` 的签名保持直接返回净变化列表；`diffProjections` 改成顶层函数，差异条目的顺序改为表依赖序加主键序。

附件引用表在阶段 0 之后新建的库里由提交与检查点写入；阶段 0 之前的旧库（`revision_asset_ref` 为空）不写迁移，回收时若引用表为空而检查点仍列有附件就跳过回收，宁可留下附件也不误删；这类库的附件核对只覆盖引用表与当前投影，等下一次新提交或检查点写入引用行之后恢复完整。

同步冲突里 `deleted_locally`（本机已删、远端还在改）没有可以写回的本机值，`keepLocal` 返回空，界面只说明“本机已经删除、远端的修改没有写入”，不提供写回按钮；其余三种冲突都能写回。一条远端提交的变化全部被跳过时没有形成提交，冲突随提交行落库的前提不成立，这种情况只返回跳过条数并记诊断。

同步位置从应用私有目录搬进 `revision_cursor` 之后，`server/README` 的同步协议说明、01 的导出恢复一节与 02 的数据版本页说明同步改成新口径；偏好文件只留账号、实例与上次同步时间。

收口时跑过 `dart format --output=none --set-exit-if-changed lib test`、`flutter analyze` 与全量 `flutter test`，三项通过；真机与两台模拟设备的整体走查仍待测试角色在验收里执行，脚本层的等价场景（写入、撤销、命名、比较、整版恢复、按留存清理、导出与恢复版本库备份、两台模拟设备同步出冲突再保留本机修改）由新增与已有测试覆盖。

## 9. 收尾记录

方案合入之后按评审意见补了一轮，决定与取舍记在这里。

同步按 git 的做法定：一次同步先拉取再推送，拉取时记下远端真正写进本机的格子，推送时跳过改动落在这些格子上的本机提交，推送位置照常前进。此前的问题是拉取把本机值覆盖成远端值之后，本机那条旧提交仍会跟在后面推上去，服务端存的是被覆盖的旧值、本机显示的是远端新值，两台设备从此分叉；现在被覆盖的提交不再推送，没落在这些格子上的提交照常推送。判断是保守的：一条提交只要有一处落在被覆盖的格子上就整条不推，不按列拆出一半去推。

本机已删、远端还在改的覆盖记录（`deleted_locally`）没有可以写回的本机值，数据版本页给它“知道了”，确认之后删除这条记录，不形成提交；其余三种冲突仍然只能用“保留本机修改”消解。

空闲检查点仍然在写命令的 Future 里等待完成：跨过累计阈值的那一次写入要等整库投影、压缩与校验值算完才返回。这样顺序确定、测试可复现，代价是这一次写入偏慢；阈值按变更明细累计字节数算，多数用户很少触发，以后要改安静期延后，调用点在 `guarded_database.dart`，不影响数据口径。

附件回收改成一条 `DELETE FROM asset_object WHERE hash NOT IN (...)`，删掉的条数由回收前的对象清单减去保留清单算出；保留哈希超过两万个时退回逐条删除，避开不同平台的 SQLite 变量上限。裁剪后的基线校验改调 `projectionsEqual`，不再保留第二份投影比较。

`foldChanges` 的一致性测试从抽样改成任意两点：60 次随机写入、1770 对提交点全部与两次重建的结果逐条比对，数量再大公共测试的超时放不下，保留原来的 200 次写入抽样用例。

没有改动、只记录理由的三处：`RevisionBlocked` 留在 `revision_maintenance.dart`，界面只通过 `historyBlockers()` 预判，不直接依赖这个异常；`clearHistory` 不删除挂在 `HEAD` 上的冲突记录，那些记录仍然可以写回；阶段 0 旧库的附件引用表为空，回收保守跳过，等一次新提交写入引用行之后恢复完整。
