# 数据库结构过度设计审查

> 审查日期 2026-11-23，范围是客户端 SQLite（`app/lib/data/db/drift/tables.dart`，schema 30，27 张表）与服务端 PostgreSQL（`server/internal/store/schema.sql`，26 张表）。体例沿用 [过度设计审查](过度设计审查.md)：成因分类、证据、建议、风险。已在该文档中列过的条目只引用编号，不重复展开，本文只补“表与列”这一层以前没有单独看过的内容。证据来自 grep 引用统计、读表定义，以及对同步与版本引擎实现的逐段阅读（见第 6 节），没有改代码、没有跑测试，行数与列数都是量级。第 1 至第 8 节的条目已经随 schema 31 实施；第 9 节是 schema 31 合入之后、0.3.0 再次调整表结构之前的复审，其中的缺陷在沙箱的测试副本里复现过。

## 1. 总体判断

结构本身比代码干净：业务表只有 14 张，列名、外键动作、CHECK 约束都有写法统一的来源（`tables.dart` 与 `checkValueSets`），多数列有读写点。问题集中在三处。

第一，客户端 27 张表里有 12 张是版本与同步的元数据（`revision_*` 9 张、`sync_shadow`、`asset_object`、`asset_chunk`），业务表 14 张、设置表 1 张。簿记表的数量接近业务表，其中 `revision_commit` 一张表就有 20 列。

第二，同一个事实存两份，版本控制一侧尤其明显：完整性有 `hash` 链、检查点 `checksum` 与 `state_digest` 三套，其实 `state_digest` 一个就够；检查点的附件清单既在 `revision_checkpoint.asset_hashes_json`，又在 `revision_asset_ref`；`revision_commit` 的两个条数是别的表数得出来的缓存；`study_plan.current_page` 是由已完成事项算出来再写回的缓存；服务端 `sync_head` 与 `sync_snapshot` 都是每账号一行，却分在两张表。

第三，为一个尚未出现的需求预留了表或列：登录方式 `phone`、`wechat`，设备能力字符串，快照让位表，清除标记表。这些与第一份审查的 B 类（预留未用）同源。

成因沿用原分类，表层只出现四类：A 规模错配、B 预留未用、C 兼容残留（仅 V6 一处，是回填工具的附属索引）、E 复制多于抽象（在这里指“同一信息存两处”）。D 与 F 不适用于表结构。另有一类不是削减而是“补强”：对照 git 的 refs 与树哈希之后发现少记了本该记的事实（分表摘要、云端序号、设备已同步到的位置、命名版本随账号同步），来自 [ADR-0053](adr/0053-标识按身份顺序指纹分工并收拢提交标识.md) 与 [ADR-0054](adr/0054-数据版本位置标记补强.md)，在表里的类别栏写“补强”，每条都写明为什么不能由其他列派生。

按已确认的条目落实，客户端削减两张表（合并 `revision_context` 与 `revision_sequence`，`profile` 并入 `app_meta`），列减少约 10 个；再加上 [ADR-0054](adr/0054-数据版本位置标记补强.md) 的补强列（`server_seq`、`table_digests_json`、`head_commit_id`，见 S13 至 S15）与 `revision_ref` 的 `commit_uid`、`sync_state`、删去的 `commit_id`，净减少约 6 列；[ADR-0056](adr/0056-本机数据按账号分空间.md) 同批删 `revision_cursor.scope`（S7）。表数上，削减两张之后，ADR-0054 新增命名版本墓碑表 `revision_ref_tombstone`（S14），[ADR-0051](adr/0051-记忆改为自由文本条目并走文档检索路径.md) 新增 `memory_usage` 与 `memory_use`（S12），合计 28 张。服务端表由 26 张降到 24 张（合并 `sync_head` 与 `sync_snapshot`，`sync_snapshot_orphan` 并入 `attachment`），索引减少 5 个，ADR-0054 新增 `sync_ref` 一张表（V13）后为 25 张。原来暂不动的条目在 0.3.0 之前定了去向（第 9.3 节）：V6 与 V10 随 schema 32 删除，V5 的索引随 schema 32 删除、代次表与 FP16 随 5.2 处理，V8、V11 与 S7 的 `blocking` 长期保留。其中约一半与第一份审查的 3.6、3.8、5.2、5.9、5.13 重叠，真正新增的是第 3 节和第 4 节的条目。

## 2. 处置原则

沿用第一份审查第 2 节的原则，并补充四条表层特有的：

| 原则 | 说明 |
|---|---|
| 一次改完 | [ADR-0017](adr/0017-表结构变化仍清空数据.md) 规定内测与公测期间客户端表结构一变就清空重建，每次改结构都会让已有内测数据作废。表层的改动应合并成一次 schema 版本变化，赶在 0.3.0 发出之前做，之后每改一次都要通知内测者 |
| 服务端改表另有代价 | 服务端没有迁移，`store.go` 按 `schema.sql` 整份重建，连 `app_user` 一起清空；ADR-0017 只管客户端。0.3.0 之前重建没有代价；之后每改一次服务端表仍清空全部内测账号重建（2026-11-23 用户定），并在发版说明里写明需要重新注册。第 4 节里原来“暂不动”的服务端条目已在第 9.3 节定下去向 |
| 与功能审查同批 | 与 3.5、3.6、5.2、5.9、5.13 重叠的条目随各自条目落地，不单独排期；3.8 已决定保留，不再有表层改动 |
| 派生优先于缓存 | 能从其他列用一条查询算出来、且数据量只有几千行的，不存列。要存，须写明读它的位置 |
| 补强列要写明不可派生 | 新增列只用于记录“当时观察到的外部事实”（例如提交落库时已知的云端位置），必须写明不能由本机其他列算出，且允许为空、为空时不影响同步正确性（S13 至 S15、V12 至 V15） |

## 6. 核实情况与局限

人工读过两份定义文件的全部内容，并核对了这些结论：`last_message_at` 在 `lib` 与 drift 查询里只有一处写入、没有读取；`asset_hashes_json` 与 `revision_asset_ref` 两处各有代码在维护；`hash` 与 `parent_hash` 只被完整性检查与裁剪锚点读取，不进同步协议，也不用于去重；`checksum` 与 `state_digest` 在读取检查点时先后各校验一次；`encoding` 只有一个写入点且恒为 `json+gzip`；`checkpoint.kind` 的四个取值都有写入点。

初稿里有三条在核对后撤回：`origin_json` 承载三个键并被撤销逻辑读取，不是单键 JSON 列（S8）；`revision_ref` 存的是 `HEAD` 加用户命名版本，集合是开放的（S11）；`grace_until` 在重试记录上不等于 `rotated_at + 60s`，是“重试不延长宽限”的依据（V3）。

初稿其余条目来自列名检索。复核 V8 时，管理后台的来源名、来源备注与模型备注都有读写入口，第一套实例的 3 个来源与 1 个模型都已填写备注；`llm_route` 当前没有 `note` 列，路由顺序用于显示和模型接入；额度备注由账号额度配置保存，实例中暂无额度覆盖。本批保留这些字段。

2026-11-23 实施之前补做了下面几项核对，结论写在各条的风险栏与 [ADR-0054](adr/0054-数据版本位置标记补强.md) 的“实施前要核对的”一节。

- S1 第 1 点：当前数据包只带业务投影，不带提交行，删列不受影响；版本库备份与整库备份都是整库快照，提交行整表带出，旧备份在恢复预检时按 `requiredColumns` 被判为缺字段而拒绝，符合 ADR-0001 与 ADR-0017，不阻碍实施。
- S1 第 2 点：列表先读取一批提交，再按这批提交编号对变更和冲突各做一次分组计数，查询次数与提交条数无关；详情页可以直接使用已载入的明细条数。用 SQLite 内存库模拟 500 条提交、每条 100 条变化和 5 条冲突，读取最近 200 条提交的两次计数，预热后测量 100 次，两次计数的合计中位数为 1.02 毫秒，查询计划分别使用变更明细主键和冲突的提交编号索引。
- S1 第 3 点：从最近的检查点重放到 `HEAD` 这条路各方情形都有起点——清理本机历史、快照重建与导入都会写 `initial` 检查点，裁剪在下界处写 `trimmed` 检查点；唯一没有起点的是“历史为空”，这时报告直接写“提交历史为空”。导入数据包追加的提交原来不带检查点，实施时一并在导入路径里补写 `initial` 检查点。
- S2：`revision_models` 与 `revision_projection` 的读取侧能改从 `revision_asset_ref` 取；`revision_maintenance` 里“引用表为空但历史可能仍有附件时不做回收”的判断改成“检查点表非空就跳过回收”，语义与原来一致，避免误删仍被引用的附件。
- S10：测试里有两处构造 `json` 编码的检查点，连同 `encoding` 读取分支一起删除。`checksum` 与 `asset_hashes_json` 必须同批删，否则校验函数先失去输入。

这次没有评估两个更大的问题：`revision_change` 对更新操作是否存整行前后各一份（`before_json`、`after_json` 都是整行 JSON 的话，存储量约翻倍，但格子级变基也许要求这样），以及 `asset_object`/`asset_chunk` 把图片存进 SQLite 是否值得（数据包与备份因此可以自包含，是有理由的取舍）。这两件事需要实测数据量才能判断。

S13 至 S15 与 V12 至 V15 来自 2026-11-23 对照 git 的讨论。复审时读了这些实现：客户端 `sync_service.dart` 的 `_pull`、`_pushBatches`、`repairFromLocal`、`repairFromCloud`，`revision_engine.dart` 的初始化路径，`revision_capture.dart` 与 `revision_log.dart` 的摘要计算，`revision_maintenance.dart` 的命名版本与清理历史；服务端 `syncsvc` 的 `Push`、`Pull`、`PlanAppend` 与 `pg/sync.go` 的 `Append`、`Reset`，以及 `auth/service.go` 的刷新令牌轮换。核对结果写进了各条的风险栏，仍未核对的写在 [ADR-0054](adr/0054-数据版本位置标记补强.md) 的“实施前要核对的”一节。该讨论同时确认 `deviceId` 与 `installId` 是 ADR-0019 有意的隔离，不合并，所以不进本审查的削减范围。

## 7.1 复审发现、不在本次表层改动范围的问题

复审发现两处同步问题。第一条经核对降为防御性处理，第二条在本批补齐分表摘要时一并修正。

**一、整批重放会让客户端跳过别的设备的提交（S13 风险栏）。** 先更正上一版的判断：`PlanAppend` 只有在整批都是重复提交时才不看 `base`、直接返回当前 `head`；只要有一个新提交而 `base` 落后，就返回 `ErrHeadMoved`，客户端收到 409 后重新拉取，拿不到错误的 head。所以“整批重放跳过别的设备提交”只在一种情形下可能发生：本机这批提交全是重复，而另一台设备恰好在这期间推了东西。这种情形接近不可达，因为提交全是重复说明上一次推送其实成功了，只是响应丢了；而响应丢的时候 `_pushBatches` 的收尾还没跑，`sync.server_head` 仍停在旧值，下一轮 `_pull` 会从旧值开始重新拉。

用三组实验核对过。第一，按原方案写的用例（A 中途推送、B 整批重放）通过，原因是用例里有新提交，走了 409 那条路。第二，把假服务端改成“混合批只追加新提交、回旧 head”，用例仍然通过，说明这个用例对 head 推进不敏感。第三，把客户端改成推送之后完全不写 `sync.server_head`，用例仍然通过，说明下一轮拉取之前这个位置会被别的路径校正。三组改动都已还原，工作区没有留下代码修改。

结论分两层。要真正复现这个问题，需要一个“整批重复 + 别的设备同时推”的用例，并且要在推送成功、写位置之前强行让响应丢失，这一套构造只用于测试，不代表真实时序。按现状，这一条不构成需要开代码的缺陷，从 7.1 里降为一条待观察的备注：如果将来推送响应增加逐条序号（S13 的 V15），顺手让客户端按“响应里最大序号不大于自己带上去的 `base`”判断整批重放、此时不推进服务端位置，作为防御；不估算工作量，也不单独开批次。现在不做改动。

**二、“以本机为准修复”会跳过云端碰过、但值和本机不同的行，却提前清掉不一致标记（`repairFromLocal` 收尾）。** 原因是收尾无条件调 `_saveDigestMismatch(false)`，只要这次推送传了任何内容就认为已经一致，而这一步补传的只有云端没碰过的行，值不同的行不在其中。方案：修复之后再比一次，用比上一次的结果决定标记，而不是按“有没有传内容”决定。有两种落地方式：

- 随 S15 做（首选）：修复之后按表比较一次摘要，只要还有表不一致就把不一致标记保留下来，账号页照常写明哪几张表不同。改动点是 `repairFromLocal` 收尾（约 1080 至 1083 行）的条件，以及账号页读取不一致表名的位置。
- S15 之前先做一版：修复之后整库比一次摘要，不一致就保留标记。说不出哪张表，但至少不会显示成“已一致”。

本批按首选方案实施，修复以只读方式核对云端已有行，补传后按实际变更计算结果。自动化用例覆盖补传后仍有差异，以及补传后两端一致的情形。

### 9.4 复审发现、不在表层的问题

按 ADR-0057 重建服务端库时，账号相关的表全部清空，但对象存储里 `attachments/<账号>/` 下的字节没有任何一步删除。账号删除与清除全部数据会按前缀清理，备份字节有每日对账兜底，而 `backup/reconcile.go` 注明 `attachments/` 由附件自己的账号前缀清理负责，整库重建不经过这条路径。这些字节是用户的图片，重建之后既没有索引行，也没有对应的账号。建议在运维手册的重建步骤里增加一步，按 `attachments/` 前缀清空对象，或者让每日对账同时覆盖附件；在 0.3.0 那次重建之前完成。

另有两项核对之后不改。时间统一存成本地时间的文本、精确到秒，单一时区的产品可以接受；跨设备的排序从不依赖客户端时间，命名版本墓碑的比较用服务端时间，这两点在实施时写进 01 第 1 节 D7。`memory_use` 里“同一秒内连续使用时往后错开一秒”的代码来自按秒存时间，S16 改完之后不再需要。`revision_cursor` 里混放了读取位置与两个同步标志，`sync.restore_align` 用 0 与 -1 表示特殊情况，写法不够清楚，但不会出错，等下次修改同步状态时再拆开。
