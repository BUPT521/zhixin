# 数据库结构过度设计审查

> 审查日期 2026-11-23，范围是客户端 SQLite（`app/lib/data/db/drift/tables.dart`，schema 30，27 张表）与服务端 PostgreSQL（`server/internal/store/schema.sql`，26 张表）。体例沿用 [过度设计审查](过度设计审查.md)：成因分类、证据、建议、风险。已在该文档中列过的条目只引用编号，不重复展开，本文只补“表与列”这一层以前没有单独看过的内容。证据来自 grep 引用统计与读表定义，没有改代码、没有跑测试，行数与列数都是量级。

## 1. 总体判断

结构本身比代码干净：业务表只有 14 张，列名、外键动作、CHECK 约束都有写法统一的来源（`tables.dart` 与 `checkValueSets`），多数列有读写点。问题集中在三处。

第一，客户端 27 张表里有 12 张是版本与同步的元数据（`revision_*` 9 张、`sync_shadow`、`asset_object`、`asset_chunk`），业务表 14 张、设置表 1 张。簿记表的数量接近业务表，其中 `revision_commit` 一张表就有 20 列。

第二，同一个事实存两份，版本控制一侧尤其明显：完整性有 `hash` 链、检查点 `checksum` 与 `state_digest` 三套，其实 `state_digest` 一个就够；检查点的附件清单既在 `revision_checkpoint.asset_hashes_json`，又在 `revision_asset_ref`；`revision_commit` 的两个条数是别的表数得出来的缓存；`study_plan.current_page` 是由已完成事项算出来再写回的缓存；服务端 `sync_head` 与 `sync_snapshot` 都是每账号一行，却分在两张表。

第三，为一个尚未出现的需求预留了表或列：登录方式 `phone`、`wechat`，设备能力字符串，快照让位表，清除标记表。这些与第一份审查的 B 类（预留未用）同源。

成因沿用原分类，表层只出现四类：A 规模错配、B 预留未用、C 兼容残留（仅 V6 一处，是回填工具的附属索引）、E 复制多于抽象（在这里指“同一信息存两处”）。D 与 F 不适用于表结构。另有一类不是削减而是“补强”：对照 git 的 refs 与树哈希之后发现少记了本该记的事实（分表摘要、云端序号、设备已同步到的位置、命名版本随账号同步），来自 [ADR-0053](adr/0053-标识按身份顺序指纹分工并收拢提交标识.md) 与 [ADR-0054](adr/0054-数据版本位置标记补强.md)，在表里的类别栏写“补强”，每条都写明为什么不能由其他列派生。

按已确认的条目落实，客户端表由 27 张降到 25 张（合并 `revision_context` 与 `revision_sequence`，`profile` 并入 `app_meta`），列减少约 10 个，再加上 [ADR-0054](adr/0054-数据版本位置标记补强.md) 的补强列（`server_seq`、`table_digests_json`、`head_commit_id`，见 S13 至 S15），`revision_ref` 的 `commit_uid`、`sync_state` 与删去的 `commit_id`，净减少约 6 列；服务端表由 26 张降到 24 张（合并 `sync_head` 与 `sync_snapshot`，`sync_snapshot_orphan` 并入 `attachment`），索引减少 5 个，ADR-0054 新增 `sync_ref` 一张表（V13）后为 25 张。暂不动的服务端条目（V5、V6、V8、V10、V11）全部落实后，服务端还可再降到约 20 张。其中约一半与第一份审查的 3.6、3.8、5.2、5.9、5.13 重叠，真正新增的是第 3 节和第 4 节的条目。

## 2. 处置原则

沿用第一份审查第 2 节的原则，并补充三条表层特有的：

| 原则 | 说明 |
|---|---|
| 一次改完 | ADR-0001 规定库版本不一致时清空重建，每次改结构都会让已有内测数据作废。表层的改动应合并成一次 schema 版本变化，赶在 0.2.0 发出之前做，之后每改一次都要通知内测者 |
| 与功能审查同批 | 与 3.5、3.6、5.2、5.9、5.13 重叠的条目随各自条目落地，不单独排期；3.8 已决定保留，不再有表层改动 |
| 派生优先于缓存 | 能从其他列用一条查询算出来、且数据量只有几千行的，不存列。要存，须写明读它的位置 |
| 补强列要写明不可派生 | 新增列只用于记录“当时观察到的外部事实”（例如提交落库时已知的云端位置），必须写明不能由本机其他列算出，且允许为空、为空时不影响同步正确性（S13 至 S15、V12 至 V14） |

## 5. 经核实不算过度、应保留

| 表或列 | 保留理由 |
|---|---|
| `llm_instance_usage` | 与 `llm_usage` 的按账号求和不能互相替代：ADR-0036 要求删号后实例日预算不减少，所以实例总量必须独立记录 |
| `sync_commit_seen` | 压缩会删掉旧的 `sync_commit`，永久去重靠它；每行几十字节，不占 256 MiB 预算 |
| `sync_shadow` | 格子级变基的底座，`column_name` 用空字符串代表整行，是为了绕开 SQLite 唯一约束把 `NULL` 当作互不相同 |
| `checkValueSets` 与各列 CHECK | 22 列的取值集合由一处常量派生并有表驱动测试。第一份审查第 10 节已列为保留 |
| `user_active`、`install_active` | ADR-0019 的决定，第一份审查第 5 节末段说明不列入清单 |
| 客户端为外键动作所建的索引（如 `idx_conversation_goal`、`idx_plan_item_conversation`） | 删目标、删资料时 `SET NULL` 与 `CASCADE` 靠它们避免全表扫描；收益虽小，但一旦删掉就在最不想遇到慢的时候（批量清空）遇到 |

## 6. 核实情况与局限

人工读过两份定义文件的全部内容，并核对了这些结论：`last_message_at` 在 `lib` 与 drift 查询里只有一处写入、没有读取；`asset_hashes_json` 与 `revision_asset_ref` 两处各有代码在维护；`hash` 与 `parent_hash` 只被完整性检查与裁剪锚点读取，不进同步协议，也不用于去重；`checksum` 与 `state_digest` 在读取检查点时先后各校验一次；`encoding` 只有一个写入点且恒为 `json+gzip`；`checkpoint.kind` 的四个取值都有写入点。

初稿里有两条在核对后撤回：`origin_json` 承载三个键并被撤销逻辑读取，不是单键 JSON 列（S8）；`revision_ref` 存的是 `HEAD` 加用户命名版本，集合是开放的（S11）。

其余条目来自对列名的 grep 统计，没有逐个读调用点：V3 的 `user_id` 是否被查询直接过滤、V8 的 `note` 是否有人填写，都属估计。S1 的三点前置核对与 S2 的读取侧核对尚未做。服务端那部分我只读了 `schema.sql` 与 grep 到的引用文件名，没有打开 sqlc 查询逐条看。

这次没有评估两个更大的问题：`revision_change` 对更新操作是否存整行前后各一份（`before_json`、`after_json` 都是整行 JSON 的话，存储量约翻倍，但格子级变基也许要求这样），以及 `asset_object`/`asset_chunk` 把图片存进 SQLite 是否值得（数据包与备份因此可以自包含，是有理由的取舍）。这两件事需要实测数据量才能判断。

S13 至 S15 与 V12 至 V14 来自 2026-11-23 对照 git 的讨论，依据是文档与 `server_client.dart` 的方法签名，没有读 `sync_service.dart` 的推送与拉取实现，也没有读服务端 `syncsvc`；各条的前置核对写在条目的风险栏与 [ADR-0054](adr/0054-数据版本位置标记补强.md) 的“实施前要核对的”一节。该讨论同时确认 `deviceId` 与 `installId` 是 ADR-0019 有意的隔离，不合并，所以不进本审查的削减范围。

## 7. 已确认与待确认

已确认：

- 客户端：S1（版本控制统一用 `state_digest`，删四列，完整性检查改为重放比对）、S2、S3、S4（截止小时并进 `app_meta`，改动不再可撤销）、S5、S6、S9（重试去重改用 `uid`，同步契约一并修改）、S10（删 `checksum` 与 `encoding`）。S7、S8、S11 保留不动，S8、S11 是核对后撤回。冲突表与 `keepLocal` 保留（第一份审查 3.8 已决定保留）。
- 服务端：表层改动与客户端一起在 0.2.0 发出之前做完，范围是 V1、V2、V3、V4、V7、V9（`capabilities` 改布尔列）与 S9 的服务端部分。V5、V6、V8、V10、V11 暂不动，分别等 5.2、5.7、管理页核对、5.9、5.13 有结论。
- 记忆表的变化并入 ADR-0051，与本审查的表层改动合成同一次 schema 版本变化。
- 标识与位置标记（提议中的 [ADR-0053](adr/0053-标识按身份顺序指纹分工并收拢提交标识.md) 与 [ADR-0054](adr/0054-数据版本位置标记补强.md)，已按用户意见全部采纳）：客户端 S9 的范围扩大为“提交身份只用 `uid`”，同步契约里的 `request_id` 字段改名为 `uid`，基线提交的 `uid` 改用 UUIDv5，整数提交编号保留为本机私有顺序、不出设备，`deviceId` 与 `installId` 不合并；新增 S13、S14、S15 三项补强；服务端新增 V12、V13、V14，其中 V12 与 V9 同表同批。

实施前的前置核对（不通过时的退路写在各条里）：S1 的三点（数据包与备份是否带那几列、`change_count` 聚合后的查询耗时、已裁剪库上重放比对的起点）；S2 的三个文件读取侧能否改从 `revision_asset_ref` 取；S10 的测试里有无 `json` 编码的检查点；S13 至 S15 与 V12 至 V14 的前置核对写在各条风险栏与 [ADR-0054](adr/0054-数据版本位置标记补强.md) 的“实施前要核对的”一节。

待确认：无。ADR-0054 里原先留着的四个点已经定下：`HEAD` 与命名版本两列都存 uid，不依赖 `HEAD` 恒等于最大提交编号（S14）；服务端不为命名版本保留被压缩的历史，名字只剩标签（V13）；命名版本的同步用 `sync_state` 加后写覆盖，不做操作队列（S14、V13）；活跃窗口以配置 `ZHIXIN_SYNC_DEVICE_ACTIVE` 的 720 小时为准，ADR-0048 的“54 天”实施时更正（V12）。
