# 计量与计费审查

- 日期：2026-11-25
- 范围：main（1502e56）的服务端 `internal/llmproxy`、`internal/nowpay`、`internal/store/pg` 的额度与核销路径，客户端的额度展示、购买面板与上下文估算；对照 ADR-0066、0067、0068。
- 性质：只读审查，代码未改动。

## 1. 现状

一次聊天请求按“预留、转发、结算、核销”四步走。

预留在 `llmproxy.(*Proxy).budget` 与 `pg.(*Store).Reserve` 里完成。估算量是 `Usage{Input: len(body), Output: max_output_tokens}.reserve`，即请求体的字节数当作未命中缓存的输入、输出上限乘 4。`Reserve` 在当天的 advisory lock 里把估算量截到“账号免费额度剩余”与“实例预算剩余”两者的较小值，截断后不足估算量时 `budget` 立即退回预留并回 429 `quota_exceeded`。

结算时，上游报告了 usage 就用 `Usage.Billed` 折算：未命中输入记 1、命中输入记 1/50、输出记 4，按五十分之一累加再四舍五入；没有报告时（`unknown`）按预留量结算。账号账本 `llm_usage.tokens`、实例账本 `llm_instance_usage` 用同一个计费量，路由统计 `llm_route_usage` 记原始 token。

核销在结算提交之后。`chargeNowPay` 读当天账号已用量减去免费额度，交给 `Meter.Record` 按 `ZHIXIN_TOKENS_PER_POINT` 向上取整，再减当天已申请（非 failed）的积分，只写差额流水，由进程内唯一的协程调 `quota.verify`。下一轮 `Reserve` 前调 `Resume` 补查未终结的流水。

客户端把 `used_tokens` 与 `daily_tokens` 按 `tokens_per_point` 折成积分显示，购买面板显示即刻收余额与三档换算。

权重本身是对的：DeepSeek 当前价目（deepseek-flash，空闲时段每百万 token 命中 0.02 元、未命中 1 元、输出 4 元）的比例正好是 1/50 : 1 : 4。

## 2. 必须先修的问题

### 2.1 买到的积分用不上

`pg.(*Store).Reserve`（quota.go 第 58–61 行）只按免费额度剩余截断，没有任何一处读即刻收余额。免费额度用完之后 `reserved <= 0`，请求直接 429，积分永远没有机会被消费。e0c093f 删除本地钱包时一并删掉了 `free + paid.balance` 这一分支，即刻收余额却没有接进来；a4f0418 起就是如此。

现在唯一会产生核销的情况，是当天最后一次请求的实际用量超过了预留量，`used` 越过 `limit` 的那一小段。用户付了钱，看到的仍是“今日额度已经用完，等次日恢复”。

这与 00 第 6 节第 5 条“积分在免费聊天额度用完之后使用”、购买面板的“每轮结束先扣当天免费额度，再扣积分”“已有积分仍可使用”都相反。试用期 12 月 21 日开始，这一条不修，收款功能等于没上线。

建议：`Reserve` 对聊天在免费额度之外再加一段“可用积分折算的 token”。余额来源不能在请求路径上同步调即刻收，建议本地维护一个影子余额：

1. 新表或 `nowpay_balance(user_id, remaining_points, synced_at)`，在购买面板刷新余额、`Overview`、每次 `verify` 成功（响应里已有 `Consume.Remaining`，现在丢弃了）时写入。
2. `Reserve` 的上限改为 `limit + max(0, remaining_points − 当天未终结流水的积分) × perPoint`，并与现有 advisory lock 同在一个事务里读。
3. 影子余额过期（例如超过 10 分钟没同步）且免费额度已用完时，可以异步触发一次 `quota.query`，本次按旧值放行或拒绝都行，误差最多一轮。
4. `Insufficient` 时把影子余额置 0，而不是只把流水记 failed。

### 2.2 预留估算偏大一个数量级，免费额度用不满

估算把请求体字节当 token。知新的上下文以中文为主，Dart 的 `jsonEncode` 不转义非 ASCII，一个汉字 3 字节，DeepSeek 一个汉字约 0.6–1 个 token；再按“全部未命中”算，估算相对实际计费量大约是 10 倍以上。

客户端默认 `defaultContextWindowTokens = 65536`，输出上限取四分之一即 16,384，乘 4 就是 65,536 个计费 token 的输出预留；输入预算约 4.9 万 token，中文约 14 万字节。一次满上下文请求的预留约 21 万，免费额度 32 万，账号用到约 11 万（三分之一）之后，满上下文的追问就会被判 `quota_exceeded`。实际同一请求在八成缓存命中、输出 1,500 token 时只计约 1.6 万。

图片更极端：`llm_protocol.dart` 以 base64 内联图片，一张 500 KB 的照片编码后约 67 万字节，单张就超过整天免费额度，带图请求永远被拒。deepseek-flash 支持图像理解，这条路径在生产上是死的。

`budget` 在 `reserved < estimate` 时整单拒绝，而 `Quota.Reserve` 的接口注释写的是“剩余不足 want 时按剩余量预留，调用方照常转发”，两处口径相反。

建议：

1. 服务端估算改成与客户端 `estimateLlmTextTokens` 同一口径：遍历请求里的文本字段，非 ASCII 每字符 1、ASCII 每 3 字符 1；`input_image` 每张按固定值（客户端用 2048）计，不按 base64 长度。两端的估算函数在注释里互相指认。
2. 输出预留不按 `max_output_tokens` 全额乘 4，改用“上限与经验值（例如 4,096）取小”乘 4，结算多退少补；或者干脆在剩余额度不足估算时按剩余量放行（恢复接口注释的语义），最后一轮的超额由结算补记，最多超一轮。
3. `defaultContextWindowTokens`（65536）大于 `maxContextWindowTokens`（32768），后者没有在任何地方生效，命名也让人以为上下文不能超过 32K；二选一后统一。

### 2.3 失败的尝试按预留全额扣

`dispatch` 里连接失败、5xx、首字超时、响应类型不对、首字前中断，都以 `attemptResult{unknown: true}` 结束（proxy.go 第 846、862、880 行等），`budget` 对 `unknown` 按预留量结算。结合 2.2 的估算，一次上游 502 可以扣掉二十多万计费 token；同一轮切换三个来源就扣三次。这些失败大多根本没有产生上游费用，例如 `sourceConnectionError` 连接都没建立。修好 2.1 之后，这部分会直接变成积分核销，且核销不可撤销。

建议按“是否可能产生上游计费”分三档：

1. 确定没有发出或上游明确拒绝（连接失败、DNS、TLS、4xx、429、首字之前的 5xx）：记 0。
2. 已经开始输出但没拿到 usage（客户端中途取消、流被截断、本轮预算用完）：按已转发的输出文本用同一估算函数计输出，输入按估算的输入计，不用预留量。`copyStream` 已经逐条解析事件，顺手累计 `response.output_text.delta` 的字符数即可。
3. 只有上游返回 2xx 却缺 usage 的整段响应，才退回预留量，并在后台统计里单独计数，便于发现不报 usage 的来源。

路由统计里 `EstimatedTokens` 现在把 `unknown` 的预留量也算进去，后台会看到夸大的估算量，同步改成上面的口径。

### 2.4 付费用量挤占实例预算

实例日预算 `ZHIXIN_LLM_INSTANCE_DAILY_TOKENS` 默认 3,200 万计费 token，按渠道价约 6.4 元，本意是给免费额度兜底。2.1 修好之后付费用量也会记进同一本账；一百个免费账号用满当天额度就把实例预算占完，之后付了钱的用户也收到 `quota_exceeded`。

建议实例账本只累计“免费额度内”的部分，超出免费额度、由积分承担的那部分不受实例预算约束（它已经有收入覆盖），或者单设一个更高的付费实例上限作为熔断。嵌入的原始 token 也记在同一本实例账本里，嵌入单价与聊天差很多，建议分 kind 记。

## 3. 核销与对账

3.1 结算读到的 `used` 含其他在途请求的预留。`chargeNowPay` 在一轮结算后读当天 `llm_usage.tokens`，这个数包含同一账号并发请求（前台回答加后台预读、记忆整理、接入密钥调用）尚未结算的预留量。现在因为 2.1 的截断，影响只在越线那一刻；2.1 修好之后，一个在途的 21 万预留就会被当成已用量折成积分申请，等它结算回落时积分已经扣走、无法撤销。建议 `llm_usage` 拆出 `reserved_tokens` 列（预留时加、结算时减，`tokens` 只记已结算量），核销只看已结算量；额度判定仍看两者之和。

3.2 余额不足的流水会反复重试。`Insufficient` 记 failed 之后不计入已申请量，下一次结算按当天累计重算，又申请同样多的积分再失败，每轮都多一行流水和一次即刻收调用。配合 2.1 的影子余额：余额为 0 时不再发起核销，也不再放行超出免费额度的请求。

3.3 长期不用的账号不会补查。`Resume` 只在该账号下一次聊天 `Reserve` 时触发，ADR-0067 已经记下。建议在每日清理任务里加一次全局补查：`status IN ('pending','processing') AND created_at < now() - interval '5 minutes'`，分批排进队列。顺带给 `nowpay_charge` 与 `nowpay_purchase` 加 ADR-0067 提到的按时间清理（succeeded/failed 保留 180 天之类）。

3.4 队列是进程内的。重启时队列里的 job 丢失，靠 3.3 的全局补查兜底即可，不必引入外部队列。

3.5 `ZHIXIN_TOKENS_PER_POINT` 的代码默认值是 1000，ADR-0068 要求部署值 10000。漏配就是十倍多扣，而且核销不可撤销。建议默认值改成 10000，或者配置了 `ZHIXIN_NOWPAY_PRODUCT_ID` 时要求显式设置这一项、缺失即启动失败。`QuotaStatus` 与 `nowpay.NewHandler` 里各有一个 `1000` 的兜底，也一并去掉，以配置校验为唯一来源。

3.6 删号会丢掉积分。即刻收的 `external_buyer_id` 是 `user_id`，删号之后余额留在支付宝一侧、无人可用。删号确认页应在有余额时提示“剩余 N 积分将无法使用”，ADR-0067 的“账号删除”一段补上这一点。

3.7 当天中途改 `llm_quota` 覆盖值，`chargeableTokens` 会按新上限重算，调低额度会让已经用过的免费部分变成待核销积分。管理员改额度属于少见操作，在 README 的额度调整说明里写明“当天生效，影响当天核销”即可。

## 4. 计价口径与设计

4.1 高峰时段不是假设。DeepSeek 价目页写明工作日 9:00–12:00、14:00–18:00 为高峰，单价是空闲时段的两倍。ADR-0068 把“官方高峰时段价格翻倍”写成未来风险，实际上它现在就在发生；按 0.4 元/百万计费 token 的高峰成本，三档毛利率是 33%、29%、25%，免费额度的成本也翻倍。建议先在 `llm_route_usage` 增加按小时或“高峰/空闲”的切分，看一周真实分布再决定：维持单一权重（接受混合毛利），或在 `Usage.Billed` 里乘时段系数。无论哪种，ADR-0068 的“代价与边界”一节应改写成现状。

4.2 权重写死在常量里，路由却是多来源的。ADR-0059、0062 允许同一个对外模型切到不同来源；deepseek-v4-pro 的比例是命中 1/30、输出 3，其他厂商又不同。更稳的设计是把单价挂在路由上（后台为每条路由填三个单价，单位“元/百万”），结算时算出“成本微元”，额度与积分都以成本为单位，`tokens_per_point` 换成“每积分的成本微元”。这样换来源、换模型、调价都只改后台，不改代码与 ADR。现阶段只有 flash 一条路由，可以先在路由配置里加单价字段但沿用当前权重，作为过渡。

4.3 后台看不到计费量。ADR-0066 已记下“用量统计”页只有原始 token。积分开卖之后，对账需要的是计费量、核销积分与即刻收余额三者对得上；建议 `llm_route_usage` 加 `billed_tokens` 列，后台再加一页按日的“免费部分 / 积分部分 / 已核销积分 / 未终结流水”汇总。

4.4 `used_tokens` 含在途预留。账号页刷新时如果有后台请求在途，显示的已用量会突然跳高再回落。3.1 拆出预留列之后，`GET /v1/llm/quota` 返回已结算量，另给一个 `reserved_tokens` 字段，客户端可不显示。

4.5 `MemoryQuota.Split` 只读 `keyID == ""` 的那一行，`split` 也只存最后一次结算，测试与 pg 口径不一致。只在测试里用，改成按天累加、按账号合计即可。

## 5. 客户端

5.1 额度用完的提示没有购买入口。`quota_exceeded` 映射到 `LlmFailure.rateLimited`，提示“今日额度已经用完，等次日恢复之后再点「重试这次回答」”（answer_notice.dart 第 109 行），`server_client.dart` 里还是“联系管理员调整”，服务端 detail 还写着“use your own key”，而客户端已经没有自填 key。修好 2.1 之后应区分三种情况：免费额度用完且没有积分（给“购买积分”入口）、积分不足（同上）、实例预算用完（只说稍后再试）。服务端在 problem 的扩展字段里给出 `reason: account | points | instance`，客户端按它分支；枚举名也建议从 `rateLimited` 改成 `quotaExhausted`，与上游限流的 `busy` 区分。

5.2 嵌入额度也按积分显示。`_embeddingQuotaText` 把嵌入的原始 token 按聊天的 `tokens_per_point` 折成积分，但嵌入不按计费权重、也不能用积分支付，显示“嵌入今日已用 x / 200 积分”会让人以为积分能买嵌入。建议嵌入保持百分比或“已用 / 每日上限”的相对显示，不用积分单位。

5.3 账号页只显示“今日已用 / 每日免费”，看不到“今天已从积分扣了多少”。2.1 修好之后，建议 `GET /v1/llm/quota` 增加当天已核销积分与影子余额，账号页一行写清“免费额度用完后，今天已用积分 N 分，剩余 M 分”。

5.4 客户端估算与服务端估算各写一套，且口径不同（见 2.2）。统一后，客户端可以在发请求前用同一函数判断“这一轮大概会不会超过剩余额度”，提前提示而不是等 429。

## 6. 建议的顺序

试用期前（12 月 21 日之前）必须完成 2.1、2.2、2.3、3.1、3.5、5.1：这六条决定付费用户能不能用、会不会被多扣。2.4、3.2、3.3、3.6 紧随其后，在第一笔真实收款之前做完。4.1 先加统计、看数据；4.2、4.3 作为后续 ADR 的议题，不阻塞上线。

每条落地时需要改 ADR-0066/0067/0068 的相应段落：2.1 涉及 0067 的“决定”，2.2、2.3 涉及 0066 的预留与结算口径，4.1 涉及 0068 的“代价与边界”。

## 8. 汇率与毛利率（2026-11-27）

合入 [ADR-0084](adr/0084-聊天与嵌入共用积分.md) 之后，聊天与嵌入共用一份每日免费额度，嵌入按原始 token 折算成计费 token。本节按 7.1 的汇率重算三档与嵌入的毛利率，判断现行售价能否覆盖成本。仓库里最近一次记录汇率的是 `83dfa19`，当时按每百万 0.15 美元、1 美元折 7.1 元估算；现行文档改用 DeepSeek 直接公布的人民币价每百万 1 元，相当于 6.7 的汇率，两种口径并列在下面。

聊天按计费 token 计费，售价由档位决定：萤火 6 元 1,000 分折每百万 0.6000 元，灯火 18 元 3,200 分折 0.5625 元，星河 48 元 9,000 分折 0.5333 元。成本取渠道价，即官方谷价的 2 折；按 7.1 的汇率，官方谷价每百万 1.065 元，渠道成本 0.213 元，高峰时段翻倍为 0.426 元；按人民币价每百万 1 元算，渠道成本 0.200 元，高峰 0.400 元。渠道对输入未命中、输入命中与输出按同一折扣计价时，每百万计费 token 的成本是常数，毛利率与缓存命中率无关。

| 口径 | 每百万成本 | 萤火 | 灯火 | 星河 |
|---|---|---|---|---|
| 7.1 汇率，谷价 | 0.213 元 | 64.5% | 62.1% | 60.1% |
| 7.1 汇率，高峰 | 0.426 元 | 29.0% | 24.3% | 20.1% |
| 人民币价，谷价 | 0.200 元 | 66.7% | 64.4% | 62.5% |
| 人民币价，高峰 | 0.400 元 | 33.3% | 28.9% | 25.0% |
| 7.1 汇率，无渠道折扣 | 1.065 元 | -77.5% | -89.3% | -99.7% |

汇率每升 0.1，每百万成本增加 0.003 元，三档毛利率各降约 0.5 个百分点，影响小于高峰时段翻倍。7.1 与人民币价两种口径相差约 2 个百分点，不改变结论；没有渠道折扣时三档全部亏损，渠道是这套定价成立的前提。

嵌入按原始 token 折算，百炼 `text-embedding-v4` 的实时输入价是每百万 0.50 元，仓库里没有渠道折扣的记录。聊天的渠道成本是每百万计费 token 0.20 元，两者相差 2.5 倍，所以 ADR-0084 每千个原始 token 记 2,500 个计费 token；按萤火档售价，每百万原始 token 收入 1.50 元、成本 0.50 元，毛利率 66.7%，与聊天按人民币价计算的毛利相同，三档都是 66.7%、64.4% 与 62.5%，嵌入的成本以人民币计价，不受汇率影响。一份 6 元的萤火全部用于嵌入时，1,000 分折 400 万原始 token，成本 2 元。折算比例与毛利率的关系如下，按萤火档售价计算。

| 折算比例 | 每百万原始 token 收入 | 成本 | 毛利率 |
|---|---|---|---|
| 20%（按两百万免费原始 token 反推） | 0.120 元 | 0.500 元 | -316.7% |
| 83.3%（盈亏平衡） | 0.500 元 | 0.500 元 | 0 |
| 100%（一比一） | 0.600 元 | 0.500 元 | 16.7% |
| 250%（按成本对齐，现行） | 1.500 元 | 0.500 元 | 66.7% |

原先把比例定在 20% 是为了让只做嵌入的账号在免费额度内还能用约 200 万原始 token，这个数字本身没有成本依据，按每百万 0.50 元算，20% 下每百万原始 token 要亏 0.38 元。按成本对齐之后，盈亏平衡不再是一个需要单独讨论的比例，剩下的不确定项是渠道对百炼的折扣：如果渠道对嵌入也按 2 折计价，成本降到每百万 0.10 元，250% 会把毛利率抬到 93.3%，比例要相应改成 500；确认之前按实时价计算。

免费额度与实例预算的成本不再随两类用量变化。共享额度默认每天 40 积分，全部用于聊天时是 0.08 元/天（7.1 汇率 0.085 元），全部用于嵌入时按人民币价也是 0.08 元/天、折约 16 万原始 token；实例的日预算 3200 万计费 token 对应 6.4 元，两类请求相同。

聊天三档在 7.1 的汇率下仍有六成左右的毛利，高峰时段降到两到三成，毛利的主要来源是渠道折扣，汇率每变化 0.1 只影响约 0.5 个百分点。嵌入按成本折算之后三档毛利与聊天相同，免费额度与实例预算也不再随用量结构漂移。剩下的风险是渠道对百炼的折扣与嵌入输入价的调整，确认之后按新的单价重算默认比例。

折算比例已按成本定为 2500，即 `ZHIXIN_LLM_EMBEDDING_BILLING_PERMILLE` 的默认值；计费单位仍按 4.2 的路由单价方案统一，那一步不急。
