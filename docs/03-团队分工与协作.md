# 知新 · 团队分工与协作

> 本文是人力与交付节奏的唯一真相，适用于 4 人团队内部。每人每周投入 8 小时，合计 32 小时，课业优先。产品定义见 [00](00-产品定义.md)，页面与验收见 [02](02-产品与交互.md)，数据结构见 [01](01-ER数据模型.md)。

---

## 1. 协作原则

1. 能完整使用比规范齐全更重要。先做出一个能安装、能操作、能演示的 APK，再回头补文档和测试；没有遇到实际困难，就不增加会议、签字和模板。
2. 分工按块划分，交付按里程碑推进。谁负责的块由谁来改，跨块改动先打招呼；不要求 CODEOWNERS、评审矩阵和一票否决。
3. 不为了“看起来专业”而加班，进度落后就砍范围，不加时间。

## 2. 角色

| 角色 | 成员 | 负责 | 不碰 |
|---|---|---|---|
| 负责人 / 主开发 | 陈思源 | 架构、服务端与同步、数据包格式与数据版本、检索与 AI 运行时、发版与内测分发，并协助吴闻杰开发应用 | 界面细节（除非阻塞里程碑） |
| 开发 | 吴闻杰 | 全部页面与交互、状态与空态、回执与撤销入口、设计系统与组件口径、外观与可访问性、设置与数据服务层（设置读写、模型配置与 API Key 的安全存取、导出与恢复、本机诊断）、表结构、仓储查询、应用服务与判定规则、每周界面走查 | 服务端、AI 对话协议 |
| 测试与验收 | 缪鹏 | 自动化测试（`app/test/` 与 `server/` 的测试）、测试用例与测试数据、手工验收、模拟器上的 V1–V11 验收、缺陷记录、AI 输出抽检、试用执行与反馈整理、对外材料定稿 | 业务代码 |
| Prompt 与插件 | 陈英硕 | 提示词与工具说明的调优、评测样例、插件运行时与插件（见 [ADR-0010](adr/0010-客户端插件的两种形态与权限.md)）、试用反馈整理、材料初稿 | 表结构与数据包格式、服务端；Dart 代码限于插件、提示词、工具说明与对应的评测 |

界面的范围不止页面本身。吴闻杰同时承担交互口径、设计系统与设置和数据服务：页面与流程按 [02](02-产品与交互.md) 第 2–5 章的现行口径实现，状态与空态、就地失败提示与回执入口在同一处维护，界面口径随实现写回 02；设计系统把色值、字号、留白与动效收在 `app/lib/ui/theme.dart` 一份定义里，页面从 `context.zhixin` 读取；外观包括深浅色、放大文字与读屏标签；设置与数据服务层包括设置与每日截止小时的读写、模型配置与 API Key 的安全存取、嵌入配置、导出包的打包与校验、恢复的预检与执行、本机诊断记录，表结构由吴闻杰按 [01](01-ER数据模型.md) 修改并同步文档，数据包格式与 AI 对话协议仍由陈思源维护。目前界面有 16 个页面与 50 个界面文件、约 1.7 万行代码，设置与数据服务另有 16 个文件、约 2200 行，数据层是 37 个文件、约 1.1 万行；吴闻杰接手表结构与应用服务之后工作量最大，陈思源在服务端之外的时间优先用于协助他。

发版与内测分发由陈思源负责，他排期紧时对外包要等他的时间；验收在 Android 模拟器上执行，物理设备只补模拟器覆盖不到的项目，模拟器上的性能、相机与语音数据不具代表性，这两点在本文第 3 节与 [02 第 8 章](02-产品与交互.md#8-验收标准)写明。吴闻杰在界面之外承担设置与数据服务层，包括设置读写、模型配置与 API Key 的安全存取、导出恢复与本机诊断；这一层与界面交替推进，11 月先接管日常修改，12 月起随验收修缺陷。

AI agent 按同一张表认领角色，角色与成员一一对应。任务里没写角色时先问，不要猜；确定之后记在本机的 `.agent-role`（不入库），下次开工先读它。一个 agent 可以同时担多个角色，接口、联调这类衔接性的工作不限定由谁来做。

### 2.1 模块主责

陈思源负责服务端并协助吴闻杰开发应用，数据层、判定规则与 AI 运行时由两人分担。划分的依据是同步：数据包格式、数据版本与检索直接决定备份与增量同步能否成立，由陈思源负责；表结构、仓储查询、应用服务与判定规则面向页面功能，由吴闻杰负责，他改这些代码时不必等待陈思源排期，表结构的改动由陈思源评审，因为主键与字段的变化会影响同步协议。测试与验收统一由缪鹏负责：新功能与缺陷的自动化测试由他编写和维护，开发者提交前仍执行 [CONTRIBUTING](../CONTRIBUTING.md) 第 7 节的检查，改动使已有测试失败时，先与缪鹏确认是测试过时还是代码有误。主责人负责改动，评审人在合入前看一遍；表里没有列出的文件，按所在目录归到最接近的一行。

| 模块 | 位置 | 主责 | 评审或协助 |
|---|---|---|---|

## 3. 交付节奏

对外的“前期 / 中期 / 后期”沿用既有叫法，内部的 P1、P2、P3 指同一段时间。

排期按 AI 辅助开发的节奏安排，全部工作在 2027 年 3 月底之前完成，结题材料在 3 月下半月准备。阶段编号 M0–M5 供 [04](04-长期路线图.md#3-阶段内容) 引用，各阶段每个人的工作写在 04。期末与春节两段只修缺陷，开发量集中在 M1 与 M3。

| 阶段 | 时间 | 目标 | 交付 |
|---|---|---|---|
| M0（P1） | 2026.11.16–11.29 | 收口与地基 | 在途改动合入 `main`；数据保留规则与主键方案写成 ADR 并实现；提示词独立成文件；V1–V11 用例与测试数据就绪 |
| M1（P2） | 2026.11.30–12.20 | 验收与内测包 | V1–V11 模拟器验收与真实模型走查；服务端整库备份与模型代理部署到测试服务器；12.21 发出 0.2.0 内测包 |
| M2（P2） | 2026.12.21–2027.01.17 | 第一轮内测与期末 | 第一轮内测两周（12.21–01.03）；期末只修阻断级缺陷，必要时发 0.2.x |
| M3（P2） | 2027.01.18–02.05 | 账号、备份与第一批插件 | 登录、云备份、“知新服务”模型来源、首次使用引导、课表导入与人格插件；02.05 发出 0.3.0，第二轮内测扩到 30 人 |
| M4（P2） | 2027.02.06–02.28 | 春节与公测准备 | 02.06–02.14 春节不排开发；02.24 功能冻结；02.28 前发出 1.0.0 公测包并完成正式服务器的备份演练 |

2026 年 10–11 月已经完成数据层、课表、数据版本与导出恢复、搭子对话与本地兜底、题目与尝试、学习中、任务与日程、语音输入与主要页面。访谈、问卷与原型测试本轮不做，改用内测反馈；兼容测试以模拟器为准，物理设备只保留 PLK110 一台用于补测，不再另借第二台；结题材料里说明这些取舍。

发版与内测分发由陈思源负责，0.2.0、0.3.0 与 1.0.0 的安装说明随包发出。验收由缪鹏执行，每个阶段在模拟器上按 [02 第 8 章](02-产品与交互.md#8-验收标准)走 V1–V11，物理设备只补模拟器覆盖不到的项目；验收记录里的界面与服务层问题由吴闻杰复现和修改。公测期间按反馈完成一次界面迭代，3 月下半月由吴闻杰整理答辩用的界面截图与演示录屏。

验收按 [02 第 8 章](02-产品与交互.md#8-验收标准)的 V1–V11 执行，先验证独立问题、多目标与跨次继续，再推进材料、系统学习与规划。每月验收只看两件事，即能安装、核心流程能完整走一遍；不额外要求覆盖率、SUS 这类指标。

### 版本号

应用在 1.0.0 之前按 0.x 记，开发与内测阶段都停在 0.x，2027.03 的公测包才记 1.0.0。仓库在 2026 年 11 月按全新历史重建，第一版记 `0.1.0+1`，此前的版本号与标签不再使用。版本号只写在 `app/pubspec.yaml` 的 `version` 一行，设置页的“关于”与发版流水线都从这一行读取，界面、文档与 CI 不另存版本常量。日常提交不改版本号，只有对外发出正式包时才改，否则四个人的发版改动会集中在同一行版本号上，合并时互相冲突；CI 每次推送构建的开发包不参与版本递增，也不打标签。

| 位 | 什么时候加 1 |
|---|---|
| 主版本 | 0 表示开发与内测；1.0.0 留给 2027.03 的公测，之后进入下一个对外阶段或者数据结构与数据包格式不兼容时再加 |
| 次版本 | 一次对外交付，或者一批对外可见的新功能：0.1.0 是 2026.11 的可用版，0.2.0 是 2026.12 的内测包，0.3.0 是 2027.02 上旬的第二轮内测包 |
| 修订号 | 只修缺陷、不改功能范围与数据口径时重发同一次交付，例如 0.2.1 |
| 构建号 | 每构建一个能安装的正式包加 1，只增不减，也不随版本名归零，因为 Android 的 `versionCode` 由构建号决定，低于已安装包时覆盖安装失败 |

版本名给正式包用，开发包在版本名后加 `-dev`，并且按另一个应用安装：开发包的 `applicationId` 是 `com.zhixin.app.dev`，桌面名称是“知新·开发”，设置页“关于”显示 `0.1.0-dev+1`，因此开发包与正式包可以同时安装，数据互不影响。开发包由每次 push 与 `flutter run` 构建，不打标签，也不改 `pubspec.yaml` 里的版本号与构建号；验收、联调与缺陷复现都用开发包，缺陷记录写 `0.1.0-dev` 这样的版本名，正式包只用于对外分发。

正式包从 Actions 手动触发，使用仓库 Secrets 里的签名配置，下载的 `app-release.apk` 在分发前改名为 `zhixin-0.1.0.apk`。第一版在设定版本号的这次提交上打 `v0.1.0` 标签；之后每个对外包在发版提交上打与版本名相同的标签，例如 `v0.2.0`，一个版本名只打一次，需要再发包时先升修订号，不移动已有标签。缺陷记录、验收记录与内测说明引用版本名，提交正文需要说明版本时也写 `0.1.0`，不写构建号。

版本名、验收项与数据版本是三套编号，彼此不互相代替：V1–V11 是 [02 第 8 章](02-产品与交互.md#8-验收标准)的场景编号，数据结构版本（见 [01](01-ER数据模型.md) 开头）与数据提交序列属于本地数据。版本号由陈思源在发版时修改并提交，其他人不改；发版提交的标题写 `chore: 发版 0.2.0`，正文写这一版改了什么，构建号与 SHA-256 由 CI 摘要列出，不另记。改完先按 [提交约定](../CONTRIBUTING.md) 第 7 节执行三条检查，再手动触发 Actions 的发版任务。

0.x 阶段允许破坏性变更，不因为数据结构或数据包格式不兼容单独升主版本；这类变更随下一次对外交付升次版本，发版说明写明需要重新导入或数据会清空。1.0.0 之后按上表，在数据结构或数据包格式不兼容时升主版本。开发阶段的兼容边界见 [ADR-0001](adr/0001-开发阶段不向下兼容.md)。

仓库按全新历史重建，只保留一个初始提交，版本从 `0.1.0` 起算；1.0.0 留给 2027.03 的公测，构建号从 1 记。

## 4. 成功标准

个人工具的成功标准与商业产品不同，不追日活与排名；项目层面守住试用规模与留存，产品层面看记忆、帮助、行动与撤销有没有真正接上。

| # | 标准 | 判定方式 |
|---|---|---|
| S1 | 两周后你还在用 | 唯一的生死线 |
| S2 | 一次记录稳定在 30 秒内 | 自测计时 |
| S3 | 记录改变了下一次安排 | 对比同一题目或同一事项；仅因过了一天导致排序变化不算 |
| S4 | 累计试用不少于 30 人，一周留存 ≥ 40% | 内测数据 |
| S5 | 公测 100 人，四周留存 ≥ 40% | 公测数据 |
| S6 | 至少一人能说出自己卡在哪类题上，并能翻回具体的题 | 试用反馈与回访 |

内测版另守两条硬性指标，即核心流程无阻断、崩溃率低于 1%。

出现下列情形，说明方向出了偏差：用户每次打开都要重新说明同一道题，说明记忆没有起作用；回答对不上当前题目与上次尝试，说明上下文没有读到；用户不敢让 AI 改日程，或者改了之后找不到撤销，说明写入机制不可信；记录之外还要维护分类、标签与知识树，说明概念又长回来了；模型不可用时产品完全不能用，说明本地兜底没有做；功能越加越多而每天只用其中两个，说明该砍功能了。

## 5. 风险

| 风险 | 后果 | 处置 |
|---|---|---|
| 范围太大，做不完 | 里程碑落到空处 | 按序砍：材料导入 → 记忆检索精度 → 日程精细度 → 语音输入；保住“记忆、帮助、下一步、撤销”四件事接上 |
| 连续两周超时 | 节奏被打乱 | 砍范围，不加时；课业优先 |
| 模型输出不稳定 | 讲解错误、提示不对，用户不再信任 | Schema 校验 + 重试 + 降级手录；核心功能不依赖 AI |
| 用户不愿配置 key | 首次使用就流失 | 引导提示、连接测试、失败分类、离线可用；登录后可用服务端模型代理，按账号限额（[ADR-0008](adr/0008-取消单机边界引入账号同步与模型代理.md)） |
| 学习数据进入服务端 | 服务器泄露或误删会影响全部登录用户 | TLS 与静态加密、令牌可立即作废、日志不记正文、可删除云端数据；服务器权限由陈思源负责，第二位管理员待定（见 [04 第 5 节](04-长期路线图.md#5-待定决定) D7） |
| 内测开始之后表结构仍会变化 | 内测与公测用户的真实记录在升级时被清空 | 主键改造在 0.2.0 之前完成，之后冻结表结构，规则见 [04 第 5 节](04-长期路线图.md#5-待定决定) D1 |
| 插件或人格设定带偏回答、越权写入 | 判分、引用与撤销规则失效 | 插件只产出草稿，由应用服务写入并形成提交；人格只影响语气与风格，合入前通过评测，见 [ADR-0010](adr/0010-客户端插件的两种形态与权限.md) |
| 期末与春节压缩可用时间 | M2、M4 的产出不足 | 这两段只修缺陷，开发量集中在 M1 与 M3；落后时按 [04 第 6 节](04-长期路线图.md#6-进度落后时的取舍)砍范围 |
| 新增范围挤占验收 | 公测时核心流程仍有阻断缺陷 | 每个阶段先清零阻断级缺陷，再做新功能 |
| 记忆带偏 | 建议像“胡说”，用户反感 | 记忆带来源与有效期，可查看、纠正、删除；推断标明身份 |
| UI / 交互经验不足 | 界面粗糙，用户不会用 | 用开源组件与设计模板；每周一次界面走查（模拟器或真机）；吴闻杰主责 |
| 没有物理设备，验收只能在模拟器上做 | 相机、语音、安装与性能没有实测数据 | 这几项在 PLK110 上补做，没有设备就记待验收，结题材料写明样本边界 |
| 排程太满或时间估不准 | 建议不可执行 | 不排课表与睡眠；不做自动重排；用户或搭子要求时只改未开始的 AI 块，并留回执与撤销 |
| 试用用户招不满 | 30 / 100 人目标落空 | 依托班级与社团分两批招；先内测 30 人，再公测 100 人；报告里写清样本边界 |
| 只有作者会用 | 数据与反馈都不足 | 先自己用，再靠内测与公测扩到 30 / 100 人；报告里写清样本边界 |
| 用户主要在纸上学习 | 应用内记录少，搭子缺上下文 | 拍照带回、一句话记结果，不追求全自动 |
| 手机是易受干扰设备 | 打开后注意力被带走 | 首页一屏给出当前活动，不给闲逛空间 |
| 库格式变化清空测试数据 | 数据包与当前版本不兼容 | 接受：内测前只有测试数据；只保留当前版本的导出与恢复 |
| 对外材料与实现分叉 | 答辩时口径对不上 | 范围与指标先写进本文；结题前核对数字、期限与样本边界 |

## 6. 协作

- 同步：每周开一次 30 分钟的短会，只回答三句话，即上周完成的内容、本周计划、当前困难；除此之外没有别的例会。
- Git：`main` 始终保持能构建；做功能开分支，合并之前自己先检查一遍，改动较大时请另一个人看一眼。提交信息的格式见 [提交约定](../CONTRIBUTING.md)。
- 文档：改了数据结构或口径，先改“唯一真相”那一份（定义改 00，字段改 01，页面与验收改 02，分工与节点改本文），再同步其他文档。数字只在一处定义，别处只做引用。
- 决策：出现取舍时按 [ADR 规则](adr/README.md) 记录，跨模块、难回退的决定写一条 ADR，单一领域的小决定写进对应文档或提交正文；一次性的背景写提交正文。
- 密钥与数据：API key 不进仓库；原始数据以本机为主副本，用户登录后同步到自建服务端，服务端的提供方 key 与数据库口令只通过环境变量注入；调用模型时只发送当次需要的那一段。
