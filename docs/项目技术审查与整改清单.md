# 项目技术审查与整改清单

> 本文记录 2026-11-23 对客户端、服务端、接口契约、数据包、更新检查、依赖与持续集成所做的技术审查，供后续整改和验收使用。审查基线为提交 `a0c1bdf` 及当时的本机工作区；工作区已有其他任务留下的未提交改动，因此凡是受这些改动影响的结论均单独注明。本文不重复[过度设计审查](过度设计审查.md)与数据库结构审查中的架构问题，也不代替 00—03、ADR 和接口契约中的现行定义。2026-11-23 入库前按最终代码核对过一遍，API-06 已经只余输出下限一项，见该条末尾的核对记录；同日批次 1 的 API-01 与 API-02 已完成，见各条的已关闭记录。

## 1. 使用方法

这份清单面向负责整改、评审和验收的成员。本文的立场是先恢复主链路的正确性，再处理可能造成资源耗尽、错误部署或错误验收的问题，最后清理维护性欠账；仅因版本较旧而没有实际风险的依赖不列为缺陷。

| 等级 | 判断标准 |
|---|---|
| P0 | 主链路当前无法完成，或者现有实现会稳定地违反服务端或上游契约 |
| P1 | 特定输入、模型或文件规模下会产生错误结果、资源耗尽、重复下载或错误部署 |
| P2 | 现有功能通常可用，但契约、测试、文档或维护机制不能可靠地防止回归 |
| 待决定 | 代码已经表达一种产品含义，但现行产品文档尚未确认该含义 |

每项整改只有在实现、针对性测试和相关文档同时完成后才能关闭。如果修改了跨模块契约，执行人还要按照仓库约定补充 ADR 或更新既有 ADR，而不能只修改本文的状态。

## 2. 总体判断

当前最先需要处理的不是继续替换库，而是完成 Responses 主链路的契约闭环。审查时客户端现行地址缺少 `/responses`，客户端发送的 `store: false` 也会被服务端字段白名单拒绝，两项共同阻断真实模型请求；这两项已由同一个 `AccountService` 查出，见第 3 节各条的核对记录，主链路是否已经恢复要靠批次 1 的契约测试证明。2026-11-23 批次 1 已按第 3 节各条的“已关闭”记录完成，两项 P0 关闭；批次 2 的模型链路整改与批次 3 的数据包、更新检查整改也在同日完成，见各条。

项目其他部分的主要风险集中在三个方面。第一，审查时备份、恢复与当前数据包都存在整包进入内存的路径，压缩包导入也没有文件数量和解压后总量限制，批次 3 已分别改为流式传输与包级预算（见 DATA-01、DATA-02）；第二，服务端自动部署没有执行与 CI 等价的生成物核对；第三，部分测试证明了实现之间的相对改进，却没有给出可以作为发布门槛的绝对质量标准。依赖审查没有发现已知 Go 漏洞，也没有发现必须立即替换的直接运行时依赖。

## 3. P0：先恢复模型主链路

### API-01　客户端请求地址缺少 Responses 路径

`app/lib/application/account_service.dart:422` 将登录后的模型地址拼为 `<服务地址>/v1/llm`，`app/lib/ai/llm_transport.dart:244-247` 又将该地址直接作为 `POST` 目标；服务端只注册了 `POST /v1/llm/responses`，见 `server/api/openapi.yaml:660`。现有单元测试分别验证了地址拼接和一个由测试直接注入的完整地址，没有覆盖登录配置经过真实传输层后形成的最终请求，因此没有发现这项接口错位。

整改时应将对话端点与嵌入端点分开表达，不能简单地在所有模型地址后追加 `/responses`，因为嵌入客户端还需要使用 `/embeddings` 与 `/embeddings/lookup`。验收至少包括一项跨 `AccountService` 与 `HttpLlmClient` 的契约测试，并断言最终路径、鉴权头和请求方法。

核对记录（入库前）：`app/lib/application/account_service.dart:422` 现为 `(endpoint: '$base/v1/llm', apiKey: current.accessToken)`，只拼到 `/v1/llm`；服务端只注册了 `POST /v1/llm/responses`（`server/api/openapi.yaml:660`），所以登录后的真实请求打不到对话端点，问题仍然成立。本条保留为 P0。

已关闭（2026-11-23）：`AccountService` 的私有取址改为只返回服务地址与令牌，两个接口地址由 `responsesEndpoint` 拼出对话地址 `<服务地址>/v1/llm/responses`，由 `embeddingsEndpoint` 拼出嵌入前缀 `<服务地址>/v1/llm`，嵌入客户端再用 `endpointUri` 接上 `/embeddings` 与 `/embeddings/lookup`。跨层契约测试写在 `app/test/application/account_service_test.dart` 的“对话请求的跨层契约”一组：只经过 `authorizeModelConfig` 拿地址，再用真实的 `HttpLlmClient` 发一次请求，断言最终路径是 `/v1/llm/responses`、方法是 `POST`、鉴权头是当前访问令牌，请求体带 `store: false` 且不带采样参数，输出上限落在 16 到 32768 之间，嵌入地址仍是 `/v1/llm/embeddings`。同组测试在改回旧拼法时会失败，这一点在整改过程中确认过。

### API-02　客户端要求无状态调用，服务端却拒绝 `store: false`

`app/lib/ai/llm_protocol.dart:165` 每次发送 `store: false`，但 `server/internal/llmproxy/proxy.go:560-565` 的 `chatFields` 不含 `store`，随后 `allowFields` 会在第 582—589 行拒绝不在白名单里的字段。当前未提交的 OpenAPI 已经写入 `store: false`，代理注释也声称服务端会固定该值，但实际转发代码尚未实现这项约束，所以当前工作区仍不一致。

服务端不应只将 `store` 加入白名单，而应忽略客户端给出的其他值并在转发前固定写成 `false`，同时用代理测试断言上游实际收到的值。OpenAI Responses 创建接口当前默认 `store: true`，因此如果服务端静默删除该字段，用户内容仍可能被上游保存，不能以“字段可选”为由省略。外部契约见 [Responses API reference](https://developers.openai.com/api/reference/resources/responses/methods/create)。

核对记录（入库前）：客户端现行代码每次请求都发 `store: false`（`app/lib/ai/llm_protocol.dart:167`），服务端现行的 `chatFields` 白名单仍不含 `store`，`allowFields` 会以 `unsupported model request field` 拒绝；代理注释写“`store` 固定为 false”，实现里没有这一步。OpenAPI 的说明与字段表已经写入 `store: false`，契约写在前面，代码没有跟上，问题仍然成立。本条保留为 P0。

已关闭（2026-11-23）：`server/internal/llmproxy/proxy.go` 的 `chatFields` 放行 `store`，`withModel` 在转发前把该字段一律改写成 `false`，不发这个字段的请求也会补上，所以上游不会再按默认值保存响应。OpenAPI 的字段说明写明取值由服务端决定。服务端测试 `TestHandlerResponsesForcesStoreOff` 让客户端分别发 `false`、发 `true` 与不发该字段，断言上游三次收到的都是 `false`。

## 4. P1：正确性、资源与部署风险

### API-03　流式正文会在条目完成事件中重复

`app/lib/ai/llm_protocol.dart:260-270` 已经消费 `response.output_text.delta`，但 `_doneItem` 又在第 340—342 行将 `response.output_item.done` 中完整的 `message` 正文作为新增量发出。上游正常地同时发送增量和完成条目时，界面会得到“增量正文 + 完整正文”。现有流式测试只组合了正文增量与 `response.completed`，没有加入携带完整 message 的 `response.output_item.done`，所以未覆盖真实事件序列。

整改时应将条目完成事件只用于确认状态，或者在没有收到过正文增量时才从完整条目补回正文，并补充包含完整官方事件顺序的测试。

已关闭（2026-11-23）：`_doneItem` 处理 `message` 条目时先看这次流有没有收到过正文增量，收到过就只确认结束、不再发正文；一条增量都没有时才用完整条目补回，供不带增量的来源使用。测试 `正文增量之后仍有完整条目时只收一次正文` 按官方顺序发了两个增量与一条完整条目，改前得到“你好你好”；`只有完整条目没有正文增量时才从条目补回正文` 覆盖补回路径。

### API-04　并行工具调用在乱序完成时可能归入错误序号

`response.function_call_arguments.delta` 的 `output_index` 位于事件顶层，客户端在第 262—267 行能够读取；`response.output_item.done` 的顶层 `output_index` 却在调用 `_doneItem` 时被丢弃，`_doneItem` 第 308—325 行改用仍未完成序号的插入顺序推测。两个调用按相反顺序完成时，完整参数、调用编号和工具名可能被写入另一项调用。

整改时应将完整事件传给 `_doneItem`，直接使用事件顶层的 `output_index`，并增加“两个工具同时分片、后开始者先完成”的测试。现有并行测试按照开始顺序完成，不能证明乱序情况正确。

已关闭（2026-11-23）：`_doneItem` 改为接收整个事件，序号依次取事件顶层的 `output_index`、条目自己的 `output_index`，最后才推测。推测这一步也一并修正：取已经由参数增量开始、还没有完成过的最小序号，并用一张已完成序号集合挡住已分配的序号，原先两个条目都不带序号时会把第二项写回第一项。测试 `两个工具乱序完成时按顶层 output_index 归位` 与 `工具条目不带 output_index 时按尚未完成的那个序号归位` 在改前分别把 `call_b` 写到序号 1、把第二个条目写回序号 1。

### API-05　无状态推理、拒答和未完成原因没有完整建模

客户端在 `store: false` 下每轮重发上下文，但 `LlmMessage`、整段响应解码与 `agent_loop.dart:140-160` 只保留正文和函数调用，没有保留需要随工具结果回传的 reasoning 条目；对于 reasoning 模型的多步工具调用，这会丢失上游要求的推理上下文。正文解析只读取 `output_text`，没有处理 `refusal`；流式和非流式路径又将所有 `incomplete` 都解释为输出长度截断，没有读取 `incomplete_details.reason`。这些情况分别会造成后续调用失败、合规拒答被误报为空响应，以及非长度原因被错误提示为“回答过长”。推理条目的外部契约见 [Reasoning models guide](https://developers.openai.com/api/docs/guides/reasoning)。

整改前应先确定服务端允许的 reasoning 模型及其状态管理方式。如果继续坚持无状态调用，客户端必须保存并回传上游要求的条目；如果服务端禁止此类模型，则应在模型能力配置和管理端校验中明确拒绝，而不能依靠模型名猜测。

部分关闭（2026-11-23）：拒答与未完成原因两项已处理。新增失败类型 `LlmFailure.refused`，流式的 `response.refusal.delta` 与整段响应 message 内容块里的 `refusal`、顶层 `refusal` 条目都按它报告，界面显示“这个问题模型不能回答，请换一种问法”，不再当成空回答。`response.incomplete` 与整段响应的 `incomplete_details.reason` 只在取值为 `max_output_tokens` 时按截断处理并保留正文，其余原因按服务端错误报告并带上原因，不再提示“回答过长”。测试覆盖流式与整段两条路径的四种组合。

推理条目的回放仍未做，原因是它取决于 DECISION-02：服务端是否允许 reasoning 模型尚未定，结论出来之前客户端不保存也不回传推理条目。批次 2 不包含这一项。

### API-06　请求参数没有按模型能力收敛

`app/lib/ai/llm_protocol.dart` 对所有模型固定发送 `temperature: 0.5`，而当前未提交的 OpenAPI 已经写明客户端不发送 `temperature` 与 `top_p`。`temperature` 并非整个 Responses API 的过时字段，但部分模型不支持它，因此当前问题是客户端没有能力判断，而不是该参数在所有模型上都应删除。默认请求应省略非必要采样参数；如果以后确有调参需求，应由服务端的模型能力配置决定是否允许。

`app/lib/ai/llm_config.dart` 还允许 `outputTokenLimit` 低至 1，当前 OpenAPI 的最小值是 16；当上下文配置小于 64 时，客户端会生成服务端必然拒绝的请求。整改时应由同一份契约或共享测试约束上下限，并删除仍写着“Chat Completions”的注释和仅由测试引用的 `reasoningDisabled` 推测逻辑。

核对记录（入库前）：审查之后的两条提交（`a3a83bd`、`ec0e203`）已经处理了本条的大部分。客户端不再发送 `temperature` 与 `top_p`，`buddyMaxOutputTokens` 与 OpenAPI 的 32768 对齐，服务端按 16 到 32768 校验、省略时补 4096，设置页的说明改成“接口走 Responses”，`reasoningDisabled` 已删除。仍然成立的是 `LlmConfig.outputTokenLimit` 的下界：`app/lib/ai/llm_config.dart:43` 仍是 `math.max(1, contextWindowTokens ~/ 4)`，`contextWindowTokens` 小于 64 时得到 1 到 15，服务端回 400。本条降为“下限没有与契约对齐”，批次 2 只保留这一项。

已关闭（2026-11-23）：新增常量 `buddyMinOutputTokens = 16`，与服务端 `minOutputTokens` 同值；`outputTokenLimit` 改为在 16 与 32768 之间取值，上下文上限配得再小也发出 16。测试遍历 1 到 1000000 的上下文上限，断言输出上限始终落在服务端接受的区间里，并断言协议请求体里的 `max_output_tokens` 就是这个值。

### DATA-01　大文件上传、下载与导入存在整包内存峰值

`app/lib/application/cloud_backup_service.dart:35-74` 在上传时对备份文件执行 `readAsBytes`，在下载时读取 `response.bodyBytes`；`app/lib/data/cloud/server_client.dart:983-1005` 又以 `Uint8List` 发送请求。恢复入口 `app/lib/ui/restore_flow.dart:152`、当前数据包入口 `app/lib/ui/data_version_page.dart:858` 也会一次性读取整个文件。服务端允许的备份上限达到 256 MiB，因此 Android 设备可能同时持有文件字节、HTTP 缓冲、压缩包对象和解压后的内容，内存峰值显著高于文件本身。

上传应使用文件流并增量计算哈希，下载应直接写入临时文件并在流上校验，导入入口应先检查文件大小再交给受限解码流程。验收需要在接近上限的测试文件上记录峰值内存，并确认取消、超时和校验失败都会删除临时文件。

已关闭（2026-11-23）：上传先在文件上分块算出 SHA-256，再由 `server_client.dart` 的 `backupUpload` 按文件流发送，`cloud_backup_service.dart` 不再调用 `readAsBytes`；下载改为 `backupDownloadTo`，边收边写临时文件、边算哈希，核对 `X-Content-SHA256` 与 `Content-Length`，服务端拒绝、超时、字节数不符与校验值不符时都删掉临时文件。云端备份入口与两个导入入口（`restore_flow.dart`、`data_version_page.dart`）在读取之前先看文件大小，超过 256 MiB 的包不读进内存，上限与服务端 `ZHIXIN_MAX_BACKUP_BYTES` 同值，写在 `domain/rules/package_budget.dart`。用例覆盖上传与下载往返、校验值不一致、下载超时与服务端声明字节数不一致，后三种都断言临时文件已删除。包内的条目数、单条目大小与压缩比仍由 DATA-02 的包级预算约束；恢复时的峰值内存再往下走，需要解码从文件流读取，同样归 DATA-02。

### DATA-02　不受信任的压缩包没有解压资源上限

`app/lib/data/backup/data_package_service.dart:44-68` 与第 93—125 行会完整解码用户选择的数据包并将数据库和图片读入内存，`app/lib/data/revisions/revision_package.dart:108-151` 对当前数据包采用相同方式。现有实现已经检查条目路径和内容哈希，但没有限制压缩包文件数、单条目解压后大小、累计解压大小与压缩比，所以体积较小的恶意压缩包仍可能耗尽内存或磁盘。

整改时应在读取条目内容之前执行统一的包级预算，至少约束压缩文件大小、条目数量、数据库大小、单附件大小、累计解压大小和压缩比，并为超限情况提供不会修改当前数据库的测试。路径安全检查应继续保留，不能用资源上限替代路径校验。

已关闭（2026-11-23）：新增包级预算 `PackageBudget`（`app/lib/domain/rules/package_budget.dart`），在读取任何条目内容之前检查压缩包 256 MiB、条目数 20000、`zhixin.db` 解压后 256 MiB、单附件 32 MiB、累计解压 512 MiB 与压缩比 100 六项，单附件上限与服务端 `ZHIXIN_MAX_ATTACHMENT_BYTES` 同值。`DataPackageService` 与 `RevisionPackageService` 都接受可覆盖的预算参数，旧格式数据包、当前数据包与版本库备份的预检和恢复共用同一份检查；`inspectRepository` 先确认包是版本库备份再检查，当前数据包仍按原路径返回 null。超限时分别抛 `BackupException` 与 `FormatException`，恢复与导入在替换或写入之前拒绝。用例覆盖六种超限、刚好等于上限、目录不计入累计大小，以及超限后当前库记录、`HEAD` 与 schema 不变。预算依据 zip 头声明的大小与条目元数据，低报大小的包在读取时仍可能产生更大内存占用，从文件流解码属于恢复峰值内存的后续工作。

### UPDATE-01　更新检查预先下载整包，用户确认后又重新下载

`app/lib/application/update_check_service.dart:206-242` 在显示更新提示之前下载安装包、写入临时文件、计算哈希并立即删除，生产下载函数第 277—285 行又使用 `response.bodyBytes` 将整个安装包放进内存。提示页 `app/lib/ui/update_notice.dart:90-97` 只打开外部浏览器，所以用户确认更新后还要重新下载同一安装包。该流程在启动自动检查时也会发生，既消耗流量和启动时间，也不能保证浏览器第二次得到的字节与第一次验证的字节相同。

如果签名对象是发布清单中的版本、地址和哈希，检查阶段应只验证清单，用户确认后再下载；如果产品要求验证安装包本身，应用就应保留并安装已经验证的文件，而不能再交给浏览器下载。无论选择哪种方式，安装包都应流式落盘和计算哈希。

已关闭（2026-11-23）：采用前者，检查阶段只读发布清单、比较版本、核对 https 与 `sha256` 格式，并用内置公钥对哈希字符串验签，不再对安装包地址发起请求；`UpdateFailure.download` 与 `UpdateFailure.hashMismatch` 随之删除，`ReleaseDownloader`、`downloadPackage` 与 `tempDirectory` 注入点一并移除。用户确认后仍由系统浏览器打开清单地址下载一次，应用内不安装，系统安装器在覆盖安装前核对安装包签名。用例把清单地址设为不可解析的 `https://example.invalid/zhixin.apk`，断言仍返回有更新，证明检查阶段没有下载；https、签名、公钥为空与网络失败的用例保留。启动检查因此不再消耗安装包流量，下载只发生在用户确认之后，也只发生一次。

### CI-01　自动部署可能绕过生成物漂移检查

`.github/workflows/ci.yml:140-154` 会重新生成 sqlc 与 OpenAPI 代码并检查差异，`.github/workflows/deploy-server.yml:53-59` 的部署前验证只执行格式、tidy、vet 和测试。两条 workflow 会在同一次 `main` 推送后独立运行，所以契约或查询已经修改、生成物尚未提交时，CI 可以报错，而部署流程仍可能使用旧生成物构建并部署。

部署前验证应复用同一段生成物核对，或者让部署明确依赖已经通过的 CI 结果。验收测试应构造“只改 OpenAPI、不改生成文件”的提交，确认它不会进入构建和部署步骤。

已关闭（2026-11-23）：采用前者，`deploy-server.yml` 的验证任务在 `go vet` 之后增加与 `ci.yml` 服务端任务相同的两步核对，重新运行 sqlc 与 oapi-codegen 后用 `git diff --exit-code` 与 `git status --porcelain` 确认生成物没有漂移，命令中的生成器版本与 `ci.yml` 一致。生成物与契约不一致的提交停在检查阶段，不会进入编译、上传与切换；代价是每次部署都要重新下载并运行两个生成器，验证任务多花一份时间。ADR-0032 的执行顺序一句同步写明这两步核对。

## 5. P2：契约、测试与维护机制

### CONTRACT-01　OpenAPI 生成不能提供文档声称的全部编译期约束

`server/api/cfg.yaml:11-14` 只生成 models 与标准 HTTP server，处理器签名仍是 `func(http.ResponseWriter, *http.Request)`，请求字段、响应体和状态码由处理器手工解析与写入。因此契约新增字段或修改响应形状时，生成代码不一定产生编译错误。`server/README.md:7` 与 `docs/轮子与技术选型评估.md:71` 对编译期保障的描述高于当前实现能力。

后续可以选择严格服务器接口生成，也可以保留现有处理器并增加契约测试，但文档必须准确说明保障边界。客户端与服务端的集成测试不能只断言路径，还应覆盖请求字段、默认值、状态码、problem 结构和流式 Content-Type。

### TEST-01　LongMemEval 目前是对照实验，不是发布质量门槛

`app/test/evaluation/longmem_eval_test.dart:617-732` 主要断言混合或跨次策略不差于前一策略，并允许部分固定用例继续在 retrieval 阶段失败。本轮输出中，字面、索引、混合与跨次策略分别通过 4/9、6/9、6/9 与 8/9。测试通过只能证明相对关系和既定失败没有变化，不能证明检索或回答质量已经达到发布要求。

团队应在 03 或评测文档中确定分策略的最低通过数、不得退化的关键用例和失败结果的保存方式，再让 CI 对这些阈值作断言。如果仍将该测试定位为诊断实验，发布结论就应单独报告实际通过数，不能只写“全量测试通过”。

### RETRY-01　模型重试没有完整传递上游退避信息

代理的可重试状态没有包含所有可能的短暂冲突状态，也没有向客户端保留上游 `Retry-After`；客户端在 `app/lib/ai/llm_transport.dart` 使用固定间隔的一次重试。该策略在低并发下通常可用，但会在限流或上游维护时制造同步重试。

整改时应先区分“切换下一上游”和“通知客户端稍后重试”，再统一处理 429、可重试的 5xx、必要的 409 与 `Retry-After`，并增加带秒数和 HTTP 日期两种头值的测试。

### SERVER-01　SMTP 取消期间会额外发送一次

`server/internal/auth/mailer.go:215-219` 在退避等待的 `select` 中使用无标签 `break`，它只退出 `select`，不会退出外层重试循环。上下文在等待期间取消后，代码仍会再调用一次 `deliver`，然后才因上下文错误退出；`staticcheck` 以 SA4011 检出了该问题。

整改时应直接返回上下文错误或使用带标签的循环退出，并增加“退避期间取消后调用次数不再增加”的测试。

### MAINT-01　Responses 迁移还留有旧术语与相互矛盾的说明

`app/lib/ai/llm_config.dart:8-11` 与 `app/lib/ui/settings_page.dart:563` 仍写着 Chat Completions，部分测试夹具仍使用旧路径，`server/internal/server/routes.go` 还保留旧路径的 404 占位处理器。`docs/分层整改清单与提示词.md` 一处将“核对上游支持 Responses”标为完成，另一处仍列为待决定，而且没有留下 provider 与 model 的核对证据。这些残留会使后续成员误判现行接口。

清理时应先用契约测试证明新链路成立，再删除旧处理器、旧字段和旧说明，并用 `rg` 检查 `chat/completions`、`Chat Completions`、旧代理路径与废弃模型名。历史原因保留在提交正文，不在现行文档中并列两种说法。

核对记录（入库前）：`a3a83bd` 与 `ec0e203` 之后，设置页与 `llm_config.dart` 的旧说法已经改成 Responses；`server/README.md` 的模型示例已经换成 `zhixin-chat` 与 `deepseek-chat`。当时另外列出三处，用于下次核对时不再重复排查，其中 `server/internal/server/routes.go` 与 `server/internal/testutil/testutil.go` 里刻意保留的 `PostV1LlmChatCompletions` 404 占位已于 2026-11-24 删除：契约与生成代码在前一天删掉这条路径之后，这两个手工方法不再受接口约束，留着只会让 `rg` 复查分不清现行实现，旧地址现在按契约之外的路径返回 404 problem。剩下两处不构成矛盾：`app/test/application/discussion_service_test.dart:954` 的 `chat/completions` 只是一个测试夹具里的地址字符串，不参与请求；`docs/分层整改清单与提示词.md` 里 G0 与 G10 的关系已经在该文件里写明。本条不再按“相互矛盾的说明”处理，批次 5 保留的是 `rg` 复查。

### MAINT-02　DeepSeek 示例与依赖维护入口需要更新

`server/README.md:441-444` 与管理后台占位提示仍使用旧的 DeepSeek 模型示例；截至本次审查，官方 [Models & Pricing](https://api-docs.deepseek.com/quick_start/pricing/) 与 [Responses API compatibility](https://api-docs.deepseek.com/guides/responses_api/) 页面列出的 Responses 模型已经不同。整改时应按项目真实使用的 provider、base URL 与 model 做一次可复现探测，不应只替换字符串。

`.github/dependabot.yml` 此前只覆盖 pub、gradle 与 action，Go 模块与 Docker 基础镜像只能靠手工盘点，2026-11-27 补上了 `server/` 的 gomod 与 docker 两条。审查时列出的 `oapi-codegen/runtime` 1.9.0 到 1.9.1、`github.com/klauspost/compress` 1.20.4 到 1.20.5 与契约测试用的 `go.yaml.in/yaml` v3 到 v4 也在同一天升完，`go vet` 与 `go test ./...` 通过；`actions/setup-go` 已经用到 v6。生成器版本仍分散在 workflow、README、CONTRIBUTING 与配置注释中，`oapi-codegen` v2.8.2 与 `sqlc` v1.31.1 各写了三四处，下一步仍然是收敛到 Go 1.27 的 `tool` 指令，再决定要不要纳入自动更新。

## 6. 待决定事项

### DECISION-01　“必须更新”是否真的阻止继续使用

`app/lib/ui/update_notice.dart:41-71` 在版本低于 `min_version` 时显示“必须更新”和“请更新之后继续使用”，但同一个对话框始终提供“以后再说”，用户关闭后可以继续使用。现行 ADR 只说明客户端判断是否必须更新，没有明确要求阻断。

产品负责人需要在 00 或 02 中选择一种口径：如果确实强制更新，应定义不可绕过的页面、离线行为、下载失败和服务端不可用时的处理；如果不准备阻断，应将标题和正文改为“建议尽快更新”，避免代码表达没有实现的承诺。

已决定（2026-11-23）：不阻断。没有应用商店作为兜底，发布清单、发布服务或网络不可用时，阻断会让用户连本机记录也打不开，与本机离线可用的承诺冲突；强制更新需要的不可绕过页面、离线行为与下载失败处理也都没有实现。客户端把低于 `min_version` 的标题改为“建议尽快更新”，正文说明云端同步与在线模型可能不可用、可以先不更新，保留“以后再说”；`UpdateCheckResult.requiredUpdate` 改名为 `belowMinimum`，只决定措辞，不改变是否提示。服务端的清单字段说明、`server/README.md` 与 02 第 3.16 节同步改成现行口径，A7 的验收条件不变。

### DECISION-02　推理模型采用无状态回放还是服务端状态

当前客户端明确发送完整上下文并使用 `store: false`，但模型列表允许管理员配置不同提供方和模型。团队需要决定是否只支持能够在无状态回放下工作的模型，还是为特定模型引入服务端状态；该决定会影响隐私说明、额度结算、失败恢复和多轮工具调用，属于跨客户端与服务端的取舍，确定后应写入 ADR。
