# 知新 · 现成轮子与技术选型评估

> 本文回答两个问题：项目里哪些手写实现可以交给已经在用或成熟的现成库，哪些已经选定的库与技术用法还能改进。范围是 2026-11-14 的 `fix/first-load-transition`（与 `main` 同源）上的 `app/`，以及 `feat/api-backend` 分支上的 `server/` 骨架。本文是评估，不是决定；采纳哪一条，按 [ADR 规则](adr/README.md) 另立条目或写进对应文档，已经采纳的条目见 [第 1.1 节](#11-已经采纳的条目)。

## 1. 结论

最值得做的改动不是引入新库，而是把已经引入的 drift 与随包 SQLite 用满。ADR-0004 为了编译期检查、统一执行器和固定 SQLite 版本换上了 drift，生成了约 1.2 万行代码，但仓库层没有一处使用 drift 的查询接口，全部 SQL 仍经 `DriftRawDatabase` 适配器以 sqflite 的形状执行，行数据靠 94 处 `fromRow` 与约 510 处 `as 类型` 手工转换；sqflite 原来还在备份、恢复校验与版本包里打开库副本，两套驱动并存，这一处已经按 ADR-0012 改完，库副本全部由 `sqlite3` 打开。随包 SQLite 已经带 FTS5 与会话扩展，关键词检索却仍是 `LIKE` 扫描加每次查询在 Dart 里现建一次 BM25 索引。剩下的两处都能在不增加依赖的前提下改好，收益直接落在类型安全和检索速度上。

服务端骨架坚持“标准库优先”是对的，但 PostgreSQL 存储、OpenAPI 契约与登录限流这三块接下来都要写，用代码生成和 `golang.org/x` 里的现成实现比手写更省，依赖口径与 ADR-0009 一致。

模型客户端、版本引擎与同步协议这三块手写得最多，但它们承载的是项目特有的语义，本文判断暂不替换，理由在第 4 节。

| 序号 | 位置 | 现状 | 结论 | 优先级 |
|---|---|---|---|---|
| 1 | 仓库层查询 | drift 只当执行器，SQL 手写、行数据手工转换 | 移进 `.drift` 文件，生成类型化查询（[ADR-0011](adr/0011-仓库查询改用drift生成代码.md)） | 高 |
| 2 | 库副本的打开方式 | 备份、恢复校验、版本包曾用 sqflite | 已统一用 `sqlite3` 打开，`sqflite` 与 `sqflite_common_ffi` 已删除（[ADR-0012](adr/0012-结束sqflite与drift并存.md)） | 已完成 |
| 3 | 关键词检索 | `LIKE` 扫描 + 每次查询现建 BM25 | FTS5 外部内容表 + 内置 `bm25()`，删掉 `bm25` 包（[ADR-0013](adr/0013-关键词检索改用FTS5.md)），已实施 | 高 |
| 4 | 页面刷新与首屏缓存 | 每次写入后手动 `_load()`，`dataVersion` 判断失效 | drift 流式查询，由版本引擎按提交涉及的表通知更新（[ADR-0014](adr/0014-流式查询与版本通知.md)） | 中 |
| 5 | 服务端 PostgreSQL | PostgreSQL 存储已实施，开发和测试仍可使用内存实现 | `pgx` + `sqlc` 由 `schema.sql` 与查询文件生成存取代码（[ADR-0015](adr/0015-服务端引入代码生成与限流依赖.md)） | 高 |
| 6 | 服务端契约 | 手写处理函数，`openapi.yaml` 只作文档 | `oapi-codegen` 生成标准库路由的严格服务接口（[ADR-0015](adr/0015-服务端引入代码生成与限流依赖.md)） | 中 |
| 7 | 登录与刷新令牌 | 无限流 | `golang.org/x/time/rate` 按账号与来源地址限流（[ADR-0015](adr/0015-服务端引入代码生成与限流依赖.md)） | 中 |
| 8 | 同步主键 | 客户端 `INTEGER AUTOINCREMENT`，对应 [04 的 D2](04-长期路线图.md#5-待定决定) | UUIDv7（Dart `uuid`、Go `google/uuid`） | 中 |
| 9 | 账号体系扩展 | 自写邮箱密码 | 只做邮箱时保持自写；要手机号或微信登录时改用 Casdoor 或 Logto | 视需求 |
| 10 | 版本引擎 | 触发器采集净变化 | 评估 SQLite 会话扩展，暂不替换 | 低 |

### 1.1 已经采纳的条目

第 1 至第 7 条已经写成 ADR，状态与日期见 [ADR 索引](adr/README.md#5-索引)。其中 ADR-0011 至 ADR-0013 已经把 [ADR-0004](adr/0004-数据层改用drift与自带sqlite.md) 的收尾工作定下来，ADR-0012 已经实施完毕，ADR-0011 与 ADR-0013 分批实施；ADR-0014 只是提议，ADR-0015 补了 ADR-0009 的依赖口径。第 8 条等 [04 的 D2](04-长期路线图.md#5-待定决定) 定下主键形态之后另立 ADR，客户端的 UUIDv7 实现随那次 schema 提升一起做；第 9、10 条保持评估，没有进入排期。

## 2. 客户端：把已经引入的轮子用满

### 2.1 仓库查询改用 `.drift` 文件生成

ADR-0004 的决定是“表结构与查询在编译期就被检查”，但目前只做到了前一半。`lib/data/repository/` 下的 12 个仓库文件全部通过 `rawQuery`、`rawInsert` 一类方法执行字符串 SQL，仓库层共有 50 处 `rawQuery`、1 处 `rawInsert`、1 处 `rawUpdate` 与 1 处 `rawDelete`，`customSelect` 与 `.watch` 没有一处使用，执行器上的 `select(` 只是方法名沿用了旧的接口形状；领域模型的 `fromRow` 共有 94 处，逐列 `as String`、`as int?` 的手工转换约 510 处，列名拼错或可空性写错只能在运行时发现。生成文件已经付出了一万多行的代价，查询却没有拿到类型检查。

团队在 ADR-0004 里明确不想把 SQL 改写成 DSL，这一点与 drift 并不冲突，因为 drift 支持把原生 SQL 写在 `.drift` 文件里，由生成器在编译期解析每条语句、校验表名列名与参数类型，再生成带类型的查询方法和结果类，返回值可以直接 `.get()` 或 `.watch()`。迁移方式是按仓库逐个搬：现有 SQL 原样放进 `.drift` 文件，仓库方法改为调用生成的方法，`fromRow` 改成从生成的结果类映射到领域模型。版本引擎、备份、恢复校验与撤销里依赖动态表名、`PRAGMA` 和触发器的原生 SQL 仍按 ADR-0004 留在 `RawSql` 适配器上，因为这部分 SQL 是在运行时拼出来的，生成器帮不上忙。

这一步的代价是仓库层与对应测试都要动，而且 `.drift` 文件里的查询改了要重新生成；收益是仓库层的列名、类型和可空性错误在 `build_runner` 阶段暴露，并为 2.4 节的流式查询准备好入口。迁移顺序、写入路径与跨表事务怎么处理，见 [ADR-0011](adr/0011-仓库查询改用drift生成代码.md)。

### 2.2 结束 sqflite 与 drift 并存

主库已经由 `NativeDatabase` 打开，而 `DataPackageService`、`restore_validation.dart`、`RevisionPackageService` 原来都通过 sqflite 的 `databaseFactory` 打开库副本做校验和打包，`raw_executor.dart` 里也曾保留 sqflite 的 `SqfliteRawExecutor`，40 个测试文件依赖 `sqflite_common_ffi`。同一份库文件因此被两套驱动、在 Android 上甚至是两个不同版本的 SQLite 打开：主库用随包的 SQLite，副本校验走 sqflite 的系统库，ADR-0004 想消除的版本差异在恢复路径上依然存在。

这三处已经改成直接用 `package:sqlite3` 的 `sqlite3.open` 打开副本（只读校验不需要 drift），测试改用同一套打开函数，`pubspec.yaml` 里的 `sqflite` 与 `sqflite_common_ffi` 已删除，`RawDatabase` 只留 drift 与 `SqliteRawDatabase` 两个实现。这是 ADR-0004 已经决定、但尚未收尾的工作，不需要新的方向，收尾方式见 [ADR-0012](adr/0012-结束sqflite与drift并存.md)。

### 2.3 关键词检索改用 FTS5

现在的关键词路径分两步：仓库层对材料、对话、作答各列用 `LIKE ?` 取候选，`keyword_ranker.dart` 再把候选文本按 `chinese_tokens.dart` 的二元组规则切开，用 `bm25` 包现建一次内存索引排序、用完即弃。`memory_recall.dart` 排记忆正文时同样每次重建索引。数据量小的时候这样能用，但扫描成本随材料页数线性增长，每次查询都重建索引，而排序只能作用在已经被 `LIKE` 选出来的候选上。

随包 SQLite 的编译选项里已经有 `SQLITE_ENABLE_FTS5`，所以这件事不需要新依赖。可行的做法是：为材料页、消息与作答各建一张 FTS5 表，`content=` 指向业务表，正文先按 `bm25Tokens` 在 Dart 里切成二元组、以空格连接后写进索引列，FTS5 用默认的 `unicode61` 分词器按空格切分；写入与删除由业务表上的触发器同步索引列，查询端用同一套规则切词，交给 `MATCH`，排序直接用 FTS5 内置的 `bm25()`。题号、页码等精确命中已经由 `shapeQuery` 判为字面查询、走原有的 `LIKE` 路径，融合顺序不变。这样切词口径保持不变，`bm25` 包可以删除，排序也覆盖全部匹配而不只是候选。外部内容表的查询要避开只出现在索引列、不在业务表里的名字，具体写法、索引的表清单与参数绑定见 [ADR-0013](adr/0013-关键词检索改用FTS5.md)。

FTS5 自带的 `trigram` 分词器看起来更省事，但它要求查询至少三个字符，中文最常见的两字词查不到，所以不建议直接用它代替二元组。FTS 索引与向量索引性质相同，都能从业务数据重建，应当登记为不参与版本采集的派生表，恢复与撤销之后整份重建，而不是让版本引擎的触发器去采集它的影子表。另一点需要先核实：`pubspec.yaml` 让 Linux 与 Windows 的测试使用系统 SQLite（`winsqlite3.dll`、`libsqlite3.so`），系统库是否带 FTS5 因发行版而异，CI 上要么先验证，要么让涉及 FTS 的测试也用随包库。

### 2.4 用流式查询代替手动重读

页面在每次写入之后手动调用 `_load()`，`plan_page.dart` 一个文件里就有 18 处，全项目 `await _load()` 共 62 处，`setState` 共 274 处；ADR-0007 的首屏预读又用 `dataVersion` 与进程内提交序号判断缓存是否失效。这套机制是自己维护的“表变了就通知读者”，而 drift 的流式查询正好提供这个能力：查询以 `.watch()` 订阅，相关表一有写入，drift 自动重跑查询并推送新结果。

难点在于本项目的写入大多经 `customStatement` 这类原生 SQL 进入，drift 不知道它们改了哪些表，因此不会自动通知。版本引擎恰好知道：每次提交收尾时，采集到的净变化已经按表归好类，`finishCommand` 只需要对这些表调用一次 `notifyUpdates`，撤销、恢复与清空在独占区结束时对全部业务表通知一次即可。这样页面可以订阅流而不必在每个写操作后手动重读，ADR-0007 里“按版本号判断失效”的部分也可以交给 drift。ADR-0007 里另外两条要求，即首屏多次查询共用一个共享访问范围、页面等转场结束再回填，是项目自己的时序约束，drift 不替代它们，需要在订阅流的地方继续保留。

这一项依赖 2.1 节先把查询搬到生成代码上，改动面也最广，建议先在“安排”或“记录”一页试做，确认与 `DatabaseGate` 的读写协调没有冲突之后再推开。状态管理不必为此引入 Riverpod 一类框架，`StreamBuilder` 加上现有的 `AppScope` 已经够用。做法与代价见 [ADR-0014](adr/0014-流式查询与版本通知.md)。

## 3. 服务端：骨架之后的几块

### 3.1 PostgreSQL 存取用 `pgx` 与 `sqlc`

ADR-0009 规定第三方依赖只在标准库没有对应能力时加入，而 Go 标准库没有 PostgreSQL 驱动，所以 `pgx` 是绕不过去的。存取代码建议用 `sqlc` 生成：它读取现有的 `internal/store/schema.sql` 与另写的查询文件，生成类型化的 Go 方法，本身只是开发期工具，不进入运行时依赖，和客户端“SQL 原样保留、由生成器做检查”的思路一致。`syncsvc` 推送时要求的 `SELECT ... FOR UPDATE` 锁定 `sync_head` 再追加，也可以直接写在查询文件里。

### 3.2 契约生成服务接口

`openapi.yaml` 被定为契约，但处理函数是手写的，两边是否一致只能靠人工核对。`oapi-codegen` 可以从同一份文件生成基于标准库 `net/http` 路由的严格服务接口，请求与响应的结构体、路径参数和状态码都由生成代码约束，契约改了而实现没跟上时编译不过。它与 ADR-0009“不引入 Web 框架”不冲突，因为生成的代码仍挂在标准库的 `ServeMux` 上。客户端是否也从契约生成 Dart 代码可以晚一点再定，接口数量还少，手写成本不高。

### 3.3 登录与刷新限流

目前登录、注册与刷新令牌没有频率限制，密码哈希用的是 19 MiB 的 argon2id，被批量尝试时既有撞库风险，也会被当成拖慢服务的手段。`golang.org/x/time/rate` 与已经引入的 `x/crypto` 同属官方扩展库，按账号和来源地址各建一个令牌桶即可，不需要外部组件。

### 3.4 同步主键用 UUIDv7

记忆里列为待定的“增量同步的全局唯一主键”可以直接用 UUIDv7：它按时间有序，作为 SQLite 与 PostgreSQL 的主键都不会像随机 UUID 那样打散索引，Dart 的 `uuid` 包与 Go 的 `google/uuid` 都已支持。服务端现在的 `newID()` 是 16 字节随机十六进制串，账号与会话用它没有问题，但同步数据的主键由客户端生成，两端应当约定同一种格式。按 ADR-0001 与 ADR-0002，这次改主键直接升 schema 版本、清空重建，不写迁移。

主键形态与时间安排以 [04 的 D2](04-长期路线图.md#5-待定决定) 为准，决定之后另立 ADR，服务端的账号与会话主键是否一起换也在那一条里定。

### 3.5 账号体系何时换成现成服务

只做邮箱加密码时，现有的自写实现（argon2id、只存令牌哈希、刷新令牌轮换）已经覆盖了核心要求，再接一个身份服务反而多维护一个进程。但面向国内用户的内测，很可能还要手机号验证码、微信登录、邮箱验证与找回密码，这几项各自都要对接第三方并处理风控，自写的成本会迅速超过收益。如果确定要做其中两项以上，建议改用可自建的身份服务，例如 Go 编写、内置国内常见登录方式的 Casdoor，或者界面与文档更完整的 Logto，由它签发令牌，知新服务端只做校验。这件事改起来会影响账号表与客户端登录流程，属于需要 ADR 的决定。

### 3.6 附件与备份走预签名地址

ADR-0009 已经定了 S3 兼容对象存储与 MinIO。实现时建议让 API 只签发预签名上传与下载地址，字节由客户端直传对象存储，不经过 `zhixin-api` 进程，这样请求体上限、超时与内存占用都不必为几十兆的备份包放宽。签名可以用 `minio-go`，它同样适用于阿里云 OSS、腾讯云 COS 等兼容接口。

## 4. 评估过、但建议暂不替换的

模型客户端 `llm_client.dart` 有 1,835 行，手写了 Chat Completions、Responses 与 Anthropic Messages 三种线格式和 SSE 解析。社区已有 `openai_dart` 与 `anthropic_sdk_dart` 两个维护活跃的包，但换过去仍要两套依赖再加一层适配；更关键的是现有代码里有大量服务商差异处理，例如 DeepSeek 默认开启的思考模式、`max_tokens` 与 `max_completion_tokens` 的分歧，类型化 SDK 往往不暴露这些厂商私有字段。服务端代理只转发 Chat Completions，“知新服务”这一档模型来源因此只用到一种线格式，自带 key 的用户才需要另外两种。现有实现可用、有测试，替换的收益主要是少维护几百行解析代码，抵不过迁移风险，所以建议保留。

版本引擎用触发器把 23 张业务表的净变化采集进暂存表，再合并成提交，撤销与恢复都建立在它上面；引擎、撤销、版本包与附件的代码加上 `revision_package.dart` 合计约 3,600 行，并有完整测试。随包 SQLite 同时开启了 `SQLITE_ENABLE_SESSION` 与 `SQLITE_ENABLE_PREUPDATE_HOOK`，`package:sqlite3` 也提供 `Session` 与 `Changeset` 接口，会话扩展生成的变更集可以直接取反用于撤销，也适合当同步的传输格式。但换成会话扩展等于重写引擎，系统库又未必开启会话扩展，测试环境也要一并改。建议在设计云同步的冲突规则时把变更集作为备选格式评估一次，而不是现在替换。

PowerSync、ElectricSQL 一类同步框架可以对接 drift，但它们要接管写入路径（PowerSync 用视图加上传队列），与版本引擎的提交、撤销语义和服务端“单账号线性提交序列”的设计都冲突，采用它们意味着推翻 ADR-0008 的同步方案，所以不建议。

Riverpod、`go_router` 与 `freezed` 都是常见选择，但在这个项目里收益不大：只有 Android 一个平台、没有深链接，命令式的 `Navigator` 加上统一的 `ZhixinPageTransitionsBuilder` 已经够用；状态主要在单页内，流式查询落地后手动刷新会大幅减少；领域模型的手工转换在 2.1 节之后会被生成的结果类取代，再加一层 `freezed` 只会增加生成代码。

如果云备份上线后希望本机库也加密，随包库的构建钩子可以把 `source` 切到 SQLite3 Multiple Ciphers，不需要换驱动，这一项等账号与备份落地后再议。

## 5. 已经用对、保持现状的

界面层的 Forui 与 `forui_lucide`、安排页的 `calendar_view`、框选用的 `crop_your_image` 加纯 Dart 的 `image`、流式 Markdown 的 `gpt_markdown`、密钥存储的 `flutter_secure_storage`、数据包的 `archive`、自建 Sentry、向量索引的 `sqlite3_vec`，以及服务端用 `x/crypto` 的 argon2id，都是在合适的位置用了合适的库，本文不建议改动。`motion.dart` 虽然是手写，但它实现的是项目自己定下的克制动效口径，官方 `animations` 包的过渡样式反而更花哨，保留更合适。`docx_import.dart` 用 `archive` 与 `xml` 手工解析 OOXML，Dart 生态里没有同时处理公式命名空间与分段规则的成熟包，同样保留。
