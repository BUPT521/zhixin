# 知新 · 现成轮子与技术选型评估

> 本文回答两个问题：项目里哪些手写实现可以交给已经在用或成熟的现成库，哪些已经选定的库与技术用法还能改进。范围是 2026-11-14 的 `fix/first-load-transition`（与 `main` 同源）上的 `app/`，以及 `feat/api-backend` 分支上的 `server/` 骨架。本文是评估，不是决定；采纳哪一条，按 [ADR 规则](adr/README.md) 另立条目或写进对应文档，已经采纳的条目见 [第 1.1 节](#11-已经采纳的条目)。

## 1. 结论

最值得做的改动不是引入新库，而是把已经引入的 drift 与随包 SQLite 用满。ADR-0004 为了编译期检查、统一执行器和固定 SQLite 版本换上了 drift，生成了约 1.2 万行代码。评估当时仓库层没有一处使用 drift 的查询接口，SQL 全部经 `DriftRawDatabase` 适配器以 sqflite 的形状执行，行数据靠 94 处 `fromRow` 与约 510 处 `as 类型` 手工转换，随包 SQLite 带着 FTS5 与会话扩展，关键词检索却是 `LIKE` 扫描加每次查询在 Dart 里现建一次 BM25 索引。这三处现在都已按 [ADR-0011](adr/0011-仓库查询改用drift生成代码.md) 至 [ADR-0013](adr/0013-关键词检索改用FTS5.md) 完成：十二个仓库的常规读写使用 `.drift` 生成的类型化语句，库副本全部由 `sqlite3` 打开、`sqflite` 已从依赖里删除，关键词检索改用 FTS5 并由触发器维护索引，收益是类型安全与检索速度。流式查询与版本通知见 [ADR-0014](adr/0014-流式查询与版本通知.md)，已在 2026-11-16 实施完毕。

服务端骨架坚持“标准库优先”是对的，PostgreSQL 存储、OpenAPI 契约与登录限流这三块按 [ADR-0015](adr/0015-服务端引入代码生成与限流依赖.md) 用代码生成与 `golang.org/x` 里的现成实现做完，对象存储与附件按 [ADR-0016](adr/0016-对象存储与附件接口.md) 接上 `minio-go`，依赖口径与 ADR-0009 一致。

模型客户端、版本引擎与同步协议这三块手写得最多，但它们承载的是项目特有的语义，本文判断暂不替换，理由在第 4 节。

### 1.1 已经采纳的条目

第 1 至第 8 条与第 11 条已经写成 ADR，状态与日期见 [ADR 索引](adr/README.md#5-索引)。其中 ADR-0011 至 ADR-0013 把 [ADR-0004](adr/0004-数据层改用drift与自带sqlite.md) 的收尾工作定下来，三条都已实施完毕；ADR-0014 也已实施完毕，ADR-0015 补了 ADR-0009 的依赖口径，ADR-0016 把对象存储与附件接口定下来并已实施；第 8 条按 [ADR-0018](adr/0018-业务表主键改用UUIDv7.md) 把业务表主键改成 UUIDv7 文本，随 schema 27 一起实施完毕。第 9、10 条保持评估，没有进入排期。

## 2. 客户端：把已经引入的轮子用满

### 2.1 仓库查询改用 `.drift` 文件生成

ADR-0004 的决定是“表结构与查询在编译期就被检查”。评估时只做到了前一半：`lib/data/repository/` 下的 12 个仓库文件全部通过 `rawQuery`、`rawInsert` 一类方法执行字符串 SQL，仓库层共有 50 处 `rawQuery`、1 处 `rawInsert`、1 处 `rawUpdate` 与 1 处 `rawDelete`，`customSelect` 与 `.watch` 没有一处使用，领域模型的 `fromRow` 共有 94 处，逐列 `as String`、`as int?` 的手工转换约 510 处，列名拼错或可空性写错只能在运行时发现。生成文件已经付出了一万多行的代价，查询却没有拿到类型检查。

十二个仓库的常规读取均已迁入 `.drift` 文件，剩余的 16 处检索 SQL 涉及字面匹配和 FTS5，按 [ADR-0013](adr/0013-关键词检索改用FTS5.md) 留在证据和材料仓库。原先通过表名与字符串条件执行的 62 处写入调用也已迁入生成语句，仍由 `GuardedDatabase` 的命令事务统一执行，事务内复用同一个连接。

团队在 ADR-0004 里明确不想把 SQL 改写成 DSL，这一点与 drift 并不冲突，因为 drift 支持把原生 SQL 写在 `.drift` 文件里，由生成器在编译期解析每条语句、校验表名列名与参数类型，再生成带类型的查询方法和结果类，返回值可以直接 `.get()` 或 `.watch()`。迁移方式是按仓库逐个搬：现有 SQL 原样放进 `.drift` 文件，仓库方法改为调用生成的方法，`fromRow` 改成从生成的结果类映射到领域模型。版本引擎、备份、恢复校验与撤销里依赖动态表名、`PRAGMA` 和触发器的原生 SQL 仍按 ADR-0004 留在 `RawSql` 适配器上，因为这部分 SQL 是在运行时拼出来的，生成器帮不上忙。

这一步的代价是仓库层与对应测试都要动，而且 `.drift` 文件里的查询改了要重新生成；收益是仓库层的列名、类型和可空性错误在 `build_runner` 阶段暴露，并为 2.4 节的流式查询准备好入口。迁移顺序、写入路径与跨表事务怎么处理，见 [ADR-0011](adr/0011-仓库查询改用drift生成代码.md)，剩余仓库见[执行规划第 6 节](选型实施规划与提示词.md#6-未完成事项盘点)。

### 2.2 结束 sqflite 与 drift 并存

主库已经由 `NativeDatabase` 打开，而 `DataPackageService`、`restore_validation.dart`、`RevisionPackageService` 原来都通过 sqflite 的 `databaseFactory` 打开库副本做校验和打包，`raw_executor.dart` 里也曾保留 sqflite 的 `SqfliteRawExecutor`，40 个测试文件依赖 `sqflite_common_ffi`。同一份库文件因此被两套驱动、在 Android 上甚至是两个不同版本的 SQLite 打开：主库用随包的 SQLite，副本校验走 sqflite 的系统库，ADR-0004 想消除的版本差异在恢复路径上依然存在。

这三处已经改成直接用 `package:sqlite3` 的 `sqlite3.open` 打开副本（只读校验不需要 drift），测试改用同一套打开函数，`pubspec.yaml` 里的 `sqflite` 与 `sqflite_common_ffi` 已删除，`RawDatabase` 只留 drift 与 `SqliteRawDatabase` 两个实现。这是 ADR-0004 已经决定、当时尚未收尾的工作，现在已经按 [ADR-0012](adr/0012-结束sqflite与drift并存.md) 收尾，不需要新的方向。

### 2.3 关键词检索改用 FTS5

评估时的关键词路径分两步：仓库层对材料、对话、作答各列用 `LIKE ?` 取候选，`keyword_ranker.dart` 再把候选文本按 `chinese_tokens.dart` 的二元组规则切开，用 `bm25` 包现建一次内存索引排序、用完即弃。`memory_recall.dart` 排记忆正文时同样每次重建索引。数据量小的时候这样能用，但扫描成本随材料页数线性增长，每次查询都重建索引，而排序只能作用在已经被 `LIKE` 选出来的候选上。

客户端已用 FTS5 检索材料页、消息与作答。材料页正文和标签、消息正文、作答正文和题解及反馈使用同一套二元组规则写入索引，关键词按 `bm25()` 排序后限制候选。题号、页码和逐字摘录使用 `instr`，字面命中在融合时优先。普通写入由业务表触发器同步索引，整版恢复在事务内重建，规则与代价见 [ADR-0013](adr/0013-关键词检索改用FTS5.md)。

### 2.4 用流式查询代替手动重读

页面在每次写入之后手动调用 `_load()`，`plan_page.dart` 一个文件里就有 18 处，全项目 `await _load()` 共 62 处，`setState` 共 274 处；ADR-0007 的首屏预读又用 `dataVersion` 与进程内提交序号判断缓存是否失效。这套机制是自己维护的“表变了就通知读者”，而 drift 的流式查询正好提供这个能力：查询以 `.watch()` 订阅，相关表一有写入，drift 自动重跑查询并推送新结果。

难点在于本项目的写入大多经 `customStatement` 这类原生 SQL 进入，drift 不知道它们改了哪些表，因此不会自动通知。版本引擎恰好知道：每次提交收尾时，采集到的净变化已经按表归好类，`finishCommand` 只需要对这些表调用一次 `notifyUpdates`，撤销、恢复与清空在独占区结束时对全部业务表通知一次即可。这样页面可以订阅流而不必在每个写操作后手动重读，ADR-0007 里“按版本号判断失效”的部分也可以交给 drift。ADR-0007 里另外两条要求，即首屏多次查询共用一个共享访问范围、页面等转场结束再回填，是项目自己的时序约束，drift 不替代它们，需要在订阅流的地方继续保留。

这一项已经按 [ADR-0014](adr/0014-流式查询与版本通知.md) 实施：版本引擎在提交收尾把改到的表连同三张版本元数据表交给 `GuardedDatabase`，事务提交之后发布一次，应用服务提供跟随写入更新的整屏读法，页面用 `LiveView` 订阅，写入、撤销、导入与换库之后都不再手动重读。评估时设想的是逐条查询以 `.watch()` 订阅；实施时改为整屏读法，原因是生成语句自己会派发 drift 的更新（回滚时也派发），而页面的一屏数据来自几个查询。状态管理没有为此引入 Riverpod 一类框架，`LiveView` 加上现有的 `AppScope` 已经够用。

## 3. 服务端：骨架之后的几块

### 3.1 PostgreSQL 存取用 `pgx` 与 `sqlc`

ADR-0009 规定第三方依赖只在标准库没有对应能力时加入，而 Go 标准库没有 PostgreSQL 驱动，所以 `pgx` 是绕不过去的。存取代码用 `sqlc` 生成：它读取现有的 `internal/store/schema.sql` 与另写的查询文件，生成类型化的 Go 方法，本身只是开发期工具，不进入运行时依赖，和客户端“SQL 原样保留、由生成器做检查”的思路一致。`syncsvc` 推送时要求的 `SELECT ... FOR UPDATE` 锁定 `sync_head` 再追加，也可以直接写在查询文件里。这一项已经按 [ADR-0015](adr/0015-服务端引入代码生成与限流依赖.md) 实施：查询写在 `server/internal/store/queries/`，生成结果落在 `server/internal/store/db`，`syncsvc` 用到的 `SELECT ... FOR UPDATE` 同样写在查询文件里。

### 3.2 契约生成服务接口

`openapi.yaml` 被定为契约，处理函数原先是手写的，两边是否一致只能靠人工核对，现在改用 `oapi-codegen`：它从同一份文件生成基于标准库 `net/http` 路由的严格服务接口，请求与响应的结构体、路径参数和状态码都由生成代码约束，契约改了而实现没跟上时编译不过。它与 ADR-0009“不引入 Web 框架”不冲突，因为生成的代码仍挂在标准库的 `ServeMux` 上。客户端是否也从契约生成 Dart 代码可以晚一点再定，接口数量还少，手写成本不高。

### 3.3 登录与刷新限流

登录、注册与刷新令牌原先没有频率限制，密码哈希用的是 19 MiB 的 argon2id，被批量尝试时既有撞库风险，也会被当成拖慢服务的手段。现在按 [ADR-0015](adr/0015-服务端引入代码生成与限流依赖.md) 用 `golang.org/x/time/rate` 限流：登录与注册按来源地址共用一个令牌桶，刷新令牌先按来源地址、解析出会话之后再按账号限流。`golang.org/x/time/rate` 与已经引入的 `x/crypto` 同属官方扩展库，不需要外部组件。

### 3.4 同步主键用 UUIDv7

记忆里列为待定的“增量同步的全局唯一主键”可以直接用 UUIDv7：它按时间有序，作为 SQLite 与 PostgreSQL 的主键都不会像随机 UUID 那样打散索引，Dart 的 `uuid` 包与 Go 的 `google/uuid` 都已支持。服务端现在的 `newID()` 是 16 字节随机十六进制串，账号与会话用它没有问题，但同步数据的主键由客户端生成，两端应当约定同一种格式。按 ADR-0001 与 ADR-0002，这次改主键直接升 schema 版本、清空重建，不写迁移。

主键形态已按 [ADR-0018](adr/0018-业务表主键改用UUIDv7.md) 定为 UUIDv7 文本，并作为单独一批实施完毕，schema 27 就是这个形态：客户端没有为此新增依赖，生成写在 `app/lib/domain/rules/uuid_v7.dart`，前 48 位取毫秒时间戳、同一毫秒内的 12 位序号递增，按主键排序与按写入顺序一致，剩下的位取安全随机数；服务端的账号与会话主键由服务端生成，不随这次更换。工作单与影响清单见[执行规划第 2.6 节](选型实施规划与提示词.md#26-主键改造已完成)。

### 3.5 账号体系何时换成现成服务

只做邮箱加密码时，现有的自写实现（argon2id、只存令牌哈希、刷新令牌轮换）已经覆盖了核心要求，再接一个身份服务反而多维护一个进程。但面向国内用户的内测，很可能还要手机号验证码、微信登录、邮箱验证与找回密码，这几项各自都要对接第三方并处理风控，自写的成本会迅速超过收益。如果确定要做其中两项以上，建议改用可自建的身份服务，例如 Go 编写、内置国内常见登录方式的 Casdoor，或者界面与文档更完整的 Logto，由它签发令牌，知新服务端只做校验。这件事改起来会影响账号表与客户端登录流程，属于需要 ADR 的决定。

### 3.6 附件与备份走预签名地址

ADR-0009 已经定了 S3 兼容对象存储与 MinIO，ADR-0016 决定客户端用 `minio-go`，它同样适用于阿里云 OSS、腾讯云 COS 等兼容接口。预签名地址让字节由客户端直传对象存储、不经过 `zhixin-api` 进程，可以省掉几十兆备份包带来的请求体上限、超时与内存占用；但它的代价是契约要改成“先换地址再直传”，对象存储还要对客户端可达，公网地址、证书与 CORS 都要单独配。客户端的登录与备份还没接，ADR-0016 因此先把契约里的三条路径按服务端代理解释实现，等附件接上、带宽成为实际瓶颈时再按这一节重新评估。

## 4. 评估过、但建议暂不替换的

模型客户端 `llm_client.dart` 有 1,835 行，手写了 Chat Completions、Responses 与 Anthropic Messages 三种线格式和 SSE 解析。社区已有 `openai_dart` 与 `anthropic_sdk_dart` 两个维护活跃的包，但换过去仍要两套依赖再加一层适配；更关键的是现有代码里有大量服务商差异处理，例如 DeepSeek 默认开启的思考模式、`max_tokens` 与 `max_completion_tokens` 的分歧，类型化 SDK 往往不暴露这些厂商私有字段。服务端代理只转发 Chat Completions，而客户端从 2026-11-22 起只连知新服务，因此客户端只剩一种线格式，见 [ADR-0050](adr/0050-客户端统一为知新服务.md)。现有实现可用、有测试，替换的收益主要是少维护几百行解析代码，抵不过迁移风险，所以建议保留。

版本引擎用触发器把 14 张登记进版本采集的业务表的净变化写进暂存表，再合并成提交，撤销与恢复都建立在它上面（表清单见 [01 第 2 节](01-ER数据模型.md#2-实体总览)）；引擎、撤销、版本包与附件的代码加上 `revision_package.dart` 合计约 3,600 行，并有完整测试。随包 SQLite 同时开启了 `SQLITE_ENABLE_SESSION` 与 `SQLITE_ENABLE_PREUPDATE_HOOK`，`package:sqlite3` 也提供 `Session` 与 `Changeset` 接口，会话扩展生成的变更集可以直接取反用于撤销，也适合当同步的传输格式。但换成会话扩展等于重写引擎，系统库又未必开启会话扩展，测试环境也要一并改。建议在设计云同步的冲突规则时把变更集作为备选格式评估一次，而不是现在替换。

PowerSync、ElectricSQL 一类同步框架可以对接 drift，但它们要接管写入路径（PowerSync 用视图加上传队列），与版本引擎的提交、撤销语义和服务端“单账号线性提交序列”的设计都冲突，采用它们意味着推翻 ADR-0008 的同步方案，所以不建议。

Riverpod、`go_router` 与 `freezed` 都是常见选择，但在这个项目里收益不大：只有 Android 一个平台、没有深链接，命令式的 `Navigator` 加上统一的 `ZhixinPageTransitionsBuilder` 已经够用；状态主要在单页内，流式查询落地后手动刷新会大幅减少；领域模型的手工转换在 2.1 节之后会被生成的结果类取代，再加一层 `freezed` 只会增加生成代码。

如果云备份上线后希望本机库也加密，随包库的构建钩子可以把 `source` 切到 SQLite3 Multiple Ciphers，不需要换驱动，这一项等账号与备份落地后再议。

## 5. 已经用对、保持现状的

界面层的 Forui 与 `forui_lucide`、安排页的 `calendar_view`、框选用的 `crop_your_image` 加纯 Dart 的 `image`、流式 Markdown 的 `gpt_markdown`、密钥存储的 `flutter_secure_storage`、数据包的 `archive`、自建 Sentry、向量索引的 `zvec`，以及服务端用 `x/crypto` 的 argon2id，都是在合适的位置用了合适的库，本文不建议改动。`motion.dart` 虽然是手写，但它实现的是项目自己定下的克制动效口径，官方 `animations` 包的过渡样式反而更花哨，保留更合适。`docx_import.dart` 用 `archive` 与 `xml` 手工解析 OOXML，Dart 生态里没有同时处理公式命名空间与分段规则的成熟包，同样保留。
