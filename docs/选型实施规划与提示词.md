## 2. 批次规划

每一批都能单独提交、单独验证，做完一批 `main` 都是可用状态。ADR-0011 的检索仓库迁移以 FTS5 为前提，服务端工程的完成情况见第 2.5 节。

### 2.1 第一批：关键词检索改用 FTS5（ADR-0013）

三张 FTS5 索引随业务行写入，由版本引擎在整版恢复和导入之后重建。索引字段、排序与切词规则见 [ADR-0013](adr/0013-关键词检索改用FTS5.md)。Windows 使用随包 SQLite，检索、分页和恢复用例随客户端测试一起运行。

### 2.2 第二批：仓库查询迁进 `.drift` 文件，第一批（ADR-0011）

**要做的事**

1. 新建 `app/lib/data/db/drift/queries/`，按仓库分文件；每条语句一个名字，现有 SQL 原样放进去，参数用 drift 的命名参数。
2. 先迁移不依赖检索的 3 个仓库：`schedule_conflicts.dart`、`study_plan_repository.dart`、`task_repository.dart`，只改读方法，写入路径与事务边界不动。
3. 生成器在 `build_runner` 阶段检查表名、列名、参数与结果列的可空性；生成的结果行映射成现有领域模型，`fromRow` 只在字段不同名或需要解析派生值时保留。
4. 生成文件提交入库，CI 的生成核对与 `app_database.g.dart` 一致。
5. `versionedTableNames` 之外的原生 SQL（版本引擎、备份、恢复校验、撤销、向量索引）不动。

**做之前要知道的事**

- `GuardedDatabase.transaction` 与命令事务仍要独占执行，生成代码要能挂在同一个连接上；如果 drift 的生成方法要求 `TransactionExecutor`，在事务回调里取 `app.transactionExecutor()`，不要在事务内另开连接。
- `study_plan_repository.dart` 引用了 `task_repository.dart` 的方法，两个仓库同批迁移，避免跨批改签名。
- 这一批最容易出现的是 SQLite 动态类型带来的可空性差异（`SUM`、`MAX` 在生成结果里可空），遇到就以生成结果为准修领域模型。

**做完的标准**

三条检查通过；三个仓库里不再有 `rawQuery`、`rawInsert` 一类字符串 SQL；对应测试的预期不变；提交正文写明迁移了哪些方法与生成代码的规模变化。

**提示词**

```text
任务：按 ADR-0011 把仓库层查询迁到 drift 的 .drift 文件，完成第一批（schedule_conflicts.dart、study_plan_repository.dart、task_repository.dart 的读方法）。角色同 .agent-role。仓库在 D:\Workspace\zhixin，先 git pull --rebase，读 docs/adr/0011-仓库查询改用drift生成代码.md、docs/轮子与技术选型评估.md 第 2.1 节、app/lib/data/db/drift/app_database.dart、app/lib/data/db/drift/drift_raw.dart、app/lib/data/db/guarded_database.dart、app/lib/data/db/write_transactions.dart 以及这三个仓库文件与它们的测试。

约束：SQL 原样保留在 .drift 文件里，不改写成 Dart DSL；写入路径、事务边界、DatabaseGate 的读写协调都不动；生成文件入库，与 app_database.g.dart 同一套提交流程；一次提交只做一件事；提交前跑 dart format lib test、flutter analyze、flutter test 并全部通过。

要做：新建 app/lib/data/db/drift/queries/ 按仓库分文件放语句；三个仓库的读方法改为调用生成方法，结果行映射成现有领域模型；fromRow 只在字段不同名或需要解析派生值时保留；遇到可空性差异以生成结果为准修模型，不保留手工转换；跑 build_runner 重新生成并提交生成文件。

完成从提交到推送的全部流程，最后汇报：迁移了哪些方法与语句数量、生成代码增加多少行、三条检查的结果、有没有可空性或类型上与原来不同、测试有没有改动及原因。
```

### 2.3 第三批：仓库查询迁进 `.drift` 文件，第二批（ADR-0011）

**要做的事**

把剩下 9 个仓库文件（`assessment_repository.dart`、`attempt_repository.dart`、`conversation_repository.dart`、`evidence_repository.dart`、`material_repository.dart`、`memory_repository.dart`、`schedule_repository.dart`、`settings_repository.dart`、`study_repository.dart`）的读写方法与跨表事务按仓库逐个迁移，一个仓库一个提交。检索仓库（`evidence_repository.dart`）的 `MATCH` 查询依赖第一批的 FTS5，所以它排在这一批的最后一个。

**做之前要知道的事**

- 14 处 `_db.transaction` 必须在迁移后仍然只形成一个提交，版本引擎的 `beginCommand` 与 `finishCommand` 仍在事务里包住它们。
- `REPLACE` 的禁止由 `WriteTx` 不提供该模式来保证，生成代码只能生成 `INSERT`、`INSERT OR IGNORE` 与 `UPDATE`，不要用 `customInsert` 绕开。
- 每迁一个仓库都要跑一遍那个仓库与引用它的测试，不要攒到最后一起跑。

**做完的标准**

三条检查通过；仓库层不再有 `rawQuery`、`rawInsert`、`rawUpdate`、`rawDelete`；`fromRow` 只剩字段不同名或派生值的位置；每个仓库一个提交，提交正文写明迁移范围。

**提示词**

```text
任务：按 ADR-0011 完成第二批仓库迁移，把剩下 9 个仓库文件的读写方法与跨表事务迁到 .drift 文件，一个仓库一个提交。角色同 .agent-role。仓库在 D:\Workspace\zhixin，先 git pull --rebase 确认第一批已经合入，读 docs/adr/0011-仓库查询改用drift生成代码.md、docs/adr/0013-关键词检索改用FTS5.md、app/lib/data/db/guarded_database.dart、app/lib/data/db/write_transactions.dart 与 app/lib/data/repository/ 下的全部文件。

约束：写入路径、事务边界与版本引擎的 beginCommand/finishCommand 不动；跨表事务仍只形成一个提交；不提供 REPLACE；检索仓库的 MATCH 查询最后迁；每个仓库单独提交，提交前跑 dart format lib test、flutter analyze、flutter test 并全部通过。

要做：按仓库迁移，先做 assessment、attempt、conversation、material、memory、schedule、settings、study，最后做 evidence；证据仓库迁移可由 drift 检查的查询，FTS5 查询的归属按 ADR-0013 第 8 条执行。字面查找继续使用绑定参数的 instr。

完成从提交到推送的全部流程，最后汇报：每个仓库迁移了哪些方法、仓库层还剩多少原生 SQL 及为什么、三条检查的结果、有哪些行为差异。
```

### 2.4 可选：流式查询与版本通知（ADR-0014）

ADR-0014 仍是提议。按它的顺序，ADR-0011 完成之后先在一个页面（“安排”或“记录”）试做，确认与 `DatabaseGate` 的读写协调、恢复时的执行器替换都不冲突，再把状态改成已采纳。试做的提示词等第二批推上去之后按当时的代码写，现在先不准备，免得照着旧代码写出一份对不上的工作单。

### 2.5 可并行：服务端（ADR-0015）

服务端已接入 PostgreSQL，使用 sqlc 生成存取代码，CI 在 PostgreSQL 17 中验证并发追加、幂等重试、备份保留与账号清理。OpenAPI 生成标准库路由和严格接口，认证限流通过 `Retry-After` 返回等候时间。备份文件当前使用配置的持久目录，S3 兼容对象存储和附件接口的后续工作见 [服务端工程说明](../server/README.md)。

## 4. 每一批都要守的约定

- 开工先 `git pull --rebase`，开工前读一遍 ADR 的现行原文，不凭本文转述执行；本文与 ADR 冲突时以 ADR 为准，并回头改本文。
- 一次提交只做一件事，标题按 [CONTRIBUTING 第 1 节](../CONTRIBUTING.md#1-标题格式)，正文写原因、影响范围与数据处置。
- 提交前跑该批对应的一整套检查，`main` 任何时刻都要能构建；做不完的留在分支上。
- 动了 `app/` 就同步 [01 第 6 章](01-ER数据模型.md#6-索引与典型查询)、`app/README` 的数据一节与评估里对应小节，不要只改代码。

## 5. 另开任务时怎么接上

新任务开始时把 `.agent-role` 的角色一并说明，然后贴对应批次的提示词即可。提示词里已经包含仓库路径、要读的文件、约束、检查命令与汇报项，不需要额外补上下文。如果角色或成员有变化，先按 [AGENTS 第 0 节](../AGENTS.md#0-你是哪个角色) 更新 `.agent-role` 再开工。

接上一个任务的成果时，先确认是不是从同一批之后开始，例如第一批只做了 FTS5 而没有动仓库，第二批的提示词照原样可用；如果上一位实施者在中途改了做法（例如为了 Windows 测试改成随包库），先读那次的提交正文与改过的 ADR，再决定这一批要不要调整。
