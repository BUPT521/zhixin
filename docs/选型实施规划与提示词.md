## 2. 批次规划

每一批都能单独提交、单独验证，做完一批 `main` 都是可用状态。批次之间只有一处硬依赖：ADR-0011 的检索仓库迁移依赖 ADR-0013 先落地，其余可以按编号顺序做，也可以单独做第 2.5 节的服务端。

### 2.1 第一批：关键词检索改用 FTS5（ADR-0013）

**要做的事**

1. 新建 `app/lib/data/db/fts.dart`，集中放三张 FTS5 表的建表语句、触发器语句与查询索引的方法，测试与生产共用这一份。
2. 在 `material_page`、`message`、`attempt` 上建三张 FTS5 外部内容表（`material_page_fts`、`message_fts`、`attempt_fts`），`content=` 指向业务表；索引列不映射业务表列名，用默认参数建表，查询只按 `MATCH` 与 `bm25()`，不选索引列的值，避免读到只存在于索引里的名字。
3. 二元组在 SQL 里用 `replace()` 拼接，口径与 `bm25Tokens` 一致：先按空白切开，去掉非字母、非数字字符，连续片段取相邻两字，再追加整段本身；带点号、连字符的片段用双引号包起来写进索引列，保证 FTS5 把它当一个词。
4. 触发器在业务表 AFTER INSERT、AFTER UPDATE OF 目标列、AFTER DELETE 上同步索引行。安装时机在 `installRevisionSchema` 之前，因为打开库时版本引擎会删除库里所有非 `sqlite_` 前缀的触发器再重建，装晚了会被清掉。
5. 把三张 FTS5 表与它们的影子表从 `versionedTableNames` 与 `allowedDatabaseTableNames()` 里排除，让恢复校验的“不认识的表”检查、版本采集与历史裁剪都不把它们当业务表。
6. `evidence_repository.dart`、`material_repository.dart`、`conversation_repository.dart` 的关键词查询改成 `MATCH`，`keyword_ranker.dart` 直接读 `bm25()` 的排序，`memory_recall.dart` 去掉 `bm25` 包，改为在候选内按同一套切词规则算分；`EvidenceService` 的 `bm25Ranking` 参数一并删除。
7. 从 `pubspec.yaml` 删除 `bm25`。

**做之前要知道的三件事**

- Windows 上的 `winsqlite3.dll` 不带 FTS5。本机跑测试时涉及 FTS 的用例会直接报 `no such module: fts5`，所以要么让 `sqlite3` 在 Windows 也用随包库（改 `pubspec.yaml` 的 `hooks` 段落，代价是下载偶发失败时要重试），要么给 FTS 用例单独 `skip` 并在 CI 的 Linux 任务上验证。选哪种在提交正文里写清，ADR-0013 的“代价与边界”也同步改。
- `schema_doc_test.dart` 会比对 [01 第 6 章](01-ER数据模型.md#6-索引与典型查询) 与代码里的索引。FTS5 表不是 `CREATE INDEX`，只要第 6 章不写成 `表(列)` 的形式就不会被当成索引比对，但新增的 FTS 说明要写清楚不参与版本采集。
- 检索结果会变多、顺序也会变，`search_service_test.dart`、`literal_lookup_test.dart`、`memory_recall_test.dart` 的预期要逐条核对，不能只把断言放宽。

**做完的标准**

`dart format`、`flutter analyze`、`flutter test` 三条通过；检索相关用例的预期按新行为更新并在提交正文写明前后差异；01 第 6 章、`app/README` 的数据一节、评估第 2.3 节、ADR-0013 的状态与实际做法一致；`bm25` 从依赖和锁文件里消失。

**提示词**

```text
任务：按 ADR-0013 把关键词检索改用 SQLite FTS5，完成第一阶段（客户端检索）。角色同 .agent-role（主开发 / 服务端）。仓库在 D:\Workspace\zhixin，先 git pull --rebase，读 docs/adr/0013-关键词检索改用FTS5.md、docs/轮子与技术选型评估.md 第 2.3 节、docs/01-ER数据模型.md 第 6 章、app/lib/data/repository/evidence_repository.dart、app/lib/application/keyword_ranker.dart、app/lib/application/memory_recall.dart、app/lib/domain/rules/chinese_tokens.dart、app/lib/domain/rules/query_shape.dart、app/lib/data/revisions/revision_engine.dart 的 installRevisionSchema。

约束：开发期不写迁移、不保留兼容分支（ADR-0001、ADR-0002）；只在 app/ 下改，不碰 server/；一次提交只做一件事；提交前必须跑 dart format lib test、flutter analyze、flutter test 三条并全部通过；不新增运行期依赖；SQL 口径与 bm25Tokens 保持一致。

要做：新建 app/lib/data/db/fts.dart 放建表、触发器与查询方法；为 material_page、message、attempt 建 FTS5 外部内容表，索引列由触发器用 replace() 拼二元组写入；安装时机放在版本引擎安装采集触发器之前；把 FTS5 表与影子表从 versionedTableNames 与 allowedDatabaseTableNames() 排除；证据、材料、对话仓库的关键词查询改用 MATCH 加 bm25()；记忆正文在候选内排序；从 pubspec.yaml 删除 bm25。

先处理 Windows 上 winsqlite3.dll 不带 FTS5 的问题，选一种做法（改用随包库，或单独跳过并在 CI 的 Linux 任务上验证）并在提交正文与 ADR-0013 里写清。改完逐条核对检索相关用例的预期，不要放宽断言来迁就新结果。

完成从提交到推送的全部流程，最后汇报：改了哪些文件、三条检查的结果、检索结果与改动前的差异、FTS5 在测试环境里的可用性怎么解决的、哪些文档同步改了。
```

### 2.2 第二批：仓库查询迁进 `.drift` 文件，第一批（ADR-0011）

**要做的事**

1. 新建 `app/lib/data/db/drift/queries/`，按仓库分文件；每条语句一个名字，现有 SQL 原样放进去，参数用 drift 的命名参数。
2. 先迁移不依赖检索的 3 个仓库：`schedule_conflicts.dart`、`study_plan_repository.dart`、`task_repository.dart`，只改读方法，写入路径与事务边界不动。
3. 生成器在 `build_runner` 阶段检查表名、列名、参数与结果列的可空性；生成的结果行映射成现有领域模型，`fromRow` 只在字段不同名或需要解析派生值时保留。
4. 生成文件提交入库，CI 的生成核对与 `app_database.g.dart` 一致。
5. `versionedTableNames` 之外的原生 SQL（版本引擎、备份、恢复校验、撤销、向量索引）不动。

**做之前要知道的事**

- `GuardedDatabase.transaction` 与命令事务仍要独占执行，生成代码要能挂在同一个连接上；如果 drift 的生成方法要求 `TransactionExecutor`，在事务回调里取 `app.transactionExecutor()`，不要在事务内另开连接。
- `study_plan_repository.dart` 引用了 `task_repository.dart` 的方法，两个仓库同批迁移，避免跨批改签名。
- 这一批最容易出现的是 SQLite 动态类型带来的可空性差异（`SUM`、`MAX` 在生成结果里可空），遇到就以生成结果为准修领域模型。

**做完的标准**

三条检查通过；三个仓库里不再有 `rawQuery`、`rawInsert` 一类字符串 SQL；对应测试的预期不变；提交正文写明迁移了哪些方法与生成代码的规模变化。

**提示词**

```text
任务：按 ADR-0011 把仓库层查询迁到 drift 的 .drift 文件，完成第一批（schedule_conflicts.dart、study_plan_repository.dart、task_repository.dart 的读方法）。角色同 .agent-role。仓库在 D:\Workspace\zhixin，先 git pull --rebase，读 docs/adr/0011-仓库查询改用drift生成代码.md、docs/轮子与技术选型评估.md 第 2.1 节、app/lib/data/db/drift/app_database.dart、app/lib/data/db/drift/drift_raw.dart、app/lib/data/db/guarded_database.dart、app/lib/data/db/write_transactions.dart 以及这三个仓库文件与它们的测试。

约束：SQL 原样保留在 .drift 文件里，不改写成 Dart DSL；写入路径、事务边界、DatabaseGate 的读写协调都不动；生成文件入库，与 app_database.g.dart 同一套提交流程；一次提交只做一件事；提交前跑 dart format lib test、flutter analyze、flutter test 并全部通过。

要做：新建 app/lib/data/db/drift/queries/ 按仓库分文件放语句；三个仓库的读方法改为调用生成方法，结果行映射成现有领域模型；fromRow 只在字段不同名或需要解析派生值时保留；遇到可空性差异以生成结果为准修模型，不保留手工转换；跑 build_runner 重新生成并提交生成文件。

完成从提交到推送的全部流程，最后汇报：迁移了哪些方法与语句数量、生成代码增加多少行、三条检查的结果、有没有可空性或类型上与原来不同、测试有没有改动及原因。
```

### 2.3 第三批：仓库查询迁进 `.drift` 文件，第二批（ADR-0011）

**要做的事**

把剩下 9 个仓库文件（`assessment_repository.dart`、`attempt_repository.dart`、`conversation_repository.dart`、`evidence_repository.dart`、`material_repository.dart`、`memory_repository.dart`、`schedule_repository.dart`、`settings_repository.dart`、`study_repository.dart`）的读写方法与跨表事务按仓库逐个迁移，一个仓库一个提交。检索仓库（`evidence_repository.dart`）的 `MATCH` 查询依赖第一批的 FTS5，所以它排在这一批的最后一个。

**做之前要知道的事**

- 14 处 `_db.transaction` 必须在迁移后仍然只形成一个提交，版本引擎的 `beginCommand` 与 `finishCommand` 仍在事务里包住它们。
- `REPLACE` 的禁止由 `WriteTx` 不提供该模式来保证，生成代码只能生成 `INSERT`、`INSERT OR IGNORE` 与 `UPDATE`，不要用 `customInsert` 绕开。
- 每迁一个仓库都要跑一遍那个仓库与引用它的测试，不要攒到最后一起跑。

**做完的标准**

三条检查通过；仓库层不再有 `rawQuery`、`rawInsert`、`rawUpdate`、`rawDelete`；`fromRow` 只剩字段不同名或派生值的位置；每个仓库一个提交，提交正文写明迁移范围。

**提示词**

```text
任务：按 ADR-0011 完成第二批仓库迁移，把剩下 9 个仓库文件的读写方法与跨表事务迁到 .drift 文件，一个仓库一个提交。角色同 .agent-role。仓库在 D:\Workspace\zhixin，先 git pull --rebase 确认第一批已经合入，读 docs/adr/0011-仓库查询改用drift生成代码.md、docs/adr/0013-关键词检索改用FTS5.md、app/lib/data/db/guarded_database.dart、app/lib/data/db/write_transactions.dart 与 app/lib/data/repository/ 下的全部文件。

约束：写入路径、事务边界与版本引擎的 beginCommand/finishCommand 不动；跨表事务仍只形成一个提交；不提供 REPLACE；检索仓库的 MATCH 查询最后迁；每个仓库单独提交，提交前跑 dart format lib test、flutter analyze、flutter test 并全部通过。

要做：按仓库迁移，先做 assessment、attempt、conversation、material、memory、schedule、settings、study，最后做 evidence；证据仓库的检索查询直接写 MATCH 与 bm25()，不要再保留 LIKE 候选路径。

完成从提交到推送的全部流程，最后汇报：每个仓库迁移了哪些方法、仓库层还剩多少原生 SQL 及为什么、三条检查的结果、有哪些行为差异。
```

### 2.4 可选：流式查询与版本通知（ADR-0014）

ADR-0014 仍是提议。按它的顺序，ADR-0011 完成之后先在一个页面（“安排”或“记录”）试做，确认与 `DatabaseGate` 的读写协调、恢复时的执行器替换都不冲突，再把状态改成已采纳。试做的提示词等第二批推上去之后按当时的代码写，现在先不准备，免得照着旧代码写出一份对不上的工作单。

### 2.5 可并行：服务端（ADR-0015）

服务端三项与客户端互不依赖，可以另开一个任务按“PostgreSQL 存储 → 契约生成 → 限流”的顺序做，每一项都是一次提交。提示词：

```text
任务：按 ADR-0015 给 server/ 补 PostgreSQL 存储、契约生成与限流。角色同 .agent-role（主开发 / 服务端）。仓库在 D:\Workspace\zhixin，先 git pull --rebase，读 docs/adr/0009-API后端采用Go与分层框架.md、docs/adr/0015-服务端引入代码生成与限流依赖.md、server/README.md、server/api/openapi.yaml、server/internal/store/schema.sql 与 server/internal/ 下各业务包的存储接口。

约束：分层与依赖方向按 ADR-0009，业务包之间不互相引用存储实现；生成代码入库，CI 增加生成核对；不引入 Web 框架；契约改了与两端代码放进同一个 push；提交前跑 gofmt -l .、go vet ./...、go test ./... 并全部通过。

要做：一、引入 pgx/v5 与 sqlc，查询写进 server/internal/store/queries/，按 schema.sql 生成存取代码，syncsvc 推送的 SELECT ... FOR UPDATE 写成单事务查询；二、用 oapi-codegen 生成标准库路由的服务接口，适配层只做类型转换与 problem+json 映射；三、用 golang.org/x/time/rate 给登录、注册按来源地址限流，刷新令牌按账号与来源地址限流。每一项一个提交。

完成从提交到推送的全部流程，最后汇报：新增依赖与工具、生成文件、三项各自的测试覆盖、限流参数与 429 的响应格式、哪些文档同步改了。
```

## 3. 建议顺序与工期

## 4. 每一批都要守的约定

- 开工先 `git pull --rebase`，开工前读一遍 ADR 的现行原文，不凭本文转述执行；本文与 ADR 冲突时以 ADR 为准，并回头改本文。
- 一次提交只做一件事，标题按 [CONTRIBUTING 第 1 节](../CONTRIBUTING.md#1-标题格式)，正文写原因、影响范围与数据处置。
- 提交前跑该批对应的一整套检查，`main` 任何时刻都要能构建；做不完的留在分支上。
- 动了 `app/` 就同步 [01 第 6 章](01-ER数据模型.md#6-索引与典型查询)、`app/README` 的数据一节与评估里对应小节，不要只改代码。

## 5. 另开任务时怎么接上

新任务开始时把 `.agent-role` 的角色一并说明，然后贴对应批次的提示词即可。提示词里已经包含仓库路径、要读的文件、约束、检查命令与汇报项，不需要额外补上下文。如果角色或成员有变化，先按 [AGENTS 第 0 节](../AGENTS.md#0-你是哪个角色) 更新 `.agent-role` 再开工。

接上一个任务的成果时，先确认是不是从同一批之后开始，例如第一批只做了 FTS5 而没有动仓库，第二批的提示词照原样可用；如果上一位实施者在中途改了做法（例如为了 Windows 测试改成随包库），先读那次的提交正文与改过的 ADR，再决定这一批要不要调整。
