# ADR-0060 一轮回答的预算与按讨论分配模型来源

## 状态

已采纳（2026-11-24）。补充 [ADR-0059](0059-模型路由按故障范围切换与恢复.md) 决定 1 的组内顺序与决定 4 的配置比例口径，契约与实现见 [模型调度与回答恢复实施方案](../模型调度与回答恢复实施方案.md) 第 4、5 节。

## 日期

2026-11-24

## 背景

客户端按一轮回答计算等待时间，服务端却按每次请求与每次尝试分别计时：服务端等待上游响应头 60 秒、流式空闲 90 秒，客户端等待首个有效输出 30 秒，客户端先结束等待时，服务端还在等下一条来源，这一轮已经交付不了结果。流式响应在收到响应头时就写出 200，上游随后只给开场事件就断开时，本可以换来源也换不了。同组路由按权重逐请求随机，一条讨论的追问与工具步骤会落到不同来源，上游已经处理过的提示词前缀无法复用。

## 决定

1. 客户端在请求头 `X-Zhixin-Round-Budget-Ms` 里带这一轮剩下的时间，单位毫秒，从用户发出提问开始计算，工具调用后的后续请求沿用同一份预算。服务端按 `ZHIXIN_LLM_ROUND_BUDGET_MAX` 截断这个值，整段回答、流式空闲等待与每次尝试等待首个有效输出都不超过它；候选还有多条时，等待首字的份额按还能尝试的候选数平分，首发与备用因此一起落在同一轮预算内。流式聊天等待首字用 `ZHIXIN_LLM_FIRST_OUTPUT_TIMEOUT`（默认 20 秒），嵌入仍用 `ZHIXIN_LLM_HEADER_TIMEOUT`。

2. 流式响应在交付正文、拒答或带有完整参数的函数调用之前暂存先行事件，暂存受 64 KiB 与本次尝试剩余首字时间约束；如果这一阶段出现断开、失败、空回答或者暂存达到上限，服务端在预算内换下一条候选，并按已获得的用量结算。客户端收到正文、拒答或完整函数调用之后，本次流绑定当前来源，后续中断由客户端保存已经收到的部分。输出达到上限时代理交付截断事件，并单独记录用量与结果。

3. 这一轮预算在没有任何来源交付有效输出之前用完时，服务端中断上游请求并回 504 `upstream_failed`，这次尝试按取消记账、不增加来源失败数。所有候选都在交付之前失败、又没有可以转给客户端的上游状态时，代理回 502 `upstream_failed`，并在 `extra.reason` 写 `candidates_exhausted`；最后一次上游返回 5xx 或 429 时仍按该状态返回。

4. 客户端在请求头 `X-Zhixin-Session-Id` 里带一条讨论的稳定标识，最长 64 个字符。服务端按账号把标识再散列一次，只在代理内参与路由选择，日志与上游不携带原值；空白、超长或没有这个头时按没有处理。同一优先组内有多条可用路由时，带标识的请求按会话与权重排出一条确定的顺序，同一会话的追问、工具步骤与重试都从同一个来源开始；会话进入冷却或来源停用时，按原顺序落到下一条可用候选。没有标识的请求保持原来的按权重随机排列。

5. 同组权重由每次请求的抽签比例改为会话配置比例，后台把配置比例、首选预览与实测请求量分开显示：配置比例表示会话落到各条路由的比例，首选预览按权重给出概率，实际请求量还受会话长短与故障切换影响。

## 代价与边界

会话分配把负载差异从逐请求随机变成按会话分布，长会话会放大某条来源的请求量与 token 消耗，出现持续排队后要按实测请求量增加主路由，不能只看配置比例。会话标识由客户端生成并随数据同步，同一讨论换设备后仍然稳定；同一账号把标识改成另一个值会被分到另一条来源，这属于客户端的错误用法，服务端不做纠正。

首字时限缩短会让部分仍可完成的慢请求提前换路，需要按真实时延与备源耗时校准。先行事件暂存在实例内存里，同时等待首字的请求数乘上 64 KiB 是它的上限，纳入 `ZHIXIN_LLM_MAX_INSTANCE_BYTES` 的约束范围之外单独计算。预算截断到 `ZHIXIN_LLM_ROUND_BUDGET_MAX` 之后，客户端给得再大也不会让服务端等更久。

## 替代方案

- 只按账号散列分配：实现更简单，但同一账号的全部讨论会集中到一条来源，账号少时负载偏差比逐请求随机更大，没有采纳。
- 客户端直接指定来源：会暴露来源标识与配置，换设备或改配置后不一致，也没有采纳。
- 按提示词前缀散列分配：把请求内容带进调度，前缀变化或上下文删减之后分配会漂移，同一讨论仍然换来源，没有采纳。
- 服务端按响应头与首字分别计时、不做统一预算：两端的期限继续各算各的，客户端先结束等待的问题仍然存在，没有采纳。
