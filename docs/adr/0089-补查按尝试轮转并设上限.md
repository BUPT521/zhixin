# ADR-0089 补查按尝试轮转并设上限

- 状态：已采纳（2026-11-27，服务端同日实施）；`nowpay_charge` 增加 `attempts` 与 `last_attempt_at` 两列、`status` 增加 `abandoned` 取值（纯新增列，约束放宽），补充 [ADR-0088](0088-核销流水的本地认领.md) 的补查口径
- 日期：2026-11-27

## 背景

全局补查每十分钟跑一次，按创建时间从最老的取五十条：`status IN ('pending', 'processing') AND created_at < now() - 5 minutes ORDER BY created_at, id LIMIT 50`。它为队列满、进程重启与请求路径上的补查遗漏兜底，但只要取到的流水本身没有结论，下一轮取的还是同一批。

超时、网关错误与未知结果都按原状态保留（[meter.go](../../server/internal/nowpay/meter.go) 的 `apply`）：扣减可能已经发生，换号重扣会多收一次，所以这类流水只能等下一次补查。积压五十条这样的流水之后，每十分钟重复取同一批，更晚的流水永远轮不到；保留期是一百八十天，这段时间里这些账号的流水一直停在待确认状态，对账日志里的 `pending` 只增不减，也说不清哪些需要人工看。

## 决定

取数、计数与终点一起改：

1. 取数按上一次尝试时刻轮转：`ORDER BY last_attempt_at ASC NULLS FIRST, created_at, id`。试过的流水排到后面，从没试过的先取，积压时更晚的流水下一轮就轮得到，不再由创建时间决定先后。
2. 补查在入队之前给每笔流水记一次尝试：`attempts` 加一、`last_attempt_at` 推到当前时刻。一次补查对同一笔流水最多记一次，队列满、这一份没排上也只记这一次。
3. 上限是 `maxSettleAttempts = 100`。加完之后超过上限的那一次把流水落成 `abandoned` 并写一条备注，补查不再发送、也不再取它。每十分钟一轮、每轮最多记一次，一百次至少是十六个多小时；积压越大轮转越慢，实际时间更长，几个小时的网关故障不会把流水判死。

`abandoned` 是新加的终态，不记 `failed`。`failed` 表示确认没有扣减，`DailyChargeTotals` 不再把它计入当天已申请量，下一次结算会按差额重新申请那一笔；结果未知的流水记成 `failed` 就等于再申请一次，而第一次可能已经扣过。`abandoned` 在本地按已经申请处理：`PointLedgerWithBalance` 把它算进未反映的核销，可用积分少这一块，保留期与 `succeeded`、`failed` 一样按 `updated_at` 清理。宁可少放行，也不重复扣款。

请求路径上的 `Resume` 不记尝试次数，也不受上限约束：它按账号取最多四条，占的是这个账号自己的请求，不会挤掉别人的流水；补查把流水落成 `abandoned` 之后，`Resume` 的查询只认 `pending` 与 `processing`，自然也不再排它。

启动检查多两项：`attempts` 与 `last_attempt_at` 缺列拒绝启动，`status` 的检查约束不含 `abandoned` 同样拒绝启动。缺约束时到上限的流水落不成终态，积压会重新变成每十分钟重复取同一批。

## 代价与边界

每次补查每笔流水多一次按主键的条件更新，代价与认领同一量级。

尝试记在入队之前，队列满时这一份没有排上但尝试已经记下；一次补查对同一笔只记一次，最多一轮记一次，不影响上限的时间量级。

被放弃的流水不再自动核销，需要人工核对即刻收一侧的扣减之后处理，后台的积分一节对它显示“不再补查”。这是这条决定的边界：上限换来的是补查不会被少数流水堵死，代价是这些流水从此只靠人工收尾。

上限按补查轮次算，不按墙钟时间。积压越大轮转越慢，放弃得也越晚；这是有意的，积压时恰恰不该批量判死。

多实例部署时每个进程各记各的尝试，上限会更早到达。服务端目前按单实例部署，两个进程同时跑的时候最多把放弃提前到一半的时间量级，方向仍然是不再多扣款。

## 替代方案

只按上一次尝试时刻轮转，不设上限。没有采纳：流水仍然会永远停在待确认状态，对账日志里的 `pending` 永远清不掉，也说不清哪些需要人工看。

超过上限记 `failed`。没有采纳：`failed` 不计入当天已申请量，下一次结算按差额重新申请，可能重复扣款。

按创建时间分页（`created_at` 大于上一次的游标）取。没有采纳：要记住游标，进程重启就丢；而且流水补上结论之后分页位置还要跟着数据变，比按尝试时刻排序复杂。

按墙钟时间判死（例如创建超过七天不再补查）。没有采纳：网关故障期间创建的流水会在故障结束之后被整批判死，而它们本来可以补上；按次数算与故障时长解耦。

## 影响

- 表结构：[schema.sql](../../server/internal/store/schema.sql) 的 `nowpay_charge` 增加 `attempts`（整数、不为负、默认 0）与 `last_attempt_at`（可空），`status` 的检查约束增加 `abandoned`；部分索引 `nowpay_charge_unsettled_created_idx` 换成 `nowpay_charge_retry_idx (last_attempt_at NULLS FIRST, created_at) WHERE status IN ('pending','processing')`。已有实例按[运维手册](../../server/运维手册.md#411-即刻收积分包的上线与回滚)的增量语句改，启动检查缺列或缺约束时拒绝启动。
- 查询：[queries/nowpay.sql](../../server/internal/store/queries/nowpay.sql) 的 `UnsettledChargesGlobal` 改按轮转排序，新增 `NoteChargeAttempt`，`DeleteTerminalCharges` 与 `PointLedgerWithBalance` 认 `abandoned`；生成代码在 [db/nowpay.sql.go](../../server/internal/store/db/nowpay.sql.go)。
- 核销执行器：[nowpay/meter.go](../../server/internal/nowpay/meter.go) 增加 `StatusAbandoned` 与 `Ledger.NoteAttempt`，[nowpay/maintenance.go](../../server/internal/nowpay/maintenance.go) 的 `Sweep` 在入队之前记尝试、拿到 `abandoned` 就跳过，上限 `maxSettleAttempts` 与对账日志的 `abandoned` 一并在那里。
- 存储：[pg/nowpay.go](../../server/internal/store/pg/nowpay.go) 实现 `NoteAttempt`，`CheckNowPaySchema` 多检查两列与状态约束。
- 契约与后台：[openapi.yaml](../../server/api/openapi.yaml) 的 `AdminPointCharge.status` 增加 `abandoned`，管理后台的积分一节显示“不再补查”。
- 文档与验收：[server/README.md](../../server/README.md) 的核销与表结构两节、[运维手册](../../server/运维手册.md) 的增量语句与保留期说明同步更新；`TestSweepGivesUpAChargeAfterTooManyAttempts` 核对到上限之后不入队也不落 `failed`，`TestSweepSkipsAChargeSettledWhileSweeping` 核对取出来之后已经终结的流水直接丢弃，`TestPostgresUnsettledGlobalRotatesAttemptedCharges` 核对刚试过的排到后面、没试过的先取，`TestPostgresNoteAttemptCountsAndGivesUp` 核对跳数、备注与不再被补查取到，`TestPostgresPrunesExpiredPurchasesAndTerminalCharges` 核对 `abandoned` 按终态清理，两条启动检查用例核对缺列与缺约束时拒绝启动。
