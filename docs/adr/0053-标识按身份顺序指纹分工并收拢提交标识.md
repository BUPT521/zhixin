# ADR-0053 标识按身份、顺序、指纹分工并收拢提交标识

## 状态

提议。择期实施，与 0.2.0 发出之前合并的那一次 schema 变化同批（见 [数据库结构过度设计审查](../数据库结构过度设计审查.md) 第 8 节），代码未开工。位置标记与摘要的补强（分表摘要、提交基点与云端序号、设备位置、命名版本同步）另见 [ADR-0054](0054-数据版本位置标记补强.md)，两条同批实施，命名版本引用 `uid` 依赖本条的 `uid` 统一。

## 日期

2026-11-23

## 背景

项目里的标识与哈希有三种用途：标明“是哪一个”（身份）、标明“谁先谁后”（顺序）、标明“内容是不是这样”（指纹）。业务行与设备之外，这三种用途在提交这一层混在了一起，同一个意思有两三个字段在表达：

- 提交身份有 `uid`（UUIDv7）与 `request_id` 两个字段。`request_id` 原本是重试幂等键，由命令参数算出；[ADR-0040](0040-数据版本的提交身份与同步变基.md) 引入 `uid` 之后，推送时 `request_id` 这个字段改填 `uid`，本机的 `request_id` 只保留“同一次动作的重试”一个用途，靠“两分钟窗口加仍是 `HEAD`”两条启发式判断，外加“撤销不释放编号”等补丁。ADR-0040 自己指出更彻底的做法是界面在用户动作发生时生成一次性编号，因为要改 29 处 `commandId` 调用而推迟。
- 内容校验有 `hash`、`parent_hash` 与 `state_digest` 三套，[数据库结构过度设计审查](../数据库结构过度设计审查.md) 的 S1 已经确认只留 `state_digest`。
- 首次同步上传的基线提交没有本机 `revision_commit` 行，它的 `uid` 由“设备编号前 8 位加变更明细 SHA-256 前 32 位”手拼，最长 41 字节，是提交身份里唯一一种不是 UUID 的格式，列值长度校验为此放宽到 64 字节。
- 提交另有整数 `id`，被问到能否与 `uid` 合并。

另外讨论了两件事，结论需要留档：跨设备时顺序是否会出异常，以及客户端的 `deviceId` 与 `installId` 是否重复。

## 决定

1. **三种用途各用一类标识。** 身份只用 UUIDv7：业务行主键、提交 `uid`、设备标识都是它。顺序只用本机整数提交编号。指纹只用 SHA-256：附件哈希、`state_digest` 与建议、引用、记忆去重用的 `contentId` 都属于这一类，它们标明的是不同对象的内容，不构成重复。

2. **整数提交编号保留，定位写清为“本机私有的应用顺序”，不并入 `uid`。** 游标位置、`sync_shadow.upto_commit`、`parent_id`、`reverted_commit_id`、`revision_change.commit_id`、裁剪保留下界与界面回执都依赖它按本机应用顺序做范围比较。远端提交带着对方设备的时间，`uid` 的时间前缀顺序与本机应用顺序不一致，用它做范围比较会出错；`uid` 换进每张带提交编号的表与索引，也会把 8 字节变成 36 字节。整数编号不出设备：同步载荷里没有任何整数提交编号（见下方核实结果），这一点写进 [01 第 5.7 节](../01-ER数据模型.md#57-数据版本的提交读取位置与同步冲突) 作为约束，今后新增载荷字段不得携带它。

3. **用 `uid` 取代 `request_id`，由界面在用户动作发生时生成。** 每次用户动作在开始时生成一个 UUIDv7，作为这次写入的提交 `uid` 一路传到命令入口；同一次动作重试时复用它。命令入口按唯一索引 `idx_revision_uid` 先查，已存在就返回原提交，不再执行写入；不存在才落库。`revision_commit.request_id` 与 `idx_revision_request` 删除，两分钟窗口、“仍是 `HEAD`”判据与“撤销不释放编号”都随之删除，29 处 `commandId` 调用改为传入动作 `uid`。同步载荷里的 `request_id` 字段改名为 `uid`，与 S9 在服务端的改动合为同一处契约变更。

4. **基线提交的 `uid` 改用 UUIDv5。** 以设备标识为命名空间、这一块变更明细的 SHA-256 十六进制串为名字，生成确定性的 UUID：同一块内容重发得到同一个 `uid`，服务端的永久去重照常按重试跳过，内容不同则不同；长度固定 36 字符，与其他 `uid` 格式一致，`uid` 的长度校验收紧为 UUID 格式。UUIDv5 的底层是 SHA-1，这里只用来去重，不涉及安全；用已有的 `crypto` 包实现，放在 `domain/rules/` 与 `uuid_v7.dart` 并列，不新增依赖。

5. **`deviceId` 与 `installId` 保持分开。** 讨论中一度建议合并，核对 [ADR-0019](0019-留存统计用匿名上报.md) 之后撤回：它明确要求安装标识不与账号、设备编号关联，两者分开是有意的隔离。后续不再提合并。

6. **同步 `scope` 与 `cloud.json` 里的 SHA-256 前缀值不动。** 它们是游标里的指纹，不是身份，没有重复。`contentId` 可以顺手改名为 `contentKey`，避免与“身份”字面混淆，这属于可选清理，不进必做范围。

7. **完整性校验的 `hash`、`parent_hash` 删除**沿用 S1 的决定，本条不重复展开。

## 跨设备顺序的结论

跨设备的权威顺序是服务端提交序列，不是任何设备的时钟：推送带 `base_seq` 做乐观锁，落后收到 409，必须先拉取再推送，服务端按到达顺序排号，各设备按这个顺序应用远端提交。时间戳只用于展示与索引局部性，不参与判定，所以设备时钟偏差不会让数据出错。这也是整数编号不并入 `uid` 的原因之一。

这套机制下仍会出现几类现象，都是既有设计的结果，不在本条改动范围内，写在这里是为了不被当成新问题：

- 本机历史顺序与服务端顺序可能不一致。离线时写了提交 5、6，再拉到远端提交，本机顺序是 5、6、远端，服务端顺序是远端、5、6；`sync_shadow` 把被远端覆盖的格子从推送里去掉，状态不会分叉，数据版本页的先后与服务端序列不是一回事。
- 后到覆盖先到，与真实修改时间无关。两台设备离线时改同一列，后到达服务端的生效，被覆盖的值留在本机 `revision_conflict`。
- `updated_at` 取决于最后写入的设备的时钟，时钟偏慢的设备后到达时，行的 `updated_at` 可能比之前更早，依赖它排序的地方（记忆召回、讨论列表）会受影响。这一条是从文档推出来的，没有核对具体查询。
- 数据版本页的“某时某分”取远端设备的 `authored_at`，设备时钟偏差时会显示得更早或更晚。
- 两分钟重试窗口随第 3 条删除；保留天数仍按本机 `created_at` 判断，时钟大幅偏差时裁剪边界会偏移，但裁剪下界不能越过未推送的位置，所以不会破坏同步。这一点需要在实施时核对代码是否严格成立。
- [ADR-0045](0045-同步两端的一致性摘要.md) 的一致性摘要负责发现最终是否一致，只检测、不自动修复。

## 核实结果

读过 `server_client.dart` 的 `ServerCommit`：推送载荷只有 `request_id`、`device_id`、`schema_version`、`actor`、`action`、`created_at`、`state_digest` 与 `changes`（`table`、`row_key`、`op`、`before`、`after`），没有 `reverted_commit_id`、`parent_id` 或任何整数提交编号，服务端的 SQL 里也没有这几个字段。所以讨论中担心的“别的设备上整数编号指向另一条提交”不成立，不需要为此改成按 `uid` 引用。

读过 `account_store.dart` 与 ADR-0019：`deviceId` 在 Keystore 里按 `zhixin.account.device.v1` 保存，`installId` 另有来源，ADR-0019 写明两者不关联。

没有核实：29 处 `commandId` 调用来自 ADR-0040，没有重新计数；`sync_commit` 表里 `request_id` 列的长度与约束没有读；基线提交构造的代码没有读；`updated_at` 与保留天数判断没有逐处核对。这些在实施前先核对。

## 代价与边界

- 双击防护从“两分钟内参数相同即合并”变成“同一次动作复用同一个 `uid`”：界面必须保证一次动作只生成一次 `uid`，并在请求进行中禁用重复触发。两次真正独立、参数相同的动作不再被合并，这是预期的行为；但原来靠两分钟窗口兜住的重复点击，要由界面的进行中状态负责，实施时需要补用例。
- 本机提交的 `uid` 由界面生成，写入层与同步层都要拒绝空值与非 UUID 格式。
- 同步契约的 `request_id` 改名为 `uid`，OpenAPI、Go 生成代码、`fake_server.dart`、客户端同步与服务端 `sync_commit`、`sync_commit_seen` 一起改，是破坏性变更，两端同批升级，与 S9 同批。
- 基线 `uid` 格式变了，已经在服务端“见过”的旧基线 `uid` 与新格式不同。按 [ADR-0017](0017-表结构变化仍清空数据.md) 随这次 schema 变化清空云端与本机数据，不写兼容分支。
- 改动要改表（删 `request_id`、`hash`、`parent_hash`），按 [ADR-0001](0001-开发阶段不向下兼容.md) 只能与 0.2.0 前那一次 schema 变化合并；错过之后每次都要通知内测者。

## 替代方案

- 把整数提交编号并入 `uid`，用 UUIDv7 排序：远端提交的时间前缀来自对方设备，与本机应用顺序不一致，游标与遮蔽的范围比较会错；体积也变大。不采纳。
- 继续保留 `request_id` 的两分钟窗口，只给 `uid` 做重试：ADR-0040 已经列过并放弃，G1 的本机部分不解决。不采纳。
- 基线提交落成本机真实提交行，用随机 UUIDv7：[ADR-0023](0023-首次同步上传基线.md) 与 [ADR-0042](0042-数据版本基线的差异上传与时间优先留存.md) 选择不落，是不想在本机历史里留下只为上传而存在的提交。不采纳。
- 合并 `deviceId` 与 `installId`：违反 ADR-0019 的匿名要求。不采纳。
- 服务端账号、会话、备份编号统一改为 UUIDv7：收益小，ADR-0018 决定 4 已经定下不动；ADR-0018 里“服务端已用 google/uuid 的 v7”与服务端代码（`rand.Read` 加 `hex`）不符，应在顺手改文档时更正，不为此改服务端。不采纳。
