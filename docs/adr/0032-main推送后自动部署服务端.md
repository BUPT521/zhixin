# ADR-0032 服务端在 main 推送后自动部署

## 状态

已采纳

## 日期

2026-11-19

## 背景

第一套实例此前由管理员在开发机上交叉编译、`scp` 上传并 `systemctl restart`，文档里写的部署步骤也只有这三步。四个人各自往 `main` 推服务端改动，线上跑的是哪个版本取决于管理员有没有记得部署：2026-11-19 部署时发现，服务器上的可执行文件还是 11 月 17 日的构建，缺少 11 月 18 日加固轮次与模型来源路由的实现，而 `server/README.md` 已经按新实现描述接口。手工部署还要求部署的人持有服务器账号与对象存储、数据库的配置上下文，与「谁方便谁做」的协作方式冲突。

仓库是公开仓库，Actions 对公开仓库不计量费用；服务器是单机 Debian，22 端口对公网开放，密钥登录之后由 `systemd` 管理进程，具备由 Actions 直接部署的条件。

## 决定

`.github/workflows/deploy-server.yml` 负责部署，触发条件是 `main` 上 `server/**` 或这个工作流本身的推送，也可以手动触发。

执行顺序固定为检查、编译、上传、切换、核对。检查与服务端 CI 相同，包括 `gofmt`、`go mod tidy -diff`、`go vet`、`go test -race`（带临时 PostgreSQL）；检查不通过不部署。编译在 Runner 上交叉编译 `linux/amd64`，服务器不装 Go 工具链。上传、切换与核对都在一次 SSH 会话里完成：把新文件传到 `/opt/zhixin/bin/zhixin-api.new-<提交前 12 位>`，把当前运行的 `zhixin-api` 备份成 `zhixin-api.prev`，用 `mv` 换上新文件，重启单元，轮询 `http://127.0.0.1:8080/readyz`；二十秒内没有就绪就换回 `zhixin-api.prev` 再重启，并让工作流失败。就绪之后 Runner 再核对一次公网 `https://zhixin.chensiyuan.work/readyz`。

部署使用专用账号 `deploy`。这个账号的私钥只存在于仓库 secret `DEPLOY_SSH_KEY`，公钥在服务器 `/home/deploy/.ssh/authorized_keys`；它拥有 `/opt/zhixin/bin` 的写权限，`sudoers` 只允许 `systemctl restart zhixin-api`、`systemctl is-active zhixin-api`、`systemctl status zhixin-api` 与读取该单元日志。服务器的主机指纹固定成 secret `DEPLOY_KNOWN_HOSTS`，工作流不用 `accept-new` 自动信任首次连接。

表结构与运行配置的变化不走这条流水线。`schema.sql` 改动仍按 ADR-0001 由管理员停服重建库，`api.env` 的变量仍由管理员在服务器上修改，两者都不适合在一次推送里对线上库直接执行。

## 代价与边界

`main` 上任何通过检查的 `server/**` 推送都会立即替换线上可执行文件。检查覆盖编译、单元测试与 `/readyz`，覆盖不到只有真实请求才会暴露的缺陷；自动回滚只在进程起不来或就绪检查失败时发生，接口行为错误仍要人发现并手工换回 `zhixin-api.prev`。

`deploy` 账号的私钥能被仓库管理员读到，等同于「能替换服务端可执行文件并重启」的权限，但拿不到 `api.env` 里的数据库口令、对象存储密钥与模型 key，也不能改 nginx、证书与系统包。轮换这把钥匙要同时改服务器的 `authorized_keys` 与仓库 secret，两步之间部署会失败，线上服务不受影响。

服务器安全组只对 GitHub 的地址段开放 22 端口，GitHub 更换地址段而安全组没有同步时，部署失败、工作流标红，线上保持原版本。部署账号被锁定或密钥泄漏时，删掉 `authorized_keys` 里对应的一行即可停止自动部署，手工部署流程仍然可用。

第一条推送如果带着加固后的启动自检不满足的配置（例如缺少固定的 `ZHIXIN_CODE_SECRET`），新进程会拒绝启动，`/readyz` 轮询失败后自动换回旧文件；这种情况下工作流是红的，需要先把配置补齐再推送。这个代价在加固轮次之后的第一次部署中已经遇到，处理办法写进了[运维手册](../../server/运维手册.md#49-自动部署与回滚)。

## 替代方案

在服务器上装自托管 Runner：不依赖入站 22 端口，但要在同一台机器上常驻一个 Runner、占用内存，而且这台机器的软件源不全，安装与升级都更麻烦，因此没有采纳。

在服务器上定时 `git pull` 并编译：服务器没有 Go 工具链，也保证不了只在检查通过之后部署，因此没有采纳。

继续手工部署：改动最少，但已经出现文档说已部署、机器上还是旧构建的情况，部署是否发生取决于个人记忆，因此没有采纳。
