# ADR-0066 额度按缓存命中折算

- 状态：已采纳
- 日期：2026-11-25

## 背景

知新给每个账号一份每日免费额度，购买聊天 Token 包时也只按额度扣减。改造之前，额度按上游报告的总 token 数一比一扣，理由是简单：一个 token 就是一个 token。上游的计价方式不支持这种记法。DeepSeek 谷价每百万 token 是输入命中缓存 0.003 美元、输入未命中 0.15 美元、输出 0.6 美元，命中与未命中差五十倍，输出是未命中输入的四倍。同一个账号只要反复追问同一份材料，命中率就能到八成以上，成本降到另一个量级，而额度照旧按总数扣，等于向命中率高的用户多收、向命中率低的用户补贴。购买余额同样受影响：正因为无法按成本定价，档位价格只能用一个混合单价，误差随用户的实际命中率浮动。

## 决定

聊天额度与购买余额都按“计费 token”扣，以一个未命中缓存的输入 token 为 1，命中缓存的输入记 1/50，输出记 4。三个权重按上游谷价的相对比例定，除以 50 之后都是整数，先按五十分之一 token 累加再四舍五入成整 token，单次调用的误差不超过半个 token。嵌入没有缓存语义，按原始 token 一比一记。

折算只写在一处，即 `server/internal/llmproxy/billing.go` 的 `Usage.Billed`，账号账本、实例账本、已购余额与路由用量都从它取数，不再各算一套。一次调用的用量只解析一次：`attemptResult` 带原始输入量、命中量与输出量，结算时由同一个函数折算，`Settle` 接口因此同时收计费量与原始拆分。来源只报总量、说不出命中与否时按原始 token 记，不把未知的输入当成输出多扣四倍。

`llm_usage` 增加 `input_tokens` 与 `cached_tokens` 两列，保存上游报告的原始输入量与其中命中缓存的部分，只用于统计命中率，不参与扣减。每日额度与实例预算的默认值同步上调：聊天从 200000 调到 320000，实例从 20000000 调到 32000000，按输入输出四比一的常见比例折算，用户实际能用的量维持不变。

## 代价与遗留

额度数字的含义变了，`llm_quota` 表里按账号写过的覆盖值不再与改造前的口径等价，需要按新单位重新核对。改造前已经写入的 `llm_usage` 行是原始 token，与新行混在同一张表里，跨天对比时要把切换日期之前的数字单独看；开发阶段不做迁移与回填（[ADR-0001](0001-开发阶段不向下兼容.md)），切换前的用量只作历史记录保留。

后台“用量统计”页展示的仍是上游原始 token 与缓存命中率，没有另设计费 token 一列，管理员核对成本时按命中率自己换算。若以后要在后台直接看计费量，需要给 `llm_route_usage` 增加一列并在页面同时展示两个数。

权重与上游价格绑定。上游调整单价、或者知新同时使用两家价格比例不同的模型时，这套权重只在其中一家上准确；届时要按实际路由的计价比例重算，或者把权重改成按模型配置。

## 上线条件

`llm_usage` 加列属于纯新增，在实例上按 `ALTER TABLE llm_usage ADD COLUMN input_tokens BIGINT NOT NULL DEFAULT 0, ADD COLUMN cached_tokens BIGINT NOT NULL DEFAULT 0` 执行即可，不需要按 [ADR-0057](0057-服务端改表清空重建.md) 整库重建。切换之后核对三项：同一账号在切换前后各发一次同样长度的对话，`GET /v1/llm/quota` 返回的 `used_tokens` 在切换后约为切换前的 1.6 倍（输入输出四比一、没有缓存命中时）；确认邮箱的账号发一次命中上下文的追问，`used_tokens` 的增长明显低于原始 token 数；`llm_usage.input_tokens` 与 `cached_tokens` 两列有值，且 `cached_tokens` 不超过 `input_tokens`。
