# ADR-0058 表结构冻结后只做加法

## 状态

已废弃（2026-11-23）。同日先按“冻结之后只做加法”写成提议，随后定下不做：0.3.0 定在 2026-12-21 发出，写这条时内测还没有开始，库里只有可以丢弃的测试数据，表结构变化继续按 [ADR-0017](0017-表结构变化仍清空数据.md) 与 [ADR-0057](0057-服务端改表清空重建.md) 清空重建即可，代价由团队承担。为这套规则准备的改动一并取消：两端的有序步骤表与一致性用例、服务端版本表、摘要规范化跳过 NULL、取值集合的 CHECK 分两类，schema 32 只做与演进规则无关的条目。

本条没有实施，代码与文档都没有按它改过。背景、决定与代价保留原样，作为 [ADR-0017](0017-表结构变化仍清空数据.md) 决定第 4 条“1.0.0 之后是否引入迁移”这一问题的参考；到那时库里有真实用户数据，届时应按当时的条件新开一条，不在本条上继续改。

## 日期

2026-11-23

## 背景

现在的规则是任何表结构变化都清空数据。客户端按 ADR-0002 与 ADR-0017 只认当前版本，版本不一致的库在打开时整库删表重建（`app_database.dart` 的 `onUpgrade` 直接调用 `_rebuild`）；服务端按 ADR-0057 由 `store.go` 执行整份 `schema.sql`，连同全部账号一起重建。ADR-0017 决定第 4 条把“1.0.0 之后是否引入迁移”留到以后决定。

这个规则在开发阶段成立，因为库里只有可以丢弃的测试数据。[04 的 M1](../04-长期路线图.md#m1-验收与内测包) 写明 0.3.0 的表结构就是公测要用的表结构，0.3.0 定在 2026-12-21 发出，之后内测者写进去的是真实的学习记录。另一方面，产品还会继续增加数据：[01 第 8 章](../01-ER数据模型.md#8-待验证与待定)把录音原文是否入库列为待定，[ADR-0010](0010-客户端插件的两种形态与权限.md) 的插件以后会写入业务表，讨论接入工具调用之后消息也可能出现新的角色。冻结之后如果仍然没有任何演进办法，每增加一列、每增加一个取值都要清空内测者的数据。

2026-11-23 对 schema 31 的复审（[数据库结构过度设计审查](../数据库结构过度设计审查.md)第 9 节）核对了三个会妨碍加法变化的现状。第一，整库摘要按“规范化之后的整行”计算，每一列都参与行哈希，给表加一列会改变每一行的哈希，升级之后的第一次完整性检查与两端比对都会报告不一致。第二，`checkValueSets` 的 24 个取值集合都写成了 SQLite 的 CHECK 约束，SQLite 修改 CHECK 必须重建整张表，给一个集合增加取值因此不是加法。第三，服务端的库没有记录自己执行到哪个版本，只能整份重建。

当时团队四人，每周约 8 小时；服务端只有一套实例、一个进程；客户端用 drift，服务端用 PostgreSQL。

## 决定

1. **schema 32 是冻结线。** 0.3.0 随 schema 32 发出，之后的表结构变化分成两类。加法变化按顺序登记为步骤，每个步骤占一个版本号，升级时按步骤补齐，数据保留；其余变化仍按 ADR-0017 与 ADR-0057 清空重建，并在发版说明里写明。版本低于冻结线的库与数据包仍然按清空与拒绝处理。

2. **允许的步骤只有不丢数据的几类。** 加列、加表、加索引；删除索引；删除整张不承载用户数据的表，包括派生缓存、进行中标记与本机缓冲；服务端放宽 CHECK 约束，因为 PostgreSQL 可以直接替换约束而不重建表。改名、删除业务列、修改类型、收紧约束、修改主键，以及改变已有列或同步载荷已有字段的含义，都不属于加法。一个需求只能用非加法变化实现时，先考虑能否改写成加法，例如加一列新列并停止写入旧列；无法改写时按清空处理。

3. **两端各维护一份有序的步骤表。** 客户端在 drift 的 `onUpgrade` 里只执行登记过的加法步骤，从库的 `user_version` 开始逐步补齐到当前版本，并同步更新 `app_meta.schema_version`。服务端增加一张单行的版本表，启动时按步骤补齐。两端的完整定义（`tables.dart` 与 `schema.sql`）仍然是新建库的唯一来源，各有一条用例核对“冻结线的结构加上全部步骤”与“按完整定义新建”的结果一致，步骤与定义因此不会各说一套。

4. **新列一律可空，NULL 表示旧数据原来的含义。** 整库摘要的行规范化跳过值为 NULL 的列，所以加一列可空列不改变任何一行的哈希，按旧检查点重放得到的投影（没有这一列）与当前表的摘要也相同。这条规范化规则随 schema 32 一起生效，定义写在 [01 第 5.7 节](../01-ER数据模型.md#57-数据版本的提交读取位置与同步冲突)。需要非空语义的新列由领域层把 NULL 读成默认值，库上不写 `NOT NULL DEFAULT`，因为非空的默认值会让每一行多出一个参与哈希的值。

5. **客户端会增长的取值集合不在库上写 CHECK。** 这类集合由领域层按 `checkValueSets` 校验，读到不认识的值时按各模型已有的 `unknown` 处理，所以增加取值只改代码，不改表；结构上封闭的集合保留 CHECK。两类各包含哪些列，列在审查第 9 节的 S25。服务端的 CHECK 保留，需要增加取值时按第 2 条放宽。

6. **JSON 列与接口字段按“忽略并保留”处理。** `structured_json`、`origin_json`、`help_json` 这类 JSON 列以及同步载荷，读取方忽略不认识的键，读出、修改、写回时原样保留不认识的键；契约新增的字段一律可选。小的附加信息先放进已有的 JSON 列，确实需要查询、建索引或约束时再按第 2 条加成实列。

7. **推送只收当前版本，读取接受冻结线以来的各个版本。** 同步推送与整库备份上传仍然只接受当前版本，同一账号的设备需要一起升级，不支持新旧版本的客户端混在一起同步。拉取到的历史提交、云端快照、当前数据包与版本库备份接受冻结线以来的任何版本：缺少的列按 NULL 处理，备份恢复之前先按步骤补齐。

8. **不预留空列、空表或通用的扩展列。** 以后需要的数据到时按第 2 条加。“留出位置”指的是第 2 至第 7 条这套随时可以加的办法，而不是提前把可能用到的列建出来。

## 代价与边界

每个加法步骤都要单独编写，并通过第 3 条的一致性用例，这比整库清空多一份工作。换来的是冻结之后增加数据不再清空内测者的学习记录。

去掉一部分 CHECK 之后，库不再拦截写错的取值，正确性改由领域层校验与表驱动用例保证。好处是另一台设备同步过来的未知取值不会让应用报错，只会在还没升级的设备上显示为未知；但第 7 条要求设备一起升级，这种情况只在升级的间隙出现。

摘要跳过 NULL 之后，一列的值为 NULL 与这一列不存在得到相同的哈希。摘要用来比较两端的数据内容，这个效果正是需要的。

非加法的需求仍然要清空。收紧约束、改名与修改类型都要等到下一次不得不清空的时候一起做，这和 ADR-0017 代价一节里“把已知的结构改动集中在少数几次发版里”是同一个做法。

混版本同步不在本条范围内。旧版本客户端要能保存并转发不认识的列，才能支持混版本同步，这需要另写一条决定。

## 替代方案

- 继续一律清空，即保持 ADR-0017 原样。没有采纳的原因是 0.3.0 之后库里是真实的学习记录，而增加数据是可以预见的常规变化，每次都清空的代价由内测者承担。
- 引入完整的迁移，例如 goose、atlas 或任意 `ALTER TABLE`。ADR-0057 已经因为维护成本没有采纳，这个理由仍然成立；只做加法的步骤不会丢数据，执行与测试都简单。
- 预留空列，或者每张表加一个通用的扩展 JSON 列。没有采纳的原因是预留未用正是审查的 B 类问题，通用列又使查询、索引与约束都无法用于其中的数据；已有的 JSON 列在第 6 条里承担这部分作用。
- 保留全部 CHECK，增加取值时重建表。SQLite 重建版本化表还要重新安装触发器与暂存表，并保证采集不把重建记成历史，这不是加法，也是最容易出错的一类变化。
- 摘要不跳过 NULL，而在每次加列之后整库重算摘要并补记一条维护提交。没有采纳的原因是旧提交与旧检查点上记录的摘要会全部失效，两端比较也要等双方都重算之后才能恢复。
