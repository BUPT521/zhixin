# ADR-0043 服务端快照登记与提交序列压缩

## 状态

已采纳

## 日期

2026-11-21

## 背景

服务端为每个账号保存一条只追加的线性提交序列，客户端按 `base_seq` 做乐观锁推送，新设备首次同步从第 1 条开始回放，每账号的序列预算是 256 MiB，超出时推送返回 413 `storage_full`（[ADR-0031](0031-云端写入与托管模型的资源预算.md)、[ADR-0040](0040-数据版本的提交身份与同步变基.md)）。2026-11-20 的差异上传（[ADR-0042](0042-数据版本基线的差异上传与时间优先留存.md)）让全新设备不再上传整份基线，序列的写入速度因此下降，读取一侧没有变化：序列体积随设备数量与使用轮次持续增长，账号到达预算之后唯一的出路是清除云端数据再重新上传基线，服务端历史与所有设备的增量位置一起作废，新设备仍然要从第 1 条回放（[改进方案](../数据版本系统对照git的改进方案.md) 第 3.7 节的 G7）。

客户端已经有两样东西可以支撑一次浅克隆：检查点是整库投影的 `json+gzip` 编码，改进方案 3.5 规划的一致性摘要给出可以比对的整库摘要；服务端只保存提交，不解析学习内容，也不认识业务表的行格式（[ADR-0009](0009-API后端采用Go与分层框架.md)）。快照因此只能由已经同步到某个位置的设备生成并上报，服务端负责保存字节、校验归属、登记位置，以及在合适的时候删掉快照已经覆盖的提交。

作出这条决定时的条件是四人团队各自开发、内测规模几十人、开发阶段不向下兼容（[ADR-0001](0001-开发阶段不向下兼容.md) 与 [ADR-0017](0017-表结构变化仍清空数据.md)），表结构与契约可以直接改，数据库与云端数据可以整体清空重传，代价由内测数据承担。本轮只做服务端一侧，客户端首次同步下载快照、判定重新克隆与空闲时登记快照由后续任务接。

## 决定

1. 契约新增快照的登记与查询。`PUT /v1/sync/snapshot` 的请求体是 `seq`、`sha256` 与 `digest`：`seq` 是这份快照覆盖的服务端序列位置，`sha256` 是快照附件的内容哈希，`digest` 是客户端按改进方案 3.5 算出的整库摘要，两个哈希都是 64 位小写十六进制。`GET /v1/sync/snapshot` 返回当前指针。`GET /v1/sync/head` 与 `GET /v1/sync/commits` 的响应增加 `earliest_seq` 与 `snapshot` 两个字段：`earliest_seq` 是保留下界，即第一条仍然可以拉取的序号，没有删除过提交时为 1；`snapshot` 给出当前快照的位置、附件哈希、摘要与登记时间，没有登记时省略这个字段。服务端只保存最新的一份快照，登记更新的位置会覆盖旧指针。

2. 登记要校验四件事。`seq` 落在 1 与当前 head 之间，登记 head 之后的位置返回 400 `invalid_request`；`sha256` 与 `digest` 都是 64 位小写十六进制；`sha256` 是本账号已经上传的附件，服务端按账号查附件索引，查不到返回 400；附件大小不超过单个附件上限，超出同样返回 400。`seq` 小于已经登记的位置返回 409 `conflict`，`extra.snapshot_seq` 给出当前位置，表示不能回退覆盖更新的快照；`seq` 与当前位置相同时按幂等重试接受并刷新指针。清除云端数据期间登记返回 409，与推送、备份和附件的写请求一致。

3. 压缩在登记快照时按保留期做一次。`sync_head` 增加 `trimmed_through`，记录已经删除到哪个序号；账号有快照之后，快照位置及之前、且服务端收到时间早于保留期 `ZHIXIN_SYNC_COMPACT_KEEP`（默认 `168h`）的提交在登记时删除，`trimmed_through` 跟着推进。保留下界 `earliest_seq` 等于 `trimmed_through + 1`。保留期的用途是让落后不多的设备继续增量拉取，不必每登记一次快照就整库重新克隆。

4. 推送超过账号预算时先压缩再判断。一次推送追加之后如果超过 256 MiB，服务端在有快照的情况下删掉快照位置之前的全部提交，不按保留期过滤，重新计算之后仍然超出才返回 413 `storage_full`；没有快照时维持压缩之前的行为。预算压力下忽略保留期是有意的：快照已经是可用的克隆基线，账号继续写入比保住一部分增量历史更重要，位置被越过的设备按重新克隆处理。

5. 拉取越过已删除区间时返回明确的错误。`after + 1 < earliest_seq` 说明客户端要的下一条提交已经删除，接口返回 410，problem 的 `code` 是新增的 `history_compacted`，`extra` 里给出 `after`、`earliest_seq`、`head` 与 `snapshot_seq`、`snapshot_sha256`、`snapshot_digest`。客户端据此下载 `snapshot_sha256` 指向的附件、导入本机、把同步位置改成 `snapshot_seq`，再把未推送的本机提交按 [ADR-0040](0040-数据版本的提交身份与同步变基.md) 的剩余部分在快照之上重放。`after` 恰好等于 `earliest_seq - 1` 时照常增量返回，因为客户端要的下一条就是保留下界；`after` 为 0 而保留下界大于 1 时同样返回 410，新设备应当先读 `head` 或拉取响应里的 `snapshot` 再下载。

6. 内存实现与 PostgreSQL 实现都保存账号级快照指针与保留下界。PostgreSQL 新增两张表：`sync_snapshot` 每账号一行，记 `seq`、`sha256`、`digest` 与 `created_at`；`sync_commit_seen` 记已经接收过的提交身份，主键是账号与 `request_id`。提交去重同时查 `sync_commit` 与 `sync_commit_seen`，压缩删掉旧提交之后，已经接收过的提交身份仍然按原样跳过，[ADR-0040](0040-数据版本的提交身份与同步变基.md) 的永久去重承诺因此保留。

7. 快照是附件，服务端不解析内容。快照由客户端按检查点格式压缩之后走 `PUT /v1/blobs/{sha256}` 上传，字节在对象存储里按账号隔离，受单个附件上限与账号附件总量上限约束；服务端只核对哈希与大小，不打开内容。被替换下来的旧快照附件不删除，因为它可能与业务行引用的哈希相同，服务端不解析内容就分不出两者，删错会让用户下载不到业务行引用的附件；这些字节留在账号附件配额里，随 `DELETE /v1/cloud` 或删除账号清除。

8. 清空云端数据同时清空快照、保留下界与去重记录。`DELETE /v1/cloud`、`DELETE /v1/sync/commits` 与删除账号把 `sync_snapshot`、`sync_commit_seen`、`trimmed_through` 与提交一起清掉，head 回到 0，下一次同步按首次基线重新开始；快照附件由现有的账号附件清理一并删除。

## 代价与边界

压缩只删除快照覆盖的部分。快照位置之后的提交永远保留，直到设备登记一份更新的快照；长期没有设备登记新快照的账号仍然会到达 256 MiB 并收到 `storage_full`，这条路径与压缩上线之前相同。

预算压力下的压缩忽略保留期，一次删掉快照位置之前的全部提交。位置在那之前的设备立即需要重新克隆，正在进行的增量拉取返回 410；设备越久不联网、快照推进得越远，遇到重新克隆的机会越大。服务端在没有任何设备登记快照之前不会删除任何提交，只支持旧协议的客户端在登记出第一份快照之前不受影响，之后必须升级到会处理 410 的版本；开发阶段两端一起升级，代价由内测数据承担。

重新克隆会替换本机数据版本历史。本机从快照附件重建投影，撤销窗口、命名版本与数据版本页里的旧提交都按快照重建；未推送的本机提交按 [ADR-0040](0040-数据版本的提交身份与同步变基.md) 的剩余部分在快照之上重放，被快照内容覆盖的格子按遮蔽规则丢弃。用户在一台设备上的历史细节因此可能变短，这是删掉服务端历史换来的。

旧快照的附件字节不回收。一份快照的大小取决于整库投影压缩之后的体积，账号附件总量上限（默认 2 GiB）要能容纳若干份历史快照；快照占用的是附件配额，与序列预算分开记账。服务端无法区分快照附件与业务附件，清理只能等到清空云端数据，或者后续引入附件引用计数。

去重表不进入 256 MiB 的序列预算，因此在预算之外还有一份随提交条数增长的索引，每条提交一行、几十字节。这是保留永久去重的代价，[ADR-0040](0040-数据版本的提交身份与同步变基.md) 已经接受去重集合随提交条数增长。

快照的正确性由客户端保证。服务端不校验 `digest` 与快照内容，登记错的快照会让之后克隆的设备得到错误数据；摘要只用于客户端之间的一致性比对，与改进方案 3.5 的用法相同。

首次同步多一次快照下载。同步总时长在快照很大时受下载速度限制，但不再逐条回放全部提交，流量通常小于整份历史。

`schema.sql` 增加 `sync_head.trimmed_through`、`sync_snapshot` 与 `sync_commit_seen`，按 [ADR-0017](0017-表结构变化仍清空数据.md) 版本不一致即清空重建，不写迁移。已有实例里 `sync_commit_seen` 是空的，去重查询同时查 `sync_commit` 与 `sync_commit_seen`，因此不需要回填，压缩之后才只靠去重表。

## 替代方案

- 继续只增不减，到 256 MiB 时清空云端重传。改动最小，与压缩之前的行为一致；代价是服务端历史与所有设备的增量位置在清空时一起作废，新设备仍要从第 1 条回放，G7 没有解决。不采纳。
- 服务端解析提交并自己生成快照。快照由服务端维护，客户端只下载一份文件；代价是服务端要理解每张业务表的行格式与合并规则，与只保存不解析的分层冲突，客户端表结构每次变化都要改服务端，内测阶段的成本高于收益。不采纳。
- 把快照放进整库备份接口。复用已有的上传下载与保留份数；代价是备份按份数保留、与恢复入口绑定，最新一份可能在第六次上传时被删掉，而且备份不表达“跟随提交序列位置的克隆基线”这一含义，还要改备份的保留口径。不采纳。
- 由服务端按固定条数合并旧提交。客户端不需要上传快照；代价是服务端不解析内容就无法合并行级变化，只能整条丢弃，等于删掉历史而不是留下可克隆的基线。不采纳。
- 只在客户端做浅克隆，服务端不删提交。客户端只下载最近若干条提交；代价是没有快照就没有基线状态，服务端序列的体积与预算问题仍然存在，G7 的增长部分没有解决。不采纳。
- 把保留期也用于预算压力下的压缩。行为更保守，设备不必因为一次预算溢出就重新克隆；代价是快照刚登记、提交又很新时压缩删不掉足够的提交，账号仍然返回 `storage_full`，压缩在真正需要的时候不起作用。不采纳。
