# ADR-0080 管理后台的积分查看

## 状态

已采纳（2026-11-26，服务端同日实施）。

## 日期

2026-11-26

## 背景

积分包从 2026-11-25 起开卖（[ADR-0067](0067-聊天额度改走即刻收积分包.md)）。账号页已经显示今天从积分扣了多少、还剩多少，额度预留也按余额副本放行，但管理后台看不到这些数字：账号管理接口只有每日额度与今日已结算用量（[ADR-0078](0078-管理后台的账号注销与额度管理.md)），“按密钥计费”页的约合积分是按计费 token 折算的估算值，不读核销流水，也不读余额副本（[ADR-0076](0076-管理后台按密钥的对账视图.md)）。用户来信说“买了积分却还是提示额度用完”时，管理员只能连 PostgreSQL 查 `nowpay_balance` 与 `nowpay_charge`，再对照 `llm_usage` 自己算；临时给某个账号补一笔积分，或者确认一笔核销到底有没有成功，都没有页面可看。

积分与免费额度的账本不同。免费额度按天重置，额度值来自 `llm_quota` 与配置，修改立即生效；积分是用户付过钱的余额，真正的数额在支付宝一侧，服务端只保存余额副本 `nowpay_balance` 与核销流水 `nowpay_charge`，核销不可撤销，也没有退款路径。把两者放进同一个“管理”动作，会让管理员以为可以直接改余额，而改副本会在下一次 `quota.query` 之后被真实余额覆盖，既没有效果，又会让对账看不到这次改动。

## 决定

1. `GET /admin/v1/accounts/{id}` 增加积分视图 `points`：`enabled` 说明这个实例有没有开通积分收款，`charged_today` 是今天已经核销成功的积分，`remaining` 是可用积分（与额度放行同一口径，余额副本减去没有反映的核销、再减去当天已占用未记流水的计费量），`synced_at` 是副本的快照时刻，`charges` 是最近五条核销流水。列表接口不带这一节，避免一页账号逐行查询余额。
2. 新增 `POST /admin/v1/accounts/{id}/points/refresh`，同步调用一次即刻收的 `quota.query`，用返回的剩余积分覆盖本地副本，再按刷新后的副本返回同一个积分视图。实例没有开通收款时返回 409，账号不存在时返回 404，即刻收不可用、商品额度单位不是积分或响应无法解析时返回 502，副本保持原值。
3. 积分一节只读。后台不提供补分、扣分、退款或修改核销状态的操作；流水只列编号、记账日、积分、计费 token、状态与时间，不改写。
4. 金额与口径不在后台另算。可用积分复用 `llmproxy.Quota.Points`，与账号页、额度预留共用同一个函数；最近流水的查询按账号与创建时间倒序，只取终态与在途都有的行。
5. 页面把额度与积分放在同一个账号弹窗里：上半部分是聊天与嵌入的每日额度、今日用量与覆盖值，下半部分是积分余额、今天已扣、副本同步时间与最近五条流水，“刷新余额”按钮只在开通收款时出现。没有开通收款、账号还没有副本与余额确实为零分别显示，缺失的余额不写成零。

## 代价与边界

余额副本可能过期。后台显示的是副本，不是此刻支付宝一侧的余额；副本超过一分钟没有同步时，下一次带额度的请求会排一次异步查询，管理员也可以点“刷新余额”立即同步。刷新是同步调用，最多等八秒，即刻收变慢时页面会等这一段时间并可能返回 502；副本保持原值，不会因为一次失败被写成零。

核销流水只列最近五条。需要核对更早的流水或按状态统计时，仍按运维手册查询 `nowpay_charge`；后台不做分页与导出，这一轮不增加新表与索引。

后台仍然没有操作审计。“刷新余额”会触发一次外部查询并写副本，但谁也不记录这次查询由谁发起；管理令牌泄漏时，攻击者可以刷新任意账号的余额，看到的数额与真实余额一致，不能把钱转走，也不能改余额。生产上继续按 [ADR-0029](0029-模型来源路由与嵌入代理.md) 限制 `/admin` 的来源地址或只经 SSH 隧道访问。

人工补分与退款没有入口。积分在支付宝一侧，补分要调即刻收的接口或与对账一起处理；后台直接改副本会被下一次查询覆盖，记一笔本地调整又会让副本、流水与真实余额三方对不上。需要人工补偿时先明确记账方式（本地调整流水如何进入可用积分、如何与即刻收对账），那是一条新的决定，不在本条范围内。

内存存储没有即刻收，积分一节只显示“这个实例没有开通积分收款”。余额、流水与刷新的真实行为只能在 PostgreSQL 装配下核对。

## 替代方案

只按密钥计费页的约合积分看用量。没有采纳的原因是它按计费 token 折算，不扣免费额度，也不读核销流水与余额副本，回答不了“这个账号还剩多少积分、今天扣了几笔、哪一笔还在处理中”。

直接改 `nowpay_balance` 的剩余积分，作为人工补分。没有采纳的原因是副本只是缓存：下一次 `quota.query`、下一次核销成功或余额不足时都会被真实余额覆盖，改动不会留下痕迹，对账也看不到；积分是用户付过钱的余额，后台应当只读。

增加一张本地积分调整流水，补分与扣分都记在里面，再与即刻收对账。本轮没有采纳，因为要先确定调整如何进入可用积分、是否补发到支付宝一侧、退款走哪条路径；这些规则没有定下来之前，加一张表只会让三方账更难看懂。

把积分视图放进“按密钥计费”页。没有采纳的原因是那个视图按密钥对账，一个账号可能有多把密钥，同一份余额会出现多行；账号管理页已经在按账号展示额度与用量，积分放在同一处，管理员处理“这个账号额度不够”时不用换页。
