# ADR-0048 设备名册与提交来源的别名

## 状态

已采纳

## 日期

2026-11-21

## 背景

提交序列按设备分来源（[ADR-0040](0040-数据版本的提交身份与同步变基.md)）：每条提交带客户端生成的设备标识，数据版本页据此把远端提交写成“来自另一台设备 1a2b3c4d”。设备标识是 UUIDv7，前 8 位对用户没有意义，两台设备之间也无法区分谁是谁。

客户端注册与登录时上报的设备名只用来在服务端列出会话，会话按令牌保存、不按设备保存，退出登录之后名字就断了；设备标识本身不随整库备份迁移，换机之后重新生成。服务端因此没有任何一处保存“这台设备叫什么”，客户端也没有地方读到其他设备的名字。

快照压缩前的门槛（[ADR-0047](0047-快照附件回收与压缩前的客户端门槛.md)）需要知道账号最近有哪些设备、它们是否支持 `snapshot` 能力，这项信息也没有地方保存。两个需求都落在同一份设备名册上，一起处理。

## 决定

1. 服务端保存账号级设备名册。新增表 `sync_device`，每行是账号、设备标识、别名、能力声明、首次出现时间与最近出现时间，主键是账号与设备标识。账号删除时级联删除，清除云端数据时整表清掉。

2. 同步请求带上设备标识与能力声明。`GET /v1/sync/head`、`GET /v1/sync/commits`、`POST /v1/sync/commits`、`PUT /v1/sync/snapshot` 与新增的设备接口接受 `X-Device-Id`（不超过 64 字符）与 `X-Sync-Capabilities`（逗号分隔的小写能力名，当前只有 `snapshot`）。带 `X-Device-Id` 的请求据此更新名册：`last_seen` 写成服务端当前时间，能力声明整组替换，别名保持不变。没有 `X-Device-Id` 的推送按提交里的设备标识补一行，能力留空，这样旧版本客户端也会出现在名册里，压缩门槛因此能看见它们。

3. 别名由用户设置，服务端保存。新增 `GET /v1/sync/devices` 返回名册，按最近出现时间倒序，最多 50 条，每条带设备标识、别名、能力声明与最近出现时间；新增 `PUT /v1/sync/devices`，请求体是设备标识与别名，别名去掉首尾空白之后不超过 64 字符，空串表示清除，只能改本账号名册里已有的设备，未知设备返回 404 `not_found`。改名不改写已经推送的提交，提交里的设备标识保持不变。

4. 客户端显示别名，未知时退回标识。同步服务在每次同步请求里带上设备标识与能力声明，同步成功之后拉一次名册并缓存在内存里；数据版本页按远端提交的设备标识查别名，查不到时仍然写“来自另一台设备 1a2b3c4d”。账号页新增“设备”一节，列出名册里的设备，本机按本机设备标识标“本机”，每台设备提供“改名”入口，现在没有别名的设备显示“未命名设备”与标识前 8 位。

5. 名册只记录发过同步请求的设备。名册不引入设备注册接口，也不从会话推导：一台设备只有在同步请求里出现之后才进名册，54 天没有出现过的设备视为不活跃，压缩门槛不再因它暂停。

## 代价与边界

名册是账号级数据，换账号之后看不到上一个账号的设备；本机设备标识不随整库备份迁移，换机之后按新设备重新进名册，旧行留在服务端直到账号删除或清除云端数据。

每次同步请求多一次名册写入。写入按账号与设备标识更新一行，不阻塞同步本身；写入失败只记日志，不影响本轮同步的结果，名册因此可能在个别轮次滞后。

别名后写覆盖先写，两台设备同时改名时以最后一次为准，没有冲突记录。别名只影响显示，不影响提交的身份、去重与同步位置。

客户端缓存的名册在进程内有效，重启之后第一次进入数据版本页之前显示的是标识；同步成功之后刷新，与账号页共用同一份缓存。

## 替代方案

- 别名保存在本机设置里。改动最小，不需要服务端表；代价是只能命名本机，其他设备的提交仍然显示标识，而用户想区分的恰恰是其他设备，因此不采纳。
- 把设备名写进每条提交。拉取之后不用再查名册；代价是每条提交多一份重复字段，提交体积与去重规则都要跟着改，历史提交改名也无法追改。
- 从会话表推导设备。会话里已经有设备名，按最近登录时间取最新一条；代价是会话按令牌保存，退出登录、令牌过期与重设密码都会删掉会话，名字随之消失，而提交要比会话活得久。
- 用设备标识前 8 位之外的固定文案区分设备。比如“另一台设备 A”“另一台设备 B”，按出现顺序编号；代价是编号与设备没有稳定对应，用户仍然无法把“设备 B”与自己的手机对上。
