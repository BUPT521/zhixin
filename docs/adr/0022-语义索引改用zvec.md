# ADR-0022 语义索引改用 zvec

## 状态

已采纳。2026-11-16 决定并完成第 1 至 6 步，同日收拢语义索引的配置入口。

## 日期

2026-11-16

## 背景

语义索引现在是一个独立的 SQLite 文件，`sqlite3_vec` 的 `vec0` 虚拟表存向量，`vector_entry` 表存片段正文与来源信息，后台 isolate 持有连接。`vec0` 表只建了向量列，检索时不知道范围：检索时先取 k 个 rowid，再逐条回表，服务层为了在限定材料或目标时不漏召回，把候选放大到 `limit × 20` 并封顶 400。`sqlite3_vec` 的构建钩子需要 clang 工具链。

zvec 是阿里巴巴开源的进程内向量库，0.8 起提供 Dart/Flutter 包，支持 Android arm64（API 28 起），检索可以带标量过滤并在同一次调用里返回字段。2026-11-16 在沙箱里用两万条 1024 维向量比较：Flat 精确检索取前 20 条约 5 ms，`vec0` 约 35 ms；HNSW 建索引在两核上要 84 秒。以知新的数据量，两者的检索耗时用户都感觉不到。测量与设计细节见 [语义索引接入 zvec 方案](../语义索引接入zvec方案.md)。

现有代码里有几处行为是按 SQLite 的宽松程度写的，换引擎时不能原样保留。`SemanticIndexService.configure` 在模型改变时用 `unawaited` 关闭旧句柄，紧接着就可能打开新句柄；`AppScopeState.dispose` 同样不等关闭完成。SQLite 允许同一个文件同时有两个连接，zvec 不允许：沙箱里同一进程第二次打开同一个 collection 会报 `Can't lock read-write collection`。zvec 的引擎初始化是进程级的，几个 isolate 共用一份，任何一个 isolate 调用 `Zvec.shutdown` 都会影响其他 isolate。Dart 包的 `upsert` 对单条文档的失败不抛异常，而是在返回的 `WriteResult` 里计数；`deleteByFilter` 不返回删除条数。这些差别决定了下面第 8 至 10 条与实施方案的写法。

## 决定

1. 语义索引的存储引擎由 `sqlite3_vec` 换成 zvec，替换限定在 `VectorStore` 接口以下；`SemanticIndexService`、证据检索、界面与后台 isolate 的消息协议保留，消息里只增加接口调整所需的参数。
2. 每个嵌入模型键对应一个 zvec collection 目录，这个 collection 的状态写在同级的同名 JSON 文件里；模型、维度或文本处理版本改变时删除旧目录。按 [ADR-0002](0002-本地数据不做迁移.md) 不迁移旧的 `vector_index.db`，唯一的例外写在实施方案第 7 节：切换发生在内测用户已有索引之后时，过渡版本搬运一次同模型的向量，避免让用户的嵌入服务重新计费。
3. 索引类型用 Flat 与余弦距离，不量化。片段数超过十万后再评估 HNSW 与量化。
4. `replaceSource` 先写其余片段、再删多余片段、最后写 0 号片段，0 号片段上的版本号与片段数作为这个来源的提交记录。任何一批写入的 `WriteResult.errorCount` 不为零，都按写入失败处理。
5. 检索按写入后不变的属性（来源种类、材料页的材料、消息与作答的讨论、来源键）在索引内部预过滤；预过滤只允许比业务规则宽，目标范围与最终的范围判断仍由业务库负责。
6. 关键词检索继续使用 [ADR-0013](0013-关键词检索改用FTS5.md) 的 FTS5，zvec 的全文检索与混合检索不在本条范围内。
7. 服务层测试改用纯 Dart 的内存索引；zvec 实现由一组契约测试覆盖，需要 `ZVEC_LIBRARY_PATH` 指向本机 C 库。
8. zvec 引擎按进程只初始化一次，任何 isolate 都不调用 `Zvec.shutdown`；同一个 collection 同一时刻只由一个句柄打开，服务层先等旧句柄关闭完成，再打开新句柄。
9. 索引打不开、被占用或写入失败时，语义检索按“不可用”处理，回答前后的原文与关键词检索照常，不弹窗。只有判定为结构损坏时才删除目录重建；被占用时只重试，不删除，因为重建意味着全部片段重新嵌入。
10. 切换运行时的版本保留 SQLite 实现，由编译期参数选择引擎；一个内测周期内没有回退，再删除 SQLite 实现与 `sqlite3_vec` 依赖。

## 实施方案

本节记录实施时遵守的细节：接口、生命周期、失败处理、预过滤、构建发布、测试与验收。分层、文档字段与写入顺序以 [方案](../语义索引接入zvec方案.md) 为准，两处说法不一致时以本节为准。下文的行为都在沙箱里用 zvec 0.8.1 的 Python 包核对过，它与 Dart 包调用同一个 C 引擎；Dart 包的接口按 pub.dev 上 `zvec` 0.8.0 的源码核对。

### 1. 接口改动

| 位置 | 替换前 | 现在 | 原因 |
|---|---|---|---|
| `VectorIndex` | SQLite 具体类 | 同步接口；实现为 `ZvecVectorIndex`（运行时）与 `MemoryVectorIndex`（测试） | 运行时与测试各用一种实现，服务层不变 |
| `indexedSources` | 无参数，读出全部来源 | `indexedSources(List<String> keys)`，isolate 内按 500 个一批 `fetch` 0 号片段 | Dart 包没有封装文档迭代器 |
| `sourceCount` | 没有；`stats()` 用 `indexedSources().length` | 新增，读状态文件里的 `source_count` | 设置页不再为了一个数读出全部来源 |
| `search` | `search(query, k: …)` | `search(query, k: …, prefilter: …)`，参数类型见第 5 节 | 范围预过滤 |
| `pruneSources` | 返回删除的来源数 | 返回删除的向量条数，取删除前后 `docCount` 之差 | `deleteByFilter` 不返回条数 |
| `meta` / `setMeta` | 任意键，存在 `vector_index_meta` 表 | 只接受 `epoch`、`built_at`、`source_count`；`model_key`、`dim`、`text_version` 由打开时写入 | 状态文件只放这几项，传错键直接报错 |
| `finishRefresh` | 没有 | 一次写入 `built_at` 和 `source_count`，另传入本次写入的向量条数 | 统计对应同一次刷新，zvec 据写入量决定是否执行 `optimize` |
| 设置页 | “清理 n 条”“n 条来源” | “清理 n 条向量”；来源数取 `sourceCount` | 跟随上面两项的口径 |

`search` 的预过滤参数是一个值类型，不是过滤表达式字符串。`ZvecVectorIndex` 把它渲染成 zvec 的过滤表达式，`MemoryVectorIndex` 在 Dart 里逐条判断。这样契约测试可以用同一组输入比较两种实现，服务层也不需要知道 zvec 的表达式语法。

### 2. 打开、关闭与并发

磁盘布局是一个 collection 配一个状态文件：

```
filesDir/vector_index/
  <模型键短哈希>/          # zvec collection
  <模型键短哈希>.json      # model_key、dim、text_version、epoch、built_at、source_count
```

状态文件按模型键分别存放，不放在 `vector_index/` 根目录共用。模型在 A、B 之间来回切换时，旧 isolate 关闭 A 与新 isolate 打开 B 可能重叠，各写各的状态文件就不会互相覆盖。状态文件用“写临时文件、再改名”的方式替换。

后台 isolate 的入口先检查 `Zvec.isInitialized`，没有初始化才调用 `Zvec.initialize`，两个 isolate 同时发起初始化时，后到的一方收到 `ALREADY_EXISTS` 后继续打开自己的 collection。引擎由同一进程内的 isolate 共用，所以 isolate 退出时只调用 `Collection.close()`，引擎由操作系统在进程结束时回收。初始化参数见第 6 节。

`SemanticIndexService` 增加一个“正在关闭”的 Future 链。`configure` 换模型、`close` 与 `clear` 关闭句柄时把关闭的 Future 挂到链上，`_open` 先等这条链结束再打开新句柄。`AppScopeState.dispose` 之后新建的服务实例看不到旧实例的链，这种情况由 `ZvecVectorIndex.open` 兜底：报错信息含 `Can't lock` 时按 100、200、400、800、1600 毫秒退避重试，约 3 秒后仍失败就抛 `VectorStoreFailure('索引正被占用')`，不删除目录。沙箱里写入后用 `kill -9` 结束进程，再次打开条数不变、锁也不残留，所以进程被系统杀掉之后不需要额外清锁。

打开成功之后，删除 `vector_index/` 下其他模型键的目录与状态文件，以及上一次留下的 `*.trash-*`、`*.broken-*` 目录。删除其他模型键的目录之前，先试着打开一次对方的 collection：对方仍被另一个 isolate 占用就跳过，留到下一次打开；删不掉的也留到下一次打开。状态文件只在对应的 collection 已经删掉或不存在时才删除，这样模型在 A、B 之间快速切换时不会删掉对方正在使用的索引。旧版的 `vector_index.db`、`-wal`、`-shm` 也在这一步删除。

`clear` 在 isolate 内依次执行：关闭 collection，把目录改名为 `<哈希>.trash-<毫秒>`，在原路径新建空 collection，写状态文件，最后删除改名后的目录。先改名再删，是为了让中途退出时原路径上要么是完整的旧目录、要么是完整的新目录，不会是删了一半的目录。沙箱里删掉 collection 的版本文件或段目录之后都无法打开，删了一半的目录正是这种状态。

### 3. 损坏与失败的处理

| 情况 | 判断依据 | 处理 |
|---|---|---|
| 目录被另一个句柄占用 | 打开时报错信息含 `Can't lock` | 退避重试约 3 秒；仍失败则这一次语义检索不可用，刷新记为失败，不删目录 |
| 结构损坏 | 打开时报其他错误。沙箱里删掉版本文件报 `Failed to find the version file`，删掉段目录报 `Segment open failed` | 目录改名为 `<哈希>.broken-<毫秒>`，新建空 collection，在本机诊断记录里记一条 `semantic_index` 类的重建记录，下一次刷新全量重建 |
| 状态文件缺失或无法解析，collection 存在 | 读状态文件失败 | 无法确认模型与维度，按结构损坏处理 |
| 写入部分失败 | `upsert` 返回的 `errorCount > 0` | 抛 `VectorStoreFailure`，这个来源计入 `failed`；0 号片段没有写成，下一次刷新会重建它 |
| 磁盘写满 | 同上 | 同上；已有内容的检索不受影响 |
| 原生库加载失败 | `DynamicLibrary.open` 抛错，isolate 没有发出就绪消息 | 沿用现在“索引打不开”的路径：检索退回原文与关键词，设置页显示失败说明 |
| 维度与模型不一致 | 写入时报维度不符 | 视为程序错误，按写入失败记录；正常情况下打开时已按模型键分目录，不会发生 |

所有失败的异常原文与调用栈仍然只进本机诊断记录，界面上的说明沿用 `VectorStoreFailure` 现有的文案。

### 4. 写入、清理与统计

`replaceSource` 的顺序见方案第 4.5 节。写入前仍调用 `normalizeVector`，再转成 `Float32List`；余弦距离对归一化不敏感，保留它是为了让 `MemoryVectorIndex` 与 zvec 的距离数值一致，契约测试可以直接比较得分。`Doc` 与 `VectorQuery` 持有原生内存，在 `try/finally` 里 `destroy`，不传出 isolate。

`pruneSources(keep)` 在 `keep` 为空时等同于 `clear`，否则执行一次 `deleteByFilter("source_key not in (…)")`。沙箱里 19,900 个键拼成的表达式约 935 KB，删除耗时 244 ms；这一步只在刷新结束时执行一次，可以接受。来源数超过五万时重新测一次，届时如果 Dart 包已经补上文档迭代器，改为遍历后按批删除。

`source_count` 在刷新结束时写入，口径是 `keep` 里满足下面任一条件的来源数：刷新开始时索引里已有它的 0 号片段，或者这一次写入成功。重写失败的来源，旧的 0 号片段仍在，仍然计入。`clear` 之后为 0。`built_at` 与 `source_count` 一起写，二者总是对应同一次刷新。

一次刷新写入超过 200 个文档时，在结束时依次调用 `flush` 与 `optimize`；否则只调用 `flush`。

### 5. 范围预过滤

预过滤的值类型有两种，由服务层根据 `EvidenceScope` 生成，生成函数放在 [evidence_scope.dart](../../app/lib/data/db/drift/queries/evidence_scope.dart) 旁边，与 `EvidenceScopeRule` 一起维护：

| 检索范围 | 预过滤 | 渲染出的 zvec 表达式 | 候选数 |
|---|---|---|---|
| 用户查找，全部记录 | 无 | 无 | `limit × 4`（不变） |
| 用户查找，一个目标 | 无；讨论与材料的目标归属可以修改，写进索引会过期 | 无 | `limit × 20`，封顶 400（不变） |
| 用户查找，一份材料 | 只保留这份材料的页，其他种类放行 | `(kind = 'material_page' and material_id = 'X') or kind != 'material_page'` | `limit × 4` |
| 回答前检索，没有目标归属 | 当前讨论的来源，加上本轮带入的来源 | `conversation_id = 'C' or source_key in ('…')` | `limit × 4` |
| 回答前检索，有目标归属 | 无 | 无 | `limit × 20`，封顶 400（不变） |

回答前检索没有目标归属、也没有当前讨论与带入来源时，业务规则本来就一条也不放行，服务层直接返回空结果，不再发起一次检索。表里的表达式在沙箱里核对过：可空的字符串字段建倒排索引后，`or`、`in` 与 `is null` 都能在 Flat 检索内部生效。

预过滤正确的前提是它只放宽、不收窄。`vector_prefilter_test.dart` 里加了一组性质测试：随机生成材料页、消息、作答与各种范围，凡是 `hitInScope` 判为在范围内的来源，`vectorPrefilterFor` 生成的预过滤也必须放行；`EvidenceScopeRule` 以后改动时，这组测试会先失败。

### 6. 引擎参数与日志

`Zvec.initialize` 传入的 `ConfigData`：查询线程与 `optimize` 线程各 1 个，避免和界面线程争用小核；内存上限 128 MB。引擎要求内存上限大于 100 MB，设得更低时初始化直接失败。

Android 上原生代码的标准输出不会进入 logcat，因此使用 `LogConfig` 将警告写入应用缓存目录下的 `zvec_logs/`，单个文件达到 129 MB 时轮转，保留 7 天。zvec 0.8.0 对单个日志文件的大小有下限校验，2 MB 会让初始化失败，129 MB 是它接受的最小整数值，见 [zvec 0.8.0 日志参数校验](https://github.com/alibaba/zvec/blob/v0.8.0/src/db/common/config.cc)。

### 7. 构建、许可、发布与回退

`pubspec.yaml` 把 `zvec` 固定为 `0.8.0`，不写 `^`。zvec 仍在 0.x，跨小版本升级时先跑决定第 7 条的契约测试，再改版本号。

Android 构建只把 `libzvec_c_api.so` 放进 APK，大小 33,081,008 字节。已经核对：它的 LOAD 段按 16 KB 对齐（`0x4000`），满足 Android 15 起对 16 KB 页面设备的要求；动态依赖只有 `libc`、`libm`、`libdl` 与 `liblog`，不会和其他插件带来的 `libc++_shared.so` 冲突。

zvec 的 Dart 包是 Apache-2.0，Flutter 的许可页面会自动列出。C 库的发布包里没有附带第三方许可清单，第 3 步按 zvec 上游仓库列出的依赖整理成 `app/lib/platform/zvec_license.dart` 里的清单，用 `LicenseRegistry.addLicense` 补进关于页的许可列表，`main.dart` 启动时调用 `registerZvecLicense` 注册一次。

运行时只使用 zvec。切换在 0.2.0 之前完成，没有过渡版本：决定第 10 条设想的编译期引擎参数与旧库搬运代码没有落地，SQLite 实现与旧引擎依赖由第 6 步删除；打开索引时删除旧版索引留下的库文件，删不掉的留到下一次打开。需要回退时用 git 回到切换前的提交重新构建。

切换后第一次刷新要把全部来源重新嵌入。用远程嵌入服务的用户，这意味着按片段数计费并占用较长时间：两万个片段即使每次请求只用 100 ms，也要半个多小时。切换在 0.2.0 之前完成，库里只有测试数据，所以直接重建，不迁移旧索引的内容；旧版的 `vector_index.db`、`-wal`、`-shm` 在第一次打开时删除，没有搬运代码。

CI 的 Linux 测试任务下载 `zvec-sdk-linux-amd64.tar.gz`，按 `zvec_sdk.json` 里的 SHA-256 校验，目录放进 `actions/cache`，键取 zvec 版本号，再设置 `ZVEC_LIBRARY_PATH`；两个打包任务也把插件默认的 SDK 缓存目录 `~/.cache/zvec-dart` 放进 `actions/cache`，避免 GitHub Releases 偶发 504。

### 8. 测试

契约测试 `vector_index_contract_test.dart` 用同一组用例跑 `MemoryVectorIndex` 与 `ZvecVectorIndex`，在方案第 5 节列出的用例之外，补上这些：

| 类别 | 用例 |
|---|---|
| 生命周期 | 模型 A→B→A 快速切换，最后一次打开成功且 A 的内容还在；被占用超过重试时间，抛“索引正被占用”且目录未被删除 |
| 损坏恢复 | 删掉版本文件、删掉段目录、状态文件写成非法 JSON，三种情况打开后都得到空索引并触发一次重建通知 |
| 写入 | `WriteResult` 有失败计数时抛错；中途失败后 `indexedSources` 返回旧版本号 |
| 清空 | 刷新进行中调用 `clear`，之后的写入落到新的空 collection；改名后的目录在下一次打开时删除 |
| 统计 | `source_count` 在全部成功、部分失败、清理之后三种情况下与实际来源数一致 |
| 预过滤 | 第 5 节的两种预过滤下 zvec 与内存实现返回的来源集合相同；范围规则的性质测试在 `vector_prefilter_test.dart` 里 |

服务层的用例只换索引实现，断言不变，模型 A→B→A 的关闭与打开顺序由服务层用例覆盖。`vector_store_isolate_test.dart` 在 `ZVEC_LIBRARY_PATH` 可用时覆盖后台 isolate 的打开、写入、查询、统计，以及同一进程里两个 isolate 先后打开、关闭之后引擎仍可再用；没有设置这个变量时跳过并打印原因。这些用例由缪鹏维护，陈思源实现。

| 步骤 | 内容 | 验收 | 负责人 |

## 代价与边界

- 2026-11-16 在 `4a73460` 上分别构建未添加与仅添加 `zvec: 0.8.0` 的 arm64 release APK，文件分别为 40,785,711 字节（38.90 MiB）与 73,881,815 字节（70.46 MiB），增加 33,096,104 字节（31.56 MiB）。APK 以未压缩方式存放 33,081,008 字节的 `libzvec_c_api.so`，清单设置 `extractNativeLibs=false`，因此安装时直接从 APK 加载原生库，ZIP 条目的 16 KiB 对齐检查通过。
- Gradle 构建时从 GitHub Releases 下载 C 库，CI 需要缓存 `ZVEC_SDK_CACHE` 目录，否则会受到 Releases 偶发 504 的影响。
- zvec 没有跨文档事务，`replaceSource` 中途退出会留下新旧混合的片段；下一次刷新会重建这个来源，检索时服务层的版本核对会把过期片段排除。
- zvec 的 Dart 包没有封装文档迭代器，`indexedSources` 改为按调用方给出的来源键读取，清理用 `not in` 过滤表达式；两万个键时约 0.24 秒。
- 一个 collection 只能有一个句柄，打开与关闭的顺序从“可以随意”变成必须由服务层保证；漏掉的地方表现为语义检索暂时不可用，而不是数据损坏。
- 结构损坏时的重建意味着全部片段重新嵌入，使用远程嵌入服务的用户会因此产生费用与等待，所以重建只在第 3 节判定为损坏时发生。
- 引擎内存上限不能低于 100 MB，这是 zvec 的下限，不是知新的选择；它是上限，不是常驻占用。
- zvec 首次公开于 2026 年 2 月，版本仍在 0.x。依赖固定到具体版本，升级跨小版本时先跑本条的契约测试。
- 内测期间需要回退时，用 git 回到切换前的提交重新构建。决定第 10 条设想的编译期引擎参数与旧库搬运代码没有落地，回退后的版本按 SQLite 实现重新建索引。

## 替代方案

- 保留替换前使用的 `sqlite3_vec`，把范围写成 `vec0` 的元数据列、正文写成辅助列。sqlite-vec 0.1.9 支持在 KNN 内部按等值、不等与 `IN` 过滤，同样能省掉回表、在材料范围内不漏召回，包体不变，写入仍有事务。这是本条最接近的替代方案，比较见[方案第 3.1 节](../语义索引接入zvec方案.md#31-与改造-vec0-表结构的比较)。它的过滤不支持 `OR`，第 5 节两条带 `or` 的预过滤要改写成派生列（例如材料页存材料 ID、其他来源存空串），`IN` 会按每个取值各返回 k 条。没有采纳的原因是过滤表达能力弱，范围要靠派生列迁就，以后接稀疏向量与混合检索也没有余地。
- 向量放进 zvec，正文与来源信息仍留在 SQLite 的 `vector_entry`。没有采纳的原因是两份存储之间又要自己保证一致，检索仍要回表，zvec 一次调用带回字段的好处就没有了，同时还要承担两个原生库。
- 用 zvec 同时承担关键词检索，一次查询融合两路结果。没有采纳的原因是关键词索引现在由业务库触发器在同一事务里维护，搬出业务库后要另外保证两份存储一致，未配置嵌入模型的用户也要依赖 zvec。
- 第一版直接用 HNSW。没有采纳的原因是在当前数据量下 Flat 已经足够快，HNSW 建索引耗时长，会在手机上长时间占用后台线程。
