# ADR-0070 额度预留与失败结算口径

- 状态：已采纳（2026-11-25，服务端与客户端同日实施）；改定 [ADR-0069](0069-积分余额的本地副本与预留放行.md) 关于实例预算的一段，把 [ADR-0055](0055-模型调用协议与上限统一.md) 的客户端上下文上限最大值从 32768 改为 65536，计费权重仍按 [ADR-0066](0066-额度按缓存命中折算.md)，积分适用范围由 [ADR-0084](0084-嵌入与聊天共用积分余额.md) 扩展至嵌入
- 日期：2026-11-25

## 背景

额度按“先预留、再结算”两步扣。预留要在转发之前判断这一轮能不能放行，所以只能用请求内容和配置估算一个上限；结算按来源报告的实际用量多退少补。2026-11-25 的计量与计费审查发现，预留这一步把请求体的字节数当成了 token 数：中文一个字三字节，全部按未命中缓存计，输出按 `max_output_tokens` 全额乘四。一次满上下文的追问因此预留约二十一万计费 token，而免费额度是三十二万，账号用到约三分之一就会被判额度不足；同一请求在八成缓存命中、输出一千五百 token 时实际只计约一万六。图片以 base64 内联，一张五百 KB 的照片编码后超过整天的额度，带图请求永远被拒。

失败的尝试也按预留量结算。连接没有建立、来源返回 5xx、首字超时、响应类型不对，都以“没有拿到 usage”结束，结算沿用预留量；一次 502 可以扣掉二十多万，换三个来源就扣三次。这些失败多数没有产生上游费用，而在 [ADR-0069](0069-积分余额的本地副本与预留放行.md) 接上积分余额之后，多扣的部分会直接变成无法撤回的核销。

实例日预算是给免费额度兜底的。积分余额接进预留之后，付费用量也记进同一本实例账；一百个免费账号用满当天额度就能占完实例预算，之后付了钱的用户同样收到 429。嵌入的原始 token 也记在这本账上，与聊天的计费口径不同。

## 决定

聊天请求的输入按内容估算，与客户端同一套算法：非 ASCII 字符每个记一个 token，辅助平面的字符记两个，ASCII 每三个字符记一个；`instructions`、`tools`、每条输入的正文、函数调用的参数与工具结果都计入，`input_image` 每张按 2048 计，`image_url` 里的 base64 不按文字读。条目计数也一致：请求体固定 32 个 token，每条输入条目带 16 的包装，带工具调用的助手消息在线格式里额外展开成若干 `function_call` 条目（各带 16 的包装与 20 的调用开销），工具结果按实际发送的 JSON 文本估算，`tools` 为空时请求里不出现这个字段、两端都不计。估算函数在服务端 `server/internal/llmproxy/estimate.go` 与客户端 `app/lib/ai/llm_context_budget.dart` 各有一份，注释互相指认，改一端要同时改另一端。

输出预留不按 `max_output_tokens` 全额乘四，取请求上限与 4096 的较小值乘四。实际输出超过这个占位量时由结算补记，少记的部分最多是这一轮的差额；靠近额度末尾的请求因此不会因为按最大输出预留而被误拒。

结算按“这次尝试有没有可能产生上游费用”分档。请求没有发出、连接没有建立、来源返回非 2xx、首个有效输出之前收到失败事件且没有 usage，这些尝试记 0；已经向客户端转出输出、但没有拿到 usage 的尝试（客户端取消、流被截断、本轮预算用完），按输入估算加上已经转出的输出估算结算；来源返回 2xx 却没有报告 usage 的整段响应，按整段响应里的正文与工具参数估算输出，再与输入估算相加。流式请求收到 2xx 的整段响应时（来源忽略了 `stream`，或者回的不是流式事件）先读正文再决定：正文里带 usage 就按 usage 结算，能解析成 Responses 响应对象就按正文估算输出，页面、错误体与实例预算不足没有读正文的尝试仍然记 0。任何情况下都不再以预留量作为实际用量。路由用量统计同步按这个口径：记 0 的尝试不增加 Token，按估算结算的尝试把估算量单独计入“估算部分”。

实例账本只累计免费额度内的部分。预留时按账号当天的免费额度剩余算出这次请求占用的免费量，只有这一段计入 `llm_instance_usage`；超出免费额度、由积分承担的部分不进实例账本。结算时按同一账号与用途重新算一次免费额度的边界，把差额落到实例账本。实例预算不够放行免费部分时，预留按实例剩余量截断，调用方发现预留不足仍整单拒绝并把这笔预留结算退回。嵌入只有免费额度，账本口径不变。

客户端的上下文上限统一为 65536。`maxContextWindowTokens` 原来取 32768、默认值却是 65536，后者没有在任何地方生效；现在两者同值，读取保存的配置与复制配置时把超出上限的值夹回，设置页输入更大的值直接报错。

## 代价与边界

估算不是 tokenizer，误差按内容浮动。中文按一字一 token 估通常偏高，表格、代码与英文按三字节一 token 估通常偏低，预留与实际用量之间仍有一段差距；预留偏多只影响额度末尾的放行，结算会把多预留的部分退回，偏少则由结算补记，单次最多补到实际用量。

失败按 0 结算的尝试可能产生上游费用。连接失败、非 2xx 与交付前的失败事件通常没有计费，但来源侧仍可能对已经处理的输入收费；来源回了 2xx 但正文是页面或错误体、或者实例响应预算不足没有读正文的尝试同样记 0，这类尝试的上游成本由实例承担，次数少时看不出来，来源长期报错时需要按后台的失败明细处理。反过来，客户端取消与首字超时按输入估算结算，可能比上游实际收取的多，也可能少，估算精度受同一套字符规则限制。

实例账本只记免费部分之后，付费部分的成本不再有实例级熔断。积分在购买时已经付过钱，单账号的额度由余额副本约束，但某个账号在余额充足时连续发起的长请求不再受实例预算限制；如果以后出现异常用量，需要另加按账号或按日的付费上限，而不是复用免费额度的实例预算。

输出预留按 4096 占位，实际输出到 32768 的请求会在结算时补记一大段，靠近额度末尾时可能把账号用量推过免费额度。这部分用量按“先免费、再积分”的规则落到积分，余额不足的请求会在核销时失败，用量已经交付、无法撤回。

两端的估算函数需要手工保持同步。服务端改了字符规则或图片固定值，客户端没有改，发请求前的判断会与服务端的预留不一致；目前只有注释互相指认，没有共享代码或自动化核对。

## 替代方案

保留按请求体字节估算，只把输出上限调小。没有采纳的原因是中文与 base64 图片的字节数都与 token 数差一个量级，调输出只能把误拒的时点往后推，输入占的大头仍在。

失败一律记 0。没有采纳的原因是已经转出部分输出、上游已经计费的请求会变成免费；按输入估算加已转出输出估算是这两种情况之间可执行的折中。

失败沿用预留量，只在后台标注。没有采纳的原因是预留本身偏大，一次 502 的扣减会超过一轮正常对话，且核销不可撤销。

付费用量继续记进实例预算，另设一个更高的付费上限。没有采纳的原因是当前只有一个实例预算，再设一个上限要同时调两处配置，而付费用量已经有购买收入覆盖，直接用免费部分作为实例预算的边界更简单。

客户端上下文上限保持 32768，把默认值也调下来。没有采纳的原因是模型的上下文窗口是 64K，调到 32K 会让默认配置用不满一半；统一到 65536 与默认值一致，超出上限的输入由设置页与读取逻辑拦住。

## 影响

- 估算与结算：[estimate.go](../../server/internal/llmproxy/estimate.go) 新增输入、输出与流式增量的估算；[proxy.go](../../server/internal/llmproxy/proxy.go) 的 `budget`、`billedTokens`、`copyStream` 按新口径结算；[quota.go](../../server/internal/llmproxy/quota.go) 与 [pg/quota.go](../../server/internal/store/pg/quota.go) 只把免费部分记进实例账本。
- 计费口径：[billing.go](../../server/internal/llmproxy/billing.go) 的 `Usage.Billed` 与权重不变；[ADR-0066](0066-额度按缓存命中折算.md) 的计费 token 定义继续有效。
- 客户端：[llm_config.dart](../../app/lib/ai/llm_config.dart) 统一上下文上限，[settings_page.dart](../../app/lib/ui/settings_page.dart) 拒绝超过上限的输入，[llm_context_budget.dart](../../app/lib/ai/llm_context_budget.dart) 的估算函数与服务端互相指认。
- 文档：[server/README.md](../../server/README.md) 的模型代理、额度与配置表同步改写；[ADR-0069](0069-积分余额的本地副本与预留放行.md) 的实例预算段由本条改定。
- 上线：没有表结构变化，不需要重建库；部署之后核对三项：一次满上下文追问的预留明显低于改造前，`llm_instance_usage` 在付费请求之后不增长，来源返回 502 时账号当天的 `llm_usage` 不增加。
