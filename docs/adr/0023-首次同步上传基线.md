# ADR-0023 首次同步上传当前数据为基线

## 状态

已采纳。

## 日期

2026-11-17

## 背景

[ADR-0008](0008-取消单机边界引入账号同步与模型代理.md) 把增量同步分两步交付：先做整库备份，再按提交推送与拉取。业务表主键改为 UUIDv7 之后，两台设备生成的标识不再相撞，服务端也有了按账号保存的线性提交序列，客户端因此可以开始接入第一步之外的增量同步。

接入时遇到一个本地历史无法直接表达的问题：本机数据库的初始基线提交 `0` 只有投影、没有变更明细，用户在做这次改动之前写入的记录从来没有作为提交推送过；一旦本机在接入同步之前清理过历史或裁剪过留存，仅推送保留提交也无法还原当前数据。如果只推送接入之后的提交，服务端会缺少接入前的全部记录，另一台设备拉取到的是一个不完整的状态。

## 决定

1. 一台设备第一次同步时，先拉取服务端已有的提交并在本机应用，再把本机当前业务投影作为一份或几份基线提交上传，最后把提交里引用到的附件按内容哈希传到服务端。基线提交的 `request_id` 由设备标识、分片序号与分片内容哈希组成，重试同一份分片时服务端按请求编号去重。
2. 基线只表达当前数据，不重放本机历史；本机提交历史仍然完整保留，之后的本机写入按提交增量推送。另一台设备拉取基线时按“主键已存在就整行覆盖、不存在就新增”应用，因此基线可以在任何一台设备上成立。
3. 同步游标保存在应用私有目录的 `cloud.json`，不进数据库、数据包与整库备份。游标记录服务端位置、已经对齐到的本机提交编号，以及拉取远端提交时在本机新生成的提交编号；恢复备份或换机之后从当前数据重新对齐，不沿用别的设备的编号。
4. 拉取到的远端提交在本机生成一条同样净变化的提交，撤销与数据版本页照常可用；服务端只保证序列线性，不合并字段，同一字段两台设备同时修改时后到达的覆盖先到达的，被覆盖的值留在提交历史里，沿用 [ADR-0008](0008-取消单机边界引入账号同步与模型代理.md) 的冲突规则。
5. 附件按内容哈希随提交同步：推送之后上传服务端还没有的附件，拉取之后下载本机缺少的附件并核对哈希。附件与备份的字节仍放对象存储，服务端不解析学习内容。

## 代价与边界

- 第一次同步会把当前本机数据整体上传一次，记录多的设备第一次同步耗时与流量都高于之后每次。基线分片只控制单次请求体大小，不改变总量。
- 两台设备各自已经有不同数据、又都第一次接入同步时，后上传基线的设备会按主键覆盖同名字段，等同一次大范围的“后到达覆盖”。这是冲突规则在首次接入时的自然结果，界面在同步结果里说明这次上传了基线，用户可以在数据版本页找回被覆盖的值。
- 游标不进备份，因此从整库备份恢复之后，下一次同步会按恢复后的数据重新对齐；恢复前在云端、本机都没有保留的提交不会再出现在云端。删除云端数据或删除账号之后同理。
- 基线只覆盖当前投影，不包含已删除记录的删除标记；其他设备上原先存在、这台设备没有的记录不会被基线删除，要等后续提交表达删除。两台设备的走查仍按 [ADR-0008](0008-取消单机边界引入账号同步与模型代理.md) 的约定继续做。
- 附件的上传与下载在提交之后单独进行，网络中断时提交已经同步、附件可能还没补齐；下一次同步会重新检查缺失项，业务行里的哈希引用不会因此改变。

## 替代方案

- 只推送本机保留提交，不生成基线。没有采纳的原因是清理过历史或裁剪过留存的设备无法用保留提交还原当前数据，另一台设备会得到不完整的状态。
- 第一次同步直接上传整库备份、其他设备下载恢复。没有采纳的原因是整库备份会替换目标设备上的全部数据，也会把本机的提交编号带过去，之后两台设备的提交序列无法按编号对齐；整库备份仍保留为换机与灾难恢复的手段。
- 服务端保存当前数据投影并提供快照接口。没有采纳的原因是服务端已经按契约只保存不解析的提交序列，增加投影接口会让服务端开始理解客户端表结构，与 [ADR-0008](0008-取消单机边界引入账号同步与模型代理.md) 的边界冲突，也让数据版本与冲突规则出现两套。
