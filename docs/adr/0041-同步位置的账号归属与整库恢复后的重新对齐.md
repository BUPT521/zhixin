# ADR-0041 同步位置的账号归属与整库恢复后的重新对齐

## 状态

已采纳

## 日期

2026-11-20

## 背景

2026-11-20 的 `main`（合并提交 `91c740a`）上，阶段 1 的同步位置与整库恢复两部分已经合入：同步的两个位置在 [ADR-0039](0039-数据版本的提交类型与同步冲突记录.md) 里从应用私有目录的偏好文件移进库里的 `revision_cursor`，提交身份与按格变基在 [ADR-0040](0040-数据版本的提交身份与同步变基.md) 里定下，schema 同时升到 29，整库恢复时数据库连同这两个位置一起回到备份那一刻。两处遗留问题因此暴露出来：退出登录、删除账号与清除云端只清偏好，库里的推送位置仍然阻塞裁剪与清理历史，同一账号重新登录时偏好里没有状态，又按首次同步整份上传基线；整库恢复之后数据库与同步位置一起回到旧备份，下一轮同步从旧位置拉取，备份之后推送过的改动因此又被拉了回来。这两处分别是改进方案里的 G4 与 G5，前者让“清理历史”长期不可用，后者让恢复的效果大部分被同步撤回。

当时团队四人各自开发，内测规模只有几十人，云端数据可以整体清空重传；按 [ADR-0001](0001-开发阶段不向下兼容.md) 与 [ADR-0017](0017-表结构变化仍清空数据.md)，开发阶段不向下兼容，表结构可以直接改，版本不一致时清空重建，不写迁移。这两处问题都会直接丢改动或者卡死入口，修法需要在同步位置里记下账号身份，整库恢复也需要表达成一条可以推送的提交，取舍见 [改进方案](../数据版本系统对照git的改进方案.md) 第 3.3、3.4 节，因此单独记一条决定。

## 决定

同步位置带上账号归属。`revision_cursor` 增加 `scope` 列（随 schema 29 一起建好），同步的两个位置 `sync.pushed` 与 `sync.server_head` 写入“账号编号 + 实例来源”的 SHA-256 前 32 位，检索索引等只登记位置的读者留空。判断这个身份是否还有本机的同步位置时按 `scope` 比较，不看偏好文件里的会话状态：位置的 `scope` 等于当前身份才继续增量同步，否则按首次基线重新建立。账号编号与实例来源在 `syncScopeFor` 里合成，两个位置写入时都带上同一个值。

退出登录、删除账号与重设密码时，`sync.pushed` 的 `blocking` 改成 0，位置与 `scope` 保留；`sync.server_head` 本来就不阻塞裁剪，位置同样保留。裁剪与清理历史只看 `blocking = 1` 的位置，所以退出之后历史清理立即可用。重新登录同一 `scope` 时从原位置继续增量同步，只推送退出期间的新提交，不再整份上传基线；`scope` 不同（换了账号或者换了实例地址）按新账号处理，新身份下一次推进位置时覆盖旧的 `scope`，换回原账号也要重新建立基线。

清除云端数据时两个同步位置与恢复标记 `sync.restore_align` 一并删除，这一点与退出登录不同。云端序列已经清空，保留旧位置会让界面按“上次同步过”显示状态，而实际同步要先上传基线并再次确认，这一轮同步在用户确认之前就报失败结束，界面状态与同步要求对不上，用户也看不到下一步该做什么。删除位置之后下一次同步按首次基线重建，与云端为空的状态一致。

整库恢复在替换数据库之前先保存恢复点，并单独读一份恢复前的业务投影，因为换库之后原来的库就读不到了。换库成功之后在恢复后的库里补记一条 `kind = restore` 的提交，净变化是“恢复前投影 → 恢复后投影”的差异，删除也在其中；`sync.pushed` 写成这条提交的父提交，`sync.restore_align` 记下这条提交的编号。补记与清空 `sync_shadow` 在同一个事务里完成，恢复之前登记的遮蔽行不再对应恢复后的提交。库里没有同步位置时（这个库从来没有同步过）不补记，也不标重新对齐，恢复不涉及云端。

待重新对齐期间自动同步不排期，账号页的立即同步先向用户确认“云端会改成恢复后的内容”，这条确认复用首次基线的 `BaselineConfirmationRequired`，只是 `afterRestore` 的文案不同。确认之后这一轮不按旧位置拉取，只按普通推送依次发送恢复提交与之后的新提交，推送完成之后两个位置收敛到当前服务端位置与本机 `HEAD`，推送期间新产生的提交留到下一轮，恢复标记与遮蔽行一起清掉。其他设备拉到的是恢复前后的差异，表现成一次正常的整版恢复。

恢复前投影读不出来或者补记失败时，`sync.restore_align` 记 -1，下一轮同步按首次基线重新对齐；恢复前后没有差异时不形成提交，恢复标记记 0，两个位置只挪到当前服务端位置与本机 `HEAD`。两条退路都不再按旧位置拉取，恢复之前的改动不会再被拉回来。

## 代价与边界

`scope` 随实例地址变化，换实例视为新账号：同一个账号在两套实例上的同步位置互不通用，各按首次基线建立一份。`revision_cursor` 以位置名为主键，库里同一时刻只保留一个身份的同步位置，换账号之后新身份下一次推进位置时覆盖旧的 `scope`，换回原账号时也要重新建立基线；换账号越频繁，整份上传的次数越多。

退出登录只改推送位置的阻塞标记，位置与 `scope` 留着，代价是裁剪与清理历史从此可以越过这个位置；清理历史之后 `HEAD` 变成一条没有净变化的基线，退出期间还没有推送的改动因此不会在重新登录后补推，云端停在退出前的位置。这条代价换来的收益是退出之后历史清理立刻可用，不必先登录再同步。

恢复提交一次包含全部差异，可能很大：单条提交受 2 MiB 上限约束，单次请求受 16 MiB 上限约束，超过单条上限时这一轮同步以 `payload_too_large` 失败；恢复提交需要按变更明细拆成多条再推，拆分留到后续做。恢复前后的数据量越大，这一条越容易触发。

恢复前投影读不出来或者补记恢复提交失败时只能退回首次基线：本机现有记录整份作为基线上传，服务端序列因此多出一整份基线，序列只增不减，这份重复数据会一直留到清除云端数据。恢复前保存恢复点失败时恢复本身中止，当前库不动，所以这条退化路径只覆盖投影读取与补记失败，不等于数据已经丢失。

待对齐期间自动同步不排期，用户在恢复之后写入的改动要等到下一次手动同步确认之后才上传；账号页用 `restoreNeedsConfirmation` 提示这一点，否则表现为同步长时间不动、用户不知道要先点一次立即同步。

退出登录与清除云端对同步位置的处理不同，理解成本增加：一个保留位置、一个删除位置，后续行为也不同，前者重新登录接着同步，后者重新上传基线。这个差异来自云端序列是否还在，判断依据要写进代码注释与界面说明，否则后来的人容易按同一种情形处理这两种操作。

`scope` 只保存哈希，不记录账号编号与实例地址，排查时不能从库里直接看出这个位置属于哪个账号与实例，只能按登录状态与账号页的信息反推。选择哈希是为了避免账号与实例信息进入可能导出的库与整库备份，代价是排障时少一条线索。

## 替代方案

退出登录时只清偏好文件、不改库里的位置，也就是 G4 的成因。改动集中在账号操作，同步服务不用改；但库里的 `sync.pushed` 仍然 `blocking = 1`，退出之后“清理历史”一直提示还有修改没有同步，裁剪下界停在退出时的位置，历史只增不减，同一账号重新登录又按首次基线整份重传。放弃。

同步位置放进 `cloud.json` 之类的偏好文件。偏好文件不随整库恢复一起回去，换机与恢复之后位置与库里的数据对不上；ADR-0039 已经改由库里保存位置，裁剪与清理统一读 `revision_cursor`，位置再放回偏好文件会让读者分散在两处。放弃。

恢复之后本机现有内容整份重传为一条基线。实现最简单，与首次同步共用同一条路径；但服务端序列会因此多出一整份数据，其他设备拉到的是一条基线而不是恢复前后的差异，G6 的浪费在每次恢复时重演。放弃。

按服务端的提交序列回放算出恢复该推什么。这样客户端不需要保存恢复前的投影；但服务端只保存提交、不保存投影，客户端要重建远端投影就得重放全部远端提交，代价随序列长度增长，而恢复流程已经在换库之前读过恢复前的投影。放弃。

`scope` 直接保存账号编号与实例地址的明文。排查时可以直接看出位置属于谁，但这两项会随库与整库备份导出，泄露面比一个哈希大，而同步判定只需要相等比较。放弃。
