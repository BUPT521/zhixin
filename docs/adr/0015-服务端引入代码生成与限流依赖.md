# ADR-0015 服务端引入代码生成与限流依赖

## 状态

已采纳。PostgreSQL 存储、OpenAPI 生成和认证限流均已实施，配置与限流额度见 [服务端工程说明](../../server/README.md)。

## 日期

2026-11-14

## 背景

[ADR-0009](0009-API后端采用Go与分层框架.md) 决定 HTTP 层只用标准库、第三方依赖只在标准库没有对应能力时加入，目前 Go 的第三方依赖只有 `golang.org/x/crypto` 的 argon2id，全部存储在内存里，接口契约 `openapi.yaml` 与手写处理函数之间靠人工核对，登录、注册与刷新令牌没有频率限制。

接下来的三块工作都会碰到 ADR-0009 的依赖口径：PostgreSQL 驱动标准库没有，只能引入第三方；存取代码、请求与响应结构体手写会与 `schema.sql`、`openapi.yaml` 脱节；限流标准库也没有现成实现，而登录与刷新令牌是批量尝试成本最低的入口。

评估见 [轮子与技术选型评估第 3.1、3.2、3.3 节](../轮子与技术选型评估.md#31-postgresql-存取用-pgx-与-sqlc)。

## 决定

1. PostgreSQL 驱动用 `github.com/jackc/pgx/v5`。它是纯 Go 实现，支持 `database/sql` 之外的连接池与批量协议，也是社区最活跃的驱动；ADR-0009 的“标准库优先”在这里让位于没有对应能力的事实。
2. 存取代码用 `sqlc` 生成。查询写进 `server/internal/store/queries/` 下按业务包分开的 `.sql` 文件，`sqlc.yaml` 指向现有的 `schema.sql` 与这些查询文件，生成类型化的 Go 方法到 `server/internal/store/db/`。生成代码与客户端 drift 的生成文件一样提交入库，CI 增加一步重新生成并核对没有差异。`sqlc` 只作开发期工具，写进 `tools.go` 或者 README 的安装说明，不进入运行时依赖。
3. 账号、会话、提交序列、备份元数据与模型用量的存储接口由生成代码实现，业务包之间仍只通过接口与 `auth.PrincipalFrom` 交互，保持 ADR-0009 第 2 条的分层。推送时锁定 `sync_head` 再追加的操作写成一条带 `SELECT ... FOR UPDATE` 的查询，由 `sqlc` 生成单事务方法。
4. 接口契约用 `oapi-codegen` 生成严格的服务接口，挂到标准库 `net/http` 的 `ServeMux` 上，保留 ADR-0009 “不引入 Web 框架”的口径。请求与响应结构体、路径参数与状态码由生成代码约束，契约改了而实现没跟上时编译失败。生成的服务接口与现有的手写处理函数之间要有一层适配，适配只做类型转换与问题响应映射，不放业务逻辑。
5. 限流用 `golang.org/x/time/rate`。按账号与来源地址各建一个令牌桶：登录与注册按来源地址限流，刷新令牌按账号与来源地址同时限流，防止同一账号被并发尝试。限流状态保存在进程内存里，单实例部署下够用，多实例部署时另行决定是否共享。
6. 客户端是否也从契约生成 Dart 代码暂不定。接口数量还少，手写调用代码成本不高，等客户端接入登录与备份之后再评估。
7. 引入这三项之后，Go 的直接第三方依赖是 `x/crypto`、`pgx/v5`、`oapi-codegen/runtime` 与 `x/time`，生成器 `oapi-codegen` 与 `sqlc` 只在开发和 CI 中运行。ADR-0009 第 1 条的依赖清单按本条更新。

## 代价与边界

- 团队要维护两个生成配置（客户端的 `build_runner` 与服务端的 `sqlc`、`oapi-codegen`），提交前与 CI 都要跑重生成核对，提交节奏比以前慢一些。
- 生成代码会随 `schema.sql` 与 `openapi.yaml` 变长，每次改表或改契约，diff 里都会出现生成文件，评审时要先看源文件再看生成结果。
- `oapi-codegen` 生成的接口与现有的 `httpx` 问题响应、请求体上限、访问日志中间件之间需要一层适配，适配层本身容易堆积逻辑，评审时要限制它只做转换。
- `x/time/rate` 的令牌桶只在进程内有效，重启后计数清零，多实例部署时各实例分别计数。内测一台机器够用，公测前再定共享方案；限流命中时返回 429 与 `application/problem+json`，客户端要按 `Retry-After` 等待，不自动重试。
- `sqlc` 生成的方法接收参数结构体，与现在手写在业务包里的存储接口签名不同，三个业务包的存储接口要按生成的方法重写一遍，测试里的内存实现也要跟着改。
- 1.0.0 之前表结构直接改 `schema.sql` 重建，`sqlc` 重新生成即可，不写迁移。

## 替代方案

- 用 `database/sql` 加 `lib/pq`。没有采纳的原因是 `lib/pq` 已进入维护状态，`pgx` 的性能与类型映射更完整，社区支持也更好。
- 用 GORM 一类 ORM。没有采纳的原因是与 ADR-0009 的分层冲突，ORM 会将存储细节带进业务包，而且 `SELECT ... FOR UPDATE` 这类同步需要的语句在 ORM 里表达得不直观。
- 手写 PostgreSQL 存取代码。没有采纳的原因是 `schema.sql` 现在有 7 张表、随同步与备份还会增加，手写与表结构容易脱节，`sqlc` 在编译期就能发现列名与类型错误。
- 用 `chi` 的路由与中间件。没有采纳的原因仍与 ADR-0009 相同，标准库路由已经够用，`oapi-codegen` 也支持直接生成标准库实现。
- 用 `golang.org/x/time/rate` 之外的第三方限流库（如 `ulule/limiter`）。没有采纳的原因是它们大多要额外的存储（Redis 或内存后端），官方扩展库已经覆盖令牌桶这一种用法。
