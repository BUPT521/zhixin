# ADR-0088 核销流水的本地认领

- 状态：已采纳（2026-11-27，服务端同日实施）；`nowpay_charge` 增加可空的 `claimed_at` 一列（纯新增列，不重建库），补充 [ADR-0067](0067-聊天额度改走即刻收积分包.md) 与 [ADR-0073](0073-余额副本的快照、刷新与放行原因.md) 的核销队列口径
- 日期：2026-11-27

## 背景

核销流水有三个入队来源。`Record` 写完流水之后立刻排一次；`Resume` 在每次请求开工前把这个账号还没有确认的流水各排一次，最多四条；`Sweep` 每十分钟把创建超过五分钟、仍未终结的流水再排一次，一批五十条。三处都只看数据库里的状态，既不检查队列里有没有同一笔，也不在发送之前认领它。

队列是单协程，同一笔流水的几份任务会依次执行，每一份都把同一个 `out_request_no` 再核销一次。本地因此没有任何去重，重复扣款完全依赖即刻收按请求号幂等；这一点只有接口文档的约定，仓库里只有 `idempotency_probe_test.go` 的一条核对用例在验证它，而这条用例默认跳过、至今没有跑过。

同一批流水还会反复占住队列。一次核销的超时是二十秒，队列容量二百五十六；一个用户在队列积压时每来一次请求就再排最多四条，队列很快被同一批流水填满，其他账号的流水排不进来，只能等下一轮。

## 决定

去重分两层。进程内，`Meter` 记一份正在队列里或正在执行的流水编号，入队时同一笔流水同一时刻只留一份，任务结束（无论成功、失败还是跳过）之后释放。数据库上，发送之前先认领：`nowpay_charge.claimed_at` 推到当前时刻，条件是这笔流水仍是 `pending`、并且 `claimed_at` 为空或者上一次认领已经超过租约。认领不到就丢弃这一份任务，不发核销、不落状态。

认领不改状态，流水保持 `pending`。把认领写成 `processing` 看起来更直接，但认领之后进程可能退出、请求根本没有发出去；`processing` 表示“发过、结果未知”，补查只按请求号查结果，查不到就一直停在 `processing`。这一笔积分从此在本地被当成已经申请，用户可用积分少一块，而即刻收一侧根本没有扣过。保持 `pending` 之后，认领过期就能重发同一个请求号，与今天 `pending` 重试的口径一致，也是探针要验证的那条约定。

租约定为两分钟：长于一次核销调用的二十秒超时，短于全局补查的十分钟一轮。进程在认领之后退出，最多等两分钟就能重发；两个进程同时在跑时，同一笔流水只有认领成功的那一个发得出去。

`TestProbeVerifyIsIdempotentPerOutRequestNo` 从“有环境时跑一次”改为发版前必跑：它用与实例同一套 `api.env`，在沙箱或测试商品上对同一个请求号连续核销两次，比较状态、金额与余额。本地认领只保证同一时刻只有一处发送，结果未知之后的重发仍然依赖幂等；探针的结果写进[即刻收整改验收记录](../即刻收整改验收记录.md)，不为幂等时按那一节的处置把重发改成本地终态。

## 代价与边界

每一笔核销在发送之前多一次数据库写入。认领用的是一次按主键的条件更新，代价与流水本身的读写同一量级。

进程内集合在重启之后是空的，补查会把流水重新排一次；那一份由数据库认领拦住其他进程，本进程里只有这一份，所以不会同时发出两份。重启时如果上一份任务已经在发送途中，两分钟之后仍然会重发一次同一个请求号，这是 `pending` 重试本身的语义，不是这次去重能消除的。

租约之内进程崩溃，这一笔流水要等到租约过期（最多两分钟）才会被重新认领；认领本身失败（数据库不可用）时这一份任务直接丢弃，流水留在 `pending`，下一轮补查再排，核销因此晚一轮。

去重覆盖的是“同一时刻”，不覆盖“上一次结果未知之后的重试”。后者仍然按原请求号重发，靠即刻收幂等兜底；探针没有跑过、或者跑出来不幂等时，按验收记录的处置处理。

## 替代方案

入队时直接把 `pending` 改成 `processing` 认领。没有采纳：认领之后进程可能退出，请求根本没有发出去；`processing` 只能按请求号查结果，查不到就一直停在 `processing`，这笔积分在本地被当成已申请、在即刻收一侧却没有扣过。

只做进程内去重。没有采纳：重启之后集合是空的，多进程部署时也各记各的；队列被同一批流水填满的问题可以缓解，但没有任何记录说明这一笔正在被谁处理。

只做数据库认领。没有采纳：同一笔流水仍然会被反复塞进队列，每一份都要先写一次数据库再被丢弃，队列满时把其他账号的流水挤出去。

在队列入口按账号限流、每笔流水只允许入队一次。没有采纳：限流只能减少重复，不能保证同一笔流水不被重发；真正需要的是“同一时刻只有一处发送”，认领表达的正是这件事。
