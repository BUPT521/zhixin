# ADR-0040 数据版本的提交身份与同步变基

## 状态

已采纳

## 日期

2026-11-20

## 背景

2026-11-20 的 `main`（`81b6ddd`，schema 28）上，客户端的数据版本系统已经按 [ADR-0039](0039-数据版本的提交类型与同步冲突记录.md) 完成提交类型、读取位置、检查点与冲突记录的改造：提交只追加，拉取先于推送，被这次拉取覆盖过的本机提交不再推送。对照 git 的做法逐项比较之后，提交身份、拉取后推送与合并规则三处仍然与 git 的对应做法不一致，方案里编号为 G1、G2 与 G3，其中 G1 与 G2 会直接丢改动或者造成两台设备分叉，本条目决定这三处的改法。判断基于 `81b6ddd`，方案文档在它之后单独提交，代码与 schema 没有变化。

G1 是 `request_id` 同时承担三种互不兼容的用途。本机用它做重试去重键，多数编号又由命令参数算出，同参数的第二次调用因此被判成重试，直接返回旧提交、不执行写入；暂停目标之后再恢复、再暂停，第二次暂停不会生效，删掉一条记忆之后重新添加同样内容也一样。推送时服务端按这个字段永久去重，而撤销会释放目标提交的 `request_id`，用户重做同一动作得到同一个编号，推送之后会被当成重复丢掉；整库恢复用的 `l-<设备前缀>-<提交编号>` 回退编号在恢复旧备份之后与复用过的提交编号相同，同样被丢掉。拉取时远端提交的编号与本机某条提交相同就按重复跳过，两台设备各自做一次同参数的新增，会各留一份不同的行。

G2 是推送时的跳过范围过大，而且遮蔽集合不持久。一条本机提交只要有一个格子（表、主键与列合起来算一格）被远端覆盖，整条都不推送，同一提交里其他行、其他列的改动一起作废；几乎每张业务表都有 `updated_at`，两台设备改同一行的不同列也会在它上面重叠，本机真正改过的内容列被一起丢掉；这个判断对拉取之后才产生的本机提交同样生效，用户在同步过程中刚做的修改也会被跳过；遮蔽集合只放在内存里，拉取成功而推送失败之后下一轮同步的集合为空，被覆盖的旧值又会被推回服务端。G3 是同一个原因在界面上的表现：远端应用按列做三方比较时，`updated_at` 也会记一条 `concurrent_update`，数据版本页因此出现“更新时间被覆盖”这类用户无法理解的冲突。

当时团队是四个人各自开发，内测规模只有几十人，两台设备并发修改同一行的机会不多，一旦发生，用户却无从判断以哪一边为准；按 [ADR-0001](0001-开发阶段不向下兼容.md) 与 [ADR-0017](0017-表结构变化仍清空数据.md)，开发阶段不向下兼容，表结构与数据包可以直接改，版本不一致时清空重建，不写迁移函数。这几个条件决定了可以在一次 schema 升级里同时改表与同步规则，不必为旧字段保留兼容分支，代价是本机历史与内测数据一起清空。

## 决定

提交身份改用 `revision_commit.uid`。`revision_commit` 增加 `uid TEXT NOT NULL` 与唯一索引，本机提交在 `_appendCommit` 里生成 UUIDv7 文本，长度为 36 字节，与业务表主键使用同一个生成器（[ADR-0018](0018-业务表主键改用UUIDv7.md)），列值长度上限按 64 字节校验；远端提交沿用服务端带来的 uid。首次同步的基线提交没有对应的 `revision_commit` 行，它的 uid 由设备编号前 8 位与该块变更明细的 SHA-256 前 32 位拼成，长度不超过 41 字节，同一内容重发时保持不变，失败后的重发因此会被服务端的永久去重当成重试；这个值不来自 `revision_commit.uid`。推送时 `request_id` 字段一律填 uid，服务端仍按它跳过已经收到过的提交；拉取时按 uid 判断远端提交是否已经应用。两台设备各自完成一次同参数的新增，会得到两个不同的 uid，因此都会应用，行集合一致。服务端的接口、字段与存储都不改，协议里这个字段的含义从“幂等键”变成“提交身份”，`syncRequestIdFor` 与 `l-` 前缀的回退编号删除。

本机的 `request_id` 只保留“同一次用户动作在短时间内重试”这一个用途，判重试需要两条同时成立：同编号旧提交的 `created_at` 落在最近两分钟内，并且这条旧提交仍然是当前 `HEAD`，也就是它之后没有任何提交。只看时间窗口会误判，因为同一个动作名与同一组参数在几秒内重复发生时，第三次动作会命中第一次留下的 `request_id`，按重试直接返回第一次的提交与结果；“暂停、恢复、再暂停”与“撤销之后立刻重做同一动作”都落在这种情况里。以“仍然是 `HEAD`”作为第二条判据之后，这两次动作之间已经产生了提交，第一次的提交不再是当前 `HEAD`，判重试不成立。两条中有一条不满足时，`_run` 先置空旧提交的 `request_id`，再照常执行写入。这样暂停、恢复、再暂停能够生效，界面双击与网络回调造成的重试仍然去重。界面在用户动作发生时生成一次性编号、重试时复用该编号的做法更彻底，但要逐个修改 29 处 `commandId` 调用，安排在后面单独做。

撤销不再释放 `request_id`，本机提交与远端提交都不释放。判重试的两条判据已经覆盖“用户重做同一动作”的情况，释放编号反而会让重做被服务端的永久去重当成重试丢掉；撤销远端提交时同样不释放，旧位置重拉时它仍然按 uid 判断为已经应用。

新增 `sync_shadow` 表保存已被远端取代的本机格子，遮蔽集合改由数据库记录。表里记 `table_name`、`row_key`、`column_name` 与 `upto_commit`，前三列上有唯一约束；`column_name` 用空字符串表示整行变化，因为 SQLite 的唯一约束认为两个 NULL 互不相同，用空字符串才能让整行遮蔽与列级遮蔽一样只留一行。整行变化时按表与主键记一行，不再细分到列。拉取应用一条远端提交时，对它真正写入的每个格子登记一行：列级变化记到列，新增、删除与整行覆盖记整行。`upto_commit` 取应用这条远端提交之前的本机 `HEAD`，含义是编号不大于它的本机提交在这个格子上的改动作废；同一个格子再次登记时取较大的 `upto_commit`。遮蔽行与远端提交在本机形成的 `remote` 提交写进同一个事务，拉取成功而推送失败时它仍然在库里。

推送从整条跳过改为按格变基，作用相当于 git 的 `pull --rebase`，粒度从行细到格子。每条待推送提交先去掉被遮蔽的格子：列级变化去掉对应的列，被整行遮蔽的行整条去掉；剩下的部分照常推送，剩余为空的提交不推，推送位置照常前进。编号大于 `upto_commit` 的本机提交不受影响，所以同步过程中用户新做的修改照常推送。剩余部分里的 `before` 不改写，因为被保留下来的列远端没有动过，其他设备上这些列的旧值与本机一致。推送位置越过某条遮蔽行的 `upto_commit` 之后删除这一行；裁剪与清理历史删掉被遮蔽的本机提交之后，`upto_commit` 早于新保留下界的遮蔽行一并删除。

`revisionBookkeepingColumns`（目前只有 `updated_at`）按维护列的合并规则处理，作用相当于 git 按文件指定合并驱动。远端应用时维护列不记冲突，冲突记录只保留用户能看懂的内容列；判断剩余部分时维护列仍然按格子遮蔽，被遮蔽时只从剩余部分去掉这一列，不影响同一行的其他列，也不让整条提交作废。这样两台设备改同一行不同内容列时双方的值都能保留，维护列由每次写入改成当前时间，两边的时间戳不同，这类差异不再产生冲突记录。冲突记录本身的字段与写回方式沿用 [ADR-0039](0039-数据版本的提交类型与同步冲突记录.md)，不改。

## 代价与边界

schema 从 28 升到 29，按 [ADR-0017](0017-表结构变化仍清空数据.md) 版本不一致即清空重建，不写迁移：`revision_commit` 增加 `uid` 与唯一索引，新增 `sync_shadow` 表。开发期的旧库在打开时清空，本机历史、命名版本与内测数据的丢失由团队承担；服务端的 `ClientSchemaVersion` 在同一个 push 里改成 29，两端一起升级，升级之前 28 的客户端推送与上传都会被拒绝。

遮蔽行的条数随远端覆盖的格子数增长，没有独立上限，只靠两个时机删除：推送位置越过 `upto_commit`，以及裁剪与清理历史删除这些本机提交。设备长期不推送（退出登录、断网、同步持续失败）时，遮蔽行留到下次推送越过对应位置才删除；因为被遮蔽的本机提交本身也受保留条数与容量预算约束，遮蔽行的条数不会超过保留历史里被远端覆盖过的格子数，代价是库文件里多出一张随历史增减的小表，以及推送时为每条提交的改动格子查询一次遮蔽行。

服务端仍然永久保留见过的提交身份并跳过重复，`seen` 集合里存的仍是提交带来的字符串，含义从“按命令参数算出的请求编号”变成“一条提交的 uid”；协议不清理这部分记录，所以集合仍随提交条数增长，区别在于 uid 不再复用，跳过只发生在真正的重试上。从旧备份恢复之后重推的旧提交会被跳过，结果与本机一致，这是有意保留的行为；恢复之后新形成的提交携带新的 uid，不会再因为编号复用被误判为重复。排障时，协议里的 `request_id` 不再表示按内容算出的幂等键，它现在标识一条提交。

推送载荷可能比现在小：一条提交只带未被遮蔽的格子，被部分遮蔽的提交不再整条丢弃。服务端的单条提交上限仍是 2 MiB，单次请求仍是 16 MiB，每账号提交序列预算仍是 256 MiB，遮蔽行只在本机库里，不进入推送载荷，也不占序列预算。推送仍按到达顺序覆盖，`base_seq` 乐观锁与 409 的处理不变；两台设备同时离线修改同一内容列时，后到的仍然覆盖先到的，被覆盖的值留在提交历史里，可以由用户在数据版本页写回，规则见 [ADR-0039](0039-数据版本的提交类型与同步冲突记录.md)。

维护列不记冲突之后，两台设备改同一行的不同内容列会各自保留，但维护列的并发修改不留下任何记录；需要判断一行最后被谁写过时，只能看提交历史里的 `remote` 提交与来源位置，数据版本页不再给出“更新时间被覆盖”的条目。G3 的现象因此消失，代价是少了一条排查线索。

两分钟窗口以本机时间为准，用户调整本机时间会让窗口变长或者变短。判重试的两条判据把两次真正独立、参数相同、中间没有任何其他提交的动作在两分钟内合并成一次，第二次只返回第一次的提交与结果，不再执行写入；网络回调造成的重试与界面双击本来就不是独立动作，仍然在这个窗口内去重。超出窗口或者旧提交不再是当前 `HEAD` 时，同编号旧提交的 `request_id` 被置空，唯一索引与回执查询都按非空值判断，旧提交不再被当成重试目标。

这条决定不改服务端保存线性序列的方式，也不引入分支与合并提交：产品只有一份数据，线性历史够用，命名版本承担标签的作用。它也不改整版恢复、首次同步上传基线与附件上传的行为，这些分别在 [ADR-0023](0023-首次同步上传基线.md) 与 [数据版本系统对照git的改进方案](../数据版本系统对照git的改进方案.md) 第 3.4、3.6 节。

## 替代方案

用规范化内容哈希替代整数提交编号，作为提交身份。哈希可以校验内容，跨设备天然唯一；但界面回执、撤销、`reverted_commit_id` 与数据版本页都按整数编号定位，换成哈希要同时维护两套映射，而且提交内容里含创建时间与来源，同一份数据在不同时刻提交会得到不同的哈希。这一项在 [方案第 1 节](../数据版本系统对照git的改进方案.md#1-对照结果) 已经列为不学的做法。本次只在整数编号之外增加 uid，编号的现有用法不变。

按行而不是按格记录遮蔽并变基。实现更简单，遮蔽集合按主键登记即可；但两台设备改同一行不同列时整行被遮蔽，本机内容列的改动仍然丢掉，G2 的一半问题保留，维护列上的重叠也没有解决。放弃。

遮蔽集合继续留在内存，另在拉取与应用之间持久化到偏好文件。改动最小；但偏好文件与数据库不在同一个事务，整库恢复到旧备份时偏好文件不跟着回退，拉取成功、推送失败之后仍可能丢掉集合，而且没法按 `upto_commit` 判断哪些本机提交受影响。放弃，写进 `sync_shadow`。

让界面在用户动作发生时生成一次性编号、重试时复用，彻底取消两分钟窗口与 `HEAD` 判据。语义更干净，编号与一次用户动作一一对应；但 29 处 `commandId` 调用分布在界面与应用服务层，一次改完的回归面比收窄时效大，本轮先用两分钟窗口加 `HEAD` 判据，这项工作排在后面单独做。放弃本轮。

只增加 uid 用于推送与拉取，本机的 `request_id` 用法保持不变。改动最小；但本机仍然按参数匹配重试，暂停、恢复、再暂停仍然不生效，G1 的本机部分没有解决。放弃。

在服务端增加 `Idempotency-Key` 请求头单独承担重试去重，正文带 uid。接口语义更清楚；但服务端协议、OpenAPI 契约、走查用例与两台设备的真机验收都要跟着改，现协议不解释这个字段的内容，只改含义就能达到目的，收益不足以支撑一轮协议变更。放弃。
