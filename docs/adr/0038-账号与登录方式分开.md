# ADR-0038 账号与登录方式分开

## 状态

已采纳

## 日期

2026-11-20

## 背景

2026-11-17 接入账号、邮箱验证与找回密码时，账号表 `app_user` 同时保存邮箱、密码与邮箱的确认时间，验证码表 `auth_code` 的主键是（账号，用途）。这套结构把“一个人”和“一种联系方式”合并成了一条记录，于是每一处按邮箱判断的地方都写得像邮箱是账号的属性：托管额度与云端写入的门槛叫“已验证邮箱”，会话鉴权读出 `email_verified`，客户端把邮箱一起写进会话。

手机号与微信登录已经列入后续计划，两者都需要“一个账号挂多种联系方式”，也需要给还没有注册的号码发验证码。按现在的结构，加一种登录方式要改 `app_user` 的列、改验证码主键、改若干处“邮箱”判断，客户端也要跟着改一遍。内测规模只有几十人，云端数据可以整体丢弃，现在把结构改对，比等三种登录方式都在用之后再改便宜得多。

## 决定

账号只保存密码与创建时间：`app_user` 保留 `id`、`password_hash`、`created_at`，邮箱、手机号、微信各在 `user_identity` 占一行，字段是 `id`、`user_id`、`kind`、`identifier`、`verified_at`、`created_at`，`(kind, identifier)` 上有唯一约束。`kind` 的 check 约束一次写好 `email`、`phone`、`wechat` 三种，代码现在只写 `email`；以后加手机号或微信，只需要新增一种 kind 与对应的登录入口，不用再改表。

验证码按登录方式保存，不挂在账号上：`auth_code` 的主键改成（用途，kind，identifier），`user_id` 允许为空。这样以后给还没有注册的手机号或新邮箱发码不需要改表，用掉验证码时也不依赖账号是否已经存在。用途的取值从 `verify_email` 改成 `verify_contact`，与 kind 并列之后含义才对得上。

发信外面包一层按 kind 分发的发送接口：`auth.CodeSender` 只认三种通道，`auth.Senders` 现在只把 `email` 交给 SMTP，其余 kind 返回 `ErrSenderUnsupported`，接口回 501。发信限流的键改成 `kind:identifier`，两种用途共用同一个桶，换用途不能多拿一份额度。

“已验证”的含义从邮箱扩展到任意联系方式：`Principal.EmailVerified` 改名为 `ContactVerified`，取值为“至少有一种登录方式已经确认”，由 `SessionByAccessHash` 用 `EXISTS (SELECT 1 FROM user_identity WHERE verified_at IS NOT NULL)` 算出。托管额度的配置项 `RequireVerifiedEmail` 改名为 `RequireVerifiedContact`，环境变量 `ZHIXIN_LLM_REQUIRE_VERIFIED_EMAIL` 改成 `ZHIXIN_LLM_REQUIRE_VERIFIED_CONTACT`，problem code 从 `email_unverified` 改成 `contact_unverified`（原口径见 [ADR-0028](0028-服务端加固的默认拒绝与预算.md) 第 5 条）。云端写入门槛读同一个值。每日清理未验证账号的条件改成“没有任何一种已验证的登录方式”。

接口直接改，不保留旧字段：注册、登录、找回密码与重设密码的请求体里 `email` 统一改成 `identifier`，服务端识别种类并做规范化，现在只接受邮箱，识别出手机号或微信按 `invalid_request` 拒绝。验证接口改成针对某一条登录方式：`POST /v1/me/identities/{id}/verification` 发码，`.../confirm` 确认。`GET /v1/me` 返回 `{user_id, created_at, identities: [{id, kind, identifier, verified}]}`，不再有顶层的 `email` 与 `email_verified`；以后加昵称与头像时在这里加一个 `profile` 字段，现有字段不动。注册撞上已登记的联系方式时 problem code 从 `email_taken` 改成 `identifier_taken`。

客户端把会话与资料分开：`AccountSession` 只存 `userId`、令牌与服务地址，令牌刷新不再顺带改写资料；新增 `AccountProfile` 保存登录方式列表，每次调用 `/v1/me` 时刷新，用 Keystore 里单独一个键保存，退出登录时一起清掉。`AccountSnapshot` 对外只提供 `displayLabel` 与 `contactVerified`，`SyncStatus.email` 改成 `accountLabel`，账号页的邮箱展示改成登录方式列表。

## 代价与边界

线上库按新的 `schema.sql` 重建，`app_user` 少了两列、`auth_code` 换了主键、`user_identity` 是新表，没有迁移语句。重建之后已经登录的会话全部失效，用户需要重新注册，已经有云端数据的账号也取不回原来的记录；当时实例里只有联调与内测数据，这个代价由团队承担。

手机号与微信只是把位置留好了，并没有接上：识别出这两种 `kind` 之后注册与登录都拒绝，发码返回 501。接入时还要各自补一个登录入口、一种发送通道与相应的风控（短信的签名与模板报备、防轰炸，微信开放平台的企业主体），这些都不在本次范围内。

更换邮箱、解绑登录方式与“没有密码的账号删号”都留到以后：那时统一加一个 `POST /v1/auth/reauth` 的短期令牌来保护这些操作，`password_hash` 再改成可空。现在所有账号都有密码，删号继续用密码确认就够了。

“已验证”按账号算而不是按用途算：一种方式确认之后，云端写入与托管额度对整条账号开放，其他登录方式仍然是未确认状态，只影响它们自己的去留与找回密码。这样做是沿用原先“确认一次邮箱就开放额度”的口径，代价是以后三种方式并存时，无法只对某一种方式收紧权限。

## 替代方案

把 `email`、`phone`、`wechat` 三种联系方式作为 `app_user` 的三个可空列，`(kind, identifier)` 的唯一性交给三个独立的部分唯一索引。这个做法改动更小，但每加一种登录方式都要加列、加索引、改一遍“哪一列非空算哪种登录方式”的判断，验证码仍然要按账号存，给未注册号码发码还是要绕开外键。放弃。

给 `user_identity` 只留 `(user_id, kind)` 与一个 JSON 字段保存联系方式。这样表更少，但判重、登录定位与验证码主键都要在应用层拼出来，库里的唯一约束帮不上忙，付出的是正确性。放弃。

保留旧接口字段，同时接受 `email` 与 `identifier`。开发阶段不承诺兼容（[ADR-0001](0001-开发阶段不向下兼容.md)），两套字段并存会让客户端与服务端的口径分叉，多出来的兼容分支还要在下一次清理时再删。放弃。
