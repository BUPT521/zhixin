# ADR-0049 嵌入统一走百炼，查询向量也走云端

## 状态

已采纳。2026-11-22 决定。本条补充 [ADR-0029](0029-模型来源路由与嵌入代理.md) 的来源配置与 [ADR-0030](0030-服务端不建检索索引.md) 的嵌入调用口径，检索索引仍留本机，不改动那两条的决定第 1 条。

## 日期

2026-11-22

## 背景

[ADR-0030](0030-服务端不建检索索引.md) 把检索索引固定在本机，服务端只承担“文本到向量”这一层，并把已经算过的向量按账号缓存在 `embedding_cache`。索引与文档向量因此已经全部走云端，唯一还在本机之外考虑的是查询向量：用户按下“按意思找”时，查询文本要先变成一个向量，才能拿到本机 zvec 里做余弦比较。

为了让查询这一段也不走网络，讨论过的方案是文档向量在云端算、查询向量在手机上用同一个开源模型本地算。这个方案的收益是省掉一次往返，并在断网时保住语义检索。代价有三项。第一项是许可证：`jina-embeddings-v5-text-small` 与 v5 全系的权重都是 CC BY-NC 4.0，商用需要单独授权，项目结题之后的形态无法预先确定。第二项是向量空间一致性：同一个模型在云端 FP16 与手机量化版上推理，输出不会逐位相同，需要实测余弦排序是否稳定。第三项是安装包与手机性能：677M 参数的模型量化之后仍有几百兆，手机单次前向未必快过一次网络往返。

团队评估之后决定不做混合方案，全部嵌入统一走云端的一个来源，模型选阿里云百炼的 `BAAI/bge-m3`。bge-m3 的权重是 MIT 许可，不存在商用限制；维度 1024 与客户端默认维度一致；百炼在国内网络下的延迟与发票都对团队方便。查询向量很短，一次嵌入请求的 token 数远小于文档片段，走云端的成本可以忽略。

## 决定

1. 嵌入只有一个来源，是百炼上的 `BAAI/bge-m3`。服务端在管理后台建立这一个来源、一个 `kind = embedding` 的对外模型与一条路由，对外模型名统一写成 `bge-m3`，维度 1024。同一个对外模型下的备用路由必须也是 bge-m3 的同一权重部署，例如另一家服务商托管的 `BAAI/bge-m3`，不经实测不得混用其他模型或精调版本。

2. 文档向量与查询向量都发到同一个接口。索引刷新时的批量嵌入与检索查询时的单条嵌入都走 `POST /v1/llm/embeddings`，客户端不再在本地计算任何向量，也不随包携带嵌入模型。查询向量不写缓存，这一点沿用 [ADR-0030](0030-服务端不建检索索引.md) 的口径。

3. 检索仍然完全在本机完成。zvec 的两份 collection、切片规则、范围与来源版本核对、关键词与向量的融合、记忆召回都不变（[ADR-0022](0022-语义索引改用zvec.md)、[ADR-0026](0026-记忆召回改用zvec全文索引.md)、[ADR-0030](0030-服务端不建检索索引.md)）。本条只改变向量的来源，不改变向量的存放位置与比较方式。

4. 断网时语义检索降级为不可用，关键词与字面命中照常。查询向量算不出来，语义一路在本轮更新里停下并在界面上说明原因；文本 collection 不依赖嵌入，关键词检索与 `instr` 字面命中继续可用。这个降级与配置了嵌入来源但来源不可用时的行为相同，不新增一套状态。

5. 用户自填 key 直连仍然保留，但不能与本机索引混用。设置页仍然允许用户填写自己的嵌入接口；一旦切换到自填来源，索引键随模型名变化而新建一份 collection，与百炼来源的 collection 互不覆盖。不允许把两个来源的向量写进同一个 collection，也不允许把自填来源与知新服务的路由配成同一个对外模型。

6. 向量缓存的口径不变。`embedding_cache` 的键仍是账号、对外模型名与文本哈希，缓存只在登录且自动同步开启的索引刷新里写入，查询嵌入不写；缓存随清除云端数据与删除账号一起删除（[ADR-0030](0030-服务端不建检索索引.md) 决定第 2、3 条，[ADR-0037](0037-遗留写路径与公开入口的加固.md) 的代次约束仍然有效）。

## 代价与边界

查询向量走云端之后，每次按下“按意思找”都要等一次网络往返，延迟由百炼的响应时间决定，本机无法再优化这一段。断网时语义检索不可用，这是放弃混合方案直接换来的代价；关键词与字面命中不受影响，[00 第 6 章](../00-产品定义.md#6-原则与优先级)的三条硬约束仍然成立。

费用全部落在服务端的托管额度上。查询次数远超文档嵌入次数，一个高频用户一天可能检索上百次，每次只要几十 token，总量仍然可控，但额度统计要把查询嵌入与索引嵌入一起算进 `llm_quota.embedding_daily_tokens`，内测期间要按实际用量调整这个默认值。由捐赠与学院经费承担的口径不变。

单一来源之后，百炼不可用时整个语义检索停下，关键词一路照常。这是把原来的多来源容错收缩到一个来源的结果；如果需要容错，加备用路由时只能用 bge-m3 的同一权重部署，并且要先验证向量空间一致。

bge-m3 在中文与多语言检索上是第一梯队，但不是最新一代模型。如果以后要换到效果更好的模型，按模型键换 collection 目录并整份重建向量，换机用户靠 `embedding_cache` 命中可以少算一部分，但缓存键换成新的对外模型名之后旧向量一律不命中，重建成本要按当时的片段数重新估算。

自填 key 直连这条路径虽然保留，但未经隔离测试，两个来源的向量混进同一 collection 会让排序悄悄错乱且不报错。实施时要保证索引键里带上来源标识，并在设置页切换来源时明确说“会重建索引”。

## 替代方案

- 文档云端、查询本地。这是讨论中的混合方案。没有采纳的原因是 Jina v5 的 CC BY-NC 4.0 许可与商用边界不清、本地量化模型与云端向量的空间一致性需要长期验证、安装包增加几百兆而手机单次前向未必快过一次往返。
- 文档与查询都改成本地。查询延迟最低，也不产生嵌入费用；没有采纳的原因是手机算全量文档向量要数小时，换机与重建的代价落在用户一侧，[ADR-0027](0027-服务端承担嵌入与检索.md) 的替代方案一节已经否掉过这个方向。
- 保留多来源并加故障切换。可用性最好；没有采纳的原因是同一对外模型下混入不同模型或精调版本会破坏向量空间，而服务端只核对维度、核对不了空间（[ADR-0029](0029-模型来源路由与嵌入代理.md) 代价与边界），维护成本高于单来源的收益。
- 按 [ADR-0030](0030-服务端不建检索索引.md) 之前的设想，让服务端也建检索索引，查询在云端一次完成。查询延迟最低；没有采纳的原因是内存放不下按账号常驻的索引、服务端要复制业务表结构与切片规则、检索命中后仍要回本机核对版本与范围，三条理由写在 ADR-0030 的背景里，本次没有变化。

## 影响

- [00 第 7 章](../00-产品定义.md#7-边界)的数据与同步段落，补一句查询向量同样走服务端还是本机，以及断网时语义检索降级、关键词照常。
- [02 第 3.14 节](../02-产品与交互.md#314-查找)的检索说明与语义索引设置页的“知新服务”说明，写明向量不在本地计算、断网时语义一路不可用。
- [server/README](../../server/README.md#模型代理)的模型代理一节，以百炼的 `BAAI/bge-m3` 为例说明来源、模型与路由的配置，并注明对外模型名统一为 `bge-m3`、维度 1024。
- [运维手册](../../server/运维手册.md)的常用操作一节，补新建百炼来源、`bge-m3` 模型与路由的步骤，以及额度口径。
- [ADR-0029](0029-模型来源路由与嵌入代理.md)、[ADR-0030](0030-服务端不建检索索引.md) 的状态，注明嵌入来源与查询向量的口径由本条补充。
- [ADR 索引](README.md)。
- 客户端：[embedding_config_store.dart](../../app/lib/data/vector/embedding_config_store.dart) 的默认维度与“知新服务”来源不变，[search_index_service.dart](../../app/lib/application/search_index_service.dart) 的查询嵌入按单条发往同一接口，不随包携带任何嵌入模型。
