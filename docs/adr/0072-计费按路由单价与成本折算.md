# ADR-0072 计费按路由单价与成本折算

- 状态：提议，2026-11-25 由计量与计费审查提出，尚未实施
- 日期：2026-11-25

## 背景

[ADR-0066](0066-额度按缓存命中折算.md) 把聊天额度折成计费 token：未命中缓存的输入记 1，命中缓存的输入记 1/50，输出记 4。三个权重取自 DeepSeek 谷价每百万 token 命中输入 0.003 美元、未命中输入 0.15 美元、输出 0.6 美元的相对比例，除以 50 之后都是整数。这套算法在只有一条 `deepseek-flash` 路由、渠道对三项按同一折扣计价时成立，计费 token 与实际成本严格成比例。

[ADR-0059](0059-模型路由按故障范围切换与恢复.md) 与 [ADR-0062](0062-按请求能力筛选路由.md) 允许同一个对外模型配置多条来源路由，按优先级、故障与请求能力切换；[ADR-0068](0068-聊天积分包的档位与价格.md) 的代价一节已经记下，换成 `deepseek-v4-pro` 时三项官方价不再等值，渠道三项的折扣比例也可能不同，每百万计费 token 的成本随请求构成变化。权重写在 `server/internal/llmproxy/billing.go` 的常量里，换来源、换模型、渠道调价或高峰时段翻倍都只能改代码与 ADR，改之前计费量与实际成本不再成比例，多扣的部分交付之后无法退回。

现阶段只有一条 flash 路由，权重恰好等于成本比例，这是暂时条件而不是设计保证；积分已经开始售卖，出现成本倒挂之后再改会把对账与已售余额一起拖进来。

## 决定

每条路由带三个单价，结算按单价算出的成本记额度与积分，权重常量退场。

单价挂在路由上，不挂在模型或来源上。`llm_route` 增加三列，分别是命中缓存的输入、未命中的输入与输出，单位是微元每百万 token 的整数，由管理员在后台按来源的实际报价填写；同一模型的不同来源、同一来源的不同上游模型因此各有各的价。路由缺价时不参与结算，服务启动时拒绝加载并报出路由名，不按最高价兜底。

一次调用的成本按三项用量乘各自单价再除以一百万累加，单位是微元。账号账本、实例账本与积分核销都以成本微元计数；每日免费额度与实例日预算也改成成本微元；路由用量同时保存原始 token 与成本微元，后台按两者核对。积分兑换比例的含义从一个积分覆盖的计费 token 数改成一个积分覆盖的成本微元，配置项与契约字段随之改名，取值按当前渠道价与档位价格重算。

实施分两步。第一步给路由加单价列、后台字段与路由用量里的成本列，结算仍按 ADR-0066 的权重，单价只用于展示与核对；用一天的 `llm_route_usage` 按两套口径各算一遍，差异落在一轮用量以内之后再走第二步。第二步把 `Usage.Billed`、预留估算与积分核销切换到成本微元，同时按新的兑换比例重算 ADR-0068 的档位表，旧权重常量删除。

高峰时段与阶梯价不在这条决定的范围内：高峰时段的价格翻倍先按空闲时段单价记录，用后台统计出一周的真实分布之后另开一条 ADR 决定是否乘时段系数。

## 代价与边界

单价由人填写，漏填与填错直接算错钱。缺价路由拒绝加载可以避免漏填，但来源调价之后旧单价仍然会被继续使用；增加每日拉取官方价目的自动同步不在本轮，来源调价时由管理员在后台手工更新，更新记录随管理操作留痕。

微元是整数，三项乘除都有舍入，单次调用的误差远小于一分钱；一年用量累积之后与渠道账单可能差出小额，对账仍以支付宝与渠道账单为准。已写入的计费 token 与成本微元不能互换，切换日之前的用量只作历史记录，开发阶段按 [ADR-0001](0001-开发阶段不向下兼容.md) 不迁移。

免费额度按成本微元发放之后，同一份免费额度在不同来源上能用的原始 token 不同，用户在切换来源时会看到已用量跳变；后台的额度覆盖值也要按新单位重新核对。

客户端的展示口径不变，仍按积分显示用量与余额；契约里 `tokens_per_point` 的语义与字段名要随切换一起改，客户端与文档在同一个 push 里更新。

## 替代方案

把权重改成按模型配置，即 ADR-0066 提到的做法。没有采纳的原因是它只能区分模型，区分不了同一模型的多条来源，而来源之间价格不同正是当前最主要的误差来源。

只加一个全局加价系数。没有采纳的原因是三项用量的价格比例本来就不同，一个系数只能把总价整体抬高或压低，解决不了命中率与输出占比不同带来的结构性偏差。

先不改，等出现成本倒挂再处理。没有采纳的原因是积分核销不可撤销，多扣与少扣都无法事后补齐；已售积分按旧比例计价，切换时还要处理余额面值。

## 影响

- 表结构与查询：[schema.sql](../../server/internal/store/schema.sql) 的 `llm_route` 加三列，第二步改 `llm_usage` 与 `llm_instance_usage` 的单位、给 `llm_route_usage` 加成本列；对应 [queries/llm.sql](../../server/internal/store/queries/llm.sql)、[queries/quota.sql](../../server/internal/store/queries/quota.sql) 与 [queries/route_usage.sql](../../server/internal/store/queries/route_usage.sql)；面向管理端的契约在 [api/openapi.yaml](../../server/api/openapi.yaml) 的路由接口。
- 计费与预留：[billing.go](../../server/internal/llmproxy/billing.go) 的权重常量由路由单价取代，[estimate.go](../../server/internal/llmproxy/estimate.go) 的预留估算与 [proxy.go](../../server/internal/llmproxy/proxy.go) 的结算、统计按同一口径改。
- 后台与配置：[admin.go](../../server/internal/llmproxy/admin.go) 的路由读写与校验；`ZHIXIN_TOKENS_PER_POINT` 改成每积分成本微元的配置项，见 [server/README](../../server/README.md#配置)。
- 文档：ADR-0066 的计费口径由本条取代时在两条的状态里互相注明；ADR-0068 的档位表与代价一节、[01 第 4 章](../01-ER数据模型.md#4-完整-ddl) 的路由表、[04 第 5 节](../04-长期路线图.md#5-决定) 同步。
- 验收：切换前用一天的 `llm_route_usage` 按两套口径重算并比较；切换后抽查一轮对话的渠道账单金额与记下的成本微元一致，再核对一次积分核销与余额副本。
