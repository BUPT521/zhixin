# ADR-0059 模型路由按故障范围切换与恢复

## 状态

已采纳。运行时可单独发布，持久用量明细随计划内数据库重建发布。本文补充 [ADR-0029](0029-模型来源路由与嵌入代理.md) 的路由顺序及 [ADR-0034](0034-模型路由用量汇总.md) 的成功口径。

## 日期

2026-11-24

## 背景

一个来源可以配置多个模型，预先按候选条数截断会让独立的备用来源无法获得尝试名额，而共用健康计数又会把某个模型的异常扩散到同来源的其他路由。管理员需要区分配置权重、当前首选概率与已经发生的故障切换，才能核对调权结果。

## 决定

1. 路由按优先级从小到大尝试，同组按权重随机排列。达到实际尝试上限后停止，跳过的候选不占名额。DNS、连接建立或 TLS 失败以及 HTTP 401 按来源级故障处理，同一次请求跳过这个来源的剩余候选。连接建立后等待响应头超时、其他可重试状态码以及无法使用的模型响应按路由级故障处理。代理写出响应前可以换路由，收到有效的 400、404、422 响应时直接结束尝试。
2. 来源与路由各自累计连续失败，三次后冷却 30 秒，之后每次失败将冷却时间翻倍，本地退避最长 5 分钟。HTTP 429 或 503 附带有效的 `Retry-After` 时，普通请求在指定时间前跳过该路由，即使还没有达到连续失败阈值。冷却到期后按原优先级和权重参与选择，每个来源或路由同时只允许一次试探，完成有效请求后恢复常规分流。管理员可以定向提前试探冷却中的路由，共用同一个并发名额，嵌入试探逐批发送。
3. 当客户端取消请求时，代理释放试探名额。已开始转发的流收到 `response.failed` 或非输出上限原因的 `response.incomplete` 时，路由记为失败，随后出现的 `[DONE]` 不改变该结果。输出达到上限时保留上游响应并结算用量，这次尝试既不恢复试探状态，也不增加健康失败计数。整段聊天响应按同样的完成状态判断，代理仍可以在写出响应前换路由。
4. 管理后台按路由开关计算同组配置比例，并按最近读取的健康状态计算首个可用优先级组的首选概率，随后各组标为失败后尝试。模型测试按执行顺序列出来源、模型和失败原因，并标明是否占用恢复试探名额。持久用量明细按 [ADR-0034](0034-模型路由用量汇总.md) 汇总首次尝试、故障切换、输出截断和客户端取消。

## 代价与边界

冷却期间如果所有候选都不可用，请求会返回上游失败，需要等待其中一条路由具备试探条件。并发请求可能抢占试探名额，因此页面的首选概率对应读取状态的时点。健康状态和试探名额由各进程独立维护，重启后从空状态开始。

已写出的流由原路由收尾，本次只修正完成与冷却判定。旧日汇总只有尝试总量，首次尝试与故障切换从本次上线开始采集。部署前按 [ADR-0057](0057-服务端改表清空重建.md) 重建数据库并在发版说明中告知内测者重新注册和同步。
