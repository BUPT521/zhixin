# ADR-0037 遗留写路径与公开入口的加固

## 状态

已采纳。本条补充 [ADR-0031](0031-云端写入与托管模型的资源预算.md) 的云端清除与写入互斥规则，更新 [ADR-0029](0029-模型来源路由与嵌入代理.md) 第 5 条的刷新令牌轮换与实例预算口径，也补充 [ADR-0028](0028-服务端加固的默认拒绝与预算.md) 的公开入口预算。

## 日期

2026-11-20

## 背景

第一轮审查修掉了实例内存预算与实例日账本，第二轮把剩下的四处写路径逐个看过，问题都在“检查与写入之间还有窗口”。

清空云端数据（`DELETE /v1/cloud`）期间，各写处理器靠一条进行中标记拒绝写入，嵌入缓存的写入也只是在写之前查一次标记。清除完成、标记删掉之后，清除之前发出的嵌入请求仍可能把派生向量写回缓存，清除返回成功的承诺因此不完整。

备份的上传、删除与保留裁剪都是“先写或先删数据行，再动对象存储里的字节”，顺序本身是对的，但删字节失败或请求中途取消时，待删的 id 已经从库里消失，重试拿不到它们，残留对象会一直占着 bucket。

刷新令牌的轮换与重放记录分两次提交。轮换成功而重放记录写入失败时，客户端拿不到新令牌，旧令牌已经作废，重放检测也没有记下这次用掉的摘要。

注册是公开入口，只按来源地址限流。每个请求在校验邮箱之前就要做一次 argon2 哈希并写入账号与会话，arp 内存预算只限制同时进行的哈希数，不限制注册总量；持续注册未验证的账号会占满邮箱与账号表。

## 决定

1. 嵌入缓存增加按账号的代次。请求开始时读一次代次，写入时在自己的事务里再读一次并比较，不一致就放弃这次写入；清空云端数据时在同一把账号锁里把代次加一并删除缓存行。两边共用 `embedding_cache:<账号>` 的事务级 advisory lock，所以“清除之后旧请求再写回”这件事在数据库里被排除，而不是靠进程内的时间差。
2. 备份对象定期对账：列出 `backups/` 下的对象，与 `backup` 表的 (账号, id) 逐一对上，库里没有对应元数据、且写入时间早于一小时的对象删掉。一小时是给正在上传的备份留的窗口，因为上传先写对象、后写元数据行。
3. 刷新令牌的轮换与重放记录在同一个事务里提交：轮换的 CAS 与旧令牌摘要的写入一起成功或一起回滚，客户端要么拿到新令牌，要么旧令牌仍然可用。
4. 注册在按来源地址的桶之外再加一层实例级上限（默认每秒 0.05 个、最多攒 10 个），换地址也不能把未验证的账号灌满库；未确认邮箱的账号保留 7 天，超过之后由每日清理删除，释放邮箱与账号行。

## 代价与边界

代次与 advisory lock 都是 PostgreSQL 上的能力，内存实现只在单进程内等价：多实例部署时仍以数据库为准，内存装配只用于本地开发与测试。对账每小时窗口内的遗留对象会留到下一个周期，最长晚一天清理；对账删除的是对象存储里的字节，元数据本来就不存在，没有用户可见的数据丢失。注册全局上限按进程计，多实例部署时实际总量是配置值乘以进程数。未验证账号保留 7 天意味着注册之后一周没有确认邮箱的账号会被删除，期间写入的会话与验证码一并清理，这个账号本来也拿不到云端写入的权限。

## 替代方案

代次的替代做法是让清除与缓存写入共用同一个进程内互斥量。没有采纳的原因是它只在一个进程内成立，而清除的承诺应该由数据库保证；[ADR-0031](0031-云端写入与托管模型的资源预算.md) 的进程内互斥仍然负责挡住“清除进行中”的写入，两者是不同阶段的保护。

备份遗留对象也可以只靠定期按账号前缀重扫，没有采纳是因为账号删除之后前缀清理只覆盖删号那一刻，后来失败的重试没人负责。

刷新令牌的两次写入也可以用重试补偿，没有采纳是因为失败的重试本身还会失败，事务是唯一没有中间状态的做法。

注册也可以只靠按地址的限流加验证码发信成本，没有采纳是因为发信成本要等用户提交邮箱之后才发生，而账号行与哈希在那之前就已经写入了。
