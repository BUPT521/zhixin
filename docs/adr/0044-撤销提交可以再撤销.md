# ADR-0044 撤销提交可以再撤销

## 状态

已采纳

## 日期

2026-11-21

## 背景

[ADR-0039](0039-数据版本的提交类型与同步冲突记录.md) 把撤销的业务约束收到应用层注册的 `UndoGuard` 与数据层的通用核对里，它定下的撤销规则把撤销提交本身排除在撤销范围之外：`_blockedReason` 对 `kind = undo` 的提交直接返回“撤销提交本身不能再撤销，需要回到更早的状态请用整版恢复”。这条限制有当时的理由，撤销写回时要定向清掉消息里的回执，反向回放装不回这些回执；代价是用户误按一次撤销之后，唯一能回到撤销前状态的路径是整版恢复，而整版恢复会推进数据代次、把更早的提交移出可撤销范围，操作比一次撤销重得多。[改进方案](../数据版本系统对照git的改进方案.md) 第 3.11 节把这一项列为 G12：git 的 `revert` 可以再 `revert`，撤销本身也应当能撤销，含义是重做。

作出这条决定时的条件与 ADR-0039 相同：四人团队各自开发，内测规模几十人，开发阶段不向下兼容，撤销规则只在应用层注册三类业务判断，数据版本的历史是一条线性提交序列。本轮不改提交表结构，只改撤销的判断、写回、三个筛选入口与界面，schema 保持 30，不触发清库重建。

## 决定

1. 撤销的方向由回指链的层数决定。撤销提交通过 `reverted_commit_id` 指向它撤销的提交，撤销与重做因此形成 `C ← U ← R` 这样的回指关系；一条提交在链上的层数为 0 时是普通提交，1 是撤销，2 是重做，3 是撤销这次重做，依此类推。撤销链上层数为奇数的提交时，这次动作是重做；层数为偶数且大于 0 时，这次动作是撤销这次重做。层数还决定动作名：撤销层数为 0 的提交记为“撤销操作”，撤销层数为奇数的提交记为“重做操作”，撤销层数为偶数且大于 0 的提交记为“撤销重做”。

2. 重做把原提交里的变化按正向写回。撤销一条撤销提交时，按这条撤销提交记录的净变化正向写入当前表；这条净变化本身就是撤销原提交的结果，所以写回之后原提交的内容重新生效。`message` 表的净变化不参与写回，因为回执是定向清掉的，正向写回无法把旧回执完整装回去。

3. 重做的核对规则与撤销相同。写回之前重新读取目标提交与当前行，核对目标提交之后同一行没有又被修改、当前值仍等于这次提交之后的值，业务规则照旧由 `UndoGuard` 判断。撤销链上自己的写回不算后续修改，所以撤销、重做、再撤销之后原提交仍然可以继续撤销。维护列 `updated_at` 照旧排除在核对与写回之外，写回时写成动作发生的时刻。

4. 重做形成的提交类型仍是 `undo`，`reverted_commit_id` 指向被重做的那条撤销提交。这样提交范围的判断仍按 `kind = undo` 一处进行，不需要新增提交类型，也不需要改提交表的取值集合；提交标签、菜单动作与图标按层数显示“撤销”或“重做”。

5. 回执不恢复，`activeCommits` 按链判断。一条提交是否仍然生效，取决于回指它的提交里是否还有一条仍然生效，只有沿回指链递归才能得出结论；`activeCommits`、`undoableCommits` 与 `receiptCommits` 三个筛选入口因此改由撤销服务（`RevisionUndoService`）沿链计算。SQL 只负责取出候选提交与回指关系，因为“有没有人回指”这种写法只能排除一层，重做之后原提交重新可撤销、已经被重做过的撤销提交不再生效，一层判断给不出正确结果。

6. 界面按层数区分动作并给确认框。数据版本页对普通提交给出“撤销这次操作”，对撤销链上的提交给出“重做这次撤销”或“撤销这次重做”；层数大于 0 的操作先弹确认框，说明会写回还是去掉内容、回执不恢复、之后改过同一格时不能执行。讨论卡片、学习页、安排页与材料页的即时回执按 `activeCommits` 重新判断是否给出撤销入口。

## 代价与边界

断链时按动作开放的表会误判。撤销链的起点已经被裁剪时，`_chainStart` 按已经走过的层数返回，链起点停在一条撤销提交上，它的动作是“撤销操作”，按动作开放的表（例如更正材料页时一并开放的材料行）因此不在白名单里，撤销会被拒绝并提示“暂不支持单项撤销”。这条路径只在裁剪正好切在链中间时出现，用户仍可用整版恢复。

界面层数只用数据版本页已经加载的提交。链上更早的提交不在当前列表里时，层数按已经走到的位置计算，标签可能与实际方向不一致，滚动读取更早的提交之后重新算对；界面对撤销链上的操作再确认一次，误判的代价因此有限。

`revision_log.dart` 的三个旧查询只排除一层。`RevisionEngine.activeCommits`、`undoableCommits` 与 `receiptCommits` 仍按 `NOT EXISTS` 判断，重做之后原提交不会重新进入结果；生产入口已经改到撤销服务，这三个方法只剩测试使用，后续应当删除或者改成沿链判断，否则测试与实现会长期各走一套。

多分支链的数据层已经覆盖，界面没有专门用例。一条提交可以被多条撤销提交回指，`_UndoChain` 按集合处理多个回指者，数据层覆盖到多分支链的第 4 层，但数据版本页只按单链显示，没有针对多分支第 4 层的界面用例；出现这种历史时标签以链上实际回指关系为准，界面行为待补测试。

## 替代方案

- 保持撤销只能做一次，误撤销之后用整版恢复。改动最小，数据层与界面都不用动；代价是误操作的恢复成本高，整版恢复会推进代次、把更早的提交移出可撤销范围，其他设备看到的是一次整版恢复。不采纳。
- 撤销时不写入净变化，只改提交历史里的指针。实现简单，撤销看起来像 `reset`；代价是当前数据与提交历史对不上，检查点、同步推送与数据版本页都按净变化工作，指针无法表达当前数据是什么，从检查点重建会得到撤销之前的内容。不采纳。
- 把重做当作一条普通的新写入提交。用户再执行一次同样的操作，类型记为 `write`；代价是重做与原提交没有回指关系，撤销链断掉，回执与提交历史无法说明这次写入是在重做哪一次操作，之后的撤销也无从判断。不采纳。
