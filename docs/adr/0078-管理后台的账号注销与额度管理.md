# ADR-0078 管理后台的账号注销与额度管理

## 状态

已采纳（2026-11-26，服务端同日实施）。

## 日期

2026-11-26

账号改为调整一份共享额度见 [ADR-0084](0084-聊天与嵌入共用积分.md)。

## 背景

`llm_quota` 从 2026-11-18 起保存按账号调整的每日额度，额度判定与账号页都会读它，但写入只有直接改库这一条路径。管理员调整一个内测账号的聊天或嵌入额度时，要自己连 PostgreSQL 写 `INSERT` 或 `UPDATE`，写错列名或漏掉 `updated_at` 都不容易被发现；[数据库结构过度设计审查](../数据库结构过度设计审查.md) 的 V11 已经记录“现在手工改库，以后补后台入口”。

注销账号同样只有账号本人可用的 `DELETE /v1/me`，请求体要求提交当前密码。管理员在用户联系不上、账号被滥用或者试用结束时没有可用的入口，只能直接删除 `app_user` 行，再手工核对对象存储里的备份与附件字节。直接删库行会漏掉对象存储前缀，也会把“注销”变成一次没有记录的运维操作；删错账号时无法恢复。

管理后台现有的账号维度只有“按密钥计费”视图：它按密钥编号对账，页面按 [ADR-0076](0076-管理后台按密钥的对账视图.md) 只显示账号编号，不能按邮箱找到账号，也看不到额度覆盖值与今天的用量。要从“这个用户反馈额度不够”走到“提高他的额度”，管理员需要先在别处按邮箱查到账号编号，再手工改库。

## 决定

1. 新增 `GET /admin/v1/accounts`，按注册时间倒序分页列出账号，并支持 `query` 按账号编号或登录方式标识的子串搜索。响应给出账号编号、注册时间、登录方式与是否已验证、额度覆盖值、生效额度与实例默认额度。`limit` 取 1 至 100，默认 20；`offset` 取 0 至 100000；越界返回 400 `invalid_request`。
2. 新增 `GET /admin/v1/accounts/{id}`，在列表字段之外返回按服务端时区计算的今日已结算用量，聊天与嵌入分开。用量只读，不推进任何计数，也不包含仍在途的预留。
3. 新增 `PUT /admin/v1/accounts/{id}/quota` 与 `DELETE /admin/v1/accounts/{id}/quota`。前者整体替换 `llm_quota` 的覆盖行：`daily_tokens` 或 `embedding_daily_tokens` 省略或为 null 时，这一类回到实例默认额度；两项都为空且没有备注时删除覆盖行。后者直接删除覆盖行。两项都写 `updated_at`，下一次模型请求生效，不需要重启服务。
4. 新增 `DELETE /admin/v1/accounts/{id}` 注销账号，请求体必须带与路径一致的 `user_id`。清理复用账号本人的删号流程：先删除对象存储里的备份与附件字节等各包数据，再删除 `app_user` 行，提交序列、附件索引、额度覆盖、嵌入缓存与其余表按外键级联。删除不可恢复；账号不存在返回 404，编号不一致返回 400。
5. 账号管理页放在后台的新页签里，列表显示邮箱、账号编号、验证状态、注册时间与两类额度；单个账号的弹窗显示今日用量，可保存或恢复额度覆盖值。注销要求再输入一次账号邮箱或编号，页面把账号编号放进请求体，编号看错时不会删掉另一个账号。
6. 权限沿用管理令牌：接口都在 `/admin/v1/` 下，与其余管理接口同一道中间件，不向普通账号开放。账号令牌不能调用这些接口，管理令牌也不能当账号令牌使用。
7. 不新增表与列，继续使用 `llm_quota`。账号与登录方式仍由 `auth` 存储提供，额度仍由 `llmproxy` 的额度存储提供，注销复用 `auth.Service` 的清理；新包只做分页、校验与视图组装。

## 代价与边界

后台仍然没有操作审计，管理令牌等同于管理员本人。注销账号与调整额度都不记录谁在什么时候做了什么，令牌泄漏时攻击者可以删号或改额度；这与模型来源配置的风险相同，生产上继续按 [ADR-0029](0029-模型来源路由与嵌入代理.md) 限制 `/admin` 的来源地址或只经 SSH 隧道访问。要补审计需要在管理接口上增加操作记录与页面，那是另一条决定。

账号管理页显示完整邮箱，与 [ADR-0076](0076-管理后台按密钥的对账视图.md) 对“按密钥计费”页只显示账号编号的取舍不同。管理员要靠邮箱辨认账号并联系本人，遮住邮箱会让搜索与联系都退回手工查库；代价是后台页面成为个人信息的展示面，浏览器标签页、截图与代理日志都可能带出邮箱。按密钥计费页仍只显示编号，两处的范围不同是有意保留的：对账不需要联系方式，账号管理需要。

搜索使用 `position(lower(...))` 做子串匹配，`app_user` 与 `user_identity` 上的现有索引帮不上忙，账号数量增长之后会退化为全表扫描。当前公测规模只有百人量级，分页上限 100 足以覆盖；需要按规模优化时另开决定，例如加前缀索引或改为按编号精确查找。

额度调整只影响之后的预留与结算，不追溯当天已经发生的用量，也不改变实例预算。删除账号不保留宽限期，账号在即刻收一侧的剩余积分随删号失去使用与退款路径，这与账号本人删号的口径一致（[ADR-0067](0067-聊天额度改走即刻收积分包.md)）。删除期间正在处理的模型请求不会被单独中断，与本人删号相同。

内存实现只用于本地联调：账号列表与额度覆盖都在进程内，进程退出后丢失；积分视图与真实删号的级联效果只能在 PostgreSQL 装配下核对。

## 替代方案

只提供运维手册里的 SQL 语句，由管理员直接改库。没有采纳的原因是每次都要重写语句，列名与空值语义容易看错，而且无法在页面上确认改的是哪个账号；SQL 仍保留在运维手册里，作为接口之外的手工兜底。

让管理员用账号本人的 `DELETE /v1/me`，先取得对方的密码。没有采纳的原因是管理员通常拿不到也不应知道用户密码；要求账号本人在场会把这件运维动作变成一次协调。

软删除账号，保留数据与登录方式但拒绝登录。没有采纳的原因是它要改登录、同步、备份、额度与唯一约束的每一处查询，还会让邮箱长期不能再注册；当前只有一位管理员、账号可以重新注册，硬删除的边界更简单。需要恢复误删账号时只能依赖数据库备份，这一点在运维手册里写明。

把账号、额度与注销都放进 `llmproxy` 的管理包。没有采纳的原因是账号与登录方式不属于模型代理，注销还要调用 `auth` 的清理；另建 `accountadmin` 包之后，账号管理与模型来源管理各自依赖自己的存储，路由层只做转发。
