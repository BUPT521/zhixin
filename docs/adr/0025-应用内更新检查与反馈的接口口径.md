# ADR-0025 应用内更新检查与反馈的接口口径

## 状态

已采纳。服务端的发布清单、更新检查与反馈接口已于 2026-11-18 实现；应用内的更新提示、设置页的“检查更新”与反馈入口同日接入，界面沿用现有设计系统。公钥以常量内置在 `app/lib/platform/release_signing_key.dart`，默认留空，发版人填好或构建时传入之后签名才能验过。

## 日期

2026-11-18

## 背景

[04 第 2.1 节](../04-长期路线图.md#21-公测前必须完成)把应用内更新检查与反馈入口列为公测前必须完成的项目。安装包不走应用商店，第一批内测用户装好之后，旧版本只能靠应用内提示升级；反馈入口要附带版本名与可选的诊断记录，缺陷才有复现条件。服务端此前只有账号、同步、备份与模型代理，没有存发布信息的地方，也没有接收反馈的接口与表。

这两件事都发生在登录之前：更新提示要在登录页之外也能出现，反馈也要让没登录的人能提交。因此它们不能沿用现有接口一律要求 Bearer 的做法，也不能把反馈挂到账号上。

## 决定

1. 发布信息是一份放在服务端本地的 JSON 文件，路径由 `ZHIXIN_RELEASE_FILE` 给出，启动时读入并校验。`GET /v1/app/releases` 公开返回清单，服务端只给每个平台的版本名、构建号、安装包地址、哈希、大小、版本下限与更新说明，不比较客户端版本，也不判断某次更新是否必须安装。客户端按平台取一项，自己比较 `version` 与 `build`；版本名在客户端已经有一套解析，服务端再写一套只会让两边分叉。
2. 反馈走 `POST /v1/feedback`，公开接口，登录与否都能提交，服务端不把反馈绑定到账号，也不保存来源地址、设备标识与账号。字段包括必填的正文字段 `content`（1 至 4000 字）、可选的联系邮箱 `contact`、版本名 `app_version`、平台 `platform` 与诊断摘要 `diagnostics`（至 65536 字）；服务端只校验长度与格式，不解析内容。提交按来源地址限流。
3. 反馈单独存一张 PostgreSQL 表 `feedback`，不设读接口。管理员按 `created_at` 直接查表，删除也直接执行 SQL；删号不影响已经提交的反馈，因为反馈本来就不属于账号。诊断摘要由客户端在本地说明会提交哪些内容之后附带，不自动上传整份诊断记录。

## 代价与边界

- 发布清单是文件，发布新版本要改文件并重启服务；漏改会让客户端一直看到旧版本。发版步骤因此多出一步，写在 [server/README](../../server/README.md#更新检查)。
- 反馈不绑定账号，回复只能靠用户填写的联系邮箱；没填邮箱的反馈只能作为记录，无法追问。也无法按账号区分内测与公测用户，只能靠 `app_version`。
- 反馈正文由用户主动提交，可能包含学习内容。这超出了“服务端只保存同步序列与备份副本”的范围，但只在用户主动提交时发生，服务端不解析、不用于模型训练，也不与其他数据关联；保留期限暂不设上限，管理员按需要手工清理，删除方式写在 [server/README](../../server/README.md#应用内反馈)。
- 公开的反馈接口可能被脚本反复提交，靠来源地址限流、正文长度上限与单行存储控制影响；限流参数可以按运行情况调整，不写进代码。
- 诊断摘要只截取用户看过的片段，完整诊断记录仍留在本机；出现需要更多信息的问题时，由管理员按联系邮箱追问，不扩大自动上传的范围。

## 替代方案

- 发布信息放数据库或环境变量：数据库里没有写入口，改一次要连库执行 SQL；环境变量每加一个平台就多几个变量，更新说明与哈希也不好放。文件与安装包放在同一台服务器上，改起来最直接。
- 反馈走邮件或 GitHub Issues：内测用户不会为一条反馈写邮件，Issues 还要求 GitHub 账号，实际使用率会很低。应用内提交才有人用。
- 反馈必须登录：不登录的用户占多数，会把他们的反馈整批丢掉，也与服务端不保存账号关联的口径冲突。
- 服务端比较版本并返回“必须更新”：版本名带 `-dev` 与构建号，客户端已有解析规则；服务端再实现一遍，两边的比较结果迟早不一致。
