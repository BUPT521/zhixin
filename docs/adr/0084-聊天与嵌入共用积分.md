# ADR-0084 聊天与嵌入共用积分

- 状态：已采纳，服务端与客户端同批更新，已有实例先完成数据库加列再部署。
- 日期：2026-11-27

## 背景

账号原先分别获得聊天与嵌入的每日免费额度，只有聊天可以用购买积分续用。用户希望将当天的额度按实际需要分配给对话或语义检索，也希望嵌入额度用完后可以用已有积分继续。独立额度使一种用量先用完时，账号仍可能同时留有另一种免费额度和购买积分。

## 决定

聊天与嵌入共用按账号、按自然日计算的免费额度，累计用量超过免费额度后，超出部分由同一个即刻收积分余额承担。服务端按两类已结算用量的合计计算当天应扣积分，再扣除当天已申请的积分，只申请差额；预留同时计入两类在途请求，避免并发占用同一份额度。后台嵌入与前台请求适用相同的扣减顺序，直接从向量缓存取回的结果不产生用量。

每日免费额度默认取 40 积分，也就是 40 万计费 token；前台、核销与文档都按积分表达，不再另写一份原始 token 的额度。聊天沿用 [ADR-0066](0066-额度按缓存命中折算.md) 的折算权重；嵌入按成本折算，每千个原始 token 记 2,500 个计费 token，按次向上取整，预留和结算采用同一比例。比例的依据是两类请求每个计费 token 的渠道成本相同：聊天的渠道价是每百万计费 token 0.20 元，百炼 `text-embedding-v4` 的实时输入价是每百万原始 token 0.50 元，二点五倍正好对齐，1 个积分约合 4,000 个原始嵌入 token。这样免费额度、实例预算与毛利率都不随两类用量的结构变化。比例由 `ZHIXIN_LLM_EMBEDDING_BILLING_PERMILLE` 配置，默认 2500；渠道价调整或者渠道对嵌入另有折扣时，按新的输入价重算并同步改这个默认值。

嵌入一次请求拆成几批，结算只认来源报告的用量：连接没有建立、来源返回非 2xx、响应读不出来，以及回了 2xx 却没有带回 `usage` 的批次都记 0；只要有一批报告了用量，就按报告的用量结算，其余批次不补记。输入字节数的估算只进路由统计的估算列，不折成计费 token，也不再拿它顶替用量。这样一次请求的几批全部失败时，免费额度与积分都不会因为中文输入被按字节数多扣。

## 代价与边界

大量导入或重建索引会占用当天可用于聊天的额度，聊天用量也会减少当天可用于嵌入的额度。按成本折算之后，索引占用的积分与它实际花掉的成本一致，四十点免费额度大致够三份五万字材料的首次索引，用量大的账号会先用完免费额度再动用购买积分。账号页分别显示两类已结算用量、共享免费额度和购买积分余额，用户可以据此核对消耗。实例每日预算仍覆盖免费部分，两类请求的付费部分都由购买积分承担。

没有带回用量的嵌入批次按 0 结算，上游可能已经计费，这部分成本由实例承担；路由统计的估算列只用来发现不报用量的来源，不参与扣减。只要来源稳定返回 `usage`，这条路径就不会产生免费用量。

旧版嵌入的原始用量和预留保留在原字段，新版只从新增的嵌入计费列和预留列读取共享用量，因此历史嵌入不会触发补扣。原聊天额度覆盖值继续作为账号的共享额度覆盖值，旧的嵌入额度覆盖项退出接口与计量。

## 替代方案

可以只共用购买积分，同时保留两份每日免费额度。这种方案能为聊天和嵌入各保留一部分免费用量，但另一种用途用完时仍无法使用账号当天尚未花完的免费额度，因此采用共享额度。

## 影响

本条调整 [ADR-0029](0029-模型来源路由与嵌入代理.md) 的独立额度、[ADR-0067](0067-聊天额度改走即刻收积分包.md) 与 [ADR-0068](0068-聊天积分包的档位与价格.md) 的积分用途，以及 [ADR-0070](0070-额度预留与失败结算口径.md) 的嵌入计量。后台按两类用量合计折算参考积分，并提供一项账号共享额度覆盖值。客户端的展示与 [账号页规则](../02-产品与交互.md) 同步，已有实例的加列和配置见 [运维手册 §4.11](../../server/运维手册.md#411-即刻收积分包的上线与回滚)。
