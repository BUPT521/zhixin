# ADR-0069 积分余额的本地副本与预留放行

- 状态：已采纳，随服务端下一次部署生效；补充 [ADR-0067](0067-聊天额度改走即刻收积分包.md) 的预留一侧，计费口径不变
- 日期：2026-11-25

## 背景

[ADR-0067](0067-聊天额度改走即刻收积分包.md) 把聊天额度改由即刻收的积分包卖出，定下“先扣当天免费额度，超出部分才折成积分核销”。2026-11-25 删除 APP 支付与本地钱包的提交（`e0c093f`）去掉了额度预留里“免费额度加已购余额”那一段，即刻收的余额没有接进来：`pg.(*Store).Reserve` 只按当天免费额度的剩余量截断，免费额度用完之后的请求一律回 429 `quota_exceeded`，积分只在最后一次越线请求的结算里被扣掉一小段。用户付了钱，页面上仍然是免费额度用完、等次日恢复的提示，与 [00 第 7 章](../00-产品定义.md#7-边界)的购买说明和购买面板的说明相反。

余额不在请求路径上读。`quota.query` 是网络调用，有超时与按账号、按实例的限流，放在预留这一步意味着每一轮对话都要多等一次往返，即刻收不可用时请求会连带失败；ADR-0067 的核销已经定在交付之后，预留再依赖外部调用会把可用性问题带进回答本身。与此同时，`quota.verify` 与 `quota.refresh` 的响应本来就带核销之后的剩余积分，客户端打开购买面板时也会查一次余额，这两个值此前都没有留下。

## 决定

服务端在 `nowpay_balance` 表里维护一份余额副本，一行是一个账号，记剩余积分与同步时间，随账号删除。写它的位置有三处：概览与单独查余额两个接口在 `quota.query` 成功之后写，核销或补查的响应带剩余积分时写，`NOW_PAY_QUOTA_INSUFFICIENT` 时按零写。副本是缓存，真正的余额始终在支付宝一侧，副本只用于判断能不能放行。

额度预留按“免费额度加可用积分”放行。可用积分是副本减去副本同步之后才写入的核销流水，再按 `ZHIXIN_TOKENS_PER_POINT` 折成 token；当天已经发生、还没有记进流水的计费量另从 token 里扣掉，同一笔用量不会因为预留与核销的先后被放行两次。嵌入不能用积分支付，仍然只有免费额度；实例预算的判定不变。

余额副本超过十分钟没有同步、或者还没有副本时，预留排一次异步的 `quota.query`，这一轮按现有副本判断：没有副本时只放行免费额度，请求回 429，余额写进来之后的下一轮就能用上积分。请求路径上因此不调用即刻收，也不需要新增配置项。

## 代价与边界

副本可能过期，放行量因此有误差。副本偏高时，超额的部分会走到核销并被即刻收拒绝，副本随即按零覆盖，多放行的用量以一次在途估算量为界；副本偏低时，用户在副本刷新之前会被挡住，刷新是一次异步查询，通常下一轮请求就能恢复。部署这次改动之前已经买过积分、此后没有再打开购买面板的账号没有副本，第一次越线的请求会收到一次 429，随后自动恢复。

付费的用量与免费额度记在同一本实例账上。实例日预算原本是给免费额度兜底的，免费账号用满一天的额度之后，付费用户也会收到 `quota_exceeded`；是否把付费部分从实例预算里分出来另定上限，等第一笔真实收款之后按实际分布决定。

核销金额仍然读 `llm_usage` 的当天用量，这个数包含同一账号其它在途请求的预留量，并发时可能多算，多算的部分不能退回。这次没有改它，因为要先在 `llm_usage` 里把预留量与已结算量分成两列；改动之前，同一账号有并发请求时，付费用户可能被多扣一点积分。

余额只用于聊天。嵌入额度按原始 token 一比一记，不参与这套折算，购买积分也不改变嵌入的用量与上限。

## 替代方案

预留时直接调用 `quota.query` 取余额。没有采纳的原因是它把即刻收的可用性与限流带进每一轮对话的请求路径，超时与失败会直接变成模型不可用。

本地自己记一本积分账，按核销扣减，不查询余额。没有采纳的原因是购买发生在支付宝一侧，本地账本看不到充值，只能靠查询对齐；既然总要查询，把查询结果留成副本更直接。

预留时把全部未终结流水的积分都减掉。没有采纳的原因是余额查询报告的剩余积分通常已经排除预占，再减一次会把同一笔扣减算两遍；按同步时间分界只算副本没有反映的部分，两个来源不会重复。

每次预留都刷新一次余额。没有采纳的原因是与按账号的限流冲突，购买面板自己的两次查询也会被这些刷新挤掉。

## 影响

- 表结构：[schema.sql](../../server/internal/store/schema.sql) 新增 `nowpay_balance`，服务端共 28 张表；已有实例按[运维手册](../../server/运维手册.md#411-即刻收积分包的上线与回滚)第 4.11 节的增量语句建表。这张表是纯新增，缺表时服务照常启动，只是免费额度之外不能按积分放行，建表之后重启一次生效；核销与购买入口两张表仍然缺表即退出。
- 查询与存储：[queries/nowpay.sql](../../server/internal/store/queries/nowpay.sql) 新增 `SaveBalance`、`BalanceForReserve`、`UnreflectedChargePoints` 与 `ChargedTokens`；预留的余额那一段在 [pg/quota.go](../../server/internal/store/pg/quota.go)，折算与读写副本在 [pg/nowpay.go](../../server/internal/store/pg/nowpay.go)。
- 核销与购买接口：[nowpay/meter.go](../../server/internal/nowpay/meter.go) 在核销结果与余额不足时写副本，并新增余额刷新任务；[nowpay/handler.go](../../server/internal/nowpay/handler.go) 在查余额成功之后写副本；[nowpay/client.go](../../server/internal/nowpay/client.go) 的核销结果带出剩余积分是否存在。
- 配置与装配：[server/README.md](../../server/README.md#即刻收收款)的“即刻收收款”一节，以及 `Stores.Balances` 与 [main.go](../../server/cmd/zhixin-api/main.go) 的装配。
- 计费口径：ADR-0067 的“先免费额度、再积分”不变，本条补的是预留一侧；[02](../02-产品与交互.md)的“模型额度”一节描述的是展示，不需要改。
- 验收：用已验证的账号买一笔最小档位，把当天免费额度用完之后再发一次对话，服务端应放行而不是回 429，`nowpay_balance` 的 `remaining_points` 随核销减少；清掉这个账号的副本再发一次对话，第一次回 429 且服务端调用一次 `quota.query`，第二次放行。
