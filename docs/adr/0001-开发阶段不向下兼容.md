# ADR-0001 开发阶段不向下兼容

## 状态

已采纳

## 日期

2026-11-13

## 背景

项目处于 0.x 开发与内测阶段，使用者是四名团队成员与少量试用者，本机保存的是可以丢弃的测试数据。此前只在数据层写了“不写迁移函数”，代码接口、设置键、页面流程与文档仍有人按兼容处理，结果是旧分支保留下来，新方案要在旧结构上让步，一次改动要维护两套路径。团队每周合计投入 32 小时，维护兼容层的时间会直接挤掉功能与验收。

## 决定

1. 1.0.0 之前不承诺向下兼容。数据库结构、数据包与备份格式、设置键、内部接口、路由与页面流程、提示词与工具协议、文档结构都可以直接改；不为了兼容旧版本保留迁移函数、兼容分支、废弃别名或双写路径。旧库、旧包与旧备份在入口处清空、拒绝或按当前结构重建，用户需要重新填写本机设置或重新导入当前版本的数据。
2. 重构以产品更好为目标，允许删除、重命名、合并与替换任何部分，包括已经被文档或代码引用过的名称，不需要为了保持旧行为而降低新方案的质量。判断一次破坏性重构是否值得做，看它是否让记录更快、帮助更准、安排更可执行或维护成本更低，而不是看它改动了多少文件。

## 代价与边界

- 升级会丢失本机旧数据，内测与试用用户可能要在破坏性发版后重新录入或导入，发版说明必须写清这一点。
- 破坏性重构仍然要保证 `main` 能构建，格式检查、`flutter analyze` 与 `flutter test` 通过，相关文档与 ADR 在同一个提交里更新，不能因为不承诺兼容就提交半成品。
- 提交正文写清改动原因、影响范围与数据处置，发版说明写清是否需要重新导入、哪些设置需要重填。
- 1.0.0 之后是否继续不兼容，按 [03 第 3 节](../03-团队分工与协作.md#3-交付节奏)的版本规则另立 ADR 决定，本条的适用范围只到 1.0.0。

## 替代方案

保留迁移函数与兼容分支，让旧库、旧包和旧设置继续可用。没有采纳的原因是开发期数据可以丢弃，兼容层的维护成本高于它保护的数据价值，而且旧分支会让新结构长期保留历史形状，后续每次改动都要同时验证两条路径。

- [00 第 7 章](../00-产品定义.md#7-边界)写明这条规则覆盖开发阶段的全部对外形态；[01 第 7 章](../01-ER数据模型.md#7-导出恢复与版本)的 schema 规则是它在数据层的具体做法，见 [ADR-0002](0002-本地数据不做迁移.md)。
