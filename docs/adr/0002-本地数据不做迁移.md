# ADR-0002 本地数据不做版本迁移

## 状态

已采纳

## 日期

2026-11-13

## 背景

本地数据保存在单个 SQLite 文件里，当前结构（见 [01](../01-ER数据模型.md)）有 15 张业务表与提交历史，导出包和版本库备份也带版本标识。内测开始之前，库里的内容都是可以丢弃的测试数据，团队需要频繁调整表结构、附件存储与恢复格式。如果每次改结构都写迁移，DDL、测试与恢复入口要同时维护新旧两套结构，改一次 schema 的成本会超过功能本身。

## 决定

应用只认当前结构版本。库文件的版本与当前结构不一致时，打开时清空旧表并按当前结构重建；数据包与版本库备份的 manifest、`user_version` 与 `app_meta.schema_version` 必须都等于当前版本，任一不符就在替换前拒绝。应用不写迁移函数，不保留旧格式分支，也不为旧开发备份提供转换入口。schema 提升时同步更新 DDL、测试、文档与当前版本的导出恢复规则，旧数据不迁移。

## 代价与边界

- 升级会清空本机记录，用户需要重新录入或导入当前版本的数据包，这是 [ADR-0001](0001-开发阶段不向下兼容.md) 的直接代价，内测之前可以接受。
- 拒绝旧包时要给出可以理解的提示，说明需要当前版本的数据包，不能静默失败。
- 清空与重建必须在一个事务里完成，重建失败时保留原库并报错，不能留下半个结构。
- 附件、提交历史、检查点与恢复点随库一起处理，清空之后旧哈希引用一并失效。

## 替代方案

为每个结构版本写迁移函数，并保留旧格式的读取分支。没有采纳的原因是开发期只有测试数据，迁移代码没有真实的用户数据需要保护，却会长期留在打开库与恢复路径上，每次改表都要同时验证迁移与新建两条路径。
