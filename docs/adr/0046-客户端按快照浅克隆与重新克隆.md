# ADR-0046 客户端按快照浅克隆与重新克隆

## 状态

已采纳

## 日期

2026-11-21

## 背景

服务端快照与提交序列压缩已经按 [ADR-0043](0043-服务端快照登记与提交序列压缩.md) 实现（提交 `149b0b2`）：账号登记快照之后，服务端按保留期 `ZHIXIN_SYNC_COMPACT_KEEP` 或预算压力删掉快照位置之前的提交，`GET /v1/sync/head`、`GET /v1/sync/snapshot` 与 `GET /v1/sync/commits` 的响应带保留下界 `earliest_seq` 与当前快照指针，拉取位置落在已删除区间时返回 410 `history_compacted`。

客户端原来的同步只有一条读路径：首次同步从第 1 条开始回放服务端序列，再把本机独有的行作为基线上传（[ADR-0023](0023-首次同步上传基线.md)、[ADR-0042](0042-数据版本基线的差异上传与时间优先留存.md)）。历史被压缩之后第 1 条已经读不到，新设备、退出登录后重新登录的设备与整库恢复后按首次基线重新对齐的设备都在第一次拉取时失败；已经有同步位置的设备在增量拉取时收到 410 也没有处理路径，只能等用户清除云端数据再重新上传基线，服务端历史与所有设备的增量位置一起作废。

作出这条决定时的条件是四人团队各自开发、内测规模几十人、两端一起升级（[ADR-0001](0001-开发阶段不向下兼容.md)），这次改动不涉及客户端表结构。快照沿用检查点的 `json+gzip` 编码，整库摘要已经按 [ADR-0045](0045-同步两端的一致性摘要.md) 实现，客户端因此可以自己生成与校验快照；服务端只保存字节与指针，不解析学习内容。

## 决定

1. 客户端解析保留下界、快照指针与压缩开关。`ServerHead` 与 `ServerCommitPage` 增加 `earliest_seq` 与 `snapshot` 两个字段，快照带 `seq`、`sha256`、`digest` 与 `created_at`，`ServerHead` 另加服务端声明的 `compact`；`pull` 收到 410 `history_compacted` 时抛出 `SyncHistoryCompacted`，把 problem 的 `extra` 里的 `after`、`earliest_seq`、`head` 与 `snapshot_seq`、`snapshot_sha256`、`snapshot_digest` 解成字段，快照字段缺失时按没有可用快照处理。

2. 首次同步按保留下界分两级。还没有与这个身份建立同步位置时，`earliest_seq > 1` 说明快照之前的提交已经被删掉，必须用快照：服务端没有登记快照时抛出 `SyncSnapshotProblem`（code 为 `unavailable`），向用户说明“云端历史已压缩，缺少可用快照，暂时不能自动重建”，不静默清空本机数据。`earliest_seq == 1` 时仍然走 3.6 的全量回放，服务端即使登记过快照也不用，落后不多的设备因此不会因为一次快照登记就改写本机历史。

3. 快照导入形成一条 `baseline` 提交与一份 `initial` 检查点。下载快照之后先按 `sha256` 核对附件字节、按 `digest` 核对整库摘要、解出投影，再补齐投影引用到的附件；装入本机时整库替换，追加一条 `kind = baseline`、动作为“从云端快照重建”、变更明细为空的本机提交，写一份 `initial` 检查点作为之后的回放起点，代次加一，并清空 `sync_shadow`，因为旧的遮蔽行对应的格子可能已经不在库里。逐行变更明细不写：快照本身是可重建的起点，再存一份与快照等量的明细没有收益，这与“清理历史”留下的基线提交是同一种做法（[ADR-0039](0039-数据版本的提交类型与同步冲突记录.md) 第 2 条）。

4. 两个同步位置写成快照位置与本机重建提交编号。`sync.server_head` 写快照的位置，`sync.pushed` 写本机重建提交的编号：快照之前的提交已经由快照表达，这条重建提交只在本机存在，不上传。之后按 `after = 快照位置` 增量拉取快照之后的提交，再把本机原有的未推送提交按 3.2 的剩余部分去掉被云端遮蔽的格子，在快照与增量提交之上重放成本机新提交，按普通推送发上去；本机没有历史时没有可重放的提交，这一步为空。

5. 增量同步遇到 410 时重新克隆。已经有同步位置的设备在拉取途中收到 410 时按同一条路径重建：本机 `HEAD` 大于 0 且用户没有确认时先抛出 `SyncSnapshotProblem`（code 为 `confirmationRequired`），替换之前不写任何东西；账号页与“我的”页捕获这个类型、按代码决定弹确认框，确认框标题为“云端历史已经压缩，这台设备要从云端快照重建”，说明撤销窗口、命名版本与更早的提交按快照重建，本机还没有推送的 N 条改动会作为新提交重放到快照之上，取消则不同步、本机数据保持不变，确认按钮是“按快照重建”。用户确认之后带 `confirmReclone: true` 重跑这一轮同步。

6. 空闲登记由同步收尾时完成。服务端在 `head` 里声明压缩已打开（`compact` 为真）时，一轮同步成功、服务端位置大于 0、没有待推送提交、这次拉取没有被跳过的变化、没有已知摘要不一致、服务端快照落后于服务端位置，客户端把当前投影按检查点格式压缩上传为附件，再登记 `{seq, sha256, digest}`，其中 `digest` 用 3.5 的整库摘要；登记之前核对本机 `HEAD` 记录的摘要与按当前表重算的摘要一致，避免把绕过命令事务的写入当成快照。同位置或更新的位置已经有快照、同一份内容在本进程登记过、服务端已经有这个附件时跳过；409 表示服务端已有更新的快照或者账号正在清除云端数据，静默放弃；其他失败只记一条 `cloud_sync_snapshot` 诊断，不阻塞这一轮同步。压缩关闭时客户端不上传快照，登记只写指针、不删提交，上传只是白占附件配额（[ADR-0047](0047-快照附件回收与压缩前的客户端门槛.md)）。

7. 3.5 的“以云端为准修复”改走快照。修复入口先读一次 head；保留下界大于 1 且服务端有快照时，改为下载快照、按快照重建本机、再补传本机独有的行，未压缩时保持原来的差异重放。修复途中拉取遇到 410 时按同样的方式改用快照。“以本机为准修复”已经让用户确认过改哪一边，它随后触发的首次同步按快照重建时不再多问一次。

## 代价与边界

保留下界为 1 时首次同步仍然全量回放，即使服务端已经有快照。快照登记之后服务端只删掉收件时间早于保留期（默认 168 小时）的已覆盖提交，账号里的提交都比较新时保留下界仍然停在 1，首次同步继续按 3.6 回放，快照带来的流量与时间收益要等提交变旧、保留下界推进到 2 以后才出现；这样做换来的是一台只落后几十条的设备不会因为云端有快照就替换本机历史。

快照的体积是整库投影压缩之后的体积，下载耗时取决于快照大小与网络。下载走一次 `GET /v1/blobs/{sha256}`，没有断点续传，中途失败的这一段字节全部丢弃，下一轮同步重新下载整份；快照越大，弱网下重建成功的概率越低。

被替换下来的旧快照附件在宽限期之后回收（[ADR-0047](0047-快照附件回收与压缩前的客户端门槛.md)）：新指针让位时把旧附件登记为待回收，让位时间早于宽限期（默认 24 小时）之后由下一次登记顺带删除字节与索引。多台设备在宽限期内交替登记时，峰值占用是最近两份快照之和；停用很久的账号没有新登记，旧快照的字节一直占着配额。

410 会让只支持旧协议的客户端停止同步。服务端在没有任何设备登记快照之前不删除提交，所以发版顺序要求所有设备先升级到会处理 `history_compacted` 的版本，之后再让任何一台设备登记快照；反过来做的话，旧设备下一次增量拉取会收到一个它不认识的错误，自动同步一直失败，只能手动升级。开发阶段两端一起升级，代价由内测数据承担。

重新克隆不删除本机原有的提交行，也不改写它们的编号与内容，只追加一条 `baseline` 提交；当前投影已经换成快照内容，撤销窗口、命名版本与更早的提交按快照重建，代次推进之后早先的提交不能再撤销。

重放时的遮蔽判断只覆盖本机已经应用过的远端提交。快照覆盖的云端改动没有在本机形成 `remote` 提交，导入时也清空了 `sync_shadow`，所以本机未推送提交里与快照内容重叠的格子不会被识别成冲突；这类重放靠写入前核对旧值来跳过对不上的变化，跳过的条数写进 `cloud_sync_reclone_replay` 诊断，由用户在本机记录里核对。

## 替代方案

- 只让新设备用快照。判断条件改成“本机没有任何数据时才下载快照”，改动更小；代价是退出登录后重新登录、整库恢复后重新对齐这类本机有数据但没有同步位置的设备，在历史压缩之后仍然无法首次同步。不采纳。
- 服务端主动推送快照地址。服务端在登记或压缩之后通知在线设备去下载快照；代价是要新增长连接或轮询通道，把服务端从被动保存变成主动通知，与客户端按写入延迟同步的形态重复，也解决不了设备离线期间错过通知的问题。不采纳。
- 把快照塞进拉取分页。`GET /v1/sync/commits` 的响应直接带快照字节；代价是快照是整库大小的附件，混进提交分页之后每次拉取的响应大小不可控，新设备第一次拉取就要等整份快照下载完才能显示分页，也绕开了附件按账号隔离与配额计量的通道。不采纳。
- 客户端缓存多份快照。本机保存最近几份下载过的快照，反复重建时不必重新下载；代价是本机存储里再留一份与业务数据等量的内容，快照按账号与实例隔离，换账号之后还要清理，而收益只落在短期内反复重建的场景。不采纳。
