# ADR-0021 实现口径统一与重构残留清理

## 状态

提议。本文把 2026-11-15 逐层读代码得到的名单写成一条决定：无调用残留先删，其余按“决定”一节的五条硬约束收敛，实施时逐项销号，不再另建一份平行清单。

## 日期

2026-11-15

## 背景

`app/` 与 `server/` 经历了几轮重构：数据层换成 drift（[ADR-0004](0004-数据层改用drift与自带sqlite.md)），仓库查询迁进生成代码（[ADR-0011](0011-仓库查询改用drift生成代码.md)），库副本结束 sqflite 与 drift 并存（[ADR-0012](0012-结束sqflite与drift并存.md)），关键词检索改用 FTS5（[ADR-0013](0013-关键词检索改用FTS5.md)），服务端引入契约与 sqlc 生成并接上对象存储（[ADR-0015](0015-服务端引入代码生成与限流依赖.md)、[ADR-0016](0016-对象存储与附件接口.md)）。这些重构都换掉了主路径，但旧访问模型与旧表达方式没有随主路径一起下线，于是同一件事普遍存在两到六份实现，正确性取决于哪一份先跑到。

写这条决定时的具体事实如下。客户端手写 Dart 约 4.99 万行、测试约 2.53 万行。十二个仓库文件已经全部使用生成查询，`RawExecutor` 按表名与字符串条件提供的六个方法在仓库层零使用，版本引擎、备份、附件与撤销仍在使用它；同一套 SQL 字符串拼装在四个文件里各写一遍。页面手动重读仍有 62 处 `await _load()`、274 处 `setState`，[ADR-0014](0014-流式查询与版本通知.md) 已经记录了这一项，本文把同类的第二实现一并收进来，不替代那一条。服务端的契约模型、sqlc 生成查询与 schema 里的 `blob` 表都有一部分没有真实调用者，而 handler 旁边各有一份手写镜像。

这些问题的共同点是修复方式相同：把“唯一真相”从文档层面推进到代码结构层面，删掉并列的第二实现，而不是再补一份兼容分支。ADR-0001 已经认为开发期不承诺向下兼容，本文沿用这一条，收敛时直接改签名、删旧入口。

## 决定

1. 数据访问只保留一个执行器抽象。`RawExecutor` 收敛为 `execute`、`rawQuery`、`transaction` 三个方法，按表名与字符串条件执行的 `insert`、`update`、`delete`、`query` 与四个未使用参数全部删除；仓库写方法一律接收 `WriteTransaction?`，事务只由 `WriteTransactions.run` 建立，仓库内不再出现 `_db.transaction`；提交上下文用显式对象传递，嵌套事务直接抛错，不再静默复用外层事务。
2. 值对象与唯一入口先立。新增 `EvidenceId`、`ClockTime`、`TimeRange`、`Score` 与统一的状态枚举，写库时刻只经 `formatDateTime`，解析只经 `requiredDateTime` 与 `optionalDateTime`，空串归一、摘要截断、可选参数分别只保留一个函数或一种写法。
3. 读写结果有类型。写返回 `WriteResult`（提交编号、是否变化、跳过原因），读返回 `Result<T>`，提示用 `Notice` 枚举；`null` 只表示“没有这条数据”，异常只表示程序错误。
4. 界面只做拼装。`AppScopeState` 只暴露 `AppServices` 与极少数基础句柄，仓库字段私有；页面统一使用一个最近请求守卫、一个数据版本监听、一套加载与错误与确认与面板组件、一个导航入口；动效时长与间距只从 `motion.dart` 与 `ZhixinSpace` 取。
5. 服务端以生成物为唯一类型来源。handler 只消费 `api.*` 生成类型与已绑定的参数，四个业务包统一为处理函数、业务服务、存储接口三层，鉴权、错误响应、对象键与请求体落盘各只有一份实现。

## 代价与边界

- 这是一份长名单，不是排期。做哪些、按什么顺序做仍由 [04](../04-长期路线图.md) 与 [03](../03-团队分工与协作.md) 决定；本文只保证“要做的事情”有唯一一份，且不再新增第二实现。
- 删除残留会让部分测试失去覆盖对象，个别测试断言的是死接口本身而不是行为，删除前要先改断言，不能靠删测试让检查通过。
- 收敛执行器与写事务会动到版本引擎、备份、恢复、撤销四条最敏感的路径，任何一条出问题都会丢用户数据；这些改动必须保持 `main` 可构建，并按分支单独提交。
- 值对象与结果类型会改变服务签名，界面与测试同步改动，期间不允许保留旧签名的兼容层，依据 [ADR-0001](0001-开发阶段不向下兼容.md)。
- 名单依据 2026-11-15 的代码。其他提交可能已经改掉其中一项，实施时以代码为准，销号时更新本文的日期与状态；本文不保留“已改为……”的旧说法。
- 服务端的契约类型替换会让 handler 签名变化，`api.gen.go` 重新生成之后若与手写镜像字段不一致，以契约为准修改 handler，不反过来改契约。
- 本文不解决“要不要引入状态管理框架”的问题。[ADR-0014](0014-流式查询与版本通知.md) 已经否掉 Riverpod 一类框架，本文沿用，只统一页面内的请求守卫与数据版本监听。

## 替代方案

- 只删死代码，不动结构。删除清单能降低噪声，但同一件事的多份实现仍在，下一次改动仍要重复一遍；未采纳为完整方案，只作为第一步。
- 按页面逐个重写。页面重写会再次实现各自的加载、守卫与提示，等于把要统一的东西再写一遍；未采纳，顺序改为先立基础类型再改页面。
- 保留 `RawExecutor` 的表名接口作为“原生 SQL 逃生口”。仓库层已经零使用，真实需要逃生的只有版本、备份与附件，它们只需要执行语句与读回行，因此逃生口收敛为三个方法即可；未采纳保留原接口。
- 为每一项单独写 ADR。二十多项各写一条会让索引失去可读性，且这些问题的修复口径相同；未采纳，合成一条并按名单销号。
- 等接口稳定之后再统一。开发期没有稳定接口，等待只会让第二实现继续增加；未采纳。
