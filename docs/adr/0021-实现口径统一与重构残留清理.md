# ADR-0021 实现口径统一与重构残留清理

## 状态

已采纳。2026-11-15 提出，同日开始实施，2026-11-16 完成主要收敛：先删无调用残留，再统一执行器与事务、值对象与结果类型、应用层与界面入口，最后统一服务端生成类型与三层结构。名单里少数项按代码现状保留，理由写在“保留项”，不再作为本条待办；新的第二实现仍然不允许出现。2026-11-16 继续收尾：截止小时刷新收进 `TimePolicyController`、撤销走应用层 `UndoService`、恢复点并入数据版本门面、五个裸字符串字段换枚举；同日晚间把时间块来源与消息角色也换成枚举，保留项里“按字段逐个换”的条目随之清空。

## 日期

2026-11-15（实施结果补记于 2026-11-16）

## 背景

`app/` 与 `server/` 经历了几轮重构：数据层换成 drift（[ADR-0004](0004-数据层改用drift与自带sqlite.md)），仓库查询迁进生成代码（[ADR-0011](0011-仓库查询改用drift生成代码.md)），库副本结束 sqflite 与 drift 并存（[ADR-0012](0012-结束sqflite与drift并存.md)），关键词检索改用 FTS5（[ADR-0013](0013-关键词检索改用FTS5.md)），服务端引入契约与 sqlc 生成并接上对象存储（[ADR-0015](0015-服务端引入代码生成与限流依赖.md)、[ADR-0016](0016-对象存储与附件接口.md)）。这些重构都换掉了主路径，但旧访问模型与旧表达方式没有随主路径一起下线，于是同一件事普遍存在两到六份实现，正确性取决于哪一份先跑到。

写这条决定时（2026-11-15）的具体事实如下。客户端手写 Dart 约 4.99 万行、测试约 2.53 万行。十二个仓库文件已经全部使用生成查询，`RawExecutor` 按表名与字符串条件提供的六个方法在仓库层零使用，版本引擎、备份、附件与撤销仍在使用它；同一套 SQL 字符串拼装在四个文件里各写一遍。页面手动重读仍有 62 处 `await _load()`、274 处 `setState`，[ADR-0014](0014-流式查询与版本通知.md) 已经记录了这一项，本文把同类的第二实现一并收进来，不替代那一条。服务端的契约模型、sqlc 生成查询与 schema 里的 `blob` 表都有一部分没有真实调用者，而 handler 旁边各有一份手写镜像。

这些问题的共同点是修复方式相同：把“唯一真相”从文档层面推进到代码结构层面，删掉并列的第二实现，而不是再补一份兼容分支。ADR-0001 已经认为开发期不承诺向下兼容，本文沿用这一条，收敛时直接改签名、删旧入口。

## 决定

1. 数据访问只保留一个执行器抽象。`RawExecutor` 只有执行语句、读回行与生成查询三类方法，按表名与字符串条件执行的 `insert`、`update`、`delete`、`query` 与四个未使用参数全部删除；仓库写方法一律接收 `WriteTransaction?`，事务只由 `WriteTransactions.run` 建立，仓库内不再出现 `_db.transaction`；嵌套事务直接抛错，不再静默复用外层事务；插入行号由执行语句的返回值带回，不在提交收尾之后再查。
2. 值对象与唯一入口先立。`EvidenceId`、`ClockTime`、`TimeRange`、`Score`（0–1）与统一的状态枚举各只有一个；写库时刻只经 `formatDateTime`，解析只经 `requiredDateTime` 与 `optionalDateTime`；空串归一只有 `nullableText`，摘要截断只有 `truncateCodePoints`，最近请求守卫只有 `RequestGate`，数据版本监听只有 `DataVersionWatcher`；枚举统一为 `value`+`label`+`unknown`+`fromValue`，未知值回落 `unknown` 而不是顶成真实值或抛错。
3. 读写结果有类型。写返回 `WriteResult`（提交编号、是否变化、跳过原因），回答收尾返回 `AnswerOutcome`，提示状态用 `Notice` 枚举、文案只在界面生成，上下文组装用 `ContextRequest`，场次结果用 `SessionOutcome`，可预期的失败在包与恢复的边界用 `Result<T>`；`null` 只表示“没有这条数据”，异常只表示程序错误。
4. 界面只做拼装。`AppScopeState` 只暴露 `AppServices` 与极少数基础句柄，仓库字段私有；页面统一使用一个最近请求守卫、一个数据版本监听、一套加载与错误与确认与面板组件、一个导航入口；动效时长与间距只从 `motion.dart` 与 `ZhixinSpace` 取，文案只在 `copy.dart`，日期与时刻只在 `format.dart`。
5. 服务端以生成物为唯一类型来源。handler 只消费 `api.*` 生成类型与已绑定的参数，四个业务包统一为处理函数、业务服务、存储接口三层，鉴权、错误响应、请求体落盘校验、对象键与 S3 配置各只有一份实现；中间件顺序固定为 request_id、访问日志、恢复、鉴权、上传限流、业务。

## 实施结果

| 层 | 原问题 | 现行口径 |
|---|---|---|
| 数据层 | 按表名拼条件的执行器接口、三层转发、向量库另起一套 | 执行器只剩语句、读行、事务与生成查询；只读副本对生成查询直接抛错 |
| 数据层 | 仓库写方法四套事务契约、`writeExecutor` 的 60 处调用散在十二个仓库 | 仓库写方法统一 `WriteTransaction?`，事务只由 `WriteTransactions.run` 建立，执行器解析集中在一个辅助函数 |
| 数据层 | 提交编号绕过生成查询 | 委托 `RevisionEngine.activeCommit`，回执与 `WriteResult` 同源 |
| 数据层 | 检索仓库 15 处 `rawQuery`、范围规则 4 份 | 范围规则输出一个 `Expression<bool>`，SQL 渲染与存在性判断共用；四类命中的整段查询仍是手写 SQL（`evidence_repository` 四处 `customSelect`、`material_repository` 一处 `rawQuery`），FTS5 的 `MATCH`/`bm25()` 与字面查找的 `LIKE` 都在其中 |
| 数据层 | 表结构 DDL 三份、表清单登记六处、索引靠正则从 DDL 抠 | 表结构与索引只在 drift 表类（`@TableIndex`），清单、必需列、索引名都从表类派生；`schemaStatements` 与手写 DDL 删除 |
| 数据层 | `.drift` 按迁移批次切分、同一条 SQL 重复 | 一张表一个文件，重复语句合并 |
| 数据层 | 备份、旧数据包与恢复点各写一遍校验 | 一个暂存库校验（版本、对象白名单、`integrity_check`、外键、必需列），三路共用 |
| 数据层 | 布尔列用 int、可选条件三种哨兵、空串八份归一 | 五个布尔列改 `BoolColumn`；可选条件改可空参数加 `IS NULL OR`；空串归一走 `nullableText` |
| 值对象 | 时间解析两种策略、写库时间三种格式、相关度七套量纲、证据标识手拼、时刻四类表示、摘要八份 | `requiredDateTime`/`optionalDateTime`、`formatDateTime`、`Score` 与权重表、`EvidenceId`、`ClockTime`/`TimeRange`、`truncateCodePoints` |
| 值对象 | 枚举三套写法、未知值三种策略、值集合三份 | 枚举统一形态，未知值统一回落；会话入口、会话状态、时间块状态、事项来源与材料种类也换枚举；值集合一份，并有测试与八个枚举逐项比对 |
| 值对象 | 时间块来源与消息角色按字符串读写 | 时间块来源用 `PlanItemSource`、消息角色用 `MessageRole`，写库只经 `value`，读库只经 `fromValue` 回落未知值；界面与测试不再比较字符串字面量 |
| 应用层 | 写路径三个入口、门面不是唯一入口 | 数据版本操作下沉 `DataVersionService`，仓库字段私有，页面只经六组服务与基础句柄 |
| 应用层 | 写方法返回五种类型、失败表达五种、提示靠字符串拼 | `WriteResult`、`AnswerOutcome`、`Notice`、`ContextRequest`、`SessionOutcome`、`ChatMessagePayload`、`MemoryDraft`；界面不再按文案子串判断状态 |
| 应用层 | 调模型三条路、配置读取失败六种处理、提示词一半在应用层 | `readModelConfig` 与 `askBuddyModel` 一个网关，提示词回 `ai/`，两份重复文案删除 |
| 应用层 | 模型客户端一个文件七件事、重试两套、空与截断判定三处、超时四个真相源 | 拆成失败、传输、协议三组文件；一个 `RetryPolicy`、一处空/截断判定、一个 `LlmRequestBudget`（整段、首字、空闲与取消同源） |
| 应用层 | 上下文是十四参数方法、记忆范围三份、命令编号界面手拼 | `ContextRequest`；`memoryScopeFor` 一个领域函数；`commandId` 由用例层按动作与稳定输入生成 |

| 应用层 | 恢复点与数据版本是并列的两个门面 | 恢复点列表、保留份数与写入并入 `DataVersionService`，页面只调 `services.data.versions` |

## 保留项

| 项 | 现状与原因 | 后续 |
|---|---|---|
| `Result<T>` 全量替换读路径 | 已在数据包预检、恢复与导入边界使用；其余读路径仍用 null 表示没有数据、异常表示程序错误，按决定第 3 条本来就允许 | 按 `SettingsService`、`PlanService`、`MaterialService` 逐个收 |
| 讨论与作答两条流水合并 | 两条流水的共享件（上下文、网关、回答收尾、草案存储）已经抽出，剩下的编排差异与保存内容不同，合并需要重写两条链路 | 排在验收之后 |
| 命令编号覆盖所有写方法 | 新建目标、事项、预约、课表、接受建议、接受记忆、材料更正等已由用例层生成；保存草稿、提交作答、模型判断按次生成令牌，确定性编号无法区分重试与新动作；完成步骤用状态短路而非编号 | 令牌改由用例层保存状态后接入，其余动作随写路径改动补 |
| `plan_page` 页签拆分 | 详情入口已拆出，页签仍共用一个 State | 按 [04](../04-长期路线图.md) 排期 |
| 跳转后重读（12 处） | `dataVersion` 只在恢复、撤销、导入与截止小时变化时推进，普通保存不推进；删掉会让页面停在旧数据（[ADR-0014](0014-流式查询与版本通知.md) 的流式查询尚未实现） | 随 ADR-0014 实施 |
| 图片两套模型（路径与内容哈希） | 消息里的图片按内容哈希保存，旧格式数据包的路径引用、`AttachmentStore` 的目录回收与导入边界仍在，两条读取路径同时有效 | 导入边界随旧格式包下线一起删，届时只留哈希 |
| 备份三路编排合一 | 校验已合一；导出与恢复的编排各自保留，因为两类包的替换与回滚语义不同 | 等旧格式包下线 |
| `llmproxy` 独立服务层 | `Proxy` 兼 HTTP 与业务规则；ADR 原文只要求四个业务包三层，`llmproxy` 不在其列 | 不排期 |

2026-11-16 复核时另记两处待收口，暂未排期：

- 设置页经 `SettingsServices.embedding` 直接读写数据层的 `EmbeddingConfigStore`，保存之后再调 `AppScopeState.applyEmbeddingConfig`，同一次配置变更要调两处，服务分组里暴露的也是配置存储本身；后续收进设置服务，页面只调一次。
- `GuardedDatabase.rawQuery` 直接走外层连接，不像 `execute`、`writeGenerated` 与 `selectGenerated` 那样优先取当前事务执行器；当前没有事务内调用点，属于潜在陷阱，下次改数据层时一并收口。

## 代价与边界

- 名单是待办的唯一一份，不是排期。做哪些、按什么顺序做仍由 [04](../04-长期路线图.md) 与 [03](../03-团队分工与协作.md) 决定；本文保证“要做的事情”有唯一一份，且不再新增第二实现。
- 删除残留让部分测试失去覆盖对象。实施时先改断言再删代码，没有靠删测试让检查通过。
- 收敛执行器与写事务动到版本引擎、备份、恢复、撤销四条最敏感的路径；每一批都保持 `main` 可构建，并按层单独提交。
- 值对象与结果类型改变了服务签名，界面与测试同步改动，没有保留旧签名的兼容层，依据 [ADR-0001](0001-开发阶段不向下兼容.md)。
- 布尔列改 `BoolColumn` 后 drift 生成的 SQLite DDL 仍是 `INTEGER` 加 0/1 的 CHECK，已有库按 bool 读出，不需要清库；表结构若再变，仍按 [ADR-0017](0017-表结构变化仍清空数据.md) 清空重建。
- 聊天消息的结构化补充改了模型之后，旧消息按同样键名读回；写入不再产生空的 `commit_id` 与 `valid_until`，撤销与回执清理会按新模型重编码。
- 本文不解决“要不要引入状态管理框架”的问题。[ADR-0014](0014-流式查询与版本通知.md) 已经否掉 Riverpod 一类框架，本文沿用。

## 替代方案

- 只删死代码，不动结构。删除清单能降低噪声，但同一件事的多份实现仍在，下一次改动仍要重复一遍；未采纳为完整方案，只作为第一步。
- 按页面逐个重写。页面重写会再次实现各自的加载、守卫与提示，等于把要统一的东西再写一遍；未采纳，顺序改为先立基础类型再改页面。
- 保留 `RawExecutor` 的表名接口作为“原生 SQL 逃生口”。仓库层已经零使用，真实需要逃生的只有版本、备份与附件，它们只需要执行语句与读回行；未采纳保留原接口。
- 为每一项单独写 ADR。二十多项各写一条会让索引失去可读性，且这些问题的修复口径相同；未采纳，合成一条并按名单销号。
- 等接口稳定之后再统一。开发期没有稳定接口，等待只会让第二实现继续增加；未采纳。
