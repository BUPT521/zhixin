# ADR-0013 关键词检索改用 FTS5

## 状态

已采纳

## 日期

2026-11-14

## 背景

关键词检索现在分两步：仓库层对检索查询按每个词拼一条 `LIKE ? ESCAPE ...`，在材料页、消息等表上取候选，`chinese_tokens.dart` 把查询与候选文本切成字符二元组，`keyword_ranker.dart` 再用 `bm25` 包为候选现建一份内存索引排序，用完丢弃；`memory_recall.dart` 排记忆正文时同样每次重建索引。`LIKE` 在中文正文上没有可用索引，扫描成本随材料页数与消息数线性增长，排序又只能作用在已经被 `LIKE` 选出的候选上，候选以外的相关记录不会进入排序。

随包 SQLite 的编译选项已经打开 `SQLITE_ENABLE_FTS5`，这件事不需要新增依赖。评估见 [轮子与技术选型评估第 2.3 节](../轮子与技术选型评估.md#23-关键词检索改用-fts5)。

## 决定

1. 为 `material_page`、`message`、`attempt` 各建一张 FTS5 表，查询与排序改由这三张索引负责，`evidence_service.dart` 与仓库层的 `LIKE` 候选路径删除。
2. FTS5 用外部内容表，`content=` 指向业务表。业务表本身没有可直接给 FTS5 切分的二元组列，因此索引列不映射业务表的列名，而是由业务表上的 AFTER INSERT、AFTER UPDATE OF 与 AFTER DELETE 触发器在写入时计算并写入索引行。触发器在 [revision_engine.dart](../../app/lib/data/revisions/revision_engine.dart) 安装采集触发器之前建立，因为打开库时引擎会删除库里所有非 `sqlite_` 前缀的触发器再重建；索引因此与业务行在同一次写入、同一个提交里更新，恢复与撤销之后不需另跑一轮对账。
3. 二元组在 SQL 里用 `replace()` 拼接，与 `bm25Tokens` 的口径一致：先按空白切开，去掉非字母、非数字字符，连续片段取相邻两字加整段本身。FTS5 用默认的 `unicode61` 分词器按空格切分，带点号的片段用双引号包起来写进索引列，保证它是一个词而不是两个。
4. 查询端用 `bm25Tokens` 切出与索引相同的词，拼成 `"词1" OR "词2"` 交给 `MATCH`，排序用 FTS5 内置的 `bm25()`。题号、页码等带符号或被引号括起来的查询已经由 `shapeQuery` 判为字面查询，走原有 `LIKE` 路径，不受这次改动影响；`mergeExactAndRanked` 的合并顺序不变，`rankKeywordCandidates` 改为查询索引而不是在内存里排序。
5. FTS5 表与影子表登记为不参与版本采集的派生表。`versionedTableNames` 与 `allowedDatabaseTableNames()` 要把它们排除在外，否则引擎会把索引当成业务表采集，恢复与撤销时还会和业务行重复。
6. 恢复与撤销之后不重建索引：触发器在导入、恢复、撤销、清空写入业务行时会同步索引，索引不需要整份重建，也不需要额外对账。如果恢复流程在执行期间关闭了触发器，由版本服务在独占区结束时重建三张索引，这一条在实施时按实际流程核实。
7. 记忆正文排序（`memory_recall.dart`）不建索引表，改为在候选内按同一套切词规则计算排序分。理由是记忆条数远小于材料页与消息，另建触发器与索引的收益抵不过维护面。
8. 索引的 `MATCH` 查询依赖 FTS5 的列限定与虚拟表语法，写不进 drift 的 `.drift` 文件，留在检索仓库的原生 SQL 上，与 [ADR-0011](0011-仓库查询改用drift生成代码.md) 第 5 条一致。
9. 从 `pubspec.yaml` 删除 `bm25` 包。

## 代价与边界

- 三张 FTS5 表与它们的索引、位置表会增加库文件体积，在默认的 `content=` 设置下 FTS5 不复制业务行的正文，所以增量主要来自分词结果与位置信息；材料页正文较长时，这部分增量会接近正文大小，量级在实施前用一份真实材料量一次。
- 触发器在每次写入时做字符串运算与切分，单次写入的耗时会增加；批量导入材料页时，导入路径仍是逐页写入，总体耗时增加，但与 `LIKE` 扫描的成本方向相反，数据量越大收益越明显。
- `replace()` 拼接的二元组规则比 Dart 的 `bm25Tokens` 多了一段 SQL 代码，两处口径要同时维护。测试要有一条用例把同一段文本分别交给两边，比对切出的词一致。
- 测试环境要考虑系统 SQLite 是否带 FTS5。Windows 的 `winsqlite3.dll` 不带 FTS5，涉及 FTS 的测试在 Windows 上要用随包库；CI 的 Linux 任务先验证 `libsqlite3.so` 是否带 FTS5，不带就把这部分测试切到随包库。
- 关键词候选的取法变了，检索结果会比现在多出一部分：现在只有被 `LIKE` 选中的记录参与排序，改成 FTS5 之后所有包含相同二元组的记录都会参与，融合之后的顺序可能与现在不同。这是检索能力的变化，验收用例要更新预期，逐条核对前几条结果仍然相关。
- 删除 `bm25` 包会让 `keyword_ranker.dart` 与 `memory_recall.dart` 的公开方法少一个可调开关，`EvidenceService` 的 `bm25Ranking` 参数同时删除，调用方与测试一起改。

## 替代方案

- 用 FTS5 自带的 `trigram` 分词器，不做二元组。没有采纳的原因是它要求查询至少三个字符，中文最常见的两字词查不到，检索覆盖反而变小。
- 在 Dart 里把整表正文读出来交给 FTS5 建内存索引。没有采纳的原因是每次查询都要整表读取，等于将现在的 `LIKE` 扫描换成更大的扫描。
- 保留 `LIKE` 候选，只把排序换成 SQLite 的 `bm25()`。没有采纳的原因是索引仍然要在写入时维护，而查询端还要多做一次 `LIKE`，两边都要维护。
- 用 `sqlite3_vec` 的向量检索替代关键词检索。没有采纳的原因是语义索引依赖用户配置嵌入模型，未配置时检索仍需可用，两者是互补关系。
