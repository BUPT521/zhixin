# ADR-0071 核销只读已结算用量与额度用完的原因

- 状态：已采纳，随服务端下一次部署生效；改定 [ADR-0070](0070-额度预留与失败结算口径.md) 的结算口径，补充 [ADR-0069](0069-积分余额的本地副本与预留放行.md) 的核销口径；`remaining_points` 的可用积分口径与新增的 `syncing` 原因由 [ADR-0073](0073-余额副本的快照、刷新与放行原因.md) 补充
- 日期：2026-11-25

## 背景

额度预留与结算共用 `llm_usage.tokens` 一列：请求开工时先把估算量加进去，结算时再按实际用量调整。核销在结算之后读当天累计用量，算出超出免费额度的部分折成积分，因此读到的数包含同一账号其它在途请求的预留量。ADR-0069 修好“免费额度用完之后按积分放行”之后，付费用户会同时在途几个请求，一个请求结算时会把别人的预留也算成已经产生的费用，多扣的积分不能退回。

同一处还有两个问题。第一，`Quota.Reserve` 在剩余量不足时按剩余量截断，代理收到不足的预留就整单拒绝，429 里却说不出是免费额度、积分还是实例预算用完，客户端只能统一提示“等次日恢复”。第二，`GET /v1/llm/quota` 只有已用量与每日额度，账号页看不出免费额度用完之后今天扣了多少积分、还剩多少，用户不知道自己买的积分在不在、用了多少。

## 决定

`llm_usage` 拆成两列：`tokens` 记已经结算的计费 token，`reserved_tokens` 记在途预留。预留只加 `reserved_tokens`；结算把这次预留从 `reserved_tokens` 里扣掉、把实际用量加进 `tokens`，两个分支都限在 0 以上。额度判定看两者之和，核销与 `GET /v1/llm/quota` 的已用量只看 `tokens`；账号页的剩余积分按已占用量（两者之和）算，见下文，这样它与放行同口径。内存实现按同一口径保存两份，测试与本地联调看到的行为一致。

`Quota.Reserve` 改成要么拿到完整的 `want`、要么返回 `*QuotaExceededError`，不再按剩余量截断。原因分三种：`account` 表示免费额度用完且没有可用积分，`points` 表示免费额度用完、有积分但不够这一次，`instance` 表示实例当天的预算用完。代理把原因写进 429 problem 的 `extra.reason`，详情按原因各写一句，不再提“用自己的 key”。余额副本缺失或过期、服务端刚排了一次查询时另回 `syncing`，见 [ADR-0073](0073-余额副本的快照、刷新与放行原因.md)。内存实现没有积分，只返回 `account` 与 `instance`。

`GET /v1/llm/quota` 增加两个可空字段：`charged_points` 是当天核销成功的积分，`remaining_points` 是可用积分，即余额副本减去没有反映的核销、再减去当天已经占用（已结算与在途预留）还没有记进流水的计费量折成的积分（向下取整），与额度放行用同一个口径，见 [ADR-0073](0073-余额副本的快照、刷新与放行原因.md)。没有开通收款时两项都是 null，客户端不显示积分那一行。账号页在聊天额度下面加一行“今天已从积分扣除 N 分，剩余 M 分”，只在两项都有时出现；当天没有超额核销时写成“今天还没有从积分扣除”。

客户端按 `reason` 分支：`account` 与 `points` 给出“购买积分”入口，打开账号与云同步页的购买面板；`instance` 只说明当天额度用完、稍后再试，不给购买入口。提示文案与入口都在回答下方的失败说明里，与“重试这次回答”并排；原因随保存的回答一起落库，重新打开讨论后仍按它决定说法与入口。

## 代价与边界

两列要在同一行上同步维护，任何一条结算路径漏写都会让额度判定与核销各看一套数字。结算把预留转成实际用量是一次写操作，重复结算会让同一次用量记两遍；调用方保证每次预留只结算一次，异常顺序由“预留与已结算都不小于 0”兜住，但重复结算仍然会多记，这一点与改动前相同。

预留改成整份成功或整份拒绝之后，一次请求要么完全放行、要么完全不写库，失败不再留下半份预留，代价是接近额度的请求会整单被拒，而不是按剩余量放一点。这是 ADR-0070 已经定下的行为，本条只是把拒绝的原因带出来。

`used_tokens` 与账号页的已用量现在不含在途请求，刷新时不会先跳高再回落；代价是同一时刻两个页面看到的数字可能相差一个请求的量，这个差在结算之后消失。`remaining_points` 取的是可用积分，因此它可能比支付宝一侧显示的余额少几分为在途核销，这个口径由 [ADR-0073](0073-余额副本的快照、刷新与放行原因.md) 定稿；它按已占用量算，有在途请求时也会比只按已结算量算的数少一份预留，这样页面显示的数不会大于实际还能放行的量。

`reason` 只在账号额度与实例预算两种判定都有明确结论时给出。免费额度没有配置（不限额度）时不会出现这三种原因。

## 替代方案

在 `llm_usage` 加一列“已核销的计费 token”，核销读它。没有采纳的原因是这样又多出一列要维护，而且它与“已结算量”是同一个数，两列迟早会对不上；直接拆成已结算与在途两列，核销读前者即可。

预留时把估算量记进一个进程内的表，结算后清掉。没有采纳的原因是服务端可能重启，重启之后在途请求的预留丢失，额度判定会按旧值通过；放在同一行里随事务提交，崩溃之后仍能看见。

429 不区分原因，由客户端读已用量与额度自己判断。没有采纳的原因是客户端拿不到积分余额，判断不了“免费额度用完但还有积分”这种情况，而且实例预算与账号额度用的是同一份额度数字。

预留继续按剩余量截断，由代理把不足的部分当整单拒绝。没有采纳的原因是截断后的预留必须立刻结算退回，多一次写库与一次竞态窗口，而且原因仍然传不出来；整份成功或整份拒绝更简单。

## 影响

- 表结构：[schema.sql](../../server/internal/store/schema.sql) 的 `llm_usage` 增加 `reserved_tokens`；已有实例按[运维手册](../../server/运维手册.md#411-即刻收积分包的上线与回滚)的增量语句加列，这条是纯新增列，不重建库。
- 查询与存储：[queries/backup.sql](../../server/internal/store/queries/backup.sql) 的 `UsedTokens` 改为两者之和、新增 `SettledTokens`，`AddTokens` 改名 `AddReservedTokens`；[queries/quota.sql](../../server/internal/store/queries/quota.sql) 的 `SettleTokens` 改为按预留与实际两个参数结算。实现见 [pg/quota.go](../../server/internal/store/pg/quota.go) 与 [pg/nowpay.go](../../server/internal/store/pg/nowpay.go)。
- 额度接口：`Quota` 接口的 `Reserve` 改为整份成功或返回 `*QuotaExceededError`，新增 `Points`；[llmproxy/quota.go](../../server/internal/llmproxy/quota.go) 定义原因，[llmproxy/proxy.go](../../server/internal/llmproxy/proxy.go) 写进 429 的 `extra.reason` 并填充额度接口的两个积分字段。
- 契约与客户端：[openapi.yaml](../../server/api/openapi.yaml) 的 `LLMQuota` 增加 `charged_points` 与 `remaining_points`；客户端的失败类型、提示文案与购买入口见 [app/lib/ai/llm_failure.dart](../../app/lib/ai/llm_failure.dart)、[app/lib/ui/answer_notice.dart](../../app/lib/ui/answer_notice.dart) 与 [app/lib/ui/discussion_chat.dart](../../app/lib/ui/discussion_chat.dart)，账号页那一行见 [02](../02-产品与交互.md) 的“模型额度”一节。
- 验收：两个请求同时在途时结算先完成的一个，`nowpay_charge` 的 `billed_tokens` 只按已结算量算；429 的 `extra.reason` 在三种情况下分别是 `account`、`points` 与 `instance`；账号页在开通收款的实例上显示当天已用积分与剩余积分。
