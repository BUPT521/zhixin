# ADR-0054 数据版本的位置标记补强：分表摘要、云端序号、设备位置与命名版本同步

## 状态

已采纳（2026-11-23 定稿）。随 [ADR-0053](0053-标识按身份顺序指纹分工并收拢提交标识.md) 及 0.2.0 发出之前合并的那一次 schema 变化实施（见 [数据库结构过度设计审查](../数据库结构过度设计审查.md) 的 S13 至 S15 与 V12 至 V15），2026-11-23 实施完成。各操作对命名版本的影响依赖 [ADR-0056](0056-本机数据按账号分空间.md) 的本机空间口径。

## 日期

2026-11-23

## 背景

[ADR-0053](0053-标识按身份顺序指纹分工并收拢提交标识.md) 整理了标识之后，又对照 git 的 refs、remote-tracking ref、树哈希与 gc 的可达性判断，检查数据版本一侧的位置标记与摘要，找到四处记录不足。它们不是过度设计，而是少记了本该记的事实，和 [数据库结构过度设计审查](../数据库结构过度设计审查.md) 的“削减”口径方向相反，所以在那份审查里按“补强”归类，并逐条写明为什么不能由其他列派生。

1. 一致性摘要只有整库一个值（[ADR-0045](0045-同步两端的一致性摘要.md)）。不一致时只知道“不一致”，两个修复入口都要整库对齐，诊断记录也说不出差在哪张表。git 的树哈希对不上时可以逐层找到不同的子树。
2. 一条提交是否已经在云端、对应云端第几条，只能由 `sync.pushed` 这个整数游标推断。整库恢复、清除云端数据等场景靠 `sync.restore_align` 之类的标记补救。git 对每个远端有 remote-tracking ref，记得清楚。
3. 压缩门槛只看设备是否在活跃窗口内、是否声明了 `snapshot` 能力（[ADR-0047](0047-快照附件回收与压缩前的客户端门槛.md)），不看设备读到了哪。窗口之内但进度落后的设备会被压缩甩到 410，只能整库重新克隆。git gc 的做法是只清理已经没有引用的对象。
4. 命名版本（`revision_ref` 的行）指向本机整数提交编号，只存在本机，换设备看不到，也不会随同步出现。

## 决定

1. **摘要按表拆开，总摘要保持不变。** 摘要定义沿用 [ADR-0045](0045-同步两端的一致性摘要.md)：每行按“表名、主键、规范化整行”做 SHA-256，按 2^256 取模求和。现在把同一个和按表分别累加：每张参与版本采集的业务表一个 64 位十六进制值，总摘要恒等于各表值之和，写事务收尾时核对这一恒等式。摘要增量在 Dart 侧计算（`revision_capture.dart` 合并净变化时得出 `digestDelta`，`_appendCommit` 把它加到父提交的摘要上），触发器不参与；改为按表得出增量映射，同时累加到对应表的值上，没有额外的行扫描。映射总是列出全部参与采集的表，没有行的表写 64 个 0，两端按同一组键比较。
   - 存放位置：本机只在 HEAD 上保存各表值，放在 S3 合并之后的单行状态表 `revision_state` 的 `table_digests_json` 一列里，不为每条提交存一份；每条提交仍只存总的 `state_digest`。检查点重建时按投影重算各表值。
   - 同步载荷：推送挂摘要的那条提交，在 `state_digest` 旁带可选字段 `table_digests`（表名到 64 位十六进制值的映射），服务端原样保存与回传，不解析内容；`sync_commit` 加可空列保存。各表值只存在 HEAD 上，推送期间又落了本机提交时 HEAD 已经前进，所以附带之前先核对“各表之和等于这条提交的 `state_digest`”，不等就不带，只带总摘要。
   - 比较与展示：先比总摘要，不一致再按表比，账号页的同步卡写明哪几张表不同，`cloud_sync_digest` 诊断记录也写出不一致的表名。
   - 修复范围：两个修复入口分开处理。“以本机为准修复”（`repairFromLocal`）本来就只补传云端从没碰过的本机行、从不删除云端的行，按表只是在挑行时再加一个条件：只看不一致的表；云端那条提交没带分表值时退回看全部表。正常情况下一致的表里本来就挑不出行，收益在云端历史被压缩之后：那时云端碰过的行只能从本机保留的远端提交推断，本机历史裁剪过的话会把一致的表里大量行误判成云端缺的、重复上传，按表过滤正好挡掉。“以云端为准修复”仍整库对齐：远端提交要整条应用，拆开按表应用在 `revision_change` 与 `sync_shadow` 里没有定义；客户端有 23 个外键动作（10 个级联删除、13 个置空），按表应用会把修改带到一致的表上并作为本机提交推出去；而一致的表与云端逐行相同，整库对齐在这些表上不产生实际变化，损失只是应用时间。

2. **提交记录云端序号 `server_seq`。** `revision_commit` 加可空列 `server_seq`：拉取应用的远端提交记它的服务端序号；本机提交推送成功后记服务端给它的序号。推送响应因此要返回逐条序号（与请求里实际发出的提交按顺序对应），这是契约的增补，与 [ADR-0053](0053-标识按身份顺序指纹分工并收拢提交标识.md) 里 `request_id` 改名为 `uid` 同批修改。新提交的序号是 `head + i + 1`，按服务端过滤掉重复之后的顺序分配；被当作重复跳过的提交返回它原来的序号，为此 `sync_commit_seen` 增加 `seq` 列，插入时写入，压缩删掉旧提交之后仍查得到。响应丢失后整批重发正是这种情形。服务端对整批重放不检查 `base`、直接返回当前 head，客户端据逐条序号判断：全部不大于自己带上去的 `base`，就是整批重放，服务端位置保持在 `base`，不跳到响应里的 head，否则拉取之后、推送之前另一台设备推的提交会被跳过。`sync.pushed` 与 `sync.server_head` 两个游标保留，继续承担“阻止清理历史”“增量起点”的职责，不因为有了逐条记录而删除；这条决定只补记录，是否能进一步用 `server_seq` 推出游标留待以后，先证明等价再动。按 [ADR-0056](0056-本机数据按账号分空间.md)，一个本机库只属于一个账号，切换账号打开的是另一个库，不存在“同一个库换账号后清空 `server_seq`”的情形；本机空间第一次关联账号时，库里的 `server_seq` 本来就全为空。

3. **压缩门槛增加设备位置这一条。** `sync_device` 增加 `synced_seq`（默认 0），记这台设备已经应用到的服务端序号。位置不需要新的上报：拉取请求里的 `after` 本来就是设备已应用到的位置，带 `X-Device-Id` 的拉取请求据此取较大值更新。客户端在整页应用并保存位置之后才发下一页请求，所以 `after` 不会高估；最后一页之后没有请求，服务端记下的位置落后一页，偏保守。推送时按请求里的 `base` 取较大值，确有新提交写入时再推进到新 head；整批重放不推进到当前 head，因为设备并没有读到别的设备在这期间推的提交。所有更新都不超过当前 head：清除全部数据之后 head 回到 0，别的设备还会带着旧的大位置来拉取。登记快照时的常规压缩（[ADR-0043](0043-服务端快照登记与提交序列压缩.md) 决定第 3 条）在原有的“早于保留期”与“不越过快照位置”之外，再要求不越过最近 `ZHIXIN_SYNC_DEVICE_ACTIVE`（默认 720 小时，即 30 天，以配置为准）内出现过的设备的最小 `synced_seq`，活跃窗口之内落后的设备因此不会被压缩甩到 410。[ADR-0047](0047-快照附件回收与压缩前的客户端门槛.md) 的能力声明门槛保留。账号序列预算压力下的压缩（ADR-0043 决定第 4 条）仍然有意忽略保留期，也同样忽略设备位置：快照已经是可用基线，继续写入比保住落后设备的增量更重要。

4. **命名版本引用 `uid`，并随账号同步名字；`HEAD` 移出 `revision_ref`。**
   - 本机命名版本：`revision_ref` 增加 `commit_uid`（文本，非空），删除 `commit_id`，不再存本机整数编号。引用到本机提交时按 `revision_commit.uid` 查：它有唯一索引 `idx_revision_uid`，一次索引查找就得到编号；查不到就是只剩标签的名字，不用另存一个可空的编号来表示。本机整数编号仍然是本机提交的主键，不出设备，同步只传 uid。另加 `sync_state` 一列，取值“干净”“已改”，见下面的合并规则。墓碑不放在这张表里，见下面的“墓碑”。
   - 为什么不两列都存：编号能由 uid 一次索引查找得到，存下来就是一份派生数据，要自己维护。本机没有这条提交的名字要置空；名字先同步过来、提交后来才拉到时要回填；这两处只要漏掉一处，引用就和提交对不上。只存 uid 这两种状态都由查询结果直接给出，没有需要维护的不变量。
   - `HEAD` 移到 S3 合并之后的单行状态表 `revision_state`，加一列 `head_commit_id`（整数，指向 `revision_commit.id`）。`revision_ref` 因此只存命名版本，没有哨兵行，整张表只有一种形状，也不再依赖“`HEAD` 恒等于最大提交编号”这个没有逐条核对过的结论：`HEAD` 就是这一列，每次落库与提交编号的预留同在一次 `UPDATE` 里写。`headId` 变成单行直读，不必联表；`revision_ref` 里不再有 `HEAD` 行，各处 `name != 'HEAD'` 的过滤、`nameCommit` 与 `deleteName` 对 `HEAD` 名字的拦截、同步命名版本时要排除 `HEAD` 的特例都不再需要。`HEAD` 不需要自己的 uid，它指向的提交本来就有。
   - `head_commit_id` 写成 `NOT NULL DEFAULT 0`，不加外键。`revision_context` 与 `revision_sequence` 两行都在 `installRevisionSchema`（`revision_capture.dart`）里创建，它在 `_ensureMetadata` 写入基线提交之前执行，合并后的 `revision_state` 这一行同样早于任何提交存在，加外键就插不进去。基线提交的编号恒为 0，默认值 0 正好指向它，不需要可空。`_ensureMetadata` 里“缺 `HEAD` 行就补成最大编号”的分支随之删除。
   - 服务端：新增账号级小表 `sync_ref`，每行是账号、名字、`commit_uid`、备注、更新时间与删除时间（墓碑，避免一台设备删除之后被另一台设备推回），主键是账号与名字；新增 `GET /v1/sync/refs` 与 `PUT /v1/sync/refs`（后写覆盖先写，请求体是名字、`commit_uid`、备注，或标记删除），与设备名册（[ADR-0048](0048-设备名册与提交来源的别名.md)）走同样的账号级、只存字节不解析的路线；每账号最多 200 个名字，名字最长 30 字，两端取同一组值。本机现在没有这两个上限（`nameCommit` 只拦空名与 `HEAD`），是新定的；名字先做 NFC 规范化，长度按规范化之后的字符数计，主键也按规范化之后的名字比较，不同键盘输入的同一个名字不会成为两条。服务端的删除时间（墓碑）永久保留，每行几十字节，不计入条数上限，比删除时间更早的写入不会让名字复活。
   - 合并规则：不做操作队列，用 `sync_state` 加后写覆盖。命名版本只是标签，与设备别名（ADR-0048）同样取舍，后写覆盖先写，不记冲突、不做冲突界面。本机新建、改名、改备注时置“已改”；同步时先把“已改”的行与墓碑推送上去，再拉取云端列表，替换所有“干净”的行，推送成功的置“干净”，推送成功的墓碑删行。两台设备离线时改同一个名字，后到达服务端的生效。未登录期间所有本机名字都保持“已改”，首次登录时一并推送。需要合并的情形有两种：首次登录（本机空间第一次关联账号），以及恢复备份（备份里的 `revision_ref` 整份换进来，见下面）。两种都把本机名字全部置为“已改”，本机与云端出现同名但指向不同提交时，保留云端的，把本机那条改名为“名字（本机）”再推送，改名后仍冲突就依次加序号，不静默覆盖另一台设备上起的名字。现有 `nameCommit` 本来就按名字覆盖，与这条规则一致。
   - 墓碑：只有用户显式删除一个名字才留墓碑，它的意思是“这个名字在所有设备上都要消失”。墓碑放在新表 `revision_ref_tombstone`（名字、删除时间，`revision_` 前缀，不参与采集），推送成功后删行；`revision_ref` 里因此没有“已删”的行，`refs()` 与各处计数不用加过滤。下面这些操作也会让本机少掉名字，但都只是这台设备或这个空间自己的事，不留墓碑（口径见 [ADR-0056](0056-本机数据按账号分空间.md)）：
     - 清理本机历史：删除本机全部提交明细、检查点与命名版本（包括还没推送的），墓碑表一并清空。下次同步时云端的名字照常拉回来，提交不在本机，显示为“只剩标签”。
     - 清除全部数据：服务端 `Reset` 清掉 `sync_ref`，本机空间整个清空，没有需要传播的删除。
     - 恢复备份：本机库整份换成备份，按上面的合并规则处理，备份里带着的墓碑表清空，旧备份不能删掉云端后来的名字。
     - 切换账号：按 ADR-0056 打开另一个空间，各空间的 `revision_ref` 互不相干，不需要规则。
   - 能否恢复取决于提交是否还在本机：名字指向的提交仍在本机保留历史里，可以像本机命名版本一样查看、比较与恢复；本机已经没有这条提交（被裁剪、重新克隆之前就已压缩、或在别的设备上建立后才同步过来而服务端已压缩），这个名字只显示为标签，注明“该版本的历史不在本机”，不可恢复。服务端不为命名版本保留被压缩的提交（见替代方案），界面在“只剩标签”的说明里提示：需要长期保留的版本请导出版本库备份。命名版本跨越本机裁剪边界时先固化为 `named` 检查点的规则（[01 第 7 章](../01-ER数据模型.md#7-导出恢复与版本)）对同步过来的名字同样适用，只要提交当时还在本机。

## 代价与边界

- 表结构：客户端 `revision_commit` 增加 `server_seq` 一列，`revision_state` 增加 `table_digests_json` 与 `head_commit_id` 两列（它依赖审查 S3 把 `revision_context` 与 `revision_sequence` 合并成 `revision_state`，两件事要进同一批），`revision_ref` 增加 `commit_uid` 与 `sync_state`、删除 `commit_id` 与 `HEAD` 行，新增墓碑表 `revision_ref_tombstone`；服务端 `sync_device` 增加 `synced_seq`、`sync_commit` 增加可空的分表摘要列、`sync_commit_seen` 增加 `seq`、新增 `sync_ref` 表。客户端部分按 [ADR-0017](0017-表结构变化仍清空数据.md) 清空重建，所以只能赶在 0.2.0 前与那次 schema 变化合并做；服务端部分不涉及客户端清库，但改契约，随同步重构批一起发。
- 契约：推送响应增加逐条序号，拉取、推送载荷增加可选的 `table_digests`，新增 `/v1/sync/refs`。旧客户端不认识新字段，两端按开发阶段的惯例一起升级。
- 分表摘要增加载荷与存储，量级是每个挂摘要的提交一份“表名到 64 位十六进制值”的映射，约一到两 KB，只在推送最后一条提交时带，不影响 2 MiB 单提交上限的判断。
- 常规压缩因设备位置而变慢：活跃窗口内有一台设备长时间不同步，常规压缩就停在它的位置之后，最长停到它离开活跃窗口为止；账号序列预算压力下的压缩不受影响，所以不会因此出现 `storage_full`。
- 命名版本的名字同步了，历史不一定同步：服务端压缩之后，新设备或重新克隆的设备看到的是只剩标签的名字。需要长期保留某个版本时，仍然要在建立它的设备上保留历史，或者由用户导出版本库备份。
- `server_seq` 是对“服务端给这条提交排了第几号”这一外部事实的记录，不能由本机其他列算出，这是它作为新增列的理由；它可以为空，空值只意味着显示不到这条信息，不影响同步正确性。
- “以云端为准修复”不因分表摘要缩小范围，仍整库对齐；它在一致的表上不产生实际变化，代价只是应用时间。
- 分表摘要只缩小诊断与补传范围，不能定位到行。表很大时要定位到行范围需要把摘要做成按主键分桶的树，目前表规模用不上。

## 替代方案

- 每条提交都存分表摘要：每条多一到两 KB，保留 500 条提交就是几百 KB，而本机只在 HEAD 与同步点用得到。不采纳。
- 把摘要做成按主键分桶的 Merkle 树，直接定位到行范围：实现复杂，当前表规模下表级已经够用，将来出现单表过大再评估。不采纳。
- 本机提交落库时记基点 `base_seq`（当时已知的云端位置），在数据版本页写“基于云端第 N 条”：它只用于显示，不参与任何判定，也不进同步载荷；同步推送本来就带一个按推送时刻算的 `baseSeq` 做乐观锁（`sync_service.dart`），那是另一个值，和落库时刻的值不是一回事，但判定用不到后者。显示用的需求并不确定，列和每次落库的写入却是实打实的成本，所以不加。同步排错确实需要它时再补，不影响现有数据的正确性。不采纳。
- 直接用 `server_seq` 取代 `sync.pushed` 游标：需要先证明两者在整库恢复、清除全部数据等场景下等价，本条先只补记录。不采纳本轮。
- 设备位置由客户端另用请求头上报：拉取请求里的 `after` 已经是这个位置，不需要新字段。不采纳。
- 命名版本做成版本化业务表，随提交同步：它会进入检查点与摘要，恢复到旧版本时名字跟着回滚，命名这个动作也会变成一条可撤销的提交，语义混杂。不采纳。
- `revision_ref` 同时保留 `commit_uid`（非空）与 `commit_id`（可空）：多出一份可由 uid 推出的编号，置空与回填都要自己维护，见决定第 4 条。不采纳。
- `HEAD` 继续作为 `revision_ref` 的一行，只给它补 uid：`headId` 要联表，各处过滤 `name != 'HEAD'`、拦截 `HEAD` 名字、同步时排除 `HEAD` 这些特例都保留，表里仍是两种语义混在一起。不采纳。
- 两个修复入口都只处理不一致的表：“以云端为准”要把远端提交拆开按表应用，拆开之后的提交在 `revision_change` 与 `sync_shadow` 里怎么记没有定义，外键动作还会把修改带到一致的表上并推出去；省下的只是应用时间。不采纳。
- 修复范围按外键图扩成闭包再按表处理：业务表多半互相连着，闭包往往接近整库，复杂而省不下多少。不采纳。
- 墓碑作为 `revision_ref` 的一种 `sync_state`（“已删”）：各处读取都要再加过滤，正是把 `HEAD` 移出去想删掉的那类特例。不采纳。
- 凡是让本机少掉名字的操作都留墓碑：在一台设备上清理本机历史，就会删掉所有设备上的名字，而用户只是想腾出这台设备的空间。不采纳。
- 服务端墓碑只保留一段时间（例如与活跃窗口对齐）：离线超过这段时间的设备回来时会把删掉的名字推回来；墓碑每行几十字节，永久保留的成本可以忽略。不采纳。
- 服务端按命名版本钉住压缩下界：一个很旧的名字就能永久阻止压缩，与压缩要解决的预算问题冲突。不采纳。

## 实施前要核对的

本节各条已于 2026-11-23 随实施核对完毕，结论写在各条末尾；核对不通过的条目按条目里的退路处理。

- 推送响应现在只有 `head`（`syncsvc/handler.go`）；新提交的序号在 `pg/sync.go` 的 `Append` 里按 `head + i + 1` 分配，能按请求顺序回传；重复提交由 `PlanAppend` 按 `sync_commit_seen` 过滤，那张表没有序号，所以加 `seq` 列（决定第 2 条）。
- 拉取位置只在整页应用完成并保存之后才推进（`sync_service.dart` 的 `_pull`），`after` 可以直接当设备位置；`persist: false` 的两处只读重读从 0 开始，取较大值不会倒退。**核对结论：成立。** 实施时把“按 `after` 推进设备位置”写在服务端拉取接口里，重读那次同样只取较大值，因此只有高估位置的风险为零、落后一页的偏保守情形。
- 本机命名版本现在没有条数与名字长度上限，两个上限是新定的（决定第 4 条）。**核对结论：成立。** 实施时每账号 200 个名字、名字最长 30 个字由两端各自校验，服务端另在库内按条件插入兜底并发。
- `revision_context` 与 `revision_sequence` 都在 `installRevisionSchema` 里创建，早于基线提交（决定第 4 条 `head_commit_id` 的写法）。**核对结论：成立。** 合并成 `revision_state` 之后同一位置创建这一行，`head_commit_id` 仍写成 `NOT NULL DEFAULT 0`、不加外键。
- 整批重放时客户端跳过别的设备提交的问题（决定第 2 条）是读代码推出来的，实施前先补一个用例复现：本机拉取之后、推送之前另一台设备推送，本机整批重发已推过的提交，断言下一次拉取仍能拿到另一台设备的提交。**核对结论：原现象不成立。** 复审用三组实验核对过：只要批次里有新提交，服务端就按 `base` 核对后返回 409，客户端重新拉取；整批重复只在“上一次推送其实成功、只是响应丢失”时出现，而那时本机推送位置还没写、下一轮拉取会从旧位置重新读。所以这一条降为防御：推送响应带上逐条序号之后，客户端按“响应里的序号都不大于自己带上去的 `base`”判断整批重放，此时不推进服务端位置、不记逐条序号（见审查 7.1 与 `sync_service_test` 的整批重放用例）。
- 恢复备份、清理本机历史、清除全部数据三条路径各自对 `revision_ref`、`revision_ref_tombstone` 与 `sync_state` 的处理，按决定第 4 条的“墓碑”逐条补测试。**核对结论：三条路径的处理已实施并有测试。** 清理本机历史删掉全部名字并清空墓碑表；清除全部数据整个清空当前空间、服务端 `Reset` 一并清掉 `sync_ref`；恢复备份整库换成备份内容、恢复之后清空墓碑表并按首次登录的规则合并名字（本机名字全部置“已改”，同名指向不同提交时保留云端、本机改名为“名字（本机）”）。
- 活跃窗口以服务端配置 `ZHIXIN_SYNC_DEVICE_ACTIVE`（默认 720 小时，即 30 天，`config.go`）为准，[ADR-0048](0048-设备名册与提交来源的别名.md) 决定第 5 条的描述已与它对齐。**核对结论：成立。**
- `revision_commit.uid` 非空且有唯一索引（`tables.dart`），可作为 `revision_ref` 的查找键；提交编号由 `revision_sequence` 分配、只增不减，清理历史也不退回，但整库恢复旧备份后编号会重复（ADR-0040），所以引用必须与提交同库、同时被替换，只存 uid 对此没有影响；现有裁剪不会删除被命名版本指向的提交（`_pruneOnce` 排除 `namedCommits`），清理历史会把命名版本一起删掉，所以本机现状下引用不会悬空，悬空只会出现在从别的设备同步来的名字上。**核对结论：成立。** 实施时 `_pruneOnce` 先把命名版本的 uid 查成编号再参与裁剪保护，查不到编号的名字只剩标签、不参与保护。
- `HEAD` 现在在 `revision_ref` 里靠名字区分，相关位置有：`headId` 与落库时更新 `HEAD`（`revision_log.dart`）、初始化与补写 `HEAD`（`revision_engine.dart` 两处）、清理历史重写 `HEAD`（`revision_maintenance.dart`）、`refs()` 的 `name != 'HEAD'` 过滤、`nameCommit` 与 `deleteName` 的名字拦截、备份与导入以及数据版本总览里数命名版本的两处查询（`revision_package.dart`、`revision_service.dart`）。`headId` 被约 47 处调用，签名不变，只改实现。**核对结论：位置清单与实际一致。** 实施之后这些过滤与拦截全部删除，`headId` 改成单行直读。
- 把 `HEAD` 移到 `revision_state` 之后要逐处改的位置就是上面这几处，另有三处：`RevisionRefs.refsByCommit` 改按 uid 分组；`_pruneOnce` 里的 `namedCommits` 与跨越下界的 `crossing` 改为先把命名版本的 uid 查成编号；通知集合 `revisionHistoryTables`（`revision_engine.dart`）与 [ADR-0014](0014-流式查询与版本通知.md) 第 2 条目前把 `revision_ref` 当作每次提交都会写的表，`HEAD` 移走之后每次提交改写的是 `revision_state`，要同步改成对 `revision_state` 通知，历史页与总览读 `HEAD` 的位置也跟着换表。`named` 检查点仍按 `commit_id` 存，它指向本机提交，不受影响。**核对结论：成立，已按此实施。**
- 后续核对发现首笔实施只接通了命名版本接口和分表摘要传输。客户端现在会同步命名版本及其删除标记，恢复备份后合并同名版本；比较摘要时会记录不一致的表，本机修复补传后再根据云端数据核对结果。命名版本写入携带本机编辑时间，服务端据此识别晚到的旧编辑，并在账号锁内核对 200 条的上限。
