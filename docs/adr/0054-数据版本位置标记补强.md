# ADR-0054 数据版本的位置标记补强：分表摘要、云端序号、设备位置、命名版本同步

## 状态

提议。择期实施，与 [ADR-0053](0053-标识按身份顺序指纹分工并收拢提交标识.md) 及 0.2.0 发出之前合并的那一次 schema 变化同批（见 [数据库结构过度设计审查](../数据库结构过度设计审查.md) 的 S13 至 S15 与 V12 至 V14），代码未开工。

## 日期

2026-11-23

## 背景

[ADR-0053](0053-标识按身份顺序指纹分工并收拢提交标识.md) 整理了标识之后，又对照 git 的 refs、remote-tracking ref、树哈希与 gc 的可达性判断，检查数据版本一侧的位置标记与摘要，找到四处记录不足。它们不是过度设计，而是少记了本该记的事实，和 [数据库结构过度设计审查](../数据库结构过度设计审查.md) 的“削减”口径方向相反，所以在那份审查里按“补强”归类，并逐条写明为什么不能由其他列派生。

1. 一致性摘要只有整库一个值（[ADR-0045](0045-同步两端的一致性摘要.md)）。不一致时只知道“不一致”，两个修复入口都要整库对齐，诊断记录也说不出差在哪张表。git 的树哈希对不上时可以逐层找到不同的子树。
2. 一条提交是否已经在云端、对应云端第几条，只能由 `sync.pushed` 这个整数游标推断。整库恢复、清除云端数据等场景靠 `sync.restore_align` 之类的标记补救。git 对每个远端有 remote-tracking ref，记得清楚。
3. 压缩门槛只看设备是否在活跃窗口内、是否声明了 `snapshot` 能力（[ADR-0047](0047-快照附件回收与压缩前的客户端门槛.md)），不看设备读到了哪。窗口之内但进度落后的设备会被压缩甩到 410，只能整库重新克隆。git gc 的做法是只清理已经没有引用的对象。
4. 命名版本（`revision_ref` 的行）指向本机整数提交编号，只存在本机，换设备看不到，也不会随同步出现。

## 决定

1. **摘要按表拆开，总摘要保持不变。** 摘要定义沿用 [ADR-0045](0045-同步两端的一致性摘要.md)：每行按“表名、主键、规范化整行”做 SHA-256，按 2^256 取模求和。现在把同一个和按表分别累加：每张参与版本采集的业务表一个 64 位十六进制值，总摘要恒等于各表值之和，写事务收尾时核对这一恒等式。采集路径本来就逐行加减，改为同时累加到对应表的值上，没有额外的行扫描。
   - 存放位置：本机只在 HEAD 上保存各表值，放在 S3 合并之后的单行状态表 `revision_state` 的 `table_digests_json` 一列里，不为每条提交存一份；每条提交仍只存总的 `state_digest`。检查点重建时按投影重算各表值。
   - 同步载荷：推送挂摘要的那条提交，在 `state_digest` 旁带可选字段 `table_digests`（表名到 64 位十六进制值的映射），服务端原样保存与回传，不解析内容；`sync_commit` 加可空列保存。
   - 比较与展示：先比总摘要，不一致再按表比，账号页的同步卡写明哪几张表不同，`cloud_sync_digest` 诊断记录也写出不一致的表名。
   - 修复范围：两个修复入口应用云端提交、补传基线时只处理不一致的表。服务端仍然不解析内容，“以云端为准”仍要拉取提交或快照，下载量不变；省下的是应用与补传的范围和对用户的说明。

2. **提交记录云端序号 `server_seq`。** `revision_commit` 加可空列 `server_seq`：拉取应用的远端提交记它的服务端序号；本机提交推送成功后记服务端给它的序号。推送响应因此要返回逐条序号（与请求里实际发出的提交按顺序对应），这是契约的增补，与 [ADR-0053](0053-标识按身份顺序指纹分工并收拢提交标识.md) 里 `request_id` 改名为 `uid` 同批修改。`sync.pushed` 与 `sync.server_head` 两个游标保留，继续承担“阻止清理历史”“增量起点”的职责，不因为有了逐条记录而删除；这条决定只补记录，是否能进一步用 `server_seq` 推出游标留待以后，先证明等价再动。换账号按新账号重新建立基线时，清空本机提交的 `server_seq`。

3. **压缩门槛增加设备位置这一条。** `sync_device` 增加 `synced_seq`，记这台设备已经应用到的服务端序号。位置不需要新的上报：拉取请求里的 `after` 本来就是设备已应用到的位置，带 `X-Device-Id` 的拉取请求据此取较大值更新；推送成功后设备位置推进到响应里的新 head。登记快照时的常规压缩（[ADR-0043](0043-服务端快照登记与提交序列压缩.md) 决定第 3 条）在原有的“早于保留期”与“不越过快照位置”之外，再要求不越过最近 `ZHIXIN_SYNC_DEVICE_ACTIVE`（默认 720 小时，即 30 天，以配置为准）内出现过的设备的最小 `synced_seq`，活跃窗口之内落后的设备因此不会被压缩甩到 410。[ADR-0047](0047-快照附件回收与压缩前的客户端门槛.md) 的能力声明门槛保留。账号序列预算压力下的压缩（ADR-0043 决定第 4 条）仍然有意忽略保留期，也同样忽略设备位置：快照已经是可用基线，继续写入比保住落后设备的增量更重要。没有位置记录的旧行按 0 处理，只要它仍在活跃窗口内就会拦住常规压缩，这是旧客户端仍然需要升级的信号。

4. **命名版本引用 `uid`，并随账号同步名字；`HEAD` 移出 `revision_ref`。**
   - 本机命名版本：`revision_ref` 增加 `commit_uid`（文本，非空），删除 `commit_id`，不再存本机整数编号。引用到本机提交时按 `revision_commit.uid` 查：它有唯一索引 `idx_revision_uid`，一次索引查找就得到编号；查不到就是只剩标签的名字，不用另存一个可空的编号来表示。本机整数编号仍然是本机提交的主键，不出设备，同步只传 uid。另加 `sync_state` 一列，取值“干净”“已改”“已删”，见下面的合并规则。
   - 为什么不两列都存：编号能由 uid 一次索引查找得到，存下来就是一份派生数据，要自己维护。本机没有这条提交的名字要置空；名字先同步过来、提交后来才拉到时要回填；这两处只要漏掉一处，引用就和提交对不上。只存 uid 这两种状态都由查询结果直接给出，没有需要维护的不变量。
   - `HEAD` 移到 S3 合并之后的单行状态表 `revision_state`，加一列 `head_commit_id`（整数，指向 `revision_commit.id`）。`revision_ref` 因此只存命名版本，没有哨兵行，整张表只有一种形状，也不再依赖“`HEAD` 恒等于最大提交编号”这个没有逐条核对过的结论：`HEAD` 就是这一列，每次落库与提交编号的预留同在一次 `UPDATE` 里写。`headId` 变成单行直读，不必联表；`revision_ref` 里不再有 `HEAD` 行，各处 `name != 'HEAD'` 的过滤、`nameCommit` 与 `deleteName` 对 `HEAD` 名字的拦截、同步命名版本时要排除 `HEAD` 的特例都不再需要。`HEAD` 不需要自己的 uid，它指向的提交本来就有。
   - `head_commit_id` 是否加外键（指向 `revision_commit(id)`，不设级联）实施时再定：加上能挡住误删 `HEAD` 所在的提交。要核对两点：`revision_sequence` 现在在基线提交写入之后才创建（`revision_engine.dart` 初始化路径），但合并进来的 `revision_context` 的创建时机还没读，如果它早于基线提交，`head_commit_id` 就要可空；恢复与整库替换路径的删除顺序也要核对。不加外键不影响本条的目的。
   - 服务端：新增账号级小表 `sync_ref`，每行是账号、名字、`commit_uid`、备注、更新时间与删除时间（墓碑，避免一台设备删除之后被另一台设备推回），主键是账号与名字；新增 `GET /v1/sync/refs` 与 `PUT /v1/sync/refs`（后写覆盖先写，请求体是名字、`commit_uid`、备注，或标记删除），与设备名册（[ADR-0048](0048-设备名册与提交来源的别名.md)）走同样的账号级、只存字节不解析的路线；每账号条数设上限（建议 200，与本机命名版本的上限对齐，实施时定）。
   - 合并规则：不做操作队列，用 `sync_state` 加后写覆盖。命名版本只是标签，与设备别名（ADR-0048）同样取舍，后写覆盖先写，不记冲突、不做冲突界面。本机新建、改名、改备注时置“已改”，删除时保留一行墓碑置“已删”；同步时先把“已改”与“已删”的推送上去，再拉取云端列表，替换所有“干净”的行，推送成功的置“干净”，墓碑行随之清掉。两台设备离线时改同一个名字，后到达服务端的生效。未登录期间所有本机名字都保持“已改”，首次登录时一并推送。首次登录是唯一单独处理的情形：本机与云端出现同名但指向不同提交时，保留云端的，把本机那条改名为“名字（本机）”再推送，不静默覆盖另一台设备上起的名字。现有 `nameCommit` 本来就按名字覆盖，与这条规则一致。
   - 能否恢复取决于提交是否还在本机：名字指向的提交仍在本机保留历史里，可以像本机命名版本一样查看、比较与恢复；本机已经没有这条提交（被裁剪、重新克隆之前就已压缩、或在别的设备上建立后才同步过来而服务端已压缩），这个名字只显示为标签，注明“该版本的历史不在本机”，不可恢复。服务端不为命名版本保留被压缩的提交（见替代方案），界面在“只剩标签”的说明里提示：需要长期保留的版本请导出版本库备份。命名版本跨越本机裁剪边界时先固化为 `named` 检查点的规则（[01 第 7 章](../01-ER数据模型.md#7-导出恢复与版本)）对同步过来的名字同样适用，只要提交当时还在本机。

## 代价与边界

- 表结构：客户端 `revision_commit` 增加 `server_seq` 一列，`revision_state` 增加 `table_digests_json` 与 `head_commit_id` 两列（它依赖审查 S3 把 `revision_context` 与 `revision_sequence` 合并成 `revision_state`，两件事要进同一批），`revision_ref` 增加 `commit_uid` 与 `sync_state`、删除 `commit_id` 与 `HEAD` 行（一增一删，净列数不变）；服务端 `sync_device` 增加 `synced_seq`、`sync_commit` 增加可空的分表摘要列、新增 `sync_ref` 表。客户端部分按 [ADR-0017](0017-表结构变化仍清空数据.md) 清空重建，所以只能赶在 0.2.0 前与那次 schema 变化合并做；服务端部分不涉及客户端清库，但改契约，随同步重构批一起发。
- 契约：推送响应增加逐条序号，拉取、推送载荷增加可选的 `table_digests`，新增 `/v1/sync/refs`。旧客户端不认识新字段，两端按开发阶段的惯例一起升级。
- 分表摘要增加载荷与存储，量级是每个挂摘要的提交一份“表名到 64 位十六进制值”的映射，约一到两 KB，只在推送最后一条提交时带，不影响 2 MiB 单提交上限的判断。
- 常规压缩因设备位置而变慢：活跃窗口内有一台设备长时间不同步，常规压缩就停在它的位置之后，最长停到它离开活跃窗口为止；账号序列预算压力下的压缩不受影响，所以不会因此出现 `storage_full`。
- 命名版本的名字同步了，历史不一定同步：服务端压缩之后，新设备或重新克隆的设备看到的是只剩标签的名字。需要长期保留某个版本时，仍然要在建立它的设备上保留历史，或者由用户导出版本库备份。
- `server_seq` 是对“服务端给这条提交排了第几号”这一外部事实的记录，不能由本机其他列算出，这是它作为新增列的理由；它可以为空，空值只意味着显示不到这条信息，不影响同步正确性。
- 分表摘要只缩小诊断与应用范围，不能定位到行。表很大时要定位到行范围需要把摘要做成按主键分桶的树，目前表规模用不上。

## 替代方案

- 每条提交都存分表摘要：每条多一到两 KB，保留 500 条提交就是几百 KB，而本机只在 HEAD 与同步点用得到。不采纳。
- 把摘要做成按主键分桶的 Merkle 树，直接定位到行范围：实现复杂，当前表规模下表级已经够用，将来出现单表过大再评估。不采纳。
- 本机提交落库时记基点 `base_seq`（当时已知的云端位置），在数据版本页写“基于云端第 N 条”：它只用于显示，不参与任何判定，也不进同步载荷；同步推送本来就带一个按推送时刻算的 `baseSeq` 做乐观锁（`sync_service.dart`），那是另一个值，和落库时刻的值不是一回事，但判定用不到后者。显示用的需求并不确定，列和每次落库的写入却是实打实的成本，所以不加。同步排错确实需要它时再补，不影响现有数据的正确性。不采纳。
- 直接用 `server_seq` 取代 `sync.pushed` 游标：需要先证明两者在整库恢复、清除云端、换账号等场景下等价，本条先只补记录。不采纳本轮。
- 设备位置由客户端另用请求头上报：拉取请求里的 `after` 已经是这个位置，不需要新字段。不采纳。
- 命名版本做成版本化业务表，随提交同步：它会进入检查点与摘要，恢复到旧版本时名字跟着回滚，命名这个动作也会变成一条可撤销的提交，语义混杂。不采纳。
- `revision_ref` 同时保留 `commit_uid`（非空）与 `commit_id`（可空）：多出一份可由 uid 推出的编号，置空与回填都要自己维护，见决定第 4 条。不采纳。
- `HEAD` 继续作为 `revision_ref` 的一行，只给它补 uid：`headId` 要联表，各处过滤 `name != 'HEAD'`、拦截 `HEAD` 名字、同步时排除 `HEAD` 这些特例都保留，表里仍是两种语义混在一起。不采纳。
- 服务端按命名版本钉住压缩下界：一个很旧的名字就能永久阻止压缩，与压缩要解决的预算问题冲突。不采纳。

## 实施前要核对的

- 推送响应能否给出逐条服务端序号，被当作重复而跳过的提交能否给出原序号；给不出时 `server_seq` 留空，只影响显示。
- 拉取的“已应用位置”是否只在整页应用完成之后才推进。如果先推进再应用，用 `after` 当设备位置会高估，需要改成应用之后再发下一次请求时才带新位置。
- 命名版本现有的名字长度与条数上限，决定 `sync_ref` 的约束。
- 活跃窗口以服务端配置 `ZHIXIN_SYNC_DEVICE_ACTIVE`（默认 720 小时，即 30 天，已在 `config.go` 核对）为准；[ADR-0048](0048-设备名册与提交来源的别名.md) 写的“54 天没有出现过的设备视为不活跃”与它不一致，实施时顺手更正 ADR-0048 的描述。
- 已核对：`revision_commit.uid` 非空且有唯一索引（`tables.dart`），可作为 `revision_ref` 的查找键；提交编号由 `revision_sequence` 分配、只增不减，清理历史也不退回，但整库恢复旧备份后编号会重复（ADR-0040），所以引用必须与提交同库、同时被替换，只存 uid 对此没有影响；现有裁剪不会删除被命名版本指向的提交（`_pruneOnce` 排除 `namedCommits`），清理历史会把命名版本一起删掉，所以本机现状下引用不会悬空，悬空只会出现在从别的设备同步来的名字上。
- 已核对：`HEAD` 现在在 `revision_ref` 里靠名字区分，相关位置有：`headId` 与落库时更新 `HEAD`（`revision_log.dart`）、初始化与补写 `HEAD`（`revision_engine.dart` 两处）、清理历史重写 `HEAD`（`revision_maintenance.dart`）、`refs()` 的 `name != 'HEAD'` 过滤、`nameCommit` 与 `deleteName` 的名字拦截、备份与导入以及数据版本总览里数命名版本的两处查询（`revision_package.dart`、`revision_service.dart`）。`headId` 被约 47 处调用，签名不变，只改实现。
- 把 `HEAD` 移到 `revision_state` 之后要逐处改的位置就是上面这几处，另有三处：`RevisionRefs.refsByCommit` 改按 uid 分组；`_pruneOnce` 里的 `namedCommits` 与跨越下界的 `crossing` 改为先把命名版本的 uid 查成编号；通知集合 `revisionHistoryTables`（`revision_engine.dart`）与 [ADR-0014](0014-流式查询与版本通知.md) 第 2 条目前把 `revision_ref` 当作每次提交都会写的表，`HEAD` 移走之后每次提交改写的是 `revision_state`，要同步改成对 `revision_state` 通知，历史页与总览读 `HEAD` 的位置也跟着换表。`named` 检查点仍按 `commit_id` 存，它指向本机提交，不受影响。
- 本条以文档与 `server_client.dart` 的方法签名为依据，没有读 `sync_service.dart` 的推送与拉取实现，也没有读服务端 `syncsvc`。

## 影响
