# ADR-0045 同步两端的一致性摘要

## 状态

已采纳

## 日期

2026-11-21

## 背景

同步按提交增量进行，两台设备各自修改、后到覆盖先到，冲突记录只写在本机。经过 [ADR-0040](0040-数据版本的提交身份与同步变基.md) 的按格变基、[ADR-0041](0041-同步位置的账号归属与整库恢复后的重新对齐.md) 的同步位置归属与 [ADR-0042](0042-数据版本基线的差异上传与时间优先留存.md) 的差异上传之后，两端仍然没有任何机制能发现“本机与云端已经不一致”：绕过命令事务的写入、被跳过的远端变化、整库恢复之后的重放，任何一种情况都只能等用户自己发现数据不对。[改进方案](../数据版本系统对照git的改进方案.md) 第 3.5 节把这一项列为 G8，并给出一个可以增量维护的整库摘要。

作出这条决定时的条件是：客户端负责计算与比较摘要，服务端只保存提交字节、不解析学习内容；两端都在开发阶段一起升级，表结构、契约与云端数据可以直接改；[ADR-0043](0043-服务端快照登记与提交序列压缩.md) 的服务端快照已经实现，快照登记里已经预留 `digest` 字段，客户端的首次同步下载快照与重新克隆尚未开始，所以摘要先用于检测，不承担重新克隆的判定。

## 决定

1. 摘要的定义固定为“表名 + 主键 + 规范化整行”的 SHA-256 多重集之和。每一行按表名、主键与整行拼成规范字符串，整行按列名升序排列，每个值写成 `{"t": 类型, "v": 内容}`，三部分各占一行；对这段字符串做 SHA-256 得到一个 256 位整数，再把全部业务行的整数按 2^256 取模求和，写成 64 位小写十六进制，空投影为 64 个 `0`。求和与读表顺序、行顺序无关，同一个状态只有一种写法。

2. 增量累加与整库重算得到同一个值。采集路径按“删除一行减一次、新增一行加一次、修改一行先减后加”算出这次命令的摘要增量，提交落库时把它加到父提交的 `state_digest` 上；整库重算按当前业务表逐行求和。检查点也保存一份投影摘要，重建时解码之后按投影重算并比对，投影与摘要对不上说明检查点本身坏了，不会被当成重建起点。

3. 契约增加可选字段 `state_digest`，服务端原样保存与回传。推送请求里的每条提交都可以带这个字段，契约把它限定为 64 位小写十六进制；服务端不解析内容，也不拿它判断一致性，只保存字节并在拉取时原样带回，没有带这个字段的提交在响应里不出现这个键。服务端不认识业务表的行格式，摘要的正确性由客户端保证。

4. 挂摘要的时机是推送结束且本机没有待推送提交，比较的时机是拉到的最新一条提交带着摘要且本机没有待推送提交。推送最后一条提交时，如果这次拉取没有跳过的变化、本机也没有已知的不一致，客户端读一次 `HEAD`、按当前表重算摘要，再确认 `HEAD` 没有变化，之后把摘要挂在最后一条提交上；首次同步的基线提交挂在最后一片上。拉取时记下本次最后一条提交带的摘要，拉完之后如果本机没有待推送提交，按当前表重算并比较；读位置与重算之间又写入了本机提交时跳过这一轮，等下一轮再比。

5. 不一致时账号页给出状态与一个重建入口。比较结果写进这个身份的同步状态（`cloud.json`），账号页的同步卡显示“本机与云端不一致”、状态标为“待修复”，并给出唯一入口“以本机为准重建云端”：先调用 `DELETE /v1/sync/commits` 清空这个账号的提交序列、快照、设备名册与命名版本，再把本机当前投影整份上传为新的基线；云端备份与附件字节不受影响。清空之后不需要再分辨哪边多、哪边少，也不会留下删不掉的行（过度设计审查 3.4）。入口先弹确认框并重新输入当前密码；清空成功而上传失败时本机记录不删除，云端可能已经清空，再同步一次会按首次同步重新对齐。清空期间有别的云操作时服务端返回 409，等它结束再重试。其他设备下一次同步发现服务端位置比本机记下的位置小，按首次同步重新对齐，不再要求用户确认一次，只把云端缺少的本机行补上去。

6. 不一致另写一条诊断记录。比较发现不一致时记一条 `kind = cloud_sync_digest` 的本机诊断，写明本机摘要、云端摘要与服务端位置；重建云端失败时记 `cloud_sync_rebuild`，说明本机记录没有删除。

## 代价与边界

重建云端是粗粒度的修复。它把账号在服务端的提交历史清空之后从头开始，提交数量、撤销窗口与命名版本的云端序列都不保留；其他设备第一次同步会各自重新上传本机内容，最后到达的覆盖先到达的。账号、整库备份与附件字节保留。清空之后本机与云端的摘要从同一条基线重新算起，不需要再比较哪几张表不同。

没有提交可挂摘要的轮次不发布。一轮同步只拉取、没有推送任何提交时，没有提交可以承载摘要；本机没有待推送提交时，下一轮推送才会把摘要挂上。首次同步的基线一篇都没有时同样不发布。

并发窗口短暂不成立时跳过一轮。挂摘要与比较都要读 `HEAD`、按当前表重算，读完之后 `HEAD` 又往前走了，这一轮就不挂也不比；跳过的代价是晚一轮发现不一致，不影响同步本身。

摘要只做检测，不做自动修复。发现不一致之后客户端不会自己选一边覆盖另一边，因为两边都可能包含用户还没有同步的修改；修复入口由用户选择，代价是用户可以暂时不处理，不一致状态一直显示到下一次同步或修复。

## 替代方案

- 不做一致性检测。改动最小，同步照旧；代价是 G1、G2、G5 这类问题出现之后只能等用户自己发现，数据版本页与提交历史看不出两边已经分叉。不采纳。
- 只比较提交数或服务端位置。实现简单，不需要算摘要；代价是提交数相同不代表内容相同，两台设备各自写入同样条数的提交、或者整库恢复之后重放同样条数，都会得到相同的计数而内容不同。不采纳。
- 由服务端计算摘要。客户端不用算，服务端在保存提交时按业务行重算；代价是服务端要理解每张业务表的行格式与规范化规则，与“服务端只保存字节、不解析学习内容”的分层冲突，客户端表结构每次变化都要改服务端。不采纳。
