# ADR-0067 聊天额度改走即刻收积分包

- 状态：已采纳，待即刻收商品审核发布后验收
- 日期：2026-11-25

## 背景

[ADR-0065](0065-支付宝购买聊天模型额度.md) 按支付宝 APP 支付接入了一次性聊天 Token 包，服务端自研 RSA2 签名、查单与异步通知，客户端用支付宝官方 SDK 打开收银台。生产应用 `2021007124660130` 签的是即刻收与 JSAPI，不是 APP 支付，客户端拿到的 `orderStr` 被收银台按“商家订单参数异常”（`ALI40247`）拒绝，这条通道买不到额度。

补签 APP 支付需要走“未上架”通道，审核只给三十天，即 11 月 25 日到 12 月 25 日；试用期 12 月 21 日开始，而应用商店上架链接在三十天内拿不到，软件著作权登记本身要一到两个月。因此补签即使通过，试用期一开始就会失效，长期不可持续。

团队已经拿到即刻收直连模式的白名单。直连模式不要求应用上架，商品、收费模式与档位价格在「即刻收」小程序里配置，审核发布之后拿到 `out_product_id`，应用服务端用同一套支付宝应用凭证调用六个接口完成购买、查余额与核销。额度单位只有次数与积分两种，知新按计费 token 计费，中间需要一层折算。

## 决定

停售 APP 支付，改为即刻收积分包直连。应用凭证继续保留，用于同一应用的即刻收签名；新增 `ZHIXIN_NOWPAY_PRODUCT_ID`、`ZHIXIN_TOKENS_PER_POINT` 与可选的 `ZHIXIN_NOWPAY_CALLBACK_URL`。`out_product_id` 从商品详情页复制，应用既不生成商品 ID，也不参与定价，档位与价格以小程序配置为准。

积分与计费 token 的折算按“一个积分等于一万个计费 token”。每轮对话结算提交之后，服务端按当天累计用量扣掉免费额度后的计费 token 除以一万并向上取整，再减去当天已申请且未失败的积分，只核销差额；一整天多记的积分因此不超过一个，短对话不会各自多记一次。折算比例做成配置项，改定价只改配置与小程序，不改代码；前台把当天用量与免费额度按同一比例折成积分展示，避免用户在 token 与积分之间换算。先扣当天的免费额度，超出部分才折成积分核销。

核销在交付之后。模型回答已经发给用户，服务端才按这一轮结算后的当天用量算出差额，写一条本地待核销流水，再由唯一的核销协程调用 `alipay.aipay.nowpaydirect.quota.verify`。流水编号本身就是提交给即刻收的 `out_request_no`，结果未知时只用原号查询或重试，不换号重扣：`PROCESSING`、超时与网关错误保持原状态，下一轮对话开工前用 `alipay.aipay.nowpaydirect.quota.refresh` 补查；确认 `FAILED` 或余额不足（`NOW_PAY_QUOTA_INSUFFICIENT`）记失败，下一次结算重新算差额。核销不可能放进数据库事务，本地流水与外部调用因此分成两步，任何一步失败都不会回滚已经交付的回答。

客户端只负责打开托管购买页。服务端按 `purchase.create` 取一张购买链接，客户端用外部应用打开 `alipays://` 入口，回到知新之后重新查 `quota.query` 刷新余额。`callback_url` 只决定支付页返回之后跳到哪里，不是到账通知，凭返回页不放行。同一账号同一档位在链接有效期内再次购买时复用原链接，不重复创单。

契约去掉支付宝异步通知与按订单号查单两条路径，保留三条：查商品与余额、取购买链接、单独查余额。`internal/payment` 只保留签名、验签与网关调用；下单、查单、通知处理器与 Android 侧的 SDK 通道已经删除，订单表、钱包表与已购额度日用量表也一并删除。

## 代价与遗留

只剩一套账。APP 支付时期写在 `model_quota_wallet` 的余额、下单表 `model_quota_purchase` 与已购额度日用量表在 2026-11-25 一并删除，那段时间没有完成一笔真实收款，停售之后也不会再产生新行；购买卡片只显示即刻收一侧的积分，对账不再需要区分本地钱包与支付宝余额。

核销不可撤销。即刻收当前不提供核销撤销与失败自动返还，交付之后发现服务本身出错，只能靠下一次结算的差额或人工处理；本地流水只是记录，不能凭它在支付宝一侧退款。

下行风险是交付了却没有扣到。核销协程是进程内的，队列满、进程被终止、连续查询失败都会让流水停在 `pending` 或 `processing`，这些账号在补查成功之前等于免费用了积分覆盖的部分。补查只在下一轮对话开工前触发，长期不用的账号不会自动补。队列容量 256、补查每次最多四条，都是按单实例的并发量估的，账号量上来之后要按积压情况调整。

积分折算比例是定价口径。一个积分一万个计费 token 是按当前渠道价格与免费额度反推的，改渠道价格就要重新算档位；小程序里的档位价格与发放积分是商品的一部分，改动要走审核，紧急调价没有热更新路径。

商品审核期间买不到。收费状态不是 `ENABLED` 时页面只说原因，不给购买入口；已下架与已归档只停新增购买，已有积分照常使用，不能据此推断权益失效。

账号删除之后，`nowpay_charge` 与 `nowpay_purchase` 只解除账号关联、保留原行，因为前者是支付宝一侧扣减的记录，后者用于对账。两张表现在都没有滚动清理，行数按购买点击与结算轮次增长；核对积压时需要的话，再给每日清理加一条按时间删除的语句。

每次打开购买页要调两次即刻收接口（查商品、查余额），频率受按账号与实例的限流约束，与其余购买接口共用同一套限流参数。

## 替代方案

补签 APP 支付并走未上架通道：技术上可行，但三十天窗口与试用期重叠，商店上架链接拿不到，通道到期之后仍然要改，所以不采纳。

客户端直接打开支付宝收银台网页并自建回调：回调只能证明页面跳转，不能证明到账，还得自己轮询对账；托管购买页把商品展示、支付与积分入账都交给即刻收，应用只负责查余额与核销，取舍偏向后者。

继续只提供每日免费额度：试用期需要验证付费意愿，[ADR-0065](0065-支付宝购买聊天模型额度.md) 的前提仍然成立，所以不采纳。

- 契约与生成代码：[server/api/openapi.yaml](../../server/api/openapi.yaml) 的三条购买接口与 `QuotaPurchaseOverview`、`QuotaPurchaseProduct`、`QuotaPurchaseOption`、`QuotaPurchaseLink`、`QuotaBalance`，服务端处理函数在 [server/internal/nowpay](../../server/internal/nowpay/client.go)。

- 计费口径：[ADR-0066](0066-额度按缓存命中折算.md) 的计费 token 不变，核销的只是“超出免费额度的部分”。
- 客户端：`app/lib/ui/quota_purchase_panel.dart` 打开托管购买页，旧的 SDK 通道与 `app/lib/platform/alipay_sdk.dart` 已删除。
- 产品定义与交互：[docs/00-产品定义.md](../00-产品定义.md) 第 6 节第 5 条与第 7 节的购买说明，[docs/02-产品与交互.md](../02-产品与交互.md) 的“模型额度”一节。
- 验收：真实账号买一笔最小档位，核对 `quota.query` 余额增加、一次对话之后核销成功、余额按 `Usage.Billed` 减少，步骤与数字记在提交正文里。
