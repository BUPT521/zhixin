# ADR-0080 管理后台的留存视图

## 状态

已采纳（2026-11-26，服务端同日实施）。补上 [ADR-0019](0019-留存统计用匿名上报.md) 的读取入口，公开的 `POST /v1/telemetry/active` 仍然只写不读；采集范围、保留期与匿名口径不变。

## 日期

2026-11-26

## 背景

留存统计的采集按 [ADR-0019](0019-留存统计用匿名上报.md) 从 2026-11-18 起就在运行：登录账号由鉴权中间件按请求日期写 `user_active`，未登录设备通过 `POST /v1/telemetry/active` 写 `install_active`，安装标识只保存 HMAC-SHA256，匿名数据按 180 天滚动删除。当时的判断是数据量小、管理员偶尔看一次，读取没有接口，[server/README](../../server/README.md#留存统计)写明“管理员直接查库得到留存数字”，并把每日活跃与一周、四周留存的 SQL 放在同一节。

内测 0.3.0 包定在 12 月发出，S4 与 S5 要求的一周与四周留存（[03 第 4 节](../03-团队分工与协作.md#4-成功标准)）从那时起才有真实样本。到那时再看 SQL 就有三处不方便。一是每次都要 SSH 到服务器再进 `psql`，[运维手册](../../server/运维手册.md)本身也把交互式 `psql` 列为受限操作；二是留存要把“首次出现”与“之后再次出现”两张口径对起来，`psql` 里手写窗口容易把首次当天算成回访，时区取自 `ZHIXIN_TIMEZONE` 而不是数据库默认值这一点也容易漏；三是结题材料与周报需要把数字给别人看，贴一段 SQL 结果没有表格与留存率，别人看不出哪一批的观察期还没走完。

后台此时已经有五个页签：模型来源、模型与路由、用量统计、账号管理、反馈（[ADR-0076](0076-管理后台按密钥的对账视图.md)、[ADR-0078](0078-管理后台的账号注销与额度管理.md)、[ADR-0079](0079-管理后台的反馈查看.md)）。管理令牌、接口转发、表格与空状态的写法都能复用，新增一页的成本主要在聚合查询与判定口径，不在页面框架。

## 决定

1. 新增 `GET /admin/v1/retention`，只读，管理令牌校验与其余管理接口相同。`days` 取 1 至 180、默认 30，越界返回 400 `invalid_request`；上限取 180 是因为匿名活跃只保留 180 天，再往前看只会得到零。
2. 响应给出 `timezone`、`days`、`daily` 与 `cohorts`。`daily` 覆盖区间内每一天并按自然日升序，没有活跃的日期也占一行、数字为 0；`installs` 是当天有匿名上报的安装数，`users` 是当天有鉴权请求的登录账号数，两者分开计。
3. `cohorts` 按匿名安装第一次出现的日子分组，只统计首次出现日落在区间内的安装；`returned_7d` 与 `returned_28d` 是第 7 天与第 28 天之内再次活跃的安装数，`day > first_day` 使首次当天不算回访。回访可以落在区间下界之后的任意一天，不要求回访当天也在区间内。
4. 登录账号只给每日活跃，不给队列留存。账号可以换设备、退出登录之后本机会新建一个未登录空间（[ADR-0056](0056-本机数据按账号分空间.md)），按账号编号算留存会把同一批人算成两批；这个口径还没定，报告里不给出，页面上写明原因。
5. 读取与写入分开：`retention.Reader` 只有三个聚合方法，写入路径的 `retention.Store` 与公开上报接口不变；内存实现与 PostgreSQL 实现都满足，联调时不需要数据库。聚合查询用 `sqlc` 生成，不新增表与列，也不改保留期。
6. 后台增加“留存”页签：上面是队列留存表（首次出现、新增安装、7 日与 28 日回访与留存率），下面是每日活跃表（日期倒序、匿名安装与登录账号两列），顶部可选 7、30、90、180 天。观察期没走完的批次在留存率一列显示“观察未满”，汇总行只合计观察期已满的批次，避免把最后几天的“还没来得及回来”读成流失。
7. 原来的 SQL 保留在 [server/README](../../server/README.md#留存统计)，用于后台不可用时核对；页面与 SQL 的判定口径一致，都是首次当天不算回访。

## 代价与边界

多了一个读取面。虽然只读、只走管理令牌，但拿到令牌的人可以看到每日活跃与队列留存，这与用量统计页暴露的信息同等级；管理访问继续按 [运维手册](../../server/运维手册.md) 只经 SSH 隧道，公网 `/admin/` 保持关闭。

每次请求都要全表扫描 `install_active` 与 `user_active`，两张表按 [审查 V4](../数据库结构过度设计审查.md) 没有为每日清理单独建索引，万行以下可以接受；内测规模只有百人量级，一天几十行，扫描代价可以忽略。按规模优化时要另开决定。

队列留存只看区间内第一次出现的安装，区间之前就已经出现的安装即使回访也不进队列，所以看 30 天时，前几天的队列是“已经存在的老安装”被排除后的结果，早期数字偏保守；这是有意为之，否则无法区分“新装”与“老装回访”。

报告没有账号维度，也没有导出，不能用来回答“某一批人第二天有没有回来”这类问题；要按账号分析得另做决定，且会碰到隐私边界。

页面只读，不提供删除与导出；匿名数据过期由保留期清理照常删除，后台不会延长任何一行的保存期限。

## 替代方案

继续只用 SQL 查看。没有采纳的原因是每次要上服务器、手写窗口与留存率、结论没法直接给人看；SQL 仍保留作为兜底，只是不再是唯一入口。

服务端每天把留存算好写进一张汇总表，页面只读汇总表。没有采纳的原因是 [ADR-0058](0058-表结构冻结后只做加法.md) 之后新增表要有明确收益，而当前数据量与访问频率都不构成理由，实时聚合已经够快；真到了需要按小时或按来源拆分的规模，再按表结构加列。

给登录账号也做队列留存。没有采纳的原因是口径未定，见决定第 4 条；先让匿名安装的队列留存把 S4 与 S5 的数字撑起来，账号一侧补上日活即可。

把留存接口放在公开的 `/v1/` 下，客户端自己展示。没有采纳的原因是留存是运营与结题用的数字，客户端没有展示场景，公开读取还会把活跃规模暴露给任何调用者。
