# ADR-0068 聊天积分包的档位与价格

- 状态：已采纳，待即刻收小程序按本表配置并审核发布
- 日期：2026-11-25

## 背景

[ADR-0067](0067-聊天额度改走即刻收积分包.md) 把聊天额度改由即刻收的积分包卖出，商品、收费模式、档位与价格都在「即刻收」小程序里配置，应用只显示档位名称、价格与发放积分数。商品审核发布之后应用才能卖出积分，试用期于 12 月 21 日开始，定价因此要在审核之前定下来，否则试用期内用户买不到额度。

定价的空间由三条约束决定。第一，计费单位定为一个积分等于一万个计费 token，已经卖出的积分按这个比例折算，改动比例会同时改变已有余额的价值，所以档位只能通过价格与发放积分调整。第二，每个账号每天有 320,000 个计费 token 的免费额度，按这个比例折 32 个积分，按渠道价折合约 0.064 元。第三，项目组的实际渠道价是每百万计费 token 0.2 元，是 [DeepSeek 官方价目](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)空闲时段价 1 元的 2 折；渠道对输入未命中、输入命中与输出按同一折扣计价，[ADR-0066](0066-额度按缓存命中折算.md) 的三个权重 1、1/50、4 与官方价的比例正好对应，所以每百万计费 token 的渠道成本恒为 0.2 元，与缓存命中率无关，缓存率只决定一份包能撑多少原始用量。按这个成本定价，三档折合每百万计费 token 0.60、0.5625 与 0.5333 元，是官方谷价的 6.0、5.6 与 5.3 折；毛利率 66.7%、64.4% 与 62.5%，加价倍数 3.0、2.8 与 2.7 倍。

试用期需要回答两个问题：用户愿不愿意为模型额度付钱，以及在哪一档上付钱。三档能让用户的选择本身反映价格弹性，档位再多会增加小程序配置与审核的次数，档位再少只能看出买与不买。

## 决定

小程序配置三档一次性积分包，比例定为一个积分一万个计费 token，价格与发放积分如下。

| 档位 | 价格 | 发放积分 | 折合计费 token | 满额度天数 | 毛利率 | 相对谷价 | 相对萤火 |
|---|---|---|---|---|---|---|---|
| 萤火 | 6 元 | 1,000 | 1,000 万 | 31 天 | 66.7% | 6.0 折 | 基准 |
| 灯火 | 18 元 | 3,200 | 3,200 万 | 100 天 | 64.4% | 5.6 折 | 9.4 折 |
| 星河 | 48 元 | 9,000 | 9,000 万 | 281 天 | 62.5% | 5.3 折 | 8.9 折 |

表中的满额度天数指这些积分按每天 32 分计算能用多少天，也就是在免费额度之外再买一份的量。三档的积分单价从 0.0060 元降到 0.0053 元，折合每百万计费 token 0.60、0.5625 与 0.5333 元；按渠道价 0.2 元/百万计算，毛利率 66.7%、64.4% 与 62.5%，加价倍数 3.0、2.8 与 2.7，售价是官方谷价的 6.0、5.6 与 5.3 折。以萤火为基准，灯火是 9.4 折、星河是 8.9 折，把一次购买拆成几次买小档会贵一点，按用量选一档即可。

加价倍数的下限由三部分构成：支付渠道的手续费、核销漏扣与对账的人工、渠道价调整的风险。核销在回答交付之后进行，流水停在 `pending` 或 `processing` 时这部分积分没有扣减，等于服务端替用户承担了成本，按 3 倍左右的加价留出的余量覆盖这类损耗，见 ADR-0067。倍数按项目组的渠道价计算，官方谷价 1 元/百万只作为售价的对照。

三档按光的范围命名：萤火是手里的一点光，灯火是一室的光，星河是满天。名字不带期限，因为积分跨日保留、不会失效，按“三天包”“月包”命名会让用户以为买到的是一段时间的会员。

换算分三层。上游报告的是原始 token，计费时按权重折算：未命中缓存的输入记 1，命中缓存的输入记 1/50，输出记 4，先按五十分之一累加再四舍五入，见 ADR-0066。折算之后的计费 token 除以一万就是积分，核销时按当天累计向上取整，再减去当天已申请的积分，只补差额，一天最多多记一个积分。免费额度按计费 token 计，每天 320,000 个，也就是 32 个积分。三种用量各自折成一个积分所需的原始 token 如下。

| 一个积分（10,000 计费 token） | 对应的原始 token |
|---|---|
| 未命中缓存的输入 | 10,000 |
| 命中缓存的输入 | 500,000 |
| 输出 | 2,500 |

例如一轮讨论发出 24,000 个命中缓存的输入与 6,000 个未命中缓存的输入，模型输出 1,500 个 token，计费量是 6,000 + 24,000 ÷ 50 + 1,500 × 4 = 12,480 个计费 token，约 1.2 个积分，这一轮结算时按当天累计记 2 个积分。下一轮同样的用量之后当天累计 24,960 个计费 token，应记 3 个积分，核销只补 1 个差额，不会像逐轮取整那样每轮各记两个。三种用量按同一个口径扣减免费额度与购买积分。嵌入按原始 token 一比一记，不参与这套折算，也不能用购买的积分支付。

免费额度与积分的优先级不变：先扣当天免费额度，超出部分才折成积分核销。核销比例、流水与补查机制都不因本表调整。前台把当天用量与免费额度按同一比例折成积分展示，用量向上取整，与核销同一方向；免费额度向下取整，因为额度只有凑满一整份积分才算数，向上取整会在额度不是比例整数倍时出现“已用 3 分 / 免费 3 分”同时又“已扣 1 分”。`GET /v1/llm/quota` 与 `QuotaPurchaseOverview` 都返回 `tokens_per_point`，客户端不写死比例。积分只用于聊天，嵌入额度另有一份每日额度，购买积分不改变嵌入的用量与上限。

## 代价与边界

价格与发放积分是商品配置，改价要走小程序审核，审核期间与发布之前用户看到的仍是旧档位，紧急调价没有热更新路径，这一点 ADR-0067 已经记过。已售积分的面值不随改价变化，改价不补发也不回收。

加价倍数按渠道价 0.2 元/百万计费 token 算出，官方谷价 1 元/百万作为对照。渠道价随官方价调整：官方高峰时段价格翻倍时，若渠道仍按 2 折计价，每百万成本变成 0.4 元，三档的倍数降到 1.5、1.4 与 1.3 倍，毛利率降到约 33.3%、28.9% 与 25.0%。后台换成 deepseek-v4-pro 时，输入命中、输入未命中与输出的官方价不再等值，渠道三项的折扣比例也可能不同，每百万计费 token 的成本按请求构成变化，命中缓存占比低的请求成本可能超过售价；换模型之前先按新单价重算档位。把单价挂在路由上、按成本折算的改造与过渡步骤见 [ADR-0072](0072-计费按路由单价与成本折算.md)（提议），改造完成之前档位表只在 flash 渠道价上准确。

免费额度按每天 320,000 个计费 token 发出，折 32 个积分，按渠道价成本约 0.064 元/天、每月 1.92 元。如果试用中多数人在免费额度内就够用，积分卖不出去的原因在额度而不在价格，调价之前先看 `llm_usage` 的用量分布。

积分核销之后不能撤销，应用里也没有退款入口，退款按即刻收与支付宝的规则处理。用户选错档位时，只能在现有余额上继续使用或者另行协商。

## 替代方案

四档，在最低档下面加一个 1 元体验档。1 元的价格最低，但 100 个积分约合三天的免费额度，和最低档 1,000 分差十倍，用户很难判断买到了什么，而且每多一个档位就多一次审核与配置，试用期先用三档观察转化。

两档，6 元与 30 元，积分按同一比例发放。决策更快，但只能看到低价与中价两个点，区分不了愿意付一点的用户与愿意长期使用的用户。

月付订阅。即刻收当前按积分包配置，连续订阅要接时长包或者每日发放，服务端还要增加按日发放与到期回收的路径；ADR-0067 已计划后续提供，本轮不做。

把 `ZHIXIN_TOKENS_PER_POINT` 调小（例如一个积分五千个计费 token）来等价于涨价。已售积分会随之贬值，用户手里的余额与定价口径一起变化，改价走小程序更直接。

按官方谷价 1 元/百万定价：6 元只能发 600 万分、600 个积分，比现在的 1,000 分少四成；试用期要看用户愿不愿意为额度付钱，把价格定在谷价附近会把大部分用户挡在外面，所以不采纳。

## 影响

- 产品定义：[00 第 7 章](../00-产品定义.md#7-边界)的购买说明写入三档的名称、价格、积分、折算比例与满额度天数，其他文档引用那一处，不另造一份。
- 交互：[02 第 3.16 节](../02-产品与交互.md#316-账号与云同步)的“模型额度”一节说明购买卡片列出档位名称、价格、积分与换算，价格不写进页面。
- 契约与客户端：[server/api/openapi.yaml](../../server/api/openapi.yaml) 的 `QuotaPurchaseOverview` 与 `LLMQuota` 都带 `tokens_per_point`，取值来自 `ZHIXIN_TOKENS_PER_POINT`，客户端用它把积分换算成计费 token、天数，以及把当天用量换算成积分。
- 服务端与运维：[server/README](../../server/README.md#即刻收收款)的“即刻收收款”一节与[运维手册](../../server/运维手册.md#411-即刻收积分包的上线与回滚)第 4.11 节补上小程序档位的配置与核对步骤；`ZHIXIN_TOKENS_PER_POINT` 的代码默认值已改为 `10000`，与部署值一致，前台按接口返回的 `tokens_per_point` 展示。
- 路线图：[04 第 5 节](../04-长期路线图.md#5-决定)的 D4 条目补一条链接。
- 验收：小程序审核发布之后，用已验证的账号在应用内核对三档的名称、价格、积分与换算，买最小档核对余额增加与一次核销，步骤同 ADR-0067。
