# ADR-0030 服务端不建检索索引

## 状态

已采纳（决定第 1 至 3 条已实施，决定第 4、5 条未开始）。2026-11-19 决定，服务端与客户端的缓存接入同日完成。检索索引由客户端维护，服务端只承担嵌入与按账号的向量缓存。[ADR-0027](0027-服务端承担嵌入与检索.md) 决定第 3、5 条由本条取代；[ADR-0024](0024-关键词检索并入zvec.md) 决定第 1、2、3 条，以及第 5、7 条中关于 `MultiQuery` 过滤与整份重建的部分，由本条取代。向量缓存、关键词与向量拆分、提交日志驱动的刷新分步实施，第一步的清单见实施一节；截至 2026-11-19，服务端的查找接口、缓存表、写入与上限淘汰、清除与模型变更时的清理都已实现，客户端清单第 1 至 3 条（哈希与 FP16 解码、批量查找、批次去重）也已接入（见 [server/README](../../server/README.md#模型代理) 与 [app/README](../../app/README.md#数据)），第 4 至 8 条（提交日志驱动的增量刷新、拆分关键词与向量 collection、应用层融合）尚未开始，第二步与第三步的清单在实施时另补，排期另定，见 [04 M1](../04-长期路线图.md#m1-验收与内测包)。

## 日期

2026-11-19

## 背景

语义索引现在全部由客户端维护：zvec 的 collection 存在应用私有目录里，检索时先在索引里取候选，再回业务库核对范围与来源版本（[ADR-0022](0022-语义索引改用zvec.md)、[ADR-0024](0024-关键词检索并入zvec.md)、[ADR-0026](0026-记忆召回改用zvec全文索引.md)）。服务端有账号、整库备份、按提交序列的增量同步与模型代理；同步服务原样保存每次提交的 `before`、`after` 行，不解析业务表，嵌入代理按路由拆批并发、按原顺序合并（[ADR-0029](0029-模型来源路由与嵌入代理.md)）。[ADR-0027](0027-服务端承担嵌入与检索.md) 把检索索引的权威位置留成待定：决定第 3 条写两条路径并存，第 5 条写服务端索引、客户端索引或两边各一份都可以。

ADR-0027 要解决的是重复嵌入造成的等待与费用：全量重建二十万个片段要数小时，换设备要重新计算，费用落在用户一侧。这个问题不需要服务端检索也能解决。服务端建索引有三项代价。

第一项是内存。第一套实例只有 2 vCPU 与 1682 MB 内存（ADR-0029）。二十万个片段按 1024 维 FP32 计算，向量本体约 800 MB，按账号常驻索引时两个用户合计就会超出实例内存；即使只把部分账号放进内存，查询与写入的余量也很小。

第二项是业务结构。索引需要知道 `material_page`、`message`、`attempt` 三张表的字段与来源键规则，还要复制一份 `semanticChunks` 的切片规则；这些结构在 1.0.0 之前每次发版都可能变化（[ADR-0001](0001-开发阶段不向下兼容.md)、[ADR-0017](0017-表结构变化仍清空数据.md)），客户端与服务端因此要锁步发版。同步日志保持原样转发，是客户端与服务端之间最简单的一层约定，建索引会破坏它。

第三项是检索仍需回到本机核对。[00 第 8 章](../00-产品定义.md#8-检索与引用)要求更正、改归属、撤销、恢复或清空之后旧命中立即退出使用，候选要按当前来源版本与检索范围核对，范围来自本机业务库，服务端没有这份数据。服务端检索于是变成“取回候选、回本机核对”，多一次往返，断网时还要退回本地，而本机索引本来就必须存在。

所以服务端只承担嵌入、不承担检索，重复嵌入由向量缓存消掉。缓存按账号保存已经算过的向量，换机、索引损坏后的重建、模型在 A 与 B 之间来回切换时先取回缓存，只补算没有的片段。

## 决定

1. 检索索引由客户端维护，服务端不建索引。切片、范围规则、融合与记忆召回都留在客户端，服务端与客户端在检索上的约定只有“模型与文本到向量”这一层；服务端的向量缓存属于派生数据，可以从业务库与嵌入服务重建，不进入数据包与整库备份。

2. 索引刷新先查缓存，再补算未命中的片段。嵌入来源是知新服务时，客户端把一批文本的 SHA-256 发给 `POST /v1/llm/embeddings/lookup`，服务端返回这个账号与这个模型下已有的向量；没有命中的文本仍走 `/v1/llm/embeddings`，嵌入成功之后由服务端按原文自行计算哈希并写入缓存，客户端不能指定某个哈希对应哪个向量。

3. 缓存按账号隔离。只给已开始同步的账号写入：客户端在自动同步开启时，随索引刷新发起的批量嵌入请求带上 `X-Zhixin-Embedding-Cache: 1`，服务端只在这时写缓存，未登录、同步关闭与自填 key 直连的用户不留下派生数据；缓存随 `DELETE /v1/cloud` 与删除账号一起清除，原文是否离开本机仍按用户选择的可发送范围决定。缓存与对外模型名绑定，同名模型必须保持同一个向量空间。

4. 关键词与向量拆成两个 collection。文本 collection 的 schema 固定，只存正文、来源键、来源版本、片段号与预过滤字段，建立全文索引，提交之后不需要等嵌入即可更新；向量 collection 按嵌入模型键与文本处理版本分目录，只存向量、来源键、片段号、来源版本、文本哈希与预过滤字段，不重复存正文。两路结果由应用层按名次倒数相加（平滑常数 60）融合，再交给 `fuseSearch` 按记录聚合，字面命中仍然置顶；3 秒静默期沿用，文本 collection 不再等嵌入。记忆召回已经有单独的纯文本 collection（[ADR-0026](0026-记忆召回改用zvec全文索引.md)），不受这次拆分影响。

5. 索引刷新由提交日志驱动。两个 collection 的状态各记录已处理的提交编号与数据代次；有净变化的提交之后，只读该提交之后的 `revision_change`，按改到的行解析来源键，只处理这些来源。数据代次变化、已处理的提交被历史裁剪、可发送范围变化或索引重建之后，退回全量扫描；片段按文本哈希与本机向量比对，没有变化的片段沿用原向量，变化的片段再查缓存，改一页材料只重算真正变化的片段。

## 实施方案

本节记录第一步（向量缓存与查找接口）的接口与服务端、客户端两份清单。服务端清单已按此实施（2026-11-19），用例在内存实现与本地 PostgreSQL 17 上通过；客户端清单第 1 至 3 条同日实施，哈希、FP16 解码、查找与批次去重由单元测试覆盖命中、未命中、旧服务端与来源不可用，换机重建的耗时与流量、拆分前后的排序对照要等拆分实施之后补做。第二步与第三步的细节写在决定第 4、5 条里，实施时另补清单。服务端与客户端可以分别开发：服务端先提供查找接口与缓存写入，旧版客户端不调用查找接口，行为不变；客户端在接口可用之后接入，遇到旧版服务端时退回现有的批量嵌入。

### 1. 查找接口

请求与响应都用 JSON，路径是 `/v1/llm/embeddings/lookup`，鉴权、未验证邮箱、并发上限与 `POST /v1/llm/embeddings` 相同。

```json
{
  "model": "bge-m3",
  "hashes": ["9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08"]
}
```

```json
{
  "model": "bge-m3",
  "dimensions": 1024,
  "vectors": [
    {
      "hash": "9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08",
      "embedding": "AAAAgD8AAIA/..."
    }
  ]
}
```

`hashes` 是片段文本按 UTF-8 字节计算的 SHA-256，小写十六进制；客户端与服务端对同一段文本使用同一口径，切片时的规范化只在客户端做一次，两边不再额外处理。单次最多 256 条，与 `ZHIXIN_LLM_EMBEDDING_MAX_INPUTS` 一致。响应只含命中的条目，顺序与请求无关；`dimensions` 取模型配置，模型没有配置维度时取命中行的维度，全部未命中时省略；`embedding` 是小端序 FP16 的 base64，客户端解码之后按现有方式归一化。格式不对、条数超限、模型未知或不是嵌入模型时按嵌入接口的现有错误返回；没有命中不是错误。查找不消耗额度，不写 `llm_usage`；访问日志与嵌入接口一样只记录路由、状态与字节数，不记录请求体。

缓存写在一张按账号隔离的表里，键是账号、对外模型名与文本哈希。写入发生在嵌入成功之后：服务端按每条输入计算哈希，转成 FP16，`ON CONFLICT DO NOTHING` 写入。请求头带 `X-Zhixin-Embedding-Cache: 1` 时才写，这个头由客户端在自动同步开启、且这一次是索引刷新时加上，检索查询的嵌入不带；服务端不根据提交序列推断，关闭同步之后缓存不再新增，已有的随下一次清除云端数据删除。每账号上限由 `ZHIXIN_LLM_EMBEDDING_CACHE_BYTES` 控制，默认 1 GiB，写入之后按 `last_used_at` 删除最久未用的行；命中时按批更新一次 `last_used_at`。

### 4. 验收

- 在换机后的空库上重建二十万片段的索引，只下载缓存并补算未命中的片段；记录耗时与流量，作为内测前的数字。
- 客户端遇到旧服务端（404）、网络失败、部分命中与全部未命中四种情况，索引结果与现在的批量嵌入一致；前三种与来源不可用已由单元测试覆盖，真机复测随拆分一起做。
- 用缓存向量与重新嵌入的向量分别检索，前 6 条排序一致或差异可解释，用陈英硕的评测集对照一次并写入验收记录。
- 没有开启同步、没有登录与自填 key 直连三种情况，服务端不留缓存，索引刷新与现在一致。

## 代价与边界

缓存占磁盘与出口流量。FP16 下每个片段约 2 KB，二十万片段约 400 MB；1 GiB 是每账号上限的初值，内测按实际用量调整，磁盘与出口流量要监控。同一段公共材料在不同账号下各存一份，这是按账号隔离的代价；没有开启同步的用户换机或重建仍要重新嵌入，这是隐私边界的代价。统计流量时注意，一次完整重建下载的是向量，不是原文。

向量可以由嵌入反推出大致内容，缓存属于派生数据。它只对已同步账号写入，随清除云端数据与删除账号删除，访问日志不记录请求体与哈希；缓存按账号隔离，避免有人用哈希探测另一个账号是否存过某段文本。

命中率依赖切片与文本处理版本。`text_version` 改变之后旧行不再命中，靠上限逐步淘汰；服务端不知道版本，缓存键只有模型与文本哈希。同名模型指向不同部署或改变维度时，旧向量会混进新索引，所以换部署要换对外模型名，改维度要清掉该模型的缓存，这条约束沿用 ADR-0029。

FP16 的精度损失对余弦排序的影响很小，但向量不再逐位相同，测试不做精确比较，验收时按评测集确认。未命中时先查找再嵌入，多一次往返；命中时省掉嵌入与计费。查询向量不走缓存，检索的延迟不变。

拆成两个 collection 之后，打开两个句柄、维护两个目录、发起两次查询，应用层融合的排序与引擎内 RRF 不完全相同，要按评测集复核。换来的收益是文本 schema 不再随嵌入配置变化，关键词检索不必等嵌入，两个 collection 的故障也不再互相牵连；文本 collection 不存向量，索引占用的内存下降。

提交日志驱动减少了全量扫描，代价是 `revision_change` 会随历史裁剪而删除。已处理的提交被裁掉、可发送范围变化或者索引重建之后，仍要退回全量扫描；变更行到来源键的映射要覆盖三张表与删除，漏掉一种来源就会漏更新，需要用例固定。单飞期间到达的新提交由刷新结束时的补齐覆盖。

服务端检索仍然不做。出现网页端或其他没有本机库的客户端、跨用户检索公共教材、手机端确实跑不动 Flat 检索这三种需求之一时，重新评估检索索引的位置；到那一步也建议客户端推送一份索引文档流（片段文本、来源键、过滤字段），由服务端建立索引，服务端仍然不认识业务表结构。

## 替代方案

- 服务端建索引，客户端只做缓存。这是 ADR-0027 第 3、5 条的原方案。没有采纳的原因是内存放不下按账号常驻的索引、服务端要复制业务结构与切片规则、检索仍要回本机核对版本与范围；它适合的三种需求不在 1.0.0 之内，条件写在代价与边界里。
- 保持一个 collection，关键词与向量继续在引擎内融合。这是 ADR-0024 的现状。没有采纳的原因是 schema 跟着嵌入配置变、关键词继承嵌入的滞后、索引损坏时两路一起不可用；拆开的融合代码只有二三十行，预过滤渲染两边共用。
- 向量缓存放对象存储，按模型打包。没有采纳为第一版的原因是查找按片段随机读，对象存储要为每一批拼接多次请求，延迟与代码量都高于 PostgreSQL 的一行一次查询；缓存超过磁盘预算时可以作为冷层再加。
- 保持现状，只做客户端批处理。没有采纳的原因是换机、重建与模型切换仍然重复计费，ADR-0027 当初要解决的等待与费用没有变化。
- 服务端解析同步日志建索引。没有采纳的原因是服务端要理解业务表与切片规则，与现在的原样转发相冲突；确实需要服务端检索时，改由客户端推送索引文档流。
