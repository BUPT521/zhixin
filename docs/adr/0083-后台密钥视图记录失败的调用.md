# ADR-0083 后台密钥视图记录失败的调用

## 状态

已采纳（2026-11-26，服务端同日实施）。补充 [ADR-0076](0076-管理后台按密钥的对账视图.md) 的读取范围，不改变 [ADR-0070](0070-额度预留与失败结算口径.md) “失败按 0 结算”的结论。

## 日期

2026-11-26

## 背景

失败按 [ADR-0070](0070-额度预留与失败结算口径.md) 记 0，这条口径是为了不让一次 502 扣掉二十多万 token。它有一个副作用：按 0 结算的尝试在 `llm_usage` 里只留下 `tokens = 0` 与 `reserved_tokens = 0`，而 [ADR-0076](0076-管理后台按密钥的对账视图.md) 的视图按 token 与预留组织，两列都是 0 的行与“这把密钥今天没有用过”完全一样。

2026-11-26 用一道接入密钥接第三方工具时，连续几次请求都在进入模型之前被拒。后台“按密钥计费”上显示“所选范围内没有密钥调用记录”，量页也看不到这些尝试，排查只能翻服务日志。用户当时的结论是“key 调用失败，并不会在后台统计界面上留下记录”，这与事实一致：记录确实没有留下来。

路由维度的 `/admin/v1/usage` 不受影响，它的 `attempts` 与未成功次数在按 0 结算时照常累加。缺的只有按密钥这一层，而这个视图正是判断“一把密钥是不是坏了、是不是被人拿去乱用”时最先看的地方。

## 决定

1. `llm_usage` 增加 `attempts` 与 `failures` 两列，按账号、自然日、用途与密钥逐行累加。`attempts` 是尝试次数，`failures` 是其中失败、按 0 结算的次数。结算时与 token 两列在同一个事务、同一条 upsert 里写入，因此失败的那一次与成功的那一次不会只写一半。

2. 这两列只用于展示。额度判定、预留、结算、核销与实例账本仍然只看 `tokens` 与 `reserved_tokens`，`UsedTokens` 与 `SettledTokens` 的语句不改。API 的额度视图、客户端看到的剩余额度与积分核销都不因为这次改表而改变。

3. `/admin/v1/key-usage` 的每把密钥与每个自然日都多返回 `attempts` 与 `failures`，后台“按密钥计费”表增加“尝试”与“未成功”两列。只含尝试、没有 token 与预留的行也返回：那正是一次失败的调用，过滤掉它之后这把密钥又会与没有用过的密钥一样。

4. 内存实现同步：尝试与失败次数单独记一份，`KeyUsage` 不再按“token 与预留都为 0”丢行。内存实现下这把密钥的名字仍然为空，页面显示“未命名密钥”，与访问令牌那一行靠前缀区分。

5. 这次改表是纯新增，按 [ADR-0057](0057-服务端改表清空重建.md) 的先例用增量语句，不清空重建：两条 `ALTER TABLE llm_usage ADD COLUMN IF NOT EXISTS ... BIGINT NOT NULL DEFAULT 0`，之后去掉默认值使列定义与 `schema.sql` 一致，语句写进[运维手册](../../server/运维手册.md)的[§4.11](../../server/运维手册.md#411-即刻收积分包的上线与回滚)。新列从部署之后开始计数，此前的行保持 0。

## 代价与边界

部署之前发生的失败调用补不回来。列是新增的，之前那些 `tokens = 0` 的行没有尝试记录，视图里仍然看不到；要看更早的数据只能翻服务日志。

尝试与失败按“结算一次”记一次，不是按“发出一次 HTTP 请求”记一次。一次请求在多个来源之间换路时，每一次尝试各自结算一次，所以换路三次的一次请求记三次尝试；这与路由用量统计的口径一致，但和用户理解的“调用了多少次”不是同一个数。

失败按 `attemptResult.success` 判定，客户端取消与本轮预算用完也记进失败。这两类在路由统计里另外记 `canceled_attempts`，密钥视图不再拆开：密钥视角只需要知道“调用没有成功”，再细分要增加更多的列，超出这次修复的范围。

两列是纯粹的附加信息，没有另外的保留期。`llm_usage` 本身按自然日保留，删号时随外键级联删除；清理规则不变。

## 替代方案

只让 `KeyUsage` 不再过滤零行，不加列。没有采纳的原因是零行在页面上显示为 0 个 token，看不出一把密钥失败了一百次还是一次，也分不清“今天用过但全部失败”和“今天根本没用过”。

另建一张按密钥的调用记录表，逐条记状态码与时间。没有采纳的原因是它要新增表、停服与长期维护一份每次调用都写的明细，而当前只需要回答“这把密钥有没有在失败”；需要逐条明细时再另开一条决定，按 [ADR-0063](0063-模型代理接入密钥.md) 保留期的口径设计。

把失败也按预留量写进 `tokens`。没有采纳的原因是这会推翻 [ADR-0070](0070-额度预留与失败结算口径.md) 的核心取舍，失败的调用重新开始扣额度，与前者要解决的问题正好相反。
