# 知新 · 架构决策记录

> 本文规定架构决策记录（ADR）的用途、位置、命名与状态，并索引已经采纳的条目。产品定义、数据字段、页面与分工的现行口径仍以 [00](../00-产品定义.md)、[01](../01-ER数据模型.md)、[02](../02-产品与交互.md) 与 [03](../03-团队分工与协作.md) 为准；ADR 回答的是“为什么这样定、代价是什么”，不复述这些文档的表格、字段与页面清单。

---

## 1. 什么时候写一条

一条 ADR 记录一个跨模块、难以回退、后来的人需要知道理由的决定。判断时看三条，满足其中一条就写：

1. 决定同时影响两个以上层面，比如数据结构、运行时、界面、构建或发版流程。
2. 决定要改回来需要重写数据、重做接口或者重新组织文档。
3. 后来的人会问“为什么不用另一种做法”，而答案不在 00–03 的现行口径里。

单一领域的小决定仍然写进对应文档的一句话或提交正文，不单独建 ADR。ADR 的数量增加以后，索引会变长，查找成本也会超过它保存的信息；只有真正需要保留理由的决定才进这个目录。

## 2. 位置与命名

- 目录固定为 `docs/adr/`，不放到其他位置，也不在 `app/` 下另建一份。
- 文件名写作 `NNNN-标题.md`。`NNNN` 是四位编号，从 `0001` 起连续递增，编号只增不减、不复用；标题用中文短名词短语，能够独立说明决定内容，例如 `0003-最低系统版本与打包架构.md`。
- 文件第一行写作 `# ADR-NNNN 标题`，与文件名一致。正文按“状态、日期、背景、决定、代价与边界、替代方案、影响”七节排列，新条目可以复制 [模板](template.md)。
- 引用时写 `ADR-NNNN` 并附相对链接；代码注释只写编号和一句话，详细内容回到本目录，不在代码里重复背景与代价。
- 本目录按 `0001` 起连续编号。代码或文档里出现的编号必须能在本目录找到对应文件。

## 3. 状态

| 状态 | 含义 |
|---|---|
| 提议 | 已经写成文字，尚未在实现与文档里生效 |
| 已采纳 | 已经按这条决定执行，相关代码与文档同步更新 |
| 已取代 | 结论被后来的 ADR 替代，本条保留原文 |
| 已废弃 | 不再执行，也没有替代条目 |

已经采纳的 ADR 不改结论，也不删原文；要改就新开一条，并在新旧两条的状态里互相注明编号。旧条目的背景与代价保持当时的样子，后来的人才能看出判断是在什么条件下作出的。

## 4. 与其他文档的关系

- 00–03 是现行口径的唯一真相，ADR 说明取舍与代价。字段、页面与分工的细节写到 00–03，ADR 只链接到对应章节。
- 一条 ADR 生效时，唯一真相、引用与 ADR 放进同一个 push；相关文档在对应位置留一句链接，不整段转载，也不另造数字。
- ADR 与 00–03 冲突时，先按 00–03 的现行口径执行，再修正 ADR 或者把它标成“已取代”。不允许两份文件长期各说一套。
