# ADR-0086 结算失败的预留退回

- 状态：已采纳（2026-11-27，服务端同日实施）；`llm_usage` 之外新增 `llm_settlement_failure` 表，补充 [ADR-0071](0071-核销只读已结算用量与额度用完的原因.md) 的预留与结算口径
- 日期：2026-11-27

## 背景

额度按“先预留、再结算”两步扣：转发之前按估算量把计费 token 记进 `llm_usage.reserved_tokens`，回答交付之后按来源报告的用量结算，把预留扣掉、把实际用量记进 `tokens`。预留这一列只有结算会减，而结算在 `pg.(*Store).Settle` 的一个事务里完成，事务失败时整体回滚，`reserved_tokens` 原样留着。

结算失败之后没有下一个人处理这笔预留。`llmproxy.(*Proxy).settle` 原来只把错误记一条日志就返回，既没有退预留，也没有留下待处理的记录。结算在等当天的 advisory lock 时碰到请求时限，或者数据库短暂不可用，这一次的事务就失败；那笔预留留到跨日，当天剩下的额度被它占着。`GET /v1/llm/quota` 只读已结算的 `tokens`（[ADR-0071](0071-核销只读已结算用量与额度用完的原因.md)、[ADR-0084](0084-聊天与嵌入共用积分.md)），所以用户看到的是“没用多少却一直 429”，重试也不会恢复。进程在结算之前退出有同样的问题：预留已经写进库，没有人在之后退它。

## 决定

`Proxy.settle` 返回错误，调用方把请求编号、账号、自然日、用途、密钥编号、这次预留与实际用量和错误写进一条 `settle llm usage` 日志。错误不再在半路丢掉，日志里的用量可以人工核对。

结算失败之后的处置放在存储实现里，因为只有它知道事务回滚到了哪一步。`pg.(*Store).Settle` 在事务失败时写一条 `llm_settlement_failure` 记录，并用脱离请求时限的新上下文立刻补退一次：在同一个事务里把这笔预留减掉、把记录删掉。记录本身写不进去时只记一条 `record the failed settlement` 错误日志。

补退还有两条路径。每次 `Reserve` 先按账号补退一次，再判断额度，所以用户的下一次请求看到的是退回之后的额度，不会因为上一次结算失败继续收到 429。进程里每十分钟做一次全局补查，每次处理五十条创建超过一分钟的记录，兜住不再发请求的账号与进程重启之后没有人处理的记录。

补退只退预留，不补记那一次的实际用量。`Settle` 返回错误时事务可能已经提交，提交阶段的网络错误无法判断结果；重记一次会变成重复扣减，少记一次只是这一次的用量没有算进去。记录里的 `billed_tokens` 保留这次没有记进去的量，日志与人工核对都用它。

每天再清一次两天以前的自然日上的在途预留（`ClearReservationsBefore`）。一次请求活不过两天，这些预留既没有结算也没有待补偿记录（进程在结算之前退出，或者记录也没写进去），留着只会让账上一直挂着一份占用量，管理后台的按密钥视图也会显示凭空存在的在途预留。

`llm_settlement_failure` 只在有待补偿记录时有行，补退成功立即删除，正常时是空的，两个索引也随之为空。服务启动时检查这张表：缺表直接退出，由自动部署回滚到上一份可执行文件。每次预留都会先补退一次，缺表虽然不影响放行，却会让每一次请求都记一条错误日志。

## 代价与边界

结算失败那一次的实际用量不再计费。用户拿到的回答是完整的，这一次的用量没有记进 `tokens`，金额很小，却确实是一次漏记；把它补记的风险是重复扣减，两者之间选择少扣。

补退可能重复减一次预留。只有“事务已经提交、返回错误”这一种情况会让补退再减一次，`SettleTokens` 把结果限制在 0 以上，最多把同一行上其它在途预留提前减掉，额度在那些请求结算之后回到正确值。要彻底消除这个窗口，需要给每一笔预留单独一行、按行结算，见替代方案。

待补偿记录与补退都依赖数据库。数据库整体不可用时前一步也失败，这笔预留留到当天结束；它占的是当天额度，次日按新的自然日重新计算，清理语句保证两天以前的账不会一直挂着。清理只改 `llm_usage` 的两列预留，不调整 `llm_instance_usage`：实例账本按自然日各记各的，那一天已经结束。

## 替代方案

失败之后重试整笔结算。没有采纳：提交阶段的错误可能意味着事务已经写进去了，重试会把同一次用量记两遍，重复扣减比少记一次更难解释，也与 [ADR-0073](0073-余额副本的快照、刷新与放行原因.md) 对结果未知的核销流水“不换号重扣”的处理一致。

把结算的超时调长。没有采纳：调长只能减少失败次数，不能保证预留最后一定被退回；数据库不可用时超时再长也会失败。

每笔预留单独一行、按行结算与退预留。没有采纳：`llm_usage` 按账号、自然日、用途与密钥汇总，改成逐笔要同时改额度判定、展示、管理后台对账与备份口径，代价与这次要解决的问题不成比例。按行汇总的重复退风险只出现在上面那一种罕见情况，暂时接受。

失败只记日志、由管理员连库修正。没有采纳：用户要等到管理员看见日志并处理，当天的额度已经过去了，而这正是这条 ADR 要消除的现象。

## 影响

- 表结构：[schema.sql](../../server/internal/store/schema.sql) 增加 `llm_settlement_failure` 与两个索引；已有实例按[运维手册](../../server/运维手册.md#411-即刻收积分包的上线与回滚)的增量语句建表，启动时检查这张表。
- 查询：[queries/settlement.sql](../../server/internal/store/queries/settlement.sql) 新增写记录、按账号取、按时间取、删除记录与清理过期预留五条查询；生成代码在 [db/settlement.sql.go](../../server/internal/store/db/settlement.sql.go)。
- 存储：[pg/quota.go](../../server/internal/store/pg/quota.go) 把 `Settle` 拆成 `Settle` 与 `settleTx`，新增 `recordSettlementFailure`、`retrySettlements`、`SweepSettlementFailures` 与 `ClearReservationsBefore`，`Reserve` 在判断额度之前先补退。
- 代理：[metering.go](../../server/internal/llmproxy/metering.go) 的 `settle` 返回错误、由调用方记日志；[settlement.go](../../server/internal/llmproxy/settlement.go) 新增补查与清理循环，[main.go](../../server/cmd/zhixin-api/main.go) 启动它。
- 文档：[server/README.md](../../server/README.md) 的表结构与额度一节、[运维手册](../../server/运维手册.md) 的增量语句与核对语句同步更新。
- 验收：PostgreSQL 用例 `TestPostgresQuotaSettleFailureIsCompensated` 核对结算失败之后的当场补退与下一次预留之前的补退，`TestPostgresSettlementFailureSweepAndStaleReservations` 核对全局补查与过期清理；`TestSettleReturnsTheQuotaError` 核对代理把错误交回调用方。
