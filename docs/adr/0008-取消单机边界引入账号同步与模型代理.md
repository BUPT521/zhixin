# ADR-0008 取消单机边界，引入账号、云同步与模型代理

## 状态

已采纳。服务端的技术框架见 [ADR-0009](0009-API后端采用Go与分层框架.md)。

## 日期

2026-11-14

## 背景

此前 [00 第 6、7 章](../00-产品定义.md#6-原则与优先级)把知新定为单机应用：不做账号、多用户与跨设备同步，换机只靠导出与恢复；模型服务由用户自填 key 并自付额度，应用不做平台代管。这个边界在只有团队成员试用时成立，因为四个人都会配置 key，也愿意手动导出备份。

内测定在 2027.01，公测按 100 人计划，试用者主要是不熟悉模型服务的大学生。[03 第 5 节](../03-团队分工与协作.md#5-风险)已经把“用户不愿配置 key，首次使用就流失”列为风险，原先的处置是引导与连接测试，不改为平台代管；换手机或重装应用时，没有手动导出的用户会丢失全部记录。团队还需要在内测期间观察真实使用情况，而单机架构下只能等用户主动导出数据包。自建 Sentry（[ADR-0005](0005-崩溃与诊断上报改用自建sentry.md)）已经让项目组维护一台服务器，增加一个 API 服务不再是从零开始的运维负担。

## 决定

1. 取消“数据在本机、不做云同步”的边界，增加一个由项目组自建的 API 服务。第一期承担三项职责，即账号与登录、学习数据的云同步与备份、模型请求代理。服务端检索、嵌入与材料解析不进入第一期。
2. 本地优先。本机 SQLite 仍是学习数据的主副本，服务端保存的是同一份提交序列的副本与整库备份。[00 第 6 章](../00-产品定义.md#6-原则与优先级)的三条硬约束保持不变：AI 写入仍形成本机提交并可撤销，记录动作的时长要求不变，模型不可用、未登录或断网时已有记录仍可查看与记录，本地兜底照常给出下一步。
3. 账号是可选项。不登录时应用与此前一样完全在本机运行；登录之后才开启同步、备份与模型代理。一个账号只对应一个人的学习数据，不做多人共享、班级空间与协作编辑，因此“按单用户做定制”仍然成立，变化的是同一个人可以在多台设备上使用。
4. 模型代理作为默认之外的另一条接入方式。登录用户可以选择“知新服务”作为模型来源，请求经服务端转发，服务端持有提供方的 key，并按账号限定每日额度；用户仍可以在设置页填写自己的 key 直连提供方，此时请求不经过服务端。项目仍不收费，不设订阅与内购，代理的模型费用由捐赠与学院经费承担，额度用完时提示改用自己的 key 或等到次日。
5. 同步分两步交付。第一步只做整库备份：客户端上传版本库备份快照，换机时登录并下载最近一份恢复，这一步复用现有的导出与恢复校验，不改变本机表结构。第二步做增量同步：客户端按提交上传净变化，服务端按账号维护一条线性的提交序列，推送前必须基于服务端最新位置，否则先拉取、在本机应用为新的提交后再推送。增量同步要求业务表主键在设备之间不冲突，现有的 `INTEGER PRIMARY KEY AUTOINCREMENT` 需要先改为全局唯一的标识，这次改动按 [ADR-0002](0002-本地数据不做迁移.md) 升 schema 并清空重建。
6. 学习数据进入服务端之后，传输使用 TLS，数据库与对象存储在服务器上加密存放，访问日志不记录请求正文与模型输出。用户可以在设置页删除云端数据，删除账号时服务端数据与备份一并删除。代理转发的请求正文只在转发期间存在于内存，服务端只记录用量所需的 token 数、模型名与时间。

## 代价与边界

- 学习记录离开本机，隐私边界从“数据只在这台手机上”变为“数据在这台手机和项目组的服务器上”。仓库公开、成员是学生，服务器的访问权限、备份与密钥轮换都要由陈思源指定专人管理，这一点比 Sentry 更敏感，因为同步副本含有学习正文。
- 团队每周合计 32 小时，服务端会占用原本给验收与缺陷修复的时间。第一期只做账号、整库备份与模型代理，增量同步排在主键改造之后；排期与负责人需要在 [03](../03-团队分工与协作.md) 里另行确认，本条不改动现有里程碑。
- 模型代理让项目第一次承担模型费用。额度、可用模型与经费来源在内测前定下来，额度数字写进 00，在此之前服务端以配置项控制，默认值标“待定”。
- 端到端加密暂不做。端到端加密会让服务端无法校验备份与提交序列，也会排除以后在服务端做检索的可能；如果试用反馈或学院要求更强的隐私保护，再单独评估。
- 增量同步的冲突规则只定了框架：服务端只保证序列线性，不合并字段；同一字段在两台设备上同时修改时，后到达服务端的提交覆盖先到达的，被覆盖的值保留在提交历史里，可以从数据版本页找回。这条规则是否够用，要在两台设备的走查之后再定。

## 替代方案

- 保持单机，只改进导出恢复的引导。没有采纳的原因是它解决不了不会配置 key 的用户，也解决不了没有导出就换机的用户，而这两类用户在公测里会占多数。
- 云端为主、客户端只做缓存。没有采纳的原因是它要求重写撤销、数据版本与本地兜底，并且断网时不能记录，违反 00 的第三条硬约束。
- 使用第三方后端服务，例如 Firebase 或 Supabase 托管版。没有采纳的原因是学习数据会落在第三方云上，和 ADR-0005 已经确定的“自建、学习数据不外流”要求冲突；Supabase 可以自建，但它带来的数据库直连接口与行级权限需要另学一套规则，团队更容易维护一个自己写的 API。
- 只做模型代理，不做账号。没有采纳的原因是代理必须按人限定额度，没有账号就无法限额，也无法防止 key 被滥用。
