# ADR-0055 模型调用协议与上限统一

## 状态

已采纳。2026-11-23 决定，服务端与客户端同批改完。本条接续 [ADR-0052](0052-客户端改用OpenAI现行请求格式.md)：线格式保持 Responses，只把两端之间的默认模型名、请求字段与输出上限统一，并删除切换期间保留的旧路径。嵌入的对外模型名由本条定为 `zhixin-embedding`，取代 [ADR-0049](0049-嵌入统一走百炼与查询向量也走云端.md) 决定第 1 条里的 `bge-m3`。客户端上下文上限的最大值后来由 [ADR-0070](0070-额度预留与失败结算口径.md) 从 32768 改为 65536，输出上限仍按四分之一计算。

## 日期

2026-11-23

## 背景

2026-11-22 的提交把服务端转发改成 Responses 之后，客户端与服务端之间留下三处对不上的地方，都是切换过程中各自改动造成的。

第一处是默认模型名。客户端保存的默认值是 `deepseek-flash`，服务端只接受管理后台配置的对外模型名，两边对不上时返回 400 `model_not_allowed`。后台实际配置的对外模型名是 `zhixin-chat` 与 `zhixin-embedding`，测试与提交正文里都能看到这两个名字。[ADR-0049](0049-嵌入统一走百炼与查询向量也走云端.md) 当时把嵌入的对外模型名定为 `bge-m3`，部署里用的却是 `zhixin-embedding`，两个名字要一起对齐。

第二处是请求字段。客户端每次对话都发送 `temperature: 0.5`，这个值是早期给 Chat Completions 调的，写死在 [llm_protocol.dart](../../app/lib/ai/llm_protocol.dart) 里。Responses 的现行做法是不在应用侧固定采样参数，部分推理模型的接口也不接受这个字段，上游收到时可能直接返回 400；服务端只做白名单放行，不拦也不改，等于把风险原样交给上游。

第三处是输出上限。客户端按上下文上限的四分之一计算 `max_output_tokens`，最高 8192；服务端把上限卡在 8192、省略时补 1024。两个上限分处两端，一端改动就会让另一端收到 400。客户端与服务端都没有暴露这个数字的配置项，靠约定维持同步。同时，8192 对读材料、写复盘这类长输出偏小，`docs/00` 里也写着单步输出最多 8192 token。

另外，契约里的 `/v1/llm/chat/completions` 在切换时保留下来，注释写的是“等其他改动一起删除”，实际已经返回 404，留在契约里只会让人以为还能调用。

## 决定

1. 对话模型的对外名统一为 `zhixin-chat`，客户端默认值也用它，与服务端管理后台一致。

2. 嵌入模型的对外名统一为 `zhixin-embedding`，取代 [ADR-0049](0049-嵌入统一走百炼与查询向量也走云端.md) 决定第 1 条里的 `bge-m3`。客户端不写死这个名字，仍从 `GET /v1/llm/models` 里 `kind` 为 `embedding` 的项取；部署时管理后台的对外模型名要写 `zhixin-embedding`。改名之后已经建立的索引与 `embedding_cache` 都以旧名字为键，按 [ADR-0001](0001-开发阶段不向下兼容.md) 不保留 `bge-m3` 的别名、不写迁移，代价见代价与边界一节。来源侧的上游模型名仍是 `BAAI/bge-m3`，改名只动对外名，不动来源配置。

3. 客户端不再发送 `temperature` 与 `top_p`。服务端仍然放行这两个字段，供管理端自测与排查使用，但不做任何默认值。

4. 输出上限两端统一。客户端 `buddyMaxOutputTokens` 与最大上下文上限都改为 32768，单次请求的输出上限取 `min(32768, 上下文上限 ÷ 4)`。服务端对访问令牌接受 16 到 32768，省略时使用 4096，三个数字写成 `llmproxy` 里的常量，接入密钥的默认值见 [ADR-0082](0082-接入密钥的模型调用按放宽的校验口径.md)。`docs/00` 的“单步输出预留四分之一，最多 8192 token”随之改成 32768。

5. 实例内存预算随输出上限放大。`ZHIXIN_LLM_MAX_INSTANCE_BYTES` 的默认值从 256 MiB 提到 512 MiB，因为非流式响应与嵌入批次按响应上限预留，输出上限翻四倍之后，沿用旧预算会把同时在途的请求压到个位数。

6. 契约删除 `/v1/llm/chat/completions`，重新运行 `oapi-codegen`，路由、类型与接口一并消失。客户端与服务端只保留 `/v1/llm/responses`。

7. 顺带修正内存额度实现里的一处截断错误。`MemoryQuota.Reserve` 原先写的是 `min(reserved, limit-used)`，第二个参数取的是上一次截断后的预留量而不是本次请求量，剩余量够用时也会被截成 0，剩余 60 token 时请求 40 会被拒绝。改为 `min(want, limit-used)`，并补了剩余量与请求量分开比较的单测。

## 代价与边界

服务端与客户端必须一起发布。服务端部署之后，仍按 `deepseek-flash` 配置的旧客户端会收到 400 `model_not_allowed`，直到升级；按 [ADR-0001](0001-开发阶段不向下兼容.md) 不保留旧模型名的别名映射。

输出上限放大之后，单次回答的 token 费用上限随之放大，账号每日额度 `ZHIXIN_LLM_DAILY_TOKENS` 的消耗会比以前快；实例内存预算提到 512 MiB 也意味着单机同时承接的请求更多，部署时要按这个数字配机器内存。

`temperature` 去掉之后，回答的风格由上游模型自己的默认值决定，应用侧不再有可调的旋钮；如果将来要按场景调整，需要重新在服务端增加来源级的参数配置，而不是回到客户端写死。

客户端的最大上下文上限改为 32768 之后，填了更大上下文窗口的模型需要用户自己改设置页；默认值只对上下文不超过 32768 的模型成立。

嵌入对外模型名从 `bge-m3` 换成 `zhixin-embedding` 之后，已经建立的语义索引与 `embedding_cache` 都以旧名字为键，改名之后全部不命中，客户端要重建一次索引、服务端缓存重新积累。现在是开发阶段的联调实例，这个代价可以接受；内测开始之后再改名，要按当时的用户数与片段数重新评估。

## 替代方案

- 两端保留一份可配置的输出上限，由服务端下发。客户端每次对话要先多读一次配置，协议也要多一个字段；上限是两端的协议常量，改动频率很低，本次没有采纳。
- 服务端在转发时删掉 `temperature`，客户端不动。这样只解决一半问题，客户端发出的字段仍然与协议说明不一致，而且服务端替客户端改写请求体，会让排查时看到的请求与代码不一致；本次选择在客户端源头上不发送。
- 保留 `chat/completions` 作为回退路径。它在切换时就已返回 404，留着只是契约上的历史包袱，按 ADR-0001 的开发阶段口径直接删除。
