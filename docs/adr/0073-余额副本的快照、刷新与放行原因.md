# ADR-0073 余额副本的快照、刷新与放行原因

- 状态：已采纳，随服务端下一次部署生效；改定 [ADR-0069](0069-积分余额的本地副本与预留放行.md) 的副本时间与刷新阈值，补充 [ADR-0071](0071-核销只读已结算用量与额度用完的原因.md) 的剩余积分口径与 429 原因
- 日期：2026-11-25

## 背景

余额副本自 ADR-0069 起承担“免费额度用完之后能不能放行”的判断，同步时间写的是写入时刻，未反映的核销按 `created_at >= synced_at` 判断。核销流水先创建、后确认，一条在余额快照之前创建、在快照之后才成功的流水会被算成副本已经反映过的扣减，副本因此偏高。余额查询与核销并发、响应乱序时，两份快照还会先后颠倒，晚到的旧快照覆盖新副本，副本同样偏高。副本偏高会多放行一次核销，而多扣的积分不能退回。

第二个问题是刷新窗口与提示。副本要过期十分钟才刷新，免费额度用完的付费用户在副本过期之后会收到 429 `account` 或 `points`，客户端据此显示购买入口，而他其实还有积分；这一轮本来可以用一次查询解决，用户看到的却是“没有积分，去买”。第三处是展示口径：账号页的剩余积分只减未反映的核销，预留放行还要再减当天已经结算、还没有记进流水的计费量，同一时刻账号页可能显示剩余 10 分而实际只能放行 8 分。

## 决定

余额副本的 `synced_at` 改为这份余额对应的快照时刻。`quota.query` 返回 `as_of_time` 时按东八区解析后使用，没有这个字段或格式不符时用查询发起的时刻；核销与补查的结果带这个字段时同样使用，没有时用发起核销的时刻。`SaveBalance` 改为条件更新，只有新的快照时刻不早于现有值才覆盖副本，乱序返回的旧快照不会让副本回退。

未反映的核销按状态与确认时间判断：`pending` 与 `processing` 一律计入，因为扣减还没有确认；`succeeded` 只在 `updated_at` 晚于快照时刻时计入；`failed` 不计。终态行的 `updated_at` 视为确认时间。核销成功或失败、要按响应里的剩余积分写副本时，快照时刻取响应给出的时刻与这次确认时刻里较晚的一个：确认时刻晚于响应里的 `as_of_time`，只按响应时刻写会把刚确认的这一笔自己算成“快照之后才确认”，可用积分平白少一笔，直到下一次余额查询才回来。`PROCESSING` 响应的剩余积分不写副本，它有没有扣住那笔预占还没有与即刻收确认。核销因余额不足被拒时，服务端将流水记为失败，并安排一次余额查询，因为这次拒绝只能确定余额低于申请量。已有查询排队或执行时复用该查询，最近一次查询已结束时可以立即安排新查询。

副本缺失或距快照超过一分钟时，预留排一次异步查询，这一轮仍按现有副本判断。如果这一轮本来就放行不了，429 的 `extra.reason` 写 `syncing`，客户端提示积分余额正在同步、稍后重试，不显示购买入口；副本新鲜却不够时，仍按有没有积分写 `points` 或 `account`。同一个账号一分钟内只入队一次查询，`RefreshBalance` 返回这次是否真的入了队，`syncing` 只在入队时出现，合并窗口里的下一次请求按已有结论写原因。

账号页、管理后台与额度预留共用同一份积分汇总，余额副本扣除所有记账日尚未反映的核销，当天已扣只统计当天核销成功的积分。已结算用量和在途预留先扣除当天免费额度，超出的部分优先由当天已申请且未失败的积分覆盖，如果还有用量需要由余额覆盖，账号页和管理后台只显示扣除这些用量后尚未占用的整积分，额度预留则按剩余计费 token 判断。例如，一积分对应 1,000 个计费 token 时，如果余额只有一积分，其中 400 个计费 token 已被预留，页面显示尚未占用的整积分为零，剩余 600 个计费 token 当天仍可预留。

核销因余额不足只申请了部分积分时，覆盖量按实际申请的积分计算，流水的 `billed_tokens` 继续保存申请时的当天累计超额用量，供对账时查阅。积分查询在同一个数据库快照中读取余额、流水和用量，核销申请按账号串行，因为同一个余额会用于核销不同记账日的用量。

核销收口用同一个可用积分，截断的对象是当天还没有申请的差额：累计应扣减去当天已经申请的积分，再与可用积分取较小值。已经申请过的积分不能从可用积分里再减一次，因为成功的那部分已经反映在副本里、待确认的那部分已经计入可用积分的扣减，再减一次会让当天后续的结算少写流水，剩下的积分被免费用掉。

## 代价与边界

副本过期之后，付费用户可能先收到一次 `syncing`，下一次请求才按刷新后的余额放行；这个窗口是一次请求，刷新失败时会持续到查询恢复。副本仍然可能偏高：快照记的是查询给出余额的时刻，查询返回之前的扣减只能靠未反映流水补回，余额不足的核销会触发查询，查询完成前仍使用现有副本。

`updated_at` 只在状态变化时更新，补查确认成功会把确认时间写回，因此一条处理中流水的成功时间晚于快照时会被算成未反映，副本偏低、放行偏保守；这与“多扣不可退、漏扣可以补”的取舍一致。写副本时把快照时刻抬到这次确认时刻之后，也会把响应返回之前刚确认、但余额查询没有读到的其它流水当成已经反映，窗口是一次核销往返的时间，方向与上面相反，范围最多一笔核销。

按快照时刻比较依赖支付宝返回的 `as_of_time`。字段缺失或格式不符时退回查询发起的时刻，服务端时钟与支付宝时钟的偏差会体现为副本时间偏差；查询发起之后到响应之间确认的核销会被算成未反映，方向同样偏保守。

预留触发的查询按账号间隔一分钟，余额不足触发的查询与同账号尚未完成的查询合并。查询与按账号 15 分钟 6 次的接口限流共用额度，高峰期购买面板的查询可能受影响。

## 替代方案

保留 `created_at >= synced_at`，把 `synced_at` 改成响应返回时刻。没有采纳的原因是核销行先创建、后成功，按创建时间判断无法区分“已经反映”与“还没有反映”，并发与乱序时副本仍然偏高。

按写入时刻比较新旧快照，不引入 `as_of_time`。没有采纳的原因是写入时刻与余额对应的时刻不同，两份响应先后到达时无法判断哪一份更新，乱序仍然会让副本回退。

在副本上再记一列已反映的核销编号。没有采纳的原因是它要按账号维护一份清单，清理与对账都更复杂，而 `updated_at` 已经能表达确认时间。

照旧在十分钟后刷新，只把原因改成 `syncing`。没有采纳的原因是十分钟的窗口足够用户完成一次购买与一次失败重试，`syncing` 会长期盖住“确实没有积分”的结论。

## 影响

- 查询与存储：[queries/nowpay.sql](../../server/internal/store/queries/nowpay.sql) 的 `SaveBalance` 按快照时间更新副本，`PointLedgerWithBalance` 汇总指定记账日的积分流水与副本未反映的扣减。积分统计与额度预留的实现见 [pg/points.go](../../server/internal/store/pg/points.go)。
- 即刻收调用：[nowpay/client.go](../../server/internal/nowpay/client.go) 的 `Balance` 与核销结果带出快照时刻；[nowpay/meter.go](../../server/internal/nowpay/meter.go) 的 `RefreshBalance` 返回是否入队，`BalanceRefreshAfter` 取代原来的十分钟常量；[nowpay/handler.go](../../server/internal/nowpay/handler.go) 写副本时带上快照时刻。
- 额度与接口：[llmproxy/quota.go](../../server/internal/llmproxy/quota.go) 新增 `QuotaReasonSyncing`，[llmproxy/proxy.go](../../server/internal/llmproxy/proxy.go) 为它写详情；[openapi.yaml](../../server/api/openapi.yaml) 更新 `remaining_points` 的描述与 429 的四种原因。
- 文档：[server/README.md](../../server/README.md#即刻收收款) 的即刻收一节与余额副本表说明；[ADR-0069](0069-积分余额的本地副本与预留放行.md) 与 [ADR-0071](0071-核销只读已结算用量与额度用完的原因.md) 的状态行注明本条改定的部分。
- 客户端：`extra.reason` 多一个取值，`syncing` 的提示与“不显示购买入口”由客户端改动落地。
- 验收：副本缺失时第一次 429 为 `syncing` 且服务端调用一次 `quota.query`，第二次按刷新后的余额放行；余额查询与核销乱序返回时副本不回退；`PROCESSING` 的剩余积分不覆盖副本；账号页的 `remaining_points` 不超过实际放行的积分。
