# ADR-0026 记忆召回改用 zvec 全文索引

## 状态

已采纳。2026-11-18 实现，测试与文档同步。召回的排序入口改为与文档同一条检索路径，决定第 3 条中“记忆不嵌入”的理由由 [ADR-0051](0051-记忆改为自由文本条目并走文档检索路径.md) 第 6、10 条改写，决定本身不变，独立目录与按需同步沿用。

## 日期

2026-11-18

## 背景

记忆召回在 `memory_recall.dart` 里按二元组命中数给候选排序：把本次问题切成二元组，数每条记忆正文命中了几个，命中的越多名次越靠前，相关程度相同时比较更新时间。这条排序是 [ADR-0013](0013-关键词检索改用FTS5.md) 第 7 条留下的做法，理由是记忆条数远小于材料页与消息，另建一张索引表不划算。

关键词检索与语义检索在 [ADR-0022](0022-语义索引改用zvec.md) 与 [ADR-0024](0024-关键词检索并入zvec.md) 之后已由 zvec 承担：材料页、消息与已提交作答的正文写进 collection 的 `content` 字段，建立 jieba 全文索引，配置嵌入来源时再加向量字段。于是同一份“什么算相关”的判断出现了两套实现：检索用引擎的分词与排序，记忆召回用 Dart 的二元组计数。两套规则的排序结果不一致，调整其中一套不会带动另一套，评测也要分别准备。

记忆召回的实际影响集中在候选超过四十条的时候：一次回答最多把四十条记忆放进提示词，条数在四十以内时每条都会进入上下文，排序只决定先后。超过四十条时排序决定哪几条被截掉，这时二元组计数认不出用词不同的同一件事，例如问题问“解完方程还要做什么”，记忆写的是“把根代回原方程验算”，两者一个字面词都不重合，这条记忆排在最后，进入不了提示词。

## 决定

1. 记忆召回的候选之间改由 zvec 的全文索引排序，召回范围仍由记忆仓库筛出：仓库先按状态、有效期与本次范围取候选，索引只决定候选的先后。约束先占预算、按用途优先分类别、同类再按相关性、最后比较来源与更新时间的规则不变，变的只是相关性这一层的来源。
2. 记忆索引是一个独立的 collection，目录为 `memory_index/`，与语义索引目录同级，不入库也不进数据包。它单独存在的原因是两个 collection 的核对规则不同：材料页、消息与作答的来源写到索引里之后，还要按业务记录、来源版本与检索范围逐条核对；记忆按 `memory` 表的状态、有效期与范围判断，与证据记录无关。放进同一个 collection 会让记忆片段占掉记录检索的候选位，也会让证据检索多一条“排除记忆”的过滤条件。
3. 记忆索引只建全文索引，不写向量，也不调用嵌入来源。嵌入来源的共享范围按材料定义，记忆不属于任何材料，把记忆正文发给远端服务需要单独的用户许可；一次回答最多带入四十条记忆，正文本来就会整段进入提示词，向量排序的收益只出现在候选超过四十条时。不嵌入也让召回不增加联网与计费，改一条记忆不会触发一次远程调用。
4. 同步按需进行，不做提交触发的后台刷新。每次召回先读当前有效且未过期的全部记忆，与索引里的来源版本逐个比较，只重写正文或更新时间变化过的条目，删掉不再有效或已经删除的条目；数据代次变化（整库恢复、导入、清空）时整份清空，与 [ADR-0022](0022-语义索引改用zvec.md) 的口径一致。记忆条数在几百条以内，这次比较与清理的开销远小于一次模型调用。
5. 本次范围只下推到查询，不写进索引。索引保留全部有效记忆，换目标或材料时不必重写条目；候选以来源键列表交给引擎，渲染成 `source_key in (...)`，空候选用一条不可能命中的等值表达式表示。这样跨范围切换只影响排序的候选集合，不产生嵌入或重写成本。
6. 索引打不开、同步失败或引擎不可用时，召回退回原来的二元组排序，回答不因此失败；待确认的记忆提案不写在 `memory` 表里，仍然不进入召回。两份排序的口径不同，降级只在索引不可用时发生，评测要分别记录走的是哪一套。
7. 记忆索引是派生数据：可以从 `memory` 表重建，不进数据包与版本库备份，清空本机数据时与语义索引一起删除，结构损坏时改名重建并记一条本机诊断记录。

## 代价与边界

- 召回路径多了同步开销：每次回答读一次全部记忆，再按来源版本比较一次。没有变化时只有读取与比较，正文改写与第一次使用时才有写入；这个开销与一次模型调用相比可以忽略，但它确实出现在回答之前的串行路径上。
- 记忆排序依赖后台 isolate 与 zvec 引擎可用。打不开时退回二元组排序，两套排序给出的名次不同，同一份记忆库在两个环境下的候选可能不一样；这是可以接受的降级，代价是评测结论要区分环境。
- 没有向量，用词完全不重合的记忆仍然排不到前面；现在的收益是把二元组分词换成 jieba 分词与 BM25 排序，并让记忆排序与检索共用同一个引擎与同一套阈值。真正的语义召回要等嵌入来源的共享规则覆盖记忆，那时再单独决定是否加向量字段。
- 分词口径从二元组换成 jieba，两字词、英文缩写、代码符号与公式的覆盖会变，评测集要复核记忆排序的前几条结果；这一项与 [ADR-0024](0024-关键词检索并入zvec.md) 留下的复核合并执行。
- 记忆索引与语义索引同处一个进程，共用 zvec 引擎的内存上限。记忆只存正文与标量字段，占用远小于材料页与消息的索引，不改变引擎的内存设置。
- 索引目录不进数据包，但它保存着记忆正文的副本。清空全部记录、清空一条记忆与整库恢复都会让索引在下次召回时删除对应条目；删除本机全部数据时索引目录随语义索引一起删除。

## 替代方案

- 继续在 Dart 里按二元组排序。没有采纳的原因：同一份“相关”的判断留在两套实现里，调整检索的排序不会带动记忆，评测也要分别准备；记忆条数增长之后，二元组计数与分词排序的差别只会更大。
- 把记忆写进材料页、消息与作答的同一个 collection。没有采纳的原因：两个 collection 的候选核对规则不同，记忆进证据索引要额外排除，证据检索也要为每一个查询多一条过滤条件；单独一个 collection 让两套规则各自成立，删除与清空的范围也更清楚。
- 记忆也写向量、按语义排序。没有采纳的原因：嵌入来源的共享范围按材料定义，记忆不属于任何材料，发送记忆正文需要单独的用户许可与开关；而一次回答最多带入四十条，正文本来就会整段进入提示词，收益只出现在候选超过四十条时。等召回评测显示确有必要，再按同一套 collection 加向量字段，不影响本条的其他决定。
- 用纯 Dart 的 `MemoryVectorIndex` 在界面线程上排序。没有采纳的原因：索引要在界面线程上同步读写，记忆条数与正文长度不受控时会占用帧；后台 isolate 已经按同一套接口维护索引，复用它不需要新增线程模型。
- 在每次记忆写入之后提交触发一次后台刷新。没有采纳的原因：记忆写入频率低，但触发链路要新增来源表监听与静默期，而按需同步在同一次召回里完成读到写，少一条时序假设；代价是第一次召回要建立索引，这一步与正文改写一起计算。
