# ADR-0079 管理后台的反馈查看

## 状态

已采纳（2026-11-26，服务端同日实施）。[ADR-0025](0025-应用内更新检查与反馈的接口口径.md) 决定第 3 条“反馈不设读接口”的后台部分由本条补上，公开接口仍然只写不读。

## 日期

2026-11-26

## 背景

应用内反馈从 2026-11-18 起按 [ADR-0025](0025-应用内更新检查与反馈的接口口径.md) 只写不读：`POST /v1/feedback` 把正文、可选的联系邮箱、版本、平台与诊断摘要写进 `feedback` 表，管理员要查看时按 `created_at` 直接查库。反馈不绑定账号，删除与保留期清理也各自执行 SQL。当时的判断是反馈量小、读取不频繁，单独开一套读接口会增加一处需要维护的权限面。

内测从 12 月开始之后，反馈成为团队发现问题的主要渠道，读取的频率与用途都变了：管理员需要按版本或平台确认某一类问题是否集中出现，需要按联系邮箱找到用户并回复，也需要把诊断摘要单独打开看，而不是在 `psql` 的结果里逐行翻看。直接查库没有分页与关键字检索，一条至多 4000 字的正文与至多 64 KiB 的诊断摘要保存在同一列，复制时容易把不需要的内容带进聊天记录；反馈表的上限是一万条，靠近上限时逐页翻 SQL 结果也不方便。[server/README](../../server/README.md#应用内反馈) 与[运维手册](../../server/运维手册.md#5-常用操作)把“管理员按语句查看”写成现行做法，本轮要把它换成页面，同时保留 SQL 作为后台不可用时的兜底。

账号管理页已经在 2026-11-26 补上，后台的页签从三个增加到四个；反馈是同一批运营需求里剩下的读取入口，管理令牌、页面框架与分页写法都可以复用。

## 决定

1. 新增 `GET /admin/v1/feedback`，按提交时间倒序分页列出反馈，`limit` 取 1 至 100、默认 20，`offset` 取 0 至 100000，越界返回 400 `invalid_request`。`query` 最长 254 字，去掉两端空白之后匹配编号、正文、联系邮箱、版本与平台的子串，空值列出全部；匹配用 `position(lower(...))`，管理员输入的 `%` 与 `_` 按普通字符处理。
2. 列表返回编号、提交时间、正文全文、联系邮箱、版本与平台，不返回诊断摘要，另给 `has_diagnostics` 说明这条反馈有没有附带诊断；正文在页面上只显示前三行，打开单条之后可以看全文。
3. 新增 `GET /admin/v1/feedback/{id}`，返回列表字段与诊断摘要全文；编号不存在返回 404。读取不改变任何数据，也不延长保留期。
4. 新增 `DELETE /admin/v1/feedback/{id}`，删除一条反馈，编号不存在返回 404，成功返回 204。保留期清理仍按 `ZHIXIN_FEEDBACK_KEEP_DAYS` 每天执行一次，后台删除只用于误提交、重复提交或用户要求提前删除的情况。
5. 后台增加“反馈”页签：顶部按编号、正文、联系邮箱、版本或平台搜索，列表显示提交时间、版本与平台、正文前三行与联系邮箱；打开一条反馈时读取全文与诊断摘要，删除按钮放在弹窗里并要求二次确认，避免在列表上误点。
6. 存储层增加 `feedback.AdminStore`（列出、按编号读取、按编号删除）与组合接口 `feedback.Repository`，内存实现与 PostgreSQL 实现都满足；`feedback.Store` 的写入与保留期清理不变，公开提交接口的处理器不感知后台读取。不新增表与列。
7. 权限沿用管理令牌：三个接口都在 `/admin/v1/` 下，与其余管理接口同一道中间件；账号令牌不能调用，管理令牌也不能当账号令牌使用。反馈仍然不绑定账号，管理接口不返回账号编号或登录方式。

## 代价与边界

后台页面因此成为反馈正文、联系邮箱与诊断摘要的展示面。管理令牌泄漏时，攻击者可以读到用户主动提交的全部原话与联系方式；这与账号管理页显示完整邮箱同等级，生产上继续按 [ADR-0029](0029-模型来源路由与嵌入代理.md) 限制 `/admin` 的来源地址或只经 SSH 隧道访问。反馈本来就不绑定账号，读到联系邮箱也不等于能把反馈对应到某个账号。

后台仍然没有操作审计，删除一条反馈不记录谁在什么时候删的，删除之后也无法恢复。需要保留证据的反馈应先复制内容或导出，再删除；保留期到期的行仍由每日任务清理，两者互不替代。误删只能依赖数据库备份，这一点与账号注销相同。

关键字检索是子串匹配，`feedback` 上的 `created_at` 索引帮不上忙，查询会退化为全表扫描。表的容量上限是一万行，当前内测规模只有百人量级，扫描代价可以接受；需要按规模优化时另开决定，例如按日期分段或只允许按编号精确查找。

列表返回正文全文，默认一页 20 条，最坏情况一页 100 条、每条 4000 字，响应约 1.2 MB；页面默认不分页抓取全部正文，管理员一次只取一页。诊断摘要只在单条读取时返回，避免列表把每条 64 KiB 的摘要一起读出。

内存实现只用于本地联调，反馈与删除结果都在进程内，进程退出后丢失；PostgreSQL 实现的关键字与分页口径由 `ZHIXIN_TEST_DATABASE_URL` 下的用例核对，未设置时跳过。

## 替代方案

继续只用 SQL 查看与删除。没有采纳的原因是缺少分页与检索，诊断摘要与正文挤在一列，复制时容易带出额外内容；SQL 仍保留在[运维手册](../../server/运维手册.md#5-常用操作)，作为后台不可用时的兜底。

把读取接口放在公开的反馈接口下，按提交编号查询。没有采纳的原因是反馈没有归属账号，公开读取会让任何拿到编号的人读到别人的原话与联系邮箱；管理令牌是现有的、范围清楚的替代。

给反馈加已读、处理中、已回复的状态列，后台按状态流转。没有采纳的原因是现在只有一位管理员，处理流程还在聊天与 Issues 里，增加列与状态机会让删除与保留期的口径多一层判断；确实需要时再按表结构加列，见 [ADR-0058](0058-表结构冻结后只做加法.md)。

反馈提交之后自动建一条 GitHub Issue。没有采纳的原因是这要求服务端持有仓库凭据，正文会离开自建服务端，用户提交时也没有同意把内容放到第三方；Issues 继续由团队成员按缺陷模板登记。
