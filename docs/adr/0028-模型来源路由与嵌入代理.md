# ADR-0028 模型来源路由与嵌入代理

## 状态

已采纳。服务端的来源与路由表、嵌入代理、管理接口与后台页面已于 2026-11-18 实现；客户端把“知新服务”用作嵌入来源、聊天模型列表按 `kind` 过滤这两项尚未接入。服务端检索索引仍按 [ADR-0027](0027-服务端承担嵌入与检索.md) 另行排期，不在本条范围内。

## 日期

2026-11-18

## 背景

模型代理此前只有一个上游：`ZHIXIN_LLM_BASE_URL` 加一把 `ZHIXIN_LLM_API_KEY`，再加一张模型名白名单，只转发 Chat Completions。[ADR-0027](0027-服务端承担嵌入与检索.md) 决定服务端可以承担嵌入，但嵌入接口还没有建立；第一套实例用的 DeepSeek 只提供聊天模型，要做嵌入就必须接入第二家服务商，例如硅基流动或阿里云百炼，单一上游的配置方式容纳不了这件事。

单一上游还有两个问题。第一，这家服务商限流或故障时，所有登录用户的回答一起失败，没有备用来源可以切换。第二，换模型、换 key 都要登录服务器改 `api.env` 并重启服务，管理员不在电脑前就无法处理；额度调整与反馈查看也都是直接执行 SQL，服务端没有任何管理入口。

团队讨论过两条路：部署现成的模型网关（new-api、one-api、LiteLLM、Bifrost 这一类），由 zhixin-api 转发给它；或者在 `llmproxy` 里自己实现路由。2026-11-18 陈思源选择后者，同时要求管理员能在网页后台配置多个模型来源，嵌入这一步只做代理与批量，服务端索引留到下一步。

## 决定

1. 路由在 `server/internal/llmproxy` 里实现，不部署独立的模型网关。知新要接的来源都提供 OpenAI 兼容接口（DeepSeek、硅基流动、百炼的兼容模式、自建的 vLLM 与 Ollama），路由只需要换地址、换 key、换模型名；账号、额度与用量记录已经在 zhixin-api 里，由它直接调用来源，不需要在两套系统之间同步账号与额度。实现只用标准库，Go 的第三方依赖不增加。
2. 配置分三张表。`llm_provider` 是来源，一个基础地址加一把 key；`llm_model` 是客户端请求里写的对外模型名，带种类（`chat` 或 `embedding`）与嵌入维度；`llm_route` 把一个对外模型指到某个来源上的模型名，带优先级、权重、每批条数与启用开关。环境变量里的那一组配置保留为只读来源 `env`，第一套实例升级之后不进后台也能照常工作；后台里同名的模型覆盖环境变量里的模型。
3. 一次请求按优先级从小到大尝试路由，同一优先级内按权重随机排列，最多尝试 `ZHIXIN_LLM_MAX_ATTEMPTS` 条。连接失败、响应头超时（`ZHIXIN_LLM_HEADER_TIMEOUT`，用于流式聊天与嵌入）、408、429、5xx、401 与 403 在向客户端写出第一个字节之前换下一条重试；400、404、422 说明请求本身有问题，直接返回。某个来源连续失败三次之后冷却 30 秒，此后每多失败一次冷却时间翻倍，最长 5 分钟；冷却中的来源排到最后，其余来源都失败时仍然会试，成功一次立即解除。健康状态只保存在进程内存里。
4. 嵌入走 `POST /v1/llm/embeddings`，请求与响应采用 OpenAI 的格式，`input` 只接受字符串或字符串数组，单次条数上限是 `ZHIXIN_LLM_EMBEDDING_MAX_INPUTS`。路由配置了 `max_batch` 时，服务端把一次请求拆成几批，同时最多发出四批，再按原顺序合并，`index` 从 0 连续编号；任何一批失败，整次请求换下一个来源重做，所以同一次请求的向量都来自同一个来源。嵌入模型配置了维度时，服务端逐条核对返回的向量维度，维度不符按来源故障处理；客户端请求的 `dimensions` 与配置不一致时直接返回 400。
5. 嵌入的用量与聊天分开计。`llm_usage` 按账号、自然日与种类各记一行，嵌入的默认额度是 `ZHIXIN_LLM_EMBEDDING_DAILY_TOKENS`，`llm_quota` 可以分别覆盖两类额度。来源没有返回 `usage` 时，嵌入按输入字数估算，聊天按请求与已转发的字节数除以三估算；流式聊天由服务端打开 `stream_options.include_usage`，客户端省略这个选项也照常计入额度。
6. 来源的 key 用 AES-256-GCM 加密入库，密钥是环境变量 `ZHIXIN_SECRET_KEY`，不进数据库与仓库；加密时把来源编号与地址的协议和主机作为附加数据，密文因此只能在原来的主机上解密。管理接口不返回 key，只返回是否已设置与末四位；修改来源时把地址换到另一台主机，必须同时重新填写 key，管理令牌因此无法把已保存的 key 引到别的地址。最后一个来源拒绝服务端的 key（401、403）时，客户端收到 `upstream_failed`，提供方的错误体不转发，因为里面可能带着打码的 key 与组织名。代理不跟随重定向。
7. 管理后台由 `ZHIXIN_ADMIN_TOKEN` 开启，令牌至少 32 个字符，与账号体系无关。`/admin/v1/` 下的接口写进 `openapi.yaml`（安全方案 `admin`），处理器与用户接口一样由生成的路由转发；`/admin/` 是编进可执行文件的静态页面，只用本站脚本，带严格的内容安全策略。令牌校验失败按来源地址限流，超限期间这个地址的所有管理请求都先返回 429；没有配置令牌时整个 `/admin` 返回 404。后台打开并且使用数据库时，`ZHIXIN_SECRET_KEY` 必须配置，否则启动失败。管理接口保存之后立即刷新路由，服务每 `ZHIXIN_MODEL_RELOAD_INTERVAL` 再从数据库读一次，直接修改数据库也会生效。

## 代价与边界

- 路由、冷却与批量拆分都由团队维护，现成网关已经有的功能（按渠道统计费用、按模型设置倍率、多 key 轮换、Anthropic 与 Gemini 原生格式的转换）这里都没有。以后需要接非 OpenAI 兼容的来源时，要么在 `llmproxy` 里增加格式转换，要么重新评估网关。
- 额度仍然是先检查再记录：并发请求都能通过检查，账号的当日用量可能超过额度，超出量与并发数和单次请求的大小成正比。内测规模下可以接受；公测前如果出现集中超额，改成先预留估算量、结束时再按实际用量校正。
- 估算只用于没有 `usage` 的情况，数字偏粗：英文按字数估算会偏高，聊天按字节估算对中文大致准确。目的只是不让这类请求免费，账单仍以提供方的统计为准。
- 冷却状态只在本进程内有效，重启之后清零，多实例部署时各实例分别判断。这与 [ADR-0015](0015-服务端引入代码生成与限流依赖.md) 第 5 条限流的口径相同。
- 一个嵌入模型的多条路由必须是同一个模型的不同部署，否则同一个索引里会混进不同向量空间的向量。服务端只核对维度，向量空间是否一致无法核对，由管理员在配置时保证；后台页面在模型列表上方写明这条要求。
- 管理令牌是一个共享密钥，后台没有操作审计，也不区分只读与可写。服务器只有一位管理员（[04 第 5 节](../04-长期路线图.md#5-决定) D7），这样够用；人数增加时改成账号加角色，并记录谁在什么时候改了哪个来源。生产上建议在 nginx 里把 `/admin` 限制在管理员的地址，或者只通过 SSH 隧道访问。
- 换掉 `ZHIXIN_SECRET_KEY` 之后，已保存的 key 全部无法解密，后台显示为 `key_error`，相关路由停用，需要重新填写；仓库不提供轮换密钥的工具。
- `llm_usage` 的主键增加了 `kind`，`llm_quota.daily_tokens` 改为可空，并新增三张表。按 [ADR-0001](0001-开发阶段不向下兼容.md) 不写迁移，第一套实例升级时由管理员按提交正文给出的 SQL 改表，或者按当前 `schema.sql` 重建库。
- 模型列表里的每一项多了 `kind` 与 `dimensions`。现有客户端只读 `id`，后台配置了嵌入模型之后，设置页的模型提示里会混进嵌入模型，直到客户端按 `kind` 过滤；这一项与“知新服务”作为嵌入来源的接入一起排给客户端。

## 替代方案

- 部署 new-api 或 one-api。它们自带后台页面、渠道路由、额度与嵌入转发，功能比本条完整。没有采纳的原因是它们有自己的一套用户、令牌与额度：知新的账号要映射成网关里的用户或令牌，额度在两边各有一份，删号、调整额度都要同时改两处；另外还要多维护一个服务与一个数据库，第一套实例只有 2 vCPU 与 1682 MB 内存。
- 部署 LiteLLM 或 Bifrost 作为内部网关，zhixin-api 只负责账号与额度。路由与后台交给它们，额度留在 zhixin-api。没有采纳的原因是知新要的路由只是 OpenAI 兼容接口之间的换地址与换 key，引入一个独立进程带来的部署、升级与故障面大于收益；LiteLLM 还需要 Python 运行时，服务器上目前只有一个 Go 可执行文件。
- 来源继续写在环境变量里，扩展成多组变量。这样不需要加密与后台，但每次增删来源都要登录服务器、改文件、重启服务，与“在后台配置”的要求不符。
- 管理员用账号登录，在账号上加管理员角色。页面可以直接复用登录，但需要改 `app_user` 表、令牌与鉴权中间件，账号被盗时后台也随之暴露；单一管理员的阶段，独立的管理令牌更简单。
- 嵌入请求在同一次请求里跨来源拆分，失败的那一批单独换来源重试。重试的粒度更细，但一次请求的向量可能来自不同的部署，混进索引之后无法区分，因此没有采纳。

## 影响

- 接口契约：[server/api/openapi.yaml](../../server/api/openapi.yaml) 新增 `/v1/llm/embeddings`、`/admin/v1/providers`、`/admin/v1/models` 等路径与 `admin` 安全方案，`Model` 增加 `kind` 与 `dimensions`，`LLMQuota` 增加嵌入用量与额度。
- 服务端代码：`server/internal/llmproxy`（路由、嵌入、管理接口）、`server/internal/admin`（令牌校验与后台页面）、`server/internal/secretbox`（key 加密）、`server/internal/store/pg/llm.go`、`server/internal/config`。
- 表结构：[schema.sql](../../server/internal/store/schema.sql) 的 `llm_provider`、`llm_model`、`llm_route`，以及 `llm_usage`、`llm_quota` 的改动。
- 文档：[server/README](../../server/README.md#模型代理) 的模型代理、管理后台与配置表，[运维手册](../../server/运维手册.md) 的配置与常用操作，[ADR 索引](README.md)，[ADR-0027](0027-服务端承担嵌入与检索.md) 的影响一节，[04 第 1 节](../04-长期路线图.md#1-现状)的服务端现状。
- 客户端（尚未改动）：`app/lib/data/cloud/server_client.dart` 的模型列表按 `kind` 过滤，`app/lib/application/embedding_client.dart` 增加“知新服务”嵌入来源，二者由客户端在接入服务端嵌入时一起完成。
