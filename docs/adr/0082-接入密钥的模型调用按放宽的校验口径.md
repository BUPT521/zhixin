# ADR-0082 接入密钥的模型调用按放宽的校验口径

## 状态

已采纳（2026-11-26，服务端同日实施）。补充 [ADR-0063](0063-模型代理接入密钥.md) 关于密钥只调用模型接口的口径，不改变其“密钥与账号共用额度、没有有效期”的结论。

## 日期

2026-11-26

## 背景

接入密钥是给用户自己的脚本与第三方工具用的（[ADR-0063](0063-模型代理接入密钥.md)）。这些工具按它们自己的 Responses 客户端组装请求，带哪些字段、输出上限填多大，都不由知新决定；服务端能做的只有接受请求或者整次拒绝。

2026-11-26 用[知新的一道接入密钥](../../server/README.md#模型代理)接 DeepSeek Harness 时，两次拒绝都发生在请求进入模型之前。第一次是 `400 unsupported model request field`：这个客户端每次请求都带 `prompt_cache_key`，开启思考时再带 `include`，而代理只放行知新客户端用到的字段。放行这一批字段之后，同一个客户端又按模型上下文上限填了 `max_output_tokens: 1000000`，得到 `400 max_output_tokens must be between 16 and 32768`。两次拒绝都不是密钥、额度或来源的问题，请求一个 token 也没有发出去。

知新客户端本身按 [ADR-0052](0052-客户端改用OpenAI现行请求格式.md) 与 [ADR-0055](0055-模型调用协议与上限统一.md) 发固定的一组字段和上限，严格校验对它有用：字段打错与上限越界当场暴露，客户端与服务端同时改动。第三方客户端没有这层约定，严格校验拦下的是它用不上的参数，用户看到的是“密钥不能用”。

## 决定

1. 用接入密钥调用 `/v1/llm/responses` 时按放宽的口径处理。代理不认识但在请求里出现的字段删掉再转发；`max_output_tokens` 超出 16 到 32768 时截到边界，写不成数字时退回 4096，截断后的值写回请求体，额度预留与转发都用这个值。

2. 用访问令牌调用时保持原来的严格校验：未知字段与越界上限仍回 400 `invalid_request`，错误码与文案不变。

3. 取值由服务端与来源决定的字段对两种调用都接受但不转发，包括 `prompt_cache_key`、`prompt_cache_retention`、`prompt_cache_options`、`service_tier` 与 `include`。缓存亲和、缓存保留与服务档位属于服务端与来源的配置；`include` 只要求上游多返回推理内容，客户端不保存推理条目，当前来源默认就会返回。

4. 放宽只做在对话接口。嵌入接口仍按原来的字段校验，第三方工具的嵌入请求带什么字段以后另议。

5. 丢弃的字段与被截断的上限不写日志。排查时按请求体与契约对照，需要统计时再增加日志。

## 代价与边界

字段名打错的脚本会得到 200 而不是 400。请求照常发出去，模型按缺了那个字段的方式回答，用户看到的是“回答不对”而不是“参数不对”，排查要多看一步契约。

输出上限被截断之后，客户端以为能拿到更长的回答，实际按 32768 截断。响应里的停止原因仍然是长度，客户端按截断处理即可；上限截断不改变额度预留与结算的口径。

同一个账号的两种凭据按两套口径处理：用访问令牌发错字段当场报错，用密钥发同样的请求会静默通过。联调时要分清正在用哪一种凭据，否则同一个请求在两处的结果不一样。

被丢弃的字段可能带着客户端真正需要的语义，例如 `include` 要求的推理内容与 `service_tier` 要求的服务档位。当前来源默认返回加密推理内容，服务档位由服务端在路由上配置；换来源之后这两项要重新核对。

放宽按凭据判断，不按来源判断。密钥可以调用的五条模型接口里，只有对话接口做了放宽，嵌入与查找仍按严格口径；把两类接口都接进第三方工具的用户会遇到不一样的错误处理。

## 替代方案

全部放宽，访问令牌的调用也不做字段校验。知新客户端发错字段时同样静默通过，联调阶段找不到问题；没有采纳。

全部保持严格，第三方工具按知新的字段表改请求。第三方客户端不接受这种要求，等于把接入密钥限定在能改代码的用户手里；与 [ADR-0063](0063-模型代理接入密钥.md) 的目的冲突，没有采纳。

只放行已知的第三方字段，其余仍然拒绝、上限仍然报错。上一版就是这样做的，同一个客户端仍然在 `max_output_tokens` 上失败；没有采纳。

把未知字段原样转发给来源，由来源决定接受与否。来源不认识这些字段时整次请求失败，错误从“客户端参数不对”变成“来源故障”，重试与换来源都救不回来，排查更远；没有采纳。

## 影响

- 代码：[proxy.go](../../server/internal/llmproxy/proxy.go) 的 `allowFields` 增加放宽模式，`responsesOutputLimit` 增加截断，`Responses` 按凭据是否为接入密钥决定口径；嵌入接口的调用显式传严格模式。
- 契约：[openapi.yaml](../../server/api/openapi.yaml) 的 `/v1/llm/responses` 说明写明两种口径的区别，生成代码随 `oapi-codegen` 重新生成。
- 文档：[server/README](../../server/README.md#模型代理)的模型代理一节写明“内部严、外部松”的边界；本条补充 [ADR-0063](0063-模型代理接入密钥.md) 的调用口径。
- 测试：[proxy_test.go](../../server/internal/llmproxy/proxy_test.go) 覆盖接入密钥放行、未知字段不转发、上限截断，以及访问令牌仍然严格拒绝的两侧。
