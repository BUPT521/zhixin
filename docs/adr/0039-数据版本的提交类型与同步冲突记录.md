# ADR-0039 数据版本的提交类型与同步冲突记录

## 状态

提议

## 日期

2026-11-20

## 背景

客户端的数据版本系统在 2026-11-20 的 `main`（`630b56d`，schema 27）上已经能按提交记录行级净变化、从检查点重建、按代次撤销，也能与云端按提交增量同步。主线成立，但有十四处问题集中在编号、留存、投影与同步四条路径上，其中五处会直接产生错误结果或者丢数据。

提交编号在 `beginCommand` 里分配，只要经过命令事务就占一个编号；没有净变化的写入也占，`WriteResult` 又按占到的编号返回“已提交”，界面因此显示一次并不存在的修改。`clearHistory` 把下一个编号退回 `HEAD + 1`，占过但没有落库的编号会被后来的提交复用。裁剪与清理历史不看同步推送读到哪里，离线期间清理过的提交再也推不到服务端。应用远端提交时不看远端旧值，新增撞上本机已有主键时整行覆盖，更新遇到本机已删的行静默跳过，用户不知道本机哪些修改被覆盖。周期检查点按 `commit.id % 25` 触发，编号会跳号，触发时在写事务里重建整库投影并计算校验值，那一次写入明显变慢。

另外九处分别是：检查点是整库 JSON，每个值包一层 `{"t","v"}`，体积约为原数据的两到三倍；`_pruneOnce` 为了数检查点条数把全部投影读进内存两次，附件回收与附件核对分别解码全部变更明细，两段代码几乎相同；按容量裁剪时保留条数逐次减半，每轮都执行 `VACUUM`；“与当前比较”做两次整库重建，`HEAD` 一侧其实就是当前表；提交类型由中文动作文案兼任；写提交行的代码有两份，投影比较有四个；`RevisionEngine` 一个文件 1734 行；安装采集时删除库里全部非 `sqlite_` 触发器；撤销的业务约束写在数据层，撤销把 `updated_at` 写回旧值，导致同一行之后改过任意一列都不能再撤销。

这些问题不推翻“触发器采集、按提交回放、按代次撤销”的主线。本次改造因此保留主线，只把编号、读取位置、检查点格式、同步冲突与撤销规则改成可以分开验证的六块。

## 决定

提交编号只增不减，只在真正形成提交、或者命令里显式要了回执编号时分配。`beginCommand` 只把 `revision_context.capturing` 置 1，`WriteTransaction.requireCommitId()` 第一次调用时从 `revision_sequence` 预留编号并写进 `active_commit`，`finishCommand` 有净变化时使用预留编号、没有预留时当场分配。没有净变化且没有预留时，序号不动；`WriteResult.changed` 与是否落库一致。清理历史不再回退下一个编号。

提交的类型由新增的 `revision_commit.kind` 决定，取值 `baseline`、`write`、`undo`、`restore`、`import`、`maintenance`、`remote`；`action` 只给人看，撤销判断与界面标签改读 `kind`。提交号之外，`revision_commit` 增加 `byte_length`（这条提交变更明细的字节数）与 `conflict_count`（应用这条远端提交时记下的冲突条数）。

历史的每个下游读者在库里登记读到哪里，记在新增的 `revision_cursor`。会丢数据的读者（同步推送）把 `blocking` 置 1，裁剪与清理历史的下界不能越过它的位置；只会退回全量重建的读者（文本索引、记忆索引）只登记位置，不阻止裁剪。同步位置因此从应用私有目录的偏好文件搬进库：整库恢复时随库一起回去，恢复旧备份得到较小的位置时会把服务端已有的提交再推一次，服务端按请求编号去重，结果不变。

同步仍然是后到覆盖先到，但本机能列出每一处被覆盖的本机修改。应用远端提交时按列做三方比较，把冲突写进新增的 `revision_conflict`：更新遇到行存在、且某列本机当前值既不等于远端旧值也不等于远端新值，记为 `concurrent_update`；更新遇到本机已删的行记 `deleted_locally`，仍跳过写入；新增撞上本机已有同一主键且内容不同记 `insert_collision`；删除遇到本机改过的行记 `deleted_remotely_modified`。冲突记录保存本机值、远端旧值与远端新值，用户可以一键把本机值作为一条普通 `write` 提交写回，这条提交照常推送，在其他设备上就是一次正常的后到覆盖。

检查点改为 `json+gzip` 编码，存在 `payload` 列，另记 `encoding`（`json` 或 `json+gzip`）与压缩前的 `raw_bytes`，校验值仍按解压后的原文计算。写事务里不再生成整库检查点：一次提交落库之后，在独占区之外的空闲时按累计的 `byte_length` 判断是否单独开一个维护事务生成检查点。命名版本只在跨过裁剪边界时才固化检查点。附件回收与核对改读新增的 `revision_asset_ref`：登记每次提交变更明细与每份检查点引用的附件哈希，回收改成一条反连接，不再解码全部变更明细。

六条泳道按文件归属并行，互相只通过阶段 0 定好的接口交互：提交编号与写入结果、历史位置与附件回收、投影与检查点、同步位置与冲突记录、撤销规则、数据版本页。`RevisionEngine` 用 `part` 机械拆分，类定义、字段、构造与表结构缓存留在主文件，其余按读取路径拆到五个 `part` 文件；拆分方式是同库的 `mixin`，公有 API 与调用方不变，每个文件由一条泳道拥有。提交行合并为一个 `_appendCommit`，撤销的行回指字段随提交一次写入，不再事后补 `UPDATE`。

撤销的业务约束由应用层注册：数据层只做通用核对（代次、后续修改、当前值、白名单），预约冲突、学习事项归属与课表三类规则实现 `UndoGuard` 接口，按 `tables` 与 `actionTables` 声明覆盖范围。撤销写回时 `updated_at` 不回到旧值，任何后续写入都会改到的列也不再阻止撤销。

## 代价与边界

服务端的同步协议不改：提交仍然按到达顺序覆盖，冲突记录只在客户端，服务端看不到，也不会替客户端合并。冲突只在应用远端提交时产生；两台设备都离线、之后同时推送时，只有后推送的设备能列出被覆盖的修改。

同步位置搬进库之后，清除历史会使库变小，但已经推送的位置不会跟着回退；从旧备份恢复时位置变小，会把服务端已有的提交再推一次，依赖服务端的请求编号去重。这是有意的取舍，代价是一轮多余的推送。

检查点压缩让读取多一次解压，压缩收益取决于投影里重复文本的比例。空闲检查点让“距最近检查点”的间隔由累计字节数决定，而不是固定条数；多数用户的历史只有约一百条提交，很少触发。命名版本不再立即固化检查点，命名之后、裁剪之前的重建仍从更早的检查点回放。

阶段 0 不改变任何行为：采集、提交、投影与撤销的原有测试全部通过，`kind` 按现有写入路径写对，检查点一律写 `json` 编码，`revision_asset_ref` 与 `revision_conflict` 建表但暂不写入。行为变化随六条泳道分别合入。

schema 从 27 升到 28，按 [ADR-0017](0017-表结构变化仍清空数据.md) 版本不一致即清空重建，不写迁移：检查点的 `projection_json` 改成 `payload` 与 `encoding`，`revision_commit` 增加三列，新增三张表。开发期的旧库在打开时清空，内测数据由团队承担。

## 替代方案

不拆文件，让一个人在 `revision_engine.dart` 上依次改完十四处问题。这样没有跨文件接口，改动顺序自由，但 1734 行的文件每次改动都要读一遍上下文，六块工作无法并行，也无法按文件归属分工；计划里约 18 人日的并行收益全部消失。放弃。

把六块拆成六个独立的服务类，各自持有执行器，由 `RevisionEngine` 组起来。类边界更干净，但仓库、撤销、同步与界面都按 `engine.foldChanges(...)` 这样的形式调用，拆开之后每个调用点都要改，而且这些服务之间要来回传投影与检查点，私有成员的共享反而变复杂。本次采用 `part` 加同库 `mixin`，公有 API 与调用方一行不动，代价是同一份库的成员分散在六个文件里，读代码时要按 `part` 表定位。放弃独立服务类。

把同步冲突交给服务端合并，客户端只接收合并结果。这需要服务端保存每台设备的位置并实现按列合并，同步协议、服务端存储与两端版本都跟着改，远超客户端数据版本的范围；内测阶段两台设备并发修改同一行的机会很少，先在客户端记录、由用户决定是否写回，代价更小。放弃。

给 `op` 与值类型保留字符串，只加一个 `kind` 列。改动最小，但动作文案与类型判断继续混在一起，撤销与界面仍然按中文文案分支，下一次改文案还会改错行为。本次把 `op`、值类型与提交类型都改成枚举，库与数据包里的序列化值不变。放弃。
