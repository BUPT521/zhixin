# ADR-0062 按请求能力筛选路由

## 状态

已采纳（2026-11-24）。落实 [模型调度与回答恢复实施方案](../模型调度与回答恢复实施方案.md) 第 5 节的兼容路由筛选，承接 [ADR-0029](0029-模型来源路由与嵌入代理.md) 的路由配置与 [ADR-0060](0060-一轮回答的预算与按讨论分配来源.md) 的组内选择。

## 背景

同一个对外模型下可以挂多条路由，但它们能做的事并不相同：纯文本模型读不了图片，没有函数调用的模型收到 `tools` 只会报错或编造调用。此前服务端一律把请求发给候选里的第一条，能不能处理交给上游判断，一次带图的提问因此常常先失败一次再换路，用户看到的是一次慢下来的失败；管理员核对过哪条路由支持图片、哪条支持工具，也没有地方记录。方案第 5 节要求每轮先按请求能力排除不兼容的候选，再按主备组选择。

## 决定

1. 路由增加两个能力标记 `supports_tools` 与 `supports_images`，表示管理员按实际调用核对过函数调用与图片输入。标记属于路由而不是来源：同一个来源可能只代理了部分能力。
2. 请求体里 `tools` 非空表示这次要用函数调用；`input` 条目的 `content` 数组里出现 `input_image` 表示这次要读图片。服务端据此构造要求，从候选里排除对应标记为假的路由，其余顺序、会话分配、冷却与试探规则不变。
3. 没有任何路由具备所需能力时，服务端不发出上游请求，直接回 502 `upstream_failed`，说明缺的是图片输入还是函数调用；带图片的请求不会退化成只发文字，函数调用请求也不会退化成普通回答。
4. 能力标记在管理后台按路由用两个复选框维护，默认勾选；保存路由时整条替换，与现有路由配置的保存语义一致。接口省略这两个字段时按支持处理，旧版后台脚本与旧客户端因此不受影响。

## 代价与边界

标记是人工核对的结论，配错时要么把请求发到读不了它的来源上，要么在本地拒绝本来能处理的请求；默认勾选意味着不核对就没有保护，上线后要按方案第 5 节用纯文本、图片、函数调用、流式与上下文长度各核对一次再取消不支持的那一项。能力筛选只影响候选集合，不改变重试与结算：候选被排除时不做健康计数，也不消耗尝试次数。图片请求在没有视觉路由时直接失败，页面按上游失败提示重试，这一步的用户体验与“上游均不可用”相同，是否需要单独的提示与降级文案留到批次验收时一起定。

## 替代方案

- 按失败结果自动学习能力：一次内容过长的 400 或一次限流会被误判成“不支持图片”，之后这条路由再也不会接到图片，没有采纳。
- 按来源或模型名推断能力：上游命名不统一，同一来源换一个模型名能力就可能变，没有采纳。
- 由客户端声明这次请求需要的能力：客户端不知道服务端配置了哪些路由，声明只能靠猜，还会把配置口径带到客户端，没有采纳。
