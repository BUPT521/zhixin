# ADR-0087 结算之后的核销申请待办

- 状态：已采纳（2026-11-27，服务端同日实施）；新增 `llm_charge_pending` 表（纯新增表，不重建库），补充 [ADR-0067](0067-聊天额度改走即刻收积分包.md) 与 [ADR-0073](0073-余额副本的快照、刷新与放行原因.md) 的核销申请口径
- 日期：2026-11-27

## 背景

一次扣费分两步落库。第一步是结算：`pg.(*Store).Settle` 在一个事务里把这次预留转成已结算用量，记进 `llm_usage.tokens`。第二步是申请核销：事务提交之后调用 `chargeNowPay`，读出当天已结算的计费 token，减去免费额度，把超出的部分交给核销执行器，执行器再减去当天已经申请过的积分，只写差额流水。

两步之间没有持久的约束。`chargeNowPay` 读当天额度、读已结算用量、写核销流水，任何一步失败都只记一条日志就返回；进程在提交之后、申请之前退出也一样，`llm_usage` 里已经有这一天的用量，`nowpay_charge` 里没有对应的流水。这段用量唯一的补救是当天之后还有一次结算：`chargeNowPay` 按当天累计用量重算差额，把漏掉的补上。当天最后一次结算落在这两步之间失败，或者它本身就是这一天的最后一段用量，之后不会再有结算写这一天；跨过自然日以后，这一天的用量就永远不会被申请核销。

后果有两层。计费上，这一段付费用量收不到钱；放行上，余额副本没有扣掉它，可用积分比实际多，用户可以在别的请求里把同一笔积分的额度再用一次（[ADR-0073](0073-余额副本的快照、刷新与放行原因.md) 的可用积分口径）。

## 决定

`llm_usage` 之外新增 `llm_charge_pending`，一行是一个账号在一个自然日还没有申请核销的计费 token。结算事务在提交之前把这一天的累计超额用量写进这张表，与用量在同一个事务里落库；同一天的多笔结算取较大的那个，后续结算的累计量覆盖前面的，早到的记录不会把数改小。写的时候用同一天已经结算的用量减去免费额度，在途预留不算在内（[ADR-0071](0071-核销只读已结算用量与额度用完的原因.md)），与结算之后那次申请的取数口径相同。

结算之后那次申请保留下来，作为快路径：绝大多数请求在提交之后几毫秒内就把差额流水写好了。待办由每十分钟一次的补查收尾，处理创建超过五分钟的记录：当天已申请的积分如果已经追上了待办折成的积分，删除待办；没有追上的，按待办里记下的用量再申请一次，执行器照旧只申请余额覆盖的那一部分，剩下的留给下一轮，用户补上积分之后收齐；超过七天还没有收齐的，删除待办并记一条 `drop the pending charge that is still unpaid` 日志，交给人工核对。

同一个账号同一天的待办只有一行，主键是 `(user_id, day)`，补查按 `created_at` 取最早的一批。补查与保留期沿用即刻收的十分钟一轮，批五十条，宽限五分钟。服务启动时，配了即刻收的实例会检查这张表：缺表直接退出，由自动部署回滚到上一份可执行文件，因为结算事务会写它，缺表时每一次结算都会失败。

## 代价与边界

超过免费额度的每一次结算都会多写一行待办，补查每轮还要为它读一次当天已申请的积分；正常时待办在一轮之内被收齐并删除，这张表接近空的。这笔开销与请求量成正比，只在收费的实例上出现。

待办记的是结算当时算出的金额，不随后台调整额度重算。管理员在同一天调高额度之后，待办里的金额可能高于按新额度重算的结果，差额已经由结算之后的快路径申请过，补查只会在没有收齐时再申请，不会重复；跨日的补查按当时记下的金额收，这被视为已经发生的债务。

待办最多保留七天。七天之后仍然收不齐，说明用户一直没有补充积分，继续每十分钟申请一次没有意义；这一段用量从此不再计费，余额副本仍然按未扣减的余额放行，与修复前一样，区别是日志里留下了金额与账号。

补查看的是当天已申请的积分，不看流水是否成功。一笔核销在补查之后才被判失败（积分不足、即刻收返回失败）时，待办可能已经被删除，这一段用量就要等下一次结算重建待办；跨日之后不再重建，这是这套机制没有覆盖到的一种顺序，记录在这里。

## 替代方案

补查直接按 `llm_usage` 重算，不建待办。没有采纳的原因是重算要知道每个账号当天的免费额度：额度覆盖值只有一份、按账号而不是按天保存，重算历史日期只能用现在的值，改过额度的账号会算错；不筛账号地扫最近几天的用量，则要在每十分钟一次的任务里遍历所有活跃账号，而绝大多数账号当天没有超额。

把核销申请放进结算事务，一次提交完成两步。没有采纳的原因是核销申请有自己的事务与按账号的锁（[ADR-0073](0073-余额副本的快照、刷新与放行原因.md)），它读余额副本、写流水、排核销队列；把它并进按天串行的结算事务会颠倒两把锁的顺序，也会让余额副本缺失或流水写失败变成整个结算失败，而用量已经交付。

只靠下一次结算的累计差额补。这就是修复前的做法，也是这条 ADR 要解决的问题：当天最后一次结算之后再没有结算，跨日就没有人了。
