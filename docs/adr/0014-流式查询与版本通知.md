# ADR-0014 流式查询与版本通知

## 状态

已采纳。2026-11-14 提出，2026-11-16 实施完成：版本引擎在提交收尾带回这次改到的表，`GuardedDatabase` 在事务提交之后、独占区释放之前发布一次，应用服务提供跟随写入更新的整屏读法，页面用 [LiveView](../../app/lib/ui/live_view.dart) 订阅，写入、撤销、导入与换库之后都不再手动重读。整库恢复、清空、导入与单项撤销按全部表补发一次，换连接之后订阅继续有效。

与 2026-11-14 的提议有两处不同，实施理由写在“实施结果”。第一，通知由版本引擎自己发出的表变更流承载，不再调用 drift 的 `notifyUpdates`，也不依赖 drift 的 `.watch()`：生成语句在回滚时同样会派发自己的更新，与“没有净变化不通知”这一条无法同时成立。第二，页面订阅一个“整屏读法”的流，而不是逐条查询各订阅一次：一次提交往往同时改到几张表，一屏数据来自几个查询，整屏重读一次比逐条拼装更简单，回填的也一定是同一时刻的数据。

## 日期

2026-11-14（实施结果补记于 2026-11-16）

## 背景

页面在写入之后手动重读数据，`await _load()` 在全项目有 62 处，`plan_page.dart` 一个文件里有 18 处，`setState` 共 274 处。[ADR-0007](0007-首屏预读缓存与失效.md) 用 `dataVersion` 与进程内提交序号判断首屏预读是否失效，覆盖恢复、清空、导入、撤销与每日截止小时变化，普通新增、编辑、删除则靠各页面自己记得重读。这套做法有两个已知问题：漏掉一处重读，页面就停在旧数据上；把重读加满，每次写入又会重复查询已经读过的结果。

drift 的流式查询提供同一种能力：查询以 `.watch()` 订阅，相关表一有写入，drift 重跑查询并推送新结果。提出这条 ADR 时（2026-11-14）本项目的写入多数经原生 SQL 进入，drift 不知道它们改了哪些表，订阅流收不到更新；版本引擎知道，因为每次提交收尾时净变化已经按表归类。此后 [ADR-0011](0011-仓库查询改用drift生成代码.md) 把仓库读写搬进生成代码，生成语句会自己派发 drift 的更新，前提因此变了：drift 知道写入，但它在回滚时也会派发，无法满足“没有净变化的写入不通知”。

评估见 [轮子与技术选型评估第 2.4 节](../轮子与技术选型评估.md#24-用流式查询代替手动重读)。

## 决定

1. [RevisionEngine.finishCommand](../../app/lib/data/revisions/revision_engine.dart) 在合并净变化之后，把这次提交改到的每一张业务表连同 `revision_commit`、`revision_change`、`revision_ref` 三张版本元数据表交给调用方；[GuardedDatabase](../../app/lib/data/db/guarded_database.dart) 在事务提交成功之后、独占区释放之前把这一批表发布出去。回滚的写入不发布，没有净变化的写入不形成提交也不发布。历史页与安排页的回执读版本元数据表，所以每次提交都带上它们。
2. 整库恢复、导入、清空与单项撤销整份改动数据：恢复与导入在事务提交之后按全部业务表发布一次，撤销与恢复走第 1 条的命令收尾，清空与换库由应用根在换库之后按全部表补发。
3. 应用服务的读法提供跟随写入更新的版本（`watchXxx`），经 `ServiceRuntime.watch(tables:, read:)` 取得；读法自己声明读到的表，通知与它有交集才重读。仓库层的普通读写不变，流式读法只是同一条读法的第二种触发方式。
4. [LiveQueries.watch](../../app/lib/data/db/live_queries.dart) 对一次订阅只回填最新一次读取的结果：读取经 `DatabaseGate` 的共享访问执行，与恢复、清空的独占区互斥；通知带上发出时的执行区，重读回到那里跑完，正式运行只有一个事件循环，页面测试里写入在真异步区、重读也在真异步区，不会出现“读取等 pump、写入等读取”的互等。
5. 页面用 [LiveView](../../app/lib/ui/live_view.dart) 订阅整屏读法：数据到达就重建，首读显示占位，出错保留上一份结果并提示一次，回填等路由与页签动画结束（ADR-0007 的时序约束保留在订阅处）。页面在筛选、选周、页签变化时换一条新的流，同一条件不重复订阅；分页（“继续读取”“更早的消息”）仍按页命令式读取，只把第一页或整屏改成订阅。
6. 状态管理不引入 Riverpod 一类框架，`LiveView` 加现有的 `AppScope` 已经够用。
7. 先做数据层机制，再在“记录”页试做，确认与 `DatabaseGate` 的读写协调、恢复时的连接替换都不冲突之后，按同一写法规格推到其余页面。

## 实施结果

| 层 | 现行做法 |
|---|---|
| 提交收尾 | `finishCommand` 用输出参数带回改到的表与版本元数据表，`GuardedDatabase` 在提交之后、独占区释放之前发布；回滚与无净变化的写入不发布 |
| 通知流 | `TableChanges` 广播“表集合 + 发出通知时的执行区”；恢复与换库由 `connectionReplaced` 按全部表补发 |
| 重读 | `LiveQueries.watch` 只回填最新一次结果，读取走共享访问，并以新读者身份登记，后面排队的写入等它读完 |
| 关库 | 关闭前停止发起新的重读，并直接关掉连接、不再等停在其他执行区里的读取；否则 drift 会把连接重新打开，测试收尾时临时目录删不掉 |
| 应用服务 | `PlanService.watchWeek/watchGoals/watchDoneItems`、`LearningService.watchRecords/watchQuestion`、`DiscussionService.watchConversation`、`MaterialService.watchList/watchMaterial/watchPages`、`ContinueService.watchHome`、`MemoryService.watchMemories`、`MemoryProposalService.watchQuestions`、`StudyPlanService.watchScreen`、`DataVersionService.watchOverview`、`SettingsService.watchSettings` |
| 页面 | 现在、记录、安排、讨论、学习、材料列表与详情、记忆、记忆建议、系统学习、数据版本、设置、容量面板都改为订阅；保存、删除、撤销、导入、恢复与跳转返回之后的 `_load()` 全部删除；`plan_week_reader.dart` 的请求编号与过期结果判断随订阅下线 |
| 保留 | 插件页与人格页读写的是不形成提交的 `app_meta`，仍用 `dataVersion` 监听在整库恢复与清空之后重读；长列表分页仍按页读 |

实施中确认的几处取舍：

- 不调用 drift 的 `notifyUpdates`。生成语句自身会派发 drift 的更新，同一笔写入会因此通知两次；而且生成语句在回滚时也会派发，与“回滚的写入不通知”冲突。版本引擎在提交收尾发出的表变更流是唯一来源。
- 通知按表发送，一次提交改到的表与版本元数据表一起发。页面因此可能收到与自己无关的刷新，这是表级粒度已知的代价。
- 整屏读法而不是逐条查询仓库的流式方法。安排页的一周、记录页一屏、讨论页一条记录都要把几个查询拼在一起，逐条订阅还要在页面里合并，反而比一次读完整屏更难维护。

## 代价与边界

- 通知按表发送，粒度比页面需要的粗：一张表被写入，所有读这张表的读法都会重跑。本项目的页面数量少，查询结果集小，这个粒度可以接受；如果后续出现多个页面读同一张大表，需要再细化到按行或按查询的通知。
- 一次提交通常只让读法与它交叉的页面各重读一次；页面切走之后订阅仍然保留，后台写入也会触发重读，这是订阅比手动重读多出来的开销，换来的是切回来立刻是最新数据。
- 安排页的“AI 的改动”读的是版本元数据表，它跟随业务表写入更新；只改版本表的操作（裁剪历史、清理历史、命名版本）不会让这一列表刷新，要等下一次业务表写入或下拉刷新。数据版本页订阅了版本元数据表，不受这一条影响。
- 没有净变化但仍然写入业务行的命令不通知，例如把字段写成与现值相同的值。这种情况下界面内容不变，跳过通知不会让页面停在旧数据上。
- 恢复时执行器会被替换：`connectionReplaced` 让通知与订阅跟着新连接走，并按全部表补发一次；恢复流程本身仍在独占区里完成，页面不会读到旧连接。
- 页面从手动重读改成订阅之后，加载、错误与空状态改由 `LiveView` 与各页面的 `builder` 表达，测试里等待页面更新的方式从“等一次 `_load`”改成“等一次推送”；本轮为每个页面补了“页面之外的提交会出现在页面上”的用例。
- 不形成提交的写入（`app_meta` 里的设置、插件启停与人格配置）没有表通知，相关页面仍靠 `dataVersion` 或换流刷新，这是本轮有意保留的边界。
- 这一项依赖 ADR-0011 的生成代码，实施顺序排在仓库迁移之后；本次实施也没有改动 `.drift` 文件与表结构。

## 替代方案

- 继续用 `dataVersion` 加提交序号，要求每个写入入口都推进一次版本号。没有采纳的原因是这一点与 ADR-0007 已经选择的“提交收尾统一推进”重复，而且页面仍需自己决定何时重读。
- 让每次写入都通知全部表。没有采纳的原因是通知范围与代价都最大，页面会收到与自己无关的刷新。
- 写入路径全部改写成 drift 的 Dart DSL，由 drift 自动推断受影响的表。没有采纳的原因是版本引擎、备份与恢复依赖原生 SQL 与触发器，ADR-0004 已经否掉了改写。
- 直接用 drift 的表更新通知（`notifyUpdates` 与 `tableUpdates`）驱动页面。没有采纳的原因写在“实施结果”第一条：生成语句在回滚时同样派发，且同一笔写入会通知两次，与“没有净变化不通知”“回滚不通知”两条冲突。
- 逐条查询各订阅一次、页面里拼装多路结果。没有采纳的原因是页面要维护多路订阅的合并与去重，而一屏数据本来就来自同一时刻的几个查询，整屏重读一次更简单。
- 引入 Riverpod 一类状态管理框架承载订阅。ADR-0014 提出时已经否掉，实施后仍不需要：`LiveView` 只做订阅与回填，状态留在各页面。
