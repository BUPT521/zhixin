# 0.4.0 发版说明

> 0.4.0 于 2026-11-27 发出，是 0.3.0 之后第一份内测包，把日程管理下线与安排页的精简合成一次发出。本版按 [ADR-0002](adr/0002-本地数据不做迁移.md) 清空客户端各空间的本机库，服务端表结构不变、账号与登录保留；schema 32 的云端同步历史在发出之前清空，客户端按空同步起点重新上传基线。安装包由 Actions 在 `9187ab6` 上构建，arm64 单包 73,807,399 字节，SHA-256 为 `67f95662c4c020e2425a85b5579ec2c3bb738eb451fd931b9c9d1f674d6e1af5`，同时放在 GitHub Release（标签 `v0.4.0`，附同名的 `.sha256` 与 `.sig`）与下载地址 `https://zhixin.chensiyuan.work/downloads/zhixin-0.4.0.apk`，发布清单的 `min_version` 同为 0.4.0。

## 1. 这次清空了哪些数据

| 位置 | 清空的内容 | 保留的内容 |
|---|---|---|
| 客户端 | schema 32 及更早的本机库：学习记录、讨论、材料、题目与尝试、记忆、提交历史、命名版本与本机设置，在第一次打开时随旧库清空重建 | 账号、登录状态、服务地址、设备标识与模型代理密钥在 Keystore 与 `cloud.json` 里，不在库里，升级后照常使用 |
| 服务端 | schema 32 的同步提交、提交去重记录、设备名册、命名版本与同步位置。发出之前库里是 1 个账号、5 条提交、2 台设备、0 个命名版本、0 份备份，2026-11-27 按此清零 | 账号、登录方式、会话、额度、模型来源与路由配置不变；附件索引与对象存储 `attachments/` 前缀下的字节没有删除 |

客户端按 [ADR-0002](adr/0002-本地数据不做迁移.md) 处理，不写迁移：本机空间库只要不是 schema 33 就在打开时清空重建，旧预约、课表以及同库的学习记录、历史与设置一并清空，两类数据包与版本库备份只接受 schema 33，其他版本在替换之前被拒绝、原数据保留。

服务端这次不做整库重建，因为表结构没有变化；清掉的只是同步历史，原因是 schema 32 的提交与快照里可能带着 `schedule_block` 与 `timetable_entry` 的行，新客户端按旧位置拉取时会重放进 schema 33 里并不存在的表（[ADR-0090](adr/0090-移除日程管理.md)）。附件索引与对象存储里的字节保留，新客户端不再引用它们，账号之后重新上传材料时会按哈希补齐；这次不对它们做删除，避免在发版窗口里动不可恢复的对象。

## 2. 升级之后要做什么

1. 直接覆盖安装 0.4.0，不需要重新注册，账号、登录方式与额度都保留。
2. 升级之前要留下的内容请先导出为文件。旧数据包与整库备份都不能导回 0.4.0，恢复入口只接受 schema 33；升级之后本机库在第一次打开时清空重建，没有导出的本机记录无法找回。
3. 打开之后登录原账号，同步按空起点重新上传本机基线，云端旧历史已经清零，不会把 0.3.0 的旧表重放进新库。
4. 同一账号的其他设备一起升级。服务端只接受 schema 33 的客户端，0.3.0 与新服务端互不相认，`/readyz` 报告的 `schema_version` 可以用来判断两端是否同步。

## 3. 这一版改了什么

- 日程管理下线：删除预约、固定课表、可用时段预算与排程冲突处理，取消预约提醒、日程导出与课表导入；“安排”只保留事项与目标两个页签，默认显示未完成事项，已完成按页展开，标题栏提供查找（[ADR-0090](adr/0090-移除日程管理.md)）。
- 下一步建议改为“立即开始”或“保存为事项”两个动作，保存时可以选择目标，也可以留作独立事项；事项保留截止日期与预计用时，“现在”的“接下来”按截止日期与估时给出提示。
- 系统学习从“现在”进入独立的计划列表，列表显示进度与下一步；打开步骤仍回到原题、讨论或材料页，完成这一步推进计划进度。
- AI 的写入在原对话里给出回执并提供撤销，数据版本页可以单独筛选 AI 改动并查看可用的撤销操作。
- 客户端 schema 升到 33，删去 `schedule_block` 与 `timetable_entry` 两张表，业务表结构与数据包格式随之变化（[01](01-ER数据模型.md)）。
- 服务端 `ClientSchemaVersion` 同一次提交改成 33，同步推送与 `GET /v1/sync/head` 都按 33 校验。
- 服务端启动时自检生产配置：发信地址、随机密钥、来源密钥与模型目录缺项时拒绝启动，不再带病监听。

## 4. 这一版还没做的

- V1–V11 的模拟器验收仍由缪鹏按 [02 第 8 章](02-产品与交互.md#8-验收标准)执行，本版发出之前没有做完，结果在发出之后补进 02 第 8 章，补出的缺陷照常登记 Issue。
- 首次使用引导、人格插件与分享到知新按 [03 第 3 节](03-团队分工与协作.md#3-交付节奏)排在 M3，本版不包含。
- 记忆的增改删工具、写入时合并近似条目与整理建议仍按[长期记忆整理方案](长期记忆整理方案.md#6-实施顺序)的顺序推进。

## 5. 验证与已知问题

客户端的格式检查、`flutter analyze`、生成代码比对与全量单元测试在推送之前通过：`dart format` 487 个文件没有改动，`build_runner` 重新生成之后与提交一致，`flutter analyze` 没有报出问题，`flutter test` 1269 个用例全部通过。服务端的 `gofmt`、`go vet` 与 `go test ./...` 同样通过。

切换当天按运维手册 §4.13 执行：先 `pg_dump` 全量备份到 `/opt/zhixin/backup/`，再清空同步历史，然后部署 schema 33 的服务端、上传安装包并更新发布清单。`/readyz`、`GET /v1/app/releases` 与用测试账号从空同步起点推送的结果记在[运维手册 §4.13](../server/运维手册.md#413-客户端-schema-33-切换)。

已知问题有两条。第一，从服务端换成 schema 33 到安装包发到下载站之间有一段窗口期，这段时间里装着 0.3.0 的设备同步会返回 400，窗口结束之后覆盖安装即可恢复，没有数据损失。第二，服务端在 15:37 到 16:04 之间因为核销补查的两列没有先加到生产库而停机，与这一版无关，处置记录见[运维手册 §4.11](../server/运维手册.md#411-即刻收积分包的上线与回滚)。
