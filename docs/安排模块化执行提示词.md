## 实施顺序

1. 提取周视图组件。由组件持有并释放 `EventController`，根据收到的周数据更新事件，保留当前 Flutter `Material` 容器、展开与收起、横滑及事件点击。周视图通过数据和回调接收已加载周、预约与课表，并报告用户选周或点击事件，业务导航和写入交给调用方。
2. 收拢安排页的读取状态。用同一个选周入口处理上一周、下一周、横滑与回到本周，刷新以当前目标周为准。读到最新结果后，一次更新已加载周及其数据，标题、预约列表、课表事件都以这份结果为准。过渡结束后回填前再次确认请求仍有效，避免旧成功结果、旧错误或旧分页结果写回。使用现有的过渡等待逻辑和时间口径。
3. 收窄依赖与验证业务写入。安排页通过 `PlanService`、`CapacityService` 读取和修改对应数据，沿用已有的冲突检查、命令事务和提交回执。在现有架构测试里添加针对周视图的规则，把组件对 `AppScope` 和具体仓库的直接导入判为测试失败。工作留在现有 Flutter 工程内，共用现有 SQLite、版本事务和数据包格式。

## 验收与交付

- 保留周视图的现有界面用例，再用可控的异步结果模拟两次请求反序完成。先交付新周，再返回旧周，确认标题、日历、预约和课表仍属于新周。验证时还应确认刷新结果与当前请求一致。
- 复核已有的预约与改期用例，确认固定安排冲突时写入被拒绝，整组顺延中任一条冲突时整组保持原样，成功的一次改期或整组顺延只生成一条提交并可按原范围撤销。沿用已有场景与断言，为现有测试未覆盖的行为补回归用例。
- 在 `app/` 先运行受影响的界面、应用服务与架构用例，提交前按仓库约定执行 `dart format --output=none --set-exit-if-changed lib test`、`flutter analyze` 和 `flutter test`。按提交约定分步提交、同步和推送，最后给出实际改动、验证结果、提交链接与仍待验收的事项。
