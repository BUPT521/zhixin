## 1. 结论

现有动效的设计口径是对的，卡顿主要来自实现层面的四件事，按影响排序：

1. **切栏动画逐帧重绘整页**。`FadeIndexedStack` 每帧重建 `Opacity` 与 `Transform.translate`，两者都会让整栏子树重新绘制；而且切栏那一帧三栏同时重建、新栏同时发起读取，读完又在动画中途触发第二段淡入。
2. **动画与数据读取挤在同一时间窗**。三栏的 `didUpdateWidget` 在 `isActive` 变真时立刻 `_load()`；记录页切到“材料”时 `MaterialList` 整棵重建并重新读取。结果回来的那一帧正好落在 200–260ms 的动画里。
3. **几处“看起来便宜”的实现在逐帧做布局或开离屏层**：输入区聚焦时边框 1→1.5px 改变了 `Container` 的内边距，整个输入区重新布局并有半像素抖动；`ExpandReveal` 与 `StreamingHint` 用 `Opacity` 组件做逐帧透明度；记录页两层 `FadeIn` 嵌套，切换时叠两层透明度。
4. **流式回答每个分片整段重解析 Markdown**。回答越长，每次更新越贵（总量近似平方增长），长回答后半段贴底滚动明显发涩。

这些都能在不改视觉的前提下修掉。建议分三批：P0（一天内，收益最大）、P1（两到三天）、P2（建立度量与防回退）。

## 3. 诊断依据（为什么这些地方会掉帧）

**`Opacity` 组件 与 `FadeTransition` 的差别。** 每帧给 `Opacity` 一个新值，`RenderOpacity` 会标记重绘，整棵子树重新录制绘制指令；`FadeTransition` 对应的 `RenderAnimatedOpacity` 只更新合成层的透明度，子树不重画。`Transform.translate` 同理：每帧新矩阵会让子树重画，除非子树自己是重绘边界。底栏切换时这棵子树就是整页，这是本方案里收益最大的一处。

**透明度本身要开离屏层。** 0 与 1 之间的透明度需要把子树先画到离屏缓冲再合成，面积越大越贵。整页淡入无法避免这一层，但可以缩短它存在的时间（透明度在前 70% 时间里走完，之后层自动撤掉），并保证层里的内容不必每帧重画。

**IndexedStack 不会停掉隐藏栏的动画。** 隐藏栏里的转圈、生成中三点仍然每帧 `build`，只是不画出来。

**动画与 `setState` 重叠。** 动画单帧预算在 60Hz 下是 16.7ms，120Hz 下是 8.3ms。切栏第一帧要同时做三栏 `build`、新栏发起读取；读取完成那一帧要重建整个列表并触发 `FadeIn` 重新播放。两件事任何一件超出预算，用户看到的就是“滑到一半停一下”。

**布局型动画在长列表里会传播。** `Align(heightFactor)`、`AnimatedSize` 每帧改变自身高度，`ListView(children: [...])` 里排在后面的所有项都要重新排位。项不多时没事；“已完成”展开、计划组展开这种可能几十项的地方就会出现。

## 4. 优化方案

### P0：切栏与公共动效组件（预计 1 天，收益最大）

**P0-1 重写 `FadeIndexedStack`：只更新合成层，隐藏栏停 Ticker。**

结构保持不变（每栏同一层包裹，避免切栏丢状态），改三点：透明度用 `FadeTransition`；位移放在 `RepaintBoundary` 外面，让整栏内容只录一次；非当前栏包 `TickerMode(enabled: false)`。

```dart
class _FadeIndexedStackState extends State<FadeIndexedStack>
    with SingleTickerProviderStateMixin {
  late final AnimationController _controller =
      AnimationController(vsync: this, value: 1);
  // 透明度在前 70% 走完，之后离屏层撤掉，剩下的时间只做位移收尾。
  late final Animation<double> _opacity = CurvedAnimation(
    parent: _controller,
    curve: const Interval(0, 0.7, curve: Curves.easeOut),
  );
  late final Animation<double> _move =
      CurvedAnimation(parent: _controller, curve: const ZhixinMotion().move);
  // didUpdateWidget / dispose 与现在相同（dispose 里一并释放两个 CurvedAnimation）。

  @override
  Widget build(BuildContext context) {
    final rise = const ZhixinMotion().rise * 1.5;
    return IndexedStack(
      index: widget.index,
      children: [
        for (var i = 0; i < widget.children.length; i++)
          _TabLayer(
            active: i == widget.index,
            opacity: i == widget.index ? _opacity : kAlwaysCompleteAnimation,
            move: i == widget.index ? _move : kAlwaysCompleteAnimation,
            rise: rise,
            child: widget.children[i],
          ),
      ],
    );
  }
}

class _TabLayer extends StatelessWidget {
  // 构造参数略
  @override
  Widget build(BuildContext context) => TickerMode(
    enabled: active,
    child: FadeTransition(
      opacity: opacity,
      child: AnimatedBuilder(
        animation: move,
        // 子树放进重绘边界：动画期间每帧只移动这一层，不重画页面内容。
        child: RepaintBoundary(child: child),
        builder: (context, child) => Transform.translate(
          offset: Offset(0, (1 - move.value) * rise),
          child: child,
        ),
      ),
    ),
  );
}
```

`TickerMode` 关掉后，隐藏栏里的 `FCircularProgress`、`StreamingHint` 会暂停而不是销毁，回到该栏时继续。`motion_test.dart` 已经通过 `FadeTransition` 取透明度，测试辅助函数不用改；补一条“非当前栏 `TickerMode` 为假”的断言。

**P0-2 `FadeIn` 与 `ExpandReveal` 同样处理。**

`FadeIn`：位移部分的子树包 `RepaintBoundary`，透明度保持 `FadeTransition`。`ExpandReveal`：把 `Opacity(opacity: …)` 换成 `FadeTransition(opacity: CurvedAnimation(parent: _controller, curve: Curves.easeIn))`，高度部分可以直接换成框架自带的 `SizeTransition(sizeFactor: …, axisAlignment: -1)`（与现在的 `ClipRect + Align` 等价，少维护一段代码），内容同样包 `RepaintBoundary`。收起后移出树的逻辑保留。

**P0-3 输入区聚焦描边不改布局。**

边框宽度保持 1.5 不变，未聚焦时把描边色调成与 `outline` 视觉等重的颜色（或在外圈用 `foregroundDecoration` 画聚焦环）。这样 `AnimatedContainer` 只插值颜色，不再逐帧重新布局整个输入区，文字也不再跳半像素。如果设计上坚持 1px 与 1.5px 的粗细差，改用 `CustomPaint`/`foregroundDecoration` 画描边，让它不参与 `padding` 计算。

**P0-4 记录页去掉嵌套淡入。**

`records_page.dart:326` 外层 `FadeIn(trigger: (_tab, _loading))` 与 `:454` 内层 `FadeIn(trigger: _shownFilter)` 同时存在时，切换筛选只需要内层；切页签只需要外层。把外层的 trigger 收窄为 `_tab`，并保证首读完成只播一次（`_loading` 由真变假时），避免一次读取连播两层。

### P1：把“读取”和“动画”错开（预计 2–3 天）

**P1-1 切栏先动画、后读取。**

现在 `NowPage / RecordsPage / PlanPage` 在 `didUpdateWidget` 里一看到 `isActive` 变真就 `_load()`。建议由 `FadeIndexedStack` 提供一个“切换已落定”的信号，页面等它落定再读：

```dart
// motion.dart：对子树公开当前栏动画，页面可以 await 它结束。
class TabTransition extends InheritedWidget {
  final Animation<double> animation;
  static Future<void> settled(BuildContext context) { /* 已完成则立即返回，否则等 AnimationStatus.completed */ }
}

// 各页 didUpdateWidget：
if (!oldWidget.isActive && widget.isActive) {
  TabTransition.settled(context).then((_) { if (mounted) _load(); });
}
```

读取本来就是异步的，晚 260ms 发起用户感知不到，但动画全程不会再被结果回填打断。同时，已有数据时切回来不要再显示转圈或重播 `FadeIn`：先显示上一份内容，读完后静默替换（`now_page` 的“继续上次”已经是这个思路，`records_page` 与 `plan_page` 对齐）。

**P1-2 切栏时隐藏栏不重建。**

`HomeShell._open` 的 `setState` 会让三栏都收到新的 `isActive`，三个页面的 `build` 都在切栏第一帧跑一遍。把 `isActive` 改成从 `ValueListenable<int>`（当前栏下标）读取，页面在 `initState` 里监听它、只在自己变为当前栏时做事，`HomeShell` 切栏时不再 `setState` 三栏的构造参数。`dataVersion` 的 `ValueListenableBuilder` 同理，下沉到各页内部监听，而不是包住整个 `FScaffold`。

**P1-3 页签内容常驻，切换只换显示。**

记录页“学习记录 / 材料”、安排页四个页签都用 `switch (_tab)` 现建列表。首次进入某页签后把它常驻（与底栏同一套 `FadeIndexedStack`，或 `IndexedStack + TickerMode`），切回来时不再重建、不再读取，滚动位置也一并保住。`MaterialList` 的 `GlobalKey` 本来就是为了保状态，常驻之后它才真正生效。内存开销是两到四个列表，可以接受。

**P1-4 长列表改为惰性构建，展开动画只作用于一个 Sliver。**

`now_page`、`plan_page` 的主体是 `ListView(children: [...])`，所有段落一次性建出来。改成 `CustomScrollView` + 若干 `SliverList.builder`：

- “已完成”“已暂停计划”这类可展开的组，展开时用 `SliverAnimatedList` 逐项插入，或在一个独立 Sliver 里做 `SizeTransition`，后续段落只在 Sliver 层面整体平移，不逐项重新排位；
- 列表项 `itemExtent` 无法固定时，至少给 `prototypeItem` 或保持默认的 `addRepaintBoundaries: true`。

`plan_page.dart:1144` 的 `AnimatedSize` 一并改为上述做法，去掉逐帧整组布局。

**P1-5 统一页面路由过渡。**

所有 `MaterialPageRoute` 换成一个 `zhixinRoute<T>(WidgetBuilder)`，过渡用 `ZhixinMotion` 的时长与曲线：进入时新页淡入 + 从右侧 24–32px 推入，旧页不缩放（缩放类过渡要给整页做快照，也不符合“不缩放”的口径）；`allowSnapshotting` 保持默认以便框架在过渡期间用快照；减少动态效果时 `transitionDuration` 为零。保留系统返回手势：iOS 用 `CupertinoPageTransitionsBuilder` 的手势包装，Android 用预测性返回。实现上也可以只在 `MaterialApp` 的 `theme.pageTransitionsTheme` 里统一配置，页面代码不动。

### P2：流式正文、细节与度量（预计 2 天，可与 P1 并行）

**P2-1 流式 Markdown 增量渲染。**

两步，第一步就能解决大部分问题：

1. **按帧合并分片**：`_streamingText.value = text` 改为“记下最新文本，若本帧未排过则 `scheduleFrameCallback` 时再赋值”，网络分片再密，正文每帧最多更新一次；如果仍然吃紧，节流到 50–80ms 一次，肉眼看不出差别。
2. **只重排尾部**：把流式文本按空行切成段（注意代码块围栏内不切），已经完整的段交给各自独立、带 `ValueKey(段序号)` 的 `MarkdownText`，它们的输入不变就不重建；只有最后一个未完成段随分片重新解析。每段外包 `RepaintBoundary`。完成态仍用整段一次渲染，保证与历史消息一致。

**P2-2 `StreamingHint` 改为纯绘制。**

三点用 `CustomPainter(repaint: _controller)` 画，透明度写进画笔颜色，外包 `RepaintBoundary`。这样每帧只重画 15×5 的区域，不再重建组件，也不再让整个气泡跟着重画。

**P2-3 分段滑块的小修。**

`ZhixinSegmented` 自身问题不大，两处顺手改：选中态的 `fontWeight` 500→600 会改变字宽，在等分模式下文字会轻微抖动，可以改用固定字重、只变颜色，或保留字重但让标签在 `Center` 内以较粗字重预留宽度；滑块的阴影随 `AnimatedAlign` 一起移动，没问题，保持。

**P2-4 建立度量，防止回退。**

1. **手工检查口径**：一律在 `--profile` 模式、真机（至少一台中端 Android + 一台 120Hz 设备）上看，调试模式的卡顿不作数。打开 DevTools 的 Performance 页与 “Highlight repaints”，P0 完成后切栏时应只看到底栏与新栏边框闪一次，而不是整页每帧闪。
2. **自动化基线**：在 `app/integration_test/` 加一个动效回放用例，用 `IntegrationTestWidgetsFlutterBinding.watchPerformance` 录下：三栏来回切换各 10 次、安排页四个页签轮换、展开收起“已完成”、一次 3000 字流式回答。输出 `FrameTiming` 的 build/raster 耗时 P90/P99 与超预算帧数，结果写入 `tool/perf/` 作为基线，后续改动对比。
3. **验收目标**（中端 Android、60Hz）：上述场景 build 与 raster 的 P90 各低于 8ms、P99 低于 16ms，超预算帧占比低于 1%；120Hz 设备上 P90 低于 6ms。
4. **组件测试补充**：`motion_test.dart` 增加对结构的断言（切栏后非当前栏 `TickerMode` 为假；`ExpandReveal` 内是 `FadeTransition` 而非 `Opacity`），把这次的约定钉进测试，而不是靠记忆。

## 5. 写回设计系统口径

建议把以下几条加进 `docs/00` §5.3 与 `docs/02` §2.1 的动效判例，作为以后新页面的写法要求：

1. 逐帧变化的透明度只用 `FadeTransition`，不用 `Opacity` 组件；逐帧位移的子树先包 `RepaintBoundary`。
2. 动画期间不改布局：聚焦、选中这类状态变化只插值颜色，宽度与字重不变。
3. 切栏、切页签先动画后读取；已有数据时返回不重播淡入、不闪转圈。
4. 常驻但不可见的内容一律包 `TickerMode(enabled: false)`。
5. 页面路由统一走 `zhixinRoute`，不再直接写 `MaterialPageRoute`。

## 6. 风险与取舍

`RepaintBoundary` 会多占一份图层内存，只加在整栏、展开块、流式段这几处大块上，不要给每个列表项手动再包一层（`ListView` 已默认加）。页签常驻会增加内存与首次进入后的后台状态，若后续页签内容变重，可以改为“最近两个页签常驻”。切栏延后读取意味着数据会晚约 260ms 出现，在已有缓存内容的前提下用户无感；首次进入没有缓存时，转圈本来就要出现，只是不再与动画抢帧。流式分段需要正确处理代码块与列表跨段的情况，先做“按帧合并”这一步并测量，确实不够再上分段渲染。

## 8. 补充：界面加载本身的优化点

以上各节解决的是“动起来不卡”，这一节解决的是“内容出来得慢、出来时跳”。

**L1 启动：首帧之前做了太多事（影响最大）。** `AppScope._init` 在首屏出来之前串行做完：解析路径、恢复中断的还原、打开数据库、`AttachmentStore.cleanupUnreferenced`（递归遍历题目图片目录）、`AttachmentCache.rebuild`（全表扫描 `message.image_paths_json`、在主 isolate 逐条 `jsonDecode`、逐个图片 `File.exists`）、读嵌入配置。后两项与首屏无关，而且耗时随数据量线性增长，用得越久启动越慢。建议：打开数据库与绑定设置之后就让首屏出来；附件清理与缓存补建放到首帧之后的后台任务（`addPostFrameCallback` 之后 `unawaited`，失败照旧写诊断记录），并且只在“上次还原 / 导入 / 异常退出”之后才做全量补建，平时跳过。需要先确认首屏读取的数据不依赖附件缓存；讨论页里图片不存在时已有缺图处理，可以接住补建前的空窗。

**L2 启动：原生启动图到首页之间多一屏转圈。** 现在是“原生启动图 → Flutter 转圈页 → 首页”三段。可以在 `main` 里 `WidgetsBinding.instance.deferFirstFrame()`，等 `ready` 完成（并给一个 1.5s 左右的上限）再 `allowFirstFrame()`，让原生启动图直接接上首页；超过上限才露出转圈页。顺带检查 `values-night*/styles.xml`：`LaunchTheme` 的父主题是 `Theme.Light`，深色模式下启动瞬间可能闪一下浅色底，`windowBackground` 需与深色底一致。

**L3 读取与动画：先读、后填。** 第 4 节 P1-1 建议“切栏动画结束后再发起读取”，更好的做法是：**立刻发起读取**，与动画并行；结果回来时若动画未结束，暂存到动画结束再 `setState`。数据不会晚出现，回填也不会打断动画。二级页面同理：在 `initState` 里开始读取，回填时检查 `ModalRoute.of(context)?.animation` 是否已完成，未完成就等 `AnimationStatus.completed`。可以封装一个 `context.afterTransition(() => setState(...))`，两处共用。

**L4 首页读取串行往返。** `ContextService.loadActivity` 里排程块、事项、待办、下一个到期项依次 `await`，每一次都是一次 sqflite 平台通道往返。互不依赖的查询并行（`(a, b).wait`），或合并成一条带 `UNION`/子查询的 SQL。首页、记录页、安排页的首屏查询都按这个口径过一遍，记录每页首屏的查询次数，目标是首屏不超过 2–3 次往返。

**L5 用占位骨架代替转圈，并固定高度。** 首页“继续上次”、记录列表首读时现在是居中转圈，读完后内容一次撑开，下面的区域整体下跳。改为与真实卡片同高的 2–3 条静态骨架（不做闪光动画，符合“不循环”的口径），读完原位替换，页面不再跳。已有上一份数据时不显示骨架，直接显示旧数据并静默刷新（第 4 节已提）。

**L6 空闲时预读另外两栏。** 首页首屏稳定后，用 `SchedulerBinding.instance.scheduleTask(..., Priority.idle)` 预读记录页第一页与安排页本周数据，放进各自服务层的内存缓存；用户第一次切过去时直接有内容。`dataVersion` 变化时清掉缓存即可，不需要额外的失效逻辑。

**L7 图片解码尺寸。** 讨论消息与采集入口的缩略图已经按显示尺寸设了 `cacheWidth`，做得对。`learning_page.dart:500` 的全屏查看直接 `Image.file(file)`，手机拍的题目照片原图解码会占几十 MB、首次打开要等一下；按 `屏宽 × dpr × 2` 设 `cacheWidth`（与 `maxScale: 4` 配合已足够清晰）。从缩略图点开时，先用同一份缩略图垫底（`frameBuilder` 里在大图未就绪时显示缩略图），大图解码好后替换，避免白屏。

**L8 列表惰性构建。** 记录页 `records_page.dart:506` 与首页、安排页主体都是 `ListView(children: [...])`，每次“加载更多”后整份 children 重新生成。与第 4 节 P1-4 一起改为 `ListView.builder` / `SliverList.builder`；“加载更多”可以在滚到距底部一屏时自动触发，按钮保留作失败重试。

**L9 讨论页打开。** 打开长讨论时，除了消息分页，还要读记忆条目、改动建议等。消息列表先出来（它决定首屏），其余侧栏数据随后到达再填；历史消息的 Markdown 只有滚到可视范围才会构建（`ListView.builder` 已保证），这一点保持。

**度量。** 在第 4 节的集成测试里加两项：冷启动到首页首屏可交互的耗时（`Timeline` 里 `Frame: first` 之后首页数据就绪），以及三栏首次进入到内容出现的耗时。验收目标建议：中端 Android 冷启动到首页内容出现低于 1.2s，与附件数量无关；切栏后内容出现不晚于动画结束。
