# 分层整改清单与提示词

> 2026-11-22 起草。依据是对 `app/lib` 与 `server/` 的 import 统计与抽查：客户端层间方向已经单向，但界面仍有 20 处直接引用数据层，其中绝大多数只是借用数据层文件里的值类型；客户端调用服务端的契约没有校验。本文把整改拆成可以逐批交给执行模型的任务。
>
> 使用方式：第一部分是背景与取舍，第二部分是按批次的清单，第三部分是提示词（先给通用约束，再按批次给任务）。批次 A 必须最先做，它给后面所有批次一条客观的终点线。

## 一、背景与取舍

现状（统计口径：`app/lib` 下各层之间的 `import`）：

- `domain` 不依赖任何其他层；`data`、`ai` 只依赖 `domain`；没有任何一层依赖 `ui`。这一条已由 `test/architecture_test.dart` 守住。
- `ui` 依赖 `data` 20 处，涉及 12 个文件。`architecture_test.dart` 目前没有约束 `ui` 与 `data` 的关系，所以这些引用没有被拦住。
- 这 20 处引用按用途分三类：
  1. 只借用值类型（`ServerQuota`、`ServerProblem`、`ServerRelease`、`ServerBackup`、`AccountIdentity`、`RevisionCommit` 等模型，`RestoreInspection`、`RestorePoint`、`EmbeddingConfig`、`ScheduleConflictException`，以及常量 `zhixinSchemaVersion`、`revisionDefaultRetentionDays`）。这类约 16 处，是主体。
  2. 调用静态方法或可变全局：`settings_page.dart` 直接写 `CrashLog.reportEnabled`。
  3. 持有数据层的服务对象：`data_version_page.dart` 与 `integrity_check.dart` 直接使用 `RevisionService`、`DataVersionService`。`DataServices` 本身就把这两个类公开给页面，所以这是服务放错了层，不是页面写错了。

已定的取舍：

- 值类型放进 `domain/models`，行为留在原处。这样 `data`、`application`、`ui` 都能依赖它，方向不变。不用 `export` 转发，也不留旧路径别名，依 [ADR-0001](adr/0001-开发阶段不向下兼容.md) 直接改所有引用，包括 `test/` 下的引用。
- 第 3 类（`RevisionService`、`DataVersionService`）这一轮不动，只进白名单。要不要把它们挪到 `application`，是需要用户定的取舍，执行模型不得自行决定。
- 服务端的分层已经符合要求，批次 A 到 E 不动服务端。批次 G 把模型接口统一成 Responses，会同时改服务端代理、契约与客户端，单独成批。
- 客户端只调用知新服务这一个固定后端（[ADR-0050](adr/0050-客户端统一为知新服务.md)），所以模型接口只需要保留两条：聊天用 OpenAI Responses，嵌入用 Embeddings。`ai/` 里只有一个实现的抽象层（`LlmWire`、`LlmDecoder`）随批次 G 合并成具体类。`LlmClient`、`EmbeddingClient`、`SecretStore` 是测试用的接缝，保留。
- 路径消减的核对结论：`openapi.yaml` 的 34 个路径里，管理端的 7 个 `/admin/v1/...` 是服务端自带的管理页（`internal/admin/ui/app.js`）在用，`/healthz` 与 `/readyz` 是运维与部署探针（部署流程核对 `/readyz`，运维手册写了 `/healthz`），其余都是客户端在用。没有可以直接删除的路径，唯一的删除是批次 G 里把 `/v1/llm/chat/completions` 换成 `/v1/llm/responses`，旧路径已于 2026-11-23 从契约与生成代码里删掉（[ADR-0055](adr/0055-模型调用协议与上限统一.md)）。
- 客户端不引入 openapi 代码生成。契约校验用一条不加依赖的测试完成（批次 E）。引入生成器要加依赖，须先写 ADR，见 [ADR-0015](adr/0015-服务端引入代码生成与限流依赖.md) 的做法。

### 批次 G：聊天接口统一成 Responses（改动跨服务端、契约与客户端）

这一批比前面几批大，要单独分支、单独评审。聊天从 OpenAI Chat Completions 换成 OpenAI Responses，嵌入保持 `/v1/llm/embeddings`，请求里显式要 `encoding_format: float`。客户端部分已按 [ADR-0052](adr/0052-客户端改用OpenAI现行请求格式.md) 完成：只连 `<服务地址>/v1/llm/responses`，工具声明与工具参数采用 Responses 的扁平形状与 `input` 条目，协议里的线格式抽象、`reasoningItems` 与按模型名判断提供方的写法都已删掉，G5 至 G8 按现在的实现验收即可，下面的描述保留作核对依据。

先说明一个会让整批失败的前提：服务端把请求转发给上游模型来源，来源必须支持 `POST /responses`（流式、工具调用、返回用量）。仓库里的测试用到过 `deepseek-flash` 这类模型名，而部分来源只提供 Chat Completions。如果来源不支持，对外改成 Responses 就意味着服务端要自己把 Responses 翻译成 Chat Completions，工作量与风险都大得多，要先由用户决定，执行模型不得自行实现这个翻译层。

## 三、提示词

### 通用约束（每一批的提示词前都附上这一段）

---

你在仓库 `zhixin`（Flutter 应用在 `app/`，Go 服务端在 `server/`）里做分层整改，依据文档是 `docs/分层整改清单与提示词.md`，先完整读完它的第一、二部分，再做我指定的那一批。

必须遵守：

1. 先读 `AGENTS.md` 与 `CONTRIBUTING.md`。不在共享工作区里切分支；用 `git worktree add ../zhixin-layering -b refactor/layering` 另开工作区，在里面做全部改动。
2. 开发阶段不向下兼容（ADR-0001）：直接改所有引用，不写 `export` 转发、不留旧路径别名、不写兼容分支。
3. 纯搬家的提交不夹带任何行为修改；搬家时保留类名、成员名、注释与顺序，只改所在文件与 import 路径。
4. 只做我指定的那一批，不顺手整理、重命名、格式化无关文件，不升级依赖。
5. 每一批做完，在 `app/` 下依次执行：`dart format --output=none --set-exit-if-changed lib test`、`flutter analyze`、`flutter test`（全量，不能只跑子集）。三条都通过再提交。改了 `lib/data/db` 下的东西就先 `dart run build_runner build` 并把生成结果一起提交。
6. 遇到下面任何一种情况就停下来，在结果里写清楚，不要自己拍板：清单里的假设与代码实际不符（例如要搬的类依赖了只在原文件里的私有函数）；搬家会让 `domain` 引入 `dart:io`、`package:http`、`package:flutter` 或 `ai`、`data` 的内容；需要改变某个方法的行为才能通过测试；需要新增依赖。
7. 提交标题按 `CONTRIBUTING.md` 的格式写，正文写清原因与影响范围：搬了哪些类、从哪到哪、改了多少处引用。不要 `git add -A`，只加你改的文件。
8. 提交之后 `git pull --rebase`，然后在结果里告诉我分支名与提交号，不要自己合并到 `main`。

最后的回复按这个格式：做了什么（一两句）；`flutter analyze` 与 `flutter test` 的结果；`_uiDataAllowlist` 现在的内容；遇到并停下来的问题；还没做的。
