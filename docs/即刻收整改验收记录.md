## 待核对：核销请求的重复与状态覆盖

- 状态：待执行（2026-11-26 列出）。2026-11-27 的 [ADR-0088](adr/0088-核销流水的本地认领.md) 已经补上入队去重与发送之前的本地认领，这条核对剩两件事：确认即刻收对同一个请求号幂等，以及决定要不要给 `SetChargeStatus` 加状态条件。本机仍然没有真实的即刻收商品、收款账号与沙箱，探针没有跑过；它现在列为发版前必跑的一步，见[运维手册 4.12](server/运维手册.md#412-发版前核对核销幂等)。

核销队列的三个入队来源（写流水之后、每次请求之前的补查、每十分钟一次的全局补查）会重复排同一笔流水。2026-11-27 起，入队之前本地去重，发送之前在流水上认领一次，同一时刻只有一份、只有一处发得出去，认领不到的那一份直接丢弃。剩下两条仍然取决于即刻收的行为：结果未知之后按原请求号重发能不能成立；`SetChargeStatus` 不带状态条件，一条晚到的结果可以覆盖已经落下的终态。

核对用 `server/internal/nowpay/idempotency_probe_test.go` 里的 `TestProbeVerifyIsIdempotentPerOutRequestNo`：它用与实例同一套 `api.env` 构造客户端，对同一个 `out_request_no` 连续核销两次一积分，比较两次的 `consume_status` 与 `consumed`，再看 `quota.query` 的余额是否只减少一次。默认跳过，需要一个沙箱或测试商品、一个还有余额的账号，以及下面这几个变量：

```bash
cd server
export ZHIXIN_NOWPAY_PROBE=1
export ZHIXIN_NOWPAY_PROBE_BUYER=<有余额的账号标识>
# 其余 ZHIXIN_ALIPAY_* 与 ZHIXIN_NOWPAY_PRODUCT_ID 取实例的 api.env
go test ./internal/nowpay/ -run TestProbeVerifyIsIdempotentPerOutRequestNo -v
```

结果按下面的表处置，结论与命令输出一起记在本节：

| 核对结果 | 说明 | 处置 |
|---|---|---|
| 两次状态与金额相同，余额只减一次 | 即刻收按请求号幂等 | 保持结果未知之后按原请求号重试；只补 `SetChargeStatus` 的状态条件，防止晚到结果改写终态 |
| 第二次返回不同状态或金额，或余额减了两次 | 不幂等 | 结果未知之后改成只用 `quota.refresh` 收尾、不再重发，同时给 `SetChargeStatus` 加状态条件 |
| 第一次就返回 `PROCESSING` | 无法核对，扣减没有确认 | 等 `quota.refresh` 拿到终态之后重跑；这一条本身也是“重复核销不该换号”的证据 |

另外两条也要在这轮核对里一起看：同一个账号两笔不同请求号同时核销时，余额是各自扣一次还是按到账顺序串行；`quota.refresh` 对一条一直是 `PROCESSING` 的流水连续查询，会不会在某一次返回 `FAILED` 之后又变回 `SUCCEEDED`，后者决定终态条件要不要写成单向。
