# 界面协调性整改清单与提示词

> 2026-11-22 起草。依据是 [配色预览.html](配色预览.html) 中“方案”一列：它的色值已经是现在 `app/lib/ui/theme.dart` 的色值，但预览看起来比真实应用协调，差别在字重、字距、描边、选中态与控件默认样式。本文把预览当作规格，让真实应用向它靠。
>
> 使用方式：第一部分是背景与取舍，第二部分是完整清单（按批次），第三部分的分隔线内是交给执行模型的提示词。

## 一、问题与取舍

真实应用与预览的差别共六处，整改围绕它们展开。

1. 描边有两种深浅。`_foruiColors` 把 Forui 的 `border` 设成了深色的 `inputBorder`，所以 FTile、FCard、FButton 的边是深灰；自写容器用浅色的 `outlineVariant`。同一页里两种边混在一起。预览里卡片、分隔线、底栏都用浅的 `border`，只有输入框用深的 `inputBorder`。
2. 字重四档混用。`titleLarge` 是 w400，`titleMedium`、`titleSmall` 是 w600，`headlineMedium` 是 w700，`pageTitle` 是 w500，三个 label 是 w500。主题文件自己写明：不指定字族后，安卓厂商字体常只有常规与粗体两档，w500、w600 会被就近取成粗体。预览只有两档：标题与强调，其余常规。
3. 中文字距沿用了 Material 为拉丁文设的值：正文 0.25，label 0.5，`titleMedium` 0.15。预览里是 0。
4. 底栏选中态用了三个颜色：图标 `onPrimaryContainer`，文字 `primary`，指示块 `primaryContainer`。预览里选中文字是 ink 加粗。
5. 控件走的是 Forui 默认样式，只覆盖了一部分。仓库里直接使用 FButton 184 处、FTile 65 处、FTextField 62 处、FCard 42 处、FSwitch 9 处，其中 FButton 以 `sm` 尺寸的 ghost 与 outline 为主。它们的字号档位、内边距、字重来自组件库默认值，与自写部件不齐。
6. 页面里还有绕开令牌的字面数字：图标尺寸 13、14、16、18、20、21、24 七种；若干 `EdgeInsets`、`SizedBox` 写死 10、14、20 等；若干 `fontSize`、`fontWeight`、`height: 1.4` 直接写在页面里。

已定的取舍：

- 页面底色保持纯白（`paper` 与 `card` 都是 #FFFFFF），层级靠浅描边，与预览一致，不改成浅灰底。
- 描边分两类。容器类（卡片、列表项、分隔线、底栏、对话框、面板）用浅的 `border`；交互控件类（输入框、选择框、复选框、outline 按钮）用深的 `inputBorder`。
- 字重只保留 w400 与 w600 两档。
- 凡预览里有明确数值的地方一律取预览的数值：`pageTitle` 26px、`FButton` 的 `sm` 标签 12.5px、底栏指示块用主色浅底（8%）。预览里没有对应元素的（例如 `headlineMedium` 的 30px）保持不变。

## 三、给执行模型的提示词

复制分隔线内的内容。

---

你在知新仓库（Flutter 应用在 `app/`，界面在 `app/lib/ui/`）里负责一次“界面协调性整改”。目标是让真实界面的字重、字距、描边、选中态与控件默认样式向 `docs/配色预览.html` 里“方案”一列看齐。完整清单与取舍在 `docs/界面协调性整改清单与提示词.md`，你严格按其中第二部分的批次 A 到 E 逐项执行，不增减范围。

开工前先读 `AGENTS.md`、`CONTRIBUTING.md`、`docs/配色预览.html`、`docs/界面协调性整改清单与提示词.md` 与 `app/lib/ui/theme.dart` 全文。读 `forui` 包在本机 pub cache 里的源码，确认 `FThemeData` 与各组件样式类的真实字段名后再写代码，不凭记忆写。

工作方式：

1. 不要在共享工作区切换分支。用 `git worktree add` 在工作区之外建一个新工作树，分支名 `feat/ui-harmony`，从最新 `main` 起。
2. 先在改动前跑一次批次 E3 的“整改前”截图，再开始动手。
3. 按 A、B、C、D 的顺序做，每个批次完成后跑 `flutter analyze` 与受影响的测试，通过后单独提交一次，提交信息用中文说明这一批改了什么。不要把几个批次合成一个提交。
4. 清单里的每一项做完后在文档里把 `[ ]` 改成 `[x]`；遇到无法按清单执行的项，保持 `[ ]` 并在该项后面写一句原因，继续做别的项。
5. 预览里有明确数值的地方以预览为准（`pageTitle` 26px、`FButton` `sm` 标签 12.5px、底栏指示块用主色浅底），清单已写成具体项；预览里没有对应元素的地方保持现状，不要自行发挥。
6. 不要新增真机性能测试或性能门槛；不要改动与界面无关的文件；不要改动 `camera_capture_page.dart` 与 `question_crop_page.dart`。
7. 页面里能用令牌就用令牌，不要为了让某一页好看而新增只服务一处的字面数字。若某处确实需要例外，在该行加一句注释说明原因。
8. 改文档时直接写成现行说法，不留删除线、“原为”“改为”这类痕迹。

验证（全部通过才算完成）：

- 在 `app/` 下 `dart format --output=none --set-exit-if-changed lib test`、`flutter analyze`、`flutter test` 全过；`workspace_flow_test.dart` 按 5 个分片分别运行。沙箱里的运行方式见仓库里已有的沙箱说明；`flutter pub get` 不要在挂载的 Windows 目录里运行，先把 `app/` 同步到沙箱工作目录再测。
- 完成批次 E1 的 `grep` 复核，并把命令与结果写进最终报告。
- 产出“整改前/整改后”各 10 张截图（五页乘浅深两套），放在 `.tmp/ui-harmony/`，在报告里逐页写一句看得出来的变化。

交付：提交留在 `feat/ui-harmony` 分支上，不要推送（推送由用户在 Windows 上完成）。最终报告写清楚：做了哪些清单项、哪些没做及原因、改动的文件数与提交列表、验证命令与结果、截图位置，以及你在 Forui 源码里确认到的与清单假设不一致的地方。
