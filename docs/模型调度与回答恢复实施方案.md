# 模型调度与回答恢复实施方案

> 当前状态（2026-11-24）｜批次一已交付，第二批的错误提示已先行交付。运行时恢复与持久用量明细分两个提交进入 `main`（`b4fb1d0`、`e07f859`），后者随同日的停服重建上线；上游限流改为 `rate_limited` 并转出 `Retry-After`，客户端据此与额度用完分开提示。故障注入验收、一轮预算与其余批次按本文继续。现行路由规则见 [ADR-0029](adr/0029-模型来源路由与嵌入代理.md)，故障范围与恢复规则见 [ADR-0059](adr/0059-模型路由按故障范围切换与恢复.md)，页面现行行为见 [02 第 3.8 节](02-产品与交互.md#38-模型配置与降级)。

## 1. 目标与基线

知新以用户发出的一轮讨论为单位衡量模型服务。上游抖动时，系统应优先在用户愿意等待的时间内交付完整回答，无法完成时应保存用户已经提交的问题、附件与可用结果，并给出能够执行的后续操作。缓存复用与上游分流以完整回答率和首字延迟达标为前提。

主备组已经能在后台配置与预览，当前主分支在同组内逐请求按权重随机排序，所以一条讨论的追问和工具后续步骤可能落到不同来源。服务端等待上游响应头的默认上限为 60 秒，客户端等待首个有效输出的默认上限为 30 秒，配置值的差距使客户端可能先结束等待。客户端已有本地兜底、停止生成和重试入口，同时会把临时繁忙与额度耗尽的 `429` 都归入额度提示。上述情况以代码默认值为基线，真实来源的时延、错误分布与缓存命中率由第一批测试记录补齐。 [路由选择](../server/internal/llmproxy/router.go) · [服务端配置](../server/internal/config/config.go) · [客户端期限](../app/lib/ai/llm_failure.dart) · [回答提示](../app/lib/ui/answer_notice.dart)

## 2. 批次与分工

分工沿用 [03 第 2.1 节](03-团队分工与协作.md#21-模块主责)，表中列出本次变更的交接内容。批次一的运行时恢复先验收，第二批中的错误提示可以并行开发，首字预算与流式切换由两端一起联调。第三批在完成率和等待时间基线建立之后扩大，第四批用导入与讨论并发的测试确定前台预留容量。

| 批次 | 主责与协作 | 交付与依赖 |
|---|---|---|
| 一 · 上游故障隔离 | 主开发负责服务端与管理后台，测试与验收负责故障注入和回归 | 接续 `fix/model-route-recovery`，交付按故障范围冷却、独立备源、有限试探、路由预览及尝试记录。持久用量明细与运行时恢复可分别发布 |
| 二 · 一轮回答的预算与交互 | 主开发负责两端协议、代理和 AI 运行时，应用开发负责讨论服务与交互，测试与验收负责联调与真机走查 | 一轮预算、流式提交边界、取消、临时繁忙提示、部分回答与原问题重试。错误提示可先交付，涉及契约的改动在同一个 push 更新两端 |
| 三 · 会话路由与前缀复用 | 主开发负责路由与请求组装，提示词与插件角色负责提示词、工具定义与质量评测，测试与验收验证结果 | 兼容路由筛选、组内会话分配、稳定前缀和按上游端点采集的缓存数据。依赖第一、二批的恢复语义 |
| 四 · 前台容量与发布验收 | 主开发负责模型代理与检索调度，应用开发负责搜索结果与进度提示，测试与验收负责并发走查 | 前台并发预留、后台分批补算、关键词降级，记录压测基线与发布对比 |

测试与验收按第 7 节记录各批次结果，开发者仍按 [提交约定](../CONTRIBUTING.md#7-提交前的检查) 执行所属端检查。合入时，主开发核对各分支依赖、接口生成结果及发版条件。服务端运行时和报表若共用开发分支，应整理成能独立合入的提交或分支，涉及持久报表字段的改动纳入下一次计划内重建，并按 [ADR-0057](adr/0057-服务端改表清空重建.md) 记录停服、数据处置和复核步骤。

## 3. 批次一 · 上游故障隔离

请求按主备组和来源可用状态筛选候选，再按实际发出的上游尝试扣减次数。连接错误或明确的共享凭据拒绝会跳过该来源的其余候选，兼容的独立备源仍有机会接手。单个模型不可用、响应格式异常等故障只影响对应路由，限流按提供方报告的共享范围判断，范围不明时先按路由处理，能够识别的 `Retry-After` 用于限制恢复试探的时间。冷却期结束时每个故障范围只允许有限的并发试探，试探完成后依据实际结果恢复流量或继续冷却。

服务端区分有效完成、失败、截断、用户取消和客户端断开，取消与断开不增加上游失败计数。收到 `response.failed` 时计为失败，并按原因判断故障范围和是否可以切换。收到 `response.incomplete` 时核对原因，如果达到输出上限，则记录截断、保留用量与部分正文，并和故障及恢复成功分别计数。每次已发出的尝试按现有额度规则结算，即使用户取消或转走另一条路由，也保留已产生的上游用量。

管理后台的配置比例、当前首选预览及实际分流分别展示，模型自测列出尝试顺序、结果与失败原因，用量区分首次尝试和故障切换。后台探测与恢复试探应在观测中可辨认，人工测试结果只用于诊断，用户回答完成率按真实回答计算。

## 4. 批次二 · 一轮回答的预算与交互

客户端从用户发送开始计算整轮时限，模型请求传递本轮剩余时间，服务端按本机上限约束该值。等待首个有效输出、连续输出间隔及整轮结束各有时限，工具调用后的请求沿用整轮预算。普通文本、带图和长材料可以校准不同的首选等待时限，首发和备用路由必须一起落在剩余预算内。客户端将断线重试也计入该预算，服务端明确返回候选已耗尽时，由当前一轮进入降级或恢复提示。

对于流式响应，服务端收到响应头、心跳或开场事件后仍可在有预算时换路，先行事件的暂存受时限和字节数约束。交付首段正文或一项可执行的完整工具调用后，本次流绑定当前路由，后续中断由客户端保存部分内容并给出恢复入口。工具后的新模型请求可以从已完成的步骤继续，并再次依照预算选路。恢复时仅复用原轮仍有效且完整的证据、调用结果或写入回执，已经执行的写入不得重复执行，用户或数据状态变化后应重新核对上下文。

| 情况 | 用户可以看到或执行的操作 |
|---|---|
| 等待上游或读取资料 | 保持一条回答的占位和停止入口，有实际工具状态时显示“正在查找资料”等对应进度 |
| 首字前换路成功 | 在原回答位置继续显示，问题、附件和讨论归属沿用原轮 |
| 上游均不可用 | 保留原问题与附件，标明本地规则提供的帮助，在原回答下提供模型重试 |
| 已显示正文后中断 | 保存正文和中断状态，从最近安全的步骤继续，无法接续时可重试原问题 |
| 达到输出上限 | 保留正文，显示回答未完，并提供继续或重试入口 |
| 短时繁忙 | 识别 `rate_limited` 和 `Retry-After`，提示稍后重试，自动重试限于仍有预算且未交付有效输出的情况 |
| 额度耗尽 | 识别 `quota_exceeded`，展示能由响应确定的额度范围与恢复时间 |
| 主动停止 | 结束本地等待与本轮上游请求，保留已生成部分，重开讨论时可辨认停止状态 |

## 5. 批次三 · 会话路由与前缀复用

以 `zhixin-chat` 为入口，管理员先选一条能稳定供应的主路由和一条故障范围独立的备路由，用实际调用核对纯文本、图片、函数调用、流式响应与可用上下文长度。首条主路由出现持续排队之后，再根据分流数据增加主路由。每轮先按请求能力排除不兼容的候选，再按主备组选择。主用组内有多条兼容路由时，按账号范围内的稳定会话标识及现有权重分配首选路由，使同一讨论的追问与工具步骤可以复用前缀。后台将权重标为会话配置比例，并单独展示受会话长短与故障切换影响的实际请求量。

当首选路由进入冷却、返回限流或按近期实测与可用容量判断可能耗尽首字预算时，依序选择其他兼容路由。换路只影响当前尝试和后续可用性判断，已交付的正文仍属于原回答。在备用路由只能处理纯文本时，带图或需要工具的请求只使用相应能力已经验证的候选。用于会话分配的标识在知新代理内使用，日志和上游字段只携带交付所需的数据。

提示词构建把稳定指令、顺序固定的工具定义以及仍适用的历史放在上游实际处理的前缀中，将当前时间、本轮检索与记忆结果和本轮问题放在后段。上下文不足时仍按现有规则删减，记忆删除、范围变化或更正立即反映在新请求中。分别验证各上游模型和协议端点实际接收的输入与缓存用量，支持命中统计时按实值记录，缺失时单列。DeepSeek 的 Responses 接口自动维护上下文缓存，从终止对象的 `usage.input_tokens_details.cached_tokens` 读取命中输入量。 [提示词构建](../app/lib/ai/buddy_prompt_builder.dart) · [请求格式](../app/lib/ai/llm_protocol.dart) · [DeepSeek Responses 文档](https://api-docs.deepseek.com/guides/responses_api/)

## 6. 批次四 · 前台容量

聊天和用户正在等待的查询向量使用前台容量，材料导入、索引重建及补算使用剩余容量。客户端区分查询与文档批次，服务端在账号与实例层给前台保留在途名额，并按来源的限额约束可并发发出的批次。后台工作以有界的小批次让出容量，先查询已有的账号级向量缓存，只补算缺失项。嵌入备路由必须指向同一向量空间，向量缓存和客户端索引仍按已约定的模型归属判断。 [向量缓存方案](adr/0030-服务端不建检索索引.md) · [嵌入来源](adr/0049-嵌入统一走百炼与查询向量也走云端.md)

语义查询超出等待时间或被限流时，搜索先展示能取得的关键词结果。批量嵌入按已完成批次保存进度，恢复后继续补算。前台请求增长时先减少并发后台批次，并在验收中核对后台业务在负载回落后能够继续完成。

## 7. 验收与发布

故障注入覆盖连接失败、响应头超时、连续 5xx、429、成功响应只有开场事件、有效输出后中断、`response.failed`、达到输出上限、用户取消和恢复试探并发。用同一份文本、带图与长材料样本分别核对主路由健康、单条路由失效、整个主来源失效及全部来源不可用。并发验收同时运行材料导入和搜索，核对聊天、查询与补算各自的结果。每轮验收还应确认重试沿用原始问题与附件，重开讨论后可以看到部分回答和正确的收尾状态，已经产生的工具写入只执行一次。

有效模型轮次从具备调用资格的用户发送可以交由模型处理的内容开始计算，包含代理临时繁忙、上游无法连接或候选耗尽的轮次。用户主动停止单列，并在对比发布前后数据时沿用同一统计口径。

| 指标 | 计算与核对 |
|---|---|
| 完整云端回答率 | 完整交付预期正文或必要工具结果的轮次除以扣除主动停止后的有效模型轮次，本地兜底与截断分别报告 |
| 故障下可用结果率 | 在注入故障且用户未主动停止的有效轮次中，交付完整云端回答、仍有帮助的部分结果或明确标记的可用本地兜底所占比例，分别报告各类占比 |
| 用户首字时延 | 从发送到第一个可见正文的时间，报告 P95、样本量及无正文轮次比例，并为工具先行的请求另记首个有效事件时间 |
| 完成一轮的上游尝试 | 报告每个完成轮次的上游尝试次数，同时按所有有效轮次核对首发、切换、失败与额外消耗 |
| 输入 Token 缓存命中占比 | 已报命中输入量之和除以同一批有缓存用量数据的请求输入量之和，按上游路由和请求类型记录，字段缺失的请求单列 |

发布前用同一套观测口径比较基线与新版本，按请求类型和故障场景报告完成率、首字 P95 与上游尝试次数。完成率提高、等待没有恶化且额外尝试处于基线与容量能解释的范围时再扩大使用范围。缓存收益作为第三批的额外验收，具体阈值由真实调用与故障注入的基线确定。监测只记录诊断所需的时长、错误类型和用量，真实学习内容、附件与凭据不进入统计。

## 8. 取舍与待定项

首选等待时间缩短会让部分仍可完成的慢请求提前换路，所以应以各类请求的实测时延和备源耗时校准。代理采用有界的串行尝试，因为同时向两个上游发送完整请求会增加计费，并可能在故障高峰占用备用容量。首次有效事件前保留的流事件也要计入实例内存预算。已交付正文或可执行工具调用后的故障交由客户端恢复，避免将不同答案接在同一处或重复提交工具操作。

会话级分配保留了复用上游前缀的机会，同时可能因不同会话的请求量而形成负载偏差，所以后台应分别展示配置比例、实时预览和实测请求量。前台预留容量会延后后台索引，具体保留比例与批次大小根据并发走查确定。缓存字段、可缓存前缀和保留时间以各上游实际支持的协议为准，未达到缓存条件的短请求按正常路径处理。

两端传递期限与会话标识的具体接口、按请求类型的预算、容量参数和上线阈值待联调测量。涉及跨端契约的取舍在实施批次通过验收时登记 ADR，并同步更新 [服务端说明](../server/README.md#模型代理) 与 [02 的交互和验收口径](02-产品与交互.md#38-模型配置与降级)。
