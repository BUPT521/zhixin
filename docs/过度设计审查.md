# 过度设计审查

> 审查日期 2026-11-22，范围是 `app/lib`、`server`、`tools`、`docs`、`app/test` 与 `.github`。审查分六路并行进行，每路用 grep 统计引用数与实现数后给出结论；本文合并重复条目，并在“核实情况”一节说明哪些结论由人工复核、哪些仍是估计。行数都是量级，没有改代码实测。表与列这一层另见[数据库结构过度设计审查](数据库结构过度设计审查.md)，记忆相关的改造见 [ADR-0051](adr/0051-记忆改为自由文本条目并走文档检索路径.md) 与[长期记忆整理方案](长期记忆整理方案.md)。

## 1. 总体判断

这个项目的主要问题不是代码写得乱，而是把“100 人公测、4 人团队、单实例、单用户几千条数据”的产品，按多实例、大数据量、第三方生态和防篡改的标准建造。同一个模式在客户端和服务端各出现一次：先为一个可能出现的需求建好机制，需求没有出现，机制默认关闭或只有测试在用，但它的代码、表、接口、文档与测试一直在维护。

归纳起来是六类成因，后文每条清单都标了所属类别。

| 类别 | 含义 | 典型 |
|---|---|---|
| A 规模错配 | 机制面向的规模远大于实际规模 | 快照压缩、嵌入缓存、限流 13 个实例、路由加权与熔断 |
| B 预留未用 | 为尚未出现的第二个使用者预留 | 能力插件运行时、人格导入、手机号与微信登录、多实例刷新循环 |
| C 兼容残留 | ADR-0001 已规定不兼容，兼容代码仍在 | 旧数据包恢复、旧索引清理、`legacy` 分支、旧量纲 |
| D 测试接缝入生产 | 为测试存在的构造参数、可空回调、替身类放在 `lib` | `SearchIndexService` 的 9 个可选回调、`MemoryVectorIndex`、12 套内存存储 |
| E 复制多于抽象 | 同一流程复制多份，或抽象只有一个使用者 | 基线上传 5 份、查找页 3 份、记忆卡片接受流程 2 份、mixin 加 `self` |
| F 文档与流程堆积 | 一次性方案、提示词、探针、基准长期留在仓库 | 53 篇 ADR、8 篇方案文档、`vector_bench` |

按原始建议全部落实，估计可减少 9000 至 11000 行手写代码；第 2 节确认保留快照压缩、插件与记忆索引之后，实际约为 6000 至 8000 行。该范围约占 `app/lib` 手写部分（约 7.8 万行）与服务端手写部分（约 2.1 万行）的 10%，另有数千行测试和约 1500 行文档。各路数字之间有重叠，已在汇总时去重，但仍是粗估。

## 2. 已定的处置原则

2026-11-22 与项目负责人确认了处置方向，下表是六个最大主题的结论，其余条目按同一原则类推：功能有明确用途的，优化实现并接入，不删除；零引用但属于预留的，在排期里写明接入时间，没有接入时间而且体量大、意义小的才删除；与已有改造方案重叠的并入该方案；不确定的先问人。

| 主题 | 处置 | 落实方式 |
|---|---|---|
| 快照压缩、设备名册、基线上传的五份重复（3.1 至 3.4） | 优化接入并重构，不删除 | 基线上传先合并为一个函数；快照与名册保留。建议客户端只在服务端声明压缩已开启时才上传整库快照，这样关闭期间不产生成本；开启时间与前置条件待定，见第 12 节问题 1 |
| 能力插件运行时与人格（4.1、4.2） | 保留 | 属预留能力，[04 第 4 节](04-长期路线图.md#4-插件路线)已把课表导入、分享到知新、人格导入排在 M3，运行时的首个使用者是课表导入插件；在它合入之前不再扩充运行时 |
| 服务端内存存储与配置（5.1、5.3、5.5 至 5.12） | 精简 | 按风险从低到高分批，内存存储随测试迁移到 PG 逐步下线 |
| 界面重复与巨型页面（4.14 至 4.24） | 复用，外观不变 | 查找页、一级页样板、数据版本页拆分、讨论与账号页拆分都只做结构调整，不改界面；记忆相关部分并入 [ADR-0051](adr/0051-记忆改为自由文本条目并走文档检索路径.md) 的改造方案，不单独处理 |
| 记忆索引、记忆卡片两份流程（4.7、6.1） | 并入 ADR-0051 | 该 ADR 已决定召回的排序入口并入文档检索路径，记忆自己的一套排序与 `MemoryRelevanceRanker` 随之消失；记忆仍用独立的 collection，只是通过语料参数走同一个检索服务接口（ADR-0051 决定第 6 条）。卡片接受流程在同一次改动里合并 |
| 文档、基准与流程（第 7 节） | 重编号并清理多余文件 | ADR 编号已改为 0051 与 0052，引用已同步；其余文件的清理范围见第 12 节问题 3 |

零引用的类与函数按下表处理，体量小的先移出 `lib`，等排期接入。

| 情形 | 做法 |
|---|---|
| 只被测试使用的替身与辅助（第 8 节前几行） | 移到 `app/test/support/`，不删除 |
| 预留，且路线图已有接入里程碑 | 保留 |
| 预留，路线图没有接入时间 | 在 04 补一行接入时间；补不出时间的，按体量与意义决定 |
| 无接入时间，体量大，意义小 | 删除，历史在 git |

第 8 节和第 9 节仍然有效：测试替身移出、死包装删除与兼容残留清理都不改变行为，可以直接做。

## 11. 核实情况与局限

人工复核了六条：`RhsRow` 零引用、`MemoryVectorIndex` 等三个类只在 `lib` 内部互相引用、`ZHIXIN_SYNC_COMPACT` 默认关闭（代码与 README 两处一致）、`FirstPartyPlugin` 只有 `PersonaPlugin` 一个实现、四个 `Plugin*Backend` 无生产实现、目录里确有两个 0051。复核同时纠正了一处：5.4 中 `RotateSession` 与 `UpdatePassword` 的 sqlc 查询仍被事务路径使用，可删的只是单步包装。

其余结论来自子审查的 grep 统计，没有再次独立核对。有几点需要使用者自己确认：生产 `api.env` 是否开了 `ZHIXIN_SYNC_COMPACT=1`（决定 3.1 与 5.8 能否做）；`llm_route` 是否已配多路由并依赖权重（5.6）；线上是否已跑过附件回填（5.7）；是否有线上用户持有旧格式数据包（3.7）；是否有人在看管理页用量报表（5.13）。
