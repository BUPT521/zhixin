# 知新 · 数据版本系统对照 git 的改进方案

> 范围是客户端数据版本系统（`app/lib/data/revisions/`）、同步服务（`application/sync_service.dart`）与服务端提交序列（`server/internal/syncsvc/`）。基线是 2026-11-20 的 `main`（`81b6ddd`），schema 28。[数据版本系统改进方案](数据版本系统改进方案.md) 的阶段 0 与六条泳道已经全部合入，本文不重复那份方案，只写对照 git 的设计之后仍然存在的问题和改法。3.1 至 3.4 已经在分支 `feat/revision-sync-git` 的 `522b8dc`、`33f83ca` 与 `b0dd4d5` 三个提交里落地，schema 同时升到 29；阶段 2 的 3.6 与 3.8 已经在分支 `feat/revision-phase2` 的 `1ba483c` 与 `8a73a25` 两个提交里落地；3.5、3.9 与 3.11 已经实现，提交分别是 `dfdad58`、`bd7a4fb` 与 `549947d`；3.10 与 3.12 的数据层随 `24e26c9` 实现，完整性检查入口、来源显示与索引读取位置迁移还没有做；3.7 的服务端一侧随 `149b0b2` 实现（[ADR-0043](adr/0043-服务端快照登记与提交序列压缩.md)），客户端首次同步与重新克隆还没有做。当前 schema 30。第 3 节各条按实现后的现行口径写，第 4 节列出每项的完成状态。

## 1. 对照结果

知新的版本系统在结构上已经很像一个“只有一条分支的 git”：提交只追加，`HEAD` 与命名版本是引用，检查点相当于树快照，附件按 SHA-256 内容寻址，整版恢复写成一条新提交而不是改写历史，推送带 `base_seq` 做乐观锁，相当于 git 拒绝非快进推送。差别集中在下面几处。

| 方面 | git 的做法 | 知新现状 | 判断 |
|---|---|---|---|
| 提交身份 | 对象按内容哈希命名，全局唯一，不会复用 | 本机用自增编号；`request_id` 同时充当本机重试去重键、推送身份与拉取去重键，而且很多是按命令参数算出来的固定值 | 要改，见 G1 |
| 拉取后推送 | `pull --rebase`：本机未推送的提交逐条在上游之上重放，只有真正重叠的行才冲突 | 拉取后，凡是改动碰到“被远端覆盖的格子”的本机提交整条不推；格子集合只在内存里 | 要改，见 G2、G3 |
| 合并规则 | `.gitattributes` 可以按文件指定合并驱动 | `updated_at` 与内容列同样处理，几乎每次都会重叠 | 要改，见 G2、G3 |
| 远端引用的生命周期 | `git remote remove` 时一并删掉远端跟踪引用 | 退出登录、清除云端之后 `sync.pushed` 仍然阻塞裁剪与清理 | 要改，见 G4 |
| 回到旧状态 | `reset --hard` 之后再 `pull` 会快进回来；想保留旧状态要用 `revert` 或提交旧树 | 整库恢复旧备份会连同旧的同步位置一起恢复，下次同步把恢复前的改动又拉了回来 | 要改，见 G5 |
| 克隆 | `clone` 只下载，不推送 | 新设备首次同步拉完全部提交之后，还会把整份数据作为基线再上传一次 | 要改，见 G6 |
| 浅克隆与打包 | 有浅克隆，打包文件做增量压缩 | 服务端序列只增不减，新设备从第 1 条回放；超过 256 MiB 只能清空后重传 | 后续做，见 G7 |
| 一致性判断 | 树哈希相同就说明内容相同 | 没有办法判断两台设备是否一致，分叉只能靠用户发现 | 要加，见 G8 |
| 自动回收 | `gc --auto` 按阈值自动触发，reflog 按时间过期 | 裁剪只有手动入口，按条数保留；一轮对话就是两条提交 | 要改，见 G9 |
| 检出 | `checkout` 只改有差异的文件 | 整版恢复删掉全部业务行再插回，内存里同时放三份整库投影 | 要改，见 G10 |
| 完整性检查 | 哈希链加 `fsck` | 只有检查点有校验值，变更明细没有；没有整体自检入口 | 可以做，见 G11 |
| 撤销 | `revert` 可以再 `revert` | 撤销提交不能再撤销 | 可以做，见 G12 |
| 作者信息 | 作者时间与提交时间分开，记录作者 | 远端提交的时间是本机应用时刻，不记来源设备 | 可以做，见 G13 |

上表的“知新现状”一列与第 2 节的问题清单都按 `81b6ddd` 的代码写。G1 至 G5 已经由 3.1 至 3.4 修掉，G6 与 G9 已经由 3.6 与 3.8 修掉；G7 的服务端一侧已经由 3.7 实现，客户端首次同步与重新克隆待做；G8、G10 与 G12 已经由 3.5、3.9 与 3.11 修掉；G11、G13 与 G14 的数据层改动大部分已经实现，完整性检查入口、来源显示与索引读取位置迁移待做。实施状态见第 4 节。

有些 git 的东西不学：分支与合并提交（产品只有一份数据，线性历史够用，命名版本已经承担了标签的作用）、暂存区（命令即提交）、用内容哈希替换整数编号（回执、界面与撤销都依赖整数编号，新增的全局标识作为第二身份就够了）、变更明细的增量压缩（先看 `byte_length` 的分表统计，确实大了再说）。

## 3. 方案

### 3.1 提交身份拆开（G1，P0）

`revision_commit` 增加 `uid TEXT NOT NULL` 与唯一索引，本机提交在 `_appendCommit` 里生成 UUIDv7 文本，与业务表主键使用同一个生成器（[ADR-0018](adr/0018-业务表主键改用UUIDv7.md)），长度 36 字节，列值长度上限按 64 字节校验；远端提交沿用服务端带来的 uid。首次同步上传的基线提交没有对应的 `revision_commit` 行，它的 uid 由设备编号前 8 位与这一块变更明细的 SHA-256 前 32 位拼成，长度不超过 41 字节，同一内容重发时保持不变。推送时 `request_id` 字段一律填 uid，拉取时按 uid 判断远端提交是否已经应用。服务端协议不用改，字段含义从“幂等键”变成“提交身份”，`seen` 的永久去重因此只跳过真正的重试，不再误伤同参数的不同提交。`syncRequestIdFor` 与 `l-` 前缀的回退编号删除。

本机的 `request_id` 只保留“同一次用户动作的重试去重”这一个用途，判重试需要两条同时成立：同编号旧提交的 `created_at` 落在最近两分钟内，并且这条旧提交仍然是当前 `HEAD`。只看时间窗口不够，因为“暂停、恢复、再暂停”与“撤销之后立刻重做同一动作”都会在窗口内再次命中上一次留下的编号，按重试直接返回旧提交；旧提交不再是 `HEAD` 说明两次动作之间已经产生了别的提交，同编号按新动作处理，先把旧提交的 `request_id` 置空再照常执行。撤销不再释放目标的 `request_id`，两条判据已经覆盖了重做同一动作的情况，释放编号反而会让重做被服务端的永久去重丢掉。界面在用户动作发生时生成一次性编号、重试时复用该编号的做法更彻底，但要逐个修改 29 处 `commandId` 调用，安排在后面单独做。

表结构变化按 ADR-0017 升到 schema 29、清空重建；服务端按 schema 相等校验，`ClientSchemaVersion` 同时改成 29。3.5、3.10、3.12 的表结构随后一起把版本升到 schema 30，服务端同步改成 30，客户端与旧版本之间不兼容，旧库在打开时清空重建。

验收：同参数“暂停 → 恢复 → 暂停”之后目标处于暂停状态；撤销后重做同一动作，另一台设备拉取后能看到重做；恢复旧备份后的新提交能推到服务端；两台设备离线各加一条同内容记忆，同步后两边行集合一致。

### 3.2 推送按格变基，被覆盖的格子写进库（G2、G3，P0）

把“哪些本机格子已被远端取代”从内存挪到库里，新表 `sync_shadow`：`table_name`、`row_key`、`column_name`（整行变化写空字符串）、`upto_commit`，前三列是主键。`column_name` 不用 `NULL` 表示整行，因为 SQLite 的唯一约束认为两个 `NULL` 互不相同，整行遮蔽会重复插入多行，写空字符串才能让每个格子只留一行（[ADR-0040](adr/0040-数据版本的提交身份与同步变基.md)）。拉取应用一条远端提交时，对它真正写入的每个格子登记一行：修改只登记 `after` 里的变化列，新增、删除与整行覆盖记整行；`upto_commit` 取应用前的本机 `HEAD`，意思是“编号不大于它的本机提交在这个格子上的改动作废”，同一格子再次登记时取较大值。遮蔽行与这条远端提交在本机形成的 `remote` 提交写进同一个事务，所以拉取成功、推送失败之后它仍然在库里。

推送时不再整条跳过，而是对每条待推送提交算出剩余部分：去掉被遮蔽的格子（列级变化去掉对应列，被整行遮蔽的行整条去掉），只推剩余部分；剩余为空的提交不推，位置照常前进。提交编号大于 `upto_commit` 的不受影响，所以同步过程中用户新做的修改照常推送。推送位置到达 `upto_commit` 之后删除对应的遮蔽行，裁剪与清理历史删掉被遮蔽的本机提交之后删除更早的行，整版恢复、导入与清理历史推进代次时整表清空。这就是 git 的 `pull --rebase`，只是粒度是格子而不是行。剩余部分里的 `before` 不用改：被保留的列远端没有动过，其他设备上的旧值与之相符。

`revisionBookkeepingColumns`（目前是 `updated_at`）按“维护列”的合并规则处理，相当于 git 的合并驱动：远端应用时不记冲突，判断剩余部分时只按格子遮蔽，不让它把整条提交拖下水。冲突记录因此只剩用户能看懂的内容列。

验收：A 改记忆内容、B 改同一条记忆的状态，双向同步后两边内容与状态都是各自的新值，且没有冲突记录；A 一条提交同时改两行、其中一行被 B 覆盖，另一行仍能推到 B；拉取之后、推送之前断网，下一轮同步不会把被覆盖的旧值推上去；同步过程中新写的修改照常推送。

### 3.3 同步位置跟着账号走（G4，P0）

`revision_cursor` 增加 `scope TEXT`，同步的两个位置写入“账号编号 + 实例来源”的 SHA-256 前 32 位。退出登录、删除账号与重设密码时，把 `sync.pushed` 改成 `blocking = 0`，位置与 `scope` 保留：重新登录时 `scope` 相同就从原位置继续增量同步，不走首次基线，不同才按新账号处理。裁剪与清理只看 `blocking = 1` 的位置，所以退出之后清理历史立即可用。清除云端数据时把两个同步位置与恢复标记 `sync.restore_align` 一并删除，因为云端序列已经为空，保留旧位置会让界面按“上次同步过”显示状态，实际同步却要重新上传基线并再次确认，这一轮同步在用户确认之前就报失败结束，界面状态与同步要求对不上。

验收：退出登录后“清理历史”不再被拒；同一账号重新登录后的同步只推送退出期间的新提交，服务端序列不会多出一份基线。

### 3.4 整库恢复写成一次“回到旧状态”的提交（G5，P0）

整库恢复在替换数据库之前先把当前状态保存成一份恢复点，并单独留一份恢复前的业务投影，因为换库之后原来的库就读不到了。换库成功之后在恢复后的库里补记一条 `kind = restore` 的提交，净变化是“恢复点投影 → 恢复后投影”的差异，删除也在其中；`sync.pushed` 写成这条提交的父提交，另一个位置 `sync.restore_align` 记下这条提交的编号。待重新对齐期间自动同步不排期。下一轮手动同步先向用户确认“云端会改成恢复后的内容”，复用首次基线的确认异常、只是文案不同；确认之后不按旧位置拉取，只推送这条提交与之后的新提交，推送完成之后两个位置收敛到当前服务端位置与本机 `HEAD`，恢复之前的改动不会再从旧位置拉回来。其他设备拉到的就是一次正常的整版恢复。

恢复前的投影读不出来或者补记失败时，`sync.restore_align` 写成 -1，下一轮同步按首次基线重新对齐；恢复前后没有差异时两个位置只挪到当前服务端位置与本机 `HEAD`。两条退路同样跳过旧位置。首次同步只传差异（3.6）已经落地，这条退路先拉取云端已有的提交，再只上传本机独有的行。

验收：开着同步恢复一份旧备份，再同步一次，本机数据保持恢复后的内容；另一台设备同步后得到同样的内容。

### 3.5 一致性摘要（G8，P1）

每条提交都带 `state_digest`：全部业务行按“表名、主键、规范化整行”做 SHA-256，整行按列名升序排列、每个值写成 `{"t": 类型, "v": 内容}`，再把这些 256 位整数按 2^256 取模求和，空投影的和是 64 个 `0`。求和与顺序无关，所以采集路径按“减去旧行哈希、加上新行哈希”累加，整库重算按全部业务行求和，两条路径得到同一个值；提交落库时把增量加到父提交的摘要上，检查点也存一份，重建时解码之后按投影重算并比对。规范形式与两条计算路径在 `app/lib/data/revisions/revision_digest.dart`，提交行与检查点的写入在 `revision_log.dart` 与 `revision_capture.dart`，取舍见 [ADR-0045](adr/0045-同步两端的一致性摘要.md)。

同步时两端交换这个摘要。推送完成且本机没有待推送提交时，客户端把当前摘要附在最后一条提交上；这次拉取有被跳过的变化、或者已经知道两边不一致时，推送不挂摘要，避免声明一个不成立的云端状态。另一台设备拉到的最新一条提交带着摘要、并且自己也没有待推送提交时，按当前业务表整库重算摘要并与它比较；读位置与重算之间又写入了本机提交，这一轮跳过，等下一轮再比。不一致时账号页的同步卡显示“本机与云端不一致”、状态标为“待修复”，给出“以云端为准修复”与“以本机为准修复”两个入口，并另写一条 `cloud_sync_digest` 诊断；两边的做法与界面文案见 [02 第 3.16 节](02-产品与交互.md#316-账号与云同步)。

摘要只做检测，不自动修复，也不阻塞同步。3.7 的客户端快照克隆还没有实现，“以云端为准修复”按服务端序列从第 1 条重新对齐，云端历史被压缩过时这一步会失败；“以本机为准修复”只补传云端缺少的本机行，删不掉云端多出来的内容。两个入口的代价与边界见 [ADR-0045](adr/0045-同步两端的一致性摘要.md) 的“代价与边界”一节。

### 3.6 首次同步只传差异（G6，P1）

首次同步先拉取这个账号的全部远端提交并在本机应用，拉取时从每条提交的变化明细里记下被触及的“表名 + 主键”，新增、修改与删除都算触及，判断只到行、不到列。服务端序列里的每一行都来自某条远端提交，所以本机投影里没有被触及过的行只有本机才有；组装基线时按表名与主键整行跳过被触及的行，只把剩下的行作为基线上传，之后照常只推送新提交。全新设备本机投影为空，一条基线也不产生，服务端序列长度不变，与 `git clone` 一致。附件只上传基线保留的行引用到的哈希，被跳过行的哈希按服务端已有处理，同一个哈希在保留行里再次出现时照常上传。配合 3.3，重新登录同一账号时也不再上传基线。

验收：新设备首次同步后服务端序列长度不变；已有本地数据的设备首次同步只上传本机独有的行，被远端提交触及过的行不进入基线。

### 3.7 服务端快照与浅克隆（G7，P1，协议变化）

服务端一侧已经随 `149b0b2` 实现（[ADR-0043](adr/0043-服务端快照登记与提交序列压缩.md)）：契约新增 `PUT /v1/sync/snapshot` 与 `GET /v1/sync/snapshot`，一台已经同步到序列 N、且没有待推送提交的设备可以登记“序列 N 的快照是附件 X、整库摘要 D”；服务端只保留最新一份，按保留期或预算压力删掉快照之前的提交，并在 head 与 pull 响应里给出 `earliest_seq` 与 `snapshot`。请求的 `after` 落在已压缩区间时返回 410 `history_compacted` 并带回快照位置、哈希与摘要；账号达到 256 MiB 预算时先压缩再判断是否超限。

客户端一侧待做：首次同步先下载快照、把本机投影替换成快照内容、把同步位置改成快照位置，再按 3.2 的剩余部分在快照之上重放未推送的本机提交；本机位置落在已删除区间之前时按“重新克隆”处理，空闲时登记快照。这部分与 [ADR-0043](adr/0043-服务端快照登记与提交序列压缩.md) 列出的客户端任务一起做，两端 schema 不因它变化。

### 3.8 自动留存（G9，P1）

对照 `git gc --auto`：一次提交落库、独占区释放之后的空闲维护里，用空闲检查点那一次统计同时判断提交条数与历史字节，提交超过 500 条或历史字节（提交变更明细与检查点压缩后长度之和）超过 256 MB 时，在维护事务里按同一套边界自动裁剪一次，不新增定时器，也不在写事务里执行。保留口径是“时间优先”：最近 14 天的提交全部保留，覆盖撤销与回执的使用窗口；更早的提交在 256 MB 预算之内继续保留，放不下时从最早的开始删；命名版本与阻塞的读取位置照旧不能越过，下界同时取“时间与预算算出的起点”与“最小阻塞位置加一”中较小的一个。保留天数存在 `app_meta`，数据版本页提供 7、14、30、60、90、180 天六个选项、默认 14 天；自动裁剪与手动裁剪共用同一套边界计算，两边结果因此一致，按留存清理的手动入口保留。

可选的第二步是“压缩旧历史”：7 天之前、90 天之内的提交按天用 `foldChanges` 合并成一条（新的提交类型 `squash`，不可撤销），保留“某天之前是什么样”的整版恢复能力，又不必为每一轮对话留一条记录。先看自动裁剪上线后的历史体积，再决定要不要做。

### 3.9 增量恢复（G10，P1）

恢复不再整库删除重插。目标提交仍在保留历史内、`foldChanges(target, HEAD)` 可用时，把这段净变化反过来逐行写入当前表：修改只写发生变化的列，新增只插缺的行，删除只删多出来的行，外键检查延迟到事务提交，删除按依赖逆序、插入按依赖正序；写入经过原有触发器采集，恢复提交的变更明细与 `state_digest` 由采集自然产生，不再按两份整库投影比较。写完分批核对被改到的行等于目标值，并把“父提交摘要加采集增量”与目标提交记录的摘要比对，通过才追加提交；没有改到的行保持原来的 `rowid`。目标版本的附件只核对目标一侧要写入的行引用到的哈希，未改到的行不重复核对。

起点已被裁掉、中间有清理历史留下的基线跳变或某条提交的变更明细不完整时，`foldChanges` 不可用，退回原来的整库替换；反向写入撞上唯一键互换这类中间状态时，也在同一个事务里退回整库替换，结果同样正确。导入数据包与从版本库备份恢复仍走整库替换。预览与恢复用同一份反向变化：增量路径直接按同一份净变化给出新增、修改与删除的数量，只有退回整库替换时才重建两份投影比较，界面上的数量与影响说明不变。恢复仍是一条 `restore` 提交，代次照常推进，恢复点与确认流程不变。

验收写成用例，位于 `app/test/data/revision_incremental_restore_test.dart`：对 200 次随机写入的历史任取目标提交，增量恢复与整库替换得到的业务表完全相同（两份库回放同一段历史，其中一份删掉一条提交的明细迫使整库替换）；只差一行的恢复不改其他行的 `rowid`（用 `SELECT rowid` 比对），恢复提交带目标投影的整库摘要；起点已被裁掉的历史退回整库替换并给出同样结果；预览的差异与实际恢复的结果一致。实现见 `app/lib/data/revisions/revision_projection.dart` 的 `restore`、`previewRestore` 与 `_restoreByChanges`。

### 3.10 哈希链与完整性检查（G11，P2）

`revision_commit` 的哈希链、摘要与检查点摘要已经随 `24e26c9` 写进数据层：`hash = sha256(parent_hash, uid, kind, 规范化变更明细)` 在 `_appendCommit` 里计算，裁剪之后最早保留的提交记下父提交的哈希作为锚点。`RevisionEngine.verifyIntegrity` 逐条重算保留历史的哈希，父提交还在库里时顺带核对父哈希，再把按当前表重算的摘要与 `HEAD` 的 `state_digest` 比较，因此改动业务行、改动变更明细或改动提交身份都能发现；检查点重建时先比对投影摘要，对不上就不把这份检查点当成起点。数据版本页的“检查数据完整性”入口与导出版本库备份前的自动检查还没有接入，`verifyIntegrity` 目前只由数据层与测试调用。实现见 `app/lib/data/revisions/revision_digest.dart` 与 `revision_log.dart`，测试见 `app/test/data/revision_integrity_test.dart`。

### 3.11 重做（G12，P2）

撤销提交可以再撤销，含义是重做。撤销与重做沿 `reverted_commit_id` 的回指链判断方向：一条提交在链上的层数为 0 时是普通提交，1 是撤销，2 是重做，3 是撤销这次重做；撤销层数为奇数的提交时这次动作是重做，层数为偶数且大于 0 时是撤销这次重做。重做把原提交里除 `message` 以外的变化按正向重新写入当前表，核对规则与撤销同一套：目标提交之后同一格又被修改、或者当前值不等于撤销提交写回的值时拒绝；撤销链上自己的写回不算后续修改，重做之后原提交重新可以撤销。回执不恢复，界面按 `activeCommits` 重新判断回执状态；提交类型仍是 `undo`，`reverted_commit_id` 指向被重做的那条撤销提交，标签、菜单动作与图标按层数显示“撤销”“重做”或“撤销重做”。

`activeCommits`、`undoableCommits` 与 `receiptCommits` 三个筛选入口由撤销服务沿链计算，SQL 只负责取出候选与回指关系，因为 SQL 里的“有没有人回指”只能排除一层；数据版本页对撤销链上的操作先弹确认框，说明会写回还是去掉内容。实现见 `app/lib/data/revisions/revision_undo.dart` 与 `app/lib/ui/data_version_page.dart`，取舍见 [ADR-0044](adr/0044-撤销提交可以再撤销.md)。

撤销链的数据层覆盖到多层与多分支，界面层数只用数据版本页已经加载的提交，链起点不在列表里时按已经走过的层数显示，滚动读取更早的提交之后重新算对。`revision_log.dart` 里只排除一层的三个旧查询已经删除，调用点改成 `RevisionService` 转调的撤销服务；撤销链起点被裁剪时，随动作开放的表会按“撤销操作”判断，材料页更正这类依赖最初动作的表因此可能被误拒。数据层覆盖到多分支链的第 4 层，界面没有专门用例。

### 3.12 作者信息与小修（G13、G14，P2）

`revision_commit` 的 `origin_device` 与 `authored_at` 已经随 `24e26c9` 加进数据层，本机提交的来源为空、作者时间等于 `created_at`，远端提交由同步应用时把服务端的设备与创建时间传进来（`_applyRemote`），并在 `app/test/application/sync_origin_test.dart` 里核对；`reverted_commit_id` 已经建索引。数据版本页还没有显示“来自另一台设备 · 某时某分”，这一步待做。检索索引与记忆索引的处理位置改为 `revision_cursor` 里的非阻塞位置、所有历史读者统一在一处登记，这一项没有做。
