# 服务端实现审查与批次

> 2026-11-27 对 `server/` 的只读审查，按废弃、半成品、不够优雅三类列出 35 处问题，逐条给出位置、证据、改法与风险，再按文件归属分成八个可以并行的批次与一个集成批次。范围只到服务端；表结构与客户端的问题见[数据库结构过度设计审查](数据库结构过度设计审查.md)与[过度设计审查](过度设计审查.md)，本文不重复。当天的执行结果与遗留项见第 10 节。

## 1. 范围与方法

审查对象是 `server/` 下 117 个非测试 Go 文件，共 33,253 行，其中 `internal/api/api.gen.go` 与 `internal/store/db/*.go` 是生成代码，占 9,423 行；另有 97 个测试文件、25,491 行。分类判断以 [ADR-0001](adr/0001-开发阶段不向下兼容.md) 为前提：开发阶段不承诺向下兼容，为旧版本保留的字段、分支与别名都算问题。

检查分四步。先用 `gofmt -l .`、`go vet ./...` 与 `deadcode -test ./...` 确认没有格式、静态检查与不可达函数方面的问题；再把 `config.Config` 的 74 个字段逐个在非测试代码里检索引用，只有 `ReleaseFile` 在配置解析之后不再被读，属正常；然后对每个导出符号检索调用点，区分生产调用与测试调用；最后逐条核对注释与代码是否一致。文中的行号以提交 b41f9ad 为准，改动之后会有偏移，定位时以符号名为准。

## 2. 总体判断

服务端整体已经清理过一轮：静态检查干净，配置项没有定义了却不读的，处理器与存储的分层清楚，注释密度与准确度都高于一般项目。问题集中在四处。第一处是只写不读的字段与只在测试里使用的导出 API，它们不影响运行，却让后来者按错误的口径理解结算与鉴权。第二处是生产路径不可达的分支，包括装配处必填却保留的 501 与“未注入”错误。第三处是同一规则在两处或三处维护，包括上限常量与用户可见文案、默认值、前缀字面量。第四处是超长函数里复制的结算分支。

这些问题大多不影响当前行为，代价出现在下一次改动：改一处漏一处不会编译失败，只会让账号额度、限流或对账的结果与预期不同。因此处置顺序按“零行为变化优先”排列，先做第一类与第二类里不改变对外行为的部分，再动涉及协议、资金与表结构的条目。

[过度设计审查](过度设计审查.md)第 5 节已经记录其中四条，本文只引用、不重复论证：5.1 的 9 套内存存储、5.3 的限流器构造、5.11 的配置默认值、5.12 的 `SetX` 装配器。本文新增的是逐字段、逐分支核对之后的具体位置，可以直接作为开发条目使用。

## 3. 废弃

**S1 模型代理的结算标志没有消费者。** 位置：`internal/llmproxy/metering.go:13-17`、`internal/llmproxy/proxy.go:698-705`、`911`、`979`。`attemptResult.unknown` 的注释写“没有拿到 usage 时结算改用估算”，`rejectedUsage` 按状态码返回 0 或 -1，`proxy.go:911` 用它的符号给 `unknown` 赋值。`finishAttempt`（`attempts.go:62-90`）、结算闭包（`metering.go:67-97`）、`billedTokens`（`metering.go:141-155`）与 `routeAttemptUsage`（`metering.go:102-132`）都不读这个字段，全仓唯一的读取是 `proxy.go:979` 的 `result.unbilled = result.unknown`；`unknown` 一共被赋值 15 次（`proxy.go` 13 处、`prelude.go:168`、`embeddings.go:366`），其余 14 次都不产生效果，400 与 500 实际走同一条结算路径。改法：删除 `unknown` 与 `rejectedUsage`，979 行改为 `result.unbilled = result.usage.Total() <= 0`，相关注释改写成以 `unbilled` 与 `usage` 为准。风险低。

## 4. 半成品

**S11 联系方式验证只覆盖三条上传路由。** 位置：`internal/server/cloud_operations.go:33`、`internal/routepolicy/routepolicy.go:43-55`。门槛写成 `if policy.Upload && requireVerified && !principal.ContactVerified`，而 `Upload` 只在 `POST /v1/backups`、`PUT /v1/blobs/{sha256}`、`POST /v1/sync/commits` 为真；`PUT /v1/sync/snapshot`、`PUT /v1/sync/refs`、`PUT /v1/sync/devices` 是零值。未确认邮箱的账号因此仍能登记快照、写命名版本与设备名册，只是不能推送提交与上传附件。`server/README.md:188`、`server/运维手册.md:297` 与 [ADR-0038](adr/0038-账号与登录方式分开.md) 承诺的是同步、备份与附件写入整体拦截。`cloud_operations_test.go` 用 `cloudOperations(false)` 跑这三条，缺口不会被用例发现。改法：给 `routepolicy.CloudWrite` 增加独立的 `RequireVerified` 字段，把三条同步写接口设为真，在 `cloud_operations.go` 改读这个字段，并补一条未验证账号写快照返回 403 的用例。风险中，会让部分内测账号的写请求开始返回 403，需要产品确认启用范围。

**S12 同步页预算没有下限，配置一低就永久返回 413。** 位置：`internal/syncsvc/service.go:100-105`、`208-218`、`internal/syncsvc/sync.go:72`。`SetMaxPullBytes` 只截上限（`min(n, MaxPushBytes)`），没有下限；单条提交最大 `MaxCommitBytes` 为 2 MiB。页预算配到 2 MiB 以下时，`trimPullBytes` 每页都裁成 0 条，`Pull` 恒回 `ErrPullTooLarge`，已经存入的提交永远拉不下来，只能清空云端数据重来。提交 b41f9ad 已经把写入侧改成“单条只按 `MaxCommitBytes` 判断”，拉取侧的不变量仍只写在 README 的一句话里。改法：装配处强制 `maxPullBytes >= MaxCommitBytes`，低于下限时抬到下限并记一条警告，或在配置层直接报错。风险中，会改变运维可见的配置语义。

**S13 backup 与 blobs 的 service 层校验在 HTTP 路径上不可达。** 位置：`internal/backup/service.go:66-71` 与 `internal/backup/handler.go:53-68`、`internal/blobs/service.go:52-54` 与 `internal/httpx/spool.go:79-89`。handler 已经比对 `X-Schema-Version`，`SpoolVerified` 已经用 `ContentLength` 与 `MaxBytesReader` 卡住大小，所以 `ErrSchemaVersion`、`ErrTooLarge` 只在测试里出现；同一规则与同一句文案在两处各写一份。改法：只保留一层判断，建议 handler 只解码、service 全权判断，删除另一份与只为它存在的哨兵错误；或者反过来把判断全部提到 handler，service 只收已经校验的参数。风险低。

**S14 auth 处理器里有五条走不到的分支。** 位置：`internal/auth/handler.go:285-286`、`342-349`。`RequestIdentityVerification` 已经先执行 `errors.As(err, &pause)`，`mailPauseError` 的值接收者 `Is` 对任何同类错误成立，紧随其后的 `errors.Is(err, ErrMailPaused)` 不会执行。`ForgotPassword` 的四条更彻底：`RequestPasswordReset`（`service.go:676-683`）把冷却、收件预算、实例总量与暂停都转成 `nil` 返回，`ErrSenderUnsupported` 又要求库里存在手机号或微信身份，而注册只写邮箱（`service.go:376-385`），所以 342、344、346、348 四条不可达，两处 `Retry-After` 取法不同也没人知道哪条生效。改法：删除这些分支，在 `RequestPasswordReset` 的注释里写清“冷却与预算一律按已受理返回”。风险低。

**S15 装配处必填、代码里却保留“未装配”的降级分支。** 位置：`internal/server/routes.go:101-109`、`internal/syncsvc/handler.go:399-401`、`internal/backup/reconcile.go:62-67`。`DeleteV1Cloud` 在 `cloud == nil` 时回 501，而 `build()`（`server.go:371`）总会注入；`ErrSnapshotUnsupported` 只在没有调用 `SetAttachments` 时出现，而装配处必调（`server.go:323`）；对账的两条“没有注入”错误同理。三处都在维护一条生产中不存在的路径，注释还把它当正常配置描述。改法：改成必填构造参数，删除 501 与“未注入”分支，对应[过度设计审查](过度设计审查.md)5.12。三个文件分属三个批次：`routes.go` 随批 4，`syncsvc/handler.go` 随批 5，`backup/reconcile.go` 随批 6。风险低。

**S16 配置里的布尔项只认 `"1"`，写错会静默改变行为。** 位置：`internal/config/config.go:386`、`392`、`423`、`460`。`get("ZHIXIN_LLM_REQUIRE_VERIFIED_CONTACT", "1") == "1"` 意味着写 `true` 会静默变成 `false`，直接关掉聊天与嵌入的 403 门槛；`ZHIXIN_MAIL_LOG`、`ZHIXIN_APPLY_SCHEMA`、`ZHIXIN_SYNC_COMPACT` 同理。同一函数的时长与整数都走 `dur` 与 `num`，写错会记错误，只有布尔是三种结果。另外 `config.go:589` 的 TTL 大小校验以 `len(errs) == 0` 为前提，任何一处无关错误都会把它跳过。改法：抽一个 `boolean(key, def)` 助手，取值不是 `0` 或 `1` 时记错误；去掉 TTL 检查前的 `len(errs) == 0`。风险低，需要先核对现有部署环境变量的写法。

**S17 `startup.go` 的分支不可达，文案与条件也不符。** 位置：`internal/server/startup.go:80-82`、`internal/config/config.go:512-516`。`prepareStartup` 前面已经保证“数据库为空时随机生成密钥”，配置层又把“有管理令牌、有数据库、没有密钥”判为错误，所以 `errors.New("ZHIXIN_SECRET_KEY is required for administration with PostgreSQL")` 只有测试能构造出来；条件里没有 `DatabaseURL`，文案却说“with PostgreSQL”。改法：删除分支，配置层只留一处校验。风险低。

**S18 即刻收失败重试的幂等口径，三处注释互相矛盾。** 位置：`internal/nowpay/handler.go:24`、`315-333`、`342`、`internal/nowpay/client.go:114`、`internal/store/queries/nowpay.sql:165`。handler 注释说“创单失败记 failed，下一次点击用同一个键再试；请求号保留在行里”，但 `failed` 落进 `default` 分支，会生成新的 `OutRequestNo` 并调用 `ReplacePurchaseLink`；SQL 注释也写“换成新的 out_request_no”；而 `client.go:114` 把 `OutRequestNo` 定义为“重试必须保持原值”的幂等号。代码按换号执行，一次失败点击重试会在即刻收侧产生第二个创单请求。2026-11-27 定：复用原请求号。改法：`failed` 状态重试时沿用行里已有的 `OutRequestNo`，不再生成新号，`ReplacePurchaseLink` 只在没有旧行时使用；`handler.go:342` 与 `queries/nowpay.sql:165` 的注释改成“同一个幂等号重试”，补一条“失败之后重试复用原请求号”的用例。风险高，涉及资金路径；上线前与即刻收对账一次，确认重复提交同一个 `out_request_no` 不会产生第二笔订单。

**S19 `RecordPattern` 与 `SetPattern` 在生产链上一次不生效。** 位置：`internal/httpx/middleware.go:49-62`、`internal/httpx/headers.go:26`、`internal/testutil/testutil.go:99-107`。`SecurityHeaders` 在访问日志与业务处理器之间把 `w` 换成 `*cacheGuard`，而 `cacheGuard` 只内嵌 `http.ResponseWriter` 接口，`statusRecorder.SetPattern` 不会被提升；`RecordPattern` 的类型断言因此必然失败。访问日志里正确的 route 来自 `AccessLog` 的兜底 `r.Pattern`，注释里“net/http 在外层中间件克隆请求之后才写 Pattern”的前提不成立。`testutil.NewServer` 没有套 `SecurityHeaders`，测试环境里反而是通的，两套链掩盖了问题。改法：让 `cacheGuard` 实现 `SetPattern` 并转交，或让 `RecordPattern` 沿 `Unwrap` 逐层查找；补一条走完整 `Build` 装配、断言 route 来源的用例。风险低。

## 5. 不够优雅

**S20 feedback 与 retention 的处理器几乎整份重复。** 位置：`internal/feedback/handler.go:15-102`、`internal/retention/handler.go:15-91`。结构体字段、`NewHandler` 的 nil 兜底、`SetGlobalLimiter`、`globalLimiterKey` 常量、按地址与全局两层限流的整段代码、`valueOrEmpty` 逐字相同，只有业务调用不同。改法：在 `httpx` 增加一个公开写入口的限流与解码组件（新文件），两个包各留业务部分。风险低。

**S21 `deref` 有三份。** 位置：`internal/accountadmin/admin.go:394`、`internal/feedbackadmin/admin.go:130`、`internal/llmproxy/admin.go:689`。三个包各写一个泛型解引用，签名只有参数名不同。改法：放进一个共用的内部小包，三个包改引用。风险低。

**S22 `build()` 里 11 段限流器构造与一个没有名字的常量。** 位置：`internal/server/server.go:236-272`、`329-332`。11 个 `ratelimit.New(rate.Limit(cfg.X), cfg.Y, 15*time.Minute, cfg.RateLimitKeys)` 只有速率与容量不同，`15*time.Minute` 出现 11 次；`adminLimits` 还单独放在 60 行之后的 331 行。改法：增加 `newLimiter(ratePerSecond float64, burst, keys int) *ratelimit.Limiter`（非正值返回 nil），`15*time.Minute` 提成命名常量，`adminLimits` 并回同一段。风险低，对应[过度设计审查](过度设计审查.md)5.3。

**S23 默认值在配置层与业务层各写一份。** 位置：`internal/config/config.go:389`、`411`、`413`、`442`、`434-436` 与 `internal/auth/service.go:159`、`163`、`internal/feedback/service.go:25`、`internal/auth/mailer.go:92-100`、`129-137`。备份份数、未验证保留天数、会话上限、反馈保留天数的默认值在两处各写一遍，靠注释“与配置项一致”人工同步；SMTP 的 4、3、30 秒更是在配置层、`NewMailer` 与 `NewSMTPMailer` 三处各写一遍，而 `num` 与 `dur` 已经拒绝非正值，后两处生产中不会命中。改法：默认值只放配置层一处，业务层的兜底只服务测试并在注释里写明。这条按文件拆开执行：`auth/service.go` 的两个默认值随批 2 删除，`feedback/service.go` 的默认值随批 8 删除，SMTP 的三处默认值随批 4 合并，`config.go` 里保留唯一一份默认值。风险低。

**S24 设备名有两套清洗，行为还不同。** 位置：`internal/backup/service.go:134-140`、`internal/auth/service.go:394-400`、`server/api/openapi.yaml:770-773`。备份侧超过 64 个字符就整段置空，auth 侧截断到 64，而契约里 `X-Device-Name` 写的是 `maxLength: 256`。同一份输入在两个入口得到两种结果，超限还不报错。2026-11-27 定：上限取 64。改法：把两处清洗合并为一个共享函数，超过 64 个字符时截断，不置空；代码在批 6 改，`internal/auth/service.go` 只改 `cleanDevice` 这一个函数，批 2 开工时以合入后的版本为准；契约的 `maxLength` 由 256 改成 64 在批 9 随重新生成一起提交。风险低。

**S25 一页的字节预算有三份实现、两套口径。** 位置：`internal/store/queries/sync.sql:104-122`、`internal/syncsvc/service.go:208-218`、`235-249`、`internal/syncsvc/sync.go:476`。PostgreSQL 侧用 `octet_length(...)+256` 的窗口函数估一遍，服务层再用 `json.Marshal` 裁一遍，内存实现还要裁一遍；同一条提交在一页里被序列化两次，两边给出的条数不同，S12 的 413 正是第二道裁剪造成的。改法：预算只留服务层一处，删掉 `Store.After` 的 `maxBytes` 参数与内存实现的额外裁剪，SQL 只按 `page_limit` 取。风险中，涉及查询与生成代码。

**S26 上限常量与用户可见文案各写一份。** 位置与现象见下表，改法统一为文案用常量拼接；契约里写死的“最近五条”改到批 9 统一处理，原因是 `api.gen.go` 由批 1 与批 9 拥有，改动契约描述要重新生成它。契约改动已经获准，排在批 9 只因为文件归属。

**S27 `MaxPushBytes` 一个常量三种含义，装配处又用另一个表达式表示同一数值。** 位置：`internal/syncsvc/sync.go:71`、`internal/syncsvc/service.go:102`、`282`、`internal/syncsvc/handler.go:26-28`、`internal/server/server.go:307`。它同时是整批推送上限、拉取页预算的上限（一个拉取参数由推送常量封顶）和 JSON 请求体上限的封顶；装配处再写 `16*cfg.MaxJSONBytes`，默认配置下恰好等于 16 MiB，一旦调整 `MaxJSONBytes`，请求体上限变了而 `Push` 的判断仍是 16 MiB，同一批提交在两层得到不同结论。改法：装配处直接传 `MaxPushBytes`（或给它独立配置项），拉取上限换成按 `MaxCommitBytes` 语义命名的常量。风险低。

**S29 密钥长度常量与生成实现脱钩，19 MiB 有两份。** 位置：`internal/auth/key.go:33-38`、`66`、`77`、`internal/auth/budget.go:7`、`internal/auth/password.go:19`。`apiKeyRandomLength = 32` 与 `apiKeyChecksumLength = 4` 参与 `apiKeyLength` 的形状判断，真正产出长度的是 `make([]byte, 24)` 与 `sum[:3]`；调大常量会让新签发的密钥被判为非法，而生成器不变、接口照回 201。`passwordMemoryMiB = 19` 与 `argonMemoryKiB = 19 * 1024` 是同一个量的两份声明，注释自己写“改哈希参数时两处要一起看”。改法：生成器由常量反推字节数；单次 Argon2 占用只定义一处，预算由它换算。风险低。
