# 知新 · ER 数据模型

> 本文是数据结构的唯一真相，目标数据库是 SQLite 3，整个应用只有一个本地文件。概念定义以 [00-产品定义](00-产品定义.md) 为准，界面读写以 [02-产品与交互](02-产品与交互.md) 为准，本文只定义表、字段与派生规则。
>
> 当前结构为 schema 32，共 13 张业务表、1 张设置表与 2 张记忆使用统计表，另有版本、附件对象与同步簿记 12 张表：业务表主键是 UUIDv7 文本，由写入方在插入前生成，外键、版本明细里的 `row_key`、撤销与恢复的定位、检查点投影与两类数据包都按这个文本标识（[ADR-0018](adr/0018-业务表主键改用UUIDv7.md)）；讨论可以独立存在并带入材料页码；一条讨论就是一条学习记录，题目由开始作答时确定的用户消息与图片派生，作答直接挂在这条记录上，不再单独存题目表。题目来源只保留用户写、拍图与模型生成，图片文字由多模态模型直接读出；学习事项只保留一段说明，系统学习的每一步就是学习事项，材料引用先由程序核对，学习判断只保存模型判断与用户提供的核对依据。界面回执存的是提交编号，撤销读提交历史，不再单独保存操作日志。本地库与数据包只接受当前版本；版本不一致的旧库在打开时清空重建，其他版本的数据包在恢复入口拒绝，内测与公测期间同样按清空处理（[ADR-0017](adr/0017-表结构变化仍清空数据.md)）。这一版沿用并收口上一版的做法：完整性只有整库摘要一个原语，`HEAD` 与提交编号并进单行状态表，每日截止小时并入 `app_meta`，学习计划的当前页由步骤算出，讨论是否结束由 `ended_at` 推出，记忆改为三类标签，召回与主动搜索先记在本机缓冲表里，再由冲刷汇总进按设备一行的使用统计（[数据库结构过度设计审查](数据库结构过度设计审查.md) 的 S16 至 S23、[ADR-0051](adr/0051-记忆改为自由文本条目并走文档检索路径.md)、[ADR-0054](adr/0054-数据版本位置标记补强.md)）。
>
> 本文的 DDL 与 `app/lib/data/db/drift/tables.dart` 表类建出的结果一致，索引由表类上的 `@TableIndex` 声明。即刻收的购买入口、积分核销流水与余额副本由服务端 PostgreSQL 保存，定义见 [server/schema.sql](../server/internal/store/schema.sql) 与 [ADR-0067](adr/0067-聊天额度改走即刻收积分包.md)、[ADR-0069](adr/0069-积分余额的本地副本与预留放行.md)。

## 1. 设计原则

| # | 决策 | 影响 |
|---|---|---|
| D1 | 学习记录独立存在，不关联知识点与题型 | 少一张分类树与两张关联表，用户不必先归类 |
| D2 | 尝试是证据的最小单位 | 同一道题可以有多条尝试，每次记提交、对错、提示、独立与延迟；对错可以留空 |
| D3 | 一次学习用 `study_session` 表示，多次尝试共用一个结果 | 与对话、日程、记忆读同一个标识 |
| D4 | 记忆单独建表，带来源、适用范围与有效期 | 可查看、纠正、删除，临时限制会过期 |
| D5 | AI 的每次写入形成一条数据提交 | 撤销与回执从提交历史读取，不需要单独的日志表 |
| D6 | 错题不建表 | 题目状态由最近一条已提交尝试派生，读时计算 |
| D7 | 时间统一用 TEXT | `YYYY-MM-DD`、`HH:MM`、`YYYY-MM-DD HH:MM:SS`，可直接比较与排序；跨设备的排序不依赖客户端时间，命名版本墓碑的比较用服务端时间 |
| D8 | 本机单文件是主副本，登录后与服务端同步（[ADR-0008](adr/0008-取消单机边界引入账号同步与模型代理.md)） | 导出 zip 包仍是本机备份；登录后版本库备份可上传，增量同步前需把业务表主键改为全局唯一 |
| D9 | 讨论可以独立存在，不要求目标归属 | 求助不必先建目标，记录按讨论标识打开 |
| D10 | 材料按页保存，引用先由程序核对 | 回答能回到原文位置，对不上的引用标为未核实 |
| D11 | 系统学习的步骤就是学习事项 | 步骤可以和普通事项一样预约、共用完成状态 |
| D12 | 学习判断按来源分别保存 | 模型判断与用户提供的核对依据各自保存结论与依据，两者都不标记是否核对；用户自评由作答记录推出 |

补充两条：业务表都带 `created_at`，可变实体再加 `updated_at`；只追加的表（`message`）不设 `updated_at`。图片压缩后按内容哈希分块保存在同一个库里，`message.image_hashes_json` 只写哈希引用，界面读取时把临时文件补回 `question_images/`；导出只打包消息仍引用的图片，应用启动时清理没有引用的临时文件。附件引用只从表结构声明的附件引用列里收集：`material.source_file_hash` 是单个哈希，`message.image_hashes_json` 是哈希组成的 JSON 数组，其他文本列即使恰好是同样的字符形状也不算引用。

## 2. 实体总览

13 张业务表与 1 张设置表，分五组；记忆使用统计、数据版本、附件对象与同步簿记单独列出。两张记忆使用统计表里，`memory_usage` 按“记忆编号＋设备编号”保存计数，`local_memory_use` 是只在本机累积的召回缓冲，表名前缀 `local_` 让它不参与版本采集、检查点投影与数据包。数据版本一侧除了提交、变更明细、命名版本与检查点，还有单行状态 `revision_state`（采集上下文、下一个提交编号与 `HEAD`）、命名版本的墓碑 `revision_ref_tombstone`、登记历史下游读取位置的 `revision_cursor`、登记附件引用的 `revision_asset_ref`、记录远端覆盖的本机修改的 `revision_conflict`，以及记录已被远端提交取代的本机格子的 `sync_shadow`。

| 组 | 表 | 作用 |
|---|---|---|
| 设置 | `app_meta` | 版本、每日截止小时、偏好、外观以外的设置与人格配置、插件的启停状态 |
| 学习 | `learning_goal`、`plan_item`、`schedule_block`、`timetable_entry`、`study_session`、`study_plan` | 目标、事项、时间块、课表、一次学习、系统学习 |
| 题目与讨论 | `attempt`、`conversation`、`message` | 作答、讨论与消息；题目由开始作答时确定的用户消息派生 |
| 材料与评估 | `material`、`material_page`、`assessment` | 材料、材料页、学习判断 |
| 记忆 | `memory`、`memory_usage`、`local_memory_use` | 记忆条目、按设备的使用统计与本机召回缓冲 |

```
learning_goal 1 ── n plan_item 1 ── n schedule_block
                     │  └── n study_session 1 ── n attempt
                     └── n study_plan 1 ── n plan_item（学习步骤）

conversation 1 ── n message
conversation 1 ── n attempt（作答直接挂在学习记录上）
conversation 1 ── n plan_item（来源讨论）
material 1 ── n material_page
material 1 ── n study_plan
assessment n ── 1 attempt
memory ── source_kind + source_id ──▶ message / attempt / study_session
revision_change ── table_name + row_key ──▶ 任意业务表
```

## 3. 派生规则

### 3.1 题目状态与错题

不存状态列，读取时按最近一条已提交尝试计算。

| 最近一条已提交尝试 | 题目状态 | 列表位置 |
|---|---|---|
| 没有 | 未作答 | 记录页「最近带入」 |
| `is_correct = 1` | 已解决 | 记录页「做对过」 |
| `is_correct = 0` | 待处理 | 记录页「待处理」，即错题 |

`submitted_at` 为空表示未提交尝试，只挂帮助与草稿，不参与状态计算。同一道题的多次尝试全部保留，界面按时间倒序列出。未提交尝试也可以带一条用户填写的核对依据，作为草稿的一部分；提交时更新同一条判断，不再新增第二条。

### 3.2 一次学习

`study_session` 在用户从讨论、题目或日程开始一次学习时创建，同一场次内的多次尝试共用它。开始时写入所属目标：从学习事项开始时取事项的目标，从讨论开始时取讨论的目标，再次作答同一道题时沿用上次场次的目标，没有归属时留空。开始学习时如果提供了学习事项，就按 `plan_item_id` 匹配未结束场次；没有提供学习事项时，才按 `goal_id` 精确匹配，其中空目标只匹配空目标。这样不同学习事项或目标下的场次不会互相复用。离开学习页时写 `ended_at`，按本次已提交的尝试推出 `outcome`：最近一次答对为完成，最近一次答错但本次有答对为部分完成，本次都没有答对为没做成，没有提交过时结果留空；本次最近一条写下的困难同时写进 `summary`。`plan_item.status` 不在学习结束时回写，结束事项由事项自己的完成操作负责。再次进入同一题目时接着未提交的尝试与草稿，但已结束的场次不复用，会新建场次。

### 3.3 记忆检索

记忆是自由文本条目，`kind` 取情景、语义、程序三类，正文允许 Markdown、换行与多句条件，表的上限 2000 字，召回预算做出来之前写入仍限 200 字（[ADR-0051](adr/0051-记忆改为自由文本条目并走文档检索路径.md)）。生成回答时只取满足以下条件的记忆：`status = 'active'`，`valid_until` 为空或不早于当前时刻，并且 `scope` 为空或等于本次目标（`goal:<id>`）或材料（`material:<id>`）。常驻由字段推出，不另存：标签是语义或程序、范围是全局、没有有效期的记忆每轮必带；情景记忆不常驻，只靠检索与模型的主动搜索。每一轮进入提示词的记忆分三层：常驻；当前范围内检索得分达到下限的相关记忆；其余由模型用 `search_memory` 主动搜索。相关程度相同时再按 `updated_at` 倒序。用户写入时由模型顺带给出的检索线索存在 `search_terms` 里，只进全文索引、不在界面显示，用来补用词不重合的缺口。常驻有字数预算，超出的部分退回相关层。用户本轮明确说出的条件优先于旧偏好表达式；记忆分情景、语义、程序三类，程序记忆不能改变判分、引用与写入权限。单条记忆进入提示词时超过 200 字截断，这一条在召回预算做出来之后改为总字数预算。启用的人格不改变这里的召回条件与排序：人格只影响提示词里的风格段落，风格冲突按用户本轮说明、人格、记忆中的做法依次优先。待确认的记忆提案不写在 `memory` 表里，用户确认之前不进入召回。

记忆的使用统计另存在 `memory_usage` 与 `local_memory_use` 两张表里，用来给没写有效期又很少被用到的记忆降权，不让模型猜过期。`memory_usage` 按“记忆编号＋设备编号”一行，保存进入相关层的次数（`recall_count` 与 `last_recalled_at`）与由 `search_memory` 读到的次数（`search_count` 与 `last_searched_at`），主键是单列 `id`，编号按 ADR-0053 用 UUIDv5 由设备编号与记忆编号算出，同一对输入重复汇总得到同一个值；汇总时各设备计数相加、时间取最大值，因此不产生同步冲突。召回与搜索先记在 `local_memory_use`：一行是某一刻把某条记忆放进了相关层（`kind = 'recall'`）或由 `search_memory` 读到（`kind = 'search'`），只保存记忆编号、种类与时刻，主键是整数行号，表名前缀 `local_` 使它不参与版本采集、检查点投影与数据包。应用进入后台且距上次冲刷不少于一天时，冲刷在一条命令里把缓冲行汇总进统计表再删除缓冲行，汇总与删除在同一个事务里完成，所以缓冲表不再需要水位列，重复冲刷也不会重复累加；这条冲刷形成一条类型为 `maintenance`、行为者为 `system` 的提交，带回执规则与普通提交相同，不另外触发同步。常驻的记忆不降权，新写入的记忆有保护期，降权只改排序与整理提示，不自动删除；缓冲行随整库备份恢复，但恢复点之后、冲刷之前的计数会丢失，计数只用于排序与整理提示，所以这个代价可以接受。

用户修改或删除记忆时，原地改写 `memory.content` 或把 `status` 改成 `deleted`；删除仍是改状态、不物理删行，作答提案靠已删除的行判断“这次作答处理过”。旧内容由提交日志保存，修改与删除都是带回执的提交，撤销沿用现有机制。用户确认保留一条记忆时写 `memory.reviewed_at`，这一列不连带更新 `updated_at`，不触发索引重建。

### 3.4 建议与本地兜底

有模型时由模型给出 1–3 条下一步，每条写清做什么与做到什么算结束，材料出处与题号写在标题或动作里，不单独建列。模型未配置、调用失败或没有给出正文时，按固定顺序给一条：

1. 今天已经排定且未完成的时间块；
2. 截止最近的待办事项；
3. 最近一条待处理题目。

兜底结果标明“本地建议”，不伪装成模型回答。

### 3.5 撤销

一次业务写入就是一条提交，`revision_change` 保存这次提交里的行级净变化：新增记修改后的整行，删除记删除前的整行，更新只记发生变化的列。撤销时在同一个事务里重新读取目标提交与当前行，核对目标提交之后同一行的相关列没有又被修改、当前值仍等于提交后的值、恢复后的时间不与课表或别的预约冲突，全部通过才按反向写入并追加一条撤销提交；撤销新建的学习事项前还要确认它没有时间块、学习场次或系统学习计划归属，避免级联删除后续数据。撤销提交还可以再撤销，含义是重做：沿 `reverted_commit_id` 的回指链判断层数，层数为奇数时这次动作是重做，为偶数且大于 0 时是撤销这次重做；重做把原提交里除 `message` 以外的变化按正向写回，核对规则与撤销相同，提交类型仍是 `undo`、回指被重做的那条撤销提交，消息里的回执不恢复，界面按提交是否仍生效重新判断（[ADR-0044](adr/0044-撤销提交可以再撤销.md)）。整版恢复或导入之后更早的提交不再进入撤销范围。现在覆盖目标、记忆、时间块、学习事项、课表与课表导入，以及消息里的回执字段，新增或删除消息本身仍不进入撤销，破坏性操作先在界面上确认。每日截止小时写在 `app_meta` 的 `day_cutoff_hour` 键上，而 `app_meta` 不参与版本采集，改动不形成提交，也不进入这里的撤销范围，应用根恢复之后重新读取设置，界面与归属日口径都使用当前的值（[数据库结构过度设计审查](数据库结构过度设计审查.md) 的 S4）。记忆页的新增、修改与删除同样形成提交，提示条给出撤销；撤销修改写回内容、有效期与检索线索，撤销删除把状态改回 `active`，撤销新增时这一行随之移除，内容与有效期都没有变化时不形成提交。讨论卡片与安排页的即时回执保存提交编号，重新打开时按提交是否仍可撤销决定按钮是否出现；消息里的回执字段不整行回滚，撤销只清掉指向那次提交的条目，同一消息里更晚留下的回执不会被一并抹掉。数据版本页按完整提交历史列出提交，展开“查看明细”逐项显示表与字段，能比较当前版本并撤销或重做，列表与撤销入口共用同一份结构判断，不能撤销或重做的提交直接禁用并写出原因，安排页的“AI 的改动”只列模型写入的记忆与接受下一步建议这几类提交，用户在记忆页自己改的记忆不在这里。清理本机历史或裁剪之后，消息里指向已无变更明细的提交回执会去掉提交编号；回执清理本身作为一条 `maintenance` 提交写入，不可撤销；撤销会把失效的提交编号装回消息，要回到更早的状态请用整版恢复。

撤销的业务约束由应用层注册，数据层只做代次、后续修改、当前值与表名单这些通用核对：预约冲突、学习事项归属与课表三类规则实现 `UndoGuard`，各自声明负责的表与随动作开放的表，生产装配在 `app_scope` 里一次注册。撤销核对与写回都排除 `updated_at` 这类维护列：目标提交之后同一行改过别的列仍可撤销，写回时维护列写撤销时刻而不回到旧值，所以撤销之后这些时间不会早于撤销发生的时间。远端提交与普通写入适用同一份表名单与同一套核对。撤销生效之后再重建图片缓存，缓存失败只返回一条说明，不把已经写回的数据报成失败，下次打开应用时重试。

## 4. 完整 DDL

下面是 drift 表类 `app/lib/data/db/drift/tables.dart` 建出的实际结构，索引在表类上的 `@TableIndex` 声明、由 drift 建表时一起创建。这份文本与建库结果逐表比对（见 `app/test/docs/schema_doc_test.dart`），改表结构时先改表类，再把生成结果抄回这里。

```sql
PRAGMA foreign_keys = ON;
PRAGMA journal_mode = WAL;

CREATE TABLE "app_meta" (
  "key" TEXT NOT NULL,
  "value" TEXT NOT NULL,
  "updated_at" TEXT NOT NULL,
  PRIMARY KEY ("key")
);

CREATE TABLE "learning_goal" (
  "id" TEXT NOT NULL,
  "title" TEXT NOT NULL,
  "scope_text" TEXT NULL,
  "due_date" TEXT NULL,
  "status" TEXT NOT NULL DEFAULT 'active' CHECK("status" IN ('active', 'paused', 'done')),
  "created_at" TEXT NOT NULL,
  "updated_at" TEXT NOT NULL,
  PRIMARY KEY ("id")
);

CREATE TABLE "asset_object" (
  "hash" TEXT NOT NULL,
  "byte_length" INTEGER NOT NULL CHECK("byte_length" >= 0),
  "created_at" TEXT NOT NULL,
  PRIMARY KEY ("hash")
);

CREATE TABLE "asset_chunk" (
  "hash" TEXT NOT NULL REFERENCES asset_object (hash) ON DELETE CASCADE,
  "seq" INTEGER NOT NULL CHECK("seq" >= 0),
  "data" BLOB NOT NULL,
  PRIMARY KEY ("hash", "seq")
);

CREATE TABLE "material" (
  "id" TEXT NOT NULL,
  "title" TEXT NOT NULL,
  "kind" TEXT NOT NULL DEFAULT 'text' CHECK("kind" IN ('text', 'slides', 'book', 'other')),
  "source_ref" TEXT NULL,
```

## 5. 表与字段说明

### 5.1 讨论与消息

讨论按 `id` 打开，日期只用于展示和筛选，不再按天合并成一段对话，因此跨天返回时恢复的是同一条记录。`goal_id` 为空表示无归属，创建讨论不要求先有目标；`goal_id` 只在用户明确选择时写入。`entry_kind` 记录这次求助来自文字、图片还是两者，用于在记录里区分只有原图的讨论。讨论是否结束不再单独占一列，`ended_at` 非空表示已经结束，结束一次讨论写入这个时间，再次发送消息时清空它；记录列表按 `updated_at` 排序，不按结束状态筛选。列表排序与“最后一条”的时间都用 `updated_at`：发消息、设目标、换材料、结束与重开讨论都推后这个时间，每一项都算一次学习行为，所以按它排到前面是有意的（[数据库结构过度设计审查](数据库结构过度设计审查.md) 的 S6、S20）。`title` 取首条用户消息的短标题，只有图片时写“图片求助”。

图片压缩后按内容哈希分块保存在同一库的 `asset_object` 与 `asset_chunk` 里，`message.image_hashes_json` 只保存哈希引用，列名按内容写“哈希”而不是“路径”，界面读取时从数据库补回 `question_images/` 下的临时文件；只有图片、没有文字时 `content` 是空字符串，界面按图片显示。`structured_json` 保存本次回答是否来自模型、记忆卡片、引用、下一步建议和已接受的建议标题；记忆卡片分别记待确认、已写入与已忽略三种状态，工具调用本身不写入历史。本轮读到的材料页只在 `used_pages` 里记材料与页码，重试时按这些位置重新读取当前保存的原文，因此更正、删除与换目标都会在下一次读取时反映出来。未接受的建议只留在这条消息里，不产生 `plan_item`；推断的记忆在用户点“记下”前不写入 `memory`。

### 5.2 事项与讨论的归属

`plan_item` 在 `goal_id` 之后增加 `conversation_id`，指回产生这项事项的讨论；接受一条下一步建议时，由用户在选择表里明确目标，未选择就不写 `goal_id`。创建事项与在原消息里记下已接受标题在同一条提交里完成，回执保存提交编号，重新打开讨论不会把同一条建议再保存一次，撤销这次提交时已接受的标题一并去掉。创建讨论或事项都不改动既有 `schedule_block`，普通求助不写预约。

题目不再单独存表：一条讨论就是一条学习记录，开始作答时，当时最后一条用户消息记进 `conversation.question_message_id`，题干与图片从这条消息读出，`attempt.conversation_id` 直接指向这条记录。用户先问方法、后来才补完整题目时，后来那条消息成为原题；之后再追问，已经确定的原题不改写。只有图片时消息 `content` 为空，界面按“图片题目”显示，原文仍是原图。讨论里的助手回答不再复制进 `attempt.help_json`，求助时从消息里直接作为帮助带入。应用在 `attempt.help_json` 的帮助条目中保存正文来源 `from_model`、收尾状态 `notices`、失败类型 `model_failure` 与这次读到的材料页 `used_pages`，因此重新打开学习页时可以从当前尝试的最后一条帮助恢复说明与重试入口，并按这些位置接续原文；早期条目缺少这些字段时仍按已有正文显示。清空一条学习记录会删除它的消息与作答，作答随外键级联删除；记录与题目从此只有一个标识。

`study_session.conversation_id` 记录这次学习属于哪条讨论，未结束场次按记录复用；记录上的目标或事项改变时先结束旧场次，再按新的归属新建，已经结束的场次保留原归属。`attempt.solution` 单独保存用户整理的解法，不覆盖答案、帮助与困难；`attempt.redo_of_attempt_id` 指向独立重做时被复查的那次已提交作答，重新打开学习页仍能判断这次是重做，提交时的 `delayed` 由两次作答的实际间隔决定。`attempt.delayed` 仍表示是否间隔后重做，`independent` 只表示用户对独立性的声明，两者不互相推断。

### 5.3 状态约定

`learning_goal.status` 只保留 `active`、`paused`、`done`，分别对应进行中、暂停与结束三个操作；`deferred` 与 `archived` 没有写入方，不再保留。创建新目标不再归档已有目标，多个目标可以同时有效。暂停只改目标状态；用户确认时可以取消这个目标下未开始的弹性安排，固定安排、其他目标的安排、独立讨论与已完成记录保持原样。取消的块状态改为 `cancelled`，不删除原行，目标状态与这些块在同一条提交里写入，撤销这次提交时一起回到暂停前；待取消的预约在事务内按目标重新读取，一次写入，写入行数与清单不一致时整组回滚；改期仍由“排一排”的确认流程处理，改期后状态回到 `planned`。已取消的预约恢复为待开始时，同样核对课表与其他预约，冲突时保持取消状态并说明原因。

`plan_item.status` 保留 `todo`、`doing`、`done`、`deferred`。`deferred` 由事项的“暂缓”操作写入，恢复待办写回 `todo`；事项的 `moved` 改名为 `deferred`，没有写入方的 `skipped` 不再保留。`schedule_block.status` 保留 `planned`、`done`、`cancelled`，`cancelled` 只由暂停目标时的取消操作写入；时间块的 `moved` 改名为 `cancelled`，没有写入方的 `missed` 不再保留。

所有事项状态变化经过同一服务入口；同一系统学习计划同时最多有一个 `doing` 步骤，设为进行中时会在事务中将其他步骤恢复为待做。新建或改动计划时间块时，在同一事务中检查它是否与其他 `planned` 时间块或课表时段重叠，跨日时按每个自然日核对；已取消或已完成的时间块不占用未来时间。新增课表时同样先核对，按这条课表每周重复的时段逐日比对待开始预约，已经结束的预约不参与，重叠时拒绝写入并指出冲突的那一条预约。

### 5.4 材料、页码与引用

一页一条记录，页码从 1 开始；同一材料同一页码唯一。添加一页只新增，页码已存在时拒绝写入并提示到材料详情更正；导入的一批页码不得重复，出现重复或无效页码时整批拒绝，材料与页码都不落库。用户更正页内文字时更新 `material_page.content`，材料行的 `updated_at` 随同一条提交更新，修改前后的整行留在历史里，旧引用因此不再通过核对。更正保存后可以从提示条撤销，材料详情按页列出更正记录；撤销会核对这一页与材料行在更正之后是否又被修改，通过后整组写回并追加撤销提交。回答里的引用写在 `message.structured_json` 的 `citations` 里，包含材料、页码、逐字摘录与核对结果；程序只在本轮真正提供过的材料页里按页码取回原文，先核对当前版本与提供时一致，再去掉空白逐字比对，本轮没有提供过的页或已经更正的旧原文不进入引用，对不上的保留原文并标为未核实，界面显示“未能核对”。回答上下文只读当前有效的记忆与材料页，检索只使用同一目标或未归属的材料与讨论，其他课程的内容不进入本次上下文。

导入 Word 时，`material.source_file_name` 保存原文件名，`source_file_hash` 指向按 SHA-256 分块保存的附件对象，原文件、材料行和正文片段在同一条提交中写入。`material_page.page_no` 保存从 1 开始的片段顺序，`label` 保存所在标题，讨论、检索与系统学习继续按材料编号和位置编号定位，引用中的 `is_docx` 决定界面显示片段编号。手动粘贴的材料使用用户填写的页码，两个文件字段均为空。

### 5.5 系统学习与学习判断

学习计划只记录材料范围与状态；每一步是 `plan_item`，由 `study_plan_id` 指回计划、`seq` 决定顺序、`page_from` 与 `page_to` 标出范围、`note` 保存一段说明，`(study_plan_id, seq)` 唯一。当前页不再写在计划行里，读取时由步骤算出：进行中或排序最靠前的未完成步骤的 `page_from` 优先，全部完成时取已完步骤里最大的 `page_to`，没有步骤时退回计划的 `page_from`（[数据库结构过度设计审查](数据库结构过度设计审查.md) 的 S5）；完成一步只改 `plan_item.status`，计划状态随步骤变化在同一条提交里更新，不再多写一次 `study_plan`。步骤因此和普通事项共用预约与完成状态。从已经结束的讨论开始系统学习时，`conversation_id` 指回那条记录。

学习判断只保存来源、结论与依据：`kind` 为 `model` 时是模型给出的判断，`basis` 写模型依据；`kind` 为 `user` 时是用户填写的核对依据，只表示用户提供了一个依据，不标记为已核对。用户自评由 `attempt` 里的帮助次数、独立性与延迟情况推出，独立性只采信用户明确的选择，未选择时为 `NULL`；是否用过帮助由 `help_json` 与独立性声明推出，不再单独保存一列。`attempt.delayed` 标记是否为隔一段时间后重做。`plan_item.priority` 与 `schedule_block.locked` 分别用于容量排序与固定安排：`locked` 为真的块是固定安排，容量规划不移动它；改期只在用户确认本次方案后执行，时间块上不保存授权标记。

### 5.6 插件写入与撤销

插件的启停状态与人格配置写在 `app_meta`，不形成提交，也不出现在数据版本页；整库备份包含这张表，换机恢复之后插件的启停状态与人格配置随之回来，当前数据包不包含它们。人格文本存在同一个键值表里，同一时间只有一条生效，启停与增删都不改写业务表。

能力插件不持有数据库连接，也不拼 SQL。插件产出草稿，由对应的应用服务校验之后在同一个命令事务里写入；一次批量导入形成一条提交，`revision_commit.action` 写清来源，例如课表导入写“导入课表”，回执与数据版本页可以整批撤销，撤销前重新核对与待开始预约的冲突。课表导入有三种来源，即截图识别、ICS 文件与模板表格：识别或解析之后先给出预览，用户确认才写入；截图识别依赖可用的多模态模型，模型不可用时退回手工添加。插件需要新的表、字段或数据包格式时，先改本文件与数据层，再写插件。

### 5.7 数据版本的提交、读取位置与同步冲突

提交的类型由 `revision_commit.kind` 决定，取值为 `baseline`、`write`、`undo`、`restore`、`import`、`maintenance`，`action` 只给人看，撤销判断与界面标签都读 `kind`。初始基线与清理本机历史后保留的那一条是 `baseline`，普通命令是 `write`，撤销是 `undo`，整版恢复与导入分别是 `restore` 与 `import`，清理失效回执与记忆使用统计的冲刷是 `maintenance`。`kind` 只表示这条提交做了什么，来源是另一台设备还是本机只看 `origin_device`，应用远端提交形成的本机提交沿用远端那条提交的类型；同步载荷里的提交对象必须给出 `kind`，缺字段或者取值不在这个集合里时服务端返回 400 `invalid_request`。提交身份只用 `uid`：全局唯一、永不复用，由界面在用户动作开始时生成 UUIDv7 并一路传下来，同一次动作重试时沿用同一个值，远端提交沿用远端的 uid，同步载荷里的 `uid` 字段与服务端去重、远端提交的本机去重都按它判断（[ADR-0053](adr/0053-标识按身份顺序指纹分工并收拢提交标识.md) 决定第 3 条）。写入层按 `revision_commit.uid` 的唯一索引先查，已存在就返回原提交、不再执行写入；不再有按动作名与参数派生的重试编号，也没有两分钟窗口，两次真正独立、参数相同的动作是两个不同的身份，各自形成提交，双击与重复触发由界面的进行中状态负责。首次同步上传的基线提交不落 `revision_commit` 行，它的 uid 以设备标识为命名空间、这一块变更明细的 SHA-256 为名字生成 UUIDv5，同一内容重发得到同一个值。提交编号是本机私有的应用顺序，只增不减，只在真正形成提交、或者命令显式要了回执编号时分配：没有净变化的读写命令不占编号，清理本机历史也不把下一个编号退回去复用；它不出设备，同步载荷里没有任何整数提交编号，新的载荷字段也不得携带它。`byte_length` 记录这条提交变更明细的字节数，留存与容量估算按它求和；变更条数与冲突条数不存列，读取时从 `revision_change` 与 `revision_conflict` 现数。`server_seq` 记这条提交在服务端序列上的序号：远端提交取拉取到的值，本机提交推送成功之后取推送响应里的逐条序号，为空只表示还不知道它排在第几条。撤销提交可以再撤销，重做形成的提交类型仍是 `undo`，`reverted_commit_id` 指向被重做的那条撤销提交，提交在回指链上的层数决定界面显示“撤销”还是“重做”（[ADR-0044](adr/0044-撤销提交可以再撤销.md)）。

提交行还记一致性摘要与作者信息（[改进方案](数据版本系统对照git的改进方案.md) 第 3.5、3.12 节）。`state_digest` 是这条提交落库之后全部业务行的一致性摘要：每一行按“表名、主键、规范化整行”做 SHA-256，整行按列名升序排列、每个值写成 `{"t": 类型, "v": 内容}`，再把这些 256 位整数按 2^256 取模求和，空投影的和是 64 个 `0`；求和与顺序无关，所以采集路径按“减去旧行哈希、加上新行哈希”累加，整库重算按全部业务行求和，两条路径得到同一个值。完整性只认这一个原语，提交不再记 `hash` 与 `parent_hash`，裁剪也不再留下哈希锚点（[数据库结构过度设计审查](数据库结构过度设计审查.md) 的 S1）。摘要按表拆开：同一个和按表分别累加，每张业务表一个 64 位十六进制值，总摘要恒等于各表值之和，没有行的表写 64 个 `0`，两端按同一组键比较；各表值只存在 `revision_state.table_digests_json` 里，每条提交仍只存总摘要，检查点重建时按投影重算，同步载荷里挂在摘要那一侧（[ADR-0054](adr/0054-数据版本位置标记补强.md) 决定第 1 条）。`origin_device` 与 `authored_at` 记作者来源：远端提交填服务端带来的设备标识与创建时间，本机提交这两列为空，界面显示作者时间时退回 `created_at`；数据版本页对远端提交写“来自另一台设备 · 设备标识前 8 位 · 某时某分”，本机提交不写来源，设备标识只显示前 8 位。完整性检查改为重放比对：从最近的检查点把变更明细重放到 `HEAD`，重放得到的摘要必须等于 `HEAD` 记录的 `state_digest`，也等于按当前业务表重算的摘要，不一致时再按表指出是哪几张表；改动业务行、改动变更明细或改动提交记录的摘要都能发现，改动提交身份不再影响这个判断。数据版本页的“检查数据完整性”入口一次跑完重放、摘要与附件核对三项，结果写明通过或者第几处不一致，再给出处理建议，导出版本库备份与上传云端备份之前也会自动跑一次。

同步时两端交换这个摘要（[ADR-0045](adr/0045-同步两端的一致性摘要.md)）。推送结束且本机没有待推送提交时，客户端把当前摘要附在最后一条提交上；这次拉取有被跳过的变化或者已经知道两边不一致时，推送不挂摘要。另一台设备拉到的最新一条提交带着摘要、并且自己也没有待推送提交时，按当前业务表重算摘要并与它比较，读位置与重算之间又写入了本机提交就跳过这一轮。不一致时账号页的同步卡显示“本机与云端不一致”、状态标为“待修复”，给出一个入口“以本机为准重建云端”，并记一条 `cloud_sync_digest` 诊断。这个入口先清空这个账号在服务端的提交序列、快照、设备名册与命名版本，再把本机当前投影整份上传为新的基线，云端备份与附件字节保留；清空之后不再分辨哪边多、哪边少，也不会留下删不掉的行。其他设备发现服务端位置比本机记下的位置小，按首次同步重新对齐，不再要求确认，只补传云端缺少的本机行。摘要只做检测，不自动修复，也不阻塞同步。

应用远端提交的规则比上一版多了列组、唯一键处置与写入顺序三处约束，前两处由表结构里的声明驱动，写在 `tables.dart`。第一，列组整组写入：`timetable_entry` 的起止时间、`schedule_block` 的起止时间、`material` 的文件名与文件哈希三组声明在 `revisionColumnGroups` 里，组里任一列变化时，采集把整组写进变更明细，远端应用也整组写入，本机改过组里的一列、远端改了另一列时，合并出来的行不会违反跨列 CHECK；代价是组的粒度变粗，改一个时间也会把同组的另一个时间写进变更明细。第二，非主键唯一约束按 `revisionUniqueKeys` 的声明分别处置：只表示顺序的列（目前是 `plan_item(study_plan_id, seq)`）遇到唯一键冲突时，把本机占着这个键的行改到同一前缀下的下一个空号，远端这一行照常写入，这次改号随同一条远端提交被采集并登记进 `sync_shadow`，推送时按格遮蔽，两端因此不会互相改写；有含义的唯一键（目前是 `material_page(material_id, page_no)`）跳过远端这一行，记一条 `reason = unique_key_taken` 的冲突，数据版本页对这条冲突只给出“知道了”，用户确认之后删掉记录，不写回任何本机值。代价有两处：只表示顺序的列在两端可能暂时不同，同一个步骤在两台设备上的序号要到下一次汇总或手动调整才一致；一条远端提交的全部变化都被跳过时不形成提交，冲突因此没有可以挂载的提交行，只有 `unique_key_taken` 是例外，它会让本机写一条没有数据变化的提交来承载冲突。

第三处约束是顺序，拉取先把附件字节落库再写业务行：引用附件的业务行（`material.source_file_hash`）有指向 `asset_object` 的外键，先写业务行会在提交时触发外键约束失败，所以客户端按变更明细里的附件引用下载缺失的字节之后才应用这批提交的行变化。出现改号的那一次拉取跳过整库摘要比对：改号让本机投影多出一段云端提交没有表达的变化，按当前表重算的摘要与云端摘要必然不同，这一轮比较没有意义，客户端只记下这次跳过，等下一轮同步再比。远端提交在本机的提交身份沿用远端的 `uid`，服务端把同一条提交重发下来时，本机按这个身份跳过，不会叠加第二次。

暂存表 `rev_stage_<表名>` 不带提交编号列：同一时间只有一个写事务，事务外暂存表总是空的，命令收尾时按整张表合并净变化再清空。`revision_state` 是版本引擎的单行状态：触发器按 `capturing = 1` 且 `suppress = 0` 采集，`capturing` 在命令开始时置 1、收尾时清 0；`active_commit` 只表示已经预留、还没有落库的编号，`next_commit` 是下一个要分配的编号，`head_commit_id` 就是 `HEAD`，指向基线提交时默认的 0 不需要外键。采集上下文与提交编号原来分在 `revision_context` 与 `revision_sequence` 两张单行表，`HEAD` 原来靠名字记在 `revision_ref` 里，这一版合成一张表，`headId` 改成单行直读、不再联表（[数据库结构过度设计审查](数据库结构过度设计审查.md) 的 S3、S14）。打开库时只删除以 `rev_capture_` 开头的触发器，再按当前列重建暂存表，库里别的触发器不受影响。

检查点的业务投影存在 `revision_checkpoint.payload`，按 `json+gzip` 压缩，`raw_bytes` 是压缩之前的字节数；编码不再单独存列，重建时统一按这一种格式解压，另有一份按解压后原文计算的 `checksum` 已随编码分支一起删除，重建时只按投影重算 `state_digest` 并与记录比对，对不上说明检查点本身坏了，不会被当成重建起点（[数据库结构过度设计审查](数据库结构过度设计审查.md) 的 S10、S21）。检查点引用的附件哈希只在 `revision_asset_ref` 里登记一份，写检查点时在同一个事务里插入，回收与核对都从引用表取，不再另外存一份 JSON 清单（S2）。写事务里不再生成整库检查点，一次提交落库、独占区释放之后，距最近检查点累计的变更明细字节数超过阈值时，才在一个单独的维护事务里按当前表生成一份检查点。命名版本只写 `revision_ref`，用 `commit_uid` 指向提交；落在裁剪边界之前时先固化成 `named` 检查点再删除历史，因此命名之后、裁剪之前的重建仍从更早的检查点回放。

历史的每个下游读者在 `revision_cursor` 登记读到哪里：`position` 是已经处理到的提交编号，`blocking` 表示这个读者会丢数据（例如同步推送），裁剪与清理本机历史不能越过它的位置。检索索引与记忆索引也在这张表里登记位置，名字是 `search.index` 与 `memory.index`，`blocking` 为 0，落后时只会退回全量重建，所以它们不阻止裁剪与清理；这两项原来写在索引目录的状态文件里，状态文件现在只保留模型键、维度、数据代次与可发送范围签名，同一版本内产生的旧状态文件仍然能读，里面多出来的提交编号在解析时忽略，位置没有登记时按全量扫描重建再从 `HEAD` 起算。索引结构损坏被重建之后状态文件里没有刷新记录，读取位置也会归零，空集合因此从头重建，不会因为位置停在旧提交而一直空着。同步的两个位置也在这张表里，`sync.pushed` 是会丢数据的一方，`sync.server_head` 只记录服务端最近拉到的位置；退出登录保留该账号空间里的同步位置，再次登录时从原位置继续。删除账号移除整个本机空间，清除全部数据为当前空间重建空库，切换账号打开另一个空间。每个账号与实例组合对应一个空间，所以位置可以直接存入该空间的库（[ADR-0056](adr/0056-本机数据按账号分空间.md) 决定第 9 条）。整库恢复清除备份里的命名版本墓碑，将恢复出的名字标为待同步，并写入 `sync.ref_merge`，下次与服务端合并名字之后再删除该标记。整库恢复把库换成备份那一刻的内容之后，本机补记一条 `restore` 提交，净变化是“恢复点投影 → 恢复后投影”的差异，`sync.pushed` 写成它的父提交，另记 `sync.restore_align` 表示待重新对齐；下一轮手动同步先要求用户确认“云端会改成恢复后的内容”，确认之后跳过拉取，只把这条差异推上去，两个位置收敛到当前服务端位置与本机 `HEAD`，恢复之前的改动不会再从旧位置拉回来。

服务端历史压缩之后，快照浅克隆与重新克隆改变本机投影与两个同步位置的写法（[ADR-0046](adr/0046-客户端按快照浅克隆与重新克隆.md)）。首次同步还没有与这个身份建立同步位置、而服务端保留下界 `earliest_seq` 大于 1 时，第 1 条提交已经读不到，必须先下载快照：附件按 `sha256` 内容寻址，下载之后核对哈希、按 `digest` 核对整库摘要，再按检查点格式导入整库投影，追加一条 `kind = baseline`、动作“从云端快照重建”、变更明细为空的本机提交，并写一份 `initial` 检查点作为之后的回放起点，代次加一、清空 `sync_shadow`。两个位置随后写成 `sync.server_head = 快照位置` 与 `sync.pushed = 本机重建提交编号`：快照之前的提交已经由快照表达，这条重建提交只在本机存在、不上传，之后从快照位置增量拉取，本机未推送的提交按 [ADR-0040](adr/0040-数据版本的提交身份与同步变基.md) 的按格变基去掉被云端遮蔽的格子，在快照之上重放后按普通推送发上去。保留下界为 1 时首次同步仍从第 1 条全量回放，服务端即使有快照也不用。已经有同步位置的设备拉取越过保留下界时，服务端返回 410 `history_compacted`，客户端在本机 `HEAD` 大于 0 且用户没有确认之前不改写本机数据，确认之后按同一路径重建。服务端位置大于 0、没有待推送提交、没有跳过的变化与已知摘要不一致、并且服务端在 `head` 里声明压缩已打开时，客户端在同步收尾时把当前投影压缩上传为附件并登记 `{seq, sha256, digest}`，`digest` 用整库摘要、登记前核对本机 `HEAD` 记录的摘要；同位置或更新位置已有快照、同一份内容本进程登记过、附件已经存在时跳过，服务端据此压缩提交序列，声明为关闭时客户端不上传快照。服务端登记新快照时把被替换的旧附件记为待回收，过了宽限期由下一次登记删除对象存储字节与附件索引行；删除提交之前还要求设备名册里最近同步过的设备都声明了能处理历史压缩（[ADR-0047](adr/0047-快照附件回收与压缩前的客户端门槛.md)）。提交里的设备标识对应账号的设备名册，别名由用户在账号页设置，数据版本页优先显示别名（[ADR-0048](adr/0048-设备名册与提交来源的别名.md)）。

`sync_shadow` 记录已经被远端提交取代的本机格子，作用相当于 git 的 `pull --rebase`，粒度从行细到格子（[ADR-0040](adr/0040-数据版本的提交身份与同步变基.md)）。应用一条远端提交时，对它真正写进本机的每个格子登记一行：修改登记到列，新增、删除与整行覆盖记整行，`column_name` 用空字符串表示整行变化，因为 SQLite 的唯一约束认为两个 NULL 互不相同，用空字符串才能让整行遮蔽每个格子只留一行。`upto_commit` 取应用这条远端提交之前的本机 `HEAD`，含义是编号不大于它的本机提交在这个格子上的改动作废；同一格子再次登记时取较大的值。遮蔽行与远端提交在本机形成的提交写进同一个事务，所以拉取成功而推送失败之后它仍在库里。推送时按格变基：去掉被遮蔽的格子再推，剩余为空的提交不推，推送位置照常前进；编号大于 `upto_commit` 的本机提交不受影响，同步过程中新写入的修改照常推送。推送位置到达 `upto_commit` 之后删掉对应的行，裁剪与清理本机历史删掉被遮蔽的本机提交之后删掉更早的行，整版恢复、导入与清理本机历史推进代次时整表清空。这张表按 `sync_` 前缀归入同步元数据，不参与版本采集、检查点投影与数据包。

`revision_asset_ref` 登记提交变更明细与检查点引用的附件哈希，附件回收与核对读这张表，不再解码全部变更明细；裁剪、清理本机历史与删除命名版本时一并删除对应的引用行。`revision_conflict` 记录应用远端提交时被覆盖的本机修改：`reason` 取 `concurrent_update`（本机与远端各改了一列）、`deleted_locally`（本机已删、远端还在改，写入仍然跳过）、`insert_collision`（远端新增撞上本机同一主键）、`deleted_remotely_modified`（本机改过、远端删掉了）与 `unique_key_taken`（远端这一行与本机另一行用了同一个有含义的唯一键，写入跳过）五种，`local_json` 是本机原来的值，`remote_before_json` 与 `remote_after_json` 是远端的旧值与新值，`resolved_commit_id` 指回把本机值写回的那条提交；没有可写回本机值的两种（本机已删、唯一键被占）由用户确认之后删掉记录，不形成提交。同步仍然是后到覆盖先到，冲突记录只在本机，服务端看不到。

## 7. 导出、恢复与版本

本地库在同一个 SQLite 文件里保存当前学习数据、业务表的行级变更历史、检查点与附件对象。库文件由 drift 的 `NativeDatabase` 打开，SQLite 使用随包的 `sqlite3`；表结构与索引在 `lib/data/db/drift/tables.dart` 的表类上声明，生成文件入库，建库时一起创建。一次业务写入形成一个提交，当前数据对应 `revision_state.head_commit_id`；每次写入由 `GuardedDatabase` 建立命令事务，命令开始时把 `revision_state.capturing` 置 1，触发器按这个标记把新增、修改、删除及外键级联写进暂存表，收尾时按表和主键合并为净变化，并按“减去旧行哈希、加上新行哈希”算出这次命令对各表摘要的增量，业务行、附件对象、版本明细与 `HEAD` 在同一事务提交，`HEAD` 与各表摘要写在同一次更新里。只有真正形成提交才占提交编号：普通命令没有净变化时不形成提交、不占编号，要求回执的命令在预留编号时就定下这次提交的编号，编号只增不减，清理本机历史也不退回复用。带提交身份 `uid` 的写入在重试时不再执行，调用方按 `revision_commit.uid` 的唯一索引取回原提交并返回同样的结果，避免重复形成提交。版本化表在 `GuardedDatabase` 的 insert、update、execute 与 rawInsert 入口拒绝 `REPLACE`，因为 `REPLACE` 隐式删除的旧行可能不触发删除采集；本机诊断记录独立保存在 `filesDir`，SQLite 异常只记录数字错误码，两类数据包和版本历史均排除诊断文件，远端采集范围见 [ADR-0006](adr/0006-诊断报告的采集范围.md)。界面回执保存的是提交编号：讨论卡片、学习页、安排页与材料详情的撤销都读提交历史，没有业务净变化的写入不形成提交，也不会留下可撤销的回执。数据版本页按完整历史列出提交、展开比较并撤销或重做，撤销提交按回指链层数显示“撤销”或“重做”，提交的类型读 `kind`，动作文案只作说明；远端提交的来源写成“来自另一台设备 · 设备标识前 8 位 · 某时某分”，时间取 `authored_at`、没有时退回 `created_at`，本机提交不写来源。

保留版本从最近的检查点开始重建：检查点保存业务投影与投影摘要，附件清单只记在 `revision_asset_ref` 里，之后按提交顺序应用带类型的行级净变化，应用前核对预期旧值，遇到摘要不符或值不一致就停止。检查点的投影按 `json+gzip` 压缩存储，编码不单独存列，重建时按这一种格式解压之后重算摘要并与记录比对。写事务里不生成检查点：一次提交落库、独占区释放之后，距最近检查点累计的变更明细字节数超过阈值时，才在一个单独的维护事务里按当前表生成一份检查点，那一次写入不再顺带重建整库投影。查看、比较、命名与单项撤销都走这一份投影和差异计算；两个提交都在保留历史内时，比较按“表名＋主键”合并这两个提交之间的净变化，起点已被裁掉或中间有清理本机历史留下的基线跳变时，退回按检查点重建两边再比较，与当前版本比较时 `HEAD` 一侧直接读当前表。恢复优先走增量路径：目标提交仍在保留历史内、`foldChanges(目标提交, HEAD)` 能算出净变化时，把它反过来逐行写回当前表，修改只写发生变化的列，新增与删除只动有差异的行，外键检查延迟到事务提交，删除按依赖逆序、插入按依赖正序；这些写入经过同一套触发器采集，恢复提交的变更明细与一致性摘要由此自然产生，写完分批核对被改到的行等于目标值，并把“父提交摘要加采集增量”与目标提交记录的摘要比对，通过才落提交。因此只差几行的恢复不再整库删除重插，没有改到的行保持原来的 `rowid`。起点已被裁掉、中间有清理本机历史留下的基线跳变或某条提交的变更明细不完整时，`foldChanges` 不可用，恢复退回整库替换：在同一个命令事务里按依赖逆序清空版本化业务表，再按正序装入经过校验的目标投影，变更明细由两份投影比较得出；反向写入撞上唯一键互换这类中间状态时也在同一个事务里退回整库替换，结果同样正确。恢复和导入推进数据代次，单项撤销只限当前代次，并核对相关字段在目标提交之后是否又被修改。

对外的两类数据包分开。当前数据包只包含干净的业务投影与仍被引用的附件，导入时先取当前 `HEAD`，提交时重新核对，通过后追加一条提交；版本库备份是 `VACUUM INTO` 生成的整库快照，包含 `HEAD`、保留历史、命名版本与附件，恢复前先在暂存处核对数据库完整性、schema、声明的 `HEAD`、从 `HEAD` 重建业务投影以及全部附件哈希，通过后才交回现有恢复流程替换连接。两个恢复入口先预检再确认：本机版本恢复用 `previewRestore` 列出新增、修改与删除的数量，预览与恢复读同一份净变化，只在退回整库替换时才比较两份投影；数据包恢复在替换前读出包内 `HEAD`、提交条数、命名版本数与当前库规模；整库恢复在替换之前把当前状态保存成一份版本库备份，写入 `filesDir/restore_points/`，恢复成功后保留，数据版本页可以回到恢复前，最多保留最近 5 份，恢复点写不出来时中止本次恢复。恢复点是应用私有目录里的文件，与导出、备份的包分开，不随数据包导出或恢复，清空全部记录时一起删除。两类数据包都排除诊断记录与密钥。读取包内条目前先按压缩头执行一份包级预算：压缩包不超过 256 MiB，条目数不超过 20000，`zhixin.db` 解压后不超过 256 MiB，单个附件不超过 32 MiB，累计解压不超过 512 MiB，累计解压与压缩包大小之比不超过 100；超限的包在读取任何条目内容之前拒绝，当前库不动。导出前按数据库引用核对附件，读不出或哈希不符时中止并列出缺项，不生成缺图的包；版本库备份的附件校验同时覆盖检查点、变更明细与当前投影。备份版本库与上传云端备份之前还会自动跑一次完整性检查，检查范围是从最近的检查点把变更明细重放到 `HEAD`、重放摘要与 `HEAD` 记录及按当前表重算的摘要比对、附件核对；发现不一致时先把第几处不一致与处理建议说明白，再由用户决定取消还是继续导出，继续导出不会改动本机数据，但备份里可能缺内容。

历史按时间优先保留，同时受 256 MB 容量预算与 500 条提交的维护阈值约束。保留天数默认 14 天，可以在数据版本页选择 7、14、30、60、90、180 天：最近这么多天的提交全部保留，覆盖撤销与回执的使用窗口；更早的提交在预算之内继续保留，超出预算时从最早的开始删。提交条数超过 500 条或历史字节（提交变更明细与检查点压缩后长度之和）超过 256 MB 时，在空闲检查点的同一个位置按这套边界自动裁剪一次，不新增定时器，也不在写事务里执行；保留天数存在 `app_meta`，自动裁剪与手动裁剪共用同一套边界计算，两边的结果因此一致。裁剪的下界同时不能越过会丢数据的读取位置中最小位置加一，因此同步还没有推到的提交不会被删掉；会丢数据的读取位置落后于 `HEAD` 时清理本机历史直接拒绝，并说明“还有 N 条修改没有同步到云端，先同步再清理”。裁剪前先生成新基线并立即重建校验，校验失败就取消本次清理；跨越裁剪边界的命名版本先固化为独立检查点再删除历史；裁剪之后更早的提交不再在库里，重放只从下界处的检查点起步，不追溯下界以前的历史。删除后的页空间不会自动归还，数据库超出预算时整库只压缩一次，不再逐次减半循环。附件回收读 `revision_asset_ref` 与当前投影的哈希，不再解码全部变更明细与检查点清单；裁剪、清理本机历史与删除命名版本时一并删除对应的引用行。

同步位置存在库里的 `revision_cursor`，不带账号归属：`sync.pushed` 是会丢数据的一方，落后于 `HEAD` 时阻止清理本机历史并让裁剪保留下界停在它之后；`sync.server_head` 只记录服务端最近拉到的位置。一个库只属于一个账号与实例，退出登录与重设密码保留该空间的同步位置，删除账号或清除全部数据时随空间移除。整库恢复把库换成备份那一刻的内容之后，本机补记一条 `restore` 提交，净变化是“恢复点投影 → 恢复后投影”的差异，`sync.pushed` 写成它的父提交，另记 `sync.restore_align` 表示待重新对齐；下一轮手动同步先要求用户确认“云端会改成恢复后的内容”，确认之后跳过拉取，只把这条差异推上去，删除、新增与修改都会到达其他设备，两个位置收敛到当前服务端位置与本机 `HEAD`，恢复之前的改动不会再从旧位置拉回来。应用远端提交时按列做三方比较，仍然写入远端值，把被覆盖的本机修改写进 `revision_conflict`，提交的冲突条数在读取时现数；维护列 `updated_at` 不记冲突，冲突记录只留内容列。本机可以在数据版本页逐条查看被覆盖的字段与本机原来的值，并把本机值作为一条普通写入提交写回，那条提交照常推送，在其他设备上就是一次正常的后到覆盖。同步仍然是后到覆盖先到，服务端不保存冲突记录，也不替客户端合并。一次同步先拉取再推送，推送按格变基：编号不大于 `sync_shadow` 里的 `upto_commit` 的本机提交在这些格子上作废，推送时去掉被遮蔽的格子，剩余为空的提交不推，推送位置照常前进，其余改动照常推送，否则本机的旧值会在远端值之后写进服务端，服务端与本机就此不一致。本机已删、远端还在改的那一条（`deleted_locally`）没有可以写回的本机值，确认之后直接删掉记录，不形成提交；远端这一行与本机另一行用了同一个有含义的唯一键时记 `unique_key_taken`，同样没有可以写回的本机值，但应用这一行时本机会写一条没有数据变化的提交来承载冲突，用户确认之后删掉记录，不形成新的提交。顺序列改号、列组整组写入与附件先落库的顺序见第 5.7 节。

同步还会交换整库摘要：推送结束且本机没有待推送提交时，最后一条提交带上当前摘要；拉取到带摘要的最新一条并且本机没有待推送提交时比较，不一致就在账号页的同步卡显示“本机与云端不一致”、给出“以本机为准重建云端”一个入口，并另写一条诊断记录（第 5.7 节、[ADR-0045](adr/0045-同步两端的一致性摘要.md)）。摘要只做检测，不自动修复，也不阻塞同步；重建入口清空服务端序列后整份上传本机投影，云端备份与附件保留，其他设备按首次同步重新对齐。

完整性检查由数据版本页的“检查数据完整性”入口发起：`RevisionEngine.verifyIntegrity` 从最近的检查点把变更明细重放到 `HEAD`，把重放得到的摘要与 `HEAD` 的记录、按当前表重算的摘要各比一次，再按表指出不一致的表名，`verifyAssets` 核对检查点、变更明细与当前投影引用的附件，两项合成一次结果；界面写明检查范围与“通过”或者“第几处不一致”，并给出先不要导出或恢复、到提交历史里找到正确版本恢复这类建议。备份版本库与上传云端备份之前的自动检查走同一个入口，发现不一致时先说明再由用户决定是否继续（[改进方案](数据版本系统对照git的改进方案.md) 第 3.10 节）。

本地库与数据包只认当前版本。库文件的版本与当前结构不一致时，打开时清空旧表并按当前结构重建；恢复入口只接受 manifest、库的 `user_version` 与 `app_meta.schema_version` 都等于当前版本的包，低于或高于当前版本、以及三者不一致的包都在替换前拒绝。应用不写迁移函数，也不保留旧格式分支。这条规则是开发阶段不向下兼容在数据层的具体做法，决策见 [ADR-0002](adr/0002-本地数据不做迁移.md)。schema 32 这次变化同样按这条规则处置：schema 31 的本机空间库在升级之后第一次打开时清空重建，schema 28 的单体布局不打开，`filesDir` 根下的 `zhixin.db`、`question_images/`、`vector_index/`、`memory_index/`、`restore_points/` 与 `data_versions/` 在第一次启动时删除；两类数据包与版本库备份只接受 schema 32，低于或高于 32 的包在替换之前拒绝、原数据保留。本机设置随之回到默认值，需要重新导入材料与课表并重填设置，发版说明写明这些影响（[ADR-0017](adr/0017-表结构变化仍清空数据.md)）。
