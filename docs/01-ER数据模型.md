# 知新 · ER 数据模型

> 本文是数据结构的唯一真相，目标数据库是 SQLite 3，整个应用只有一个本地文件。概念定义以 [00-产品定义](00-产品定义.md) 为准，界面读写以 [02-产品与交互](02-产品与交互.md) 为准，本文只定义表、字段与派生规则。
>
> 当前结构为 schema 26，共 15 张业务表，另有数据版本与附件对象 8 张表：讨论可以独立存在并带入材料页码；一条讨论就是一条学习记录，题目由开始作答时确定的用户消息与图片派生，作答直接挂在这条记录上，不再单独存题目表。题目来源只保留用户写、拍图与模型生成，图片文字由多模态模型直接读出；学习事项只保留一段说明，系统学习的每一步就是学习事项，材料引用先由程序核对，学习判断只保存模型判断与用户提供的核对依据。界面回执存的是提交编号，撤销读提交历史，不再单独保存操作日志。开发期只使用可丢弃的测试数据，本地库与数据包只接受当前 schema 26；版本不一致的旧库在打开时清空重建，其他版本的数据包在恢复入口拒绝。
>
> 本文的 DDL 与 `app/lib/data/db/schema.dart` 保持一致。

## 1. 设计原则

| # | 决策 | 影响 |
|---|---|---|
| D1 | 学习记录独立存在，不关联知识点与题型 | 少一张分类树与两张关联表，用户不必先归类 |
| D2 | 尝试是证据的最小单位 | 同一道题可以有多条尝试，每次记提交、对错、提示、独立与延迟；对错可以留空 |
| D3 | 一次学习用 `study_session` 表示，多次尝试共用一个结果 | 与对话、日程、记忆读同一个标识 |
| D4 | 记忆单独建表，带来源、适用范围与有效期 | 可查看、纠正、删除，临时限制会过期 |
| D5 | AI 的每次写入形成一条数据提交 | 撤销与回执从提交历史读取，不需要单独的日志表 |
| D6 | 错题不建表 | 题目状态由最近一条已提交尝试派生，读时计算 |
| D7 | 时间统一用 TEXT | `YYYY-MM-DD`、`HH:MM`、`YYYY-MM-DD HH:MM:SS`，可直接比较与排序 |
| D8 | 单文件、无账号、无服务端 | 导出 zip 包即备份，换设备靠恢复 |
| D9 | 讨论可以独立存在，不要求目标归属 | 求助不必先建目标，记录按讨论标识打开 |
| D10 | 材料按页保存，引用先由程序核对 | 回答能回到原文位置，对不上的引用标为未核实 |
| D11 | 系统学习的步骤就是学习事项 | 步骤可以和普通事项一样预约、共用完成状态 |
| D12 | 学习判断按来源分别保存 | 模型判断与用户提供的核对依据各自保存结论与依据，两者都不标记是否核对；用户自评由作答记录推出 |

补充两条：所有表带 `created_at`，可变实体再加 `updated_at`；只追加的表（`message`）不设 `updated_at`。图片不进数据库，路径写 `message.image_paths_json`，导出只打包消息仍引用的图片，应用启动时清理没有引用的图片。

## 2. 实体总览

15 张业务表，分五组；数据版本、附件对象与采集暂存表单独列出。

| 组 | 表 | 作用 |
|---|---|---|
| 基础 | `app_meta`、`profile` | 版本、时区与每日截止小时、偏好 |
| 学习 | `learning_goal`、`plan_item`、`schedule_block`、`timetable_entry`、`study_session`、`study_plan` | 目标、事项、时间块、课表、一次学习、系统学习 |
| 题目与讨论 | `attempt`、`conversation`、`message` | 作答、讨论与消息；题目由开始作答时确定的用户消息派生 |
| 材料与评估 | `material`、`material_page`、`assessment` | 材料、材料页、学习判断 |
| 记忆 | `memory` | 记忆；写入与撤销的记录读提交历史 |

```
learning_goal 1 ── n plan_item 1 ── n schedule_block
                     │  └── n study_session 1 ── n attempt
                     └── n study_plan 1 ── n plan_item（学习步骤）

conversation 1 ── n message
conversation 1 ── n attempt（作答直接挂在学习记录上）
conversation 1 ── n plan_item（来源讨论）
material 1 ── n material_page
material 1 ── n study_plan
assessment n ── 1 attempt
memory ── source_kind + source_id ──▶ message / attempt / study_session
revision_change ── table_name + row_key ──▶ 任意业务表
```

## 3. 派生规则

### 3.1 题目状态与错题

不存状态列，读取时按最近一条已提交尝试计算。

| 最近一条已提交尝试 | 题目状态 | 列表位置 |
|---|---|---|
| 没有 | 未作答 | 记录页「最近带入」 |
| `is_correct = 1` | 已解决 | 记录页「做对过」 |
| `is_correct = 0` | 待处理 | 记录页「待处理」，即错题 |

`submitted_at` 为空表示未提交尝试，只挂帮助与草稿，不参与状态计算。同一道题的多次尝试全部保留，界面按时间倒序列出。未提交尝试也可以带一条用户填写的核对依据，作为草稿的一部分；提交时更新同一条判断，不再新增第二条。

### 3.2 一次学习

`study_session` 在用户从讨论、题目或日程开始一次学习时创建，同一场次内的多次尝试共用它。开始时写入所属目标：从学习事项开始时取事项的目标，从讨论开始时取讨论的目标，再次作答同一道题时沿用上次场次的目标，没有归属时留空。开始学习时如果提供了学习事项，就按 `plan_item_id` 匹配未结束场次；没有提供学习事项时，才按 `goal_id` 精确匹配，其中空目标只匹配空目标。这样不同学习事项或目标下的场次不会互相复用。离开学习页时写 `ended_at`，按本次已提交的尝试推出 `outcome`：最近一次答对为完成，最近一次答错但本次有答对为部分完成，本次都没有答对为没做成，没有提交过时结果留空；本次最近一条写下的困难同时写进 `summary`。`plan_item.status` 不在学习结束时回写，结束事项由事项自己的完成操作负责。再次进入同一题目时接着未提交的尝试与草稿，但已结束的场次不复用，会新建场次。

### 3.3 记忆检索

生成回答或建议时只取满足以下条件的记忆：`status = 'active'`，`valid_until` 为空或不早于当前时刻，并且 `scope` 为空或等于本次目标（`goal:<id>`）或材料（`material:<id>`）。再按本次用途选取：规划先取适用于本次的时间限制与偏好，讲解先取讲解偏好与本题困难，检查先取带来源的近期进展；约束先占预算，其余条目按记忆正文的查询相关性排序，相关程度相同时再按 `updated_at` 倒序，最多 40 条。用户本轮明确说出的条件优先于旧偏好。单条记忆进入提示词时超过 200 字截断。待确认的记忆提案不写在 `memory` 表里，用户确认之前不进入召回；困难与进展在写入时记录本次目标或材料的范围，偏好与限制不写范围、始终保持全局，因此其他目标的困难不会进入回答。与当前题目、事项的精确关联留到后续版本；现在先保证不把全量记忆与整段对话塞进上下文。

用户修改或删除记忆时，直接更新 `memory.content`，或把 `status` 改为 `superseded`、`deleted`；后续检索不得再取用旧内容。用户对记忆的这些修改不另写追溯记录，回答只读当前有效内容。

### 3.4 建议与本地兜底

有模型时由模型给出 1–3 条下一步，每条写清做什么与做到什么算结束，材料出处与题号写在标题或动作里，不单独建列。模型未配置、调用失败或没有给出正文时，按固定顺序给一条：

1. 今天已经排定且未完成的时间块；
2. 截止最近的待办事项；
3. 最近一条待处理题目。

兜底结果标明“本地建议”，不伪装成模型回答。

### 3.5 撤销

一次业务写入就是一条提交，`revision_change` 保存这次提交里的行级净变化：新增记修改后的整行，删除记删除前的整行，更新只记发生变化的列。撤销时在同一个事务里重新读取目标提交与当前行，核对目标提交之后同一行没有又被修改、当前值仍等于提交后的值、恢复后的时间不与课表或别的预约冲突，全部通过才按反向写入并追加一条撤销提交；撤销新建的学习事项前还要确认它没有时间块、学习场次或系统学习计划归属，避免级联删除后续数据。一条提交只能撤销一次，撤销提交本身不再进入撤销范围，需要回到更早的状态时用整版恢复；整版恢复或导入之后更早的提交也不再进入撤销范围。现在覆盖目标、记忆、时间块、学习事项、每日截止小时与消息里的回执字段，新增或删除消息本身仍不进入撤销，破坏性操作先在界面上确认。每日截止小时写在 `profile` 一行，撤销后应用根重新读取设置，界面与归属日口径都使用撤销后的值。记忆页的新增、修改与删除同样形成提交，提示条给出撤销；撤销修改写回内容与有效期，撤销删除把状态改回 `active`，撤销新增移除这一行，内容与有效期都没有变化时不形成提交。讨论卡片与安排页的即时回执保存提交编号，重新打开时按提交是否仍可撤销决定按钮是否出现；消息里的回执字段不整行回滚，撤销只清掉指向那次提交的条目，同一消息里更晚留下的回执不会被一并抹掉。数据版本页按完整提交历史列出变更、展开比较并撤销，列表与撤销入口共用同一份结构判断，不能撤销的提交直接禁用并写出原因，安排页只列记忆写入、确认记忆与接受下一步建议三类提交。清理历史或裁剪之后，消息里指向已无变更明细的提交回执会去掉提交编号；回执清理本身作为一条普通提交写入，检查点重建与当前数据因此保持一致。

## 4. 完整 DDL

```sql
PRAGMA foreign_keys = ON;
PRAGMA journal_mode = WAL;

CREATE TABLE IF NOT EXISTS app_meta (
  key         TEXT PRIMARY KEY,
  value       TEXT NOT NULL,
  updated_at  TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS profile (
  id                   INTEGER PRIMARY KEY CHECK (id = 1),
  day_cutoff_hour      INTEGER NOT NULL DEFAULT 4 CHECK (day_cutoff_hour BETWEEN 0 AND 6),
  created_at           TEXT NOT NULL,
  updated_at           TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS learning_goal (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  title       TEXT NOT NULL,
  scope_text  TEXT,
  due_date    TEXT,
  status      TEXT NOT NULL DEFAULT 'active'
              CHECK (status IN ('active', 'paused', 'done')),
  created_at  TEXT NOT NULL,
  updated_at  TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS material (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  title       TEXT NOT NULL,
  kind        TEXT NOT NULL DEFAULT 'text'
              CHECK (kind IN ('text', 'slides', 'book', 'other')),
  source_ref  TEXT,
  source_file_name TEXT,
  source_file_hash TEXT REFERENCES asset_object(hash),
  goal_id     INTEGER REFERENCES learning_goal(id) ON DELETE SET NULL,
  created_at  TEXT NOT NULL,
  updated_at  TEXT NOT NULL,
  CHECK ((source_file_name IS NULL) = (source_file_hash IS NULL))
);

CREATE TABLE IF NOT EXISTS material_page (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  material_id INTEGER NOT NULL REFERENCES material(id) ON DELETE CASCADE,
  page_no     INTEGER NOT NULL CHECK (page_no > 0),
  label       TEXT,
  content     TEXT NOT NULL,
  created_at  TEXT NOT NULL,
  updated_at  TEXT NOT NULL,
  UNIQUE (material_id, page_no)
);

CREATE TABLE IF NOT EXISTS conversation (
  id                   INTEGER PRIMARY KEY AUTOINCREMENT,
  title                TEXT,
  goal_id              INTEGER REFERENCES learning_goal(id) ON DELETE SET NULL,
  material_id          INTEGER REFERENCES material(id) ON DELETE SET NULL,
  page_no              INTEGER,
  source_ref           TEXT,
  context_text         TEXT,
  question_message_id  INTEGER,
  entry_kind           TEXT NOT NULL DEFAULT 'text'
                       CHECK (entry_kind IN ('text', 'photo', 'text_photo')),
  status               TEXT NOT NULL DEFAULT 'open'
                       CHECK (status IN ('open', 'ended')),
  ended_at             TEXT,
  last_message_at      TEXT,
  created_at           TEXT NOT NULL,
  updated_at           TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS message (
  id               INTEGER PRIMARY KEY AUTOINCREMENT,
  conversation_id  INTEGER NOT NULL REFERENCES conversation(id) ON DELETE CASCADE,
  role             TEXT NOT NULL CHECK (role IN ('user', 'assistant', 'system')),
  content          TEXT NOT NULL,
  image_paths_json TEXT,
  structured_json  TEXT,
  created_at       TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS study_plan (
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  material_id     INTEGER REFERENCES material(id) ON DELETE SET NULL,
  goal_id         INTEGER REFERENCES learning_goal(id) ON DELETE SET NULL,
  conversation_id INTEGER REFERENCES conversation(id) ON DELETE SET NULL,
  title           TEXT NOT NULL,
  page_from       INTEGER,
  page_to         INTEGER,
  current_page    INTEGER,
  status          TEXT NOT NULL DEFAULT 'active'
                  CHECK (status IN ('active', 'paused', 'done')),
  created_at      TEXT NOT NULL,
  updated_at      TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS plan_item (
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  goal_id         INTEGER REFERENCES learning_goal(id) ON DELETE SET NULL,
  conversation_id INTEGER REFERENCES conversation(id) ON DELETE SET NULL,
  study_plan_id   INTEGER REFERENCES study_plan(id) ON DELETE CASCADE,
  seq             INTEGER CHECK (seq IS NULL OR seq > 0),
  title           TEXT NOT NULL,
  note            TEXT,
  page_from       INTEGER CHECK (page_from IS NULL OR page_from > 0),
  page_to         INTEGER CHECK (page_to IS NULL OR page_to > 0),
  due_at          TEXT,
  est_minutes     INTEGER CHECK (est_minutes IS NULL OR est_minutes BETWEEN 5 AND 240),
  priority        INTEGER NOT NULL DEFAULT 0 CHECK (priority BETWEEN 0 AND 2),
  status          TEXT NOT NULL DEFAULT 'todo'
                  CHECK (status IN ('todo', 'doing', 'done', 'deferred')),
  source          TEXT NOT NULL DEFAULT 'user' CHECK (source IN ('user', 'ai')),
  origin_json     TEXT,
  completed_at    TEXT,
  created_at      TEXT NOT NULL,
  updated_at      TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS timetable_entry (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  weekday     INTEGER NOT NULL CHECK (weekday BETWEEN 1 AND 7),
  start_time  TEXT NOT NULL,
  end_time    TEXT NOT NULL,
  title       TEXT NOT NULL,
  location    TEXT,
  created_at  TEXT NOT NULL,
  updated_at  TEXT NOT NULL,
  CHECK (end_time > start_time)
);

CREATE TABLE IF NOT EXISTS schedule_block (
  id            INTEGER PRIMARY KEY AUTOINCREMENT,
  plan_item_id  INTEGER NOT NULL REFERENCES plan_item(id) ON DELETE CASCADE,
  start_at      TEXT NOT NULL,
  end_at        TEXT NOT NULL,
  source        TEXT NOT NULL DEFAULT 'user' CHECK (source IN ('user', 'ai')),
  status        TEXT NOT NULL DEFAULT 'planned'
                CHECK (status IN ('planned', 'done', 'cancelled')),
  locked        INTEGER NOT NULL DEFAULT 0 CHECK (locked IN (0, 1)),
  created_at    TEXT NOT NULL,
  updated_at    TEXT NOT NULL,
  CHECK (end_at > start_at)
);

CREATE TABLE IF NOT EXISTS study_session (
  id              INTEGER PRIMARY KEY AUTOINCREMENT,
  goal_id         INTEGER REFERENCES learning_goal(id) ON DELETE SET NULL,
  plan_item_id    INTEGER REFERENCES plan_item(id) ON DELETE SET NULL,
  conversation_id INTEGER REFERENCES conversation(id) ON DELETE CASCADE,
  summary         TEXT,
  outcome         TEXT CHECK (outcome IN ('done', 'partial', 'not_done')),
  started_at      TEXT NOT NULL,
  ended_at        TEXT,
  created_at      TEXT NOT NULL,
  updated_at      TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS attempt (
  id                 INTEGER PRIMARY KEY AUTOINCREMENT,
  conversation_id    INTEGER NOT NULL REFERENCES conversation(id) ON DELETE CASCADE,
  session_id         INTEGER REFERENCES study_session(id) ON DELETE SET NULL,
  redo_of_attempt_id INTEGER REFERENCES attempt(id) ON DELETE SET NULL,
  user_answer        TEXT,
  solution           TEXT,
  is_correct         INTEGER CHECK (is_correct IN (0, 1)),
  independent        INTEGER CHECK (independent IN (0, 1)),
  delayed            INTEGER NOT NULL DEFAULT 0 CHECK (delayed IN (0, 1)),
  help_json          TEXT,
  feedback           TEXT,
  submitted_at       TEXT,
  created_at         TEXT NOT NULL,
  updated_at         TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS assessment (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  attempt_id   INTEGER NOT NULL REFERENCES attempt(id) ON DELETE CASCADE,
  kind         TEXT NOT NULL CHECK (kind IN ('model', 'user')),
  result       TEXT NOT NULL,
  basis        TEXT,
  created_at   TEXT NOT NULL,
  updated_at   TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS memory (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  kind         TEXT NOT NULL
               CHECK (kind IN ('preference', 'constraint', 'difficulty', 'progress')),
  content      TEXT NOT NULL,
  scope        TEXT,
  source_kind  TEXT NOT NULL CHECK (source_kind IN ('user', 'message', 'attempt', 'session')),
  source_id    INTEGER,
  valid_until  TEXT,
  status       TEXT NOT NULL DEFAULT 'active'
               CHECK (status IN ('active', 'superseded', 'deleted')),
  created_at   TEXT NOT NULL,
  updated_at   TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS revision_commit (
  id                  INTEGER PRIMARY KEY AUTOINCREMENT,
  parent_id           INTEGER REFERENCES revision_commit(id) ON DELETE SET NULL,
  generation          INTEGER NOT NULL,
  actor               TEXT NOT NULL CHECK (actor IN ('user', 'ai', 'system')),
  action              TEXT NOT NULL,
  request_id          TEXT,
  restored_commit_id  INTEGER,
  reverted_commit_id  INTEGER,
  change_count        INTEGER NOT NULL DEFAULT 0,
  created_at          TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS revision_change (
  commit_id    INTEGER NOT NULL REFERENCES revision_commit(id) ON DELETE CASCADE,
  seq          INTEGER NOT NULL,
  table_name   TEXT NOT NULL,
  row_key      TEXT NOT NULL,
  op           TEXT NOT NULL CHECK (op IN ('insert', 'update', 'delete')),
  before_json  TEXT,
  after_json   TEXT,
  PRIMARY KEY (commit_id, seq)
);

CREATE TABLE IF NOT EXISTS revision_ref (
  name        TEXT PRIMARY KEY,
  commit_id   INTEGER NOT NULL,
  note        TEXT,
  created_at  TEXT NOT NULL,
  updated_at  TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS revision_checkpoint (
  id                INTEGER PRIMARY KEY AUTOINCREMENT,
  kind              TEXT NOT NULL
                    CHECK (kind IN ('initial', 'periodic', 'trimmed', 'named')),
  commit_id         INTEGER NOT NULL,
  projection_json   TEXT NOT NULL,
  asset_hashes_json TEXT NOT NULL,
  checksum          TEXT NOT NULL,
  created_at        TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS revision_context (
  id            INTEGER PRIMARY KEY CHECK (id = 1),
  active_commit INTEGER,
  suppress      INTEGER NOT NULL DEFAULT 0 CHECK (suppress IN (0, 1))
);

CREATE TABLE IF NOT EXISTS revision_sequence (
  id          INTEGER PRIMARY KEY CHECK (id = 1),
  next_commit INTEGER NOT NULL
);

CREATE TABLE IF NOT EXISTS asset_object (
  hash         TEXT PRIMARY KEY,
  byte_length  INTEGER NOT NULL CHECK (byte_length >= 0),
  created_at   TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS asset_chunk (
  hash  TEXT NOT NULL REFERENCES asset_object(hash) ON DELETE CASCADE,
  seq   INTEGER NOT NULL CHECK (seq >= 0),
  data  BLOB NOT NULL,
  PRIMARY KEY (hash, seq)
);
```

数据版本之外，打开库时按业务表的实际列生成每张表一张采集暂存表（`rev_stage_<表名>`）与新增、修改、删除三个触发器；暂存表只在当前命令事务里存在记录，提交后合并为净变化并清空。

种子数据只有两条，`schema_version` 写入当前版本。

```sql
INSERT OR IGNORE INTO app_meta(key, value, updated_at)
VALUES ('schema_version', '25', datetime('now', 'localtime'));
INSERT OR IGNORE INTO profile(id, day_cutoff_hour, created_at, updated_at)
VALUES (1, 4, datetime('now', 'localtime'), datetime('now', 'localtime'));
```

## 5. 表与字段说明

### 5.1 讨论与消息

讨论按 `id` 打开，日期只用于展示和筛选，不再按天合并成一段对话，因此跨天返回时恢复的是同一条记录。`goal_id` 为空表示无归属，创建讨论不要求先有目标；`goal_id` 只在用户明确选择时写入。`entry_kind` 记录这次求助来自文字、图片还是两者，用于在记录里区分只有原图的讨论。`status` 为 `open` 时出现在“现在”，结束一次讨论写 `ended_at` 与 `ended`；再次发送消息时重新置为 `open`。`last_message_at` 用于记录排序，`title` 取首条用户消息的短标题，只有图片时写“图片求助”。

图片压缩后按内容哈希分块保存在同一库的 `asset_object` 与 `asset_chunk` 里，`message.image_paths_json` 只保存哈希引用，界面读取时从数据库补回 `question_images/` 下的临时文件；只有图片、没有文字时 `content` 是空字符串，界面按图片显示。`structured_json` 保存本次回答是否来自模型、记忆卡片、引用、下一步建议和已接受的建议标题；记忆卡片分别记待确认、已写入与已忽略三种状态，工具调用本身不写入历史。未接受的建议只留在这条消息里，不产生 `plan_item`；推断的记忆在用户点“记下”前不写入 `memory`。

### 5.2 事项与讨论的归属

`plan_item` 在 `goal_id` 之后增加 `conversation_id`，指回产生这项事项的讨论；接受一条下一步建议时，由用户在选择表里明确目标，未选择就不写 `goal_id`。创建事项与在原消息里记下已接受标题在同一条提交里完成，回执保存提交编号，重新打开讨论不会把同一条建议再保存一次，撤销这次提交时已接受的标题一并去掉。创建讨论或事项都不改动既有 `schedule_block`，普通求助不写预约。

题目不再单独存表：一条讨论就是一条学习记录，开始作答时把当时最后一条用户消息记进 `conversation.question_message_id`，题干与图片从这条消息读出，`attempt.conversation_id` 直接指向这条记录。用户先问方法、后来才补完整题目时，后来那条消息成为原题；之后再追问不会改写已经确定的原题。只有图片时消息 `content` 为空，界面按“图片题目”显示，原文仍是原图。讨论里的助手回答不再复制进 `attempt.help_json`，求助时从消息里直接作为帮助带入。清空一条学习记录会删除它的消息与作答，作答随外键级联删除；记录与题目从此只有一个标识。

`study_session.conversation_id` 记录这次学习属于哪条讨论，未结束场次按记录复用；记录上的目标或事项改变时先结束旧场次，再按新的归属新建，已经结束的场次保留原归属。`attempt.solution` 单独保存用户整理的解法，不覆盖答案、帮助与困难；`attempt.redo_of_attempt_id` 指向独立重做时被复查的那次已提交作答，重新打开学习页仍能判断这次是重做，提交时的 `delayed` 由两次作答的实际间隔决定。`attempt.delayed` 仍表示是否间隔后重做，`independent` 只表示用户对独立性的声明，两者不互相推断。

### 5.3 状态约定

`learning_goal.status` 只保留 `active`、`paused`、`done`，分别对应进行中、暂停与结束三个操作；`deferred` 与 `archived` 没有写入方，不再保留。创建新目标不再归档已有目标，多个目标可以同时有效。暂停只改目标状态；用户确认时可以取消这个目标下未开始的弹性安排，固定安排、其他目标的安排、独立讨论与已完成记录保持原样。取消的块状态改为 `cancelled`，不删除原行，目标状态与这些块在同一条提交里写入，撤销这次提交时一起回到暂停前；待取消的预约在事务内按目标重新读取，一次写入，写入行数与清单不一致时整组回滚；改期仍由“排一排”的确认流程处理，改期后状态回到 `planned`。把已取消的预约恢复为待开始时，同样核对课表与其他预约，冲突时保持取消状态并说明原因。

`plan_item.status` 保留 `todo`、`doing`、`done`、`deferred`。`deferred` 由事项的“暂缓”操作写入，恢复待办写回 `todo`；事项的 `moved` 改名为 `deferred`，没有写入方的 `skipped` 不再保留。`schedule_block.status` 保留 `planned`、`done`、`cancelled`，`cancelled` 只由暂停目标时的取消操作写入；时间块的 `moved` 改名为 `cancelled`，没有写入方的 `missed` 不再保留。

所有事项状态变化经过同一服务入口；同一系统学习计划同时最多有一个 `doing` 步骤，设为进行中时会在事务中将其他步骤恢复为待做。新建或改动计划时间块时，在同一事务中检查它是否与其他 `planned` 时间块或课表时段重叠，跨日时按每个自然日核对；已取消或已完成的时间块不占用未来时间。新增课表时同样先核对，按这条课表每周重复的时段逐日比对待开始预约，已经结束的预约不参与，重叠时拒绝写入并指出冲突的那一条预约。

### 5.4 材料、页码与引用

一页一条记录，页码从 1 开始；同一材料同一页码唯一。添加一页只新增，页码已存在时拒绝写入并提示到材料详情更正；导入的一批页码不得重复，出现重复或无效页码时整批拒绝，材料与页码都不落库。用户更正页内文字时更新 `material_page.content`，材料行的 `updated_at` 随同一条提交更新，修改前后的整行留在历史里，旧引用因此不再通过核对。更正保存后可以从提示条撤销，材料详情按页列出更正记录；撤销会核对这一页与材料行在更正之后是否又被修改，通过后整组写回并追加撤销提交。回答里的引用写在 `message.structured_json` 的 `citations` 里，包含材料、页码、逐字摘录与核对结果；程序只在本轮真正提供过的材料页里按页码取回原文，先核对当前版本与提供时一致，再去掉空白逐字比对，本轮没有提供过的页或已经更正的旧原文不进入引用，对不上的保留原文并标为未核实，界面显示“未能核对”。回答上下文只读当前有效的记忆与材料页，检索只使用同一目标或未归属的材料与讨论，其他课程的内容不进入本次上下文。

导入 Word 时，`material.source_file_name` 保存原文件名，`source_file_hash` 指向按 SHA-256 分块保存的附件对象，原文件、材料行和正文片段在同一条提交中写入。`material_page.page_no` 保存从 1 开始的片段顺序，`label` 保存所在标题，讨论、检索与系统学习继续按材料编号和位置编号定位，引用中的 `is_docx` 决定界面显示片段编号。手动粘贴的材料使用用户填写的页码，两个文件字段均为空。

### 5.5 系统学习与学习判断

学习计划只记录材料范围、当前页码与状态；每一步是 `plan_item`，由 `study_plan_id` 指回计划、`seq` 决定顺序、`page_from` 与 `page_to` 标出范围、`note` 保存一段说明，`(study_plan_id, seq)` 唯一。完成一步改的是 `plan_item.status`，计划按进行中或下一条待做步骤前移 `current_page`；步骤因此和普通事项共用预约与完成状态。从已经结束的讨论开始系统学习时，`conversation_id` 指回那条记录。

学习判断只保存来源、结论与依据：`kind` 为 `model` 时是模型给出的判断，`basis` 写模型依据；`kind` 为 `user` 时是用户填写的核对依据，只表示用户提供了一个依据，不标记为已核对。用户自评由 `attempt` 里的帮助次数、独立性与延迟情况推出，独立性只采信用户明确的选择，未选择时为 `NULL`；是否用过帮助由 `help_json` 与独立性声明推出，不再单独保存一列。`attempt.delayed` 标记是否为隔一段时间后重做。`plan_item.priority` 与 `schedule_block.locked` 分别用于容量排序与固定安排：`locked` 为 1 的块是固定安排，容量规划不移动它；改期只在用户确认本次方案后执行，时间块上不保存授权标记。

## 7. 导出、恢复与版本

本地库在同一个 SQLite 文件里保存当前学习数据、业务表的行级变更历史、检查点与附件对象。一次业务写入形成一个提交，当前数据对应 `revision_ref` 中的 `HEAD`；每次写入由 `GuardedDatabase` 建立命令事务，触发器把新增、修改、删除及外键级联写进暂存表，提交时按表和主键合并为净变化，业务行、附件对象、版本明细与 `HEAD` 在同一事务提交。版本化表在 `GuardedDatabase` 的 insert、update、execute 与 rawInsert 入口拒绝 `REPLACE`，因为 `REPLACE` 隐式删除的旧行可能不触发删除采集；诊断记录仍写在 `filesDir` 的独立文件里，只用于排障，保存前清除 SQL 文本、绑定参数与学习正文，不进入版本历史或数据包。带请求编号的写入在重试时不再执行，调用方可以从 `revision_commit.request_id` 取回原提交并返回同样的结果，避免重复形成提交。界面回执保存的是提交编号：讨论卡片、学习页、安排页与材料详情的撤销都读提交历史，没有业务净变化的写入不形成提交，也不会留下可撤销的回执。数据版本页按完整历史列出提交、展开比较并撤销。

保留版本从最近的检查点开始重建：检查点保存业务投影、附件哈希清单与校验值，之后按提交顺序应用带类型的行级净变化，应用前核对预期旧值，遇到断链或值不一致就停止。查看、比较、命名、单项撤销与整版恢复都走这一份投影和差异计算。整版恢复在同一个命令事务里按依赖逆序清空版本化业务表，再按正序装入经过校验的目标投影，追加一条恢复提交；因此唯一键互换这类中间状态也能恢复。恢复和导入推进数据代次，单项撤销只限当前代次，并核对相关字段在目标提交之后是否又被修改。

对外的两类数据包分开。当前数据包只包含干净的业务投影与仍被引用的附件，导入时先取当前 `HEAD`，提交时重新核对，通过后追加一条提交；版本库备份是 `VACUUM INTO` 生成的整库快照，包含 `HEAD`、保留历史、命名版本与附件，恢复前先在暂存处核对数据库完整性、schema、声明的 `HEAD`、从 `HEAD` 重建业务投影以及全部附件哈希，通过后才交回现有恢复流程替换连接。两个恢复入口先预检再确认：本机版本恢复用 `previewRestore` 列出新增、修改与删除的数量，数据包恢复在替换前读出包内 `HEAD`、提交条数、命名版本数与当前库规模；整库恢复在替换之前把当前状态保存成一份版本库备份，写入 `filesDir/restore_points/`，恢复成功后保留，数据版本页可以回到恢复前，最多保留最近 5 份，恢复点写不出来时中止本次恢复。恢复点是应用私有目录里的文件，与导出、备份的包分开，不随数据包导出或恢复，清空全部记录时一起删除。两类数据包都排除诊断记录与密钥。导出前按数据库引用核对附件，读不出或哈希不符时中止并列出缺项，不生成缺图的包；版本库备份的附件校验同时覆盖检查点、变更明细与当前投影。历史同时受保留条数与 256 MB 容量预算约束，裁剪前先生成新基线并立即重建校验，校验失败就取消本次清理；跨越裁剪边界的命名版本固化为独立检查点，附件回收按当前数据、保留提交、检查点与进行中任务的引用计算。

本地库与数据包只认当前 schema 26。库文件的版本与当前结构不一致时，打开时清空旧表并按当前结构重建；恢复入口只接受 manifest、库的 `user_version` 与 `app_meta.schema_version` 都等于 26 的包，低于或高于当前版本、以及三者不一致的包都在替换前拒绝。应用不写迁移函数，也不保留旧格式分支。这条规则是开发阶段不向下兼容在数据层的具体做法，决策见 [ADR-0002](adr/0002-本地数据不做迁移.md)。

## 8. 待验证与待定

- 记忆的语义检索已经接入，召回规则见 [00 第 8 章](00-产品定义.md#8-检索与引用)；原始筛选仍按有效状态、适用范围与更新时间，具体条件见第 3.3 节，真机与真实模型下的召回质量待验收。
- 错误尝试与已解决题目的保留期未定，默认全部保留，导出包随之变大。
- 多设备同步不做；跨设备只靠导出与恢复。
- 间隔复习的间隔序列未定，间隔由用户或搭子按当前安排确定，试用后再定序列。
- 录音与语音转写的原文是否入库未定，当前只存转写结果。
- 图片换机恢复后的显示已经按相对路径实现并用测试覆盖，真机上的原图显示与分享入口仍待验证。
- 材料检索已经接入关键词与语义两路，跨材料的相关内容仍可能漏掉；引用只核对逐字摘录，模型给出相近改写时显示未核实。
- 系统学习、容量规划与学习判断已经实现数据与界面，真实模型生成顺序的质量、可用时段校准与延迟后独立表现的判定标准仍待真机与真实模型验证。
- 暂停目标时可以确认取消该目标未开始的弹性安排，固定安排保留；改期由用户选定事项与时间后执行，按固定或弹性属性自动调整尚未进入首批。
- 预约提醒没有进入本期范围，未实现提醒、通知权限与静音入口。
