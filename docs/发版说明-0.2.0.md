# 0.2.0 发版说明

> 0.2.0 把 0.1.0 之后的功能、那次表结构变化与服务端重建合成一次发出。本版按 [ADR-0017](adr/0017-表结构变化仍清空数据.md) 与 [ADR-0057](adr/0057-服务端改表清空重建.md) 清空客户端各空间的本机库与服务端的全部账号数据，没有迁移，也没有兼容分支，所以表结构、同步契约与服务端库都从这一版统一算起。表结构变化与这次发版绑在一起的理由见 [ADR-0051 的代价与边界](adr/0051-记忆改为自由文本条目并走文档检索路径.md)，服务端整份重建的理由见 [ADR-0057](adr/0057-服务端改表清空重建.md)。发布日期与包的分发方式在发出时补到本节。

## 1. 这次清空了哪些数据

| 位置 | 清空的内容 | 保留的内容 |
|---|---|---|
| 客户端 | 本机的学习记录、图片、语义索引与这个账号空间的设置，升级后第一次打开时按新结构重建；没打开过的空间在下次打开时重建 | 账号与登录状态在 `cloud.json` 与 Keystore 里，不在库里，升级之后照常打开现有空间 |
| 客户端文件布局 | 0.1.0 的 `filesDir/zhixin.db`、`image_cache/` 与 `vector_index/` 这套单体布局换成按空间分目录的 `spaces/<空间标识>/`，旧的单体目录不再读取 | 服务地址、会话与设备标识；外观与学习设置随空间重建为默认值 |
| 服务端 | 全部账号、学习数据、提交序列、快照、设备名册与命名版本，按新的 `schema.sql` 整份重建 | 实例的模型来源、模型、路由与额度配置，以及用量记录与访问日志 |

客户端这一次把表结构变化合并成一次：完整性只留整库摘要一个原语，检查点去掉重复的校验列，单行状态表与 `HEAD` 合表，记忆改成三类标签并记录使用统计，提交身份只用 `uid` 并新增云端序号与分表摘要，命名版本改按 `uid` 引用并随账号同步。服务端同期合并两张每账号一行的表、删掉让位表、`request_id` 改按 `uid` 去重、设备名册改布尔能力列并记录已同步位置、新增命名版本表。两端都只做清空重建，不写按列的迁移脚本，逐条范围见[数据库结构过度设计审查](数据库结构过度设计审查.md) 第 8 节。

## 2. 升级之后要做什么

1. 重新注册并登录。服务端的账号已经随库重建清空，旧账号与旧密码都不再存在。
2. 重新导入课表与材料。需要留下的学习记录、图片与讨论，请在升级之前用 0.1.0 导出数据包或备份版本库，留作核对；0.1.0 的包不能直接导回 0.2.0，恢复入口只接受当前结构（客户端 schema 31）的包，版本不一致的包在替换之前被拒绝，原数据保留。
3. 把同一账号在其他设备上也升级到 0.2.0。同步契约把推送与拉取载荷里的 `request_id` 改名为 `uid`，并增加逐条序号与可选的分表摘要，旧客户端与新服务端互不认识，两端要一起升级；服务端用 `/readyz` 报告的 schema 版本判断，版本不一致时直接说明两端要一起升级。
4. 重新设置。学习设置（截止小时、保留天数、拍照方式、人格）与外观都随空间保存，空间重建之后回到默认值。

## 3. 这一版改了什么

- 本地库按账号分空间：一个账号一个空间，切换账号不再把上一份记录带过去，也不反复整份上传；退出登录可以保留或删除这个账号在设备上的数据，“清除云端数据”改名为“清除全部数据”，“清理历史”改名为“清理本机历史”（[ADR-0056](adr/0056-本机数据按账号分空间.md)）。
- 命名版本随账号同步，换设备之后能看到名字；名字指向的提交已经不在本机时显示为“只剩标签”，注明该版本的历史不在本机，需要长期保留时请导出版本库备份（[ADR-0054](adr/0054-数据版本位置标记补强.md)）。
- 一致性摘要按表拆开比较，不一致时账号页写明哪几张表不同，“以本机为准修复”只补传不一致的表（[ADR-0054](adr/0054-数据版本位置标记补强.md)）。
- 数据完整性检查改为从最近的检查点重放到 `HEAD` 比对摘要，不再维护提交哈希链（[数据库结构过度设计审查](数据库结构过度设计审查.md) S1、S10）。
- 记忆改为自由文本条目，按情景、语义、程序三类组织，删除改为改状态；写入查重、主动搜索与“很久没用到”的整理建议要用的字段与使用统计已经建好（[ADR-0051](adr/0051-记忆改为自由文本条目并走文档检索路径.md)）。

## 4. 这一版还没做的

- 记忆的三工具增改删、写入时合并近似条目、`search_memory`、三层召回预算与“很久没用到”的整理建议排在 M3，按[长期记忆整理方案](长期记忆整理方案.md#6-实施顺序)的顺序推进；这一版先把表建好，写入仍限 200 字。
- 服务端快照压缩的代码已经接入，剩下在测试实例打开 `ZHIXIN_SYNC_COMPACT`、两台设备走查之后打开生产开关，客户端按快照浅克隆与重新克隆在开关打开之后才会用到；设备位置门槛与分表摘要已经就位，现状见 [04 第 3 节 M1](04-长期路线图.md#m1-验收与内测包)。
- 记忆的语义检索按 ADR-0051 决定第 10 条沿用全文检索，预约提醒与日程导出按 [ADR-0020](adr/0020-预约提醒用本地通知与日程导出用ICS.md) 排在后面，本版表结构不为它们预留列。

## 5. 验证与已知问题

客户端的静态检查与全量单元测试（本机 1224 个用例）、服务端的 `gofmt`、`go vet` 与全量测试在推送之前都通过；V1–V11 在模拟器上的逐条记录按 [02 第 8.5 节](02-产品与交互.md#85-模拟器冒烟记录) 补写，新增的三类记忆分栏、命名版本“只剩标签”与两个改名后的危险操作还没有逐条记录。Windows 开发机上的账号页全量用例曾出现既有停滞，合入时以 Linux CI 的结果为准。
